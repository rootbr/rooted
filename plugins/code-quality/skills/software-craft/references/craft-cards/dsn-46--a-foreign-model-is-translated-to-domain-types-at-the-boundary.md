# Code that exchanges data with a system whose model differs in meaning translates between the two models in a layer at that boundary, so the rest of the code works only with its own domain types

## Thesis
Where code exchanges data with another system whose model differs in meaning from the local one — an external service, any system the team does not control, or legacy code inside the same application — a translation layer stands between the two. Toward that system the layer conforms to its data model or methods, toward the rest of the code it uses only the local data model, and it holds all the logic necessary to translate between the two models. The rest of the code receives and hands over values of its own domain types, so the other system's data model — its types, its data schema and its API — stays inside the translation layer and out of the local logic.

## Rationale
Keeping access to a legacy system forces the new code to adhere to at least some of that system's APIs or other semantics, and may make it support outdated infrastructure, protocols, data models or APIs it would not otherwise contain; legacy systems often have quality problems such as convoluted data schemas or obsolete APIs, and where they do, that support corrupts a design that would otherwise be clean. Similar problems can arise with any external system the team does not control: its data schema or API might leak into the application, and the leakage can compromise the application's design. A layer that translates between the two lets the other system stay unchanged without compromising the local design; its purpose is to ensure that the dependency on the outside system does not limit that design and to protect the local model from changes in the other system's model. While a legacy and a new system coexist during a migration and call each other, cross-system dependencies without such an adapter can break components or force the new system to adopt the legacy conventions; the adapter protects the new design from legacy semantics.

## Example
```java
bad:  import com.acme.legacy.crm.CustRecDto;
      CustRecDto rec = legacyCrm.fetchCust(id.value());
      if (rec.getStatCd().equals("A") && rec.getCrLmt() >= order.total()) { approve(order); }
good: Customer customer = customers.byId(id); // the translation layer maps CustRecDto to Customer
      if (customer.isActive() && customer.canSpend(order.total())) { approve(order); }
```

## Limits
The rule does not reach a system whose model has no significant semantic differences from the local one: there the layer might not be suitable, and where one is kept, it is focused on translation logic, with no business rules or orchestration placed in it. The layer has costs of its own: it adds latency to calls between the two systems and one more component or service to manage and maintain. It may be a component inside the application or an independent service, there may be more than one such layer, and it may handle all communication with the other system or only a subset of features; a project context that routes only a named subset of features through the layer rejects the finding for the rest. Code inside the translation layer conforms to the other system's data model or methods by design and is no finding.

## Validator
Grep the hunk for a name from another system's model: a generated client or message type, a data-transfer, request, response or payload type, an import from a generated, legacy or external-system module, and field names or code values read off or written into such a value. Decide whether the changed code belongs to the translation layer — the code that calls that system and maps between its model and the local one — or to local logic: a domain type, a business rule, a decision or a calculation; translation code is no finding. Open the callers of the changed symbols and trace where the foreign value goes: whether a mapping to or from a local domain type stands between the other system and the logic that uses it, or whether the foreign type, its field names or its code values reach that logic, its signatures or its stored state. Compare the two models for the concept at hand: a value in a different unit, a code set whose values do not correspond one to one with the local values, a different granularity or a different meaning is a semantic difference; where the other system's values mean what the local ones mean and differ only in names, nesting or encoding, stop. Validator question: **Does local logic outside the translation layer take in or hand over another system's type, field names or code values for a concept whose meaning in that system's model differs significantly from the local model's?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-46`, severity minor, `file`, `symbol`, `code` = the line from the diff where local logic takes in or hands over the other system's type, field name or code value, quoted verbatim, `fix` = the mapping between the foreign value and a local domain type placed in the layer that talks to that system, and the logic rewritten against that domain type, in the file's language, `rationale` = the other system, the concept whose meaning differs between the two models, and the local code that now depends on the foreign model).
