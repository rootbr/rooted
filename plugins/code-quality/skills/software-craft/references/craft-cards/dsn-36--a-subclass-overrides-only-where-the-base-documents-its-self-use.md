# A subclass or trait implementor overrides an implemented method of another library's type only where that type documents which of its own methods call it

## Thesis
A subclass whose base class is defined in another library, one built and released separately from the subclass (a dependency, the standard library or a built-in type), overrides a method that already has an implementation only where the base class documents its self-use of that method: which of the base class's own methods call it on the same instance. Where that self-use is undocumented, the subclass instead holds an instance of the base type and forwards each call to it, adding its own behaviour in its forwarding methods, or it extends a type whose documentation states which of its methods call each method the subclass overrides. A default method of an interface or trait that calls another method of the same interface is the same self-use, and an implementor that keeps a default method overrides a method that default calls only under the same condition. Embedding offers no such dispatch: a promoted method runs with the embedded value as its receiver, so a method of the same name on the outer type does not change what the embedded value's own methods call, and an outer method written in the expectation that it does breaks the rule.

## Rationale
Methods have no special privileges when calling other methods of the same object, so a method of a base class that calls another method of the same base class may end up calling a subclass's override of it. A subclass that overrides such a method is intertwined with its base class: the two are not composed, and their behaviour cannot be understood independently. Unless the base class lays down which of its methods call which, such a subclass can often be written only by observing the existing pattern of behaviour, and a change to how the base class's methods delegate to each other is very likely to break it. The dependency runs both ways. When an inherited bulk add adds each element in turn through the single-element add, a subclass that counts in its own add and again in a bulk add that then calls the inherited one counts each element added in bulk twice. When a built-in dictionary's constructor and bulk update bypass an overridden item-assignment method, a subclass that normalizes keys in that method keeps unnormalized keys from both, which makes inheriting from the built-in unreliable. Within a single library, built and released as one unit, this dependency can be tolerable, but across library boundaries it is very problematic unless the base class has established firm rules from the beginning; it has frequently been observed that designing a class well for subclassing takes far more effort than designing it for ordinary use, precisely because these rules of delegation need to be laid out if independently designed subclasses are to have any chance of working. A base class can state its rules, as a skeletal implementation does: its documentation describes the implementation of each non-abstract method in detail, each of which may then be overridden where a more efficient implementation exists, and a design check meant for library projects passes an overridable method that carries a doc comment, naming an explanation of its self-use of overridable methods as the good practice for that comment. A class modifier that lets other libraries implement a class but not extend it guarantees that a call from one of its instance methods to another on the same instance invokes a known implementation from the same library, which reduces the fragile base class problem. Forwarding removes the dependency: a forwarded call runs with the held instance as its receiver, so the held instance's own methods reach its own implementations and never the wrapper's, and a wrapper that counts in its add and in its bulk add, forwarding each, counts each element once whatever the held instance's bulk add calls. A default method of an interface or trait can call other methods of the same interface, including those an implementor supplies, so overriding a default that other defaults call re-creates the dependency on how the defaults delegate.

## Example
```rust
bad:  impl Sink for Counted {    // another crate's Sink: overrides default write_line, which default write_lines calls undocumented
          fn write(&mut self, b: &[u8]) { self.out.extend_from_slice(b) }
          fn write_line(&mut self, s: &str) { self.lines += 1; self.write(s.as_bytes()); self.write(b"\n") }
      }
good: impl<S: Sink> Sink for Counted<S> {
          fn write(&mut self, b: &[u8]) { self.inner.write(b) }
          fn write_line(&mut self, s: &str) { self.lines += 1; self.inner.write_line(s) }
          fn write_lines(&mut self, ls: &[&str]) { self.lines += ls.len(); self.inner.write_lines(ls) }
      }
```

## Limits
- Within a single library, where the base class and its subclasses are designed and released together, the dependency can be tolerable. The rule reaches a base class from another library; a project context that names such a base class as co-designed and released with its subclasses rejects the finding.
- Supplying a method that the base type declares abstract or required is the use the base type was built for: a skeletal implementation names the methods a subclass provides, an abstract base class's mixin methods come from inheritance once the required abstract methods are supplied, and a trait's defaults are built on the methods it asks implementors to specify. The rule concerns overriding a method that already has an implementation.
- A subclass that overrides no method its base class's own methods call, and expects none of them to call a method of its own, is outside the rule; so is an implementor that keeps no default method of an interface or trait that calls, or that it expects to call, a default it overrides, as a forwarding implementation that overrides each such default does; and so is an outer type that embeds a value and adds methods without expecting the embedded value to call them.
- Whether a subtype keeps its base type's pre- and postconditions, how deep or wide a hierarchy grows, and how a base class author chooses between designing for extension and closing a class to subclassing are outside the rule.

## Validator
Grep the hunk for an override marker or keyword, a class declared to extend another, a subclass of a built-in or standard container, a call through super to a named method, a trait implementation or a method with a self receiver added inside one, or an embedded field or an exported method added to a type that embeds one. Name the base type and decide whether it is defined in another library than the subclass's own: a dependency, the standard library or a built-in type. Open the base type's definition where the repository or its vendored sources hold it, and its documentation otherwise. For each method the subclass overrides that already has an implementation in the base type, trace which of the base type's own methods call it on the same instance (a bulk operation calling the single-element one, a constructor or update routine assigning entries, a default method calling another method of its interface), and which bypass it although the subclass expects them to route through it. Read the base type's documentation of those methods for a statement of that self-use: an implementation note naming the methods it calls on the same instance, or a documented hook; a table that only lists which methods are abstract and which are inherited does not say which inherited method calls which. For an embedded field, check whether the outer type defines a method named like an embedded method that the embedded value's other methods call, and whether the outer code expects those calls to reach it. Validator question: **Does a subclass override an implemented method of a base type from another library whose own methods call it or are expected by the subclass to call it, or an implementor override a default method of an interface or trait from another library while keeping a default that calls it or that it expects to call it, where that type's documentation does not state that self-use, or does an outer type expect an embedded value's methods to call its own method?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-36`, severity major, `file`, `symbol`, `code` = the overriding or shadowing method's signature line, or the class, impl or embedded-field line that ties the type to its base, quoted verbatim from the diff, `fix` = the subclass rewritten to hold an instance of the base type and forward each call to it with its added behaviour in its own forwarding methods, or to extend a library type whose documentation states which of its methods call each method the subclass overrides, in the file's language, `rationale` = names the base type, the overridden method, the base method that calls or bypasses it, and the undocumented self-use the subclass depends on).
