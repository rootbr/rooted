# Code a change adds or rewrites receives each dependency its tests replace as a constructor argument, parameter or field, and patching a module, global or static binding is kept for code the change does not edit

## Thesis
Production code that a change adds or rewrites (a routine the diff adds, or one whose body the diff edits) receives each dependency its tests replace, such as the system time, the file system, the network, user interaction, a non-deterministic function or global state, as a constructor argument, a parameter or a field holding an object or function value, with the production dependency supplied by default. Rebinding a name at run time (patching a module attribute or an imported name, mocking a module through the test runner, mocking a static method or a constructor, calling a static setter, reassigning a mutable global) is kept for code the change does not edit: third-party code, and existing code put under test during an interim refactoring before it is changed.

## Rationale
Code that interacts with its environment, such as the file system, the network or user interaction, yields tests that pass when first generated but may fail in a different environment; tests on classes that use the system time may have failing assertions when executed at a different time than when they were generated, and separating code from its environment dependencies by bytecode instrumentation reduced the number of unstable generated tests by more than 50% over 100 projects, which shows that such a dependency needs a substitution point, not which form it takes. Developers report that they frequently mock the dependencies that make testing difficult and prefer not to mock classes that encapsulate domain concepts or rules. An object passed in lets the application provide a controlled view of the current instant and time zone, obtaining the time from an object rather than a static method can simplify testing, and passing that object into any routine that requires the current instant is the documented best practice for applications. Global state is unsafe when independent test cases interact with each other through it or when users are tempted to swap it for a test double; the main migration passes dependencies as parameters to constructors, functions, methods or fields on the call chain, and a mutable global, a function pointer included, gives way to dependency injection. Rebinding instead depends on how the code reaches the name: a patch acts where the object is looked up, which is not necessarily where it is defined; a runner's module mock cannot reach a call made from another function in the same file, which the runner documents as intended behaviour and leaves to the application's architecture; and the hoisting of module-mock calls that works under one module system fails under another, because static imports are evaluated before looking at the code. For code the author controls, dependencies made explicit and passed into the code under test are a safer long-term pattern than a global patch. Dependency injection is the documented remedy for both the same-file limit, beside splitting the code into multiple files, and a mutable global, the state through which independent test cases interact.

## Example
```rust
bad:  pub static NOW: RwLock<fn() -> SystemTime> = RwLock::new(SystemTime::now);
      pub fn sign(msg: &str) -> String { stamp(msg, (*NOW.read().unwrap())()) }
      *signing::NOW.write().unwrap() = fixed_time; // in tests/sign.rs
good: pub struct Signer { pub now: fn() -> SystemTime }
      impl Signer {
          pub fn new() -> Self { Signer { now: SystemTime::now } }
          pub fn sign(&self, msg: &str) -> String { stamp(msg, (self.now)()) }
      }
      Signer { now: fixed_time }.sign(msg) // in a test
```

## Limits
The rule is contested, and whether the change edits the code whose dependency a test replaces separates the cases. Where the change adds or rewrites that code, test-runner documentation names explicit dependencies passed into the code under test the safer long-term pattern for code you control, and module-mocking documentation holds that making the application testable is the job of its architecture, not of the test runner. Where the change does not edit that code, mocking-library documentation accepts partial mocks for "code you cannot change easily (3rd party interfaces, interim refactoring of legacy code etc.)" while declining them for new, test-driven and well-designed code, scopes static-method and constructor mocks to the current thread and a user-defined scope, and documents patching the name where the code under test looks it up; a replacement installed at that name is the documented form there, and existing code the change leaves unedited is outside the rule. A hook variable private to its own module and set only by that module's own tests is left undecided and unflagged: a standard library keeps such a variable, holding a production system call by default and swapped by its own package's tests, a style guide's counter-example has the same shape, and no source separates the two. Global state that is logically constant, or behind an API whose observable behaviour is stateless, and that no test swaps, is safe as a direct call, and so is a dependency no test replaces: use of an injected clock is itself optional.

## Validator
Grep the hunk for the triggers: a patch of a module attribute or imported name, a runner-level module mock, a static-method or constructor mock, an assignment to a global or static binding, a static setter, a reassignable function-valued or lock-guarded global. For each hit, open the file and, for a hit on a global or static declaration, the usages of that name across the repository, then name the production routine whose dependency the rebinding replaces or the global supplies, and check in the diff whether the change adds that routine or edits its body. Trace how the routine reaches the dependency: through a constructor argument, a parameter or a field, or through a module, global or static name that a test rebinds. Leave unflagged a replacement for which the routine reading the replaced name is third-party code or code the change leaves unedited (a third-party function that added code calls directly, patched by its test, is still flagged), a hook variable private to its module and set only by that module's own tests, and global state that is logically constant and that no test swaps. Validator question: **Does code the change adds or rewrites reach a dependency its tests replace through a module, global or static name that a test rebinds, rather than through a constructor argument, a parameter or a field?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-18`, severity minor, `file`, `symbol`, `code` = the rebinding line in the test or the global the added code reads, verbatim from the diff, `fix` = the routine taking that dependency as a constructor argument, parameter or field with the production value as its default and the test passing its replacement, in the file's language, `rationale` = the dependency replaced, the name the test rebinds, and that the change edits the code reading it).
