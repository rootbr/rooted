# Research note — Runtime configuration

Topic `runtime-configuration` of group H. Tools and hygiene, domain `tooling`, id prefix `TOOL`. Formulation locators: SW4.8 (SWEBOK Guide V4.0 ch. 4 §4.8; the V3 section of the same number, 'Runtime Configuration and Internationalization', is transcribed at ligurio/swebok-v3 master 3_software_construction.md); PP 'Configuration' (The Pragmatic Programmer, 20th anniversary ed., ch. 5 'Bend, or Break'); the 97 Things essay 'One Binary' (thing_61); The Twelve-Factor App 'III. Config' as a practitioner formulation (heroku/12factor content/en/config.md).

The canon agrees on the core of runtime configuration. SWEBOK V3 §4.8 defines late binding of values at run time. PP Topic 32, One Binary and Twelve-Factor III say to move out of the code only what varies between deploys. TAOUP ch. 10, CLIG, Abseil TotW #45, the SRE Workbook ch. 14 and PP's 'Don't Overdo It' keep options few. The Google and Uber Go guides read configuration at the entry point and pass it explicitly. The SRE Workbook, the Google Go guide and TAOUP's Rule of Repair validate configuration and fail loudly with an actionable message. SWE at Google ch. 14 and 23 and Continuous Delivery ch. 2 test configuration with the code that reads it. The industry disagrees on several points. On the channel, Twelve-Factor's environment variables for all config, credentials included, are opposed for secrets by CLIG, the OWASP Secrets Management Cheat Sheet and CWE-526. TAOUP and CLIG instead pick a channel by the setting's lifetime and apply a fixed precedence. One Binary and CD version configuration apart from the code, while SWE at Google and the SRE book keep it with the code. Live reload is out of scope. Hightower falls back to defaults when the file is missing, while Lau and Shore treat that as an error. For environment variable names, CLIG and Ruff ask for upper case, while POSIX reserves lower-case names for applications. The admissible evidence is one systems-research line: Too Many Knobs (FSE 2015), Spex (SOSP 2013), PCheck (OSDI 2016), the ACM CSUR 2015 survey, ctest (OSDI 2020) and ConfigX (OOPSLA 2021). Tool rules add Sonar S1313/S1075/S4507, PMD AvoidUsingHardCodedIP and SpotBugs DMI_HARDCODED_ABSOLUTE_FILENAME. Standards add ASVS 13.4.2 and CWE-214, CWE-489 and CWE-526. Platform documentation adds ECMA-262 parseInt, Java Boolean.parseBoolean, Python configparser and argparse, Go flag and os, and Node util.parseArgs. Together they back eleven cards. They cover environment-specific endpoints and paths kept out of code, reading configuration at the entry point, adding no option nobody must choose, no secret on a command line, debug off by default, documented option constraints, checking every value at start-up, a start-up error that names the setting, rejecting rather than overruling an invalid value, reporting a setting that is ignored, and testing a configuration change with the code. One build artifact for every environment, source precedence, branching on an environment name, configurable production timeouts and the deprecation window for a removed option have only practitioner formulations, so they stay pending. Defaults, including no placeholder default for an environment-dependent value, are already DSN-17; units in time types are DSN-51; secrets in code are INP-10.

## Formulation layer

Most of the canon for this topic was opened through GitHub copies. Fetched: SWEBOK V3 §4.8 and §3.5, the 97 Things essays 'One Binary' and 'Deploy Early and Often', Twelve-Factor III, IV and V and its community update FAQ, The Art of Unix Programming ch. 10, the Command Line Interface Guidelines, Abseil TotW #45, the Google Go and Python and Uber Go style guides, Google eng-practices, Software Engineering at Google ch. 14, 23 and 25, and the SRE book ch. 8. The SRE Workbook ch. 14–15, The Pragmatic Programmer Topic 32 and the first-edition Metaprogramming tips, and Continuous Delivery ch. 2 and 5 were reached only through GitHub-hosted reader notes or course slides, so they are relayed. The SWEBOK V4 §4.8 body, Code Complete §10.6, APOSD ch. 8, Clean Code G35, Release It! and Shore's 'Fail Fast' are unfetched paraphrases. The canon agrees on these points: move out of the code only what varies between deploys; build one artifact and promote it through every environment; keep options few, each with a safe default; read configuration at the entry point and pass it explicitly; validate semantically and fail loudly with an actionable message; and test configuration together with the code that reads it. It disagrees on channel and repository. Twelve-Factor puts all config, credentials included, in environment variables, while CLIG forbids secrets in environment variables, and both TAOUP and CLIG assign flags, environment and files by how long a setting lives, with a fixed precedence. One Binary and Continuous Delivery version configuration values apart from the code, while SWE at Google and the SRE book keep static configuration in the code repository under the same review. The aposd-vs-clean-code discussion says nothing on configuration. The canon's own numbers (TotW #45 'majority of flags never varied', SWE book 'number one reason for our major outages', the Takeout 95%) are unpublished organisational observations, so any card needs the evidence layer's papers behind it.

## Reception layer

Practitioners agree on most of the topic's core. Values that change from one deploy to the next belong outside the code (Twelve-Factor, Pragmatic Programmer Tip 55, One Binary, and the hard-coded IP, URI and path rules in PMD, Sonar and SpotBugs). Configuration should be tested with the code it drives (Software Engineering at Google ch. 14 and 23, Sridharan, ctest). Bad configuration should fail at startup with an actionable message (Lau, the Google Go style guide, Go flag's ExitOnError, PCheck, and SPEX's 'silent overruling'). Fewer knobs are better (Too-Many-Knobs FSE 2015, Abseil TotW #45, the SRE Workbook ch. 14, PP's 'Don't Overdo It', Hadlow's Configuration Complexity Clock). The live disputes are these. (1) The environment as the channel for credentials: Twelve-Factor says yes, while CLIG, the OWASP Secrets Management Cheat Sheet, Mónica and twelve-factor issue #4 (2024) say no or 'not only'; Remy Sharp defends using env vars for secrets in practice. (2) Restart versus live reload: PP calls restart-to-change 'hopelessly out of touch', and TotW #45 and SWE ch. 24 warn about values that change after startup; reload is outside this corpus anyway. (3) A missing config file falling back to defaults (Hightower) versus treating it as an error (Lau, SPEX). (4) Endpoints given as startup parameters versus service discovery (SWE ch. 25 versus PP). Limits the tools and papers add: env values are strings, and set-but-empty is not the same as unset (Go Getenv/LookupEnv; envconfig and caarlos0/env behave differently). os.environ is a snapshot taken at startup, and Rust's set_var is unsafe in multi-threaded programs, so read once at startup. Strictly rejecting unknown flags makes it harder to remove an option (TotW #90). Users who keep a default that is wrong for their environment cause 17.5–53.3% of misconfigurations. WebSearch was exhausted and HN, Lobsters and author blogs were unreachable. Practitioner blogs were reached only through GitHub-hosted reading lists and notes, which are marked relayed. Mónica's post is unfetched. I found no Error Prone, Semgrep, Checkstyle, typescript-eslint, go vet or sonar-go rule on this topic.

## Evidence layer

Most of the research evidence on runtime configuration comes from one systems-research line (Xu, Zhou and others). The full texts are openable as PDFs on tianyin/tianyin.github.io. They are: Too Many Knobs (FSE'15), PCheck (OSDI'16), Spex / Do Not Blame Users (SOSP'13), the ACM CSUR 2015 survey, ctest (OSDI'20), EnCore (ASPLOS'14) and ConfigX (OOPSLA'21). Between them they back the rules on validating every value at startup and failing with a message that names the parameter, on parsing values strictly instead of silently overruling or ignoring them, on not adding options nobody sets, on choosing safe defaults (or none where no safe default exists), and on testing configuration changes against the code that uses them. Tool rules back keeping environment-specific endpoints and paths out of code: PMD AvoidUsingHardCodedIP, Sonar S1313/S1075 (the working sonar-java path is sonar-java-plugin/src/main/resources/...) and SpotBugs DMI_HARDCODED_ABSOLUTE_FILENAME. Official documentation (Go flag/os, Rust std::env and env!, Python configparser/argparse, Node util.parseArgs, Java System.getenv and Boolean.parseBoolean, ECMA-262 parseInt) documents strict versus lenient conversion and unknown-key handling, and a local cross-language run confirmed it. The one-binary rule has no research backing: it rests only on Software Engineering at Google ch. 23 (a book) and 97 Things (formulation). Not openable here: Yin et al. SOSP'11 (orchestrator snippet only), Facebook's Holistic Configuration Management (known only through citing papers), the ICSE'21 configuration-evolution study (arXiv denied), Sayagh et al. TSE 2020, Shore's 'Fail Fast', and SWEBOK V4 §4.8. Two disputes in the sources: (1) Twelve-Factor's 'store config in environment variables' is contradicted by the OWASP Secrets Management Cheat Sheet for secrets and by the Java System.getenv documentation, which prefers system properties. (2) PCheck, citing Facebook, reports 42% of high-impact configuration errors as 'obvious' typos, while ctest says failure-inducing configuration changes are rarely trivial mistakes.

## Spine — candidate rules in source order

1. **A value that differs between the environments the program is deployed to, such as a host address, a service URL or an absolute file path, is read from the environment, a flag or a configuration file rather than written into the code** — A host name or IP address, a service URL or URI, or an absolute file path that changes when the program runs on another host, network or environment is supplied at run time through the environment, a flag or a configuration file, never written into the code as a literal or a named constant. A hard-coded address embeds infrastructure configuration in the application. Moving a service or scaling out then needs a code modification and a full redeployment, and different values cannot easily be used across development, staging and production.
