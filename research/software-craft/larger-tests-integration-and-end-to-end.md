# Research note — Larger tests, integration and end-to-end

Topic `larger-tests-integration-and-end-to-end` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: SEG14 (Software Engineering at Google ch. 14 'Larger Testing': fidelity, flakiness, the structure of a large test, types of larger tests); SEG11 ('Testing Overview') for test size and scope as SEG defines them.

Software Engineering at Google ch. 11 'Testing Overview' and ch. 14 'Larger Testing', with ch. 23 on hermetic testing and quarantine, is the canonical formulation for this topic. It classifies every test by size (the resources it uses) and scope (the code it verifies), asks for the smallest test that covers a behaviour, and makes every test hermetic: it sets up and tears down its own environment and relies on no shared database. Tests wait by polling or by events, never by sleeping. Third-party services stay out of automated tests, slow and flaky tests are kept apart, and a rerun only delays the fix. The evidence backs the parts a reviewer can check. Flaky-test research in Java, JavaScript, Python, UI suites and across five languages names the leading causes: asynchronous waits (Luo FSE'14, relayed; Lam ICSE'20; Hashemi ICSME'22; Romano ICSE'21: 106 of 235; Costa TSE'22), order dependence and state shared between tests (Gruber ICST'21: 59% of 7,571; iDFlakies 50.5%; Zhang ISSTA'14; Gyori ISSTA'15; non-idempotent tests in IDoFT), and network dependence (Dietrich 2022; Hashemi 13%). The same research shows reruns are a weak and costly detector: 170 reruns for 95% confidence, misses after 10,000 reruns, and restarted builds that triple median merge time (Gruber; Alshammari ICSE'21; Durieux MSR'20; Haben 2021). It also links ignored failures to more crash reports (Rahman and Rigby FSE'18). Official documentation and tool rules back the rest: Go, pytest, the Rust book, JUnit, Bazel, Gradle, Spring, Django, Selenium, Playwright, Cypress and Testcontainers, with Sonar S2925 and S1607, eslint-plugin-playwright and eslint-plugin-cypress. Together they cover waiting on a condition, data each test creates, removal of state another test can see, slow tests that can be selected out, retries that are tracked, skips that give a reason, no live third-party calls, setting up UI tests through the API, and the fidelity limits of rollback isolation. The industry disagrees in four places. The test mix: SEG's 80/15/5 and Wacker's 70/20/10 against Dodds's 'mostly integration' and Goldberg's component tests, with SWEBOK ranking no stage above another. When cleanup runs: after each test in pytest, Go and Django, before each test in Cypress and Playwright, after the whole run for Goldberg. A hermetic environment per run against a stable staging environment: SEG against Playwright. Whether a pass on retry fails the build: Playwright and Gradle options against Li Haoyi. The cleanup dispute separates on whether one test's state can reach another, a condition both official sources name. The mix and the staging question have no sourced separating condition and stay out of cards. The process-level and run-order form of test independence belongs to unit-testing-and-test-quality, which is drafting its own test-independence rule.

## Formulation layer

I fetched the canonical formulation for this topic in full from raw.githubusercontent.com: SEG ch. 14 'Larger Testing' (Graves), ch. 11 'Testing Overview' (Bender) and ch. 23 'Continuous Integration' (Tannenbaum, for hermetic testing and flaky-test quarantine). I also fetched the relevant 97 Things essays (thing_82, thing_25), the google/eng-practices 'Tests' section and the aposd-vs-clean-code discussion. That discussion covers only unit tests and TDD and says nothing about larger tests. SEG supplies most of the checkable positions: size versus scope, write the smallest possible test, hermetic tests that set up and tear down their own environment and do not depend on test order or a shared database, poll with a timeout or react to an event instead of sleeping, make production timeouts tunable for tests, reduce the SUT at the UI/API and third-party boundaries, separate slow, nonhermetic tests into their own build, and treat rerunning flaky tests as a delay, not a fix. The practitioner texts outside SEG could not be opened (Fowler's 'Eradicating Non-Determinism in Tests' and test pyramid, Wacker's 'Just Say No to More End-to-End Tests', Feathers' unit-test rules, Meszaros, GOOS, Continuous Delivery), so they appear only as marked paraphrases, plus one relayed Testing Blog snippet. The canon disagrees in three places. The 80/15/5 pyramid ratio is SEG's own 'very rough guideline' and is disputed by the Testing Trophy and honeycomb formulations. SEG ch. 11 treats automatic reruns as only a delay, while ch. 23 lists retries as a common tactic. And SEG's 'chained' pairwise tests share persisted output between tests, which strains its own rule that tests must not depend on run order.

## Reception layer

This reception layer was built only from sources hosted on GitHub. The WebSearch budget was used up, and Hacker News, Lobsters and the vendor and blog hosts are denied, so no forum thread was read. Tools check two of this topic's rules mechanically. Sleeping for a fixed time in a test is flagged by Playwright no-wait-for-timeout, Cypress no-unnecessary-waiting and Sonar S2925 (Java); I found no such rule in Ruff or clippy. A bare skip with no reason is flagged by Sonar S1607 (Java and Python) and Playwright no-skipped-test. Four positions are contested by named sources. (1) The pyramid ratio: SEG's 80/15/5 against Dodds's 'mostly integration' and Goldberg's 'beyond the pyramid', a dispute that is largely about what 'unit' and 'integration' mean. (2) Whether each test removes its own data: transaction rollback in Django, Spring and Rails, and Microsoft's playbook, against Cypress's 'clean before' and Goldberg's 'clean up after all tests, each test acts on its own records'. (3) A hermetic environment per run against a shared staging environment (Playwright) or infrastructure kept running on the developer's machine (Goldberg). (4) Whether flaky failures should block merges: Li Haoyi (2025) says no, while Playwright failOnFlakyTests and Gradle failOnPassedAfterRetry fail the build. Retries on their own are rejected by Gradle, Bazel, SEG and Li alike. On waiting for a condition rather than for elapsed time, every source agrees; only polling against event notification is argued (Goldberg). I could not open Wacker 2015, Fowler 2011 and 2021, Rainsberger or the Google flaky-test blog posts (one line of the latter is relayed); research abstracts came through the neverworkintheory bibliography on GitHub.

## Evidence layer

Fifty-nine (rule, source) pairs back eight candidate rules. The strongest evidence is research on flaky tests in several languages. Asynchronous waits and concurrency are leading causes in Java (Luo FSE'14, Lam ICSE'20), JavaScript (Hashemi ICSME'22), UI tests (Romano ICSE'21: 106 of 235) and across C/Go/Java/JS/Python (Costa TSE'22). Order dependency is the dominant cause in Python (Gruber ICST'21: 59% of 7,571) and half of the iDFlakies Java dataset (50.5%). Reruns are costly and do not reliably detect flakiness (170 reruns for 95% confidence; 10,000 reruns still miss some; restarted builds triple merge time).

All the rule-level checks were fetched from official documentation and static-analysis rules: Go -short, -shuffle, t.Cleanup and t.TempDir; pytest markers, fixture teardown and the flaky-tests page; Rust #[ignore], parallel tests and the tests/ directory; JUnit @Tag, execution order and polling with @Timeout; Playwright, Cypress and Testcontainers docs; Sonar S2925 and the Playwright and Cypress lint rules. No equivalent sleep-in-test lint turned up in Ruff, clippy or staticcheck.

WebSearch was out of budget, so I reached every paper through GitHub-hosted copies: ACM bib exports, SIGSOFT OpenTOC, IEEE metadata dumps, the It Will Never Work in Theory reviews, arXiv text dumps and the authors' Pages sites. The specific causes Luo found are only relayed through secondary texts. Trautsch et al. (JSS 2020) on unit-versus-integration defect detection is unfetched, because its abstract is cut off before the results. No abstract was found for Memon et al. (ICSE-SEIP 2017).

The canon disagrees on several points. Google's own ratios differ (80/15/5 in SEG versus 70/20/10 on the blog), and SWEBOK ranks no test stage above the others. On cleanup, pytest, Go and JUnit clean up after each test, while Cypress and Playwright prefer resetting or starting from scratch before it. JUnit allows ordered integration tests. Practitioners fix flakiness by adding delays (21 of 236 UI fixes). Apple reports that eliminating flakiness is not realistic for non-hermetic system tests. Beller et al. found that fast tests are not run more often.

## Spine — candidate rules in source order

1. **A test's size is the resources it may use and its scope is the code it verifies, and a test is classified on both rather than by a unit or integration label** — A test has two independent dimensions: size, the processes, machines, network and time it needs, and scope, the code paths it verifies. A broad-scoped test can be small when doubles stand in for every out-of-process dependency, and a narrow test can be large. Labels such as 'unit' and 'integration' are used inconsistently. Bazel maps its sizes onto those labels, and the Rust book calls any test in tests/ an integration test, so the cards of this topic judge a test by the resources it uses.
