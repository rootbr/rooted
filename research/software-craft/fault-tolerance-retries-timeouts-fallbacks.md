# Research note — Fault tolerance with retries, timeouts and fallbacks

Topic `fault-tolerance-retries-timeouts-fallbacks` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: SW4.5 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.5; its V3 counterpart, ch. 3 §4.5 'Error Handling, Exception Handling, and Fault Tolerance', is openable in the ligurio/swebok-v3 transcription master 3_software_construction.md); the call-site discipline is usually formulated in practice from the stability patterns of Nygard's Release It! (2nd ed.) and the Google SRE book chapter 'Addressing Cascading Failures' — practitioner texts, formulation only.

The canon names retrying as a fault-tolerance strategy without conditions. SWEBOK V3 ch. 3 §4.5, the openable counterpart of SW4.5, also counts a neutral value, or a phony value with a benign effect, among legitimate techniques. The practitioner formulations agree on the call-site discipline: Release It! 'Timeouts', the SRE book chapters 'Addressing Cascading Failures' and 'Handling Overload', Software Engineering at Google ch. 25, DDIA, and the Azure and AWS guidance. Every remote call gets a bounded timeout or deadline, and that deadline passes to the callee. Code retries only failures it classifies as transient, makes a bounded number of attempts with growing, jittered delays, and repeats a state-changing call only once it is idempotent or carries a client-generated key. Retries happen at one layer. The sources split in four places. The first is which layer owns the retry: the layer above the rejecting one, the layer with full context, or the lowest layer and the client library. The second is whether to fall back at all: Hystrix and the .NET guide offer cached, default and even silent fallbacks, while AWS argues against fallback in distributed systems. The third is whether the first retry may be immediate, and the fourth is fixed per-request caps versus process-wide retry budgets. The evidence is strongest for timeouts and retry policy. Two studies measure the defects. Dai et al. (IC2E 2018) studied 156 timeout bugs: 31% were missing timeout checks and 47% misused values. Stoica et al. (SOSP 2024) studied 70 retry bugs and found them split about evenly between IF, WHEN and HOW to retry. CWE-1088 catalogues the missing timeout. The rules are stated across languages by RFC 9110 §9.2.2 and §10.2.3, gRPC A6, Google AIP-194, AIP-155 and AIP-4221, the Go context package, and the Go, JDK, Rust, CPython and gRPC documentation. Mechanical tool checks exist only for Python (Pylint W3101, Ruff S113, Semgrep use-timeout) and Go (contextcheck, noctx, gosec G118). No openable study measures stacked retries, jitter on its own or silent fallbacks, so those rules rest on standards and documentation. Two sources qualify them. The end-to-end argument (Saltzer et al. 1984) treats a lower-layer retry as a performance enhancement, and SWEBOK accepts benign substitute values. The separating conditions of the retry-at-one-layer and fallback cards keep both cases.

## Formulation layer

SWEBOK V3 ch. 3 §4.5, which I fetched, names "backing up and retrying" as a fault-tolerance strategy but sets no conditions for it. The V4.0 section SW4.5 could not be opened. The conditions come from the practitioner canon. I opened the SRE book ch. 21–22 and both Builders' Library articles through third-party GitHub copies, and reached Release It! only through reader notes (relayed). Azure, .NET and Google AIP guidance, SWE at Google ch. 25 and DDIA 2nd ed. were also fetched. These sources agree on four rules: a deadline on every remote call and its propagation; retrying only transient failures with bounded attempts and randomized backoff; idempotency or a client-assigned request ID before retrying a mutation; and retrying at one layer. The canon disagrees on two points. First, which layer retries: SRE ch. 21 says the layer immediately above the rejecting one; the Azure Retry pattern says the higher-level task with full context; APOSD says a low layer, retrying without bound. Second, fallbacks: the .NET guide and Hystrix recommend cached, default or even silent fallbacks, while AWS "Avoiding fallback" and SRE ch. 22 say a rarely used fallback is untested, must be exercised, and needs alerting. Clean Code's Special Case pattern concerns a domain absence, not a failed call. Brooker's 2022 reflection qualifies his own backoff-and-jitter formulation as a complement to a bounded retry policy, not a substitute for it. Not opened: SWEBOK V4.0, Code Complete (paraphrase notes only), and Release It! itself. The aposd-vs-clean-code discussion says nothing on the topic. One new openable path: RFC 9110 is at httpwg/httpwg.github.io main specs/rfc9110.html.

## Reception layer

Industry practice largely agrees on the call-site discipline. Lint rules and library docs treat a missing timeout as a defect, and they agree on retrying only what the server can safely receive twice. Tool coverage is uneven. Pylint W3101, Bandit B113, Ruff S113, Semgrep use-timeout and Sonar S7618 check Python requests and httpx; noctx, contextcheck and gosec G118 check Go context propagation; Sonar S7483 and Ruff ASYNC109 make the caller own async timeouts. A search of ESLint, typescript-eslint, Clippy, Error Prone, Sonar Java/Go and semgrep-rules found no rule for Java, Rust or TypeScript. Positions conflict in six places. Retry budgets are offered in place of fixed per-request counts (Linkerd/Alex Leong, Finagle, reqwest, Azure, gRPC throttling). Some sources allow an immediate first retry (urllib3, Azure, Finagle), and Marc Brooker's critique of backoff is cited from memory. Azure's guidance against retrying at every layer clashes with the same page's "implement retries ... at each layer" and with client libraries that retry by default (OkHttp, gRPC transparent retry, AIP-4221, the Azure SDK). Netflix Hystrix documents "Fail Silent" fallbacks, while Jacob Gabrielson (cited from memory) argues against fallback altogether. The idempotency header is not settled (IETF Idempotency-Key, an Internet-Draft, against Microsoft's Repeatability-Request-ID). Library defaults differ: no timeout by default in requests, Go, the JDK, reqwest and axios, 10 s in OkHttp; tenacity retries forever and go-retryablehttp retries POST. Unopened: the WebSearch budget was spent and HN, Lobsters, aws.amazon.com, sre.google and brooker.co.za are denied, so the Gabrielson and Brooker critiques are unfetched paraphrases that must not anchor anything. Opened instead: the Wasabi SOSP 2024 PDF on the author's GitHub Pages, and a run of the AWS backoff simulator. In that run no backoff finished soonest but made the most calls, plain exponential backoff was slowest, and full jitter made the fewest calls.

## Evidence layer

Two empirical studies were opened in full from GitHub-hosted copies. Dai et al. (IC2E 2018) studied 156 timeout bugs: 31% were missing timeouts, 47% misused timeout values and 5% unnecessary timeouts. Stoica et al. (Wasabi, SOSP 2024) studied 70 retry bugs: IF 36% (wrong retry policy, 17), WHEN 33% (missing delay 10, missing cap 13) and HOW 31% (improper state reset 12). A third study, Liu et al. (HotOS 2019, 112 Azure incidents), adds unresponsive components and handlers that ignore error reports. Together these anchor the rules on timeouts, transient-only retry, bounded retry with delay, and safe repetition. Standards and official documentation back every candidate rule in at least three of the five languages: CWE-1088, OWASP ASVS 13.1.3, Go net/http and context, JDK HttpRequest, CPython socket, Rust TcpStream, the gRPC deadline, retry and A6 documents, RFC 9110 §9.2.2 and §10.2.3, the IETF Idempotency-Key draft, and Google AIP-155, AIP-194 and AIP-4221. Pylint W3101, Ruff S113 and Semgrep use-timeout are the tool rules, but all are Python-only. Not opened: the Metastable Failures paper (HotOS 2021), Gunawi et al. (SoCC 2016), the AWS Builders' Library and the Google SRE book (all unfetched). No openable empirical study measures retries stacked across layers, jitter on its own, or a silent fallback default at a call site. Those three claims rest on documentation (gRPC A6, AIP-194, AIP-4221, RFC 9110) and on formulation (Azure Architecture Center), and the Azure page contradicts itself on retrying at each layer. Disagreements in the canon: SWEBOK §4.5 counts a neutral or phony substitute value as a legitimate fault-tolerance technique with no observability condition, against the explicit-fallback rule. Dai reports unnecessary timeouts (5%) as bugs, against 'a timeout on every call'. The gRPC connection-backoff algorithm reconnects without an attempt cap and only caps the delay. The end-to-end argument treats lower-layer retries as an optional performance enhancement rather than forbidding them.

## Spine — candidate rules in source order

1. **A fallback that replaces the result of a failed remote call leaves a mark that the call failed, in what it returns or in a recorded event, and never substitutes a success or a permission the call did not give** — When code answers a failed or timed-out remote call with a substitute, such as a cached or stale value, a default, or an empty or degraded result, the substitution is explicit. The caller can tell that the result is a fallback, or the failure is recorded. The substitute is never a permissive answer to the question the failed call was meant to decide: access granted, a check passed, a write or payment reported as done. A non-transient failure such as data loss is surfaced, not absorbed. The rule does not forbid substitutes. A benign substitute value and graceful degradation are recognised fault-tolerance techniques, and a substitute may stay silent toward the caller where the result is optional, provided the failure itself is recorded.

3. **Every call to a remote service or another process carries a finite timeout or deadline, set at the call or on the client it goes through, so the caller cannot wait forever** — An awaited or blocking call to a remote resource has a finite bound on how long the caller waits. This covers an HTTP request, an RPC, a database or socket connection and a call into another process. The bound is passed at the call or configured on the client, channel or context the call goes through. A missing timeout and an explicitly infinite one (zero or None, where that means no limit) both leave the caller hanging when the callee stops responding. The documented default is no limit in Go's HTTP client, Java's HTTP client, Python's sockets and requests, Rust's TcpStream and reqwest, gRPC and axios. A check establishes the effective bound: a client whose documented default is finite meets the rule, and a per-read inactivity timeout bounds each wait rather than the call as a whole. The rule covers waits on another component. A timeout on a local lock or intra-node synchronization is outside it, and choosing the value is a separate question.
