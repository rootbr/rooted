# A call made while serving a request passes that request's deadline and cancellation on to the downstream call, shortening it at most and never starting a fresh or longer one

## Thesis
Code that serves a request carrying a deadline or a cancellation signal makes each remote call on that request's behalf under the request's own signal or under one derived from it, so that the call is cancelled when the request is and its deadline is never later than the request's. A derived signal may bring the deadline earlier or add a cancellation of its own, and it keeps the request's deadline wherever that one is earlier; where the downstream client takes only a timeout, the timeout passed is the request's remaining time or less. Three forms break the chain: a fresh root context or signal created between the incoming request and the outgoing call, a new cancellation signal not linked to the request's, and a fixed timeout that can exceed the time the request has left. A function on the call path takes the signal from its caller; creating a base signal of its own there is rare and fits only where the caller's signal is the wrong one for the work. The signal takes whatever form the language and framework give it — an explicit context argument, a deadline a framework propagates automatically, a cancellation scope, an abort signal or a cancellation token — and each form can be passed on or derived.

## Rationale
A deadline is the point in time past which a caller is unwilling to wait for a response; a timeout is a duration, converted to a deadline by adding it to the time the call starts. Clients that do not wait around unnecessarily and servers that know when to give up processing a request improve resource utilization and latency. When the deadline passes, the caller gives up with a deadline-exceeded failure and the serving framework may cancel the call, but stopping any activity spawned to serve the request is the job of the serving code. A downstream call made under a signal derived from the request's is cancelled with the request, because cancelling a signal cancels every signal derived from it. A call made under a fresh root or an unlinked signal is not cancelled with the request: a root context is never cancelled and cascades no cancellation, so the downstream work goes on after the caller has given up, and a server that keeps processing a request it cannot answer within the request's deadline just wastes valuable resources and, in the worst case, crashes. Checkers report a non-inherited context in the middle of a call chain as one that could break the call link, and a fresh root used in concurrent work spawned while serving a request, in place of the request's context, as a context-propagation failure that leaks concurrent tasks and resources. A fixed timeout ignores the time the request has already spent: a server that has used 0.5 s of a 2 s deadline has 1.5 s left to give its own downstream call. A callee that sets its own timeout takes the decision from the caller, which may want a different duration or one deadline coordinated across several concurrent operations, and combining functions that manage their own timeouts can lead to complex and unpredictable behaviour when calls nest or run concurrently under a shared deadline. A derived deadline or a combined signal does not lengthen the request's: a derived deadline is adjusted to be no later than the one asked for and is the parent's when the parent's is earlier, a combined abort signal aborts when any of its inputs does, whichever is sooner, and the effective deadline under nested cancellation scopes is the one that expires first. One RPC framework propagates an incoming call's deadline to its outgoing calls automatically in some of its implementations, by default in some languages and only when enabled in others, which avoids the error-prone approach of manually including the deadline for each outgoing call.

## Example
```python
bad:  def Get(self, request, context):
          return self.stub.Fetch(request, timeout=30)
good: def Get(self, request, context):
          left = context.time_remaining()
          budget = 30 if left is None else min(30, left)
          return self.stub.Fetch(request, timeout=budget)
```

## Limits
An entry point that starts the work creates the root signal: a main function, initialization, a test, and a server framework that builds a fresh signal for each incoming request, fills it from that request and scopes its lifetime to the request's. Work that has to keep running after the request is cancelled, such as a background operation the request starts, may take a detached signal, one that keeps the request's values but not its cancellation or deadline, or a new root where no detaching form exists. Where the framework propagates the incoming deadline to outgoing calls automatically, a call that does not replace the propagated signal follows the rule, and so does a fixed deadline added to such a call where the client takes the earlier of the call's deadline and the propagated one. A call awaited inside the request's cancellation scope is bounded by that scope already, and a timeout scope opened inside it, unless shielded from the outer one, can only bring the deadline earlier. A request that carries no deadline and no cancellation signal has nothing to propagate, and the call's own timeout applies. Whether a remote call has a finite timeout at all, the value a timeout takes, how a retry spends the time left, and the release of the cancel handle a derived signal returns are judged by their own rules.

## Validator
Grep the added lines for a fresh root context or signal, a new cancellation controller or token, a derived deadline or timeout, a timeout scope, and a numeric timeout passed to a call. For each hit, open the file and decide whether the enclosing function runs on behalf of an incoming request that carries a deadline or a cancellation signal: a request or RPC handler, a function that receives a context, a signal, a cancellation token or the request itself, or a function such a one calls. Skip an entry point that starts the work (a main function, initialization, a test, a server framework building each request's signal), work detached on purpose so that it outlives the request (a detaching form that keeps the parent's values without its cancellation or, where the language and framework offer no detaching form, a new root with a comment saying the work has to outlive the request), and a request that carries no deadline and no cancellation signal. For the remote call the hit governs, trace where its deadline and its cancellation come from. The request's signal passed on, a signal derived from it, a call awaited inside the request's cancellation scope, a call whose framework propagates the incoming deadline without the code replacing it, and, where the downstream client takes only a timeout, a timeout capped at the request's remaining time all pass. A fresh root, a new signal or token not linked to the request's, and a fixed timeout that can exceed the request's remaining time break the rule, and so does a function on the call path that drops the signal it was given and creates its own. Validator question: **Does an added line make or set up a remote call on behalf of a request that carries a deadline or a cancellation signal under a fresh root context or signal, a new signal not derived from the request's, or a fixed timeout not capped at the request's remaining time, outside an entry point and outside work deliberately detached from the request?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-37`, severity major, `file`, `symbol`, `code` = the line that creates the fresh root or unlinked signal, or passes the fixed timeout, quoted verbatim from the diff, `fix` = the same call made under the request's signal or one derived from it, or, where the downstream client takes only a timeout, with its timeout capped at the request's remaining time, in the file's language, `rationale` = which incoming deadline or cancellation the call drops and what downstream work keeps running after the caller has given up).
