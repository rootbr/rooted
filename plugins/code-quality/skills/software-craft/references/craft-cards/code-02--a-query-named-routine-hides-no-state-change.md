# A routine named as a query, predicate, accessor or conversion hides no state change, and a getter or predicate returns what its name asserts

## Thesis
A routine whose name reads as a query — a get accessor, an is, has or can predicate, a noun-phrase accessor or property, a to or as conversion — leaves unchanged all state its caller can observe, unless the name announces the change (get-or-create, load-and-cache). Observable state is a field, a global, an argument, a file, a store or a network peer that calling code can read back, and a new object stored where calling code can reach it; a cache whose only observable effect is speed is not a change. A getter named after a field returns no other field, and a predicate returns true exactly when the assertion its name makes holds. A routine called for its effect carries an imperative verb phrase, and where one operation has both an in-place and a copying form on a mutable receiver, the two carry different names, and the name that the language's documented convention gives the mutating form goes to the form that changes the receiver: the plain verb against a participle or noun for the copy (sort, sorted), or a marked verb against the plain verb for the copy (sort!, sort). A body changed under an unchanged name is held to the same check as new code.

## Rationale
A caller who trusts a query name treats the call as free of consequences, and a reader who trusts it does not open the body or the routines it calls; a hidden write therefore reaches both as behaviour neither expected. An identifier that describes its entity's behaviour incorrectly, or an entity that betrays what its name conveys, is a linguistic antipattern, and a getter that does more than return its attribute without documenting it, such as one that stores a new object in its attribute on every call, is one of the catalogued forms. A name or description that is misleading with respect to the implementation is expected to cost developers more time and effort to understand, or to lead them to wrong assumptions when they use the code, and the presence of linguistic antipatterns significantly increases developers' cognitive load, measured with functional near-infrared spectroscopy during comprehension tasks. A getter that returns a field other than the one its name matches, when a field of the matching name exists, is most likely a typo or a copy-paste bug, and a default-on lint reports it as suspicious. Official naming guidelines bind name to effect: one language's guidelines give a routine without side effects a noun phrase, a routine with side effects an imperative verb phrase, and a Boolean member the form of an assertion about its receiver when the use is nonmutating; another language's guidelines have a method name suggest whether it mutates its object or returns a new one; still others mark the mutating form of a pair and leave the plain verb to the copy. Holding the body to the name restores the property that a call site can be understood from the names it calls.

## Example
```python
bad:  def get_items(self):
          self.items.sort()
          return self.items
good: def sorted_items(self):
          return sorted(self.items)
      def sort_items(self):
          self.items.sort()
```

## Limits
A cache or memo whose only effect a caller can observe is speed stays within a query name, and so does computing a field on first read when no caller can tell the difference. A get accessor whose documentation at its declaration states the extra action is outside the catalogued antipattern and passes; a noun-phrase, predicate or conversion name is held to the name alone. A read that leaves its source as the next reader finds it — a query to a store, a request that changes nothing at a network peer, a file opened and read within the call — changes none of the state the rule counts; a read that consumes from a stream, a queue or an iterator held in a field or passed as an argument advances state its caller observes and counts as a write. A routine whose name is fixed by an interface it implements — an iterator's advance, a stream's read, a framework callback — carries the effect that interface documents. Nothing here requires a side-effect-free routine to take a noun form, and a routine named by any other verb phrase (compute, find, fetch) reads as an action and is outside the query forms the rule holds to its body. State that no calling code reads back, such as a diagnostic log line or a metrics counter, is outside observable state. On an immutable receiver there is no in-place form, so a verb that returns a changed value has no second form to be confused with. A naming convention documented in the project context that gives a prefix another meaning, such as a get documented to create on a miss, is the tolerance that rejects the finding. The rule weighs a name's promise against its body; the name's length, spelling and casing are outside it.

## Validator
Grep the added lines for a routine signature or call whose name opens with a query or conversion word (get, is, has, can, to, as), for an accessor form (a property, a getter, a zero-argument method named by a noun), and for an assignment to, or a mutating call on, a field. Open the file and take each routine whose signature the hunk adds or renames, or whose body the hunk changes, and whose name reads as a query, predicate, accessor or conversion; read its whole body and each routine in the file it calls. Trace every write it makes: an assignment to a field, a global or an argument; a mutating call on one of them; a write to a file, a store or a network peer; a new object stored where a caller can reach it. Set aside a write the name announces, a get accessor's extra action that its documentation at the declaration states, and a cache whose only visible effect is speed. Compare a getter's return value with the field its name matches, and a predicate's result with the assertion its name makes. Where one operation has an in-place and a copying form on a mutable receiver, check that the form carrying the name the language's documented convention gives the mutating form changes the receiver, and that the other only returns a changed copy. Validator question: **Does a routine's name misstate its body — a query, predicate, accessor or conversion name over a write the caller can observe and the name does not announce, a getter returning a field other than the one its name matches, a predicate whose result differs from whether the assertion its name makes holds, or, where one operation has an in-place and a copying form on a mutable receiver, the form the language's documented convention names as the mutating one leaving the receiver unchanged, or the form it names as the copy changing the receiver?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-02`, severity major, `file`, `symbol`, `code` = the added line that writes the state or returns the mismatched value, with the routine's signature line when the diff adds it, quoted verbatim from the diff, `fix` = the body brought to its name (the field the name matches returned, the predicate's condition corrected, the in-place and copying bodies placed under the names the convention gives them) or the routine renamed to announce its effect with an imperative verb phrase or a name that states the extra action, or split into a query that changes nothing and a separately named command, in the file's language, `rationale` = what the name promises, the state the body changes or the value it returns instead, and the wrong assumption a caller trusting the name would make).
