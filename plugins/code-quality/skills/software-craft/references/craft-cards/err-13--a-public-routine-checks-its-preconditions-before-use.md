# A routine callable from outside its module checks, before it uses or stores a value, each condition on its arguments and its object's state that its correctness needs and its types do not enforce, and fails there when one is violated

## Thesis
A routine or constructor that code outside its package or module can call (public, protected or exported, in a type that such code can also reach) checks each condition on its arguments or on its object's state that its correctness needs and its parameter types do not enforce: an argument present rather than null, a number inside its range, an index inside its bounds, the object in the state the call requires. The check comes before the first statement that uses the value under that condition, and before the routine stores the value or changes its object's state. A violated condition fails there with the language's precondition failure: an invalid-argument, null-argument, out-of-range or illegal-state error, or a panic on misuse or a returned error where the language reports a caller's mistake that way. The call is then reported as the caller's mistake, and the bad value does not break the routine.

## Rationale
A precondition is a requirement that the routine's specification places on its caller, and a check of it in a public routine ensures that the caller has obeyed it; when the check fails, the error tells the caller that it made a mistake, and the bad call is flagged as the one that passed the illegal argument. A contract violation indicates a bug on the caller's side, which the calling programmers fix in their code rather than recover from at run time. Checking the values of the input parameters protects the routine from being broken by invalid inputs; an argument the routine does not validate can lead to incorrect calculations, runtime exceptions, violated class invariants and inconsistent object state. Validating the input before the routine modifies its object, or ordering the code so that whatever can fail runs before the object is modified, keeps the object consistent when the check fails. Validation in the routine itself keeps the validation code in one location, which reduces the size of the code and raises the likelihood that the checks are performed consistently and correctly. Forgetting a precondition check is a common slip: across more than 4 million bug-fix commits from 101,471 GitHub projects, confronted with a manual analysis of 369 real bug fixes from five open-source projects, the fixes gave direct evidence that developers often forget to add if-statement precondition checks to their code. A static analyser reports the omission: an externally visible method that dereferences a reference argument without verifying that it is not null. A type can carry the check instead: when a parameter's type rules out the bad value (a type that expects something rather than nothing, an unsigned integer that is never negative, a wrapper type whose constructor validates), the compiler has already ensured a valid value, the routine need not check it at run time, and the bug is caught during compilation rather than through a run-time failure.

## Example
```rust
bad:  impl Sampler {
          pub fn set_ratio(&mut self, ratio: f64) { self.ratio = ratio; }
      }
good: impl Sampler {
          pub fn set_ratio(&mut self, ratio: f64) -> Result<(), RatioError> {
              if !(0.0..=1.0).contains(&ratio) { return Err(RatioError(ratio)); }
              self.ratio = ratio;
              Ok(())
          }
      }
```

## Limits
The rule is contested, and who can call the routine separates the cases. Testing an argument in both the caller and the callee is largely discredited, in part for performance, and normal practice validates on one side of each interface only: caller validation can be faster, because the caller may know invariants that keep invalid values out, while callee validation keeps the check in one place. Where unknown code can call the routine, because it is public or protected or belongs to a library's public surface, the routine validates its parameters itself, and the check is a precondition check at an API boundary (the Source entries marked callee). Where the routine is reached only from checked entry points, because it is private, internal, or restricted to its package or module, it relies on its callers' checks: a routine designed to be called only by known code is made internal, and the same check on a non-public routine's parameter would be an assertion that the class or package itself is not broken, since the preconditions at the public boundary should have kept the bad value from getting that far (the entries marked caller). Complete validation of every argument of every routine can add cost and complexity beyond its value in all but the most critical code, a cost for which validation at the API boundaries is the suggested response. A routine whose stated contract requires the caller to validate its arguments, where every call does, is outside the rule, and so is an unchecked variant, named or documented as not checking and offered beside a checking one, for callers whose performance requires skipping the check and who are otherwise confident the inputs are valid; a project context that states such a contract for its public routines rejects the finding. No check is needed for a condition that a parameter's type rules out, where the compiler or a static type checker the project runs enforces the type, nor for a value that the routine handles correctly whatever its type permits. A parameter validated by another call in the routine before its use counts as checked, and an explicit check made as the routine processes its input, rather than ahead of all of it, follows the rule while it comes before the use of the value it checks and before the routine stores the value or changes its object's state. The failure that a use itself raises, a dereference of a null value or an access at an index out of bounds, is not a check: a publicly callable routine checks its arguments so that such a failure, which exposes how the routine is implemented, does not reach its caller. Validation of data that crosses a trust boundary, whether a failed check stops the program or returns an error, whether a check the build can remove may stand in for this one, and how the precondition is documented are judged by their own rules.

## Validator
Grep the added lines for routine and constructor signatures that are public, protected or exported. Open the file and confirm that code outside the routine's package or module can call it: the routine is not private, internal or restricted to its package or module, its name does not carry the leading underscore or lower-case initial that marks a name as module-private, and its enclosing type is not private, internal, unexported or restricted to its package or module. For each parameter, and for each field of the object the routine depends on, name the condition the body relies on: the value is present rather than null, an index is inside the bounds it is used with, a count, size, ratio or divisor is inside its range, the object has been opened or initialised and not yet closed. Drop a condition the parameter's type already rules out under the compiler or the project's static type checker (a non-optional or non-nullable type, an unsigned type, a wrapper type whose constructor validates) and a value the routine handles correctly for every value its type allows; drop every condition of an unchecked variant whose name or documentation says it does not check and that sits beside a checking one, and every condition when the project context states that callers validate the arguments of its public routines. For each remaining condition, read the body from its first line and find the check (a conditional that throws, raises, panics or returns an error, a precondition helper, a call to another routine that validates the value, placed before the use; the failure that the use itself raises, a null dereference or an out-of-bounds access, is not a check) and the first statement that uses the value under that condition, stores it in a field, or changes the object's state. Validator question: **Does a routine callable from outside its module use or store an argument, or act on its object's state, under a condition its parameter types do not enforce, with no check of that condition before that statement, or with the check placed only after the routine has stored the value or changed its object's state?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-13`, severity major, `file`, `symbol`, `code` = the routine's signature line and the first line that uses, stores or acts on the unchecked value, verbatim from the diff, `fix` = the same routine checking the condition before that line and before any change of its object's state, failing with the language's precondition failure (an invalid-argument, null-argument, out-of-range or illegal-state error, or a panic or a returned error where the language reports a caller's mistake that way) that names the argument and its value, in the file's language, `rationale` = the condition the routine relies on, the unchecked use, and what a violating call would compute, store or break instead of being reported as the caller's mistake).
