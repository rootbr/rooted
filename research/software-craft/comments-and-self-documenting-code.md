# Research note — Comments and self-documenting code

Topic `comments-and-self-documenting-code` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC32 (Code Complete 2nd ed. ch. 32 'Self-Documenting Code'); APOSD (A Philosophy of Software Design ch. 12 'Why Write Comments? The Four Excuses', ch. 13 'Comments Should Describe Things that Aren't Obvious from the Code', ch. 15 'Write The Comments First'); the Clean Code position as its author states it in johnousterhout/aposd-vs-clean-code README.md, section 'Comments'; the 97 Things essays 'A Comment on Comments' (thing 16) and 'Comment Only What the Code Cannot Say' (thing 17). Marked contested in the design note.

The canon covers comments in four places: Code Complete ch. 32, A Philosophy of Software Design ch. 12, 13, 15 and 16, Clean Code ch. 4 as Ousterhout quotes it in the aposd-vs-clean-code README, and the 97 Things essays 16 and 17. It agrees that a comment does not repeat the code. A comment carries the reason, or whatever else the code cannot say. A comment that contradicts the code is worse than none. Commented-out code belongs in version control. The official guides for all five target languages (PEP 8 and PEP 257, Go Doc Comments, rustdoc and the Rust API Guidelines, and Google's Java, Python, TypeScript and Go style guides) add three points. A public or exported item carries a doc comment in the language's documented form. That comment tells a caller what the signature does not: side effects, errors and panics, preconditions and special cases. It leaves out implementation detail. The industry disagrees on four points. (1) Ousterhout says missing comments cost more than bad ones and that team-internal interfaces need comments too. Martin calls comments as generally practised a net negative and documents only public APIs. The official guides draw the line at visibility, which separates the two camps for the presence rule. (2) Should unclear code be restructured rather than commented? Google eng-practices and Henney say restructure; Google Python style and Ousterhout say comment. No sourced condition separates them, so this rule is held pending. (3) May TODO markers stay? Google style and Ruff's flake8-todos rules keep markers that link tracked context. ESLint no-warning-comments, Ruff FIX, Sonar S1135 and godox flag them. They are separated by whether the marker points to tracked context. (4) Doc-comment form: prose versus Errors, Panics, Args or Returns sections. The language's documented convention decides. The evidence is mostly official documentation and static-analysis rule pages. Research is thin and mixed. Wen et al. 2019 (relayed) find that only 13–20% of code changes trigger a comment change, and Hata et al. 2019 find that almost 10% of links in comments are dead. Against these, Nielebock et al. 2019 find no significant effect of comment type on correctness in small tasks, and Ibrahim et al. 2012 (relayed) find that inconsistent comment updates are not in themselves tied to more bugs. So no card claims a defect rate, and severities stay at minor or suggestion.

## Formulation layer

I opened the 97 Things essays 16 and 17 and the full johnousterhout/aposd-vs-clean-code README. The README covers the sections 'Comments', 'Comments Summary', 'A Tale of Two Programmers', 'Test-Driven Development' and 'Closing Remarks', and through it the Clean Code p. 54 passage that Ousterhout quotes. I also opened the official guides: PEP 8, PEP 257, Go Doc Comments, Effective Go, the Rust book ch. 14.2, the rustdoc guide, the Rust API Guidelines, Google's Java, Python, TypeScript, C++ and Go style guides, google/eng-practices, Software Engineering at Google ch. 10 and the Linux kernel coding style. Code Complete ch. 32, A Philosophy of Software Design ch. 12, 13, 15 and 16, and Clean Code ch. 4 itself could not be opened from here, so those items are paraphrases from memory, marked unfetched; they are formulations and never a card's anchor. The canon agrees on four points: don't restate the code, put rationale and non-obvious constraints in comments, keep comments current, because a contradicting comment is worse than none, and leave commented-out code to version control. Most official guides also require an interface comment on public API items that tells the caller what the signature does not: side effects, errors and panics, preconditions, special cases, and concurrency guarantees. The disagreement is real. Ousterhout says missing comments cost 10–100x more than wrong ones (his own estimate) and that interfaces need comments even inside a team. Martin calls comments a failure of expression and a net negative as generally practiced, and prefers long names. Smaller conflicts: section-style doc comments (Rust, Google Python) versus prose-only ones (SWE at Google); 'tell WHAT not HOW' (Linux kernel) versus 'why, not what' (Google), where the two use 'what' in different senses; and mandated doc comments on every visible member (Google Java/C++) versus Clean Code's 'mandated comments'.

## Reception layer

The reception layer rests on the public Ousterhout–Martin exchange (aposd-vs-clean-code README.md, fetched). The two disagree on whether missing or bad comments cost more, on long names versus short names plus comments, on trusting comments, and on interface comments for code used only inside the team. They agree only that implementation code needs comments where it is non-obvious, and that a side-effect warning in an interface comment is useful. The industry style guides (Google eng-practices and the Google C++, Python, Java and TypeScript guides, Linux, LLVM, Go CodeReviewComments, PEP 8, SWE at Google) agree on three points: do not restate the code, explain why, and document what callers need. They split on the following: the vocabulary (Linux says 'tell WHAT, not HOW'; Google says 'explain why, not what'); doc-comment boilerplate sections (SWE at Google finds Returns/Throws sections unnecessary, while Checkstyle JavadocMethod, clippy missing_errors_doc and Ruff pydoclint check for them); doc comments on private code (detekt DocumentationOverPrivateFunction against Go CodeReviewComments and clippy missing_docs_in_private_items); and TODO markers (Google, Airbnb and Ruff TD rules endorse TODO with a link, while ESLint no-warning-comments, Sonar S1135, godox and rustc tidy flag or reject them). Tools check mechanically only that a comment is present, that tags match the signature (Error Prone InvalidParam, Ruff DOC102, detekt OutdatedDocumentation, rustdoc broken links), commented-out code (Ruff ERA001, Sonar S125, with false positives acknowledged), and markers. No tool checks whether a comment restates the code or has drifted from it in meaning. Most comment rules are off by default: Ruff files them as pedantic, clippy as pedantic or restriction, and rustc's missing_docs is allow-by-default 'because it can be noisy'. The WebSearch budget was spent and the forum and blog hosts are denied, so the following could not be opened and appear only as unfetched or none-found items: Hacker News and Lobsters threads, the practitioner blogs (antirez, Atwood, Spertus, Google Testing Blog), and threads from 2024–2026. The one experiment reachable through neverworkintheory (Nielebock et al. 2018, fetched) found no significant effect of comment type on correctness in small tasks, and found that participants rated comments more useful than they measured. This weighs against the experience-based claims of both camps.

## Evidence layer

Official documentation and static-analysis rule pages back most candidate rules in openable form across Java, Python, TypeScript, Go and Rust. They cover five rules: write an interface (doc) comment on public items saying what the caller needs (PEP 257, Go Doc Comments, Rust API guidelines C-FAILURE, Google Java/Python/TS/Go style; checked by Checkstyle, Ruff/Pylint, clippy, revive, Sonar S1176); do not restate the code (PEP 8, Google style guides, eng-practices); keep comments consistent with the code (PEP 8; Error Prone InvalidParam, Ruff DOC102, doctest and rustdoc doc tests); delete commented-out code (Sonar S125, Ruff ERA001, a rooted eval fixture); and give TODO markers a tracked link or resolve them (Google TODO format, ESLint, Checkstyle, Ruff, Sonar). The research reachable here is limited. It comes from neverworkintheory abstracts fetched from its GitHub source (Nielebock 2018, Hata 2019, Louis 2020, Zampetti 2021, Hofmeister 2017, Maalej-free) and from the repository's earlier first-hand reading of Wen 2019 and Ibrahim 2012, which is relayed here, not reopened. Fluri 2007, Tan 2007 (iComment), Steidl 2013, Pascarella 2017 and Woodfield 1981 could not be opened: the WebSearch budget was used up, the papers are absent from the NWIT bibliographies, and no GitHub copy turned up (csnagy.github.io and sailresearch/sail-website answer 404). They appear as unfetched paraphrases and must never be a card's only anchor. The canon disagrees at several points. Nielebock 2018 found no significant effect of comment type on correctness in small tasks, and longer times with documentation comments. Ibrahim 2012 holds that inconsistent comment changes are not by themselves correlated with more bugs. TODO practice is split: Google style asks for a tracked link rather than a person, while Go Notes and Ruff TD002 expect a username; ESLint and Ruff FIX say resolve before production. Effective Go names disabling code as a use of block comments. The recast-into-code side of the Ousterhout–Martin dispute has only adjacent evidence: Nielebock participants preferred identifiers, and Hofmeister's naming result belongs to naming-identifiers.
