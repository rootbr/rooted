# Research note — Code smells and antipatterns

Topic `code-smells-and-antipatterns` of group F. Changing code, domain `change`, id prefix `CHG`. Formulation locators: CC24 (Code Complete 2nd ed. ch. 24 'Refactoring', the 'Reasons to Refactor' list of warning signs); the smell catalog the topic is usually formulated from is Fowler and Beck, Refactoring 2nd ed. ch. 3 'Bad Smells in Code' — a trade book, named as formulation only.

The canon frames each smell as a warning sign that marks code to examine, not as a defect, and leaves the fix to refactoring. Its sources are Code Complete ch. 24 'Reasons to Refactor', Fowler and Beck's ch. 3 catalog (formulation only), and the Blob and Lava Flow antipatterns. It is firmer about dead code and commented-out code: delete them and rely on version control. The industry splits on class-level smells. PMD, Pylint and Sonar ship god-class, data-class and class-size checks, but PMD's quickstart leaves them off and Ruff marks its port pedantic. Pylint exempts declared record types and recommends a dataclass plus a free function. Ousterhout's classitis, the Rust API guidelines and Java records push back on 'small classes' and on the data-class smell. Dead-code checks are the opposite case: on by default in every toolchain opened and limited to private or unexported items, with stated limits for reflection, frameworks and side-effect fields. The evidence is mixed once size is controlled. Khomh 2012 (size alone cannot explain the higher change and fault odds), Palomba 2018 and Taba 2013 report harm. Olbrich 2010 (god classes less change- and defect-prone per unit of size), Sjøberg 2013 (no smell raised effort after file size and change count), Hall 2014 (fault effects under 10 percent) and Santos 2018 (no strong evidence on effort, low human agreement) do not. Tufano 2015/2017 shows most smells are present when code is created and 80 percent survive, so checks belong on new and changed code at review. Six rules have evidence for a card. They cover feature envy toward a class with behaviour (with a data-carrier separating condition), a field assigned before every read, unreferenced private or unexported declarations, unread parameters, unused imports, and statements after an unconditional exit. God class stays pending for want of a separating condition, and divergent change needs change history. Shotgun surgery, data class, lazy class, speculative generality and commented-out code fold into cards the corpus already ships: DSN-08, DSN-29, DSN-14 with DSN-06, DSN-19 and CODE-72.

## Formulation layer

The canon frames this topic the same way across sources. McConnell's CC24 'Reasons to Refactor' list and Fowler and Beck's ch. 3 catalog present each smell (poor cohesion or Large Class, divergent change, shotgun surgery, feature envy, lazy element, speculative generality, temporary field, data class) as a sign to look at the code, not as a defect, and the bliki adds that smells "don't always indicate a problem". Dead code and commented-out code are treated more firmly: Clean Code, Remove Dead Code, Tidy First?, 97 Things #17 and Sonar S125 all say to delete it and rely on version control. The official docs and lint rules I opened (Effective Go, rustc dead_code) attach a scope precondition: they flag only unused items that are unexported or local. None of the books could be opened (CC2, Refactoring 2nd ed., Clean Code, APOSD, AntiPatterns, WELC, Pragmatic Programmer, Tidy First?), and the bliki pages are on a denied host, so every book formulation is a marked paraphrase from memory. The fetched formulations come from 97 Things, the Ousterhout–Martin discussion, Software Engineering at Google, Google eng-practices, SWEBOK V3, Effective Go, the rustc lint source, Sonar and PMD. WebSearch was exhausted, and the NWIT bibliography holds none of the core smell papers. The canon disagrees in four places: (1) small classes (Clean Code ch. 10, Fowler's Large Class) against Ousterhout's classitis and over-decomposition; (2) fixing every broken window (Pragmatic Programmer) against leaving untouched mess alone (Refactoring ch. 2, SWE at Google ch. 20); (3) eng-practices' gradual decay through small changes against Tufano 2015's finding that smells are present from inception; (4) YAGNI against SWEBOK's 'anticipating change', which Fowler's Yagni note settles by limiting YAGNI to presumptive features. The four relayed studies split on effect size: Khomh 2012 and Palomba 2018 found more change and fault proneness, while Sjøberg 2013 found no extra effort once file size and number of changes were controlled. Cards should therefore state each smell's effect with the source's precondition.

## Reception layer

Reception splits along what a tool can check reliably. Dead code is checked almost everywhere by default: Go will not compile unused variables or imports, rustc warns on dead_code, and unused-code rules are on by default in ESLint recommended, Ruff, Error Prone (WARNING), the PMD quickstart and SonarPython's Sonar way. Each of these tools limits the check to private or unexported items, or states known limits (reflection, frameworks, dynamic Python, code still being written). Commented-out code is flagged by Sonar S125 and Ruff ERA001, and Ruff notes false positives. Class-level smells are offered but held back. PMD's quickstart comments out GodClass, DataClass, TooManyMethods and TooManyFields. Ruff marks too-many-public-methods as preview and pedantic. Pylint made no-self-use optional as 'too opinionated'. SonarPython's Sonar way leaves out the file-size rule. Data Class is openly contested: PMD flags it, while Pylint exempts dataclasses and its own fix example turns a class into a dataclass plus a free function. Rust API guidelines and Java records endorse passive data carriers, against Landre's 97 Things essay. In research, the effect of smells beyond size is contested: Sjøberg 2013 against Khomh 2012 and Palomba 2018. El Emam 2001 (opened via NWIT) and Rahman and Devanbu 2013 add size confounding and the advantage of process metrics. Tufano 2015 contests the 'arise over time' story that Sonar's Monster Class rule tells. Practitioner sources (SWE at Google ch. 20, Before You Refactor, grug's Chesterton's fence, Abramov) favour acting on smells in code being changed, and the Boy Scout Rule is the counterpoint. No openable source disputes the warning against over-engineering (Google eng-practices, Goodliffe). Could not open: HN and Lobsters threads, 2024 to 2026 surveys (WebSearch budget spent, hosts denied), Silva 2016, CC24 and Fowler ch. 3. No mainstream linter checks divergent change or shotgun surgery; for feature envy only IntelliJ's inspection exists.

I opened the abstracts of almost every candidate study from GitHub-hosted copies. These are maxxbw54/Paper-Repository (TSE, EMSE, ICSE, FSE and TOSEM abstract dumps), the BibTeX dataset of Santos et al.'s 2018 systematic review (hannousse/Semantic-Scholar-Evaluation), IEEE and ACM BibTeX dumps (xw48/secpapers10years), a TOSEM abstract mirror and neverworkintheory. The canon splits on harm once size is controlled. Khomh 2012 ('size alone cannot explain'), Palomba 2018 and Taba 2013 (higher bug density) report more change, more faults or more bug density. Against them, Sjøberg 2013 finds no effort effect after adjusting for size and number of changes. Olbrich 2010 finds god classes changed less and had fewer defects per unit size. Hall 2014 finds fault effects always under 10 percent. Human agreement on smells is low (Mäntylä 2004, Schumacher 2010, Santos 2018), and Tufano 2017 shows most smells exist from creation and 80 percent survive, against the 'grows over time' framing in Vaucher 2009 and Sonar S6539.

## Spine — candidate rules in source order

1. **A code smell marks code to examine rather than a defect, and a finding for one states the effect its source measured under that source's conditions** — A code smell is a surface sign that may point to a deeper design problem. Studies that measured smells found effects that depend on the smell, the system and the outcome measured. A systematic review found no strong evidence linking smells to maintenance effort and low human agreement on smell detection. Where smells affected faults, the effect was always under 10 percent, and only about 30 percent of observed maintenance problems involved files with smells. A finding for a smell therefore names the code as worth examining and states the effect its source measured under that source's conditions, never as an absolute defect.
