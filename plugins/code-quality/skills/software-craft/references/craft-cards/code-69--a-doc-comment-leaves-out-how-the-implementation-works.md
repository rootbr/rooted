# A doc comment describes what a caller needs to know and leaves out how the current implementation works, unless that detail, such as a complexity bound, matters to callers

## Thesis
A routine's doc comment, the comment that the language's documented doc-comment convention attaches to its declaration, states what the routine returns or, for a routine called for its side effects, what it does, and gives enough information to write a call without reading the routine's code. Internal details of how the current implementation works, such as the algorithm it uses, are left to comments inside the body. An implementation detail enters the doc comment only where it is relevant to how the routine is to be used, such as an asymptotic time or space bound that is particularly important to callers, a performance implication of how the routine is used, or the side effect of mutating one of its arguments. The same split holds for any declaration: its doc comment is written for a user of the code, and a comment that only concerns the implementation is an ordinary comment.

## Rationale
Tools such as editors and documentation generators understand doc comments, while ordinary comments are only for other humans; the doc comment is the comment a user of the code reads, and it gives enough information to write a call without reading the routine's code. It focuses on what the operation returns or does, detailing what the caller needs to know, and special cases can be particularly important to document. The comment at the declaration describes use of the routine where that is not obvious, and the comments at its definition describe its operation. Details of the implementation that are not relevant to the caller, however subtle and important, are better expressed as comments beside the code than in the doc comment. An example doc comment for a sort routine in a language's doc-comment guide shows the split: it states that the sort makes one call to the length method and O(n*log(n)) calls to the comparison and swap methods, says the sort is not guaranteed to be stable, and names no sorting algorithm. Because it makes no mention of which algorithm is used, it is easier to change the implementation to a different algorithm in the future.

## Example
```go
bad:  // Index returns the position of key in keys, or -1 if key is absent.
      // It runs a binary search, keeping lo and hi and halving the gap each step.
      func Index(keys []string, key string) int { ... }
good: // Index returns the position of key in keys, or -1 if key is absent.
      // keys must be sorted in ascending order; Index makes O(log n) comparisons.
      func Index(keys []string, key string) int {
          // Binary search: halve [lo, hi) until it is empty.
          ...
      }
```

## Limits
A detail that is relevant to how the routine is to be used stays in the doc comment even when the implementation decides it: an asymptotic time or space bound particularly important to callers, a performance implication of how the routine is used, the side effect of mutating an argument, and a special case or other behaviour a caller sees, such as whether a sort is stable. An input requirement that the algorithm imposes, such as sorted input, is stated as a requirement on the call's inputs; the algorithm stays unnamed unless callers observe it, as when the routine calls a caller-supplied function at the points the algorithm visits. A comment inside the body that explains the algorithm is where that detail belongs, and the rule flags nothing there; a doc comment that omits a bound is not flagged either, since a bound is admitted where it matters to callers, not required. A note on the current implementation that the doc comment sets apart under a heading or tag naming it as such, such as a current-implementation section or an implementation-note tag, is outside the rule: the label keeps the note out of the guarantees callers rely on, so the implementation stays free to change. A documentation convention stated in the project context that keeps implementation notes in doc comments rejects the finding. The rule weighs where an implementation detail is written; whether a routine needs a doc comment at all, whether a doc comment states everything a caller needs, whether a comment restates the code, and whether a comment still agrees with the code are separate questions.

## Validator
In the hunk's added lines, find each doc comment: a comment in the form the language's documented doc-comment convention gives to documentation, with its continuation lines, or, where that convention attaches a plain line comment to the declaration that follows it, the comment block directly above a declaration. Read it with the declaration it documents. Mark each sentence that tells how the current implementation works rather than what the routine returns or does: the algorithm it runs, the internal data structures it keeps or builds, the helpers it calls, the loop or the steps it goes through. Clear the part of a marked sentence that states an asymptotic time or space bound, a performance implication of how the routine is used, a side effect such as mutating an argument, a special case, an input requirement, or another behaviour a caller observes, such as ordering, stability, an equivalence to a sequence of public calls, or the calls made to a caller-supplied function. Skip comments inside the body and any text under a heading or tag that sets it apart as a note on the current implementation, and skip the finding where the project context keeps implementation notes in doc comments. Validator question: **Does an added doc comment, outside a heading or tag set apart for notes on the current implementation, describe how the current implementation works (its algorithm, internal data structures, helper calls or steps) beyond a time or space bound, a performance implication of use, a side effect, a special case, an input requirement or another behaviour a caller observes?** Yes → flag.
