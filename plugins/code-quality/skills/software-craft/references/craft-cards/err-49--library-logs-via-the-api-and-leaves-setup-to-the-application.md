# Library code logs through the logging API its users configure and leaves the logging implementation, its handlers and its configuration to the application

## Thesis
Code shipped as a library for other programs to use writes its log records through the logging API or facade of its language or codebase, and leaves to the application that uses it the choice and initialization of the logging implementation, the handlers that deliver records to their destinations, and the verbosity. Where the facility names its loggers, the library's records go to a logger named for the library's package or module, not to the root logger. On its own initiative — at import, in a constructor, or inside a routine whose purpose is other than setting up logging — the library's code calls no configuration routine of the logging facility, initializes or installs no logging implementation, sets no process-wide logger, output or level, and adds no handler to any logger other than a do-nothing one on the library's own loggers. The application chooses its logging implementation and initializes it early in the program's run, from its entry point, usually by calling the initialization function that the implementation provides; a library that is itself a logging implementation, or a library routine that exists only to set up logging, holds that setup for the application to call.

## Rationale
A logging facade is a single logging API over the logging implementation: libraries log through it, and the program that uses them chooses the implementation most suitable for its use case. The end user who deploys the library is the one who has to read the logs and process them, and a library that configures logging on its own often overrides that end user's wishes; a library that hands its users a transitive dependency on one specific implementation imposes that implementation on them, which defeats the purpose of the facade. Configuring handlers is the prerogative of the application developer, and handlers a library adds under the hood might well interfere with the application developer's unit tests and with delivering logs that suit their requirements. When every logging package supports one handler interface, an application that has linked in many of them gets consistent logging across all its dependencies by creating one handler in its main function and installing it once for each logging library. Records sent to the root logger make it difficult or impossible for the application developer to configure the library's verbosity or handlers as they wish, and carry the root logger's name rather than the library's, which makes them less useful for debugging. A library that leaves configuration alone still works when the application configures none: one facility then prints the library's events of warning severity and above to standard error, which its documentation regards as the best default, another emits a single warning and discards every record, and a third ignores the records made before an implementation is initialized.

## Example
```python
bad:  logging.basicConfig(level=logging.DEBUG)
      logging.getLogger(__name__).addHandler(logging.StreamHandler())
      logging.info("fetched %d rows from %s", count, table)
good: logger = logging.getLogger(__name__)
      logger.info("fetched %d rows from %s", count, table)
```

## Limits
A library's tests need a logging implementation while they run, and a test-scope dependency on one does not affect the library's end users, so test code and test-only dependencies may install and configure an implementation. A do-nothing handler attached to the library's top-level logger, so that its records are not printed when the application configures no logging, is within the rule. An executable that the library's package also ships, such as a command-line tool or a script's main block, is application code, and its entry point chooses and initializes the implementation. A dynamic library may need a wrapper, safe across a foreign-function interface, through which it initializes logging itself. A library that is itself a logging implementation, or a routine a library exports only to set up logging, holds its initializing and configuring calls in the function the application calls from its entry point; that function is within the rule, and the same calls run at import, in a constructor, or inside a routine with another purpose are not. The check covers a library's logging setup and its root-logger calls; whether a print or console call ought to be a log record is a separate question. A module the project context marks as application code is outside the rule.

## Validator
Decide first whether the file is library code: a module that other programs import, rather than an executable's entry point, a command-line script, a test, a test fixture or test-only configuration; read the path, the packaging hints in the file and the project context. In the hunk's added lines, find logging setup and root-logger use: a call that configures the logging facility or initializes or installs an implementation, a call that sets the process-wide default logger, its output, flags or level, a handler added to a logger, and a logging call or logger lookup that targets the root logger where the facility offers named loggers. Open the file to confirm that the call runs as part of the library — at import, in a constructor, or in a routine its callers invoke for a purpose other than setting up logging — and not inside a main guard, an entry point, or the initialization function that a logging implementation, or a library routine that exists only to set up logging, provides for the application to call. A do-nothing handler on one of the library's own loggers passes, and so does setup inside a wrapper the file documents as the logging initialization of a dynamic library called across a foreign-function interface. Validator question: **Does library code added in this hunk configure the logging facility, initialize or install a logging implementation, set the process-wide logger, output or level, add a handler other than a do-nothing one on the library's own loggers, or log to the root logger where named loggers are available?** Yes → flag.
