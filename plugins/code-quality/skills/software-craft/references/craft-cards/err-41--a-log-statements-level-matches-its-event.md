# A log statement's level matches its event, with routine events at info or below, a failure the code does not pass on at warning or above, and diagnostic detail at debug or trace

## Thesis
A log statement records its event at the level whose meaning matches the event. A routine event that confirms things are working as expected, such as a start-up, a completed step or a successful call, is recorded at info or below. A failure the code handles without raising or returning it is recorded at warning or above: at error or above when the software could not perform some function, at warning when something unexpected happened or a problem lies ahead while the software still works as expected. Detail of interest only when diagnosing a problem is recorded at debug or trace. A facility whose levels carry other names applies the level of the same meaning.

## Rationale
A record's level decides how it is shown and whether it is recorded at all. A record at error or above indicates an erroneous situation, which a viewer may display in a different colour or find along with every other erroneous record. A configuration records only the levels at or above its threshold: one common configuration records info and above and suppresses debug until it is needed, another tracks only warning and above by default, and trace is typically disabled in default configurations. A misjudged level therefore costs in both directions. A real error recorded at a level that is not enabled by default, such as debug, leaves important error messages missing for failure diagnosis: in one studied program, a configuration error logged at info, which was not a default level for its production runs, went unreported until its developers, after diagnosing it without logs, changed the level to error. A non-error event recorded at error level may confuse users and developers or cause unnecessary overhead in production runs. Detail of interest only when diagnosing belongs at debug, which the common configuration suppresses until it is needed; recorded at info, it is output on every run of that configuration. Developers often do not assign the right level the first time: in four large, widely used open-source programs with server components, 2,389 (26%) of the 9,076 modifications made to logging code as after-thoughts, rather than as updates consistent with other code changes in the same patch, changed a message's verbosity level; in 1,712 (72%) of those an error level stood before or after the change, and among these 277 raised a message from a non-error level to an error level and 376 lowered one from an error level to a non-error level.

## Example
```go
bad:  slog.Error("worker started", "queue", name)
      slog.Info("calling sendReport", "report", r)
      if err := sendReport(ctx, r); err != nil {
          slog.Debug("send report failed", "id", r.ID, "err", err)
      }
good: slog.Info("worker started", "queue", name)
      slog.Debug("calling sendReport", "report", r)
      if err := sendReport(ctx, r); err != nil {
          slog.Error("send report failed", "id", r.ID, "err", err)
      }
```

## Limits
A condition the code expects and handles as an ordinary outcome, such as a lookup that finds nothing, after which the software still performs its function, is an event of normal operation and fits info, or debug for very detailed output. A failure the code raises or returns is reported by that act, so a debug record of it at the raising site follows the rule; the level is judged where the failure is handled without being passed on. Choosing between an error level and a fatal level that aborts the process changes how the program runs as well as what it records, and lies outside this rule, as does the choice among a facility's several verbose levels. For a failure the code does not pass on, the rule holds the record to warning or above and does not judge between warning and error, which turns on whether the software could still perform its function. Which of error and critical fits a suppressed error depends on the specific error and the application domain, so a level policy the project documents for its domain governs that choice and any level such a policy assigns to an event; the tolerance is the one the project context states. The rule judges the level of a record the code writes: whether an event warrants a record at all, what the record says, and the threshold a program configures lie outside it. A failure the code expects and recovers from by design, so that the software is still working as expected, may be recorded at info, and at debug where it indicates no actual issue, such as a request the client cancelled; the level of such a record is judged by its own rule.

## Validator
Grep the added lines for a log call: a logger or console method named for a level (error, warn, warning, critical, fatal, severe, info, debug, trace, fine, finer, finest), a level macro, or a log call that takes the level as an argument. Skip a call through a facility that has no levels. For each call, read its message and the hunk around it and classify the event it records: a routine event (a start-up, a completed step, a successful call, an expected outcome the code treats as normal), a failure (a caught exception, an error result, a failed check), or detail of interest only when diagnosing (entering or leaving a routine, a dump of a value or a state). For a failure, trace the handler to its end in the hunk: when the code raises, returns or rethrows the failure, or records it again at warning or above, skip. Compare the level with the event, and skip a choice between warning and error for a failure the code does not pass on, a choice between an error level and an aborting fatal level, a choice among verbose levels, and a level a documented project policy assigns. Validator question: **Does an added log call record a routine event at warning or above, a failure the code does not pass on only below warning, or detail of interest only when diagnosing at info or above?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-41`, severity minor, `file`, `symbol`, `code` = the added log call, verbatim from the diff, `fix` = the same call at the level whose meaning matches its event (info or debug for a routine event, warning or error for a failure the code does not pass on, debug or trace for diagnosing detail), in the file's language, `rationale` = the event the call records, the level it uses, and which reader misses or misreads the record at that level).
