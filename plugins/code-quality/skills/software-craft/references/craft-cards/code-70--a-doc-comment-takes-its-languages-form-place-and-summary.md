# A doc comment takes its language's documented form, sits where the documentation tool attaches it and opens with the summary its convention prescribes, and an implementation note takes ordinary comment syntax

## Thesis
Text written for the users of a declaration is in the doc-comment form that the language's documentation tool reads, at the position where that tool attaches it, as the language's documented convention places it: before the declaration, with no blank line between and ahead of any annotation or decorator where the tool requires each, or as the first statement of its body. A doc comment opens with the summary its convention prescribes, of the length and set apart from the rest as that convention says, and the summary's form (its mood, a fragment or a full sentence, whether it starts with the declared name) and the comment's layout (labelled sections, block tags in a set order, or plain sentences) follow the governing convention: the documentation style the project declares, else the form the file's existing doc comments use where the documented conventions for the language disagree or admit more than one form, else the language's documented convention. Doc-comment syntax stands only where the tool attaches it to a declaration; anywhere else it is moved to the declaration it describes, turned into an ordinary comment, or deleted. A note on how the code is implemented that does not concern its users is an ordinary comment beside the code it explains.

## Rationale
A documentation tool reads a comment only in its doc-comment form and only where it attaches it, which depends on the language: immediately before a top-level declaration with no intervening newline, just before the item it documents, before any annotation (after one, the compiler fails to recognise it as documentation) or decorator, or as the first statement of a module, class or routine. Editors and documentation generators understand doc comments, while ordinary comments are only for human readers of the source, so text for callers written as an ordinary comment is missing wherever tools present documentation, the command-line lookup that prints a symbol's doc comment included. Doc-comment syntax where the tool attaches nothing, such as on a statement inside a routine, on a class or method nested in a routine, between an annotation and its declaration, or with no declaration after it, is ignored and does not end up in the generated documentation; one compiler warns on it by default and suggests a plain comment, and static analysers flag it, one giving the fix as moving it to the right place, converting it to an ordinary comment or removing it. The summary is the part tools show on its own: it is reused to describe the declaration in searches and module overviews, may be used by automatic indexing tools, and in one convention is the only part of the text that appears in class and method indexes; a doc comment with no summary, such as one that opens with a block tag for the return value (an inline return tag that the tool expands into the summary sentence is a summary), is a documented mistake that a static check flags on public and protected declarations. The conventions bound the summary differently: one line separated from the rest by a blank line; one physical line of at most 80 characters ending in a period, question mark or exclamation point; everything before the first empty line, kept to one line as good practice; a brief fragment; a first sentence that starts with the name being declared. They differ on its form too: one prescribes the command form ("Return that") and rejects the descriptive "Returns the pathname ...", one admits either form provided it is consistent within a file, one requires a noun or verb phrase fragment rather than a complete sentence or an imperative and gives "Returns the customer ID." as correct, and one starts with complete sentences naming the declared symbol. Layout differs the same way: sections that each begin with a heading line ending in a colon; error and panic conditions each in a section of its own; block tags in the order parameter, return, throws, deprecated and never with an empty description; parameter and return tags only where they add information; complete sentences. A summary form that one convention gives as correct another rejects, so each doc comment is held to the convention that governs it. Implementation detail that is not relevant to the caller is better expressed in a comment alongside the code than in the doc comment, whose readers want to know how to use the code rather than how it is implemented.

## Example
```rust
bad:  // Returns the position of the first item with this key, if any.
      pub fn find(items: &[Item], key: u32) -> Option<usize> {
          /// A linear scan; the list never exceeds a few dozen items.
          items.iter().position(|i| i.key == key)
      }
good: /// Returns the position of the first item with this key, if any.
      pub fn find(items: &[Item], key: u32) -> Option<usize> {
          // A linear scan; the list never exceeds a few dozen items.
          items.iter().position(|i| i.key == key)
      }
```

## Limits
A detail of the implementation that bears on how the routine is used, such as a side effect on an argument it mutates, belongs in the doc comment. Where the governing convention lets a non-public routine carry an ordinary comment that describes it, placed after the routine's header line, in place of a doc comment, that comment meets the rule. Where the convention requires its summary and formatting only on the documentation it requires, as on public and protected declarations, an optional doc comment on another declaration is not flagged for its summary or format. Doc-comment syntax that the language's tools attach to something other than a following declaration is attached, not dangling: an inner doc comment that documents the enclosing module, and a string literal right after a simple assignment at the top level of a module, of a class body or of a constructor, or right after another doc comment, which tools may extract as documentation. A single-line comment holding one XML tag that the compiler reads as a directive is not a doc comment. Where the language's doc comment is an ordinary comment distinguished only by its position, the form check reduces to that position: no blank line between the comment and the declaration. Where the documented conventions for the language disagree or admit more than one form, as on the summary's mood, a summary in the form the file's existing doc comments use meets the rule. The rule judges a comment's form, position, summary and layout and where an implementation note sits; whether a declaration needs a doc comment at all, and whether a comment's content is accurate, complete or needed, are outside it. A documentation-style tolerance stated in the project context, such as a declared summary mood or section layout, rejects the finding.

## Validator
Grep the added lines for doc-comment openers and block tags, and for ordinary comment lines directly above a declaration. For each, read the hunk context: the declaration or statement that follows, any annotation, decorator or blank line in between, and the file's other doc comments. Classify the comment as text for the declaration's users (what it does, returns, requires, raises or changes) or as a note on how the code works. For user-facing text, check that it is in the language's doc-comment form at the attaching position; where the language's doc comment is an ordinary comment placed before the declaration, check only that no blank line separates them. For doc-comment syntax, check that it sits at a declaration's attaching position, before the declaration or as the first statement of its body as the language places it, unless the comment documents the enclosing module, follows a simple assignment at the top level of a module, a class body or a constructor, or another doc comment as the language's tools allow, or is a compiler directive. For each doc comment, check that it opens with a summary of the length, separation and form the governing convention sets, that its layout is that convention's, and that it carries no implementation detail that does not bear on how the declaration is used. Take the governing convention from the project context's declared documentation style, then from the file's existing doc comments where the documented conventions for the language disagree or admit more than one form, then from the language's documented convention; skip a non-public routine described by an ordinary comment where that convention allows it, and the summary and format of an optional doc comment that convention exempts. Validator question: **Does an added comment put text for the declaration's users in a form or position its documentation tool does not attach, put doc-comment syntax where that tool attaches it to no declaration, open a doc comment with anything other than the summary the governing convention prescribes or lay it out against that convention, or carry in a doc comment an implementation note that does not concern the caller?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-70`, severity suggestion, `file`, `symbol`, `code` = the added comment lines and the declaration or statement they document or precede, quoted verbatim from the diff, `fix` = the comment in the language's doc-comment form at the attaching position with the governing convention's summary first, or turned into an ordinary comment beside the code it explains, or removed, in the file's language, `rationale` = which part fails (form, position, summary, layout, or an implementation note in a doc comment) and the convention that governs it).
