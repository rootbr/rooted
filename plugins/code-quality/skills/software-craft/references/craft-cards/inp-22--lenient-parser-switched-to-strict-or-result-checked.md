# A parser that by default accepts forms outside the format the code accepts, such as duplicate JSON names, NaN, malformed CSV, rolled-over dates or unvalidated URLs, is switched to its strict mode or its result is checked before use

## Thesis
Where a parser's default accepts forms that the code's stated input format excludes, the code sets a strict option of the parser that rejects those forms, uses a parser whose default rejects those forms, or verifies the parsed components before using them; a successful parse alone is not taken as proof that the input conforms to that format. The forms in question are those a parser documents as accepted by default: the number values NaN and Infinity in JSON, repeated names within an object with only the last value used, bad CSV input while the strict flag is off, date text not in the formatter's form or with a field beyond its range, and URLs the parser does not validate.

## Rationale
Several standard parsers succeed on input outside the format they are named for. One JSON decoder accepts Infinity and NaN as number values, and accepts repeated names within an object, using only the value of the last name-value pair. Another matches incoming names to record fields case-insensitively by default, and its documentation calls that matching another vector through which duplicate names can occur. A CSV reader raises an error on bad input when its strict flag is true, and the flag defaults to false. A date parser lets the parse succeed by default when the input is not in the form its format method uses but can still be parsed as a date, and its calendar, lenient by default, treats "February 942, 1996" as the 941st day after February 1, 1996. Its strict option does not make the single-argument parse consume the whole text: that parse may not use the entire text of the given string, so a valid date followed by other text still parses. A date formatter built from a pattern uses the smart resolver style, which in the ISO calendar keeps the day-of-month from 1 to 31 and converts any value beyond the last valid day-of-month to that last valid day. A URL splitter performs no validation and may return components that contain more than perhaps they should; a URL constructor gives no guarantee that the instance conforms to the URL syntax specification; a URL parser counts input that includes credentials as a validation error, and a validation error does not mean that the parser terminates. Code that takes such a parse as its syntax check has the weakness of receiving input expected to comply with a syntax without validating that it does: when untrusted input is not validated for the expected syntax, attackers could cause parsing failures, trigger unexpected errors, or expose latent vulnerabilities that might not be directly exploitable if the input had conformed. Where several programs read the same text, it is important that all of them agree on its meaning. Many JSON texts are syntactically valid but semantically ambiguous, duplicate names among them, and if an authenticating service and an executing service believe the same crafted request is from different users, an attacker could bypass the authenticator with valid credentials for one user and act on behalf of another. A public JSON test suite marks a class of inputs that parsers are free to accept or reject, and a survey of parser differentials catalogues the anti-patterns underlying them, including an XML vulnerability in which faulty Unicode parsing produced a higher-order parser differential. The strict option, or some verification of a returned component before trusting it, is the means the documentation offers to reject input that does not strictly conform: a hook that raises on invalid JSON numbers or alters the handling of repeated names, a strict dialect flag, non-lenient date parsing that insists on strict adherence to the format, a strict resolver style that rejects a day-of-month invalid for its year-month, or a decoder whose default rejects duplicate names.

```typescript
good: const endpoint = new URL(input);

```

## Limits
Where the forms a parser accepts beyond the specification belong to the format the code states it accepts, accepting them is a stated decision, not a defect: coercing input to the desired type is useful in many scenarios, such as UUIDs, URL parameters, HTTP headers, environment variables and dates, and a strict mode is the opt-in for situations where coercion is not desirable. The separating condition is whether the stated format itself allows that range of expressions: a format can explicitly allow a range of valid expressions of the same semantics, with precise definitions for error handling, and that is distinct from relying on the robustness principle, where interoperation depends more extensively on implementations making compatible decisions. Where input is provided by users, allowing flexibility might make a format more accessible, especially for non-expert users. Outside the stated format the strict side holds: reject any input that does not strictly conform to specifications, or transform it into something that does; ignoring faulty or ambiguous input is almost always the incorrect solution; one language's API guidelines set aside the robustness principle and have its code enforce the validity of input whenever practical; a JSON decoder whose defaults are chosen for strictness and interoperability rejects duplicate names. A parser whose default already rejects the ambiguous form, such as an IPv4 address parser that does not tolerate leading zeros to prevent confusion with octal notation, satisfies the rule without an option. The rule reaches the syntax the input is expected to comply with; the other properties input validation considers, such as the full range of acceptable values and conformance to business rules, lie outside it.

## Validator
Grep the hunk for a call that parses JSON, CSV, a date or a URL. Open the file and establish the format the code states it accepts: the declared type or schema, a comment or specification reference, or what the parsed value is used for. Look up the parser's documented default for non-standard number values, repeated or case-folded names, bad delimited input, out-of-range date fields and unvalidated URL components, and check whether the call sets the parser's strict option and whether that option rejects the form in question; a parse call that may not use the entire text also needs a check that the whole text was consumed. Trace the parsed value from the call to its first use and look for a check of its components, such as scheme, credentials, host, field count or a round trip of the date, in between. Validator question: **Does the code act on a form its stated format excludes because it uses the result of a parser whose documented default admits that form, with neither an option set that rejects that form nor the parsed components checked before use?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-22`, severity major, `file`, `symbol`, `code` = the parser call and the first use of its result, quoted verbatim from the diff, `fix` = the same call with the parser's strict option set, a call to a parser whose default rejects the excluded form, or a check of the parsed components that rejects the excluded form before use, in the file's language, `rationale` = the lenient default the parser documents and the form the code's stated format excludes).
