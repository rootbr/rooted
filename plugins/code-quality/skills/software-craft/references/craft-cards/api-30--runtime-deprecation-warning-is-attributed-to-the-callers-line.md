# A deprecation warning emitted at run time is attributed to the caller's line rather than to the line inside the deprecated element

## Thesis
A deprecation warning raised at run time inside an element that other code calls, by a call that records a source location, reports the line in the caller's code that used the element, not a line inside the element or elsewhere in the library. The warning call reaches that line with the means its interface provides: a stack level that names the deprecated routine's caller — 2 where the interface numbers the warning call's own line 1, and 1 where it numbers the line that queries the location 0 — when the deprecated routine raises the warning itself and its caller calls it directly, and one more for each routine in between when a helper it calls raises the warning or a wrapper stands between it and its caller; a list of the library's own files to skip, when no constant level fits every call path; the deprecated routine named as the function at which to cut the recorded stack trace; or a caller-tracking marker on the deprecated routine and on each routine between it and the location query.

## Rationale
A warning that refers to the source of the deprecated element itself, rather than to its caller, defeats the purpose of the warning message; attributed to the caller's line, it appears to come from the correct place and gives the caller context. By default the reported location is the warning call's own: a stack level of 1 names the line on which the warning call stands and each higher level names a frame further up the stack, so a routine that warns on entry needs level 2 to name its caller; a location query in an unmarked routine points at its own line wherever the routine is called from; and a recorded stack trace is cut by default at the warning call, so it starts in the routine that raised the warning, while naming another function at which to cut it leaves out of the trace that function and every frame it called, so the trace starts at the line that called it. A caller-tracking marker makes a location query return the call site in the nearest unmarked routine up the stack, so marking every routine from the query up to the deprecated entry point yields the caller's line. The reported location also decides whether the warning is seen at all. Where a runtime's default filter shows deprecation warnings only when their nominal location, as the stack level sets it, is in the main program, a warning attributed to the library's line stays hidden even when the main program made the call. In such a runtime the deprecation category, meant for developers who call the library, reaches them through the main program and through test runners, which display all warnings for the code under test, while a warning meant for the end users of an application takes a category reported for all code.

## Example
```rust
bad:  pub fn open(mode: &str) -> Handle {
          if mode == "v1" { eprintln!("{}: mode v1 is deprecated; use v2", Location::caller()); }
          ...
      }
good: #[track_caller]
      pub fn open(mode: &str) -> Handle {
          if mode == "v1" { eprintln!("{}: mode v1 is deprecated; use v2", Location::caller()); }
          ...
      }
```

## Limits
A deprecation marked with the language's deprecation attribute, annotation or doc-comment tag, and reported by the compiler, type checker or linter at each use, already names the use site; the rule covers warnings raised at run time. A deprecation decorator whose documented default already emits the warning at the direct caller of the deprecated object is correct with that default when the code that uses the element calls the decorated object directly; where another wrapper stands above the decorated object, that wrapper is the direct caller, and the level counts it. A warning call that records no source location, and the choice between the developer-facing deprecation category and a category reported for all code, are outside the rule, which judges only where a warning points. A caller-tracking marker is a hint the implementation need not preserve: a call through a function pointer, including a method called through a type-erased object whose methods are marked, appears to come from the marked routine's definition site, and such a call path is outside the rule.

## Validator
Grep the added lines for a deprecation raised at run time: a call to a warning facility, a deprecation or future-warning category, a process-warning call, a print or log call whose message says deprecated, a deprecation decorator, a stack-level argument, and a source-location query. For each hit, read the enclosing routine in the hunk and confirm that the warning records a source location and is raised inside an element other code calls; skip a warning that records no location, a deprecation the compiler, type checker or linter reports from a marker, and a decorator left at a documented default that already names the direct caller, with no other wrapper above the decorated object. Count the frames from the warning call up to the caller's line in the numbering the interface documents: where the warning call's own line is level 1, the line that called its routine is level 2; where a skip count numbers the line that queries the location 0, the line that called its routine is 1; each routine in between, a helper below the deprecated routine or a wrapper above it, adds one; a deprecation decorator numbers its levels from the element's direct caller, so its level 1 is the caller's line and each higher level names a line one routine further up. Read what the call passes — a stack level, where an omitted one is the default of 1; a list of the library's own files to skip; a function at which to cut the stack trace; or a caller-tracking marker on each routine from the location query up to the deprecated entry point — and check that it reaches that line. Validator question: **Does an added runtime deprecation warning report a location other than the caller's line that used the element, such as the warning call's own line, another line in the library, or a line further up the stack than that caller?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-30`, severity minor, `file`, `symbol`, `code` = the warning call or location query quoted verbatim from the diff, `fix` = the same warning with the stack level, skip list, trace-cutting function or caller-tracking marker that makes it report the caller's line, in the file's language, `rationale` = the location the warning reports now and the caller's line it should name).
