# A tool-generated change holds only the edits its rewrite requires, keeping the comments and layout of the code it does not rewrite, and leaves other hand edits, dependency updates and reformatting to separate changes

## Thesis
A change produced by a rewriting tool holds only the edits its rewrite requires: the tool's output on the lines it rewrote, the whitespace its own formatting pass changes on the lines beside them, and a dependency version the tool itself changes or a hand fix without which the rewritten code does not build, with the comments and layout of the rest of the code kept. Other hand edits, dependency updates and reformatting of code the tool did not rewrite go in separate changes, and a run over a large project may apply the fixes of its most prolific rules as separate changes.

## Rationale
A rewriting tool may fix hundreds of files in one run, and its fixes are expected to be applied with only cursory review, which is why the fixer has to be correct even in obscure edge cases. For a large change generated by an automatic refactoring tool the reviewer trusts completely, the reviewer's job is just to verify and say that the change is really wanted; such a change can be larger, while merging and testing still apply. Starting the run from a clean working state makes the change consist only of edits from the tool, which eases its review. Dependency updates committed on their own keep a logical separation of commits, and formatting changes in a separate commit show which changes are just formatting versus other code changes and can possibly be ignored in blame. Reprinting a file from an abstract syntax tree yields code that is not necessarily equal to the original, whereas a concrete syntax tree keeps all formatting details (comments, whitespace, parentheses), and a lossless semantic tree prints the source back without clobbering formatting, with the code it inserts matching the local style around it. Adjacent comments are among the tricky edge cases that a refactoring primitive such as deleting a statement has to handle correctly. Format preservation is necessary wherever formatting is not 100% consistent throughout the repository, while a formatting pass run with the rewrite aligns the lines beside a rewritten one. A migration recipe may change a dependency's version in the same run as the code that needs it, and the sites it could not migrate are fixed by hand before the results are committed; when changes depend on each other, the whole system has to keep working after each one is submitted. On a large project, applying the fixes of the most prolific rules as separate changes may reduce the burden of review.

## Example
```rust
bad:  // cargo fix --edition added `dyn`; the same change dropped the doc line, reflowed, hand-edited
      fn shapes(n: usize) -> Vec<Box<dyn Shape>> { Vec::with_capacity(n * 2) }
good: /// Returns an empty list sized for `n` shapes.
      fn shapes(n: usize) -> Vec<Box<dyn Shape>> {
          Vec::with_capacity(n) // only `dyn` above came from the tool
      }
```

## Limits
A change that holds only a dependency update, or only formatting, is the separate change the rule asks for and is outside it, and so is the edition or toolchain field a migration sets in its manifest. A dependency version the tool itself changes and a hand fix at a site the tool reports it could not migrate belong to the tool's change when the rewritten code does not build without them, and whitespace that the tool's own formatting pass changes on a line beside a rewritten one, such as fields or trailing comments realigned after a rename lengthens a line, is part of its output. The rule judges what a tool-generated change holds, not whether each rewrite preserves behaviour; merging and testing still apply to such a change however it was produced.

## Validator
Grep the hunk and the change description for the name of a rewriting tool, a migration command or an inline directive. Open the hunk and sort each changed line: a line inside an expression the rewrite targets, whitespace the tool's formatting pass realigned on a line beside a rewritten one, a dependency version the tool itself changed or a hand fix the rewritten code needs to build, and the edition or toolchain field the migration sets in its manifest belong to the tool's change; any other line that differs only in whitespace, wrapping or line breaks, a comment deleted or moved beside a rewritten line, a dependency update the tool did not make, or another edit of a kind the tool's rule does not make does not. Trace each deleted comment to whether the rewrite removed the statement it annotated. Validator question: **Does a change presented as a rewriting tool's output also hold a changed line that the sort leaves outside the tool's change, such as a dependency update the tool did not make, a hand edit its rewritten code does not need to build, reformatting its formatting pass did not make beside a rewritten line, or the loss of a comment the rewrite did not require?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-29`, severity minor, `file`, `symbol`, `code` = the changed line that is not the tool's output, quoted verbatim from the diff, `fix` = the line as the tool alone would leave it, with the hand edit, dependency update or reformat moved to its own change, in the file's language, `rationale` = the kind of edit mixed into the tool's output and the review it costs: the change can no longer be checked as the tool's output alone).
