# Maintaining software-craft

What changes together when a card, a script, a prompt, a signal or a tier changes, what to re-run, and how a topic is researched. Paths are relative to the skill directory; `plugins/` paths from the repository root. `README.md` §Layout maps who reads or runs each file.

- Before committing a card, an agent prompt or SKILL.md: `maintenance/scripts/validate-craft-cards.py --pending maintenance/pending-evidence.md references/craft-cards`, for a Python card `maintenance/scripts/validate-craft-cards.py --language python --pending maintenance/pending-evidence-python.md references/craft-cards-python`, and for a Java card `maintenance/scripts/validate-craft-cards.py --language java --pending maintenance/pending-evidence-java.md references/craft-cards-java`, then the audit (repository Quality Gate).
- A rule is one card in `references/craft-cards/`; adding or removing one means its card, its `maintenance/craft-cards-provenance.md` line, its topic's research note under `research/software-craft/` (the "Cards derived" table), and a `maintenance/craft-cards-taxonomy.md` value when a facet is new; a `META-` card's line names the checklist section it was carded from in place of a research note.
- A Python rule is one card in `references/craft-cards-python/`; adding or removing one means its card, its `maintenance/craft-cards-python-provenance.md` line and its topic's research note under `research/software-craft-python/`. A Java rule is one card in `references/craft-cards-java/` and its line in `maintenance/craft-cards-java-provenance.md`; that line, with the origin section of the Java review checklist it names, is the whole record of the rule's sources. A further language corpus registers its prefix and language in `LANGUAGE_PREFIXES` in `scripts/cardlib.py`, together with its `applies_to` value as a new facet value.
- The validator rejects a `## Source` heading: a card's sources live on its provenance line, which `scripts/render-reports.py` reads for a finding's source pointer and `scripts/craft-cards.py --provenance <RULE_ID>` prints (`BLOCKS` and the provenance helpers in `scripts/cardlib.py`). `cardlib.provenance_map_path` is the one place that knows a map's address — `maintenance/<corpus>-provenance.md` for `references/<corpus>/` — and the renderer, the card index, the validator and `maintenance/scripts/write-topic-result.py` go through it.
- A rule with no openable evidence, or a contested rule with no sourced separating condition, lives in `maintenance/pending-evidence.md` (a Python rule in `maintenance/pending-evidence-python.md`, a Java rule in `maintenance/pending-evidence-java.md`) until one is found; it has no card and no id.
- A topic is re-researched, or a new one added, through `maintenance/scripts/research-topic-workflow.js` with the topic's row from the design note's taxonomy as its arguments; `maintenance/scripts/write-topic-result.py` writes the run's note, cards, provenance lines and pending entries, renumbering ids contiguously from the cards already in the tree, and merges several runs of one topic. A cut-short run continues from its journal through `maintenance/scripts/research-continue.py`, whose bundles carry the finished stages as `resume_state`; the second fix round is the same script with `--round 2` over the journals of the first, carrying only the rules the skeptic sent back with `revise`, and `--closing-edit` ships a rule the last verdict sent back after the drafter applies that verdict's edits verbatim. A new topic is a new row in the design note's taxonomy table and a new entry in its deviations section. A Python topic runs through `maintenance/scripts/harvest-python-sources.py`, `maintenance/scripts/python-corpus.py`, `maintenance/scripts/python-triage-workflow.js` and `maintenance/scripts/python-topic-workflow.js`, as `research/2026-10-15_software-craft-python-cards.md` records.
- When the aggregation definitions, the schemas, the severity scale or the prompts change, change `scripts/craft-review-workflow.js` and `plugins/code-quality/agents/craft-finder.md` / `craft-verifier.md` in the same commit as SKILL.md §Aggregation and §Workflow; the severity scale is also `SEVERITIES` in `scripts/cardlib.py`, the table of SKILL.md §Phase 8 and `GRAVE` and `RECOMMENDATIONS` in `scripts/render-reports.py`; when the stages, the parts or the result shape change, `scripts/bundle-run.py`, `scripts/merge-parts.py`, `scripts/render-reports.py` and their tests change with the workflow; when the developer's procedure, the design brief's sections or the dispatch table change, `plugins/code-quality/agents/software-developer.md`, SKILL.md §Build model, §Design and §Build and the design note's §Design → Build contract change together.
- When a card's triggers, a structural signal, a threshold or the candidate list change, change `scripts/static-craft.py` (`SIGNALS`, `THRESHOLDS`, `CANDIDATE_RULE_IDS`, and `LANGUAGE_CANDIDATES` for a language's own heuristics), `scripts/cardlib.py` (`SIGNALS`), the design note's "Structural signals" table and `maintenance/tests/test_static_craft.py` together, then re-run the tests (§Scripts) and the fixture grading (`evals/grade.py`) in both modes of `evals/fixture/make-fixture.sh`, and for a Java card or heuristic in both modes of `evals/fixture-java/make-fixture.sh` against `evals/expected-java.json`.
- A new facet value (a `step`, an `applies_to` scope) is a `scripts/cardlib.py` constant, a `maintenance/craft-cards-taxonomy.md` row and a `maintenance/scripts/research-topic-workflow.js` enum in the same commit.
- Pin the tier models in `evals/evals.json`; re-run the fixture on every model change.
- Re-run the smoke task (`evals/evals.json`, `smoke_task`) when the Design → Build contract changes — the brief's sections, what either dispatch carries, the confirmation, the deviation rule or the dispatch table — and record the run there.
- A card the fixture seeds is a row in `evals/expected.json` and a seed plus a control in `evals/fixture/head/`, a Java card's a row in `evals/expected-java.json` and a seed plus a control in `evals/fixture-java/head/`; renaming the card's id renames the row.

## Scripts

The authoring scripts, each with what it does, reads, writes and the privileges it takes; the run scripts are declared in SKILL.md §Phase 6. Every script of the skill is standard library only, with no pinned dependency, and a change to any of them re-runs the tests below and the fixture grading.

- `maintenance/scripts/research-topic-workflow.js` — orchestrates the research of one topic of the universal corpus: sources, spine, drafts, skeptic verdicts and fixes; reads its `args` (the topic's row of the design note's taxonomy, `next_id`, the shipped titles) or a continuation bundle's embedded state; the script writes no files and returns the note's material, the cards, the provenance lines and the pending entries, and its agents write only their scratch directories; privileges: spawns sub-agents that read the web through the fetch channel and run the validator.
- `maintenance/scripts/python-topic-workflow.js` — orchestrates one topic of the Python corpus: spine, draft packs, skeptic packs, closing edit; reads its `args` (from `python-corpus.py topic-args`) and the harvest cache; the script writes no files and returns the shape `write-topic-result.py` reads, and each agent writes its restart file under `<state_dir>/<phase>/`; privileges: spawns sub-agents that run the validator and `check-python-cards.py`.
- `maintenance/scripts/python-triage-workflow.js` — one judge per batch of harvested catalog items gives a verdict per item; reads its `args` and the batch briefs; the script writes no files, and each judge writes `<state_dir>/triage/<batch>.json`; privileges: spawns sub-agents.
- `maintenance/scripts/harvest-python-sources.py` — collects the rule catalogs of Ruff, Pylint, SonarSource, Bandit and flake8-bugbear; reads the projects' GitHub trees and raw files, and a Ruff catalog file or `uvx ruff rule --all`; writes `items.jsonl`, `summary.json` and the fetch cache `src/` under `--out`; privileges: network (none with `--offline`) and the `uvx ruff` subprocess when no catalog file is given.
- `maintenance/scripts/python-corpus.py` — prepares the inputs of the two Python workflows and merges their outputs (`triage-briefs`, `triage-merge`, `topic-args`, `save-run`); reads the harvest, the topic list, the universal card index, the restart files and the cards directory; writes under the state directory; no network.
- `maintenance/scripts/research-continue.py` — reads a research run's journals and its output or bundle; writes continuation bundles of the research workflow that carry the finished stages, for a cut-short run or a later fix round (G-18); no network.
- `maintenance/scripts/write-topic-result.py` — reads one or more research runs' outputs and the cards directory; writes the research note and the cards, and appends to the provenance map and the pending-evidence file; no network.
- `maintenance/scripts/check-python-cards.py` — checks drafted Python cards: the validator, the Example, the triggers, each citation's source and quoted fragments, the title, the provenance line; reads the draft files, the harvest and the universal index; writes a temporary directory and the fetch cache `<state>/../check-cache/`; privileges: network to peps.python.org, arxiv.org and raw.githubusercontent.com (none with `--no-network`), and the validator as a subprocess.
- `maintenance/scripts/validate-craft-cards.py` — checks every card against the corpus schema of `maintenance/craft-cards-taxonomy.md` and, with the maps, one provenance line per card and no shipped id among the pending entries; reads the cards, the provenance map (`--provenance`, else the one `cardlib.provenance_map_path` names) and `--pending`, a language corpus with `--language <lang>`; writes nothing; no network.
- `maintenance/tests/` — the unit tests of every script of the skill, the run scripts included: `python3 -m unittest discover -s maintenance/tests -p 'test_*.py'` from the skill directory. They build their fixtures under temporary directories, run git in a temporary repository and `node --check` when node is installed (`test_bundle_run.py` checks both workflow scripts as the runtime wraps them, G-11), and fetch nothing.

## Authoring gotchas

The card-authoring entries of the gotcha list; their ids are shared with `references/gotchas.md`, which holds the run's entries.

G-10. The audit's static pre-pass flags a "backslash path" (R-42) on a card's `triggers` line? The line holds regular expressions, and the pre-pass reads a backslash escape after a word — `catch\s*\(`, `except\b` — as a Windows path. The finding is a false positive on every trigger: dismiss it, and rely on `maintenance/scripts/validate-craft-cards.py`, which compiles each pattern as Python `re` and rejects a literal dot written as backslash-dot (it is written `[.]`); whether a pattern matches the bad half of the card's Example is the skeptic's check in the research workflow, not the validator's.

G-16. A research topic's cards cite a paper the skeptic could not open? The authoring environment reaches papers only through the search index, so a paper enters a card as `relayed` with the snippet quoted on the provenance line; and the runtime caps the search tool at 200 calls per session for all sub-agents together (`CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION`), after which every call answers with the budget message, so a topic run after the cap carries the orchestrator's own search snippets in its `candidate_evidence` and the cap in the workflow's `channel_note`, and papers reach the agents only through GitHub-hosted copies. A card whose only anchor is `unfetched` never ships; re-verify `relayed` citations from an environment with arXiv access and mark them `fetched` on the provenance line when the paper states the claim.

G-18. A research topic cut short (a session limit, a killed process) re-runs its skeptics when resumed with `resumeFromRunId`? The runtime's resume replays the unchanged prefix of agent calls and runs everything after the first divergence live, and the pipeline's call order after the drafts depends on which draft finished first, so a resumed topic replays the sources, the spine and the drafts and re-runs every first verdict. Continue from the journal instead: `maintenance/scripts/research-continue.py --journal <transcript>/journal.jsonl --from-output <task output> --split 3` writes bundles that carry the finished stages as `resume_state` and draft only their own keys, so only the fixes and second verdicts run; `maintenance/scripts/write-topic-result.py --run <cut-short output> --run <bundle output> ...` merges the runs into one note. A bundle above the runtime's 512 KiB script limit is refused: raise `--split`, since each bundle carries only its own keys' drafts and verdicts and no source layer. The second fix round is the same mechanism: `--round 2` with every journal of the first round names `fix:`/`verify2:` as the state and carries only the rules the second verdict sent back with `revise`; `--resume-cut-short` finishes a round whose fixes ran and whose skeptics were cut short; `--closing-edit` ships a rule the last verdict sent back after the drafter applies that verdict's edits verbatim; a topic's writer merge then lists the cut-short output and every bundle output of both rounds.
