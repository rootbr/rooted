# A table keyed by an enumerated type pairs each entry with its member named in the source, not with the member's ordinal or declaration position

## Thesis
A table whose entries belong to the members of an enumerated type pairs each entry with its member in the source, as a map keyed by the member itself or as a literal keyed by each member's name, and code reads the table through the member. Outside a data structure built for enumeration keys, the pairing rests on the member, not on its ordinal, its index in the list of its type's members, or a number the language assigned it from its declaration position. A positional array or list whose n-th entry is taken to belong to the n-th declared member is the defect, and so is a serialized number turned back into a member by indexing the member list.

## Rationale
A member's ordinal is its position in its type's declaration, starting at zero, and implicit numbering follows declaration order too: a member declared without a number takes the index of its declaration or one more than the member declared before it, counting from zero, or from one for automatic values. The ordinal is not guaranteed to be stable across builds, because members can be added, removed or reordered, and code that depends on a member sitting at a particular index of the member list depends on that order too; a number defined by declaration position changes with the same edits. The ordinal is designed for sophisticated enumeration-based data structures, such as a set or a map of members, and most programmers will have no use for it; implicit numbering is documented as useful where the member values themselves do not matter but each must be distinct from the others, and automatic values as usable when the exact value is unimportant. A literal that labels each entry with its member's name works regardless of the members' values as long as they are distinct, the property implicit numbering is documented as serving, and a map keyed by the member itself is the documented replacement for a map keyed by its ordinal. The keyed form can keep the array representation: one standard library's map for enumeration keys takes all its keys from a single enumeration type and is represented internally as an array, a representation documented as extremely compact and efficient, with every basic operation in constant time, and a literal labelled by member names can build an array. Where a number must stay stable for serialization, the documented suggestion is an explicit field on the member, in place of indexing the member list with the stored number.

## Example
```typescript
bad:  enum Level { Low, High }
      const LABELS: string[] = ["low", "high"];
      function label(level: Level): string { return LABELS[level]; }
good: enum Level { Low, High }
      const LABELS: Record<Level, string> = { [Level.Low]: "low", [Level.High]: "high" };
      function label(level: Level): string { return LABELS[level]; }
```

## Limits
A data structure built for enumeration keys, such as a set or a map of members, is the use the ordinal is designed for and may hold its entries in an array internally; such a structure is outside the rule. A number held in an explicit field of the member, the documented suggestion for a number that must stay stable, is not its ordinal, and neither is a number written beside the member in its declaration, which implicit numbering leaves as written; a lookup through either is outside the rule. The documented check exempts an index into the member list whose innermost enclosing type is the enumeration itself or a type that encloses it, though not one written in a type nested inside the enumeration, and not a read of the ordinal in either place.

## Validator
Grep the hunk's added lines for a read of a member's ordinal, an index into the list of an enumeration's members, a member cast to an integer or its value used as an index, and a positional array literal of strings. Open the file and find the table that the index reads or the literal declares, and the enumerated type whose members its entries belong to. Where the file declares that type, read whether its members carry numbers written beside them or take them from their declaration position; where it does not, flag a read of the ordinal or an index into the member list, and leave a member's bare value used as an index unflagged. Pass a positional array that no enumeration's members index, a map keyed by the member itself, a literal keyed by each member's name, a lookup through a number held in an explicit field or written beside the member in its declaration, code inside a data structure built for enumeration keys, an index into the member list whose innermost enclosing type is the enumeration itself or a type that encloses it, and a table the project context exempts. Leave aside whether every member has an entry and what the table answers for a key it lacks. Validator question: **Does added code pair a table's entries with an enumeration's members by position, reading an entry or decoding a serialized number through a member's ordinal, its index in the member list, or a number assigned from its declaration position, outside a data structure built for enumeration keys and other than an index into the member list whose innermost enclosing type is the enumeration itself or a type that encloses it?** Yes → flag.
