# The release of a resource that was written to has its failure checked on the success path, and is never left only to a deferred or automatic release that discards the error

## Thesis
When code has written to a file or an output stream, the release that can report a deferred write failure — the close, the flush or the sync — has its failure checked on the path where the writes succeeded, and that failure is handled or passed to the caller rather than discarded. Three forms meet the rule: an explicit release call whose error is tested and handled, returned or thrown; a deferred handler that hands the release error to the routine's result when no earlier error is already set; and a scoped-release construct that reports the release failure to the caller. A release that discards its error — a deferred close whose result is dropped, a destructor, a quiet close that ignores exceptions — stays as the backstop for the paths that exit before the checked release, and is not the only release of a written resource.

## Rationale
Data written to a handle may stay cached in memory until the handle is closed, or until a later point, so a write failure may first be reported by the close or the sync; a buffered stream's close can first call its flush and then close the stream beneath it. When the errors those calls return are discarded, the program may be unaware that data loss occurred, and a write made without the scoped construct or an explicit close might not be completely written to the disk even if the program exits successfully. A release left to a destructor is where the error is lost: a file closed on leaving scope has the errors detected on closing ignored by its destructor, and a buffered writer dropped without a flush attempts the flush but ignores any error that happens in the process. That destructor also runs while the program unwinds from a failure, where a failing destructor aborts the program; so the release that can fail is a separate close method that returns its error, and the destructor does the teardown, ignoring or logging its errors, when that close was not called. The documented fix for a discarded deferred close keeps the deferral but has it set the routine's returned error to the close error unless a write error was set first.

## Example
```java
bad:  Writer out = Files.newBufferedWriter(path);
      try { out.write(text); } finally { IOUtils.closeQuietly(out); }
good: try (Writer out = Files.newBufferedWriter(path)) {
          out.write(text);
      }
```

## Limits
The rule is contested, and two conditions separate the cases: whether the resource was written to, and whether the project context adopts the exclusion of release errors for written resources. On a written resource, write failures may not occur until the close or the sync, a discarded release error can leave data loss unnoticed, a checker that flags writable file handles only rates its check high precision, and standard library documentation directs code that must handle close errors to an explicit sync or flush (the Source entries marked check). Where a failure to free a resource cannot affect future program behaviour — a resource freed in a cleanup block and never reused, whose failure can matter only through resource exhaustion — suppressing the failure is accepted, and once exhaustion is handled, sanitizing and logging it is enough; one linter ships an exclusion preset for unchecked close and flush errors because almost all programs ignore them and in most cases that is acceptable, and one security checker retired its rule against deferring an error-returning call as more inconvenience than fix (the entries marked tolerate). The data-loss evidence concerns writable handles whose data may not have been flushed, so a resource that was only read falls on the tolerate side and is outside the rule, and a connection or transaction released directly is outside it as well, since the evidence concerns files and output streams. A project context that adopts the exclusion of release errors for written resources rejects the finding. A scoped-release construct that reports the release failure — thrown when the body succeeded, reported together with the body's failure when both failed — meets the rule with no explicit call. The backstop is sound where a second release does no harm: one stream contract requires a close to have no effect when the stream is already closed, and one file close returns an error on a second call, which the discarding backstop drops; other close contracts leave a second call undefined or allow it a visible side effect, so over such a resource the backstop runs only when the checked release was not called. Whether the code also syncs for durability is outside the rule: only a sync gives a reasonable guarantee that the data is flushed, and it is generally more expensive than a close, which is not required to block until the data has been written. Releasing on every path, the order of releases, and what a handler does with a release error it has received are judged by their own rules.

## Validator
Grep the added lines for a deferred close, flush or sync with its result dropped, a release assigned to the blank identifier or an underscore binding, a quiet-close helper, and a close, end or flush whose rejection goes to an empty handler. For each hit, open the file, trace the resource to where it was opened or received, and decide whether it is a file or an output stream the routine wrote to: opened or created for writing or appending, wrapped in a writer, or passed to a write, print or copy call. Skip a resource that was only read and a connection or transaction released directly rather than through an output stream, and skip the hit when the project context adopts the exclusion of release errors for written resources. On the path where every write succeeded, look for a release whose failure is not discarded: an explicit close or sync of that resource whose error is tested and handled, returned or thrown (a checked flush counts only for a buffered writer with no close that returns its error), a deferred handler that assigns the release error to the routine's returned error when no earlier error is set, or a scoped-release construct that reports the release failure. Validator question: **Does an added line leave the release of a file or output stream the routine wrote to only to a deferred, automatic or quiet release that discards its error, with no release on the success path whose failure is checked?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-28`, severity major, `file`, `symbol`, `code` = the deferred, discarded or quiet release quoted verbatim from the diff, `fix` = the release called on the success path with its error checked and returned or thrown, a deferred handler that sets the routine's returned error to the release error when no earlier error is set, or the scoped-release construct that reports it, with any deferred or quiet release kept only as the backstop for early exits, in the file's language, `rationale` = which written resource's write failure the discarded release error can hide).
