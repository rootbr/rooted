# Research note — Boundary enforcement and package structure

Topic `boundary-enforcement-and-package-structure` of group K. Architecture, domain `architecture`, id prefix `ARCH`. Formulation locators: Clean Architecture ch. 34 'The Missing Chapter' (package by layer, by feature, by component; access modifiers and build-time rules as the boundary) and ch. 21 'Screaming Architecture'; Software Engineering at Google ch. 18 'Build Systems and Build Philosophy' (visibility in the build graph) and ch. 16; SWEBOK Guide V4.0 ch. 3 'Software Design' (architectural structures, modularity). Marked contested in the design note.

At the component level, meaning a unit of release, build or deployment, the canon takes three positions. Clean Architecture ch. 34 (Brown, relayed through reading notes) holds that packages are only folders while every type is public, and that the compiler or the build should enforce the boundary. Ch. 21 says a project's top level shows what the system does, not which framework it uses. Software Engineering at Google ch. 18 says to keep build-target visibility as small as possible. Official documentation supports most of this. Every major toolchain documents a check that enforces a component boundary: the go command's internal directories (the Go 1.4 notes say the language itself cannot enforce it), Rust crate privacy, Kotlin and C# internal, JPMS exports, Bazel target visibility and Node's exports map. Checkers fill the gap where the compiler cannot: Spring Modulith says the Java compiler 'is not of much use' once internals are public, and import-linter, ArchUnit and dependency-cruiser run as checks in CI. Five rules are carded from that evidence. (1) A declared boundary is held by a toolchain check, not by a folder or a name. (2) A new support package goes into the toolchain's hidden area, and the component lists its public parts explicitly. (3) A boundary rule fails the build: dependency-cruiser defaults to warn, and Bazel says visibility checking stays on in submitted code. (4) A dependency used only inside the implementation stays private (Gradle implementation, CMake PRIVATE). (5) Each directory with buildable files is its own build package (Bazel best practices). A sixth card, from Gradle, keeps sibling components on one split scheme. It is the part of the naming dispute that the evidence supports. The industry disagrees on naming top-level packages by capability. Angular, Spring Boot's typical layout, Spring Modulith and Django are capability-first. Rails generates by layer, ArchUnit's own example uses layer-named packages, and Gradle says the scheme matters less than splitting consistently. Fowler's size condition reaches me only as a search summary of a practitioner blog, so that rule stays pending. The same holds for the JavaScript dispute over index-file public APIs (Feature-Sliced Design against bulletproof-react). On the convention side, PEP 8 and the Python tutorial make a naming convention the declaration, because the language enforces nothing. That gives the toolchain-check rule its separating condition: it applies where the toolchain or the project's checker offers a checked form. The research on drift reaches me only through search summaries: Rosik et al. 2011, Brunet et al. 2012 and Ghorbani et al. 2019. None of these studies compares enforced with unenforced boundaries, so no card is rated major on research grounds. The javac, import-linter and rustc reproductions back no card until they are committed under evals/fixture/.

## Formulation layer

The canon takes three positions at the component level. (1) A boundary is real only when the toolchain enforces it. In Clean Architecture ch. 34, Brown says that when every type is public, packages are folders and every packaging style gives the same encapsulation, and he prefers the compiler as the enforcer; the build and language documentation (Go `internal`, Bazel visibility, JPMS exports, Rust, C# and Kotlin module-level visibility, Node `exports`) and the check tools (import-linter, ArchUnit, dependency-cruiser, Spring Modulith) document how the boundary is enforced. (2) A top-level package is named by the capability it provides: Screaming Architecture, the DDD Reference 'Modules' pattern, the Go naming guidance (no util, common or model packages), Angular's feature-area rule, Spring Boot's sample layout and Django's apps all say so. (3) A component exposes a small, explicit API: SEG ch. 18 says to minimize visibility; Bazel, Go's layout guide and Spring Modulith say to declare the public interface and keep the rest internal. The canon disputes the second position and part of the first. Rails' layout groups code by framework artifact type by default. Fowler (relayed) accepts layers at the top level for smaller systems, until one layer grows too big. Brown himself says package by feature makes one controller the only entry point. ArchUnit says compile-time checks have an advantage over its own test-time checks, while Brown's notes say static analysis lengthens the feedback cycle; PEP 8, the Python tutorial and Node's 'not a strong encapsulation' describe boundaries kept by convention. From here I could not open the books (Clean Architecture, the official SWEBOK V4 text), martinfowler.com, blog.cleancoder.com, Brown's slides, JEP 261 or the Sarkar papers: those items are relayed through GitHub reading notes or search summaries, or marked unfetched. The Ousterhout–Martin discussion takes no position on package structure.

## Reception layer

The industry checks component boundaries mechanically on every major stack, and the tools' own documentation states why a folder convention is not enough. Spring Modulith says the Java compiler "is not of much use" once an internal type is public, NetArchTest says convention-only discipline "often breaks down as projects grow", and Biome says an exported JS/TS symbol is importable from anywhere. These tools fall into three groups: compiler or build visibility (Go internal, Rust pub(crate), Kotlin and C# internal, Bazel visibility, Node "exports"), test-time or lint-time contracts that can gate CI (ArchUnit, Spring Modulith, import-linter, Tach, dependency-cruiser, eslint-plugin-import, Nx, Packwerk, deptrac, Checkstyle ImportControl), and ratchets for grown codebases (FreezingArchRule, package_todo.yml strict mode). Two limits recur: Node calls its own "exports" encapsulation "not a strong encapsulation", and Packwerk accepts false negatives in order to avoid false positives. Naming top-level packages by capability rather than by layer is the contested rule. Fowler (relayed) gives the condition: layer-first top level is "OK for smaller systems", and larger systems should split first into domain modules. Crosmer (relayed) defends layers at the top level. Rails' default app/ layout is layer-first, while Spring Boot's own typical layout, Spring Modulith's module detection and Django's "application" are feature-first. Exposing a public API through an index file is contested in the JS ecosystem: Feature-Sliced Design requires it and lints it with Steiger, while FSD itself and bulletproof-react document bundler and tree-shaking costs of barrel files, and bulletproof-react now recommends direct imports. Rust's own linters conflict on crate-boundary visibility: rustc unreachable_pub recommends pub(crate), and clippy redundant_pub_crate flags it inside private modules. Both checks are off by default. ## Evidence layer

Official documentation for every major toolchain states the toolchain-enforced boundary, and I opened each one. The Go command's internal directories (the Go 1.4 notes add that "The Go language does not have the power to enforce this distinction"), Rust's pub(crate), JPMS exports, Kotlin and C# internal, Bazel target visibility, Gradle api/implementation, Node "exports", and the CI contract tools (import-linter, ArchUnit, dependency-cruiser, Spring Modulith verify()) all state it. Spring Modulith's own docs say the Java compiler "is not of much use" once internals must be public, and Python's tutorial says private names "don't exist in Python". Three local runs reproduce the claim with javac 25, rustc and import-linter 2.15. They are not yet committed fixtures, so they back no card until moved under evals/fixture/. The research is relayed only from WebSearch summaries, since every paper host is denied. Rosik et al. 2011 found that detecting drift did not lead a team to remove it. Brunet et al. 2012 found violation counts rising across 19 versions despite clean-up, with over 3,000 violations. Ghorbani et al. 2019 found inconsistent JPMS declarations in 74% of 38 apps. Sarkar et al. 2007 counts calls that bypass a module's API. None of these studies measures enforcement in CI against no enforcement, and the Sarkar 2009 abstract could not be retrieved. Naming packages by capability is the contested rule. The Angular style guide, Google Go style, Django apps, Spring Modulith and Now in Android favour feature-named units. Rails generates by layer (app/models, app/controllers), ArchUnit's own example defines layers by controller/service/persistence package names, and Gradle says "the specific scheme matters less than ensuring that your build is split logically and consistently". A search for an empirical comparison of package-by-feature against package-by-layer found only blog posts.

## Spine — candidate rules in source order

1. **A boundary a change declares between components, such as a part kept for one component's own use or a dependency one component may not take on another, is held by a check the toolchain or the project's dependency checker runs, not by a directory name, a naming convention or a sentence in a document alone** — Where a change declares a boundary between components (a package, directory or module kept for one component's own use, or a rule that one component may not depend on another), it declares it in the checked form the project's toolchain offers. That form is component-scoped visibility (the go command's internal directories, Rust crate privacy, Kotlin or C# internal), a module system's export list, build-target visibility, a package export map, or a contract in the dependency checker the project runs whose violation fails the build. A directory or package name the toolchain ignores, such as an internal sub-package whose types are public or a leading-underscore package, does not hold the boundary, and neither does an invariant stated only in prose. Where the language enforces nothing at that scope and the project runs no dependency checker, the naming convention is the declaration and the rule does not apply. A checked form need not be airtight to count: Node's export map yields to an absolute-path require, and a static checker in a dynamic language accepts false negatives. A compile-time check and a test-time check both satisfy the rule.
