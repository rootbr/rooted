# A pipeline expression that nests a second iteration or passes a step a long inline function is split into named steps or loops

## Thesis
A data transformation written as one expression, a chain of calls or a comprehension, writes one level of iteration, holds at most one filter clause when it is a comprehension, and passes each step a library function, a named function or a short inline function. An expression that iterates a second, nested sequence, through a second iteration clause or through a flattening step whose function maps, filters or iterates each element's inner sequence instead of only returning it, is rewritten as nested loop statements, or as named intermediate results and named functions so that each expression writes one level of iteration. A step whose inline function exceeds the bound for its language, more than one line or more than 80 characters, the top of the documented range, where the language's inline functions hold a single expression only and more than ten lines of code where they can take a statement block, passes a named function instead.

## Rationale
A comprehension with a second iteration clause is two loops nested in one expression: for each element of the first sequence, the second is looped over from the beginning. A flattening step whose function runs its own map or filter has the same shape, since it replaces each element with the contents of the sequence that function produces. Complicated comprehensions and generator expressions can be hard to read, a comprehension with too many iteration clauses is one a reader fails to understand, and multiple filter clauses in one comprehension are hard to read, down to telling whether all of them have to pass. Guidance that forbids a second iteration or filter clause asks for readability over conciseness and writes the two-loop case as nested loop statements. A small function that does one thing is easier to specify, to read and to check for errors than a large one that performs a complicated transformation, and when a program does not work each function is an interface point where the data can be checked: the intermediate inputs and outputs isolate the function responsible for the bug. To see the values inside a chain, iterator and stream libraries supply a step that is inserted into it, mainly for debugging, to check what is happening at various parts of the pipeline as elements flow past a point. An inline function that does too much becomes an overly complicated expression that takes time to disentangle; it is harder to read and debug than a named local function, and its lack of a name makes stack traces harder to understand. The documented bounds differ with the language's inline functions. Where they hold a single expression only, one-liners are fine, and past one line or 60 to 80 characters a named nested function might be better. Where they can also take a statement block, an inline function is meant for behaviour that fits in a few lines of code, since otherwise the source code can quickly become unreadable, and one checker flags an inline function of either form past ten lines of code by default.

## Example
```typescript
bad:  const largeAmounts = orders
        .flatMap(order => order.lines.filter(line => line.qty > 0).map(line => {
          return line.qty * line.price;
        }))
        .filter(amount => amount > limit);
good: const lines = orders.flatMap(order => order.lines);
      const filledLines = lines.filter(line => line.qty > 0);
      const amounts = filledLines.map(line => line.qty * line.price);
      const largeAmounts = amounts.filter(amount => amount > limit);
```

## Limits
A chain of any length meets the rule when it writes one level of iteration and each step passes a library function, a named function or an inline function within its bound: one-liners are fine, a suitable built-in or library function needs no new function, and a chain of iterator adapters focuses on the high-level objective of a loop instead of the bits of looping and building new collections. A comprehension with one iteration clause and one filter clause meets it, also when laid out over several lines, and so does a flattening step whose function only returns each element's inner sequence, leaving the flattening to the library. Sources differ on the second iteration clause: one style guide forbids it, while one linter allows two iteration clauses and flags a third; a project context that adopts the two-clause tolerance rejects the finding for an expression with exactly two levels of iteration, and a third level is flagged under either. The one-line bound for a language whose inline functions hold a single expression only is stated as a preference, a named function that might be better, and the ten-line bound is a checker's configurable default, so a project context that documents another bound for inline functions rejects the finding within it. Naming a stage does not require materializing it: a lazy stage can be bound to a name, or returned from a named function as a lazy sequence, whereas collecting it allocates a new data structure that may not be needed. A named lazy stage can be single-use: an iterator protocol may promise only forward movement, with no reset or copy, and a stream is operated on only once, so a single-use stage that two later steps read needs a new iterator for each, while a lazy sequence that the language lets a caller walk again or copy needs none. Side effects inside a step, laziness that defers or skips effects, a fold that a loop states more plainly, the cost of a loop against an iterator, failure handling inside a pipeline and parallel pipelines are outside the rule.

## Validator
Grep the added lines for a line that continues a chain with a mapping, filtering, flattening, sorting, grouping, folding or collecting call, three such calls on one line, a flattening call whose function holds its own pipeline call, and a pipeline step whose inline function opens a block at the end of its line. Read the whole expression in the hunk. Count the levels of iteration it writes: a second iteration clause, or a flattening step whose function maps, filters or iterates each element's inner sequence rather than only returning it, adds a level. In a comprehension, count its filter clauses. For each step that passes an inline function, count the inline function's lines of code and, where the language's inline functions hold a single expression only, its characters. Read the project context for a documented two-clause tolerance or another bound on inline functions. Validator question: **Does an added pipeline expression write a second level of iteration, a second filter clause in a comprehension, or a step whose inline function runs past one line or past 80 characters where the language's inline functions hold a single expression only, or past ten lines of code where they can take a statement block, beyond any tolerance the project context documents?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-52`, severity minor, `file`, `symbol`, `code` = the pipeline expression's nested iteration, extra filter clause or over-long inline function, quoted verbatim from the diff, `fix` = the expression rewritten as named intermediate results, a named function for the inner iteration or the long step, or nested loop statements, so that each expression writes one level of iteration, in the file's language, `rationale` = the second level of iteration, the extra filter clause or the inline function's length against its bound, and which intermediate value the split lets a reader check).
