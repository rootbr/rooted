# Research note — Complexity and deep modules

Topic `complexity-and-deep-modules` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: SW1.1 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §1.1 'Minimizing Complexity'); APOSD (A Philosophy of Software Design ch. 2 'The Nature of Complexity', ch. 4 'Modules Should Be Deep', ch. 7 'Different Layer, Different Abstraction', ch. 8 'Pull Complexity Downwards'); the public discussion of module depth in johnousterhout/aposd-vs-clean-code README.md as a formulation.

The canon makes minimizing complexity a construction driver. SWEBOK §1.1 states it, opened here in the V3 transcription because V4.0 could not be reached. A Philosophy of Software Design turns that aim into a test of depth: a module should hide a lot of functionality behind an interface simpler than its implementation; shallow modules and pass-through methods add interfaces without hiding anything; adjacent layers should offer different abstractions; and complexity related to a module's job belongs inside the module rather than in every caller. The industry agrees on the narrow end of that claim, and the openable evidence sits there. Official guides for Go, Python and TypeScript say to export only what callers use, to add no abstraction layer or interface before a real need, and not to wrap an existing interface or client method for method. Java, Python and JavaScript linters flag an override or constructor that only calls its parent. Two studies favour defaults over decisions forced on callers: Xu et al., FSE 2015, found that most configuration knobs are rarely set, and Stylos and Clarke, ICSE 2007, found that required constructor parameters made programmers less effective. The canon disagrees on five points. On how far to decompose, Ousterhout and Martin agree only that a unit whose implementation is no more detailed than its interface is over-decomposed. Convenience entry points for the common case are disputed. On which way complexity should move, 'pull complexity down' meets Lampson's 'Leave it to the client', matklad's 'push ifs up' and the Go guide's two-way trade-off. Decorators are disputed: Krein et al. 2016 found the Decorator pattern preferable in maintenance when the developer knows the pattern. On class-size thresholds, tools set between 20 and 100 public methods, while El Emam et al. 2001 found that class metrics lose their association with faults once size is controlled and Scalabrino et al. 2021 found that no metric captures understandability. No openable study measures module depth itself. Depth therefore stays a formulation, and the cards rest on its checkable extremes: units and wrappers that hide nothing, surfaces wider than their callers use, decisions pushed onto every caller, and abstraction added before a need.

## Formulation layer

The canon's case for module depth and interface width rests on three sources. The first is SWEBOK §1.1 (V3 fetched from the ligurio transcription; the V4.0 wording cannot be opened from here), which makes minimizing complexity a construction driver but says nothing about depth. The second is A Philosophy of Software Design chs. 2, 4, 7 and 8 (the book cannot be opened from here, so these are marked paraphrases from memory): it supplies the deep/shallow test, classitis, the common-case rule, different layer / different abstraction, pass-through methods with their stated exceptions, decorators, and pull-complexity-down with its three preconditions. The third is the aposd-vs-clean-code README (fetched), which restates depth in the authors' own words and records Martin's counter-positions: err on the side of decomposition, trust the names, and decompose large methods into small classes. Official documentation states narrower and partly language-bound versions: Google's Go guide (unnecessary abstraction; a trade-off between code simplicity and API-usage simplicity; small interfaces; every exported type adds cognitive load), Google's Python and TypeScript guides (no pass-through accessors, make the field public — a fix that depends on properties and does not carry over to Java, Go or Rust), the Rust API guidelines (a forwarding newtype that hides a representation is a legitimate wrapper), and eng-practices (too complex means not understood quickly; over-engineering; complexity accumulates through small changes). The canon disagrees on four points: how far to decompose (Ousterhout vs Martin and Clean Code ch. 10); convenience operations (Ousterhout and Blanchette make the common case simple, while Hohpe and Bloch warn against convenience methods and lumping operations together); the fix for trivial accessors (the Google guides say make the field public, Ousterhout says avoid exposing data, Effective Java prefers accessors); and generality (eng-practices warns against code that is more generic than it needs to be). Items that could not be opened: the APOSD, Clean Code, Refactoring, Effective Java and Code Complete books, Bloch's talk, SWEBOK V4.0, and any APOSD errata. ## Reception layer

Reception agrees on the narrow-interface, no-pass-through side of the topic. The Go proverb, Effective Go, Google's Go decisions ("Do not wrap RPC clients in new manual interfaces just for the sake of abstraction") and TigerBeetle's "inverse hourglass" function shape all hold that position, and the pass-through checks that tools turn on by default do too (PMD UselessOverridingMethod in quickstart, Pylint W0246, ESLint no-useless-constructor, clippy redundant_closure). Two things are openly contested:
- How far to decompose: Ousterhout and Martin argue it in their joint README and agree only that over-decomposition exists.
- Which way complexity should move: matklad and TigerBeetle "push ifs up", Google's Go guide treats code simplicity against API simplicity as a trade-off, and Uber's Go guide prescribes hand-written delegate methods over embedding, against a blanket "pass-through is a red flag" rule.

Size and complexity thresholds disagree widely between tools:
- Public methods: 20 (Pylint, Ruff), 45 (PMD), 100 (Checkstyle).
- Cognitive complexity: 15 (Sonar, PMD), 25 (clippy), 30 (gocognit).

PMD's quickstart leaves all of these checks off and Pylint disables too-few-public-methods in its own pylintrc. Clippy states that cognitive complexity "is not something we can calculate". Via neverworkintheory, El Emam 2001 (no class-metric effect once size is controlled) and Scalabrino 2021 (none of 121 metrics capture understandability) undercut the class-level and understandability metrics. Not opened: the APOSD book text, every Hacker News, Lobsters and vendor page (WebSearch budget exhausted, hosts denied), the sonar-java RSPEC pages, and the Muñoz Barón cognitive-complexity paper. Items that rely on them are marked unfetched or mention them only in notes.

## Evidence layer

Most of the evidence that could be opened is documentation and tool rules. Static-analysis checks cover public-surface size in four of the five languages: Java (PMD ExcessivePublicCount 45, Sonar S1448 35, Checkstyle MethodCount 100), Python (Pylint R0904 20) and Go (revive max-public-structs 5); TypeScript has only the Google style guide's visibility rule. Forwarding-only overrides and constructors are flagged in Java, Python and JS/TS (PMD UselessOverridingMethod, Sonar S1185, Pylint W0246, ESLint no-useless-constructor). Wrapper and too-thin classes are flagged in Python and TS (Pylint R0903, typescript-eslint no-extraneous-class). The official style guides add matching guidance: Google Go and Google TS, Effective Go, Go CodeReviewComments, PEP 8 and PEP 20, SWEBOK V3 §1.1 and design §1.4, and google/eng-practices. Two research results opened through the neverworkintheory bibliography back 'pull complexity downwards' directly: Xu et al. FSE 2015 (up to 54.1% of configuration knobs rarely set; 51.9% removable) and Stylos & Clarke ICSE 2007 (programmers were more effective without required constructor parameters). Lampson's SOSP 1983 Hints (opened from papers-we-love) supports minimal interfaces but contests pulling complexity down ('Leave it to the client', 'Don't hide power'). No openable study measures module depth itself or isolates pass-through methods, and both are recorded as none found. The class-level research canon is contested and was mostly unopenable: El Emam et al. 2001 (opened) found that size removes every OO-metric association with faults; Scalabrino et al. 2021 (opened) found that none of 121 metrics captures understandability; and clippy now disclaims cognitive complexity as a measure. All of these stand against the unopened Basili et al. 1996, Khomh et al. 2012, Palomba et al. 2018 and Muñoz Barón et al. 2020, and Olbrich et al. 2010 reports that God Classes are not more harmful once size is normalized. Chidamber & Kemerer 1994 and Briand-Daly-Wüst 1998 were dropped as definitional (they state no rule). The EMSE 2023 understandability paper (doi 10.1007/s10664-023-10396-7) could not be opened and its content is not recalled, so it carries no item; SWEBOK V4 could not be opened, so the V3 transcription stands in for SW1.1.

## Spine — candidate rules in source order

1. **Code is kept as simple as its job allows, judged by whether readers understand it quickly and callers can use it without introducing bugs** — Construction minimizes complexity because readers can hold only limited structure in working memory. It does so by preferring simple, readable code to clever code, by standards and by modular design. Complexity is judged by the reader and the caller: code is too complex when readers cannot understand it quickly, or when developers are likely to introduce bugs when they call or modify it, and this holds for lines, functions and classes alike. The aim names no criterion of its own. Its checkable forms are this topic's rules on units, wrappers and surfaces that add complexity without hiding anything.
   - formulation: SWEBOK Guide V4.0 ch. 4 §1.1 'Minimizing Complexity' (design-note locator SW1.1; V4.0 not opened, V3 ch. 3 §1.1 opened in the ligurio/swebok-v3 transcription); A Philosophy of Software Design 2nd ed. ch. 2 §2.1 'Complexity defined' and §2.2 'Symptoms of complexity'; johnousterhout/aposd-vs-clean-code README.md, 'Introductions' and 'Comments' ('complexity is in the eye of the reader'); Software Engineering at Google ch. 1 ('clever' as an accusation); Code Complete 2nd ed., cited by SWEBOK V3 as the reference for §1.1
   - reception: not contested
   - evidence: IEEE Computer Society, Guide to the Software Engineering Body of Knowledge (SWEBOK Guide) V3.0, 2014, ch. 3 'Software Construction' (community transcription ligurio/swebok-v3, 3_software_construction.md) — ch. 3 §1.1 'Minimizing Complexity' (fetched, standard); IEEE Computer Society, SWEBOK Guide Version 4.0, 2024, ch. 4 'Software Construction' — ch. 4 §1.1 'Minimizing Complexity' (unfetched, standard); Google, Engineering Practices Documentation, 'What to look for in a code review' (google/eng-practices review/reviewer/looking-for.md) — section 'Complexity', first paragraph (fetched, official-documentation)

More sources would not unblock this rule; it needs a criterion, and the topic's checkable rules already carry the aim.

2. **A change adds no complexity it does not need, however small, because complexity accumulates from many small additions** — Most systems become complex through many small changes that add up. A change that degrades code health is therefore not accepted, even when each dependency or obscurity it adds is small. A commit-level study of Java projects finds that corrective changes tend to add complexity and that deliberately perfective changes reduce it. The policy gives no measure of its own for what counts as an unneeded addition.
   - formulation: A Philosophy of Software Design 2nd ed. ch. 2 §2.3 'Causes of complexity' and §2.4 'Complexity is incremental'; M. M. Lehman, 'Programs, life cycles, and laws of software evolution', Proc. IEEE 68(9), 1980, Law II 'Increasing Complexity' (unfetched)
   - reception: not contested
   - evidence: Google, Engineering Practices Documentation, 'What to look for in a code review' (google/eng-practices review/reviewer/looking-for.md) — section 'Context', second paragraph (fetched, official-documentation); A.    - disposition: held-not-checkable — A review policy without a criterion of its own. On a diff it reduces to this topic's checkable rules, each of which already counts a small addition. 3. **A module's interface width counts every obligation a caller must know, including call order, side effects and preconditions, not only its signatures** — A module's interface is everything a developer must know to use it. That includes the formal signatures and types and also the informal behaviour: ordering constraints, side effects and preconditions. An abstraction fails both by exposing details that do not matter and by omitting details that do, which makes it look simpler than it is. Interface width is therefore not a count of public methods.
   - formulation: A Philosophy of Software Design 2nd ed. ch. 4 §4.1 'Modular design', §4.2 'What's in an interface?', §4.3 'Abstractions'; johnousterhout/aposd-vs-clean-code README.md, 'Comments' (definition of abstraction) and 'Method Length' (the PrimeGenerator hidden side effect)

   - evidence: John Ousterhout and Robert C. Martin, 'A Philosophy of Software Design vs Clean Code', johnousterhout/aposd-vs-clean-code README.md — README.md, 'Comments' (definition of abstraction) (fetched, formulation)
   - disposition: held-not-checkable — Definitional: it says what to count, not what to flag. 4. **A module provides functionality that is large compared with the interface it asks callers to learn** — Depth weighs a module's benefit, the functionality it hides, against its cost, the interface its callers must learn. The best modules hide a lot behind interfaces much simpler than their implementations. Depth is a ratio judged by a reader: the formulation gives no threshold, and no tool measures functionality against interface. Its checkable extreme, a unit that hides nothing, is stated by shallow-unit-hides-nothing.
   - formulation: A Philosophy of Software Design 2nd ed. ch. 4 §4.4 'Deep modules' (Unix file I/O and garbage-collector examples); johnousterhout/aposd-vs-clean-code README.md, 'Method Length' (JOHN's opening on deep and shallow methods)
   - reception: not contested
   - evidence: John Ousterhout and Robert C.
