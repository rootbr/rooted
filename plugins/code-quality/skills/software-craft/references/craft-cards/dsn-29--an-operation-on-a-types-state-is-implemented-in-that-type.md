# An operation on a type's state is implemented in that type, not in outside code that reads its fields, decides and writes the result back, unless the type is a data carrier with no invariant

## Thesis
An operation that reads an object's state, decides from it and writes the outcome back into the same object is implemented in the object's type, and callers ask the object to perform it instead of reading its fields or accessors and writing the result back themselves. The rule holds where the type has an invariant — a logical condition on its members, such as a validated value, a bound a field must respect or a field derived from others — whether the type states the condition in its constructor, setters or operations, or the outside code keeps it through the decision it makes before the write as a condition no user of the type may break, not as one caller's own policy. It covers two shapes: code in another module, a manager, service or helper among them, that reads a type's fields or accessors, decides and writes into the same object; and an added type with only fields and accessors whose condition such outside code keeps. In most cases the fix moves the operation into the type, which then guards its condition itself; in some other cases it removes the holder and moves its data into the classes that worked on it. A data carrier with no invariant — a record, a data class, or a struct whose fields are all public and can vary independently of one another — is outside the rule.

## Rationale
A simple holder that reveals its state while its behaviour is defined elsewhere breaks encapsulation, and classes tend to rely strongly on their data representation, which makes the design brittle. A public field, which clients can mutate arbitrarily, pins down a representation choice and prevents the type from providing any validation or maintaining any invariant on its contents. An invariant is a logical condition on an object's members that the constructor establishes and every public operation can then assume; when all members can vary independently of one another, no invariant is possible. Moving the operation into the type restores the proximity of data and behaviour, and with direct access to the representation kept to the functions that need it, fewer functions can cause trouble by modifying the object's state and fewer need to change after a change in representation. In 395 releases of 30 open-source projects, the fault-proneness of classes holding a method more interested in a class other than its own rose by a factor of 8 in the periods that smell affected them, compared with the periods it did not; their change-proneness did not show the rise most other smells showed, and the same study reads smells in general as co-occurring with intrinsically fault-prone code rather than as the direct cause of faults.

## Example
```typescript
bad:  class AccountService {
        withdraw(account: Account, amount: number): void {
          if (account.getBalance() < amount) return;
          account.setBalance(account.getBalance() - amount);
          account.withdrawnToday += amount;
          account.limitReached = account.withdrawnToday >= account.dailyLimit;
        }
      }
good: class Account { private balance = 0; withdraw(amount: number): void { ... } }
      account.withdraw(amount);
```

## Limits
The sources disagree about data holders. One side reads a simple holder that reveals its state and lacks functionality as a sign that its behaviour is defined elsewhere, a break of encapsulation, and moves the operations back into it. The other provides a transparent carrier for a fixed set of values as a construct of its own, finds public fields most appropriate for compound, passive data structures, and defines data as relatively simple objects that group related attributes and have no invariant. The invariant separates the cases: a type with one is an abstract data type that guards it behind an intentionally limited interface, while data is a plain aggregate whose members can vary independently, and outside code that writes such a member while keeping no condition on the members, neither a bound on one nor a relation among several, passes, as does a default, clamp or normalization a caller applies to a member only for its own use when other users of the type may set that member to any value. An immutable record-style carrier, whose fields cannot be reassigned after construction, is still a transparent carrier when it validates, defensively copies or normalizes its arguments in its constructor; a carrier whose fields can be reassigned is judged by its invariant like any other type. A helper that needs no direct access to the type's representation, calling only the type's own operations and reading no field or accessor to decide a write back into the object, stays outside the type. A project context that declares a set of types as passive carriers operated on by other code rejects the finding for those types. Code that only reads another object's state to compute a value of its own, the width of a type's interface, the visibility of its fields and a mutable internal object handed to a caller are judged by their own rules.

## Validator
Grep the added lines for a write into an object other than the enclosing type's own instance — a setter call, a field assignment or a compound assignment — whose value is computed from that object's fields or accessors, for a conditional on an object's fields followed by a write into the same object, for an added holder declared with only fields and accessors, and for an added manager, service, helper or processor type. For each write, search the repository for the declaration of the object's type and read its fields, constructor, setters and operations; for an added holder, search its usages for code that reads its fields or accessors and writes back into it. Name the condition the type states or the outside decision keeps: a validated value, a bound, a field derived from others; for a condition only the outside decision keeps, search the other writes to that member and confirm that no user of the type may break it. Skip a write the type's own methods perform, a carrier whose members vary independently when the write keeps no condition on them, neither a bound on one member nor a relation among several, an immutable record-style carrier, a default, clamp or normalization a caller applies to a member only for its own use when other users of the type may set that member to any value, a helper that calls only the type's own operations and reads no field or accessor to decide a write back into the object, and a type the project context declares a passive carrier. Validator question: **Does code outside a type read that type's fields or accessors, decide from them and write the outcome back into the same object, where the type states an invariant or the outside decision keeps a condition on its members that no user of the type may break?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-29`, severity minor, `file`, `symbol`, `code` = the outside read, decision and write-back on the object, or the added holder's declaration with the outside line that keeps its condition, quoted verbatim from the diff, `fix` = the operation as a method of the type that checks the condition, with the caller rewritten to call it, in the file's language, `rationale` = the condition on the type's members that the outside code keeps and the type that cannot guard it).
