# A class that code outside its own module can subclass and that calls its own overridable methods documents those calls for subclasses or is closed to subclassing

## Thesis
A class that code outside its defining library, package or module can subclass, and whose own method bodies call methods a subclass can override, takes one of three courses. It documents that self-use as an extension contract for subclass authors: the doc-comment of each non-private method that calls an overridable method, directly or through private helpers, or the type's documentation, names the methods it calls and how it calls them (once or repeatedly, in what order, under what condition). Or its own method bodies call no overridable method, calling non-overridable helpers instead. Or it is closed to subclassing from outside its library: a closing modifier or annotation, a modifier that lets outside code implement the type's interface but not extend its implementation, or a constructor that outside code cannot call, with factory functions in its place. A trait whose provided methods call other methods of the trait takes the same three courses; a trait meant to be implemented only inside its library closes by requiring a private marker trait that outside code cannot name, and its documentation states that it is sealed and not meant to be implemented outside that library.

## Rationale
A subclass that overrides methods of its superclass is intricately intertwined with it: the two are not composed, and their behaviour cannot be understood independently. Such a subclass can often be written only by observing how the superclass's methods delegate to each other, so a programmer who changes that delegation is very likely to break the subclasses that override those methods. The calling pattern is a contract of its own, the extension contract, different from the external contract between the class and its users; where it goes undocumented, subclass authors are on their own, and a future version may break their extensions by rearranging internal call patterns. Any call to an overridable method can be overridden in unpredictable ways and execute arbitrary code, which makes such methods costly to design, test and maintain, and their contract usually takes more effort to define and document; designing a class well for subclassing has frequently been observed to take far more effort than designing it for ordinary use, because the rules of delegation must be laid out if independently designed subclasses are to have any chance of working. Documented self-use tells a subclass author what an override changes: provided operations that make repeated calls to an underlying method have quadratic performance when that method is linear and will likely need to be overridden; a documented hook names the method whose override can substantially improve the performance of the operation that calls it, and the method that must be overridden before an inherited operation stops throwing. Within a single module, where superclass and subclasses are co-designed, the cost of getting this wrong is very low, since it is easy to fix all of the clients; across library boundaries it is very problematic unless the superclass has established firm rules from the beginning. Closing the class to outside extension reduces the hazard instead: when one of its methods calls another on itself, the call reaches a known implementation from the same library, other libraries cannot override methods the class's own methods might later call in unexpected ways (the fragile base class problem), and the authors keep the freedom to change the implementation, changes that might break subclasses, and to add to the interface incrementally; a sealed trait can gain methods in a non-breaking release, which would ordinarily be a breaking change. A trait's provided method is the counterpart of an inherited method: an implementor may override it, and its body may call other methods of the trait, even ones without a default implementation, so the same calling pattern arises. An open class that adds no overridable or protected members gives inexpensive extensibility, because unsealed types carry relatively low test costs.

## Example
```rust
bad:  pub trait Store {
          fn get(&self, key: &str) -> Option<String>;
          fn contains(&self, key: &str) -> bool { self.get(key).is_some() }
      }
good: pub trait Store {
          fn get(&self, key: &str) -> Option<String>;
          /// Provided: calls `get` once and returns whether it found a value.
          fn contains(&self, key: &str) -> bool { self.get(key).is_some() }
      }
```

## Limits
The rule reaches only a class or trait that code outside its defining library, package or module can extend or implement and whose own method bodies call an overridable method. Inside one module, where superclass and subclasses are co-designed and every subclass can be fixed along with the base, and in an application project rather than a library, an open class is no finding. An open class whose methods call no overridable method is no finding: sealing a class because no extensibility scenario comes to mind is not a good reason, and unsealed classes with no added overridable or protected members are inexpensive extensibility. A class designed for extension, whose documentation describes its calling pattern and its hooks, stays open; capping a hierarchy meant as an interface with closing modifiers is rarely needed for logical reasons and can damage its extensibility. A class that a framework or library requires to be open stays open and documents its self-use; ad-hoc extension of a class not designed for it also serves to mock classes in tests and to apply temporary patches to library classes, with the extender on its own. Embedding differs from subclassing: a method promoted from an embedded value runs with the inner value as its receiver, not the outer one, so the rule does not reach embedding. A closing annotation that only a type checker enforces closes the class to checked code alone; where the language has no closing modifier, a constructor that outside code cannot call keeps outside code from extending the class. A project context that marks a package internal, with every subclass and implementor in the repository, rejects the finding. Contested. One position closes what was not designed for extension: across library boundaries an overriding subclass depends on how the superclass's methods delegate to each other, so a public class is usable but not subclassable by other modules unless marked open, a class not designed to be subclassed is marked final, a class closed to outside extension guarantees that its calls on itself reach known implementations, and a trait meant to be implemented only in its library is sealed; its evidence is a language evolution proposal, a static-analysis check, a typing standard, two language references and an API guideline. The other position leaves classes open: do not seal a class without a good reason, unsealed classes with no added overridable or protected members are inexpensive extensibility, closing classes in a hierarchy meant as an interface is rarely needed for logical reasons, and frameworks require classes to be open; its evidence is a platform's framework design guidelines, a core guidelines rule and a compiler plugin's documentation. Two conditions separate the cases: code outside the library can extend the type, and the type's own methods call overridable methods. The closing position's delegation hazard meets both, since its proposal tolerates the hazard within a single module and its check makes sense only for library projects; its closing default and its check also reach a library class with no overridable self-use, for room to change the implementation and to add to the interface, and there the rule raises no finding, following the open position; the open position's cases fall outside the rule or satisfy it by documentation, since its inexpensive open class adds no overridable or protected members and is outside the rule unless its methods call an inherited overridable one, its hierarchy meant as an interface is designed for extension, and a class a framework must extend stays open and documents its self-use.


A call that a constructor, initializer, copy or deserialization routine makes on the object under construction is not made acceptable by documenting it; such a call is judged by its own rule.
## Validator
Grep the hunk for an added class declaration without a closing modifier, an added overridable or protected method, or an added public trait. Open the file and decide whether code outside the defining library, package or module can extend the type: it is public or exported, carries no closing modifier or annotation, has a constructor outside code can call, is not sealed by a private marker trait, and, in a language whose classes are closed unless marked open, is marked open. Take the project context or the package's build and publishing configuration as the answer to whether the code ships as a library that others extend; stop when it is an application, or a package whose subclasses and implementors all live in the repository. Trace each non-private method body of the type, following its calls into private helpers, for calls on the receiver, explicit or implicit, to methods a subclass or implementor can override: any method that the call resolves through the receiver's run-time type and that the language does not make final or private (a naming convention does not make a method private, and a static or class method called on the receiver counts where the language resolves it through the subclass), abstract or required methods, and any method of a trait. For each such call, read the doc-comment of the non-private method that makes the call or reaches it through private helpers, and the type's doc-comment: a description of which overridable methods the method calls and how, or a statement that the type is sealed together with a mechanism that seals it, satisfies the rule; a description of what the method returns, with no word on the calls it makes, does not. Validator question: **Does a class or trait that code outside its library can subclass or implement call, from one of its own method bodies, a method that a subclass or implementor can override, with no doc-comment of the non-private method that makes or reaches that call, or of the type, describing it and the type not closed to extension from outside its library?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-41`, severity minor, `file`, `symbol`, `code` = the line in the method body that calls the overridable method, quoted verbatim from the diff, or the class or trait declaration line when the call lies outside the hunk, `fix` = a doc-comment on the non-private method that makes or reaches the call, naming the overridable methods it calls and how, or the type closed to extension from outside its library (a closing modifier or annotation, a constructor outside code cannot call with a factory function in its place, or a trait sealed by a private marker trait and documented as sealed), in the file's language, `rationale` = the overridable method the body calls and the subclass or implementor behaviour that a change to that call would break).
