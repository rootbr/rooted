# A method returns or passes on, and does not call into, an object it obtained through another object's getter or field, except along builder calls, collections, transformations, strings and primitives

## Thesis
A method may call any method on its own object and on what its own methods return, on its parameters, on the objects held in its own class's fields, and on the objects it obtains from a constructor, a factory, a builder or a static method. An object it obtains through an accessor from one of these other than its own object — a getter, that is a call with no arguments and a result, named get…/is… or after the field it returns, or a read of the receiver's field — is one step too far: the method returns it or passes it as an argument, and calls no method and reads no field on it. `b.getC().doIt()` and `order.customer.address.update(...)` break the rule at their first accessor step, and so does a local variable assigned such a value and then called. A step does not count when it is a call that is not a getter, a call that returns a value of a type related to its receiver's (a transformation such as `expr.withFoo(...)`), a call that returns a collection, map, iterator, stream or array, an element taken from such a container, a call on a builder, or a string, number or boolean value. Where the method needs work done by a collaborator's collaborator, the immediate collaborator offers an operation that does it, or the method receives the object it needs as a parameter.

## Rationale
The rule bounds how far a method reaches for the objects it works on. Its purpose is to reduce coupling between classes or objects of different levels of abstraction, and the getter step that hands a method another object's collaborator is the step that breaks a boundary of abstraction. The law the rule implements is stated as language-independent; its motivation is to make software as modular as possible, and the principles it covers include coupling control, information hiding, information restriction and information localization. The tool that implements the rule counts no accessor step for a transformation, which stays as far away as its receiver, or for a container's elements, which stay as far away as the container, and makes room for collections, the builder pattern and getters that do not appear to break a boundary of abstraction. Over 395 releases of 30 open-source projects, chains of more than three method calls, confirmed by hand among a tool's candidates, were rare — present in 13% of the releases, and in the most affected release in 4 of 427 classes (0.9%) — and high fault-proneness was particularly evident for them; an earlier study had found this smell the one most correlated with fault-proneness. The same study saw no strong difference in the fault-proneness of the same classes between the periods when they carried the chain and when they did not, rated the effect of removing it as limited on fault-proneness and medium on change-proneness, and read smells in general as co-occurring with intrinsically fault-prone code rather than directly causing its faults. These measurements concern chains longer than three calls; none of them measures the single accessor step the rule flags.

## Example
```go
bad:  func (s *Scheduler) Notify(job *Job) error {
          return job.Owner().Mailbox().Send(job.Summary())
      }
good: func (s *Scheduler) Notify(job *Job) error {
          return s.mailer.Send(job.Owner(), job.Summary())
      }
```

## Limits
- Contested. The strict side is the tool's default threshold, the most restrictive it offers, which corresponds to the original law: one getter call is allowed on a value the method does not trust, and a call on its result is reported; the paper that states the law presents it as language-independent and also identifies valid violations, which its abstract does not list. The tolerant side rests on the tool's own warning that the rule "is prone to many false-positives and low-priority warnings", which raising its threshold reduces drastically, and on a framework developer who granted that each of a group of tightly coupled classes knows the members of the others, yet judged them best viewed as one unit and kept direct member access for performance at the core of a message loop; that developer was the only one in the evaluation who saw no need to refactor the class. Two conditions separate the cases. The first is what the chain passes through: an accessor step into an object that another object holds counts, while a builder call, a transformation, a collection or its element, a string or primitive value, and a value only returned or passed as an argument do not. The second is a documented project tolerance: a project context that documents a higher tolerated number of accessor steps, or documents a group of classes as one unit, rejects the finding for a chain inside that tolerance or that unit.
- A field of another instance of the method's own class counts as the method's own field in any method of that class, as an equality or comparison method needs.
- A chain that the documentation of a standard-library or third-party type prescribes to its callers, such as closing a response body read from the response's field, is outside the rule; the finding is rejected for it.

## Validator
In the hunk's added lines, find each chain in which a method is called on, or a field is read from, the result of an accessor applied to another object: a call with no arguments named get…/is… or named after a field, a property read, or a field read, whose receiver is a parameter, a field of the method's class, a value one of the method's own methods returns, an object obtained from a constructor, factory, builder or static call, or a local variable holding one of these. Include a local variable assigned such a result and called later in the method. Open the file and resolve the types along the chain. Discard the step when the accessor runs on the method's own object, when the call is not an accessor, when it returns a value of a type related to its receiver's, when it returns a collection, map, iterator, stream or array or takes an element from one, when its receiver is a builder, and when the value is a string, number or boolean. Discard the chain when the accessor's result is only returned or passed as an argument, when the field read belongs to another instance of the method's own class, and when the documentation of the standard-library or third-party type the chain runs through prescribes the chain to its callers. Check the project context for a documented higher tolerance of accessor steps or a group of classes documented as one unit. Validator question: **Does an added line call a method on, or read a field of, an object that the method obtained through another object's getter or field read, where that step is no builder call, transformation, collection access or string or primitive value, the object is not only returned or passed on, no standard-library or third-party documentation prescribes the chain, and no documented project tolerance covers it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-09`, severity minor, `file`, `symbol`, `code` = the chain quoted verbatim from the diff up to the first call or field read on the accessor's result, `fix` = the method calling an operation of its immediate collaborator, receiving the needed object as a parameter, or passing the accessor's result on as an argument, in the file's language, `rationale` = names the accessor step, the object whose held collaborator it hands out, and the call made on that collaborator).
