# A private or unexported function, method, field, constant or type that no code references is removed, unless reflection, a framework or a side effect of holding it puts it to use

## Thesis
A function, method, field, constant or type that its visibility or naming marks internal to its unit (private to its class or file, or unexported from its package, crate or module) and that no code, tests included, references after the change is dead code and is removed. This covers a declaration the change adds without a use and one whose last reference the change deletes; where the lost reference is itself the defect, such as a call an edit dropped by mistake, the reference is restored instead. A declaration reached through reflection, a serialization hook, an implicit call or an annotation-driven framework, a constructor declared only to keep its class from being instantiated, and a field never read but held for the action its value performs when released or for a marker property its type withholds from the enclosing type, are not dead code and stay; where the toolchain still reports one of them, it carries the marker the toolchain provides for that case instead of being removed.

## Rationale
A method that is never called is dead code; cleaning it out decreases the size of the maintained codebase, which makes the program easier to understand and keeps bugs from being introduced into it. Unused private members take up space in the code and can confuse readers, and a change that rewrites a routine takes care that its new behaviour satisfies all existing callers, when sometimes one of those callers was never reached in any execution and could safely have been deleted. Unnecessary code still draws maintenance at unnecessary cost: a two-year industrial case study quantified the maintenance activity that went into code that was unused, and interviews with professionals plus four experiments suggest that dead code is harmful in the maintenance and evolution phases. In a controlled study where six developers performed three maintenance tasks each on four functionally equivalent systems, file size and the number of changes explained almost all of the modelled variation in effort. Confinement is what makes removal safe: a declaration that cannot be referenced from outside its unit can be removed without considering the impact on other source files, while a library's public items count as part of its interface. Dead code may also signal a mistake or unfinished code, and an unused private class member is most likely an error due to incomplete refactoring, so the missing reference is examined before the declaration goes.

## Example
```java
bad:  int price(Order order) { return discounted(order); }
      private int discounted(Order order) { return order.base() - order.rebate(); }
      private int legacyPrice(Order order) { return order.base(); }
good: int price(Order order) { return discounted(order); }
      private int discounted(Order order) { return order.base() - order.rebate(); }
```

## Limits
A member used only through reflection, a serialization hook, an implicit call, or a framework that annotations enable, such as dependency injection or mocking, is in use although no reference shows it; static analysis cannot detect that usage, so it keeps a keep annotation or a suppression marker rather than being removed. A field that is never read but is held for the action its value performs when released, or for a marker property its type withholds from the enclosing type, changes behaviour when removed: the first keeps a lint allowance on the field and the second uses a phantom marker type in its place. A declaration intended for use outside its unit is given the visibility that exposes it instead of being deleted. Public or exported declarations of a library are outside the rule, since they count as part of its interface. A function called only from assembly code, or aliased through a link-name directive, has a use that a source analysis is not aware of. In a dynamic language, a static analyser is likely to miss some dead code, and code that is only called implicitly may be reported as unused. A constructor declared only to keep its class from being instantiated, typically the sole zero-argument constructor of a class of static members, is unreferenced by design; deleting it lets the language supply a public constructor, so it stays.

## Validator
Grep the hunk for added or edited declarations whose visibility or naming marks them internal to their unit (a private modifier, a private-name sigil, a leading underscore, a lowercase unexported name, an item without a public modifier or with one restricted to its crate or parent module) and for deleted lines that referenced such a declaration. For each one, open every scope its visibility admits (the enclosing top-level class, the file, the module with its submodules, the package or the crate) together with the tests that reach it, or the whole repository where the privacy is a naming convention or a check that code elsewhere can bypass by naming the member in a string, and search for the name both as an identifier and as a string literal; trace every hit to a real use. Then check the declaration for reflective access, a serialization hook, an implicit call (an initializer or entry point the runtime invokes, or an override or a trait or interface implementation reached through the declaration it implements), an annotation on it or on its enclosing class, a keep or suppression marker, an allowlist entry, a constructor whose only job is to keep its class from being instantiated, and a field held for its release action or for the marker property of its type. Where the hunk deleted the last reference, read the surrounding diff to decide whether the deletion was intended or a call was dropped by mistake. Where nothing references the declaration, read its doc comment and the rest of the change to decide whether it is meant for use outside its unit and lacks only the modifier that exposes it. Validator question: **Does the change leave a declaration its visibility or naming marks internal with no reference in the scope searched, and with no reflective, serialization, framework, implicit-call or side-effect use, no instantiation-blocking role and no keep marker accounting for it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-08`, severity minor, `file`, `symbol`, `code` = the unreferenced declaration's signature line verbatim from the diff, or the deleted line that held its last reference, `fix` = the file with the declaration deleted, with the dropped call restored where the lost reference is the defect, or with the modifier that exposes the declaration where its doc comment or the rest of the change presents it as meant for use outside its unit, in the file's language, `rationale` = names the declaration, the scope and tests searched, and the absence of any reflective, serialization, framework, implicit-call or side-effect use and of an instantiation-blocking role).
