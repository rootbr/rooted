# Each identifier follows the naming convention its language's official style documentation sets for its kind, or the project's established convention where that differs

## Thesis
Each added identifier takes the form that its governing convention sets for its kind (type, routine, variable, field, parameter, constant, module): the case and the word separator, the case of an acronym or initialism inside the name, the prefix and suffix markers the convention defines and no others, and the part of speech where the convention states one as a directive rather than as typical, such as a noun phrase for a type and a verb phrase for a routine that performs an action. Constant case marks only the kinds that convention gives it to: where the convention reserves it for module-level or static values, a local variable keeps the variable form even when it is never reassigned, and a mutable value keeps the variable form only where the convention also requires a constant to be deeply immutable. The governing convention is the style already established in the module, then the project's declared or established house style, then the language's official style documentation; where the language documents no single convention, the project's house style decides.

## Rationale
A convention gives each kind of name its own visible form, so the form tells a reader the kind of a name before the declaration is found, and a name written in another kind's form reads as that kind: a local variable in constant case reads as a module-level constant. The form is more than appearance in some languages: in one, the case of a name's first letter decides whether the name is visible outside its package; in another, the compiler warns by default on a type not in capitalised camel case, on a variable, function, field or module not in lower-case underscore form (a local written in constant case included), and on a static not in upper case. Acronym case shows why the rule defers to the language rather than to one form: the documented conventions disagree, one counting an acronym as one word (Uuid), one keeping an initialism in a single case (URL or url, never Url), one capitalising a two-letter acronym whole and a longer one as a word (IOStream, HtmlTag), one capitalising every letter of the acronym (HTTPServerError). The casing studies disagree on accuracy and tie recognition speed to training. In a study of 135 programmers and non-programmers, camel case gave higher accuracy regardless of training, and those trained in camel case recognised camel-case identifiers faster than underscore ones; an eye-tracking replication with programmers trained mainly in the underscore style found no difference in accuracy and faster recognition of underscore identifiers; a later journal study is summarised as finding no significant difference in comprehension between the two styles as long as developers had training or experience in the style, with a slight edge for camel case on shorter names. The gain therefore lies in matching what the code's readers are trained on: the language's official convention for its wider community, the module's prevailing style for the readers of that module. The style documents and tool rules defer the same way: one ranks consistency with the style guide as important, within a project as more important and within one module or function as most important, and prefers internal consistency where an existing library has a different style; a linter's casing rule is to be turned off where established coding standards use a different convention; another asks for the project's own naming convention, and another for one house style that leaves imported libraries in their original style.

## Example
```python
bad:  class order_item: ...
      def fetchJson(url): ...
      def total(items):
          taxRate = 0.2
          return sum(items) * (1 + taxRate)
good: class OrderItem: ...
      def fetch_json(url): ...
      def total(items):
          tax_rate = 0.2
          return sum(items) * (1 + tax_rate)
```

## Limits
A name dictated from outside the code keeps its outside form: a routine that overrides or implements an inherited declaration, a name a framework requires or looks up by string, generated code, a wire-format, database or configuration field mapped one to one, and a binding that mirrors a foreign library's names. Where the language or its convention gives part of a name a meaning, such as the case of its first letter or a leading underscore marking whether the name is visible outside its package or module, that part follows the visibility the name needs, and only the rest of the name is compared with the module's prevailing form. In a module whose established style differs from the language's convention, a new name in the module's style meets the rule, and a new name in the language's convention is flagged unless the project context documents a migration of that module to the language's convention. Where the language documents several styles and the project declares none, the file's prevailing style governs, and in a new file the added names need only agree with each other. A naming pattern configured in the project's linter or style configuration is a declared house style, and where that configuration checks the module's new names, its pattern governs them ahead of the module's prevailing style. A part of speech that a convention describes only as typical flags nothing, and a name in a part of speech that the convention's directive admits conforms, such as an interface named by an adjective phrase, a field named by an adjective, or a boolean property named by an affirmative phrase with or without an is, can or has prefix. The rule judges names the change adds; renaming existing names to conform is a separate change, and a rename that would break existing callers is outside it. The rule weighs a name's form only, the part of speech its convention requires included: its length, its choice of words beyond that part of speech, its meaning and whether it tells the truth about the code are outside it. A naming tolerance stated in the project context rejects the finding.

## Validator
Grep the added lines for declarations: types, routines, variables, fields, parameters, constants and modules. Open the file and note, for each kind, the form its existing declarations use: case, word separator, acronym case, prefix and suffix markers, and which values take constant case. Read the project context for a declared house style or a configured naming pattern, and take the language's official convention for each kind; the governing convention is the module's established style, then the house style, then the language's convention, except that a naming pattern the project's linter or style configuration checks the module's new names against governs them ahead of the module's established style. For each added name, compare its form with the governing convention for its kind; for a name in constant case, check that its kind is one the governing convention gives constant case to: where that convention reserves constant case for module-level or static values, a local variable in constant case does not qualify, and a mutable value in constant case fails only where that convention also requires a constant to be deeply immutable. Skip a name dictated from outside the code: an override or implementation of an inherited declaration, a framework-required name, generated code, a mapped wire-format or database field, a foreign binding. Compare a first-letter case or a leading underscore that the language gives a visibility meaning with the visibility the name needs, not with the module's prevailing form. Validator question: **Does an added name take a case, word separator, acronym form, prefix or suffix marker, constant form or part of speech that the convention governing its kind does not give it, or lack a marker that convention requires, without being dictated from outside the code?** Yes → flag.
