# Adding a variant or field to a published type breaks callers that match it exhaustively or build it with a literal that has to give every field, unless the type was declared open to additions

## Thesis
Two additions to a published type, one that code outside its defining package can name, break that outside code. A new variant of an enumeration breaks a match or switch that the compiler or a type checker holds to cover every variant. A new field of a record type breaks a literal or constructor call that has to give every field, whether by name or by position, and a pattern that has to name every field. Such an addition stays within a major version only where the type was declared open to additions or, for a record, where the compatibility policy published for its package or for its language has outside code build it with keyed literals; any other such addition is a breaking change and ships under a new major version. An open enumeration is marked so that every match over it outside its package needs a wildcard arm. An open record is marked so that outside code can neither build it with a literal nor destructure it without a rest pattern, or it already holds a private field, so that no outside code can rely on a literal of it or an exhaustive pattern over it. Making an already published type open breaks the outside literals and matches it then rules out, so the choice to leave room for growth is made when the type is first published.

## Rationale
Exhaustiveness checking turns a new variant into a break: a match that explicitly checks all the variants breaks once a variant is added, and a type checker that verifies a switch or match over a union or an enumeration reports the new member as the case the code does not handle. A record breaks the same way: once a public field is added to a record with no private field, existing literals of it and exhaustive patterns over it break; a positional literal of a record type imported from another package fails to compile on the addition of any field, even an unexported one, while a keyed literal that may leave fields unset continues to compile; and a constructor that takes every field by position changes its signature with each new field. A marker that a type may gain variants or fields preserves backwards compatibility by restricting outside code in advance: outside the defining package a marked record cannot be built with a literal and a pattern over its fields needs a rest pattern, and a match over a marked enumeration needs a wildcard arm because matching a variant does not count towards exhaustiveness. A record that already holds a private field can gain or lose private fields without effect outside, since no outside code could be relying on literals of it or on exhaustive matches against it. Opening a type later costs what any other break costs: adding a private field to a record whose fields are all public makes outside literals impossible to write, which can break code irreparably, and a change that breaks client code requires a new major version. The choice is a trade-off rather than a default. Leaving a published type exhaustive is a stability commitment under which every new variant or field is a breaking change; marking it open takes from every outside match the exhaustiveness check that names the case it does not handle, and the linter check that flags every exported enumeration and record not marked open sits among the checks that are off by default and enabled case by case. Openness keeps outside code compiling; existing code that does not set a new field continues to work when the value the field takes unset is meaningful and preserves the old behaviour.

## Example
```rust
bad:  pub enum Status { Active, Suspended, // Closed added in 1.1
          Closed,
      }
      pub struct Limits { pub max: u32, pub burst: u32 } // burst added in 1.1
      #[non_exhaustive] pub enum Mode { Fast, Safe } // marker added in 1.1
good: #[non_exhaustive] // since 1.0
      pub enum Status { Active, Suspended, Closed }
      #[non_exhaustive] // since 1.0
      pub struct Limits { pub max: u32, pub burst: u32 }
      impl Limits { pub fn new(max: u32) -> Self { Self { max, burst: 0 } } }
```

## Limits
The rule reaches code outside the defining package: inside it the open marker has no effect, and a positional literal of the package's own record type is not the fragile case. A published type left exhaustive is no finding by itself; it is a stability commitment the authors may choose, and the check that flags every exported exhaustive type is a restriction enabled case by case. The finding is the addition that breaks the commitment within a major version. An addition released under a new major version declares the break and is no finding. In a package still at major version zero anything may change at any time and the public API should not be considered stable, so an addition there is no finding, except where the package manager's compatible-update requirement admits every later release that keeps the leftmost nonzero version component: there that component plays the part of the major version, and an addition that keeps it is a finding. Where no compiler or type checker that outside code may run can hold a match over the type to cover every variant, a new variant breaks no outside match at compile time, and the variant half of the rule does not apply. Other ways a new field can break outside code, such as a field of a non-comparable type that makes a comparable record non-comparable and breaks code that compares its values, and whether a new field's default keeps the old behaviour, are outside this rule. A project context that places the type outside the public API the project declares, in the code or in its documentation, or among unstable features its stability promise does not cover, rejects the finding.

## Validator
Grep the hunk for an added variant line, an added field line, an enumeration or record declaration, an open-to-additions marker or a first private field. Open the base version with `git show <base_sha>:<path>` and find the type each added line belongs to. For an added variant or field, establish four facts: the type is visible outside its package in a published package; the base did not already declare it open with a marker, a private field, or a compatibility policy, published for the package or for its language, under which outside code builds it with keyed literals; outside code can match it under an exhaustiveness check, build it with a literal or constructor call that has to give every field, or destructure it with a pattern that has to name every field; and the change keeps the package's major version at one or above, or keeps the leftmost nonzero component of a 0.y.z version where the package manager's compatible-update requirement admits the later releases that keep it, read from the manifest, the module path or the changelog. For an added marker or first private field on a type the base published without one, apply the same version test. Validator question: **Does the change either, within a major version at one or above or within the leftmost nonzero component of a 0.y.z version that the package manager treats as compatible, add a variant or field to an outside-visible type the base did not declare open where outside code can match it exhaustively, build it with a literal or constructor call that has to give every field, or destructure it with a pattern that has to name every field, or newly declare such a published type open?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-25`, severity major, `file`, `symbol`, `code` = the added variant, field or marker quoted verbatim from the diff, `fix` = the addition released under a new major version, with the type declared open in that release where it is expected to grow, in the file's language, `rationale` = the outside match, literal or pattern the addition breaks and the major version the change keeps).
