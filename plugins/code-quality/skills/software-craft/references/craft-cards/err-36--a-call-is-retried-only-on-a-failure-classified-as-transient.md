# A failed call is retried only on a failure classified as transient, and a permanent error, an invalid request, the caller's cancellation or the caller's expired deadline goes to the caller without a retry

## Thesis
The condition that decides whether a failed call is retried admits only failures that a later attempt of the same request can clear: the callee is unavailable (a network hiccup, a temporary overload or scheduled maintenance), the connection broke, or the callee limited the request rate and named how long to wait before a new request. The following failures go to the caller on their first occurrence, without a retry: an invalid argument, a missing resource or one that already exists, a refused permission, failed authentication, a failed precondition, an operation the callee does not implement, data loss, the caller's cancellation, and the expiry of the caller's deadline for the whole call. The condition is written as that classification — the error types or status codes that the callee and its protocol mark as transient — rather than as every error or every non-success status.

## Rationale
Many failures are transient, and running the task again with little or no change succeeds: an unavailable callee generally results from network hiccups and is retryable in the expectation that the connection becomes available soon, and a temporary overload or scheduled maintenance is likely to be alleviated after some delay. Other failures are not transient and may need a different remedy. Retrying a request with an invalid argument will never succeed. A missing resource, a refused permission, failed authentication and a failed precondition each wait on a change — the resource created, the permission granted, the client authenticated, the system state changed — and a client is not to retry them until that change has happened. Data loss is unrecoverable and is surfaced to the application at once. The caller's cancellation and deadline are to be honoured: the call's deadline spans all its attempts, and once it passes the call fails however many attempts were configured or made. Among 70 retry bugs studied in six open-source distributed applications, 17 — about a quarter — came from a wrong retry policy: in 9, non-recoverable errors were retried, which increased job latency or left client APIs unresponsive; in 8, recoverable errors were not retried, causing stuck jobs or even large-scale performance degradation and system failure. A broad error type sweeps permanent failures into the retry: a policy that retried every I/O error also retried the permission failure that the I/O error type includes, and a permission failure wrapped inside a general error that was always retried escaped the check that excluded it until the fix unwrapped the cause. Treating cancellation as a recoverable error makes the cancel fail and wastes resources; one cancelled job kept retrying its writes indefinitely. The classification needs upkeep as the callee changes: with a long list of error codes, which ones are transient is hard to track — one studied application had 74 — and when a library upgrade began to return a new transient error, the calling application did not notice or handle it for over a year. A rate-limit response may name how long to wait before a new request, while an exhausted quota may not recover for several hours, and retries meanwhile may be billed.

## Example
```java
bad:  for (int attempt = 1; ; attempt++) {
          try { return client.fetch(request); }
          catch (IOException e) { if (attempt == MAX_ATTEMPTS) throw e; }
          pause(attempt);
      }
good: for (int attempt = 1; ; attempt++) {
          try { return client.fetch(request); }
          catch (UnavailableException e) { if (attempt == MAX_ATTEMPTS) throw e; }
          pause(attempt);
      }
```

## Limits
No list of codes fits every application: a protocol library can report one code for different causes, and servers can return the same codes, so each application decides which codes it retries, and a condition that follows the retry classification the callee's owner or the project context documents meets the rule, provided it still passes an invalid argument, data loss, the caller's cancellation and the caller's expired deadline to the caller. In general the codes to retry are those that show the callee did not process the request; where the callee's owner knows an operation is idempotent, a wider set, such as an internal error, may be retried as well. Some timeouts on a single attempt, while the caller's deadline still has time left, are transient failures: a server that timed out waiting for the request lets the client repeat it, and a keep-alive that times out is reported as unavailable. A conflict that aborts a read-modify-write sequence or a transaction is retried at the level above the single call, by restarting the whole sequence, and code that does so meets the rule. A request may be repeated once its cause has been changed: with new or replaced credentials after an authentication failure, or resubmitted after the correction the error names. A read designed to wait until a resource is created may retry a not-found answer, a design that is generally discouraged. An exhausted resource that is not a quota and is expected back much sooner may be retryable. Whether the operation is safe to repeat, how many attempts are made and how long the call waits between them are judged by their own rules.

## Validator
Grep the added lines for a retry loop or attempt counter, a retry decorator, annotation, policy, option or helper call, and a retryability predicate. For each hit, open the file and find the condition that decides whether a failure is retried: the caught error types, the predicate's body, the list of retryable codes or statuses, or the policy's include and exclude sets. Trace each broad error type or catch-all in the condition to the failures it spans, including errors the call path wraps inside a general type, and check whether the condition tests for the caller's cancellation and for the expiry of the caller's deadline before it retries. Set aside a condition that follows a retry classification the callee's owner or the project context documents and still passes an invalid argument, data loss, the caller's cancellation and the caller's expired deadline to the caller; a timeout on one attempt that leaves the caller's deadline time to run; a restart of a whole read-modify-write sequence or transaction on an abort; a repeat after the credentials or the request were changed; a read designed to wait until a resource is created; and an exhausted resource, not a quota, that the callee documents as recovering soon. Validator question: **Does an added or changed retry condition admit every error, every non-success status, or a failure that a later attempt of the same request cannot clear — an invalid argument, a missing resource, a refused permission or failed authentication, a failed precondition, data loss, the caller's cancellation or the caller's expired deadline?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-36`, severity major, `file`, `symbol`, `code` = the added retry condition quoted verbatim from the diff — the caught type, the predicate, the list of retryable codes or the policy line, `fix` = the condition narrowed to the named error types or status codes that a later attempt can clear, with every other failure, the caller's cancellation and the caller's expired deadline passed to the caller on first occurrence, in the file's language, `rationale` = the permanent failure, cancellation or deadline the condition admits and what retrying it costs: an attempt that cannot succeed, a later report to the caller, a cancel that fails).
