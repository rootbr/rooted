# Research note — Python packaging and project tooling

Topic `python-packaging-and-project-tooling` of group python, domain `tooling`, id prefix `PY`. Formulation locators: PyPA guide; PEP 517, 518, 621; Ruff and mypy docs.

The four candidates of this topic all turn on Python's own version: what the running interpreter is and what the project declares as its floor. Pylint's W2601-W2607 flag syntax and standard-library features (f-strings 3.6; `:=`, positional-only parameters and `typing.final` 3.8; `except*`/`ExceptionGroup` 3.11; PEP 695 syntax 3.12; comprehension unpacking 3.15) newer than the `py-version` minimum. Ruff's UP036 flags `sys.version_info` blocks that only run below the minimum Ruff takes from `target-version` or `requires-python`. Ruff's flake8-2020 family (YTT101-YTT303) flags reading the `sys.version` string and comparing one version component alone, and RUF048 flags `map(int, __version__.split("."))`. The documentation agrees with the catalogs. The PyPA guide says `requires-python` declares the minimum supported Python and that pip compares it with the running interpreter. CPython's sys documentation says not to extract version information from `sys.version` and to use the `sys.version_info` tuple. The PyPA version specification (PEP 440) defines epoch, pre-, post-, dev and local segments that `int()` cannot parse. No position is contested and every candidate becomes a card. The relayed arXiv papers (2310.12598, Watchman, 2507.18075) concern dependency conflicts and configuration issues that TOOL-01 to TOOL-07 already state, so they back no rule here. The topic's other owned areas (src layout, lock files, ranged dependencies, ruff/mypy configuration, entry points) produced no Python-specific candidate. Unverified by me: the triage note says version-string-split-to-int extends INP-13, a universal card outside the tooling list given to me, so the card rests on the Python-specific PEP 440 segments and `packaging.version`. If INP-13 already names version strings, that card should become universal-instance of INP-13.

Topic `python-packaging-and-project-tooling` of group python, domain `tooling`, id prefix `PY`. Formulation locators: PEP 517, 518, 621, 508; PyPA packaging guide and specifications; setuptools docs.

The topic covers how a Python project is declared and built: the [build-system] table, the [project] metadata table, dependency metadata as opposed to requirements files, console_scripts entry points, the src layout and the commands that build and install a project. The static-analysis catalogs have almost nothing here, so every rule rests on official documentation fetched for this run: PEP 517, PEP 518 (through the PyPA pyproject.toml specification), PEP 621, the PyPA guide, setuptools and pytest. The documents agree on most points. python setup.py commands are deprecated and MUST NOT be run. Dependency metadata, not a requirements file, is what pip reads when a package is installed. The [build-system] table should always be present in a project that is built. New projects use the [project] table. console_scripts entry points are the cross-platform way to install a command. The one contested point is project layout: pytest strongly suggests the src layout and the PyPA guide explains the import-path hazard the src layout avoids, while setuptools calls the flat layout practical for the REPL but more error-prone, and the PyPA guide notes that the src layout requires installing the project. The separating condition is a project built into a distribution and imported from processes started in its root. The candidate project-metadata-in-project-table-with-requires-python was split in two: the [project]-table rule keeps the key, and requires-python got its own key. requires-python needs a separate check (does the floor exist), it has its own evidence, and PY-71 takes a declared floor for granted. Claims the fetched texts do not state were stripped from the candidates: the build-time import check of entry points, the editable-install indistinguishability phrasing, and the exact-pin clause of the dependency candidate, which TOOL-04 already states. arXiv:2310.12598 (abstract fetched) supplies the measured scale of PyPI configuration issues behind the dependency-metadata card; arXiv:2507.18075 concerns vulnerable dependency ranges (TOOL-09's ground) and backs no card here.
