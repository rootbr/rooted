# A constructor or factory with more than a small handful of optional inputs takes them by name, not by position or through telescoping overloads

## Thesis
A constructor or factory that accepts more than a small handful of optional inputs with no natural order lets each caller set the optional inputs it needs by name and leave out the rest. It does so in a form the language supports: named parameters with defaults that the signature accepts only by name, an options object or struct whose fields the caller sets by name and may omit, option values named for the input each one sets and passed through a variadic parameter, or a builder whose methods are named for the inputs they set and whose own constructor takes only the required data. The optional inputs are not taken as a run of trailing positional parameters, nor through a telescoping family of constructors or overloads in which each adds trailing parameters to a shorter one. Required inputs may stay positional. The rule applies primarily to exported constructors and factories.

## Rationale
As parameters are added, the role of each becomes less clear and adjacent parameters of the same type become easier to confuse; a routine with many arguments is less memorable and harder to read at the call site, where the reader is left asking what the fifth argument means. Parameters that share similar types are prone to mix-ups when the routine is called with positional arguments. Where there are no default values, a signature that takes every input by position forces callers to provide all possible parameters; where defaults exist, a positional caller still supplies every optional input that precedes the one it changes, because each positional argument binds to the parameter at its position. Default values give a caller an easy way to override a default on the rare occasion it needs to, without defining lots of functions for the rare exceptions. Construction that needs many inputs, compound data, optional configuration data or a choice between several flavours can easily lead to a large number of distinct constructors with many arguments each, and as they evolve, keeping the parameter order consistent across the overloads becomes increasingly difficult. A named form changes the call site: a call that pairs each field or method name with its value is self-documenting and harder to swap, with no confusion about argument order; irrelevant or default inputs can be omitted; and an options struct can grow over time without changing existing call sites. The documented counts differ. One style guide states the condition as more than a small handful of optional parameters that do not have a natural order; linter defaults flag more than five arguments, more than five positional arguments, more than seven arguments, or ten or more parameters; and one linter's documentation states that for almost all interfaces comprehensibility suffers beyond a handful of arguments. This rule reads more than a small handful as five or more optional inputs taken by position.

## Example
```python
bad:  def __init__(self, host, port=5432, timeout=30.0, retries=3, tls=False, pool=10): ...
      Client("db", 5432, 30.0, 3, True)
good: def __init__(self, host, *, port=5432, timeout=30.0, retries=3, tls=False, pool=10): ...
      Client("db", tls=True)
```

## Limits
Inputs with a natural, well-established order may stay positional: a call whose use is self-evident, such as two values compared or two sequences zipped, and a well-known convention such as four colour channels, where four or more positional parameters make sense and naming each one every time would waste the caller's time. A few overloads that give convenient signatures for genuinely frequent common cases are a documented alternative to a named form and answer the finding when none of them takes more than a small handful of optional inputs by position; the finding is the telescoping family, too many variants each adding trailing parameters, or an overload that itself takes more than a small handful of optional inputs by position. The heavier named forms cost code: option values passed through a variadic parameter require a substantial amount of additional code and should be used only where their advantages outweigh that overhead, and the choice among the forms follows how the call looks across all expected uses, an options struct being often preferred when every caller sets one or more options or many callers set many, option values when most callers set none and the options are many or used infrequently. Splitting a highly configurable constructor into several simpler ones, or grouping inputs that belong together into their own type, are documented alternatives and answer the finding when no run of optional inputs is left for callers to pass by position. For an unexported constructor or factory these techniques may be unnecessary, since the recommendation applies primarily to exported interfaces, and one linter does not count the parameters of a private constructor. A project tolerance rejects the finding: a raised argument-count or positional-argument threshold in the project's linter configuration that the signature stays within. Routines that are neither a constructor nor a factory, such as a method that configures an existing value, are outside this rule.

## Validator
Grep the hunk for an added or changed constructor, factory or constructor-function signature, or for an added constructor that delegates to another constructor of the same type with more arguments. Open the file and list the type's constructors, overloads and factories with each parameter marked required or optional: optional where it carries a default value or an optional marker, where a shorter overload or sibling constructor fills it with a fixed value, or where a caller may pass its zero, empty, null or absent value to leave it at its default. Count the optional inputs the signature accepts by position, whether or not it also accepts them by name, and the overloads that each add trailing parameters to a shorter one, and read the added call sites in the hunk for positional arguments that restate a default. Treat five or more optional inputs taken by position as more than a small handful: beside even one required input the signature then exceeds the lowest documented default for argument lists in general, more than five positional arguments; the higher defaults, more than seven arguments and ten or more parameters, count every parameter of any routine and do not raise this bar. Skip inputs with a natural, well-established order, a few overloads for genuinely frequent common cases when none of them takes five or more optional inputs by position, a private constructor, and a signature within a raised threshold in the project's linter configuration. Validator question: **Does an added or changed constructor or factory accept more than a small handful of optional inputs with no natural order by position, as trailing positional parameters or through a telescoping family of overloads?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-02`, severity minor, `file`, `symbol`, `code` = the added signature, delegating constructor call or overload declaration that takes the optional inputs by position, verbatim from the diff, `fix` = the same construction with its required inputs still positional and its optional inputs taken by name through named parameters with defaults accepted only by name, an options object or struct, option values or a builder, in the file's language, `rationale` = how many optional inputs or overloads the construction carries and that a positional caller supplies every input before the one it changes and can swap same-typed arguments unnoticed).
