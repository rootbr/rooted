# An import whose names the file never uses is removed, unless it re-exports a name as part of the module's interface or is marked, in the language's form or the linter's configuration, as made only for its side effects

## Thesis
An import whose bound names the file never uses — by a reference, or by a use the language resolves through the import without naming it — is removed. An import that re-exports a name to make it available outside the module is declared as a re-export in the language's form for one, and an import made only for its side effects is written in the language's side-effect form, which gives the imported module no name in the file, or, in a language whose every import binds a name, names a module that the linter's configuration lists as having side effects on import. A blank reference that exists only to silence the unused-import check identifies the code as a work in progress, and the import it covers is eventually used or removed.

## Rationale
Where the language rejects an unused import at compile time, its documentation gives the reasons: unused imports bloat the program and slow compilation, an effect that can become substantial as a program accumulates code and programmers over time. In a language whose import executes the imported module when the file loads, an unused import adds a performance overhead at runtime and risks creating import cycles. An unused import also increases the cognitive load of reading the code, clutters it, and may signal a mistake or unfinished code. Some languages refuse to compile a program that imports a package without referring to any of its exported identifiers, trading short-term convenience for long-term build speed and program clarity. The side-effect form makes clear that the module is imported for its side effects, because there is no other possible use of it: in the file, it has no name. Where the language's tools document a redundant alias or an interface list as the re-export form, declaring the re-export that way instructs the tools to respect it and to avoid marking it as unused; elsewhere a redundant alias is itself an unused import, and the re-export is declared with a visibility modifier on the import.

## Example
```typescript
bad:  import { parse, format } from "./codec";
      import { registry } from "./plugins"; // loaded to register the plugins
      export const read = (text: string) => parse(text);
good: import { parse } from "./codec";
      import "./plugins"; // registers the plugins when loaded
      export const read = (text: string) => parse(text);
```

## Limits
An import made only for the side effects of loading the module is correct in the side-effect form: the import renamed to the blank identifier, or the file imported without bringing any name into the module. In a language whose every import binds a name, a module imported for its side effects is listed in the linter's documented setting for modules known to have side effects on import. A name imported to re-export it as part of the module's public interface is correct when declared as a re-export in the form the language's compiler and linter recognize: a visibility modifier on the import, or, where the tools document that form, a redundant alias of the name to itself or a list that declares the name as part of the module's interface. While a program is under active development, a blank declaration that silences the unused-import error is the documented workaround; by convention it comes right after the imports and carries a comment, both to make it easy to find and as a reminder to clean it up later. The declaration identifies the code as a work in progress, so a change offered as finished that carries one is still flagged. A blank declaration that assigns a value of another type to an imported interface type exists only for the type checking, a compile-time check that the type implements the interface, and is a use of the import, not a silenced one. An import kept only to check whether a module is available is a candidate for an explicit lookup of the module instead. An import the language uses without its name appearing in the file — a trait whose methods are called, a factory that markup compiles to, a compiler directive written as an import — is in use.

## Validator
Grep the hunk for added or changed import lines and for blank declarations that refer to an imported name. For each name an import in the hunk binds, search the whole file for a use outside the import statements: a reference to the name, or a use the language resolves through the import without naming it, such as a method called through an imported trait or interface, markup compiled to a call of an imported factory, or a compiler directive written as an import. For an import with no such use, open its declaration and check whether it is declared as a re-export (a visibility modifier on the import, or a redundant alias or an interface list where the language's tools document that form as a re-export) or written in the side-effect form that binds no name, or, where every import binds a name, names a module that the project context states the linter's configuration lists as having side effects on import. For a blank declaration, check whether it is the imported name's only reference and whether it only names the imported symbol; a declaration that assigns a value of another type to an imported interface type checks at compile time that the type implements it, and is a use. Validator question: **Does the hunk add or keep an import whose bound names the file never uses, outside a declared re-export, the side-effect form and a module the project context states the linter lists as imported for its side effects, or an import whose only reference is a blank declaration that silences the unused-import check?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-10`, severity minor, `file`, `symbol`, `code` = the import line or the blank declaration quoted verbatim from the diff, `fix` = the import removed or narrowed to the names in use; rewritten in the side-effect form, or, where every import binds a name, its module added to the linter's setting for modules with side effects on import, only where the module is loaded for its side effects; replaced by an explicit lookup of the module where it only checks that the module is available; or declared as a re-export; in the file's language, `rationale` = names the imported name with no use in the file and the cost it carries in the file's language: a heavier read in every language, a larger program and slower compilation where the language rejects unused imports at compile time, a runtime overhead and an import-cycle risk where the import executes the module when the file loads).
