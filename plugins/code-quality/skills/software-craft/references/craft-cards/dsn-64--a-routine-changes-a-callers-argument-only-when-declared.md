# A routine changes an object its caller passed in only when its signature, name or documented contract declares the change

## Thesis
A routine changes the contents of an object its caller passed in and still holds — adds to or removes from the caller's collection, sets a field of the caller's object, sorts or fills the caller's array in place — only when the change is declared where a caller looks before the call: in a parameter type that marks the argument as modifiable, in a language or codebase whose parameter types are read-only by default; in a name that states the change; or in the routine's documented contract. Otherwise the routine leaves the argument as it received it and works on a copy or returns a new value. Rebinding the parameter variable to another value leaves the caller's object as it was, since the parameter name is no alias of the caller's name, and is outside the rule.

## Rationale
The caller still holds the object it passed, so a change the routine makes to the object's contents is visible to the caller after the call, and a view that shares the argument's storage, such as a sub-range view over the caller's array, carries the change through as well. Tool documentation states that mutating function arguments can lead to confusing, hard-to-debug behavior and that side effects on parameters can make errors difficult to track down. Professional developers interviewed in a study of language support for immutability stated that incorrect state mutations are a major source of bugs, for example an object thought to be immutable changed by some other object because references were reused instead of immutable copies. A declaration tells the caller what the call does to its object: a parameter type that marks a modifiable reference makes it clear to callers that the object is assumed to be modified, a read-only parameter type gives callers a contract from which to reason whether the routine has side effects, and where references are read-only by default, a parameter that is not read-only is assumed to be one the routine modifies. A naming convention can carry the same declaration by marking the names of routines that modify their arguments, so that the copying and the modifying form of one operation carry different names, and a documented contract can carry it, as a reader's contract states that it reads into the caller's buffer and may use all of it as scratch space during the call while a writer's contract requires that it not modify the caller's data, even temporarily. Where a routine hands results back through its arguments, returning the results instead is almost always the clearest solution, and programs are far easier to reason about when called routines do not modify state.

## Example
```typescript
bad:  function printRanking(items: Item[]): void {
          items.sort((a, b) => b.score - a.score);
          items.forEach(item => console.log(item.name));
      }
good: function printRanking(items: readonly Item[]): void {
          const ranked = [...items].sort((a, b) => b.score - a.score);
          ranked.forEach(item => console.log(item.name));
      }
```

## Limits
The rule is contested. One position holds that a routine leaves its arguments unchanged: lint rules report a modification of a parameter's properties, a parameter whose type is not read-only, and a parameter passed to a function that modifies it, because, as their documentation states, mutated arguments can lead to confusing, hard-to-debug behavior and side effects on parameters can make errors difficult to track down. The other holds that a routine may change an argument when it declares the change: a reader fills the caller's buffer as its documented purpose, a modifiable reference type makes the mutation very clear, passing a mutable object is one documented way to hand output back, and a naming convention marks the functions that modify their arguments. What separates the two is whether the change is declared where a caller looks. The first position's own reasons name the undeclared change — accidental mutation of inputs, unintended behavior, a read-only type as a clear contract to consumers — and its property check is off by default and exempts the parameters a configuration names; one guideline holds both positions at once, making references read-only by default to avoid a called function unexpectedly changing the value, and calling a modifiable reference not inherently bad when the called function is supposed to modify the object. A parameter that a convention in the project context names as one routines may change is declared by that convention, as a lint configuration names the parameters its property check exempts. A method changing the object it is called on, a change to a local the routine created or to a copy that shares no storage with the argument, and a routine whose name reads as a query, predicate, accessor or conversion, which is held to its name, are outside the rule.

## Validator
Grep the added lines for a mutating call on a variable (add, append, push, insert, put, set, merge, remove, delete, clear, a setter, sort, reverse, fill, splice), an assignment or increment to an element or field of a variable other than the receiver or to the object behind a dereferenced pointer or reference, a delete of an element or field, a library or built-in call that sorts, fills, reverses, copies into, clears or deletes from a collection in place, and a merge into a target object. Open the file and, for each match, find the enclosing routine and trace the changed object to its source: a parameter, an element or field reached through one, or a view or shallow copy that shares storage with one. Set aside a change to a local the routine created, to a copy that shares no storage with the argument, or to the receiver; a rebinding of the parameter variable; and a routine whose name reads as a query, predicate, accessor or conversion. For each remaining change, read what a caller sees before the call: the parameter's type, which declares the change when it is a modifiable reference where the language or the codebase gives unchanged parameters a read-only type; the routine's name; its doc comment and the documented contract of an interface it implements; and the project context, for a convention that names parameters routines may change. Validator question: **Does the routine change the contents of an object passed in as an argument, directly or through a view or shallow copy that shares the argument's storage, while neither the parameter's type, the routine's name, its documented contract nor a convention in the project context declares the change?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-64`, severity major, `file`, `symbol`, `code` = the added line that changes the argument, with the routine's signature line when the diff adds it, quoted verbatim from the diff, `fix` = the routine working on a copy of the argument or returning a new value, or, where changing the argument is the routine's purpose, the declaration added — a modifiable-reference parameter type where the codebase types unchanged parameters read-only, a name that states the change, or a doc comment that states it — in the file's language, `rationale` = the argument the routine changes, the caller that still holds it, and the places a caller looks where the change is not declared).
