# Code that detects an unexpected broken assumption, contract or invariant that later code relies on stops or propagates an error instead of continuing on a substitute value

## Thesis
Code that detects a broken assumption, guarantee, contract or invariant stops there with an assertion failure, a panic or a process exit, instead of substituting a value (a null, a zero, an empty or default value, the unchanged input) or logging and carrying on, when the broken state is unexpected rather than an occasional, foreseeable failure and the code after the check relies on not being in it. Where the offending value came from a caller and continuing cannot be insecure or harmful, or where the internal state is still recoverable, an error the caller must handle serves in place of the stop; neither case continues on a substitute. When a failed invariant check means the internal state has become unrecoverable, the program terminates, and no handler recovers that stop merely to avoid the crash. A foreseeable failure, such as malformed input or a rate limit, is reported as an ordinary error and the program keeps running.

## Rationale
Code after an invariant check is written on the assumption the check protects, so that it need not re-check the state at every step. A substitute value lets that code run on a state it was not written for: a value the caller cannot tell from a real result can lead to bugs and attribute the failure to the wrong routine, and a failure swallowed on the way can leave the system in an inconsistent state with no record of why. A stop at the check reports the mistake where the offending value is still in hand. A broken invariant is a programming mistake, fixed by changing the code rather than by recovering at run time, and continuing past it can be insecure or harmful, since operating on invalid data can expose the program to vulnerabilities; where further execution is unsafe, terminating the process is to be considered in place of raising an error. Recovering the stop further up to keep running carries the same cost: the further the handler is from the failure, the less it knows about the program's state, which may be holding locks or other resources, so the recovery can propagate a corrupted state and open failure modes that are harder to diagnose. Programs rarely remain in an expected and usable state after a null-dereference failure, and continuing after catching and logging or suppressing it rarely succeeds. A foreseeable failure differs in kind: it happens in normal operation and the caller can recover in a way that suits its situation, so it travels as an error the caller handles. A state that a type can rule out needs no run-time check at all.

## Example
```python
bad:  match record.state:
          case State.OPEN: return open_total(record)
          case State.CLOSED: return closed_total(record)
          case _: return 0  # unreachable: the invariant says this cannot happen
good: match record.state:
          case State.OPEN: return open_total(record)
          case State.CLOSED: return closed_total(record)
          case _: raise AssertionError(f"unhandled state {record.state!r}")
```

## Limits
The rule is contested, and the kind of failure separates the cases. The stop fits a broken assumption, contract or invariant that is unexpected and that later code relies on, and termination fits a failed invariant check that leaves the internal state unrecoverable (the Source entries marked stop). Continuing fits a foreseeable failure and a problem that can be masked or worked around (the entries marked continue); the rule counts a problem as masked only where no later code relies on the broken assumption, the reliance the stop side names, so that the substitute is a correct result for every later use: there the code reports an error or applies its documented fallback and keeps running. The outer bound is a system for which a process exit is worse than limping on: a safety- or mission-critical system may catch and log every failure at its outermost layer and warm-start, or shut down a failing subsystem while other services continue, and the evidence calls the right handling of assertion failures in high-reliability systems an open question; such a tolerance, documented in the project context, rejects the finding. Where the stop did not report an unrecoverable internal state, a handler that recovers it without continuing the failed operation follows the rule: a module that raises and recovers its own internal signal to turn it into a returned error at its public boundary, re-raising any signal it did not raise, and a worker loop that isolates each task calling untrusted code. Where a type rules the bad state out (a non-optional type, a validating constructor, an exhaustive match the compiler or a type checker enforces), the type does the check and no run-time stop is needed. Which error type a stop raises, whether an assertion the build can strip is the right form of check, how a routine documents its preconditions, and the text of the stop's message are judged by their own rules.

## Validator
Grep the added lines for a comment or message calling a state impossible, unreachable or one that cannot happen; a default or wildcard branch that returns a null, a zero, false, an empty or a default value; a check that names an invariant or a corrupt, inconsistent or illegal state; and a handler that recovers a panic or an assertion failure. For each hit, read the hunk and name the condition the branch handles, then classify it: a broken assumption, contract or invariant (a state the code or its comment calls impossible, an enumeration value that reaches a default after every member has its own branch, a value the surrounding code established, a result the routine's own logic guarantees), a foreseeable failure (user input, a file, a network reply, a lookup that can miss), or a case the design serves on purpose (a default that gives the members no branch lists their intended result); a foreseeable failure and a case served on purpose are outside the rule. For a broken invariant, read what the branch does. An assertion failure, a panic, an unreachable marker that panics or aborts when reached, or a process exit follows the rule; an error that propagates to the caller follows it unless the check found the internal state itself unrecoverable, where only a stop does. For a substitute value, a log line followed by the normal path, or the input passed on unchanged, trace the value forward in the hunk: code that adds it to a total, stores it, indexes with it, or returns it to a caller that cannot tell it from a real result relies on the broken invariant; a substitute that is the documented, correct answer for every later use masks the problem and follows the rule. For a recovery, check whether the handler resumes the failed operation or returns a normal result from it, rather than turning its own module's signal into an error at the module boundary, isolating one task that calls untrusted code in a worker loop, or restarting at the outermost layer of a documented fault-tolerant system. A handler that recovers a stop the hunk shows was raised for an unrecoverable internal state, and keeps the program running, breaks the rule even when it drops the failed operation, unless it is that outermost restart. Validator question: **Does an added branch continue on a substitute value or a logged warning after meeting a broken assumption, contract or invariant that the code after it relies on, or return an error from a check that found the internal state unrecoverable, or does an added handler recover such a stop only to keep the failed operation running, or, where the stop reported an unrecoverable internal state, only to keep the program running?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-06`, severity major, `file`, `symbol`, `code` = the added branch or handler line that substitutes the value, logs and carries on, returns an error from an unrecoverable state, or recovers the stop, verbatim from the diff, `fix` = the same branch stopping with an assertion failure, a panic, an unreachable marker that panics or aborts when reached (never an optimizer hint whose reaching is undefined behavior), or a process exit, or, where the offending value came from a caller or the internal state is still recoverable, returning an error the caller must handle, naming the broken invariant and the offending value, or the recovering handler removed so the stop propagates, in the file's language, `rationale` = which assumption or invariant broke, which later code relies on it, and what the substitute value or the recovery lets that code compute or write).
