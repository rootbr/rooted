# A wrapper type whose every method forwards unchanged to one wrapped object is added only to hide that type from client code, restrict its methods, adapt it to an interface or give it a distinct meaning

## Thesis
A type that holds one object, and whose every method other than its constructor or initializer only calls the method of the same name on that object with the same parameters and returns its result unchanged, is added only where it does at least one of four things: it keeps a concrete implementation type out of the signatures its users see, those of an exported type or a public API or of the project's own boundary around a third-party library, so that the implementation can change without breaking the code that uses it; it exposes a restricted set of the wrapped type's methods instead of all of them; it lets the wrapped type implement an interface or trait that the wrapped type cannot be made to implement itself; or it statically distinguishes one interpretation of an underlying type from another. A forwarding type that does none of these is an unnecessary level of abstraction, and its callers use the wrapped object directly. Where an interface already exists, generated code such as an RPC client or server in particular, code uses that interface and does not wrap it in a new hand-written interface just for the sake of abstraction or testing. Methods a type gains by embedding, or every method it gains by automatic dereferencing, delegate to the same method of the wrapped object in the same way as hand-written forwarding methods.

## Rationale
A forwarding type is one more type for a reader to understand next to the one it wraps, and every exported type increases the cognitive load for the reader. An exported interface commits its package to maintaining that API for external callers, and maintaining perfectly mirrored interfaces across many packages can create an unnecessary burden. Complexity employed unnecessarily is a burden on those who need to read or change the code in the future, and it is easy to add complexity to code as needed but much harder to remove existing complexity after it has been found to be unnecessary. Code made more generic than it needs to be is over-engineering: the problem to solve is the one known to need solving now, and a future problem is solved once it arrives and its actual shape and requirements can be seen. A forwarding type earns its place by what it hides or changes. One that keeps an implementation type out of a public signature promises less to the client, so the representation can change in the future without breaking client code; hand-written delegate methods, though tedious, hide an implementation detail and leave more opportunities for change; a wrapper that implements only the methods wanted restricts the inner type's behaviour; and two newtypes over one underlying type let the code statically ensure that their two interpretations are not confused. A study that measures such classes separately does not tie them to a change or fault cost: across 395 releases of 30 open-source projects, classes detected as delegating more than half of their methods and confirmed by manual validation affected 30% of the releases, with at most eight in one release; unlike most of the 13 smells studied, the same classes were not generally more change-prone while affected than while unaffected, and removing them had a limited effect on change- and fault-proneness, although its pooled comparison of classes affected by any of the 13 smells with classes affected by none found the affected classes more change- and fault-prone.

## Example
```python
bad:  class OrderRepository:  # forwards every method of OrderStore
          def __init__(self, inner: OrderStore): self._inner = inner
          def get(self, order_id: str) -> Order:
              return self._inner.get(order_id)
          def put(self, order: Order) -> None: self._inner.put(order)
      def ship(repo: OrderRepository, order_id: str) -> None: ...
good: def ship(store: OrderStore, order_id: str) -> None:
          order = store.get(order_id)
          ...
```

## Limits
The rule reaches pure forwarding only: a method that adds a check, a conversion, a default, logging, caching, retrying or locking, or that changes a parameter or result type, is not a forwarding method, and a type with one such method is outside the rule; a new type can expose a public API different from that of the private type inside it. A base type whose forwarding methods exist so that its subtypes override some of them is outside the rule. An interface introduced to break a circular dependency between two packages is outside the rule, although needing one is often a signal of improperly structured packages. A wrapper the project owns around a third-party library other than an RPC client, written so that tests double the wrapper instead of the library, hides that library when the library's low-level API, concepts and exceptions stay inside its boundary; one whose forwarded signatures pass the library's own types through to its callers leaks the abstraction it was written to provide. A project context that names a forwarding layer as a required architectural boundary rejects the finding. Contested. One position removes the forwarding layer: simple code has no unnecessary levels of abstraction, an interface waits until a real need exists, and an existing interface, such as a generated RPC client, is used rather than wrapped in a new hand-written interface just for the sake of abstraction or testing; its evidence is official style and code-review guidance. The other position keeps a thin forwarding wrapper as legitimate: a newtype whose only method forwards to the wrapped value hides the representation and lets a public API promise less; hand-written delegate methods choose which methods form an exported type's interface and keep the shared implementation type out of it; a wrapper restricts the inner type's behaviour by implementing just the methods wanted; and an interface makes sense for two or more concrete types handled by the same logic, to break a dependency cycle, or to narrow a massive API surface to the one or two methods a function needs; its evidence is official language documentation, API guidelines and style guidance. What separates the cases is whether the forwarding hides or changes something that callers would otherwise depend on: an implementation type kept out of an exported signature, wrapped methods left out, an interface the wrapped type cannot implement, a second implementation outside tests, a dependency cycle broken, or a static distinction. A forwarding type that passes on all of the wrapped type's methods with the same signatures, and that is either not exported beyond the code that changes together with the wrapped type or exported to users who see the wrapped type anyway, protects no client code from a change and is the defect; its callers could take the wrapped object in its place.

## Validator
Grep the hunk for an added class, struct, newtype, interface or trait, and for method bodies that are one call on a held field, in shapes such as `return self._x.m(a)`, `this.x.m(a)`, `w.x.M(a)` and `self.0.m(a)`, or a dynamic attribute hook. Open the added type and check every method it declares other than its constructor or initializer: the body only calls the method of the same name on the same held object, passes the parameters through in order and returns the result unchanged; count methods gained by embedding or automatic dereferencing, and an attribute-lookup hook that returns the held object's attribute, as forwarding; any other statement, a changed parameter or result type, or a call on a second object ends the check with no finding. Search the repository for the type's callers and for the wrapped type: whether the type is exported to code outside its package or module and keeps the wrapped implementation type out of every signature that code sees, whether the callers also construct, import or receive the wrapped type, whether the wrapped type has public methods the wrapper leaves out, whether the wrapper implements an interface or trait that the wrapped type cannot implement itself, whether subtypes extend the type and override some of its methods, and whether a signature relies on the wrapper as a type distinct from the wrapped one. For an added interface, compare its methods with an existing interface or generated client it mirrors, and look for a second implementation outside tests or a package dependency cycle it breaks; a test double as the only other implementation does not count. Validator question: **Does the change add a type whose every method other than its constructor or initializer forwards unchanged to one held object, or a hand-written interface that wraps an existing interface or generated client, while hiding or changing nothing for its callers: no implementation type kept out of an exported signature, no wrapped method left out, no interface the wrapped type cannot implement, no subtype that overrides some of its methods, no second implementation outside tests, no dependency cycle broken and no static distinction?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-15`, severity minor, `file`, `symbol`, `code` = the added type's or interface's declaration line and one forwarding method line, quoted verbatim from the diff, `fix` = the callers taking the wrapped object or the existing interface directly with the forwarding type removed, or the type reduced to the methods its callers need, in the file's language, `rationale` = the wrapped type, the methods forwarded unchanged, and the absence of any hidden implementation type, left-out method, adapted interface, overriding subtype, second implementation outside tests, broken cycle or static distinction).
