# Research note — Concepts the interface reviewer found uncovered

Topic `gaps-interface` of group C. Interfaces, domain `interface`, id prefix `API`. Formulation locators: the taxonomy topics of the concepts and their canon locators: api-design-and-use (SW4.1); api-evolution-and-deprecation (SEG15, SEG21).

The interface reviewer found three concepts with no card. Each yields one candidate rule, and all three go to the drafter as cards. (1) No new use of a deprecated element. Software Engineering at Google formulates it as preventing backsliding: ch. 15 'Preventing backsliding' and 'Deprecation Warnings', which shows the warnings on newly changed lines only, plus ch. 20 and ch. 22. SEI CERT MET02-J states it as a standard ('Never use deprecated fields, methods, or classes in new code'). The compiler, type checker or linter of every corpus language documents the use-site check: java.lang.Deprecated and javac, Sonar S1874 and S5738, staticcheck SA1019, typescript-eslint no-deprecated, PEP 702, rustc, ECMA-334 and the C++ working draft. No source disputes the rule. The sources disagree on scope: staticcheck and javac exempt deprecated callers and the defining package, while PEP 702 and a local rustc run flag them. They also disagree on mechanism: Linux turned its build warnings off and reviews patches against a list, and pyright, mypy and typescript-eslint ship the check opt-in. The card therefore takes the scope every tool flags: code outside the defining package that is not itself deprecated. (2) A release that breaks the declared public API raises the major version. SemVer item 8, the Go modules reference with its /vN import compatibility rule, Cargo, Eclipse and Google's AIP-180/185 state it, and gorelease, cargo-semver-checks, Eclipse PDE API Tools and Elm enforce it. Venturini et al. (TOSEM 2023, arXiv:2301.04563) found that 44% of the breaking changes that reached npm clients came in minor and patch releases. The rule is openly contested by PEP 387, the PyPA guide (NumPy's loose SemVer, CalVer), Rust RFC 1105 ('not all breaking changes are major'), SEG ch. 21 ('a lossy estimate') and Hickey ('change the name'). The sourced separating condition has two parts: the project declares semantic versioning, or its package manager assumes it, and it is at 1.0.0 or later. The ecosystem's published policy decides which breaks count as major. (3) An operation clearly associated with one owned type is a method of that type. Rust C-METHOD, the Rust book, Swift's API Design Guidelines and the .NET Framework Design Guidelines state it, with a receiver condition and an ownership condition. C++ Core Guidelines C.4/C.5, Kotlin's extension functions, Python's and Go's len and Julia's multiple dispatch contest it. The separating condition comes from the guidelines themselves. The operation has one obvious receiver among owned types that have behaviour, the method adds no unwanted dependency, and the language's guideline decides the form: in C++ and Kotlin, an operation declared beside the type satisfies the rule. The card leaves passive data carriers out, because CHG-06 records the sources splitting on them. It leaves write-back on a type with an invariant to DSN-29, envious methods to CHG-06 and static-only namespace classes to DSN-05. Beyond Venturini et al., no fetched research measures any of the three. Sawant et al., Raemaekers et al., Ochoa et al. and Stylos and Myers stayed unfetched.

## Formulation layer

Concept 1 (no new use of a deprecated element): the SEG15 locator states it directly. 'Preventing backsliding' calls for tooling that stops new uses of what is being removed. 'Deprecation Warnings' says warnings prevent new uses but rarely migrate old ones, and are best shown on newly changed lines, which SEG20 and SEG22 repeat. Official language documentation says the same thing: Java's Deprecated Javadoc ('used or overridden in non-deprecated code'), the Rust reference, C# Obsolete, PEP 702, the Go wiki and PEP 387's soft deprecation. The only tension is 97 Things #42, which accepts suppressing a warning. Concept 2 (a breaking release raises the major version): SemVer item 8, the Go module reference (import compatibility rule, /vN path), gorelease, RFC 1105, Cargo, AIP-185 and Conventional Commits all state it. The canon disagrees sharply here. SEG21 calls SemVer a lossy estimate that overconstrains and overpromises, and Hyrum's Law adds that any observable change can break someone. Hickey says not to break at all and to rename instead. PyPA notes that most projects bump loosely (NumPy breaks in minor releases), PEP 387 removes features in minor releases after a deprecation period, Abseil treats each LTS as a major version, and RFC 1105 holds that not every breaking change is major. Concept 3 (method of the type, not a free function or static helper): Rust C-METHOD, the Rust book, Swift's 'Prefer methods and properties to free functions', .NET's 'if you do own source code of a type, consider using regular instance methods', and 97 Things #32 and #11 support it. Kotlin prefers extension functions placed with the class. It is contested by C++ Core Guidelines C.4 and Meyers Item 23 (make a function a member only if it needs the representation), by Guido's len(x) rationale and by Julia's multiple dispatch (operations that belong to several types equally); this supports the rule's 'clearly associated' condition. Not opened: Clean Code G14/G18, Refactoring's Feature Envy, Larman's Information Expert, Evans' Services, Meyers, Bloch and SWEBOK V4 §4.1 are recorded as marked paraphrases. The Kubernetes deprecation policy, the Kotlin backward-compatibility guide and the Haskell PVP spec answered 404 at every raw path tried, and the aposd-vs-clean-code discussion has nothing on any of the three concepts.

## Reception layer

Concept 1 (no new use of a deprecated element) has broad support. A SEI CERT rule (MET02-J, 'Never use deprecated ... in new code') and tool rules in every major language back it: staticcheck SA1019, rustc's deprecated lint, javac, Sonar S1874/S5738, typescript-eslint no-deprecated and Linux checkpatch. The C# and C++ standards back it too. The disputes are about mechanism and scope, not the rule. Software Engineering at Google ch. 15 and the Linux kernel argue that build-wide deprecation warnings cause alert fatigue, so the check belongs on newly changed lines or patches. Tools also disagree on whether the defining package, its tests and deprecated callers are exempt: staticcheck and javac exempt them, PEP 702 does not. Python type checkers, detekt and typescript-eslint ship the check off by default or only in their strict configuration. Concept 2 (major bump on a breaking release) is checked mechanically by gorelease, cargo-semver-checks, Eclipse PDE API Tools, japicmp, Elm and semantic-release, and the Rust project's accepted 2026 goal moves the check into cargo publish. It is openly contested: Hickey's Spec-ulation, SEG ch. 21, CalVer, the PyPA versioning guide, Rust RFC 1105 ('not all breaking changes are major'), Stufft, ZeroVer and Ashkenas's 'romantic versioning' all dispute it, and npm and Cargo treat 0.x minor bumps as breaking, against SemVer item 4. Concept 3 (an operation with a clear receiver is a method) is stated by the Rust API Guidelines, Swift and .NET and nudged by PMD DataClass, IntelliJ and JDeodorant. It is contested by C++ Core Guidelines C.4 (member only if it needs the representation), Kotlin's 'use extension functions liberally', Julia's multiple dispatch and Python's len() rationale. Every no-self-use rule (Sonar S2325, Pylint/Ruff PLR6301, ESLint class-methods-use-this, clippy unused_self) marks the boundary: an operation that does not use the receiver is not 'clearly associated' with it. I could not open: practitioner threads (WebSearch budget exhausted, HN and Lobsters denied), the Hynek, Cannon and Gábor blog posts and the Ashkenas gist, the Cargo SemVer reference and Haskell PVP spec paths (404), the Sonar way Java profile, and Meyers 2000 and Stylos and Myers 2008 (recorded unfetched).

## Evidence layer

The evidence layer opened 55 sources from GitHub raw and pkg-style mirrors and ran three local hands-on checks for the three gap concepts. (1) No new use of a deprecated element: the compiler, type-checker and linter documentation of all five corpus languages states the check. The sources are typescript-eslint no-deprecated, staticcheck SA1019, Sonar S1874, java.lang.Deprecated and the javac man page, PEP 702, the Rust reference's deprecated attribute, Kotlin @Deprecated and the Go wiki. SEI CERT MET02-J states it as a standard ("Never use deprecated fields, methods, or classes in new code"). The sources disagree on the precondition. java.lang.Deprecated and SA1019 exempt uses inside deprecated code, and SA1019 also exempts the defining package. PEP 702 asks for diagnostics in the defining module too, and a local rustc run warned inside a #[deprecated] function and in the same module. The checks are opt-in in pyright, mypy and typescript-eslint (strict), and the Linux kernel switched its __deprecated warnings off. ## Spine — candidate rules in source order

1. **A change adds no new call, reference, import, subclass or override of an element marked deprecated in code that is not itself deprecated and lies outside the package that defines the element** — A line a change adds does not call, reference, import, subclass, implement or override an element marked deprecated, whether by the language's marker (@Deprecated, #[deprecated], [[deprecated]], Obsolete, warnings.deprecated, a JSDoc @deprecated tag) or by a 'Deprecated:' paragraph in its doc comment. The rule holds where the added code is not itself deprecated and lies outside the package or module that defines the element. The fix is the replacement the notice names. A suppression written on the new use (a deprecation-suppression annotation, an allow attribute, a lint-disable, nolint or type-ignore comment, a warning pragma or a warnings filter) leaves the use in place and so does not exempt it. Several cases are outside the rule because the sources split on them or the element carries no marker. Code that is itself deprecated, the defining package and the element's own tests are exempt by java.lang.Deprecated and staticcheck SA1019, while PEP 702 asks type checkers to flag uses in the defining module and rustc warns inside deprecated code. Also outside: an element deprecated only in a later version than the one the project targets (SA1019); a soft or documentation-only deprecation with no marker (PEP 387, Node.js); an obsolete element with no marker (CERT MET02-J); a revoked deprecation; and a portion of the project that the project context declares will stay on the deprecated API (typescript-eslint 'When Not To Use It'; PEP 702 on application developers who target one version). A use of an element marked for removal is the more urgent case (Sonar S5738 rates it Major against Minor for S1874). The rule judges the use whether or not a check is configured: javac prints only a per-file summary by default, pyright, mypy and typescript-eslint ship the check opt-in, and Python hides run-time DeprecationWarning in imported modules. Migrating existing uses belongs to large-scale-changes-and-migrations. An analyzer configured to reject an old path during a migration is CHG-32's case, and a new diagnostic from a configured check is TOOL-13's. API-27's Limits defer new uses of a marked element to this rule.

2. **A version bump of a package that declares semantic versioning and is at 1.0.0 or later raises the major number whenever the changes it releases break the declared public API, and a Go module from v2 on takes the matching /vN module path** — The rule holds in a project that declares semantic versioning, or whose package manager assumes it (Go modules, Cargo), and whose version is 1.0.0 or later. In such a project, a version bump that releases a backward-incompatible change to the declared public API raises the major version and resets minor and patch to zero. Such a change is one of those API-20 to API-25 name: a structural break, or a break of documented behaviour (the Go reference counts the 'public interface or documented functionality'), or a change the ecosystem's published policy classes as major. In Go the major version lives in the module path: a breaking change to a module released at v1 or later goes into a module whose go.mod path carries the next /vN suffix, with every import inside the module updated. On a diff the check reads the version-bearing lines: a manifest version field, a changeset's bump type, a changelog release heading, or the Go module path of a module that already has a v1-or-later release. A diff that breaks the API but sets no version is judged where the version is set. Several cases are outside the rule. Versions below 1.0.0 are exempt (SemVer item 4; Go treats v0 as unstable and gorelease does not fail on it), though Cargo and npm read the left-most non-zero component as the compatibility boundary. A project that publishes a different policy (CPython's PEP 387, NumPy's loose semantic versioning, calendar versioning) follows that policy. A change that the ecosystem's policy classes as minor although it can break some client is exempt (Rust RFC 1105; Cargo's possibly-breaking category). A break already released in a minor version is answered by a patch release that restores compatibility, never by editing the released version. Before a release, the preferred fix is the compatible form (API-22, API-23), and the major bump is the remedy when the break is needed. API-diff tools (gorelease, cargo-semver-checks, japicmp, Elm) detect structural breaks only, so a behavioural break rests on the author's judgment. At a service boundary, AIP-180/185 and Kubernetes put the same rule in the API's versioned path, where API-22 judges the in-place change. Marking the break in the release notes is DOC-22's rule.

3. **An operation whose one obvious receiver is a type with behaviour of its own that the codebase defines is a method of that type, not a free function or a static method of a helper or utility class** — Take a free function, or a static method of a helper or utility class, whose one obvious receiver is a value of a type the codebase defines and that has behaviour of its own, and which acts on that value using nothing beyond it and its other arguments. Such an operation is declared as a method of that type, so that it is found by asking what can be done with a value of the type. 'Clearly associated' is the guidelines' own condition and is read through their exceptions. Outside the rule are an operation with no obvious self (min(x, y, z)), an unconstrained generic (print(x)), established domain notation (sin(x)), an operation that relates several types equally (x + y), and a function that never uses the value. A conversion lives with the more specific of the types involved. The type must be one whose declaration can hold the method: a class, struct, enum or named type in the same crate or package (Rust, Go), not an interface, a type alias or a foreign type. An operation whose method form would make the type depend on a type or layer it must not depend on (.NET's String.ToUri) also stays outside. Where the language's own guidelines place such an operation beside the type rather than in it, that form satisfies the rule: C++ Core Guidelines C.4/C.5 make it a non-member in the class's namespace when it needs no direct access to the representation, and Kotlin's conventions make it an extension function in the class's file. A passive data carrier with public state and no invariant is outside the rule, because the sources split on it as CHG-06 records. Other cards own neighbouring cases: outside code that reads a type's fields, decides and writes back into a type with an invariant is DSN-29's case, a method of another class that calls one class's methods three or more times is CHG-06's, and a static-only namespace class of stateless helpers with no receiver is DSN-05's.
