# A boundary rule a change adds to a dependency or visibility checker fails the build on a violation, and the build's own visibility check stays on in submitted configuration

## Thesis
A rule that a change adds to, or edits in, a checker of component boundaries — a forbidden or allowed dependency, an architecture rule asserted in a test, a package's dependency enforcement, a target's visibility — is set at the level at which a violation fails the run. Where the checker assumes a warning for a rule whose severity is left out, the rule states its severity. The checker's enforcement switches and the build's own visibility check stay on in the configuration that submitted code builds with. Where violations present before the rule block adopting it at the failing level, those violations are recorded in the checker's store of known violations, so that later runs fail only on new violations and the store is worked off rather than added to.

## Rationale
A severity-graded checker stops a build at error severity: its run exits with a non-zero code when it finds a violation at error severity, in the same fashion as linters and test tools, so a violation at info or warn is reported while the run exits zero, and a rule at ignore is not checked at all. An invocation with a warning threshold exits with an error status once the warning count exceeds that threshold, so under a threshold of zero a warning-level violation fails the run as well. One such checker assumes warn for a rule whose severity is left out and for a dependency outside its allowed list, so a rule written without a severity does not stop the build. A package-level checker enforces a package's dependencies only once the package's configuration switches enforcement on. A build's visibility check is switched off by a flag that disables target visibility enforcement; the build's documentation offers that flag for prototyping and advises against it in submitted code. In a test-based checker the failure is the thrown assertion: checking a rule throws an assertion error on a violation, while evaluating it returns the violations as a result for the caller to handle. When a rule is introduced into a grown code base there are often hundreds or even thousands of violations, too many to fix immediately. Recording them in a store of known violations keeps the rule checking: later runs report only new violations, and the store can shrink automatically as known violations are fixed. Such a store is worked off over time rather than added to, and a strict or shrink-only mode refuses new entries. A boundary check runs in the CI pipeline to keep the package system valid at each version of the application. A rule is typically set at the failing level to enforce compliance with it during continuous integration testing, pre-commit checks and pull request merging, because that level makes the run exit with a non-zero code.

## Example
```java
bad:  EvaluationResult result = LAYERS.evaluate(classes);
      if (result.hasViolation()) {
          log.warning(result.getFailureReport().toString());
      }
      try { LAYERS.check(classes); }
      catch (AssertionError e) { log.warning(e.getMessage()); }
good: FreezingArchRule.freeze(LAYERS).check(classes);
```

## Limits
A build's visibility check may be switched off for prototyping, in an invocation outside the configuration that submitted code builds with. The level that skips a rule is documented for disabling a rule inherited from an extended rule set; such a disable stays outside the check where the inherited rule guards no boundary the project declares. The same level is documented for disabling a rule temporarily; for a boundary rule held back by existing violations, the store of known violations sets those violations aside while new ones still fail. A warning level is also documented for introducing a rule that will later be set to error; for a boundary rule a store of known violations carries that introduction while new violations still fail, so a warning level on a rule the change introduces stays outside the check only where the checker offers no store of known violations. A warning level is also documented for a rule whose violations are reported while compliance is not enforced, typically one that flags something other than a potential build-time or run-time error. A forbidden dependency that compiles and runs is of that kind, yet the build's documentation keeps target visibility enforced in submitted code and the package checker's documentation recommends running its check in the CI pipeline to keep the package system valid at each version; a boundary rule a change adds declares a boundary whose compliance is enforced, so that use does not take a boundary rule out of the check. A warning level is also documented for a rule that cannot determine with certainty that a problem has been found, one whose possible false positives need manual review; where the checker's own documentation states that a boundary rule may report false positives, a warning level on that rule stays outside the check. The store of known violations is for violations present before the rule: it is updated to record existing violations and to remove those worked off, and recording a violation to resolve it is the very last resort; an entry that the change adds to admit its own new violation is judged as a new dependency, outside this check. A rule already below the failing level that the change leaves untouched is outside the hunk.

## Validator
Grep the hunk for a boundary rule whose severity or level is warn, info, ignore, off or a numeric level below error; for a boundary rule entry added without a severity in a checker whose default is warn; for a visibility or package-enforcement switch set to false; and for an architecture rule that is evaluated and logged, or whose assertion error is caught, instead of checked. Open the hunk around each hit and confirm that the change adds or edits that rule or switch, that it guards a dependency, layer, package or visibility boundary, and, for a warning level on a rule the change introduces, that the checker offers a store of known violations, and, for any warning level, that the checker's documentation does not state that the rule may report false positives. Trace where a disabling flag lives: a checked-in build settings file, a CI configuration or committed build options count as configuration that submitted code builds with; a documented local prototyping command does not. Where the hunk itself invokes the checker so that any warning fails the run, as a warning threshold of zero does, a warning level fails the run and is no hit. Validator question: **Does the change add or edit a boundary rule below the level at which a violation fails the run, or switch a boundary check off in configuration that submitted code builds with?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-13`, severity minor, `file`, `symbol`, `code` = the rule entry, severity value, switch or flag line quoted verbatim from the diff, `fix` = the same rule at the failing level or the switch turned on, with violations present before the rule moved into the checker's store of known violations, in the file's language, `rationale` = names that a violation at this level, or with this switch off, passes the build; for a warning level it adds the exception of an invocation that fails the run on any warning).
