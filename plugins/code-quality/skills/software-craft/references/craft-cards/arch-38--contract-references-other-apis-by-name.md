# A service's contract refers to a resource that another API owns by its resource name or identifier, imports from outside itself only generic or organisation-wide common types, and, where published as a single document, references another file only if that file's content is durable and immutable

## Thesis
A service's contract refers to a resource that another API owns by that resource's name, the unique identifier users reference it by, rather than by that API's message or schema type. From outside itself the contract imports only common components intended for use by many APIs: generic global types such as a timestamp or a postal address, which any API may use, and an organisation's common package, which only that organisation's APIs use. A contract published as a single specification document is self-contained: it references a fragment in another file only where that file's content is held durable and immutable. The files of one interface-definition package define one API at one version, and their imports of each other stay inside the contract.

## Rationale
A contract that depends on the message types of another API introduces uncertainty in the behaviour its customers expect and in the dependency management of its client libraries: any change to the other API can cause problems. When a field is added to the other API's message, it is open whether this API's customers see it and how soon. When the other API's major version is deprecated, it is open whether this API has to move to the successor and whether that move requires a new major version of this API too. It is also open how client library versioning reflects changes to the API depended on. A resource message used as a field's type couples the two resources in every respect: a change to the schema, permissions or other requirements of either resource affects the other and makes roll-outs significantly more complex. A reference by name keeps the owning service involved in resolving the reference and isolates the logical concerns of each resource. Keeping APIs isolated from each other, with a limited set of common components maintained in a highly disciplined way, reduces many of these dependency issues. A common package admits new messages and enums, removes no existing field or enum value, and avoids adding fields to existing messages, adding values to existing enums, or changing the meaning of existing values. Where a single representation is safe to share, a common component lets a message from one API's response serve in another API's request without copying. A reference from a single specification document to a fragment in another file points at content that in general is neither durable nor immutable, so the semantics of the API may change in unexpected ways.

## Example
```python
bad:  ORDER_PROTO = """
      import "customers/v1/customer.proto";
      message Order { customers.v1.Customer customer = 1; }"""
      ORDER = {"properties": {"customer": {
          "$ref": "../customers/openapi.yaml#/components/schemas/Customer"}}}
good: ORDER_PROTO = """
      import "google/protobuf/timestamp.proto";
      message Order { string customer = 1; google.protobuf.Timestamp placed_at = 2; }"""
      ORDER = {"properties": {"customer": {"type": "string", "pattern": "^customers/[^/]+$"},
                              "placed_at": {"type": "string", "format": "date-time"}}}
```

## Limits
Generic global types such as a duration, a timestamp, a date, money or a postal address may be imported by any API; an organisation-specific common package may be imported by the APIs of that organisation and by no API outside it. An import used only internally, for example to apply visibility labels or to give instructions to internal infrastructure, is acceptable provided that the public components carry no such reference. Where the resource name cannot be used and the resource's ID alone is strictly necessary, the field carries that ID. A package one API shares between its own major versions is not a common component: when two versions use effectively the same API-specific type, each version carries its own copy. An import between the files of one interface-definition package stays inside the contract, as those files define one API in one package that carries one version. In a specification document published on its own, a remote reference to a common component, or to this API's own definitions at the same major version, is admitted where its owner guarantees durable and immutable content, as with an immutable specification revision published through an internal API repository or a reusable fragment a guideline publishes for that purpose; an immutable revision admits no type that another API owns. How one API versions and deprecates its own surface lies outside this rule.

## Validator
Grep the hunk for an import of an interface-definition file and for a `$ref` whose target lies in another file, by relative path or by URL. Open the contract file and, for each imported file or referenced fragment, establish its owner: this API at the same major version, this API at another major version, a global package of generic types, an organisation-specific common package, or another API. For a type owned by another API, check whether a public field embeds it where that resource's name, or its ID where the name cannot serve, would carry the reference. For a type owned by another major version of this API, check whether a public field embeds it where this version's own copy of the type would serve. For an organisation-specific package, check whether this API belongs to that organisation. For an import of a package that is neither this API's own nor a common component, check whether only internal annotations use it and the public components carry no reference to it. For a reference from a specification document published on its own to another file, check whether the target is an immutable published revision or a mutable location such as a branch path or a sibling file. Validator question: **Does the contract's public surface embed a type owned by another API or by another major version of this API, use an organisation's common package from outside that organisation, or, where the contract is a specification document published on its own, reference a fragment in another file whose content is not held durable and immutable?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-38`, severity minor, `file`, `symbol`, `code` = the import line or `$ref` line and the field that uses it, verbatim from the diff, `fix` = in the file's language, the field carrying the other API's resource name or identifier as a string where the embedded type belongs to another API, a copy of the type in this version's own package where it belongs to another major version of this API, a common-component type where a common component carries the concept, or, for a fragment that belongs to this API or to a common component, that fragment inlined or referenced at an immutable published revision, `rationale` = names the API or location that owns the embedded type and the change or deprecation the contract would inherit from it).

- Google API Improvement Proposals, AIP-185 "API Versioning", § Guidance (fetched): "A new major version of an API **must not** depend on a previous major version of the same API." / "An API surface **must not** depend on other APIs, except for in the cases outlined in [AIP-213][] and [AIP-215][]."
- Google API Improvement Proposals, AIP-122 "Resource names", opening, § Fields representing another resource and § Disallow embedding of resources (fetched): "each resource has a unique identifier that users use to reference that resource" / "If using the resource name is not possible and using the ID component alone is strictly necessary, the field **should** use an `_id` suffix" / "Tightly couples resources in all aspects: Changing the requirements in the schema, permissions, or otherwise for either resource impacts the other, significantly increasing complexity of roll outs."
- Google API Improvement Proposals, AIP-191 "File and directory structure", § Single package and § File names (fetched): "APIs defined in protocol buffers **must** define each individual API in a single package, which **must** end in a version component." / "It is often useful to divide API definitions into multiple files."
- Zalando RESTful API and Event Guidelines, rule #234 "only use durable and immutable remote references" (fetched): "Normally, API specification files must be *self-contained* [...] the content referred to is _in general_ *not durable* and *not immutable*. As a consequence, the semantic of an API may change in unexpected ways."
- Caveat: the proposals are written for resource-oriented APIs defined largely in protocol buffers and the guideline for OpenAPI specification files; the card carries the proposals' claims to any contract at a service boundary and the guideline's self-containment claim to any contract published as a single specification document; one interface-definition package may span several files, which the file-structure proposal admits.
