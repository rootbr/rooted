# A declaration in an inner scope shadows no outer variable, package or built-in that code in that scope, or after it within the same routine, still needs

## Thesis
A declaration in an inner scope that reuses a name bound in an enclosing scope (a variable, a field, a parameter, an imported package or a built-in) takes a name of its own whenever code in that scope, or after it within the same routine, still needs the outer entity; where the code means to set or update the outer variable itself, the declaration is dropped and the code assigns to the outer variable. The outer entity is still needed when code after the end of the inner scope, within the same routine, reads the name, which there refers to the original again, or when code inside the inner scope was meant to reach the outer entity: a field it should update, a package or built-in it calls. A rebinding that computes its value from the outer one and replaces it, with no code after the declaration needing the original, conforms.

## Rationale
A declaration in an inner scope takes every use of the name to itself until the scope ends; when the scope is over, the shadowing ends and the name refers to the outer entity again. Code after the block that was meant to see the new value reads the original: a deadline capped inside a conditional block is lost after it, and an error declared afresh inside a loop shadows the routine's error variable, so the routine returns the wrong value. Such code compiles; even a compiler that rejects an unused variable accepts it once the inner variable is used inside the block. Inside the scope the reverse holds: code meant for a field can reach the local instead, the wrong variable, leading to hard-to-detect bugs; a variable named after a package renders the package's free functions and values inaccessible; a reader may mistake a variable for the built-in it hides, and a call meant for that built-in reaches the variable. Reusing a built-in name either shadows the original within the scope or makes the code confusing; in the best case the compiler complains, and in the worst case such code may introduce latent, hard-to-grep bugs. If the inner variable is later removed or renamed, behaviour might change unexpectedly, because the outer variable is then the one in use. A name of its own keeps one name referring to one variable across the scope and keeps the active binding easy to track, which shadowing can hurt, especially in large code bases.

## Example
```java
bad:  int total;
      void add(int[] values) {
          int total = 0;
          for (int v : values) total += v;
      }
good: int total;
      void add(int[] values) {
          for (int v : values) total += v;
      }
```

## Limits
Whether every shadow is a defect is contested. Blanket checks flag a declaration whenever it hides a variable, name or field of an enclosing scope, because the same name can refer to different variables in different parts of the scope and the outer variable becomes inaccessible. Opposing guidance holds that shadowing a binding with a closely related one is idiomatic, a way to perform a few transformations on a value and keep the variable immutable afterwards, and further guidance says shadowing should usually be avoided while some scenarios may make it fitting. Several shadow checks are off by default: one blanket check is absent from its linter's recommended configuration, the rebinding lints sit in an allow-by-default restriction group, and one variable-shadow analyzer generates too many false positives and is not enabled by default. The separating condition is whether the outer entity is still needed after the declaration: that analyzer reports a shadow only where the outer variable is mentioned after the inner one is declared, because a shadow whose original is not used afterwards is inconsequential, and a package needs no rename unless it still needs to be used while the variable is in scope. The same analyzer also skips a shadow whose type differs, since a different type implies the programmer really wants two different things; the card applies the still-needed condition whatever the types. Outside the rule therefore: a rebinding computed from the outer value that replaces it; a variable named after a standard package within a very small scope that never uses the package; a built-in name reused where the scope never needs the built-in, which built-in checks flag for the confusion and the variable-shadow analyzer calls fine; and an unrelated rebinding whose outer entity nothing needs afterwards, which an opt-in lint flags as possibly a mistake and the analyzer calls inconsequential. Where the project context adopts a blanket, built-in or unrelated-shadow check, such a declaration is held to that check. Also outside: a test parameter named after a fixture function of the same module, the default form of a test framework that injects fixtures by parameter name, which the outer-name check's own documentation calls a common issue and resolves by naming the fixture explicitly or with a plugin; a constructor or setter parameter named after the field it assigns, since the local-variable field-shadow rule does not flag parameters and the field-hiding check that does offers options to ignore constructor and setter parameters; a built-in name on a project's documented ignore list.

## Validator
Take each added declaration the triggers matched: a short declaration, a keyword-introduced binding, a typed local or a plain name binding in a routine body, and a variable or parameter named after a built-in or an environment global. Open the file and find whether the same name is already bound in an enclosing scope: a field of the enclosing type, a parameter, a local of an enclosing block or routine, a module-level variable, an imported package, a built-in of the language, or a global of its runtime environment. Where it is, trace the name from the declaration to the end of the enclosing routine. After the inner scope ends, check whether the name is read again; note whether that read was meant to see the value the inner declaration computed, such as a capped deadline, an error or a result, which makes it a wrong-value bug. Inside the scope, check whether the code calls the shadowed package or built-in through the name, or writes the inner binding and never reads its final value while the outer variable is what the routine exists to update. Check each case the Limits leave out before flagging. Validator question: **Does an added declaration reuse the name of a variable, field, parameter, imported package or built-in from an enclosing scope while code in that scope, or after it within the same routine, still needs the outer entity?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-23`, severity minor, `file`, `symbol`, `code` = the added shadowing declaration quoted verbatim from the diff, `fix` = the declaration given a name of its own, or, where the code means to set or update the outer variable, the declaration dropped so that the code assigns to the outer variable, in the file's language, `rationale` = the outer entity the declaration shadows and the use in or after the scope that still needs it).
