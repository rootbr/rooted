# Adding a member without a default implementation to a published interface or trait that outside code may implement breaks every existing implementation

## Thesis
Once a library has released an interface, trait, abstract base type or other object type that code outside its module may implement, every member added to that type gets a default implementation that existing implementations inherit, so that they need not supply it. Where the language offers no default, or where outside code may satisfy the type by its shape alone without inheriting from it, the member goes on a separate new interface, either one that extends the old one or one that holds the new member alone, and the code that wants the member checks at run time whether the supplied value implements it. A type meant to be implemented only inside its module is closed to outside implementation in its first release. It can be closed by the language's sealing mechanism, by a member or a supertype that outside code cannot name, by returning in place of an interface a concrete type that outside code can neither implement nor match by its shape, or by documentation stating that it is not for outside implementation. Members can then be added to it without a breaking release.

## Rationale
An implementation written against the old type does not implement the new member, so once the member is added it no longer satisfies the type. Where it is used as the type, it stops compiling or type-checking. Where abstract members are checked when an object is created, it can no longer be instantiated. The set of outside implementations is open-ended and unknown to the module, so the only safe assumption is that the change makes some of them fail: adding a member with no default is a major change. With a default in place, existing implementations that inherit from the type are unaffected; one that satisfies the type by its shape alone inherits no default and still lacks the member. A member that carries a body but is still marked abstract is not a default, because every implementation must still override it. A separate interface leaves the old type unchanged. A value of an interface that extends the old one can still be passed wherever the old type is expected, and the run-time check gives the new behaviour only to values that provide it. That works only while the old type without the new member can still be supported, which limits how far the module can extend later. A closed type is implemented only inside its module, or outside it only by embedding one of the module's own implementations, and the embedding type keeps satisfying the type when a member is added. When the module alone implements a type, the type's changes come with the module's own releases, and the module can update its implementations to match. Closing a type that was released open is itself a major change, because outside code that implemented it can no longer do so. Closing frees additions only: removing a public member or changing its signature still breaks callers. A type closed by a language mechanism leaves callers no safe way to build their own test doubles of it, short of embedding the type where the language allows that, so the module can ship test helpers or doubles kept in step with the type. A type closed by documentation alone still lets callers write doubles, which they update when the type changes.

## Example
```go
bad:  type Store interface {
          Get(key string) ([]byte, error)
          Delete(key string) error // added in a minor release
      }
good: type Store interface{ Get(key string) ([]byte, error) }
      type Deleter interface{ Delete(key string) error }
      func Remove(s Store, key string) error {
          if d, ok := s.(Deleter); ok { return d.Delete(key) }
          return errors.ErrUnsupported
      }
```

## Limits
The rule does not reach a type that outside code cannot implement: a non-exported or internal type, or one whose documentation marks it private. Such a type changes together with its implementations. A release that declares the break with a new major version or a new module path is outside the rule. So is a version below 1.0.0, where anything may change at any time, except where the ecosystem's default version ranges accept every release that keeps the left-most non-zero component: there a bump of that component (0.5.2 to 0.6.0) declares the break, and a break without it is in the rule. A member that implementations need not supply is outside the rule. A default does not remove every hazard. A member added with a default, or added to a closed type, can still collide with a member of the same name that an outside type already has, its own or one inherited from another interface it implements. The call then becomes ambiguous, or the outside type fails at run time and fails to compile when rebuilt, or its existing method stands in for the new one without meeting the new contract. Such an addition is often treated as non-breaking where a name clash is unlikely. Where a clash in outside code is likely, a different name is advisable. Some type systems list further cases where adding even a defaulted member is a major change, such as a member that stops the type from being usable through dynamic dispatch. A project context that declares the type closed to outside implementation, or the release a major one, rejects the finding.

## Validator
Grep the hunk for an added member line inside an interface, trait, protocol, abstract base type or other object type that outside code may implement: a method signature with no body, a required property, an abstract-marked method, a stub method, or any non-optional member of a type that outside code may satisfy by its shape alone. Open the base version with `git show <base_sha>:<path>` and confirm that the type existed there without the member; a type new in the diff is outside the rule. Decide whether the member is required. It is required when it is not optional and has no default body that every implementation inherits; on a type that outside code may satisfy by its shape alone, an implementation that matches it by shape inherits no body, so every member that is not optional is required. A member marked abstract counts as required even when it carries a body. Decide whether outside code may implement the type. It qualifies when it is exported or public in a library that other code depends on and it was open at base. Open means not sealed by the language, carrying no member or supertype that outside code cannot name, not a concrete type that outside code can neither implement nor match by its shape, and not documented as private or as not for outside implementation. Read the type's doc-comment and the project context to decide. A type that was open at base and is closed in this diff counts as open. Check the diff and the manifest for a major-version bump or a new module path, and the released version for one below 1.0.0. A version below 1.0.0 is left without a compatibility promise unless the ecosystem's default version ranges accept every release that keeps its left-most non-zero component; there only a bump of that component counts as the major-version bump. Validator question: **Does the diff add a required member to a type that existed at base, is exported from a library and was open to implementation outside its module, with no major-version bump or new module path in the change and no released version below 1.0.0 that the ecosystem leaves without a compatibility promise?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-24`, severity major, `file`, `symbol`, `code` = the added member line quoted verbatim from the diff, `fix` = in the file's language, the member given a default implementation where implementations inherit from the type, or else moved to a new interface that the code needing it checks for at run time, `rationale` = names the type and the member and states that every implementation outside the module that inherits no default for the member lacks it and stops satisfying the type).
