# A design decision such as a data format, an encoding, a record layout or an identifier scheme is encoded in only one module, and other modules reach it through that module's interface

## Thesis
Each decision a project makes about its own data — a file or wire format, an encoding, a byte layout or a delimiter, the names and meaning of a record's fields, an identifier scheme — is encoded in one module, and every other module that reads, writes or relies on it does so by calling that module's operations. Added code that parses or builds what another module already parses or builds, that repeats that module's delimiter, field positions, key names, byte offsets or identifier pattern, or that reads what another module writes by knowing the layout itself, reaches the decision through the owning module instead; where no module owns the decision yet, the shared knowledge moves into one module that both sides call. The same holds when code is split by the order of its steps, such as reading, changing and writing a file, and each step knows the format.

## Rationale
A module's secrets are assumptions about its implementation that other modules are not allowed to make: they are the things that can change, while its interface defines the things that cannot change without simultaneous changes to the implementation and its clients. A second module that encodes the decision makes that assumption, so the decision can no longer change without simultaneous changes to both modules; and where neither module depends on the other in the code, the two change in tandem with no apparent structural dependency between them. A system is easier to program and to modify when its parts make fewer assumptions about each other. When each major step of the processing is a module, the format of the stored data is used by every step and a change to it changes every module; when each module hides one design decision from all others, knowledge of how the data is stored stays in one module and a change to it can be confined there. Groups of modules that change in tandem with no apparent structural dependency are one of six architecture anti-patterns detected from structural relationships and revision history in 19 large-scale software projects: files involved in these anti-patterns are more error-prone and change-prone, the more anti-patterns a file is involved in the more error-prone and change-prone it is, and every one of the six contributes, with an unstable interface (a widely used interface that changes frequently) and a crossing (a file with both high fan-in and high fan-out) contributing the most by far. The measure is per file and pooled over the six anti-patterns, an association rather than the measured cost of one leaked decision.

## Example
```python
bad:  # module a writes the record
      out.write(f"{rec.id}|{rec.name}|{rec.email}\n")
      # module b reads it back
      email = line.split("|")[2]
good: # module records, the one place that knows the layout
      def dump(rec): return f"{rec.id}|{rec.name}|{rec.email}\n"
      def email_of(line): return line.rstrip("\n").split("|")[2]
      out.write(records.dump(rec))  # module a
      email = records.email_of(line)  # module b
```

## Limits
A standard format handled through a common library is no module's secret: the standard fixes it, as an interface fixes the things that cannot change, so two modules that both read it share an interface rather than an assumption; what stays secret is the project's own decision about its data — which fields a record carries, under which names, in which order and with what meaning, and how its identifiers are built. A decision the owning module states in its published interface, such as a documented file format that other programs read, belongs to what that interface defines as unable to change without changing the module and its clients together, so code that relies on it as documented makes an allowed assumption rather than a hidden one; the decision is then part of that interface, and a widely used interface that changes frequently is one of the two anti-patterns that contribute most to error- and change-proneness. One part may deliberately assume more about another — that a set is kept sorted, so a membership test takes log n steps rather than n — because additional assumptions often allow less work to be done, sometimes a lot less; the trade suits algorithms and the tuning of small modules, while in a large system the ability to improve each part separately is usually more important, and a project context that records such a trade for a named pair of modules rejects the finding for that pair. Hiding the decision makes the system easier to program and modify, not necessarily easier to design: a good interface is hard to design, and hiding pulls against the desire not to hide power. The check concerns one decision encoded in two modules; which members a module exposes, how wide or deep its interface is, how many dependencies it has and which way they point, and objects shared mutably between modules are separate questions.

## Validator
In the hunk's added lines, find each place that builds, parses or relies on a decision about the project's data: a delimiter passed to a split or join, a byte layout read or written field by field, a format, pattern or date-layout string, a field or key name used as a literal subscript, an identifier assembled from a literal prefix, a serializer or parser call whose result the code then reads field by field. Name the decision each place encodes: the delimiter and the field positions, the byte offsets and widths, the key names, the identifier pattern, or the format of data that another module writes or reads. Search the repository for another module — a file, type or package other than the one holding the added code — that encodes the same decision: the same delimiter with the same field positions, the same key literals, the same prefix or pattern string, the same offsets, or the code that writes what the added code parses or parses what it writes; follow the data from the added code through its callers to that module. Pass the place when it calls an operation of the module that owns the decision, when the other encoding lives in the same module as the added code, when the only shared part is a standard format handled by a common library, when it relies on a decision the owning module documents in its published interface, and when a project context records the trade for that pair of modules. Validator question: **Does added code encode a decision about the project's data — a format, an encoding, a byte layout or delimiter, record key names or an identifier scheme — that another module also encodes, instead of reaching it through the one module that owns it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-28`, severity major, `file`, `symbol`, `code` = the added line that encodes the decision, quoted verbatim from the diff, `fix` = the added code rewritten in the file's language to call the owning module's operation — or, where no module owns the decision yet, the one module that both sides then call, with its operation and the two call sites, `rationale` = the decision, the other module that also encodes it with its path and symbol, and the change that would have to land in both).
