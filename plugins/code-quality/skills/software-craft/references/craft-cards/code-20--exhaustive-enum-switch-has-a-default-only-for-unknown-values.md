# A switch whose cases cover every member of an exhaustiveness-checked enumerated type has no catch-all default, unless an unknown value can reach it, where the default handles that value without silencing the check

## Thesis
A switch or match over an enumerated type whose exhaustiveness a compiler or a checker the project runs verifies, and whose cases already handle every member with none of them falling through into the default, has no catch-all default or wildcard branch that the check counts toward exhaustiveness wherever a value outside the members the code was compiled or type-checked against is very unlikely to reach it at run time, as in an application whose build accurately tracks changes to its dependencies. Where such an unknown value can reach it (code shipped as a library that switches on an enumeration defined in another library that can be upgraded beneath it without this switch's exhaustiveness being checked again, a client switching on a value that a server running a newer version may send and that its decoding passes on unchecked, an enumeration its defining package declares open to added members, used outside that package), the switch keeps a default that handles the unknown value, either reporting it as an error that names the value or taking an action that a comment beside it explains. That default is one the check does not count: it carries the marker comment the checker honours, asserts that the value has the empty type, or sits under a checker that does not count a default toward exhaustiveness, so the check still reports any known member left without its own case.

## Rationale
On a switch whose cases handle every member and none falls through into it, a default is redundant, a form of dead code. Its cost arrives when a member is added to the enumeration. With no default, the check reports the switch and its author either handles the new member explicitly or restores the default; with a default the check counts toward exhaustiveness, the report never comes and the new member is silently caught up in the default. The check sees the members present when the code was compiled or type-checked, and the run time can differ. Where adding a member does not force dependent code to be recompiled, code built against one version of an enumeration from another library can run with a newer version that adds a member, and a server running newer software can send a value the client's older types do not name; with no default, execution simply falls out of a switch that was thought to be exhaustive, unless the language itself raises on a value no case matches. A defensive default covers that value at run time, and one the check does not count keeps both the run-time safety for unknown values and the enforcement that every known member is handled. An assertion that the value has the empty type does both at once: a type checker reports it once it is reachable, which a member without a case makes it, and at run time it raises when called. Where run-time checking against unexpected values is not needed, the check alone suffices and the switch needs no default.

## Example
```typescript
bad:  switch (state) {
        case "open": return 1;
        case "closed": return 2;
        default: return 0;
      }
good: switch (state) {
        case "open": return 1;
        case "closed": return 2;
      }
```

## Limits
The rule is contested, and whether a value outside the members the switch was compiled or type-checked against can reach it at run time separates the cases. One side removes a default from a switch that handles every member, so that the check keeps reporting members added later, where that skew between compile time and run time is very unlikely, and keeps a defensive default where it is not: in a library switching on another library's enumeration, in a client to which a newer server can send unknown values, and outside the package of an enumeration declared open to added members (the Source entries marked no default). The other side asks for a default in every switch, even when every current member is covered, expressed for example as an assertion, to protect the code against members added later (the entries marked default always). Several rules that ask for a default make an exception for a switch the compiler checks or one that covers every member: one does not validate switches the compiler requires to be exhaustive, one expects no default on an enumeration switch that uses every constant, and one exempts a switch on an enumerated value because the compiler warns about unhandled values, asking only that a default that should never execute be treated as an error. Where no compiler or checker the project runs verifies the switch, nothing reports a member added later; a default that reports the unknown value as an error, or takes an action its comment explains, is then the guard, and the rule asks for no removal. Where the language forces a catch-all on an enumeration declared open to added members and no check the build runs reports the members it covers, the counted default is the only form available and is not flagged, though it still handles the unknown value. Where a project style documented in the project context requires a default in every switch, the switch keeps its default, and the finding asks that the default be one the check does not count, not that it be removed. A default on a switch whose cases leave some members unnamed, and the form of a switch's branches and fallthrough, are judged by their own rules.

## Validator
Grep the added lines for a default label, a wildcard or catch-all binding arm, an assertion that a value has the empty type, a comment mentioning skew, and a switch or match head. For each hit, open the file, find the switch or match and the type of the value it dispatches on, and continue only when that type is an enumerated type (an enumeration, a union of literal or tagged types, a closed set of subtypes, a named type whose constants its package enumerates) and the cases name every member the code can see, none of them falling through into the default. Establish whether a compiler or a checker verifies the switch: a switch or match the compiler requires to be exhaustive, a declared result the compiler reports as missing only when a member is left without a case, or an exhaustiveness check named in the inventory or the project context; with none, stop. Read the default, if any, and decide whether the check counts it toward exhaustiveness: a plain default or wildcard counts; a default carrying the marker comment the checker honours, one that asserts the value has the empty type, or one under a checker configured not to count defaults does not. Then decide whether an unknown value can reach the switch: the code ships as a library and the type comes from another library that can be upgraded beneath it without this switch's exhaustiveness being checked again, the value is decoded from a message, a file or a peer that may run a newer version by a decoding that passes a value outside the members on rather than rejecting it, or the type is declared open to added members and defined outside this package; when none of these holds, a type defined and built in the same application is closed, and so is a type not declared open whose switches the compiler checks for exhaustiveness again whenever the type they are built against changes. On a closed switch, a counted default is the finding. On a switch an unknown value can reach, a missing default where the language lets a value no case matches fall out of the switch silently, a counted default where the language or the check offers an uncounted form, and a default that drops the value without reporting it as an error or explaining its action in a comment are the finding. Validator question: **Does a switch whose cases cover every member of an exhaustiveness-checked enumerated type, none falling through into the default, carry a default the check counts although no unknown value is likely to reach it, or, where an unknown value can reach it, lack a default although a value no case matches would fall out silently, carry a counted one the language or the check could avoid, or carry one that neither reports the value as an error nor explains its action?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-20`, severity minor, `file`, `symbol`, `code` = the default or wildcard line, or for a missing default the switch or match head, verbatim from the diff, `fix` = for a switch no unknown value is likely to reach, the switch with the counted default removed and every member in its own case, a raise naming the value placed after the switch where every case leaves the routine and the language requires a statement there, and the default kept in a form the check does not count where removing it would leave code that does not compile or break a project style documented in the project context that requires a default in every switch; for a switch an unknown value can reach, a default that reports the value as an error naming it or explains its action in a comment, marked or typed so the check still reports a member without its own case, in the file's language, `rationale` = the enumerated type, whether a value outside its members can reach the switch and from where, and which member added later the counted default would hide or which unknown value the missing default would let fall through).
