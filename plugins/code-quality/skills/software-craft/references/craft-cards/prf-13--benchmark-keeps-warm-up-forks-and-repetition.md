# A benchmark keeps a discarded warm-up, separate-process runs and repeated measurement, and hand-timed code discards its first runs and times many runs rather than one

## Thesis
A benchmark whose result is compared or reported keeps a warm-up whose results are discarded, runs in a separate process where its harness forks, and measures more than one result in all: warm-up and fork counts stay above zero, the measured results, counted as values or iterations per process times processes and repetitions, number more than one, and two versions are compared over repeated runs of each rather than over one result per version. Timing code written outside a harness first executes the code without recording those results, then times a batch of many executions and repeats that timed batch, so that more than one timed value results rather than one.

## Rationale
Execution time differs from run to run; in a virtual machine the non-determinism stems from sources such as just-in-time compilation and optimisation driven by timer-based method sampling, thread scheduling, garbage collection and various system effects, and it is inherent, so run-to-run variance is one of the effects every experiment accounts for. Running a benchmark in several separate processes aggregates the results across several launches and allows that variance to be estimated. A runtime that optimises from profiles can mix the profiles of different benchmarks run in one process and render uniformly bad code for every one of them; a separate process per benchmark can help to evade this. The number of processes should be large enough to reduce the effect of random factors such as address-space layout randomisation and a randomised hash function, and the total number of values, processes times values per process, should be large enough to get a uniform distribution. A warm-up executes the routine repeatedly to fill the processor and operating-system caches and, where a just-in-time compiler runs, to give it time to compile the code; this helps keep cold caches and compilation time from throwing off the later measurements, and the warm-up result is ignored. Where each measured value is itself a calibrated batch of executions, 100 ms by default in one harness, skipping the first value is usually enough; sometimes more values are skipped. Benchmarks are often noisy, and a single result may not be representative of the overall behaviour. Harness defaults carry these safeguards: one runs 5 warm-up iterations, 5 measurement iterations and 5 forks; another spawns 20 worker processes that each run once to warm up, with that result ignored, and then measure 3 values; a timing utility repeats the timing 5 times by default, which its documentation calls probably enough in most cases; a comparison tool asks that each benchmark be run at least 10 times, ideally 20, to gather a statistically significant sample. A study of benchmarks in 123 open-source systems lists configuring benchmarks with zero forks among five bad practices, finds each of them prevalent, and finds that these bad practices often significantly impact the benchmark results.

## Example
```java
bad:  @Fork(0) @Warmup(iterations = 0) @Measurement(iterations = 1)
      @Benchmark public int decode() { return codec.decode(payload); }
      long t0 = System.nanoTime(); int n = codec.decode(payload); long ns = System.nanoTime() - t0;
good: @Fork(5) @Warmup(iterations = 5) @Measurement(iterations = 5)
      @Benchmark public int decode() { return codec.decode(payload); }
      int n = 0; for (int i = 0; i < 10_000; i++) n += codec.decode(payload);
      for (int r = 0; r < 5; r++) { long t0 = System.nanoTime(); for (int i = 0; i < 100_000; i++) n += codec.decode(payload);
        System.out.println((System.nanoTime() - t0) / 100_000 + " ns/call, checksum " + n); }
```

## Limits
A benchmark that measures cold performance on purpose, such as start-up, a first call or a cold cache, keeps its first execution in the result: a single-shot mode exists to estimate cold performance without hiding the warm-up invocations, with defaults of zero warm-up iterations, one measurement iteration and 5 separate-process runs, and a cold-cache run clears the caches before each timed run; there the rule drops the warm-up and the batch of many executions and still asks for more than one measured result in all, from separate processes or repeated runs. A run that executes each benchmark for exactly one iteration and one repetition to verify quickly that the benchmark can run successfully, without waiting for full execution, produces no result to compare or report and is outside the rule. Warming up until results seem stable is outside the rule: on some benchmarks performance is never stable, and an arbitrary number of warm-up values may make the benchmark less reliable, since two runs may use a different number of warm-up values; the rule asks for a warm-up whose results are discarded, not for a steady state.

## Validator
Grep the hunk for a fork count of zero, a warm-up iteration count of zero, a measurement iteration count of one, a run, count or repeat value of one, a single-iteration time budget, or a high-resolution clock read. Open the file and confirm the code is a benchmark whose result is compared or reported: a benchmark method or its configuration, a benchmark command line, or hand-written timing whose elapsed value is printed, stored or compared; a clock read that serves logging, a metric or a timeout, a count of one on a command that runs no benchmark, and a run that only checks the benchmark executes are no finding. Check whether the benchmark measures cold performance on purpose, as a single-shot mode, a step that clears caches before each timed run, or a timed first call or start-up does; if so, skip the warm-up and batch checks and check only that separate processes or repeated runs give more than one measured result in all. For a measurement, value or repeat count of one, multiply it by the separate processes and repetitions the configuration runs; more than one measured result in all is no finding. For hand-written timing, trace whether the code runs untimed before the timed section, whether the timed section covers more than one execution, and whether the timed section is repeated so that more than one timed value results. Validator question: **Does a compared or reported benchmark run with no separate process where its harness forks or with a single measured result in all, a timed batch counting as one result, or, when it does not measure cold performance on purpose, run with no discarded warm-up or time one execution per timed batch?** Yes → flag.
