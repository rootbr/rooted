# Research note — Technical debt

Topic `technical-debt` of group F. Changing code, domain `change`, id prefix `CHG`. Formulation locators: PP 'Software Entropy' (The Pragmatic Programmer, 20th anniversary ed., ch. 1 'A Pragmatic Philosophy', topic 'Software Entropy': broken windows); the 97 Things essays 'Act with Prudence' (en/thing_01/README.md), 'The Boy Scout Rule' (en/thing_08/README.md) and 'The Road to Performance Is Littered with Dirty Code Bombs' (en/thing_74/README.md) in 97-things/97-things-every-programmer-should-know.

The canon builds this topic from four formulations. The Pragmatic Programmer's 'Software Entropy' warns against broken windows. Seb Rose's 'Act with Prudence' allows deliberate debt only if it is logged when the compromise is made and repaid soon. Martin's Boy Scout Rule says to leave each module cleaner than you found it. Pepperdine's 'dirty code bombs' are complex or highly coupled code that makes later changes unpredictable. Clean Code ('later equals never'), APOSD (complexity is incremental, stay strategic) and Fowler's litter-pickup refactoring restate these ideas. Cunningham's later reflection disputes reading the debt metaphor as licence for shortcuts. Industry agrees on three points: a change must not lower code health (Google eng-practices), cleanup deferred without a record usually never happens, and a shortcut that ships unresolved is tracked in an issue. Industry disagrees on three points. First, whether a debt marker may stay in merged code: Google style, Checkstyle, Sonar and Ruff TD say yes; ESLint no-warning-comments, Ruff FIX, clippy todo, godox, rustc tidy and CWE-546 say no. Second, whether a marker names a person or an issue. Third, whether every change owes a cleanup beyond its own code: the Boy Scout Rule says yes; Software Engineering at Google ch. 20, small-CLs guidance and 'Before You Refactor' say no. The evidence that opens is as follows. A controlled experiment (Levén et al., EMSE 2024; 29 developers, 95% credible intervals) found that existing debt of a given type makes developers add new debt of that type, even when it is not needed. SATD mining studies (Potdar & Shihab, relayed; Bavota & Russo; Maldonado et al.; Zampetti et al. 2018) show that recorded debt is common and long-lived. It is removed mostly in passing during bug fixes and feature work, often by accident and seldom acknowledged. Interview studies (Li et al.; Zampetti et al. 2021; Storey et al.) describe markers linked to issues and the risk that developers stop admitting debt. Industrial feature-flag studies cover stale flags, the kill-switch exception, and giving each flag an owner and an expiry at creation: Piranha (ICSE-SEIP 2020) and Meinicke et al. (ICSE-SEIP 2020), both opened in full. Six rules become cards: no new debt beside existing debt; a shipped shortcut recorded with a tracked debt marker; a paid-off marker removed together with its debt; a retired flag leaving no dead branch; a temporary flag declared with an owner and an expiry; and no unfinished-work placeholder on a production path. Five rules are held. The Boy Scout mandate has no separating condition. Marker deletion while the debt remains, and new reliance on code flagged as temporary, lack evidence. Deadline-only debt is held as not checkable. Recording touched debt is folded into the shipped-shortcut rule. The marker's own wording stays with the comments topic.

I could not open The Pragmatic Programmer 'Software Entropy', Clean Code, A Philosophy of Software Design, Refactoring 2nd ed., Code Complete, Cunningham's 1992 report and 2009 reflection, Fowler's quadrant, Hodgson's feature-toggles article or SWEBOK V4. Those items are paraphrases marked unfetched. Levén et al. (broken windows), Potdar & Shihab and Bavota & Russo rest on the orchestrator's relayed snippets. The canon agrees on four points: do not add new debt where debt already exists (broken windows, zero tolerance, 'don't accept CLs that degrade code health'); a change leaves touched code at least no worse; cleanup deferred without a record rarely happens ('later equals never', eng-practices); and a debt that cannot be paid now is filed in the tracker and optionally marked in code with a reference to it. It disagrees on three: (1) whether a marker may stay in shipped code at all (Google guides, Clean Code, Checkstyle and Ruff TD accept tracked TODOs; ESLint no-warning-comments, Ruff FIX002, clippy todo, rustc tidy and Code Complete treat markers as unfinished work to remove before production); (2) whether a marker names a person (C++/Shell guides allow it and say a name is not a commitment; Java/Python guides say to avoid it and use a bug link); (3) whether boarding up with commented-out code (PP) is acceptable, since Clean Code says to delete it. Boy Scout's 'clean up at least one other thing' also sits uneasily with eng-practices' advice to keep refactorings in separate CLs. Cunningham's later reflection disputes reading the debt metaphor as permission for shortcuts.

## Reception layer

Linters across all five languages check debt markers mechanically, and they disagree about what a marker is for. ESLint no-warning-comments, Ruff FIX, clippy::todo, godox and Sonar S1135/S1134 treat TODO/FIXME as unfinished work to resolve before shipping. Checkstyle TodoComment and Ruff's own FIX docs treat a marker as a legitimate way to track work, and Ruff TD002/TD003 and unicorn expiring-todo-comments check the marker's shape: author, issue link, expiry. A second set of tools shows the industry's practical version of "no new debt next to old debt": they report new violations only and freeze the existing ones. These are golangci-lint `new`, ESLint bulk suppressions, and SWE-at-Google ch. 20 ("focus on newly introduced warnings"). The same set flags stale suppressions as debt of their own (staticcheck, Rust #[expect], ESLint reportUnusedDisableDirectives, Ruff RUF100). The canon disagrees in four places. (1) Owner versus tracking reference: Google's Java and Python guides advise against TODOs that name a person, while Ruff TD002, the Go doc-comment Notes and the C++ guide use a name. (2) Whether deliberate debt is acceptable: Seb Rose allows it if tracked, Uncle Bob's 'Professional Programmer' rejects "fix later", and Marquardt says interim solutions usually stay and "leave it as is" is a real option. (3) The Boy Scout Rule against "if it isn't broken, why fix it", argued by Attapattu and SWE ch. 20, with Google eng-practices letting small cleanups ride along and sending refactorings to a separate CL. (4) Whether every marker needs a ticket: PEP 350 (rejected) calls that too burdensome, and Zampetti et al. find that SATD is implicitly discouraged in industry. Several sources could not be opened. WebSearch was exhausted, so papers are reachable only as the orchestrator's relayed snippets (Potdar & Shihab, Bavota & Russo, Levén et al.) or through GitHub-hosted copies: the Piranha ICSE-SEIP paper is in-tree at uber/piranha, and the Zampetti and Hata abstracts are on neverworkintheory. Wehaibi et al. was dropped because its snippet states only the research questions. The gist host and the cpython Doc raw path (404) were not reachable, and Tufano 2015, Storey 2008 and the Pragmatic Programmer's 'board it up' passage are unfetched.

## Evidence layer

Every candidate rule in this topic has at least one source that can be opened. Recording debt where it lives: SATD mining studies show that recorded debt is widespread, long-lived and unevenly removed (Potdar relayed; Bavota & Russo, Maldonado et al., Zampetti et al., Tufano et al. and Romano et al. fetched through GitHub-hosted IEEE metadata or the authors' repositories). Interview studies (Li et al., Storey et al., Maipradit et al.) and Google's style guides and eng-practices tie the marker to an issue reference and an owner. The tool canon disagrees on two points: whether to track a marker (Checkstyle, Sonar, PEP 350) or remove it before production (ESLint, Ruff FIX, clippy todo, CWE-546), and whether to name an author (Ruff TD002) or a bug rather than a person (Google Java/Python guides, which conflict with the C++ guide). Broken windows: the Levén et al. experiment was opened in full through an arXiv mirror (29 developers, Java, 95% credible intervals), and Tufano and Bavota support persistence. Spinellis & Avgeriou report complexity debt being paid back by a self-correcting process. Paying down touched debt is supported by Maldonado and Li et al. and qualified by Google's small-CLs guidance, SWE-at-Google ch. 20 and AlOmar et al. Stale flags: the Piranha (ICSE-SEIP 2020) and Meinicke et al. papers were opened in full. Rahman et al. (MSR 2016), the Wehaibi findings and Lehman's law could not be opened, and SWEBOK V3 has no technical-debt text.

## Spine — candidate rules in source order

1. **Code a change adds to code that already carries debt meets the same bar as code added to clean code, reusing functionality the code already provides and repeating none of the surrounding duplication, poor names or other smells** — When a change extends code that already carries technical debt, such as duplicated logic, non-descriptive names or other smells, the code it adds is held to the bar the project sets for any new code. It reuses functionality the code already provides instead of re-implementing it, names what it introduces descriptively, and copies none of the debt patterns around it. The existing debt neither lowers that bar nor obliges the change to pay it off. In a controlled experiment, existing debt of a given type raised the likelihood that developers extending a system added new debt of that type, even where it was not necessary. Review guidance rejects changes that degrade code health, because systems become complex through many small changes that add up.

2. **A change adds no new use of code that an existing debt marker flags as temporary or due for removal, so that the recorded debt does not grow** — Code that an existing debt marker presents as temporary, such as a shim, a workaround or a compatibility path awaiting removal, gains no new callers or dependents in a change. Each new dependent widens the debt and makes the recorded removal harder. A change that must rely on such code updates the tracked issue rather than silently enlarging the removal.
