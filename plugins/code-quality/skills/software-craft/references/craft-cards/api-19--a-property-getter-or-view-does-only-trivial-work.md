# A property, a getter or a view conversion does only trivial work, and costly, remote or failing work is exposed as an ordinary method

## Thesis
An operation read with the syntax of a field — a property or a getter accessor — does what reading a field does: at most a trivial computation or control of access to an attribute, with no precondition the caller must meet, and it does not fail; an operation that performs a complex computation, executes a remote call, takes perceivably longer than getting the value of a field, or can fail is exposed as an ordinary method instead. In a language that has no properties, a getter — a routine that takes no argument besides its receiver and is named by the value it returns, with or without a get prefix — that performs a complex computation or executes a remote call takes a name that states the work, with a word such as compute or fetch in place of get, so that the reader sees the call may take time and could block or fail. A conversion named as a view of the underlying representation exposes that view at no cost, and a conversion with nontrivial cost at runtime takes the name of a conversion that does work rather than the name of a view.

## Rationale
A property has the calling syntax of a field, and its implementation is held to the general expectations of regular attribute access: that it is cheap, straightforward and unsurprising; in some scenarios a function with no arguments may be interchangeable with a read-only property. Attribute notation makes the caller believe that access is relatively cheap, which is why a computationally expensive operation is kept out of a property, and a method is preferable to a property for a time-consuming operation, one perceivably slower than the time required to set or get the value of a field. A property getter is expected to be a simple operation without preconditions, and a getter that can throw should probably be redesigned as a method; a property is preferred over a function when its algorithm does not throw, is cheap to calculate or cached on the first run, and returns the same result over invocations while the object's state has not changed. For an operation that performs a complex computation or executes a remote call, a word such as compute or fetch in place of get makes it clear to the reader that the call may take time and could block or fail. A conversion named as a view is free and exposes a view into the underlying representation, while a conversion that does work to change one representation into another, such as an expensive encoding check on the bytes of its input, has nontrivial cost at runtime, and naming it as a view would not be correct.

## Example
```go
bad:  func (r *Repo) Owner() string {
          resp, err := http.Get(r.ownerURL)
          ...
      }
good: func (r *Repo) FetchOwner(ctx context.Context) (string, error) {
          req, err := http.NewRequestWithContext(ctx, http.MethodGet, r.ownerURL, nil)
          ...
      }
```

## Limits
A property or a getter that controls access to an attribute or calculates a trivially derived value is the intended use of the shape, since its logic is simple and unsurprising. In a language that has properties, a routine called as a method, with or without a get prefix, is the alternative to a property for getting a value whose computation is complex or whose cost is significant, so it is outside the accessor shapes. A value calculated on the first read and cached for later reads meets the cost condition, as caching is generally fine in an accessor and lets the calculation be lazy; that first read is still held to not throwing, and a remote call made on it still may take time and could block or fail. An indexed access that validates its index argument is expected to fail on an invalid index, so the no-failure condition does not reach it. Where the underlying concept itself uses the word get, such as an HTTP GET, the word names that concept rather than an accessor. A conversion named as producing a new representation is expected to do work, and one named as consuming its input may be cheap or costly; only the conversion named as a view is held to costing nothing. A routine that takes arguments, or that is named by a verb stating its work, is outside the accessor shapes, and whether an accessor changes state or whether its name agrees with its declared type is outside this rule. A project context that fixes the accessor shape for costly work, such as a framework or an interface the type implements that requires a property or a getter for that value, rejects the finding.

## Validator
Grep the added lines for an accessor shape — a property declaration or decorator, a getter accessor, in a language that has no properties a routine that takes no argument besides its receiver and is named by a noun or with a get or is prefix, a conversion named as a view — and for a call that reaches a network, a database, a file, a subprocess or a sleep. Open the file and take each accessor-shaped operation whose declaration the hunk adds or renames or whose body the hunk changes, together with each accessor-shaped operation that encloses a matched call; read its body and each routine in the file it calls. Trace whether it executes a remote call, reads or writes a file or a database, waits on a sleep, a channel or another blocking call, runs a computation beyond a trivial derivation from the receiver's fields such as parsing, sorting, searching or validating a whole input, or, in a property or a getter accessor, checks a precondition and throws or returns an error when the check fails. Set aside control of access to an attribute, a trivially derived value, a lock held only around the read of a field, a value computed once on the first read and cached when that read neither calls a remote service nor can fail, an indexed access that fails only on an invalid index, a get that names the underlying concept such as an HTTP GET, a conversion named as producing a new representation or as consuming its input, a routine called as a method in a language that has properties, and an accessor shape the project context fixes. Validator question: **Does a property or a getter accessor do work beyond a trivial derivation — a remote call, a complex computation, work perceivably slower than reading a field or a precondition check that fails — does a conversion named as a view have nontrivial cost at runtime, or does a getter in a language that has no properties perform a complex computation or a remote call under a name that does not state that work?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-19`, severity minor, `file`, `symbol`, `code` = the accessor's declaration line and the added line that performs the costly, remote or failing work, quoted verbatim from the diff, `fix` = the operation exposed as an ordinary method whose signature carries the failure in the language's usual form and, for a getter in a language that has no properties, whose name states the work (compute, fetch), or the costly work moved out so that the accessor returns a stored value, in the file's language, `rationale` = the expectation the accessor shape sets for its reader (cheap, no precondition, no failure) and the work the body performs instead).
