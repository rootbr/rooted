# Research note — Concepts the change reviewer found uncovered

Topic `gaps-change` of group F. Changing code, domain `change`, id prefix `CHG`. Formulation locators: no canon chapter of its own; the concepts come from the domain reviewer's reading of the corpus.

The topic covers two concepts the change-domain reviewer found uncovered. It has no canon chapter of its own. (1) Fix-up commits are folded into the commit they fix, so a series is presented in final form. This belongs to the 'small steps' taxonomy topic, whose research note (small-steps-and-minimal-diffs.md) held it as not checkable. Official project documentation agrees on the end state, and all of it was fetched and re-verified for this spine: Kubernetes ('Sausage => squash', 'Layers => don't squash'), git SubmittingPatches and MyFirstContribution ('patch C which fixes patch A' should not ship), Linux 5.Posting ('final form ... not the path you took'), Zephyr ('No fixup or merge commits are allowed'), LLVM, GitLab and Node. Git's own 'fixup! ', 'squash! ' and 'amend! ' title markers, together with three working CI checks (GitLab's Danger rule and two GitHub Actions), make the marked case checkable on the commit list base..head. The industry disagrees on timing, not on the end state. Git, Linux and Zephyr rewrite every iteration. Kubernetes, LLVM, GitLab, Node and CPython keep fix-ups as separate commits during review and fold them at landing or through a squash merge. It also disagrees on granularity: LLVM and Phabricator reduce a change to one commit, while Kubernetes and git keep layered commits. Fossil rejects history rewriting altogether. Every side keeps already-merged or published history out of reach. The earlier hold rested on the claim that a finder sees no commit list. That no longer holds: DOC-07 and DOC-08 already read `git log base..head` at base-compare scope and anchor on the first added line of a matched hunk. Concept 1 is therefore carded, contested, with a separating condition: the rule binds the series as it lands and is met by a fold at landing or by a squash merge. That condition has fetched evidence on each side, and the GitLab Danger rule encodes it (fail when ready, warn on draft, ignore when the MR squashes on merge). No empirical study of folding could be opened, so the card rests on documentation and tool checks. Two cases yield no finding: no commit list (an uncommitted working tree) and a single-commit change. (2) Deliberate debt only for a hard deadline or an emergency. This belongs to the 'technical debt' taxonomy topic. Google eng-practices (fetched) is the only openable official source. Faithfully stated, it says that a definite worsening of code health is justified only by an emergency. An emergency is a small change, reviewed again afterwards. A hard deadline, one whose miss would be disastrous, can create an emergency. Soft deadlines never justify sacrificing code health. The concept's wording, 'a hard deadline or an emergency' as two equal grounds, is not what the source says. The TAP framework study (arXiv:2204.09623, fetched via a GitHub-hosted extraction) accepts intentional debt for any set deadline if the whole team decides on it consciously, tickets it and repays it. Rose, and Fowler's prudent-deliberate quadrant, agree as formulations. Martin rejects any exception. No source separates these positions and no study compares hard and soft deadlines. Concept 2 is therefore pending-no-separating-condition. It is checkable only where a change description cites urgency as the reason for a shortcut the change adds. The same contest is already pending in the corpus under 'clean up introduced complexity unless it is an emergency' (the refactoring and code-review-as-author-and-reviewer entries). It does not narrow CHG-34, which explicitly leaves whether a shortcut may ship at all outside its scope.

## Formulation layer

Concept 1, fold fix-ups into the commit they fix: every formulation I could open is project process documentation, and all of it was fetched. The kernel says a series is posted in its 'final form', 'not the path you took'. Git says each iteration is a full replacement, so v2 ships a correct patch A rather than A plus a later patch C that fixes it. Kubernetes says 'Sausage => squash' and 'Layers => don't squash'. LLVM, GitLab, Node, Go/Gerrit, OpenStack, QEMU, Chromium and rustc all agree that merged history carries no fix-up commits. Git's own 'fixup! ', 'squash! ' and 'amend! ' title markers, and a CI action that greps base..head for them, make the leftovers mechanically checkable. The canon disagrees on three points. Timing: git and the kernel rewrite every iteration, while Kubernetes, GitLab, LLVM and Node keep fix-ups as separate commits during review and squash only at merge. Granularity: Kubernetes and git keep layered commits, while LLVM squashes every PR to one commit and Phabricator wants one idea per commit. Legitimacy: Fossil's documentation calls history rewriting dishonest. Git and the kernel limit folding to unmerged work. Concept 2, deliberate debt: Google's eng-practices (fetched) say only an emergency justifies worsening code health, and that most deadlines are soft and do not justify it. A hard deadline (one where something disastrous would happen if missed, such as a contractual obligation) appears only as a case that can make a change an emergency, not as a separate allowance next to it. Rose's 'Act with Prudence' allows debt for any deadline that 'absolutely demands' it, provided it is tracked. Martin ('The Professional Programmer', Clean Code) rejects rushing under any deadline. I could not open APOSD, Clean Code, The Clean Coder, The Pragmatic Programmer, Fowler, McConnell, Cunningham or the Dagstuhl report: these are marked as unfetched paraphrases, and WebSearch was unavailable. The aposd-vs-clean-code discussion and SWEBOK V3 say nothing on either concept.

## Reception layer

Concept 1 (series in final form, fix-ups folded): most project documentation I could open agrees on the end state. Fix-up, review-response, typo, WIP and merge commits do not reach the shared branch (Kubernetes, git, Linux, Zephyr, Mozilla, Gerrit, LLVM, Node, GitLab). The projects split on two points. The first is timing: git, Linux and Zephyr rewrite the series at every iteration, while Kubernetes, LLVM, CPython, Node, GitLab and ostree want fix-ups kept as separate commits during review and squashed only at merge, often by a bot. The second is the final shape: Kubernetes, git, Zephyr and Node keep layered commits, while Phabricator and the always-squash setups of LLVM and CPython reduce a change to one commit, and GitHub's 2026 stacked-PR docs move the layers into separate PRs instead. Fossil ('Rebase Considered Harmful') disputes the whole practice. The tool rules make the concept checkable on base..head, against the earlier 'held-not-checkable' disposition: block-autosquash and block-fixup actions, the GitLab Danger fixup rule and its 10-commit warning, gitlint's WIP title rule, and Zephyr's gitlint config all key on fixup!/squash!/amend!/WIP titles. Linux, git and jj agree on one limit: once history is published, a fix goes on top as a new commit, for example with a Fixes: tag, and is not folded in. Concept 2 (deliberate debt only for a hard deadline or emergency): Google eng-practices (emergencies, pushback, standard) is the only openable official source. It says soft deadlines do not justify sacrificing code health, but it never says that a hard deadline permits debt; a hard deadline only turns a launch into an emergency, and the emergency change must be small and is reviewed again afterwards. Fowler's deliberate-prudent quadrant, Seb Rose's 'Act with Prudence' (any deadline or a thin slice), Cunningham 1992 and Wiese et al. 2022 dispute the narrow trigger, because they accept conscious, tracked debt for ordinary project deadlines. GitLab defers debt it discovers to follow-up issues for iteration, not for urgency. No static-analysis rule checks an urgency justification, so the rule can be checked only against a change description that claims urgency. WebSearch was not used (budget exhausted). martinfowler.com, c2.com, HN and Lobsters were not reachable. Fowler and Cunningham are relayed only through third-party GitHub pages.

## Evidence layer

Concept 1 (a series is presented in final form, with fix-up commits folded into the commit they fix) has broad, consistent backing from official project documentation, all fetched. These include Kubernetes ('Sausage => squash / Layers => don't squash'; a list of commit kinds to squash), Git SubmittingPatches ('present a logical progression made by a perfect developer'), Linux 5.Posting ('not the path you took'), Zephyr ('No fixup or merge commits are allowed'), Gerrit, Mozilla, LLVM, GitLab, QEMU and rustc. git-commit --fixup and rebase --autosquash supply the marker. Three tool checks fail a fixup!/squash! commit: the GitLab Dangerfile and two GitHub Actions. A local demo confirmed that the marker can be found on base..head and folded by autosquash. Two preconditions recur: fix-ups stay as separate commits during review and are folded only at the end of review or at landing (Kubernetes, Node.js, GitLab, LLVM); and where the platform squash-merges every PR (LLVM, GitHub, GitLab), the merge does the fold. The position is disputed by Fossil's 'Rebase Considered Harmful', with GitHub Docs and rustc-dev-guide naming the loss of history as a cost. No empirical study measuring the effect of folding fix-ups could be opened; Ram et al. (FSE 2018), Bird et al. (MSR 2009) and Paixão et al. (SCAM 2019) are recorded only from memory. Concept 2 (deliberate debt only for a hard deadline or an emergency) rests on Google eng-practices, all fetched: emergencies.md defines hard versus soft deadlines and says 'you shouldn't be sacrificing code health' for soft ones; standard.md and pushback.md allow worsening code health or deferring cleanup only in an emergency. SWE at Google ch. 19 and the Kubernetes exceptions process back this up. The research reachable through a GitHub-hosted arXiv mirror and neverworkintheory shows that tight deadlines are the most-cited cause of technical debt (Wiese et al.; Matsubara et al., both citing InsighTD) and that existing debt begets new debt (Levén et al., 29 developers). No study separates hard from soft deadlines. The position is contested: the TAP framework accepts intentional debt for any set project deadline if it is recorded and repaid; Kuutila et al. (as restated by Matsubara et al.) report that time pressure can raise efficiency up to a point; Potdar & Shihab find that time pressure does not correlate with the amount of self-admitted debt; and Lim et al. and Besker et al. (unfetched) report practitioners treating deliberate debt as a legitimate business trade-off. Both concepts were already recorded as held-not-checkable in research/software-craft/small-steps-and-minimal-diffs.md and technical-debt.md. Concept 1 becomes checkable only if a finder sees the commit list at base-compare scope; concept 2 is checkable only against a change description that invokes urgency.

1. **Before a series lands as separate commits, each commit that only fixes an earlier commit of the same series, such as a fixup!, squash! or amend! commit or one addressing review feedback or a typo in it, is folded into the commit it fixes, while independent layered commits stay separate** — A series lands in its final form, not as the path taken to reach it. A commit between base and head that fixes a bug in an earlier commit of the same unmerged series, addresses review feedback on it, corrects a typo in it or rewrites code it added is folded into that commit. A commit whose title starts with 'fixup! ', 'squash! ' or 'amend! ' is such a commit by construction. Independent changes layered toward one goal stay separate commits. The rule binds the series as it lands. Fix-ups kept as separate commits during review and folded at landing meet it, and so does a squash merge that folds them. A fix to a commit already merged or published goes on top as a new commit. 2. **A change that definitely worsens code health, such as by shipping a shortcut or leaving complexity it introduces uncleaned, is made only in an emergency, which a hard deadline whose miss would be disastrous can create, and never to meet a soft deadline** — Most deadlines are soft: they express a wish for a feature to be done by a certain time. Missing one, such as delaying a release by a week, is not disastrous, and code health is not sacrificed to meet it. Only an emergency justifies a change that definitely worsens code health or leaves complexity it introduces uncleaned. An emergency change is a small change that does one of the following: lets a major launch continue instead of rolling back; fixes a bug significantly affecting users in production; handles a pressing legal issue; closes a major security hole; or meets a hard deadline whose miss would be disastrous, such as a contractual obligation. It is reviewed thoroughly again once the emergency is resolved. On a diff the rule is checkable only where the change description cites urgency as the reason for a shortcut the change adds.
