# A routine that hands out a mutable collection, array or buffer its object keeps as private state returns a copy or a read-only view

## Thesis
A routine that callers outside its object can reach, and that gives its caller a mutable collection, array, map, slice or buffer the object keeps in a private field, returns a copy of it or a read-only view of it rather than the live object or a mutable reference to it. A read-only view is an unmodifiable wrapper that refuses mutators and delegates reads to the owner's collection, a declared result type that forbids writes, or a read-only reference; it gives read access without a copy. Where the caller needs the contents as they stood at the call, the routine returns a copy, because changes the owner makes later are visible through a view.

## Rationale
Where the result refers to the field rather than copying it, the caller holds the owner's own storage: assigning that result binds the caller's name to the owner's object without copying it, slices and maps hold references to an underlying data structure, a slice taken from another shares its underlying array, and a change the caller makes to an element through the result is a change to the owner's field. Elements can then be removed or replaced outside the object that owns them, which violates the object's encapsulation and leaves it open to unexpected changes in its state. Where clients can mutate a field's contents arbitrarily, the type can neither validate those contents nor maintain invariants on them. Where untrusted code reaches the owner's instances and unchecked changes to the returned object would compromise security or other important properties, the owner has to hand out something else, and a new copy is the better approach in many situations. In interviews about language support for immutability, professional developers stated that incorrect state mutations are a major source of bugs, for example an object thought to be immutable changed by some other object because references were reused instead of immutable copies. A copy is distinct storage: for a collection that is mutable or contains mutable items, it lets one side change its copy without changing the other, so the caller can add, remove or replace elements without affecting the owner. An unmodifiable view gives the caller read access to the internal collection while preventing it from modifying the collection unexpectedly, and its reads are delegated to the backing collection. A result type declared read-only also tells the caller that it is not meant to change the contents at all.

## Example
```rust
bad:  pub fn entries(&mut self) -> &mut Vec<Entry> {
          &mut self.entries
      }
good: pub fn entries(&self) -> &[Entry] {
          &self.entries
      }
      pub fn snapshot(&self) -> Vec<Entry> {
          self.entries.clone()
      }
```

## Limits
A view is not a snapshot: changes to the backing collection remain possible and are visible through it, so a view is not necessarily immutable. A view or an unmodifiable copy whose elements are mutable is still mutable through those elements, and it can be considered effectively immutable only when all its elements are immutable. A shallow copy inserts references to the elements found in the original, so a mutable element stays shared with the owner; a deep copy inserts copies of them and may copy too much, such as data intended to be shared between copies. The rule asks for a copy or view of the collection, array, map, slice or buffer, and leaves a mutable element held inside it outside its reach. A collection the owner already keeps immutable is returned as it is, since no caller can change it. An unmodifiable view whose backing collection is effectively immutable, or is referenced only through unmodifiable views, can be considered effectively immutable and so shows no later change. Where the language refuses a mutable reference to a value while an immutable one is in use, the value does not change under a caller holding a read-only reference, and that reference stands in for a copy for as long as the caller holds it. A read-only result type that only the type checker enforces changes no behaviour at runtime: it stops writes from type-checked callers and is mainly a statement of intent. A routine whose documentation declares that its result shares the owner's storage, and states until when the result stays valid or what a change made through it affects, hands out that storage by design, typically to avoid a copy, and is outside the rule; the rule concerns storage handed out without that declaration. A private routine whose result no routine reachable from outside the object passes on is outside the rule. A compound, passive data structure, for which public fields are the appropriate design, keeps no private state for the rule to protect; a project context that documents a type as such a structure rejects the finding.

## Validator
Grep the added lines for a return of a field, a signature of a routine whose result is a collection, an array, a map, a slice or a byte buffer, and a routine that takes its receiver mutably and returns a mutable reference. Open the file and take each routine whose result is one of those kinds and that callers outside the object can reach: a public, protected or exported routine, or a private one whose result such a routine passes on. Trace the returned value to its source. Continue when it is a field the object keeps private, a sub-slice of that field, or a mutable reference to it, and that field holds a mutable collection, array, map, slice or buffer. Skip a result that is a fresh copy, including a value the language copies on return, an unmodifiable view, a read-only reference or a value of a declared read-only type. Skip a routine whose documentation declares that its result shares the owner's storage and states until when it stays valid or what a change made through it affects. Skip a field that holds an immutable collection, and skip an owner that is a compound passive data structure whose fields are public by design or that the project context documents as one. Where the routine's name or documentation promises the contents as they stood at the call, check that it returns a copy and not a view. Validator question: **Does a routine that callers outside the object can reach hand its caller, without documentation declaring that the result shares the owner's storage, the live mutable collection, array, map, slice or buffer the object keeps in a private field, or a mutable reference to it, or return a view where its name or documentation promises the contents as they stood at the call?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-66`, severity major, `file`, `symbol`, `code` = the return statement, or the signature that hands out the field, quoted verbatim from the diff, `fix` = the routine returning a copy of the field or a read-only view of it, and a copy where the routine promises the contents as they stood at the call, in the file's language, `rationale` = the private field the caller can change through the result, the elements it can remove or replace from outside the owner, and the state or invariant the owner can no longer guarantee).
