# Research note — Variables, scope and numerics

Topic `variables-scope-and-numerics` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC10 (Code Complete 2nd ed. ch. 10 'General Issues in Using Variables': initialization, scope, persistence, binding time, one purpose per variable); CC11 ('The Power of Variable Names') whose naming rules belong to naming-identifiers; CC12 ('Fundamental Data Types': numbers, integers, floating point, characters and strings, booleans, enumerated types, named constants, arrays); CC13 ('Unusual Data Types': structures, pointers, global data); the 97 Things essay 'Floating-point Numbers Aren't Real' (thing 33).

The canon here is Code Complete 2nd ed. ch. 10, 12 and 13. No copy could be opened, so its items are paraphrases from memory and serve only as formulation. The openable formulations are the 97 Things essays 15 (Kimchi), 33 (Allison) and 73 (Saariste). The canon agrees on a core: declare a variable close to its first use and initialize it there; give it the narrowest scope; use it for one purpose; remove unused variables; name meaningful literals; keep mutable state out of globals; and respect the limits of fixed-width integers and binary floating point. Most of this is stated in openable form by official documentation and by tool rules that run in practice. The documentation includes the Google Java, JS, TS, Python and Go guides, the Uber Go guide, Effective Go, the Go spec, the Rust book, Reference and RFC 560, the CPython docs and PEPs 238 and 485, ECMA-262 and the OpenJDK javadoc. The tool rules come from Checkstyle, PMD, Error Prone, SpotBugs, Sonar, ESLint, Pylint, Ruff, clippy, staticcheck, gosec and go vet. Research is thin. Dietz et al. (ICSE 2012, C/C++) find accidental integer overflows common even in mature programs, alongside many intentional wraparounds. Binkley et al., relayed through Islam et al. (JSS 2014), find a global variable holding large dependence clusters together in half of 21 C programs, but Islam et al. find such clusters unrelated to faults. No study of magic numbers, shadowing or declaration distance was found. Every numeric rule carries a language condition. Java and Go wrap silently on overflow, Rust panics in debug and wraps in release builds, Python ints never overflow, and TypeScript numbers lose integer exactness above 2^53 - 1. Integer division truncates in Java, Go and Rust, while Python's / is true division and // floors. Go's untyped constant expressions are exact. The industry disagrees on five points. (1) Magic-number checks are pedantic or off by default (Ruff, ESLint, Airbnb); a literal counts as magic when it has a role apart from its value (Google Go style). (2) On shadowing, ESLint, Checkstyle, Pylint and Sonar flag every case, while the Rust book and clippy call shadowing with a closely related value idiomatic. The line falls where code still needs the outer entity or the inner value is unrelated (Google Go, go vet, clippy). (3) On the tolerance for float equality, SpotBugs and Sonar Java suggest a fixed absolute margin, while clippy, PEP 485, Error Prone and MDN scale the margin to magnitude. The line falls on whether the values have a known range or a zero expected value. (4) Const-by-default is required by Google's TS guide and disputed by Abramov and Simpson, and no admissible source gives the condition, so it stays pending. (5) The TC39 Decimal proposal disputes integer minor units as a substitute for decimal money, so the money card rests only on a decimal type. Fourteen rules ship as cards, one is pending, two are held and twelve fold into cards or held rules.

## Reception layer

Fetched from raw.githubusercontent.com: the rule pages of ESLint, typescript-eslint, Checkstyle (with its google_checks.xml and sun_checks.xml presets), PMD (with its quickstart ruleset), Error Prone, SpotBugs, SonarSource, Pylint, Ruff (with its 2026 rule categories), clippy (with its changelog), go vet, gosec, go-mnd and gochecknoglobals. Also fetched: the Google and Uber style guides, PEPs 238, 327 and 485, Rust RFC 560, the Go loopvar design doc, the Go FAQ, MDN, the TC39 Decimal proposal, Abramov's 'On let vs const', Simpson's YDKJSY appendix, and the Ousterhout–Martin discussion. Five positions are disputed by named sources. (1) Magic-number rules: Ruff files PLR2004 as Pedantic, Pylint ships it only as an opt-in extension, ESLint leaves it out of recommended and marks it frozen, Airbnb turns it off, and Google's Go guide says a constant with no role beyond its value should not exist. (2) prefer-const: Abramov and Simpson dispute it, while the Google TS and JS guides and Airbnb require it. (3) Blanket no-shadow rules: the Rust book calls shadowing idiomatic, clippy moved shadow_unrelated to restriction in 1.57, the go vet shadow pass is off by default for false positives, and Pylint's own docs record the clash with pytest fixtures. (4) The 'compare floats with an epsilon' fix: clippy, MDN, PEP 485 and Error Prone each warn against a fixed or machine epsilon, clippy moved float_cmp to pedantic in Rust 1.57, and SpotBugs still suggests a fixed 1e-7. (5) The 'money as integer cents' fix: TC39 Decimal objects that currencies have different numbers of decimal places and that fractional cents occur. Tools largely agree, and keep these checks on by default or in their starter rulesets, on: int arithmetic that overflows before widening, integer division assigned to a float, BigDecimal(double), lossy literals, loop-variable capture, and non-final public statics. Go removed loop-variable sharing in 1.22, and the Go team's design doc gives the measured rates. Not opened: Hacker News, Lobsters, Peter Bourgon's blog, Rob Pike's golang/go#19623 and the Bruce Dawson posts (WebSearch budget exhausted, hosts denied), so no 2024–2026 forum thread could be checked; the freshness items come from the 2024 G115 changelog, the Go 1.22 loopvar change, Ruff's preview categories and the TC39 Decimal stage history.

## Evidence layer

Most of the evidence for this topic is official language documentation and static-analysis rule pages. Each of these was opened as raw text from GitHub: the Go spec, the Rust book and reference, the CPython docs and PEPs, the ECMA-262 spec, the OpenJDK javadoc, the Google and Uber style guides, and rules from Checkstyle, ESLint, PMD, Error Prone, SpotBugs, SonarSource, Pylint, Ruff, clippy and go vet. Where research was reachable, it came only through GitHub-hosted copies. Three abstracts were fetched that way: Dietz et al. ICSE 2012 on integer overflow (from llvm/llvm-www-pubs), Di Franco et al. ASE 2017 on numerical bugs (from a mirrored bib), and the open-access text of Islam et al. JSS 2014. Islam et al. restate the Binkley et al. finding that 50% of 21 programs had a global variable holding together large dependence clusters, but the same paper finds dependence clusters not correlated with faults. Wulf and Shaw (1973) are reachable only as a quotation in a blog hosted on GitHub. Goldberg 1991 is reachable only as a partial reprint, so his critique of epsilon-equality and the Dinda and Hetland developer survey stay unfetched. No empirical study of magic numbers, shadowing, or declaration distance was found. Every numeric rule depends on the language; local probes confirmed this on Python 3.11, Node 22/tsc 6, Go 1.24, Java 21 and Rust 1.94: Python ints never overflow, TS numbers lose integer exactness above 2^53-1, Go and Java wrap silently, Rust panics in debug and wraps in release, Python floors -7//2 while the others truncate, and Go untyped constant expressions make 0.1+0.2==0.3 true. The canon disagrees most on shadowing: the Rust book and clippy call related-value shadowing idiomatic, Google Go calls intentional shadowing useful, and go vet's shadow pass is off by default for false positives. It also splits on float comparison: Sonar and SpotBugs suggest an absolute margin, while clippy, Error Prone and math.isclose warn that a fixed epsilon fails across magnitudes and near zero. Tool adoption is uneven: ESLint no-magic-numbers is frozen and not recommended, and the clippy numeric lints are pedantic or restriction, which means allow-by-default.

## Spine — candidate rules in source order

1. **A local variable is declared close to its first use, not at the start of its block ahead of code that does not use it, and is initialized in its declaration or immediately after it** — Declare each local variable close to the point where it is first used, within reason, rather than habitually at the start of its block, so that its scope is no larger than the code needs; give the declaration an initializer, or initialize it in the statement that follows. A declaration is premature when statements that may return or throw lie between it and the first read. The rule has no fixed threshold: Checkstyle's default allowed distance of three statements is a tool convention, a declaration whose initializer has side effects that must run early stays where it is, and final declarations are exempt by default in that check. The cost of an early declaration differs by language: Go silently gives a declared but uninitialized variable its type's zero value, Rust (and Java's definite assignment) reject a read before every path has assigned it, and Python has no declarations, so in Go an early declaration without an initializer yields a plausible but wrong value rather than an error.

They also let independent tests interact, which breaks test filtering, parallel runs and sharding. Pass the dependency explicitly instead. A library does not export package-level variables that control behaviour for all its clients, and a module does not export a mutable binding. Where mutable global state is warranted, it is internal to its module, external access goes through functions or methods, and a comment explains the design reason. Module-level constants are permitted and encouraged, and package state is acceptable when it is logically constant or when the caller cannot observe it (a private cache whose hits and misses look the same). Research on 21 C programs found a global variable holding large dependence clusters together in half of them, but a later study found such clusters unrelated to faults. So the measured cost lies in dependence and understanding, not in defect counts. Concurrent access to a global belongs to concurrency correctness.
