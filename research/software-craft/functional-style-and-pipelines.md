# Research note — Functional style and pipelines

Topic `functional-style-and-pipelines` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'Transforming Programming' (The Pragmatic Programmer, 20th anniversary ed., topic 30, ch. 5 'Bend, or Break': a program as a pipeline of transformations, and error handling inside the pipeline).

The canon agrees on a core: Pragmatic Programmer Topic 30, Effective Java Items 42, 45 and 46, Refactoring's Replace Loop with Pipeline and Split Loop, the Python Functional HOWTO and SICP 3.5. Write a data transformation as a sequence of steps, each close to a pure function of the step before. Callbacks given to map, filter or a stream should have no effect beyond their return value. A lazy pipeline does nothing until something consumes it, so it should be consumed promptly. Long callbacks and long chains need names. The industry disagrees in four places. (1) Pipeline or loop as the default: Airbnb, the Kotlin conventions, the Rust book and Fowler prefer pipelines; Pike, the Go blog, the Google TypeScript guide and Bloch prefer loops or judge case by case. (2) reduce: clean-code-javascript, Airbnb and Hughes favour it; Python 3.0's What's New, the HOWTO, MDN and eslint-plugin-unicorn prefer a loop. (3) Function reference or forwarding lambda: Pylint, clippy and Sonar favour the reference; MDN, unicorn and the Google TypeScript guide favour the lambda. Whether the step passes extra arguments separates the two. (4) Flagging every loop-variable capture: Sonar S1515 does; the Go team's measurements argue against it. Official documentation and tool rules in all five languages support eleven cards, each grounded in documented semantics: side-effect-free callbacks; no map run only for its effects; lazy pipelines left unconsumed or consumed late; single-pass iterators; closures that read a loop variable after their iteration; no mutation of the collection being traversed; a loop for work that exits early; named long callbacks; named intermediate results; MDN's conditions for reduce versus a named operation or a loop; and callback arity. Hands-on runs on OpenJDK 21, Python 3.11, Rust 1.94, Node 22 and Go 1.24 reproduced every laziness, single-pass, capture and parseInt claim. They are scratch files and must move to an openable form before a card can cite them. No fetched study measures whether a pipeline reads better or carries fewer defects than a loop. Pankratius 2012 found that a functional style did not lower debugging effort, and Uesbeck 2016 and Lucas 2019 are unfetched. The pipeline-or-loop default and the split-loop question therefore stay pending. Lambda parameter naming, pair-carrying across stages, stateful closures and effects-at-the-edges have only practitioner formulations.

## Formulation layer

The canon agrees on a core: write a data transformation as a sequence of steps, each one as close as possible to a pure function of the step before (PP Topic 30, Effective Java Items 45 and 46, Refactoring's Replace Loop with Pipeline, the Python Functional HOWTO, 97 Things #2). Callbacks given to map, filter or a stream should have no side effects; a forEach, or a map run only for its effects, should become a plain loop or a terminal report (EJ 46, Rust's Iterator::map doc, Python 3.0 What's New, MDN map). It also agrees that a lazy pipeline does nothing until something consumes it and should be consumed once and promptly; SICP calls mixing delay with printing or assignment 'odious programming style'. The canon disagrees in four places. (1) Pipeline or loop as the default: Airbnb and the Kotlin conventions prefer higher-order functions, while Rob Pike, the Google TS guide and EJ 45 ('if you're not sure, the iterative version is probably the safer choice') do not. (2) reduce: clean-code-javascript recommends it, but Python 3.0's What's New, the HOWTO, eslint-plugin-unicorn and MDN all say a loop or a named method is usually clearer. (3) Long chains: Clean Code says to split a train wreck into explanatory variables, but PP Tip 45 says intermediate variables leave the coupling in place and exempts transformation pipelines over stable library calls. (4) Splitting work into several passes or tiny steps: Fowler would split first and optimize later, but in the APOSD discussion Ousterhout measured a 3-4x slowdown from a split loop and objected to over-decomposition. Most book chapters were read through third-party GitHub copies or bilingual translations of the original text (PP, Clean Code, Effective Java, Refactoring via notes, Code Complete via a rules file), so they serve only as formulation and provenance. Fowler's 'Collection Pipeline' article and Bernhardt's 'Functional Core, Imperative Shell' were not opened; martinfowler.com is denied and a talk has no text. WebSearch was not used (budget exhausted). GitHub code search was used only to find raw paths.

## Reception layer

I opened every item from raw.githubusercontent.com in this run. They cover the rule pages of rustc, clippy, Ruff, Pylint, Sonar (Python and Java), Error Prone, Checkstyle, ESLint and eslint-plugin-unicorn. They also cover the language teams' own positions (Go blog and proposal, PEP 289, Python 3.0 What's New, the Functional HOWTO, Rust std docs, the java.util.stream docs, MDN) and named practitioners: Pike, Bloch, Kuchling quoting Lundh, Slatkin, Simpson, Reitz's guide, the Airbnb and Google style guides, the Kotlin conventions and samber/lo. I checked key tool behaviour hands-on under /tmp: JDK 21 skips peek() when count() can be taken from the source, rustc warns on an unused lazy map, Node 22 iterator helpers do not run until consumed, and Ruff 0.15.8 flags B023, PERF401 and C417. Settled ground: closures capturing a loop variable (Go changed its semantics on Google-scale data, C# did the same earlier, and five linters flag it), a side effect inside map or a lazy step (lazy helpers that are never consumed are flagged by rustc, Error Prone and unicorn), and naming long lambdas and steps (Bloch, Lundh, Google, Checkstyle and Sonar, though the line limits differ: 1–3 lines for Bloch, 10 for the tools). The canon is openly split on whether to prefer pipelines over loops: Pike, Bloch, the Go blog and Google TS lean to loops, against Airbnb, clean-code-javascript, Kotlin and samber/lo. It is also split on reduce: Python 3.0, Kuchling, MDN, unicorn no-array-reduce and clippy unnecessary_fold against Airbnb, clean-code-javascript and the Rust patterns book. These rules therefore need Limits, not absolutes. I could not open Hacker News, Lobsters, vendor sites or any paper text (the WebSearch budget is spent and those hosts are denied). The three candidate papers are relayed only through the orchestrator's snippets, and the C++-lambda and Java-lambda comprehension studies are unfetched and must not anchor a card.

## Evidence layer

Official documentation and tool rules in all five languages back the core rules. Java's java.util.stream documentation, Python's Functional HOWTO and What's New 3.0, the Rust std and book, MDN, and Go's iter package and loopvar proposal say the same things: keep pipeline steps free of side effects and leave the source alone, do not run map just for its effect, a lazy pipeline does nothing until something consumes it and may skip effects entirely (Java count and peek), a lazy pipeline can be walked only once, and a closure captures the variable rather than its value. Lint rules back each of these (rustc map_unit_fn, Error Prone ReturnValueIgnored and StreamToIterable, unicorn no-unused-iterator-helper, Ruff B023, Sonar S1515, ESLint array-callback-return and no-loop-func, clippy unnecessary_fold, Checkstyle LambdaBodyLength). Hands-on runs on OpenJDK 21, Python 3.11, Rust 1.94, Node 22 and Go 1.24 reproduced every laziness, single-pass and capture claim; the scratch tests live in /tmp/craft-research/fsp-ev/hands/RUNS.txt and are not yet in a form anyone can open. The canon disagrees in three places. (1) Passing a function reference instead of a lambda: Pylint, Ruff, clippy and Sonar recommend it, but unicorn, the Google TypeScript guide and MDN's parseInt example warn against it for JS array callbacks. (2) A loop versus reduce: the Python docs and unicorn prefer the loop, MDN calls it a tradeoff, and Hughes 1989 treats reduce as the glue for named operations. (3) Flagging every loop-variable capture: Sonar S1515 does, while the Go team's measured data (about 1 in 8,000 test packages broken, 0.005% of loops buggy) argue against a blanket ban. Empirical research was largely unreachable because WebSearch was spent: Pankratius 2012 (functional style does not lower debugging effort) and Dyer and Chauhan 2022 came from neverworkintheory abstracts, Khatchadourian 2020 and Mazinanian 2017 are relayed snippets, Uesbeck 2016 is unfetched, and no fetched study measures whether a pipeline reads better or carries fewer defects than a loop.
