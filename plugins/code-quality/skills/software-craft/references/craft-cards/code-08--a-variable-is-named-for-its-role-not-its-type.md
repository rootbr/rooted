# A variable is named for its role, and its name does not repeat a type that its declaration states or a static type checker knows

## Thesis
Where the type of a variable, parameter or field is stated at its declaration — by a declared type, an annotation, or an initializer that shows it — or is known to the language's static type checker, the name says what the value is for (greeting, supplier, users) and restates none of that type. It carries no type prefix in the Hungarian manner (strName, szBuf, dwFlags, bEnabled), no word that repeats the declared built-in, primitive or collection type (nameString, usersInt, userSlice, id_to_name_dict), and it is not the bare name of such a type (a variable named string or number). A type-like qualifier stays in two cases: two representations of one value share the scope, such as the text read from input and the number parsed from it (ageString beside age), and the type word is needed to avoid ambiguity between names.

## Rationale
A name is read at every use, so each word in it earns its place only by telling the reader something the code does not already say. The type is already said: the declaration or annotation states it, a static type checker knows it and checks every use against it, and in most cases how the value is used shows the reader what type it has. A type word therefore adds nothing salient at the use site, makes the name either verbose or cryptic, and takes the place of the word that would say why the value exists — which of two strings is the greeting and which the name. The type word is also a second, unchecked copy of the type. When the type changes, a list becoming a set or a string becoming a parsed number, the checker verifies the new type but not the name, so either every use of the name changes along with the type or the name goes stale and misleads the way an outdated comment does. Naming the value for its role removes the copy: the name stays true when the representation changes and carries the information the type cannot. The two qualifiers survive because there the type is the salient difference: when a raw and a parsed version of one value share a scope, the representation is what tells them apart, and a type word that resolves an ambiguity is information rather than repetition.

## Example
```typescript
bad:  function greet(strName: string, userArray: User[]): string {
        const string = `Hello, ${strName}`;
        return `${string} and ${userArray.length} others`;
      }
good: function greet(name: string, guests: User[]): string {
        const greeting = `Hello, ${name}`;
        return `${greeting} and ${guests.length} others`;
      }
```

## Limits
Whether a type belongs in a name is contested, and one condition separates the cases: whether a declaration, an annotation, an initializer or the language's static type checker already carries the type. Where one of them carries it, the guidelines that reject type encoding call it generally unnecessary and actively harmful in a strongly statically typed language, because the encoded types get out of date and rot like comments; they ask that names not be decorated with information that is included in the type, since the compiler always knows the type of a variable; the rule holds there. Where nothing carries it — an unannotated parameter in a dynamically typed language — naming an argument so that it reveals its expected type (aString, anInt) is a common, deliberate practice adopted to compensate in part for the missing static type information, developers use it frequently, and a type-inference heuristic that reads these hints inferred correct types for 81% more method arguments in one prototype; the guideline that rejects type encoding notes the technique's use in untyped languages and aims its objection at statically typed ones. Such a name is outside the rule. A prefix or suffix that marks what a value means or where it lives rather than its type — cnt for a count, p for an indirection, m_ for a member — encodes no type information and is outside the rule. A decoration the project documents and applies consistently, such as a suffix marking an observable stream, is a documented project tolerance and rejects the finding. The rule reaches the names of variables, parameters and fields that the change declares: a routine that converts to or parses into a type is named for that type because the type is its purpose (a conversion to a 64-bit integer named for its target type), and a name fixed from outside the change — an overriding routine's parameter, a field an external format or generated code dictates — is outside it. A name that is a domain type's own noun (a user of type User, users for a list of User) names the concept the value stands for and is outside the check; where the scope gives the value a narrower role, such as a factory that serves as the supplier, the role word reads better, and that choice rests with the author. Where a value has no meaning beyond its type and its type is unimportant, a common name such as value or item replaces the bare type name.

## Validator
Grep the added lines for a type prefix in the Hungarian manner (str, sz, lp, dw, arr, obj, int, bool, or a lone b, f or i before a capitalized word), a type word joined to a name as a suffix or as an underscore-separated word (String, List, Array, Dict, Map, Set, Slice, Int, Bool, Obj), and a declaration whose whole name is a built-in type name. For each match keep only a name the added line declares — a variable, constant, parameter or field — and set aside a routine name, a call, and a name the line only reads. Read in the hunk whether the declaration, an annotation or the initializer states the type, or whether the file's language checks types statically; where neither holds, set the name aside. Confirm that the word restates that type rather than a meaning such as a count, an indirection or a member marker; that no second representation of the same value shares its scope, declared beside it in the hunk or read in its initializer; that the word resolves no ambiguity between two names in scope; and that neither the project context documents the decoration nor an inherited declaration, an external format or generated code fixes the name. Validator question: **Where the type of a variable, parameter or field is carried by a declared type, an annotation, an initializer that shows it or the language's static type checker, does an added declaration give it a type prefix, a word restating that built-in, primitive or collection type, or a bare built-in type name, where the word tells apart no second representation of the value, resolves no ambiguity, and nothing outside the change fixes the name?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-08`, severity suggestion, `file`, `symbol`, `code` = the added declaration line carrying the type-encoded name, verbatim from the diff, `fix` = the declaration and its uses in the hunk renamed to the word for the value's role, in the file's language, `rationale` = the type prefix or type word, the declaration, annotation or checker that already states that type, and the role the new name names).
