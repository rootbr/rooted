# An untrusted value written into HTML, script, style, a URL or a header goes through the template engine's contextual escaping or an encoder for that context at the point of output, never through a raw-markup escape hatch without an HTML sanitizer

## Thesis
An untrusted value (a request parameter, header or cookie, or stored user content) that the code writes into an HTML element, an HTML attribute, a script, a style sheet, a URL or an HTTP header passes through the template engine's automatic, context-aware escaping, or, where no engine is used or the engine leaves a gap, through an output encoding library's encoder for the context required, applied as the final step before the interpreter that reads the output; a text sink on an ordinary element that never parses its value as markup (a text node, a text property, a form value, or an attribute set by a fixed name from the safe-attribute list such as title, alt or class) takes the original value without an encoder; a raw-markup escape hatch receives only markup from a completely trusted source or untrusted markup that a well-known HTML sanitization library or framework feature has sanitized.

## Rationale
Injection is untrusted data interpreted according to the syntax rules of the interpreter that receives it, so a variable meant to be shown as text is interpreted as code. Browsers parse HTML, script, URLs and style sheets differently, so there are many different output encoding methods; script encoding and HTML encoding are not interchangeable, and the wrong method may introduce weaknesses or harm the functionality of the application. Encoding belongs as close as possible to where the data is rendered: a filter applied to every request cannot tell whether a parameter will be rendered between tags, inside a script or in an event-handler attribute, and it often misses tainted input such as request headers. Stored data stays in its original state, not in an encoded or escaped form, to prevent double encoding. A templating engine with contextual autoescaping treats data values as plain text and encodes each for the HTML, script, style or URI context where it appears, and applications built with modern web frameworks have fewer cross-site scripting bugs because the frameworks template and auto-escape. The protection holds only when it is on: some engines ship with autoescaping disabled and recommend that the calling code configure it, and a plain-text template package writes a script tag in the data into the page unchanged; the HTML-mode package of such a pair is the one to use whenever the output is HTML. Escape hatches skip the engine: methods that wrap a string as trusted content do not auto-escape it, and direct assignment of markup to the document is probably the most common vector for cross-site scripting, where potentially unsafe strings from a user reach the document without first being sanitized.

## Example
```python
bad:  env = Environment(loader=loader, autoescape=False)
      def comment_html(text):
          return Markup("<p>" + text + "</p>")
good: env = Environment(loader=loader, autoescape=select_autoescape())
      def comment_html(text):
          return Markup("<p>%s</p>") % text
```

## Limits
A raw-markup escape hatch is correct for markup from a completely trusted source, such as a template the developer wrote; the contextual-escaping security model likewise assumes that template authors are trusted and the data passed to the template is not. A text sink treats the value as text and never executes it, so it takes the original text without pre-encoding; it is safe only on an ordinary element, never on a script or style element, and an attribute set by name is safe only when its name is fixed and on the safe-attribute list, never an event-handler attribute or srcdoc. Output that is plain text rather than HTML, such as a text template, takes no HTML escaping; an engine can enable and disable autoescaping per template, HTML versus text. Output encoding is not perfect: a value placed directly in a script, inside an HTML comment, directly in a style block, or as an attribute or tag name is not fully protected even with output encoding, so the value stays out of those positions. An encoder for a URL component or an attribute does not validate a complete URL, and a framework that blocks script-scheme URLs does not replace application-specific URL validation, such as allowing only http and https URLs. A filter applied to all input can succeed for very specific applications, for instance when every input that is ever rendered is validated to be only alphanumeric. No single technique solves cross-site scripting, and a combination of defensive techniques is needed; this rule covers output encoding and sanitization, and the rest of that combination, with authentication, authorization and cryptographic design, sits with the security specialty.

## Validator
Grep the hunk's added lines for direct markup assignment, raw-HTML properties and directives, trusted-content wrappers and 'safe' filters, autoescaping switched off in an engine's settings or a template tag, a plain-text template package, and markup built by concatenation or interpolation, including a template value inside an event-handler attribute. For each hit, open the hunk and trace the value that reaches the output back to its origin: a request parameter, header, cookie, stored user content or another external value is untrusted; a literal, a constant or a template the developer wrote is trusted. Check what stands between an untrusted value and the output: a text sink on an ordinary element that receives the value as text, the engine's autoescaping in HTML mode at a position that engine escapes for (an engine whose escaping is HTML-only covers element text and ordinary quoted attributes, not a script, a style, a URL component or an event-handler attribute), an encoder whose context matches the position (element text, attribute, quoted script string, style value, URL component, header), or, for markup that must render as markup, a call into an HTML sanitization library. In string-built output, count a value placed directly in a script, an HTML comment, a style block, or an attribute or tag name as unprotected whatever encoder it passed, and a value inside an event-handler attribute as unprotected by an attribute encoder alone. Validator question: **Does an untrusted value reach HTML, script, style, URL or header output in this hunk through an unsanitized escape hatch, an engine whose escaping is off or does not cover the value's position, or string-built output with no encoder, an encoder for a different context, or a position no encoder protects?** Yes → flag.
