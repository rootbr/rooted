# An argument named like one of the callee's parameters is passed at that parameter's position, or carries a comment naming the parameter it fills

## Thesis
At a call site, the named arguments, those written as an identifier or a field selection, stand in an order that no reordering of them would pair more closely with the callee's parameter names: an argument whose name matches one of the parameter names is passed at that parameter's position, unless another argument of the same name is passed there. A name matches a parameter when it equals the parameter's name, ignoring case and word-separator style, or when it is clearly closer to that parameter's name, in spelling or in meaning, than to the name of the parameter at its own position. Where the order is deliberate, as when a height is passed for a width to rotate an image, each moved argument carries a comment at the call naming the parameter it fills. A comment written at an argument as a parameter name followed by an equals sign names the parameter at that argument's position.

## Rationale
Identifier names are often used to convey meaning over and above the semantics of the language itself, and a call whose argument names match the callee's parameter names reads more clearly. When the names match but are passed in a different order, the mismatch indicates a mistake in the order that will likely lead to unexpected results: the operation succeeds but its result is unexpected, as when the variable holding the dividend is passed as the divisor. In a statically typed language the mistake occurs for routines that accept several arguments of the same type; in a dynamically typed one every call that passes two or more arguments is susceptible, for lack of static type checking. Comparing argument names with parameter names finds such defects in real code: run over 200 million lines of internal code and 10 million lines of predominantly open-source external code, a checker for argument selection defects, in which the wrong argument is chosen for a call, found defects even in large, mature projects, with a true positive rate of 85% at higher thresholds (459 true and 78 false positives) and 2,060 true against 1,207 false positives at lower ones. A learned detector of swapped arguments, applied to 50,000 files of a dynamically typed language, yielded 23 bugs and 27 false positives among the 50 warnings it ranked most likely; one bug called a function that expects an error followed by a result with the two the other way around. Closeness is judged in spelling or in meaning: one checker converts names to one case and word-separator style, scores each argument against each parameter by an edit distance normalized between 0 and 1, and reports a reordering only when it lowers the total distance by at least 0.6 for each argument it moves, leaving the arguments alone when it is not sure; the learned detector also pairs names that are close only in meaning, such as width with x_dim and height with y_dim. The edit-distance checker's documentation suggests a comment at a deliberate swap to make it clear to future readers, a comment containing the parameter's name stops it from reporting that argument, and its semantics-preserving fix adds such comments to the potentially swapped arguments. A second check compares a comment written as a parameter name followed by an equals sign with the parameter at its argument's position, and reports one that does not match.

## Example
```go
bad:  func resize(img Image, width, height int) Image { ... }
      thumb := resize(img, height, width)
      turned := resize(img,
          /* height= */ height,
          /* width= */ width)
good: func resize(img Image, width, height int) Image { ... }
      thumb := resize(img, width, height)
      turned := resize(img,
          height, // width: a quarter turn
          width)  // height
```

## Limits
An argument bound by name at the call rather than by position, such as a field of an options record, is outside the rule: the call writes each field beside its value, which makes the binding self-documenting and harder to swap. An argument with no name, such as a literal or an arithmetic expression, gives nothing to compare for order, and the order check weighs only the named arguments around it; a field selection is named by the field it selects, and a parameter-name comment at any argument, a literal included, still names the parameter at its position. A parameter named with a low-information word — key, value, label, a one- or two-letter lower-case name optionally followed by digits, or arg, param or str followed by a digit — is used in so many contexts that a near match to it has no reliable similarity score, and one checker leaves such parameters out; for such a parameter only an argument whose name equals it exactly counts as a match, the case that checkers comparing exact names report. In a routine or type whose name contains a word about reversing things — backward, complement, endian, flip, inverse, invert, landscape, opposite, portrait, reciprocal, reverse, rotate, rotation, swap, transpose, undo, or a form of these — swapping the arguments is expected, and one checker does not report a call there. When a reordering would put an argument at a position where another call to the same callee in the same routine already passes that argument, or, in a recursive call, where the routine's own declaration already has a parameter of that name, the same checker does not report the call. How many parameters a routine takes, and whether distinct parameter types should make a swap fail to compile, are judged by their own rules.

## Validator
Grep the added lines for a call that passes two named arguments in the reverse of a usual pair — height before width, y before x, end before start, max before min, last before first, value before key, new before old, and their compound forms, or a destination and a source in either order, since copy routines take them both ways — and for a parameter-name comment at an argument; in the matched hunk, take as well any other call that passes two or more named arguments. For each call, find the callee's declaration in the file, across the repository, or in the standard library or dependency that declares it, and list its parameter names in order; skip a call whose callee's parameter names cannot be found. Compare each named argument with every parameter name, ignoring case and word separators, and ask whether a reordering of the named arguments would pair them more closely with the parameters: an exact name in another position, or a name that shares another parameter's distinctive word or meaning rather than its own parameter's. Skip an argument bound by name, an unnamed argument, a near but inexact match to a parameter with a low-information name, a call inside a routine or type whose name is about reversing things, a reordering that would put an argument where another call to the same callee in the same routine, or the routine's own declaration in a recursive call, already has it, and a moved argument whose adjacent comment names the parameter it fills. For each parameter-name comment, check that it names the parameter at its argument's position. Validator question: **Does an added call pass named arguments in an order that a reordering would pair more closely with the callee's parameter names, without a comment at each moved argument naming the parameter it fills, or carry a parameter-name comment that names a parameter other than the one at its position?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-14`, severity major, `file`, `symbol`, `code` = the call quoted verbatim from the diff, `fix` = the call with its arguments in the order of the callee's parameters, or, where the order is deliberate, each moved argument with a comment naming the parameter it fills, or a parameter-name comment rewritten to name the parameter at its position, in the file's language, `rationale` = which argument names match which parameters and the position each argument fills instead, or which parameter a parameter-name comment names and which parameter sits at its position).
