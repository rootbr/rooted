# A routine that acquires a resource releases it before it returns, unless it hands the resource on to its caller, to an object that owns it or to a routine that takes over its release

## Thesis
A routine that opens a file, a socket, a connection or a stream, obtains a database statement or result set, creates a temporary file or directory, or obtains a cancellation function releases that resource itself before it returns: it closes the file, socket, connection, statement, result set or stream, removes the temporary file or directory, and calls the cancellation function. The exception is a hand-off: the routine returns the resource, alone or inside a returned object, stores it in an object that owns it and releases it, or passes it to a routine that takes over its release, as that routine's documentation or body shows. A resource released nowhere breaks the rule — a stream opened and read inline, a discarded cancellation function, a temporary file or directory never removed, a value whose destructor is deliberately skipped while no new owner holds its handle — and so does one released only if a finalizer, or some other part of the program with no stated responsibility for it, happens to run later.

## Rationale
A garbage collector reclaims memory, but it does not free a non-memory resource such as an open file descriptor or a database connection when the program stops using it, and failing to release such resources when they are no longer needed can result in resource exhaustion. Under a traditional garbage collector an unreferenced file object is collected, and closed, only at varying and possibly long intervals, so a loop that opens a file on each pass and never closes it will probably run out of file descriptors there, while a reference-counting runtime closes the previous file as each new assignment drops it, and an explicit release works regardless of the memory-management scheme. Many database servers allow only a fixed number of connections, so failing to release connections can exhaust them rapidly. Calling a cancellation function releases the resources of its context — it removes the parent's reference to the child and stops any associated timers — and failing to call it leaks the child context until the parent is cancelled; a background parent is never cancelled. Removing a temporary file once it is no longer required lets its name and its storage be recycled. Data written to an output file that is never closed may not be completely written to the disk, even when the program exits successfully. Skipping a value's destructor prevents its cleanup from running, possibly causing leaks. Where the release is code the programmer has to call for every instance of a file handle or a socket and the programmer forgets it, the system might become overloaded and crash. A program may also leak resources when it relies on finalizers to release them, or when there is confusion over which part of the program is responsible for releasing them; the rule names that part — the acquiring routine, or the owner it hands the resource to. A tool rule checks a similar shape with a looser hand-off: a routine that creates a stream, does not store it in a field, pass it to a routine that might close it or return it, and does not close it on every path out of the routine is reported because this may result in a file descriptor leak.

## Example
```python
bad:  def first_line(path):
          stream = open(path)
          return stream.readline()
good: def first_line(path):
          with open(path) as stream:
              return stream.readline()
```

## Limits
An object that implements the closing interface but holds no operating-system resource — a stream backed by a collection, an array or a generating function — needs no release; a stream whose source is an input-output channel does. A wrapper the routine builds around a resource it received from its caller or from the runtime, such as a reader over a caller's socket stream or over the standard input, needs no release by the routine, since the resource comes from somewhere that keeps the responsibility to close it. A stream documented to close its own handle when it ends or fails is released by reading it to its end, or by an iteration over it that destroys it on an early exit, in the routine or in a routine it is handed to; one the routine leaves part-read is released nowhere. A shared resource the program opens once and keeps, such as a connection pool that maintains its own idle connections, rarely needs closing and falls outside the rule, while a connection a routine borrows from the pool is returned to it after use. A value whose type has cleanup code that the compiler inserts to run whenever the value goes out of scope is released at the end of its owning scope with no further call; a call that consumes such a value and yields its raw handle typically makes the caller the handle's unique owner, which then closes it once it is no longer needed. An object that the runtime's reference count or garbage collector closes once nothing refers to it does not count as released by its scope, since under a traditional collector the same object is closed only at varying and possibly long intervals. No method guarantees the removal of a temporary file orphaned by abnormal termination, not even a release block that runs when the routine returns or an error leaves it, since abnormal termination may keep that block from executing; such a file is outside the rule. Whether the release also runs when an error leaves the routine early, and the order in which several resources are released, are judged by their own rules.

## Validator
Grep the added lines for an acquisition: an open, a connect or a dial, a request whose response carries a body stream, the construction of a stream, reader, writer, socket or channel, a database connection, statement or result set, a temporary file or directory, a context call that returns a cancellation function, and a call that skips a destructor or yields a raw handle. Open the file and find the routine that encloses each hit. Skip an object that holds no operating-system resource, such as a stream over an in-memory collection, a wrapper around a resource the routine received from its caller or from the runtime, and a shared resource the program opens once and keeps, such as a connection pool; a connection borrowed from that pool is still in scope. Trace the acquired value through the routine. It passes when the routine releases it — a close, remove or cancellation call, an acquisition inside the language's scoped-release construct, an owned value whose type has cleanup code the compiler runs when its scope ends, or a stream documented to close its own handle at its end, read to that end or iterated by a construct that destroys it on an early exit, never an object left for the runtime's reference count or garbage collector to close — or when it leaves the routine as a hand-off: returned alone or inside a returned object, assigned to a field of an object whose own release releases it, or passed to a routine whose documentation or body takes over its release. A value discarded at the call, left in a local that goes out of scope unreleased, stored where only an unrelated routine might release it later, or stripped of its destructor with no new owner for its handle is released nowhere. Validator question: **Does an added line acquire a file, socket, connection, database statement or result set, stream, temporary file or directory, or cancellation function, or skip the destructor of a value holding one, in a routine that neither releases it before returning nor returns it, stores it in an object that owns it or passes it to a routine that takes over its release?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-19`, severity major, `file`, `symbol`, `code` = the acquiring line quoted verbatim from the diff, `fix` = the acquisition inside the language's scoped-release construct or followed by its release before the routine returns, or the resource returned or stored in an object that owns and releases it, in the file's language, `rationale` = which resource is left unreleased and what it holds until something else frees it — a file descriptor, a pooled connection, a live context, disk space).
