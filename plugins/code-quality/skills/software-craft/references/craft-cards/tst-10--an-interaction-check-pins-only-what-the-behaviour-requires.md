# An interaction check pins only the calls, arguments, counts and order that the behaviour under test requires and asserts that no other call happened only when the absence of other calls is that behaviour

## Thesis
When a test verifies how the code under test called a test double, it checks the minimum that the behaviour under test requires: the call that carries the behaviour, the arguments that behaviour determines, and a match-anything placeholder for every other argument. It checks how many times a call happened only when a different number of calls would make the code behave wrongly, and in which order calls happened only when a different order would. It checks that no other call reached the double only when the absence of other calls is itself the behaviour under test, and it names the one forbidden call wherever the behaviour forbids that call rather than every call. A call the behaviour under test does not depend on stays unverified; a test that would check several behaviours through one double's calls becomes one test per behaviour, each pinning what its own behaviour needs.

## Rationale
A test is meant to fail when a requirement breaks. Each argument, call, count, order or absence of other calls that a check pins beyond the behaviour under test is a claim about the implementation instead, so a change that keeps the behaviour — another value for an incidental argument, a new call to the same collaborator, one call split in two, two independent calls swapped — fails the test. Such tests are brittle: they are over-specified to check artefacts of the implementation rather than requirements, and a suite with many of them slows development and inhibits refactoring. The remedy is to re-examine the code and either weaken the check to what the requirement states or change an object structure that forces incidental detail into the test. The exact order of calls is often irrelevant and may change over time; a double that rejects every call the test did not declare enforces rigour but can make the test fail with every other internal code change; and a check that no further interactions happened, written into every test, yields over-specified, less maintainable tests. The coupling shows in maintenance: in a manual analysis of more than 300 changes to calls of a mocking library's API in four systems, 51% (172) were induced by production code — a change to the doubled type's interface or to how a method works internally — and 49% (164) by improvements to the test itself. The minimum still includes the relevant arguments: a check that a call happened, without its arguments, is weaker than one that validates them, and a placeholder for an argument that does not matter still fixes the number and position of the arguments. One test per behaviour keeps each failure pointing at the behaviour that broke, where one long test that checks several behaviours through the same double fails for a change to any of them. The rule restores the property that a test's failures track the behaviour it names rather than the implementation that currently provides it.

## Example
```python
bad:  def test_greeting_shows_name(greeter, prompt):
```

## Limits
A count or an order is the behaviour when the code exists to control it: a cache that reads its store at most once, a retry that stops after a set number of attempts, a charge or a message sent exactly once, a lock taken before the write it guards, events a consumer needs in sequence; pinning that count or order meets the rule. An absence of other calls is the behaviour on a path whose requirement is that a collaborator stays untouched — a dry run, a rejected input that reaches no store, a read-only query; a check that the one forbidden call never happened states it more precisely than a check that no call happened, unless every call is forbidden. The single call that a plain verification implies by default, or a called-once assertion on a call the behaviour makes once, is the ordinary shape of a verification and is no finding by itself. Where a framework's doubles reject every undeclared call by default, that strictness is the framework's rather than the test's claim; the rule then reads the declared expectations, and an incidental call declared as allowed any number of times with any arguments meets it. A project whose stated testing convention is strict interaction checking in every test sets a tolerance that rejects the finding. The rule reads interaction checks on doubles only: whether a test should check interactions at all rather than returned values or resulting state, how its other assertions are worded and how it is named are outside it.

## Validator
Grep the hunk's added lines for interaction checks: a verification or called-with assertion, an explicit call count, an in-order or sequence check, an equality or subsequence check on a double's recorded call list, and a check that no other call or no call at all happened. Open the test file and, for each test that holds such a check, name the behaviour under test from the test's name, its arrange and act steps and its assertions on results or state. Take each pinned element in turn — each verified call, each literal argument, each count other than the default single call, each order constraint, each whole-list or no-other-calls check — and ask whether a change to the code under test that keeps that behaviour (another value for an incidental argument, one more call to an incidental method, another order of independent calls, a new call to the same double) would fail it. Skip a count or an order the behaviour depends on (a cache, a retry limit, an exactly-once side effect, a required sequence), a no-other-calls check on a path whose behaviour is that the double stays unused, and an incidental call that a strict double declares as allowed any number of times. Validator question: **Does an added interaction check pin a call, an argument, a count, an order or the absence of other calls that the behaviour under test does not require, so that a change keeping that behaviour would fail the test?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-10`, severity minor, `file`, `symbol`, `code` = the added interaction-check line that pins the incidental call, argument, count, order or absence of other calls, verbatim from the diff, `fix` = the check reduced to the relevant call with match-anything placeholders for incidental arguments, the count, order or no-other-calls check removed or replaced by a check that the one forbidden call never happened, or the incidental check moved to a test of its own behaviour, in the file's language, `rationale` = the behaviour the test names, the pinned detail that behaviour does not require, and a behaviour-preserving change that would fail the check).
