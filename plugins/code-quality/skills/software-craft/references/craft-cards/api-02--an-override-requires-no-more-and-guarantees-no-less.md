# An overriding or implementing method requires no more of its callers and guarantees no less than the method it replaces

## Thesis
A method that overrides a base-class method or implements an interface or trait method accepts every call the replaced method's contract accepts and delivers everything that contract promises. It adds no check that rejects an argument or an object state the supertype's contract allows, narrows no parameter type, and stays callable with every argument list the supertype's signature accepts, each argument bound to the parameter the supertype binds it to: it adds no required parameter, removes no default value and reorders no positional parameter, and, where a call that passes an argument the method does not declare fails, it removes no parameter, even one with a default value. It returns no value the supertype's contract rules out, such as a null where the supertype promises a non-null value, and raises no failure the supertype's contract does not announce. It keeps every invariant of the supertype. It may accept more, through a more general parameter type, an added optional parameter or a weaker precondition, and promise more, through a narrower return type or a stronger postcondition.

## Rationale
Client code is written against the supertype, and an instance of any subtype may be passed to it and treated as an instance of the supertype. When an override strengthens a precondition, for example by adding a parameter constraint, client code that works correctly against the supertype can fail against the subtype, and a call that passes an argument type the override does not accept can crash at run time; the same substitution breaks when an override weakens a postcondition, for example by returning a null where the supertype promises a non-null value. An override that requires a new parameter or removes a default fails or misbehaves on a call that omits that argument, one that removes a parameter rejects a call that passes it wherever a call may not pass an argument the method does not declare, and one that reorders positional parameters binds a positional argument to a different parameter. A weaker precondition and a stronger postcondition carry no such risk: client code written against the supertype still works against the subtype, so a subtype that only accepts more and promises more replaces its supertype with no fear of breaking existing code. The subtype relation should ensure that any property proved about supertype objects also holds for subtype objects, and a class's invariants include all the invariants of its supertypes. Potential violations are numerous in practice: in a study of the 200 most popular open-source projects of one package repository, which compared the contracts of methods in an override relationship, 1,368 pairs were classified as a strengthened precondition, 37 as a weakened precondition, 343 as unchanged and none as a weakened or strengthened postcondition. Among them were an override that throws when an offset argument is negative where the base method throws no run-time exception and its documentation warns of none, and an override of a plain setter that throws an unsupported-operation error with no indication in the supertype that a subtype might not support it. The classification is mechanical: it flags possible problems without weighing their actual impact, it under-approximates them because some inheritance relationships were missed, and it under-counts postconditions because it does not classify assertions.

## Example
```rust
bad:  impl Cache for Disk { // trait Cache: get takes any key, None when nothing is stored
          fn get(&self, key: &str) -> Option<Bytes> {
              assert!(key.len() <= 255, "key too long"); // rejects a key the trait allows
              self.read(key)
          } }
good: impl Cache for Disk {
          fn get(&self, key: &str) -> Option<Bytes> {
              self.read(&file_name(key)) // file_name hashes a key too long for a file name
          } }
```

## Limits
The supertype's contract is what the supertype states: its signature, its declared parameter and return-value constraints and its documentation. An exception that the supertype's documentation warns may be thrown in overriding methods is part of that contract, and an override that throws it adds no precondition. A check in an override that makes explicit a precondition the supertype already has adds none either; it can change which error type reports a violation, a change that could break a caller but is unlikely to. A constructor is outside the rule, whether or not the language treats a subtype's constructor as overriding its supertype's, so constraints on the parameters of a subtype's constructor are outside the rule. Renaming a parameter breaks only a caller that passes it by name; where every call passes it by position, renaming it for readability is common and tolerated. Where a call may pass more arguments than the method declares, an override that drops a trailing parameter stays callable with the supertype's arguments, and dropping it is a finding only when the supertype's contract gives that argument an effect the override no longer delivers. Substituting a new version of a method for its old version is a different substitution from a subtype for its supertype, so a change to one method's own contract between versions is outside the rule.

## Validator
Grep the added lines for an override marker (an override annotation, decorator or keyword), a trait or interface implementation header, a class declaration that extends or implements a supertype, a compile-time assertion that a type satisfies an interface, a call through super, a throw, raise, panic, assertion, precondition-check call, error return or null return, a nullability or validation annotation, and an instance-method definition; keep a line of the last three kinds only when the file shows that its enclosing method, or the method it defines, overrides or implements a supertype method. For each overriding or implementing method the diff adds or changes, open the file, name the supertype, and open the supertype's declaration in the repository (`git grep` the supertype's name and the method's name); read the replaced method's signature, its declared constraints (nullability or validation annotations, type hints), its documentation and, where the supertype has a body, its checks. Where the supertype is declared outside the repository and nothing in the diff or the file states its contract on the point in question, do not flag. Compare the override with it: each check in the override's body that throws, panics, asserts or returns an error for an argument or an object state, and each parameter of its signature, against what the supertype accepts; each value the override can return and each failure it can raise against what the supertype promises; and each field the override writes against the supertype's invariants. A compiler or type checker that accepts the override has checked at most its signature, and one widely used checker accepts a narrowed parameter type in a member declared with method syntax, so read the body even when the build passes. A check that restates a precondition the supertype already has, an exception the supertype's documentation warns may be thrown in overriding methods, a constructor, a parameter renamed where every call passes it by position, and a trailing parameter dropped where a call may pass an argument the method does not declare and the supertype's contract gives that argument no effect the override fails to deliver are not findings. Validator question: **Does an added or changed overriding or implementing method reject an argument or object state that the supertype's contract accepts, narrow, remove, reorder or newly require a parameter, return a value that contract rules out, raise a failure that contract does not announce, or leave the object breaking an invariant of the supertype?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-02`, severity major, `file`, `symbol`, `code` = the override's added check, signature line, return statement or field write that narrows the supertype's contract, verbatim from the diff, `fix` = the override accepting every argument and state the supertype accepts and returning only what the supertype promises — the check removed or the case handled within the contract, the parameter type and parameter list restored, the invariant kept — or, where the subtype cannot keep the contract, the subtype relation replaced by a type of its own, in the file's language, `rationale` = the term of the supertype's contract the override breaks, quoted from its signature, constraint or documentation, and the call written against the supertype that now fails).
