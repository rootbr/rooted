# A method that calls methods of one other project class three or more times and uses that class more than its own is moved to that class, unless the class is a library, ancestor, nested or enclosing class or a passive data carrier

## Thesis
A method that calls methods of one other project class three or more times, and uses more features of that class, fields or methods, than of its own class, is moved to that class, whole or as the chain of calls it makes, since such a method often has its functionality located in the wrong class. The count covers project classes with behaviour of their own; calls to library classes, to ancestors of the method's class or of a class enclosing it at any depth of the inheritance chain, and to classes nested in the method's class or enclosing it stay out of it, and so do uses of a passive data carrier whose state is public, through public fields or plain accessors, and that keeps no invariant.

## Rationale
A method that calls another class's methods three or more times is often an indication that this functionality is located in the wrong class. When the method uses more features of the other class than of its own, it is more tightly coupled to the other class than to the one where it is currently located. Moving that chain of calls to the called class itself is the better form. Developers confirm the smell as other detectors find it, not this count: eighty developers evaluated a topic-model recommender's move-method recommendations that remove feature envy, with results indicating the recommendations are accurate and meaningful, and 12 developers of four open source projects recognized more than 75 percent of the instances of five smells, feature envy among them, that a change-history detector identified as actual design or implementation problems. Misplaced methods are also a strong driver of developers' judgement that a class is a god class.

## Example
```go
bad:  func (s *Scheduler) Run(j *Job) {
          j.Start(); j.Process(); j.Finish()
      }
good: func (j *Job) Run() {
          j.Start(); j.Process(); j.Finish()
      }
```

## Limits
The count leaves out calls to library classes, ancestor classes, and classes nested in or enclosing the method's class, and inside the count the pattern is often, not always, a sign of misplaced functionality. A passive data carrier is left out of the count because the sources split on it: a catalog's own example moves a computation onto a frozen data class with three public fields and no methods, while a public field that clients can mutate prevents a type from maintaining any invariant on it, public fields suit compound passive data structures, a record is a transparent carrier for a fixed set of values, and a linter's documentation for a class with one method that prints its own fields shows both a data class plus a free function that reads them and the class kept with that method and a second one. The same linter made its check for methods that do not use their bound instance optional as too opinionated. The separating condition is whether the called class has behaviour of its own, methods beyond the accessors of its fields or an invariant it maintains, or is a passive carrier with public data and no invariant: on the behaviour side the call count is often an indication of misplaced functionality and developers judged a topic-model recommender's moves accurate and meaningful; on the carrier side functions outside the type are one accepted form and the sources do not settle the move, so the rule does not flag it. The rule names a misplacement, not a measured cost: across 395 releases of 30 projects smelly classes were more change- and fault-prone than smell-free ones, while in a study where six hired developers each performed three maintenance tasks on four functionally equivalent systems none of 12 investigated smells was significantly associated with increased effort after adjusting for file size and the number of changes.

## Validator
Grep the hunk for a method whose body calls methods on one parameter, field or local of another type three or more times. Open the file and count, for that method, its uses of the other class's fields and methods against its uses of its own class's fields and methods. Trace the other class to its declaration and leave it out when it is a library class, an ancestor of the method's class or of a class enclosing it at any depth, a class declared inside the method's class or enclosing it (lexical nesting, not a field the class holds), or a passive data carrier whose state is public, through public fields or plain accessors, and that keeps no invariant. Validator question: **Does a method in the hunk call methods of one other project class with behaviour of its own three or more times while using more features of that class than of its own?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-06`, severity minor, `file`, `symbol`, `code` = the method's signature and its calls to the other class, verbatim from the diff, `fix` = the method or its chain of calls moved onto the called class and invoked from the original site, in the file's language, `rationale` = the called class, the number of calls to its methods, the number of uses of its fields and methods, and the number of uses of the method's own class's fields and methods).
