# Research note — Inheritance versus composition

Topic `inheritance-versus-composition` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'Inheritance Tax' (The Pragmatic Programmer, 20th anniversary ed., topic 31, ch. 5 'Bend, or Break': interfaces and protocols, delegation, mixins and traits as the alternatives to inheritance); CC6 (Code Complete 2nd ed. ch. 6 'Working Classes': containment ('has a') and inheritance ('is a') relationships).

The canon (PP Topic 31 'Inheritance Tax' and Code Complete ch. 6, with Effective Java Items 18-20 and 40, GoF ch. 1, APOSD 19.1, POODR, Riel and Fowler as further formulations) agrees on three points. Implementation inheritance ties a subclass to its ancestors' implementation. It belongs to true subtypes. Containment, delegation or an interface serves otherwise. The canon disagrees in four places. (1) How strong the default against inheritance is: PP, GoF and POODR say composition first, Fowler says inheritance first. (2) Whether to close classes: Bloch, Kotlin, Swift SE-0117 and PEP 591 say close them; the .NET guidelines and C++ Core Guidelines C.139 say leave them open. (3) Where to cap depth: Riel says six, McConnell says fewer, tools use 5 to 7. (4) Whether to use mixins: PP and the TypeScript handbook say yes; Google's TypeScript guide and Rhodes say no. The openable evidence is mostly official documentation and tool rules. It covers: override markers (Error Prone, noImplicitOverride, PEP 698, mypy); overridable calls from constructors (PMD, Sonar S1699, CA2214, SpotBugs MC, the TypeScript initialization order); and the self-use mechanism behind the fragile base class (SE-0117, the JDK @implSpec docs, the Python tutorial, Ruff FURB189, Bloch's public InstrumentedHashSet). It also covers the platform's own admissions of subclasses that cannot stand in for their base (Timestamp, Properties) and the official Go and Rust accounts of embedding and Deref. Research is thin and mixed. Palomba et al. 2018 tie Refused Bequest to change-proneness, with only a limited effect on faults. The depth studies conflict (Daly against Cartwright; Prechelt and Giordano against El Emam and Jabangwe), and Microsoft's DIT page states that no depth threshold has empirical support, so the depth rule stays pending. The general preference for composition needs human judgment, so it is held to feed the Rationale of the checkable cards. Result: eight cards, six pending rules, one held principle and five folded rules.

Not opened: the books' own publisher pages, PP errata, Fowler's bliki and the papers cited inside the canon (Snyder 1986; Liskov and Wing 1994), which belong to the evidence layer. ## Reception layer

The reception layer agrees on the direction of the rules: prefer composition, interfaces or delegation for code reuse; mark every override; never call overridable methods from a constructor. Java and Python tools check these mechanically (Error Prone, PMD, SpotBugs, Sonar, Checkstyle, Pylint, mypy, pyright), and TypeScript has the opt-in noImplicitOverride. The sources disagree in four places. (1) Whether a class should be closed by default: Bloch through Checkstyle DesignForExtension, Kotlin, Swift SE-0117, Scala 3, Dart 3 and PEP 591 say close it; the .NET Framework Design Guidelines, C++ Core Guidelines C.139 and Kotlin's all-open plugin for Spring say leave it open. (2) What depth to enforce: Sonar S110 flags depth over 5, CA1501 flags depth of 5 or more, Pylint flags more than 7 ancestors, and the relayed research is mixed (Daly versus Cartwright, Jabangwe). (3) Whether mixins, Go embedding and Rust Deref are safe substitutes: Rhodes, the Google TypeScript guide, the Uber Go guide and the Rust API guidelines say no; the TypeScript handbook, Effective Go and the std Deref docs present them as usable. (4) Two pairs of tools contradict each other: Error Prone EqualsGetClass against Sonar S2160 on subclasses that add fields to value types, and Ruff FURB189 against the Python collections docs on subclassing dict. Software Engineering at Google records that 'Composition is often more appropriate than inheritance' needs human judgment, so the tools check only proxies: depth, override marking, constructors and final. Five snippets confirm the claims the cards would rest on (Bloch's InstrumentedHashSet counts 6 insertions for 3; a dict subclass's update bypasses __setitem__; --strict does not enable noImplicitOverride; Go embedding does not dispatch to the outer type; Rust default trait methods dispatch to the impl). The layer could not open any Hacker News or Lobsters thread, any practitioner blog (Fowler, Holub), or any 2024–2026 survey, because the WebSearch budget is used up and those hosts are denied; papers were reachable only through the orchestrator's relayed snippets and the neverworkintheory bibliography.

## Evidence layer

The strongest openable evidence on this topic is official documentation and tool rules. The rules most clearly backed are these: mark every override explicitly (Error Prone, TypeScript noImplicitOverride, PEP 698, which cites production outages from silent orphans after a rename, mypy explicit-override); do not call overridable methods from a constructor (PMD, Sonar S1699, CA2214, the TypeScript initialization-order section); a subtype must honour its base type (mypy [override], the TypeScript handbook, and the JDK's own Timestamp and Properties javadoc, which disown their inheritance from Date and Hashtable); and in Go and Rust, embedding and Deref are not subclassing (Effective Go, Uber's Go guide, Rust API guideline C-DEREF, the std Deref docs). Each of these is also reproduced locally (javac 21, CPython 3.11, tsc 6.0, go 1.24, rustc 1.94, mypy 2.4); the local runs are not openable until committed as evals/fixture tests. Empirical research reached only through a GitHub-hosted copy: Palomba et al. EMSE 2018 for Refused Bequest (median change-proneness 43 with the smell vs 26 without; removal helps change-proneness but not fault-proneness); Giordano et al. EMSE 2023 and SANER 2022 for inheritance and delegation in 12 and 3 Java projects; and El Emam et al. TSE 2001, via neverworkintheory, where no CK metric predicted faults after controlling for size. Not opened and kept as unfetched or relayed: Chidamber-Kemerer (its DIT definition is relayed through the Microsoft DIT page), Daly 1996, Cartwright 1998, Prechelt 2003 (only a secondary description in Giordano 2023), Jabangwe 2015, Khomh 2012, Liskov-Wing 1994 and Mikhajlov-Sekerinski 1998. The sonar-python S110 page and the Error Prone ConstructorInvokesOverridable doc answered 404. The canon disagrees in three places. On inheritance depth, tool thresholds (Sonar 5, CA1501 5, Pylint 7, CISQ 7 parents and 10 children) are admitted by Microsoft's own DIT page to have no empirical basis, and the studies conflict (Daly: 3 levels about 20% quicker; Cartwright: slower; El Emam: size explains the effect; Giordano: DIT/NOC correlate with defects and effort). On closing classes, Kotlin's final-by-default, Swift SE-0117, PEP 591 and Checkstyle DesignForExtension are opposed by C++ Core Guideline C.139 and the .NET sealing guideline. On mixins, the TypeScript handbook documents them and the Google TypeScript style guide forbids them.

## Spine — candidate rules in source order

1. **A subclass overrides a method that other methods of its base class call only where the base class documents those calls** — Where a language has implementation inheritance, a base-class method that calls another method on its own instance runs a subclass's override of that method. A subclass that overrides such a method therefore depends on how the base class's methods call one another. When the base class does not document that self-use, a release that changes how its methods delegate to each other breaks the subclass, which often could only have been written by observing the existing behaviour. Two examples: a HashSet subclass that counts in both add and addAll reports 6 insertions for 3, because the inherited addAll calls add; and dict.__init__ and dict.update bypass a Python dict subclass's overridden __setitem__. A subclass overrides such a method only where the base class documents the self-use, as the JDK's skeletal collection classes do in @implSpec. Otherwise it holds an instance of the base type and forwards to it, or it extends a base type built for extension, such as collections.UserDict. In Go, embedding has no dispatch to the outer type: a promoted method runs on the embedded value, so the embedded type's own methods never call an outer method of the same name, and expecting them to is the Go form of the defect.
