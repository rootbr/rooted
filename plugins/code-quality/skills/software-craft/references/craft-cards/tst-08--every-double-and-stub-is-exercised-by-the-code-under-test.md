# Every double and every stub a test configures is exercised by the code under test with the configured arguments

## Thesis
Each test double a test creates and configures reaches the code under test: the test passes it in, directly or inside another object; another double's stub or a patch hands it to the code under test as a return value; the test framework injects it into the object under test; or a patch installs it at the name the code under test looks up, which is not necessarily the name where the replaced object is defined. Each stub the test configures is realized: during the test, the code under test calls the stubbed operation on that double with arguments that match the arguments or matchers the stub specifies. Four cases fail the rule: a stub the code under test never calls, a stub whose arguments never match the call the code under test makes, a double created and configured but never handed to the code under test, and a patch applied to a name the code under test does not look up. A default stub in a fixture's shared setup meets the rule when at least one test of that fixture realizes it.

## Rationale
A stub states part of the scenario a test checks: which call the code under test makes and what that call returns. A stub the code never calls is unnecessary test code, left by an oversight, a copy-paste or a misreading of the test or of the code, and it makes the test harder to read and reason about. Stubs can also become unnecessary as a test suite evolves, and their definitions can then produce unreliable results in later versions of the suite; across 128 projects that stub with one mocking framework, 280 stubbing definitions led to 1,529 unnecessary stubbings. A stub whose arguments differ from those of the call the code makes typically marks a mistake, a typo or a misunderstanding in the test or in the code under test, which one mocking framework's maintainers put at 95% of argument mismatches, the other 5% being deliberate calls with other arguments; the call the code does make gets the double's default answer, or fails, instead of the configured one. A double created and configured but never passed to the code under test is to be removed or used: the code under test runs against whatever it was given instead, and the configured double checks nothing. A patch replaces the object one name points to, and several names can point to the same object: where an import copies the reference into the importing module, that module holds its own reference, so a patch of the name where the object is defined leaves the code under test running the real object while the test appears to have replaced it, and a patch of a shared standard-library original can break the test runner itself. A substitution that the module loader makes for a whole module before the code under test imports it reaches every module that imports it. A study of 2,365 test doubles replacing 784 classes found that doubles can introduce test smells and even mistakes in test code, and the stub never called and the stub called with other arguments are both catalogued test smells. The rule restores the property that every double and every stub in a test is part of the scenario the test exercises.

## Example
```rust
bad:  let mut catalog = MockCatalog::new();
      catalog.expect_price().with(eq(8)).returning(|_| 20);
      let mut audit = MockAudit::new();
      audit.expect_record().return_const(());
      assert_eq!(Cart::new(catalog).total(&[7]), 20);
good: let mut catalog = MockCatalog::new();
      catalog.expect_price().with(eq(7)).returning(|_| 20);
      assert_eq!(Cart::new(catalog).total(&[7]), 20);
```

## Limits
A default stub in a fixture's shared setup or constructor that at least one test of the fixture realizes, while other tests leave it unused, is a documented tolerance; a shared stub that no test of the fixture realizes is a finding. A stub the test explicitly marks as allowed to stay unused (a lenient stub), for the rare case in which the unused-stub check is a false alarm, rejects the finding, as does a tolerance the project context states for a named fixture. Code under test that deliberately calls the stubbed operation with other arguments as well meets the rule as long as the stubbed call also happens. A double the framework injects into the object under test, by annotation or through a dependency-injection container, counts as passed in; an unconfigured placeholder passed only to fill a parameter carries no stub and is no finding. An expectation whose count forbids the call (a never or a times-zero expectation) on a double that reaches the code under test verifies that the code under test does not make that call and is no finding; on a double that never reaches the code under test it verifies nothing and the double is a finding. Where the code under test reaches the name through the defining module rather than binding it in its own, the defining module is the correct patch target. A substitution of a whole module that the module loader makes before the code under test imports it reaches every module that imports it, so the module's own path is the correct target however the code under test binds the names it imports. The rule reads stubs, expectations and patches on added lines of a test: a stub left unnecessary by a change to the code under test alone, with no test line changed, is outside its reach, and whether a test should use a double at all, how many stubs it needs and which interactions it verifies are questions the rule leaves open.

## Validator
Grep the added lines for stub and expectation configuration (a return, throw or answer chained on a stubbed call, a return-value or side-effect assignment, a mock-return or mock-implementation call, an expectation call) and for a patch of a name. For each configured double, find where it goes: into a constructor or a call of the code under test, directly or inside another object; out of another double's stub or a patch as its return value, which reaches the code under test when that stub or patch is realized; into the object under test by framework injection; or into place by a patch. A reference to the double only as the receiver of its own stubbing, expectation or verification call does not count as reaching the code under test. For each stub, open the code under test that the test calls and trace the path the test's inputs take: check that it calls the stubbed operation on that same double, and that the arguments it passes match the stub's arguments or matchers. For each patch, resolve where the code under test looks the name up: when an import copied the reference into the code under test's module, so that rebinding the name where it is defined leaves that module's copy unchanged, the target is that module's name; when the code under test reaches the name through the defining module, the defining module is right; when the module loader substitutes the whole module, the target is the module the code under test imports, directly or through another module. Skip a shared-setup stub that another test of the fixture realizes, a stub marked lenient, and an expectation whose count forbids the call on a double that reaches the code under test; a double the framework injects counts as reaching the code under test, and its stubs are still checked. Validator question: **Does the added test configure a stub that the code under test never calls or calls only with non-matching arguments, create and configure a double that never reaches the code under test, or patch a name other than the one the code under test looks up?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-08`, severity minor, `file`, `symbol`, `code` = the added line that configures the unrealized or mismatched stub, creates the unused double or applies the patch, verbatim from the diff, `fix` = the stub removed or given the arguments the code under test passes, the double passed into the code under test or removed, or the patch moved to the name the code under test looks up, in the file's language, `rationale` = which call the code under test actually makes or which name it actually looks up, and what runs in place of the configured double).
