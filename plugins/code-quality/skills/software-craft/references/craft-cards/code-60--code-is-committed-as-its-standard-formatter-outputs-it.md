# Code is committed as its standard formatter outputs it, and hand layout the formatter would rewrite is kept only under its documented skip directive where the formatted output would lose a structure

## Thesis
Where a formatter governs a file, either one the project configures or runs or one the language's official documentation names as its standard, every added or changed line is committed as that formatter prints it under the project's settings, and layout the formatter would rewrite is not adjusted by hand. When the formatted result reads badly, the program is rearranged, or the output is reported as a formatter bug, rather than worked around. Hand layout that the formatter would rewrite is kept only under the formatter's own documented skip directive, placed where the formatter honours it, and only for a region whose formatted output would lose a structure the hand layout shows, such as the rows of a matrix literal. Ordinary code kept under a skip directive for a layout preference, hand layout under a skip directive placed where the formatter does not honour it, and a layout warning suppressed on a line the formatter would print differently are the defect.

## Rationale
Layout issues are the most contentious and the least consequential: readers can adapt to different layouts, but it is better if they do not have to, and less time goes to the topic when everyone adheres to one style. Laying out code is a mostly mechanical task that takes time and mental effort, and a formatting tool relieves the writer of it. Readers comprehend code by pattern matching, so when all code is formatted alike, a project new to a reader takes less mental effort to comprehend; the benefit is larger again when the layout is consistent across the language's community, typically through the formatter's default settings. Outside the choices it preserves as written, a formatter applies its layout regardless of the original, so a hand adjustment it would rewrite does not survive its next run: a formatter that joins lines that fit reprints a matrix laid out in rows on a single line unless the skip directive marks it. Layout enforced by a linter's rules in place of a formatter is much less consistent and less able to handle edge cases than a purpose-built formatter. Output that is not exactly the layout the writer would choose is worth accepting for a layout that is fully automatic.

## Example
```python
bad:  # fmt: off
      result = compute(first_value,
                       second_value)
      # fmt: on
good: result = compute(first_value, second_value)
      # fmt: off
      identity = [1, 0,
                  0, 1]
      # fmt: on
```

## Limits
The rule reaches a file only where a formatter governs it. A project that runs no formatter and documents hand layout checked by a style checker instead, on the ground that formatters "often either aren't configurable enough or just can't anticipate how format should be done", is outside the rule, and its checker's rules govern the layout. A project that offers its formatter as an aid, under which "[a]uthors are allowed to change its output" until a part of the code base opts in to enforcement, is outside the rule wherever that enforcement is absent. The formatter's settings are the project's to choose: a setting other than the default is no finding, and the code is compared with the output under the project's settings. Layout the formatter preserves as written stays the writer's choice and is no finding: a single blank line inside a routine, a trailing comma that keeps a collection one item per line, an object literal kept on several lines because a line break follows its opening brace, a line the writer wraps where the formatter sets no line length, and a line the formatter leaves over the limit because it cannot break it without breaking other rules. A file the formatter's configuration excludes, such as generated code in its ignore file, is not governed by it. How much hand layout may go beyond what the formatter preserves is contested. One side holds that when the formatter's answer "doesn't seem right, rearrange your program (or file a bug [...]), don't work around it", and that output not formatted "100% the way you'd like" is "worth the 'sacrifice'"; the other holds that formatters "often either aren't configurable enough or just can't anticipate how format should be done", and a formatter documents its skip attribute "for things you do not want [it] to mangle". The separating condition is what the formatted output would lose and whether the formatter documents a skip directive: a region whose rows or columns the formatter would collapse, the documented example being a matrix it would reprint on one line, goes under the formatter's documented directive; everywhere else the formatter's output stands, and where the formatter documents no skip directive the program is rearranged. Lines the change does not add or alter are outside the rule, an added line that carries neither a skip directive nor a layout-warning suppression is left to the formatter's own run, and a layout tolerance stated in the project context rejects the finding.

## Validator
Grep the hunk for a skip directive (an ignore comment, a skip attribute, an off/on or skip pragma, an editor's formatter marker) and for a suppressed layout warning (line length, indentation, brace style). Open the file and the project's configuration (a formatter section in the project or build file, a formatter configuration or ignore file, a pre-commit or CI step that runs a formatter) and read `project_context`; name the formatter that governs the file, or the standard formatter the language's official documentation names. Stop when no formatter governs the file, the file is in the formatter's ignore list, the project documents hand layout checked by a style checker, or the project lets authors change the formatter's output where no check enforces it. For a skip directive, check that the governing formatter documents it and honours it at that place: some formatters take an off/on pair only around whole statements in one block and ignore a skip comment at the end of an expression. Then compare the hand layout under it with what the formatter would print, and decide whether the formatted output would lose a structure the hand layout shows, such as rows and columns of values. For a suppressed layout warning, decide whether the formatter would print the suppressed line differently; a line the formatter leaves as it is, including one it cannot break, is its output. Skip the layout the formatter preserves as written, and skip an added line that carries neither a skip directive nor a layout-warning suppression: the formatter's own run rewrites it. A skip directive shields its layout from that run; a layout-warning suppression does not: the run rewrites the line and leaves the suppression behind, so a suppressed line the formatter would print differently is hand layout committed without the run. Validator question: **Does an added skip directive keep a layout that the governing formatter would rewrite, where that formatter does not document and honour the directive at that place or the formatted output would lose no structure the hand layout shows, or does an added layout-warning suppression sit on a line the governing formatter would print differently?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-60`, severity suggestion, `file`, `symbol`, `code` = the skip directive, suppression comment or hand-laid line, quoted verbatim from the diff, `fix` = the region as the governing formatter prints it, with the program rearranged where that output reads badly, or, for a region whose layout shows rows or columns, the hand layout placed under the formatter's documented directive where it is honoured, in the file's language, `rationale` = the governing formatter, the layout it would print, and why the hand layout is or is not a structure the formatted output would lose).
