# Research note — Duplication and single source of truth

Topic `duplication-and-single-source-of-truth` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'DRY—The Evils of Duplication' (The Pragmatic Programmer, 20th anniversary ed., topic 9, ch. 2 'A Pragmatic Approach': duplication of knowledge, not of text, in code, documentation, data and representations); CC24 (Code Complete 2nd ed. ch. 24 'Refactoring') where it lists duplicated code as a reason to refactor; the 97 Things essay 'Don't Repeat Yourself'.

The canon agrees on one formulation: every piece of knowledge (a decision, rule, constant or schema) has a single authoritative representation (PP Topic 9's DRY, Beck's Once and Only Once, Raymond's SPOT), and its test is whether one change forces edits in several places (PP's acid test, Refactoring's Duplicated Code, CC24's parallel modifications, APOSD's change amplification). It disagrees on how far to push the removal of duplicated text. Clean Code G5 says to find and eliminate duplication wherever you can. Against it, PP's own 'a coincidence, not a duplication', Metz's wrong abstraction, Dahan's 'Beware the Share', SWE at Google's DAMP for tests and the Go proverb defend copies whose likeness is coincidental or whose sharing would couple independent parts. The public APOSD vs Clean Code discussion has no exchange on the question, and the Rule of Three's timing has no openable separating condition. The evidence supports the knowledge reading and a change-cost rationale, not a general defect claim. Inconsistent changes to clones are frequent and a significant number of them are faults (Juergens et al. 2009). Duplication made modification harder in a controlled experiment with novices (Hermans and Aivaloglou 2016). Copies fall behind their source (Ragkhitwetsagul et al. 2021: 100 of 153 outdated). But cloned code is not shown to be more defect-prone in general (Rahman, Bird and Devanbu 2012), and Kapser and Godfrey judge up to 71% of clones beneficial while naming verbatim snippets and parameterized code as mostly harmful. So the duplicated-block card carries a sourced separating condition. Copies meant to do the same thing are written once. Boiler-plating, replicate-and-specialize, cross-cutting concerns, experimental forks, code that will not change, short snippets and test-case duplication are accepted. The propagation card rests on Juergens, CWE-1041 and the tool documentation. Knowledge duplicated without copied text rests on official documentation across the five languages. Derived values rest on React state structure, PostgreSQL generated columns and functools.cached_property. Representations generated from one declaration rest on protobuf, go generate and stringer, TypeScript mapped types, dataclasses, Rust derive and Java records, with Nassif et al. 2021 as research. A value kept in two places rests on the PyPA single-source version page, doctest and Go examples. Repeated string literals rest on Sonar S1192, PMD, Checkstyle and goconst. Re-implemented behaviour rests on Spinellis and Avgeriou 2021 and jscpd's semantic pass; it is contested by the copy-over-dependency position, which Go's own standard library and style guide set the limits of. Identical branches rest on tool rules in all five languages, and control-flow may claim them. The repeated-switch and wrong-abstraction rules have no admissible evidence. Documentation duplication, information leakage, shotgun surgery, parallel hierarchies, forks and CI duplication gates yield to their owning topics.

## Formulation layer

The canon on this topic agrees on one core formulation: every piece of knowledge has a single, authoritative representation (Hunt and Thomas's DRY, Beck's Once and Only Once, Raymond's SPOT, Meyer's Single Choice, Ousterhout's information leakage). It also agrees that the test is whether one change forces edits in several places (PP's acid test, Refactoring's Shotgun Surgery, CC24's parallel modifications, APOSD's change amplification). Fetched texts carry the conditions under which a copy is accepted: identical code that encodes different knowledge (PP 'coincidence, not a duplication'), copies generated from a known authoritative source (Hunt on c2), a cache whose impact is localized (PP Line example, Python cached_property), tests that favour clarity (SWE at Google DAMP, Beck's note on empathy), the Rule of Three, a duplicate preferred over the wrong abstraction (Metz, Dahan), and 'a little copying' over a dependency (Go proverb). The canon disagrees on how far to push elimination. Clean Code says 'Find and eliminate duplication wherever you can' and Fowler says added duplication 'is often papering over a problem'. Against them stand Metz, Dahan, PP's own coincidence case, SWE at Google's DAMP and the Go proverb, and the public APOSD vs Clean Code discussion contains no exchange on duplication. Most book texts were read through third-party GitHub transcriptions (PP 20th ed., APOSD, Clean Code, Refactoring 2nd ed.) and marked fetched with that caveat. Code Complete's ch. 24 prose, Meyer's OOSC, PP 1st ed. and the Artima interview were reachable only as extracts or quotations and are relayed. The remainder of CC24 ('parallel modifications', Parnas) is a paraphrase from memory. WebSearch was not used, as this run's instructions required.

## Reception layer

Static-analysis tools agree on what to flag, though their thresholds differ. They flag cross-file duplicated blocks (PMD CPD, which has no default and uses 100 tokens in its examples; Pylint R0801 at 4 lines; golangci dupl at 150 tokens; jscpd at 50 tokens and 5 lines), repeated string literals (Sonar S1192 at 3, PMD at 4, Checkstyle at 2 occurrences, goconst at 3), identical function bodies (S4144) and identical branches (S1871, Error Prone, clippy, Ruff SIM114). For identical branches, most tools say the cause is usually a copy-paste error, not a maintenance cost. Sonar's default quality gate fails new code above 3% duplicated lines. Practitioners split on duplicated code but not on duplicated knowledge. Metz (relayed through Dodds and Endler), Dodds, Abramov, Endler (2025), grug, Gross (LoB), Dahan ('Beware the Share'), the Go proverb and SWE-at-Google's 'DAMP, not DRY' for tests dispute removing text-level duplication on sight. Their reasons are a wrong abstraction, coincidental similarity, coupling and test clarity. PP's own restatement ('knowledge, of intent'), Ousterhout's information leakage and React's 'avoid redundant state' all back a single source for a decision, rule or derived value. Kapser and Godfrey (71% of clones beneficial; harmful patterns are verbatim snippets and parameterized code) give the critique a research basis, and Hermans and Aivaloglou find that duplication slows modification; both were reached through neverworkintheory. Rahman/Bird/Devanbu, Juergens et al. and GitClear 2025 could not be opened here; they are recorded as unfetched pointers for the evidence layer. Hacker News, Lobsters, sandimetz.com and martinfowler.com were unreachable and WebSearch was exhausted, so no thread-level reception was gathered.

## Evidence layer

Fifty-six items cover thirteen candidate rules: 50 fetched and 6 unfetched. Nothing is relayed, because WebSearch was out of budget. Research came only through GitHub-hosted copies: the It Will Never Work in Theory posts and bibliography, the author-hosted bird.bib, a third-party BibTeX export that carries the Juergens ICSE 2009 abstract, and the included-studies file of the Santos 2018 smell review. Juergens (inconsistent changes to clones are frequent and a significant number of them are faults), Hermans 2016 (duplication makes modification harder), Ragkhitwetsagul 2021 (66 percent of copied snippets were outdated) and Nassif 2021 (85% of 835 specifications were not tested or correctly documented) support the rules, along with CWE-1041 and SWEBOK V3 §3.5. Tool rules back each rule across the five languages: Pylint R0801 (4 lines), PMD CPD, dupl and golangci (100/150 tokens), jscpd (50 tokens), Sonar S4144, S1871 and S1192 (threshold 3), clippy, Error Prone, Ruff SIM114, Checkstyle and goconst. The canon disagrees on defect-proneness. Rahman, Bird and Devanbu (EMSE 2012) find most bugs are not associated with clones, and that clones may be less defect-prone. Kapser and Godfrey judge up to 71% of clones positive, but call verbatim snippets and parameterized code mostly harmful. So a card should rest on change cost and the risk of inconsistent changes, not on general defect-proneness. Its Limits come from documented conditions (boilerplate, replicate-and-specialize, an experimental fork, a little copying over a dependency, test readability, code that will not change). ## Spine — candidate rules in source order

1. **Every piece of knowledge in a system has one authoritative representation that every other use refers to or derives from** — Every piece of knowledge (a decision, a rule, a constant, a schema) has a single, unambiguous, authoritative representation within the system. The test is whether changing one fact forces edits in several places or several formats, such as code and documentation, or a schema and the structure that holds it. The principle concerns duplicated knowledge and intent, not duplicated text.
   - formulation: PP 20th ed., ch. 2, Topic 9 'DRY—The Evils of Duplication', opening section p. 80 (Tip 15) and 'DRY Is More Than Code' p. 81 (the acid test); c2 wiki DontRepeatYourself, 'Therefore' and 'Notes' (signed AndrewHunt); Venners, 'Orthogonality and the DRY Principle', Artima 2003 (relayed); TAOUP ch. 4 'The SPOT Rule'; Fowler, bliki 'BeckDesignRules' (Once and Only Once); 97 Things 'Don't Repeat Yourself' (thing 30)
   - reception: not contested
   - evidence: Hunt, A., Thomas, D. The Pragmatic Programmer, 20th Anniversary Edition (Addison-Wesley, 2019), Topic 9 'DRY—The Evils of Duplication' — Topic 9, p. 80 (Tip 15) and p. 81, read in a third-party GitHub transcription (blocks 13-16) (fetched, formulation)
   - disposition: held-not-checkable — The principle has no binary form on a diff as stated. Its checkable forms are change-reaches-every-copy, duplicated-block-written-once, repeated-literal-named-once, derived-value-computed-from-source, representation-declared-once, hand-kept-copies-checked and existing-routine-reused, and it feeds their Rationale (one fact, one place to change). It is recorded in the research note as the topic's core formulation.
   - facets: step ['design'], applies_to ['universal'], triggers [], scope hunk, semantic, minor
2. **A change to one copy of duplicated code is made in every other copy meant to do the same thing, or the copies are merged into one** — When the change edits a block (a fix, a new condition, a changed constant or call) and the repository holds other copies of that block that are meant to do the same thing, the same edit reaches every copy in the same change, or the copies are merged into one routine that every place calls. An edit that leaves another copy unchanged is an inconsistent change. Inconsistent changes to clones are very frequent and induce a significant number of faults (commercial and open-source systems, ICSE 2009). A fix applied to one copy can miss the same weakness in the other (CWE-1041). Copies fall behind their source: of 153 code clones copied from open-source projects into Q&A answers, 100 (66 percent) were outdated and 10 were buggy (TSE 2021). Tool documentation states the mechanism. Every copy must be found, changed and tested (Pylint R0801). Copies not kept in sync grow apart until detectors no longer recognise them, so CPD's authors advise removing duplicates rather than keeping them in sync (PMD CPD). The rule holds only for copies meant to do the same thing: a copy made to diverge (replicate-and-specialize, a platform variant) need not receive the edit. The rule has no lexical signature, because any edit can touch a copy. It therefore runs on every diff, and the finder searches the repository for the pre-change text of each edited block of several lines.
