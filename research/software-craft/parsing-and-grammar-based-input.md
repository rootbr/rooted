# Research note — Parsing and grammar-based input

Topic `parsing-and-grammar-based-input` of group J. Input and security hygiene, domain `input`, id prefix `INP`. Formulation locators: SW4.9 (SWEBOK Guide V4.0 ch. 4 §4.9; the V3 section of the same number, 'Grammar-Based Input Processing', is transcribed at ligurio/swebok-v3 master 3_software_construction.md); PoP9 (The Practice of Programming ch. 9 'Notation': little languages, regular expressions, data formats, programmable tools); the practitioner formulations 'parse, don't validate' (Alexis King's essay) and the language-theoretic security (LangSec) position.

The canon describes more than it prescribes. SWEBOK §4.9 (the V3 text, transcribed, stands in for V4.0) says grammar-based processing parses the input into a tree, and the program computes on that tree. The Practice of Programming ch. 9 treats regular expressions, data formats and little languages as notations, and its CSV case study is the classic case against splitting by hand. The practitioner formulations sharpen this into rules. King's 'parse, don't validate' says to parse at the boundary into the most precise representation and never act on input before it is fully parsed. LangSec contributes the shotgun-parsing antipattern (Momot et al. 2016, reachable only through King's verbatim quotation) and 'be definite about what you accept'. The cards rest on standard and tool evidence. Standards: the current OWASP Input Validation Cheat Sheet ('Parse Safely, Then Validate', size and depth limits before parsing, whole-value regex matches, length bounds and non-backtracking engines, reject with a clear error), CWE-20 (parsing as a distinct layer; decode once), CWE-185/625/1286/1333 and NISTIR 8397 on fuzzing. Official documentation of every corpus language covers parser leniency and regex engines. Tool rules come from SonarSource, CodeQL, eslint-plugin-regexp, clippy, staticcheck and Error Prone. Research on regexes: Davis et al. 2018/2019, Michael et al. 2019, Wang et al. 2020 and Barlas et al. 2022. The industry disagrees on strictness. RFC 9413, the Rust API Guidelines and Go's encoding/json/v2 reject faulty or ambiguous input. RFC 1958's robustness principle, the WHATWG URL parser, Pydantic's lax coercion and the defaults of Python json/csv, Go json v1 and Java date parsing tolerate it. RFC 9413 §2.3 separates the cases: a format may explicitly allow a range of forms with precise error handling, which is different from relying on tolerance. That distinction lets the reject-whole and strict-parser cards ship. Unknown but well-formed fields stay unresolved: protobuf and Tolerant Reader preserve or ignore them, OWASP and INP-01 list allowed fields, and no source separates the cases. On ReDoS the tools and studies agree on the mechanism. Abramov, the safe-regex maintainers and the 2025 SoK limit it to untrusted input on backtracking engines, and Go and Rust engines guarantee linear time, which gives the card its separating condition. No empirical study of parse-once typed representations was found, so that card rests on CWE-20, OWASP and official documentation. Round-trip tests (TST-41), parser crash-versus-error (ERR-12), unsafe loaders (INP-06), eval (INP-05) and allowed object fields (INP-01) are already carded elsewhere.

## Formulation layer

Fetched sources: SWEBOK V3 §4.9 (the text is descriptive, not prescriptive), Alexis King's 'Parse, don't validate' and her follow-up 'Names are not type safety' (both from her GitHub Pages source), the RFC 9413 source on GitHub, Rob Pike's 2011 lexing slides, the OWASP Input Validation cheat sheet and ReDoS page, the Fuzzing Book's grammar chapter, Crafting Interpreters' syntax-error chapter, the Python csv and json docs, the Go regexp and json v2 docs, the 97 Things essays and the Ousterhout–Martin discussion. Unfetched, so marked (paraphrase): The Practice of Programming ch. 9 and the ch. 4 CSV case study, the SWEBOK V4 text, Code Complete §8.5, TAOUP, Fowler's Tolerant Reader, Allman, and every LangSec paper. Two LangSec papers are reachable only indirectly: King's essay quotes the definition of shotgun parsing from 'Seven Turrets of Babel', and the orchestrator's search relayed a summary of Ali et al. 2023. No GitHub-hosted copy of a LangSec paper or the langsec.org site turned up. The sources disagree in four places. First, the robustness principle (RFC 1958 as RFC 9413 quotes it, TAOUP, Tolerant Reader) against RFC 9413's 'virtuous intolerance', LangSec's 'be definite about what you accept' and OWASP's 'reject invalid requests'. Second, regexes as hand-made parsers for simple formats (97 Things #23) against Pike ('overkill', 'misuse of a dynamic engine'). Third, accepting several formats in user-entered fields (97 Things #66; RFC 9413 §Flexible Protocols allows it for user input) against strict rejection. Fourth, error recovery that reports many errors in language tooling (Nystrom) against rejecting a malformed data input as a whole. Separately, StrictYAML's 'Norway problem' page blames YAML 1.2, but the YAML 1.2.2 spec's Core Schema contradicts that, so the hazard has to be stated for YAML 1.1-style implicit typing.

## Reception layer

The industry agrees on the mechanisms behind this topic's rules and disputes their scope. 'Parse, don't validate' (King 2019) is reflected in Pydantic, Zod, the Rust API Guidelines and the rewritten OWASP Input Validation Cheat Sheet, but the vocabulary is inverted: Pydantic and Zod call parsing 'validation', and OWASP writes 'Parse Safely, Then Validate'. King herself (2020) disputes the reading that a wrapper type alone counts as parsing. How strict a parser should be is the main contested point. RFC 9413, the Rust guidelines (C-VALIDATE) and Go's 2026 encoding/json/v2 defaults reject faulty or ambiguous input. RFC 1958's robustness principle, the WHATWG URL parser, Pydantic's lax coercion, and the ignore-unknown-fields defaults of serde, Go, Pydantic and protobuf tolerate it. Standard parsers are also lenient by default (Python json and csv, java.net.URL, Go net/url), so cards must separate malformed input from well-formed unknown content and must not assume that 'the standard parser' is strict. On regular expressions the tool rules agree: SonarSource S5852, S8786, S5850 and S5843 (default threshold 20), eslint-plugin-regexp, clippy, staticcheck, Error Prone, and OWASP's full-match and length-bound advice. Abramov (2021) and the safe-regex maintainers dispute ReDoS severity and heuristic accuracy where no untrusted input reaches the regex, anchor semantics differ between Java/Python and Go, and Ruff S307's literal_eval-on-input example contradicts the CPython docs. Not opened: Hacker News and Lobsters threads (WebSearch budget exhausted and hosts denied), Fowler's Tolerant Reader, and the papers themselves. Seven Turrets was reached only through King's GitHub-hosted quotation, Ali et al. 2023 only as the orchestrator's relay, and the Davis ReDoS studies only as titles named in the safe-regex README.

## Evidence layer

Most candidate rules have an openable source. The standard-class sources come from GitHub mirrors: the current OWASP Input Validation Cheat Sheet (its sections "Parse Safely, Then Validate", "Reject invalid requests…" and the whole-value regex rule) and CWE-20/185/625/1286/1333 from the official CWE-CAPEC repository. The CWE-20 entry carries the LangSec mitigation of parsing as a separate boundary layer, and RFC 9413 comes from its GitHub source. Official documentation backs every target language. Python json/csv/re/ipaddress/urllib.parse/ast, Go encoding/json (v1, and v2 under GOEXPERIMENT), encoding/csv, net/url and regexp, JDK Matcher/DateFormat/ResolverStyle/URL, the Rust regex crate and API guidelines, serde, and the TypeScript handbook all state the parsing, strictness, anchoring and linear-time facts in their own words. Tool rules cover ReDoS (Sonar S5852/S8786, eslint-plugin-regexp, CodeQL, Semgrep), anchoring (CodeQL, Sonar S5850), hand-splitting (Error Prone StringSplitter), regex parsing of HTML and substring checks on URLs (CodeQL), and unsafe loaders (Ruff S506). Research comes from the author-hosted PDFs and abstracts of Davis et al. (FSE 2018: 1% of unique npm/pypi regexes super-linear; FSE 2019: 15% semantic and 10% performance differences across languages; ASE 2019: 38% of developers know ReDoS) and from neverworkintheory abstracts (Wang et al. MSR 2020; Miller et al. TSE 2020). The LangSec papers (Momot et al. 2016 via a verbatim quotation in King's essay, Ali et al. 2023 via the orchestrator's snippet) and the grammar-fuzzing papers (via fuzzingbook) are relayed only. No empirical study of 'parse once into a typed representation' was found. The canon disagrees on leniency: RFC 9413 and the Rust API guidelines reject Postel-style tolerance, while the WHATWG URL parser, Go json v1, Python json/csv defaults and Java's default date parsing are lenient by design. On ReDoS severity, the FSE 2018 study calls it a larger threat than guessed, while the 2025 SoK says many engines now have defenses.

## Spine — candidate rules in source order

1. **Text in a structured format such as JSON, CSV, XML, HTML, a URL, a date or an IP address is read, and its parts are checked, through the language's standard or established parser for that format, never by splitting, slicing, substring tests or a regular expression over the raw text** — A value in a format with a grammar — JSON, CSV, XML or HTML, a URL, a date, an IP address, a query or configuration language — is read with a maintained parser for that format: the language's standard one, or the established library where the standard library has none (the JDK ships no CSV reader). A check on one of its parts, such as a URL's host, is made on the parsed component. It is never made by splitting the raw text on a delimiter, slicing it, testing it for a substring, prefix or suffix, or matching it with a regular expression. Regular expressions are kept for simple, structured fields (OWASP). General HTML cannot be parsed with them (CodeQL), and a substring check on a URL can be bypassed by an allowed host embedded in an unexpected place. A hand-written recursive-descent or state-machine parser for a format the program itself defines counts as a real parser. Deciding which hosts or values are acceptable is INP-01's rule, and sanitizing HTML for output belongs to INP-01 and INP-03.

2. **Input is parsed in one layer at the boundary where it enters into a typed value, or into a type whose only constructor checks it, and processing code takes that value instead of raw text or an untyped map whose parsing and checks it repeats** — Input is parsed in one distinct layer at the boundary where it enters, into the program's internal representation: a typed value, or a type whose only constructor runs the checks.
