# Session fixation protection stays on, a hand-written login path changes the session id, and sessionFixation().none() is never configured

## Thesis
The session fixation strategy remains the default `changeSessionId` (or `newSession` or `migrateSession`); a diff that sets `sessionFixation(s -> s.none())` is the defect. A hand-written authentication path — a custom filter that sets the `SecurityContext`, a controller that logs a user in after an OTP or an SSO callback, an MFA step-up, a role change — calls `request.changeSessionId()` (or invalidates and recreates the session) before the elevated state is stored.

## Rationale
In a fixation attack the attacker obtains a session id first, plants it in the victim's browser (a link carrying the id, a cookie set from a sibling host), and waits for the victim to log in; the session then carries the victim's authentication under an id the attacker knows. Changing the id at the moment of authentication — the framework's default — means the id the attacker planted is never the authenticated one. The default acts inside the framework's own authentication mechanisms; a login the code performs itself bypasses them, so it has to change the id itself. The same applies to any privilege change, because the pre-change id may have been exposed while the session was low-privilege. `none` disables the protection, and the documentation says it leaves the application vulnerable.

## Example
```java
bad:  http.sessionManagement(s -> s.sessionFixation(f -> f.none()));
      SecurityContextHolder.getContext().setAuthentication(auth);          // custom login, same session id
good: request.changeSessionId();                                            // before storing the login
      SecurityContext ctx = SecurityContextHolder.createEmptyContext(); ctx.setAuthentication(auth);
      SecurityContextHolder.setContext(ctx); contextRepository.saveContext(ctx, request, response);
```

## Limits
Applies to session-based authentication. A stateless chain (`SessionCreationPolicy.STATELESS`, bearer tokens, no `HttpSession`) has no session to fix, and `sessionFixation` settings there are inert. A login performed through the framework's `AuthenticationManager` with `formLogin` or another built-in mechanism inherits the default and needs no call. `none` in a test profile is out of scope.

## Validator
On the triggered hunk find `sessionFixation(...).none()`, and each place the code stores an `Authentication` or elevates privileges outside the framework's login filters. For the latter, look in the file for `changeSessionId()`, or `invalidate()` followed by `getSession(true)`, before the store. Validator question: **can a session id that existed before authentication or before a privilege change still identify the elevated session?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: SEC-25`, severity major, `file`, `symbol`, `code` = the `none()` setting or the context store quoted verbatim from the diff, `fix` = the default strategy kept, or `changeSessionId()` before the store, `rationale` naming the pre-authentication id that survives).
