# A TODO or FIXME marker added by a change points to where its context is kept and says what work remains, or the change does that work instead

## Thesis
Each marker comment that a change adds to flag work left undone (TODO, FIXME, XXX, HACK or the project's own marker word) carries a pointer to where its context is kept and a description of the work that remains. The pointer is a link to a resource that holds the context, preferably a tracked issue; in a language whose documented note convention has the form MARKER(uid): body, the uid, usually the username of someone who can provide more information, is the pointer. A marker whose text puts the work off to a future time, such as later, someday or after another change, names a very specific date or a very specific event; a marker whose text names no time needs neither. A marker that lacks these parts is settled within the change: the change adds the missing parts, linking the marker to a tracked issue filed for the work, or does the work and removes the marker.

## Rationale
A marker flags a place where additional work or improvements are needed but are not implemented immediately. Such markers sometimes get overlooked or forgotten, leading to incomplete or unfinished code, and a developer who marks a suspected bug to deal with later sometimes lacks the time or simply forgets to get back to it. Experience with deferred cleanup shows that the more time passes after the change that called for it, the less likely it is to happen, and that unless it is done immediately after that change it usually never happens, because it gets lost or forgotten in the press of other work; a problem a change exposes but cannot address right now is filed as a bug assigned to its developer so that it does not get lost, and a marker may reference that bug. An issue is the preferred pointer because issues are tracked and carry follow-up comments; a link near the marker makes it easier for whoever resolves it to get the context, and a consistent marker format can be searched to find out how to get more details. A description of the issue gives future readers its context, and a marker whose text puts the work off to a future time names a very specific date or event that future maintainers will comprehend, rather than an open "later".

## Example
```python
bad:  def total(items):
          # TODO: fix later
          return sum(item.price for item in items)
good: def total(items):
          # TODO: https://issues.example.com/123 - Subtract refunds when the refund API ships.
          return sum(item.price for item in items)
```

## Limits
Practice divides on whether a marker stays in merged code at all. Some style guides keep a marker on code that is temporary, a short-term solution, or good enough but not perfect, when it links to a resource that holds the context, preferably a tracked issue, and linters check that form for an issue link and a description. Another style guide keeps a marker that carries a description and no pointer. Marker-reporting checks flag each marker: one advises fixing or reviewing the code and removing the comment before the code counts as production-ready, another reports marker tags because they sometimes get overlooked or forgotten. Both sides send work that cannot be finished now to a tracked task: one asks for tasks when a marker cannot be fixed in the current merge request, the other for a filed bug that a marker may optionally reference. The project's policy separates the cases. A project that runs a marker-reporting check, that defines its own marker words, such as one word that blocks landing until it is fixed or removed and another for a note left in the codebase, or whose stated style keeps a described marker without a pointer, decides, and its rule replaces this one; the resolve-before-deploy check itself states that it may not be appropriate for a project that uses TODO comments as a form of documentation, such as to provide context for future work. A project style that avoids naming an individual or team as the context asks for the issue link in place of a username. A marker on a line the change did not add is outside this rule.

## Validator
Grep the added lines of the hunk for a marker word (TODO, FIXME, XXX, HACK, or a marker word the project context defines) inside a comment; skip a match inside a string literal or an identifier, and a marker on a context line the change did not add. For each added marker, read its comment and the comment lines directly beside it. Look for three parts: a pointer to the context, which is a link or reference to an issue or another resource that holds the context, or the uid of a note written in the language's documented MARKER(uid): body form; a description of the remaining work beyond the marker word or a placeholder such as "fix later", "cleanup" or "temporary"; and, when the comment's text puts the work off to a future time (later, someday, after another change), a specific date or a specific event. Where the project context states its own marker policy, apply that policy in place of these three parts. Validator question: **Does a marker comment the change adds lack a pointer to where its context is kept, lack a description of the remaining work, or put the work off to a future time in its text without naming a specific date or event?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-62`, severity suggestion, `file`, `symbol`, `code` = the added marker comment quoted verbatim from the diff, `fix` = the marker rewritten in the file's language with a link to the issue that tracks the work and a description of what remains, plus the date or event when its text puts the work off to a future time, or the code with the work done and the marker removed, `rationale` = which part is missing (pointer, description, date or event) and the work the marker leaves undone).
