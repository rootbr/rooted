# An operation whose one obvious receiver is a value of a type with behaviour of its own that the codebase defines is a method of that type, not a free function or a static method of a helper or utility class

## Thesis
A free function, or a static method of a helper or utility class, whose one obvious receiver is a value of a type the codebase defines is declared as a method of that type when four conditions hold. The type has behaviour of its own. Its declaration can take the method: it is a concrete type whose source the codebase owns, not an interface. The operation uses that value. The method form gives the type no dependency that the codebase's dependency rules forbid. The test is whether the operation is clearly associated with that particular type; declared as a method, it is found where a reader asks what can be done with a value of the type.

## Rationale
A method needs no import or qualification: a value of the appropriate type is all a caller needs. Methods also make it easy to answer the question of what can be done with a value of a given type, especially in generated documentation. A static class is a compromise between pure object-oriented design and simplicity. It should be used sparingly and only as a supporting class for the object-oriented core, not as a miscellaneous bucket. A utility class whose fields and methods are all static may indicate a lack of object-oriented design. For a type whose source is owned, the guidance is to consider regular instance methods instead of extension methods.

## Example
```typescript
bad:  export function canWithdraw(account: Account, amount: number): boolean { ... }
      if (canWithdraw(account, amount)) { ... }
good: export class Account {
        deposit(amount: number): void { ... }
        canWithdraw(amount: number): boolean { ... }
      }
      if (account.canWithdraw(amount)) { ... }
```

## Limits
Free functions are kept for operations with no one obvious receiver, and those fall outside the rule. They include an operation with no obvious self, such as the minimum of several values; an unconstrained generic, such as printing any value; and an operation whose function syntax is part of the established domain notation, such as a sine. A generic operation read across many kinds of container, such as a length, also falls outside, as does an operation where it makes little sense to deem it to belong to one argument more than another, as addition belongs no more to its left operand than to its right. A conversion between two types lives with the more specific of them. A function that never uses the value also falls outside: an instance method that does not use its receiver normally accesses no instance state and need not be a method. Where the language binds a method only to a type declared in the same package as the method, and never to an interface, an operation on an interface or on a type from outside the codebase stays a function. An operation whose method form would give the type a dependency that breaks the dependency management rules stays off it, in the way that an instance method on a string type returning a URI type would be the wrong design. A passive data carrier, an object that carries data with every field public and no invariant relating its fields, is outside the rule. Where to declare an operation with one obvious receiver is contested, and the language's own guideline separates the cases. One guideline makes a function a member only if it needs direct access to the representation, for less coupling and fewer functions to change after a change in representation, and places helper functions in the same namespace as the class they support. Another has a function that works primarily on an object considered as an extension function with that object as receiver, placed in the same file as the class when it is relevant to all of the class's clients and next to the code of its one client when it makes sense only for that client. In a language whose guideline says either of these, the placement it sets satisfies the rule. Elsewhere the stated preference is methods and properties over free functions, and regular instance methods for a type whose source is owned. Outside code that reads a type's fields and writes them back, and a static-only class of helpers with no receiver, are judged by their own rules.

## Validator
Grep the hunk for an added or changed free function, or a static method of a class used as a helper or utility, that takes a value of a type the codebase defines. Open that type's declaration and confirm four things: it is a concrete type in the codebase, not an interface or a type from a dependency; it has behaviour of its own beyond public fields; it is not a passive data carrier, with every field public and no invariant relating its fields; and its package can take the method. Read the function's body. Confirm that it uses that value and treats no other argument as an equal operand. Confirm that it is not a generic over any type, not domain notation, and not a conversion that belongs with a more specific type. Trace every type the body depends on and confirm the receiver type's module may depend on each one under the codebase's layering. Open the callers at scope and confirm they hold a value of the receiver type at the call. Check the file's language: where its guideline places helpers beside the type, a non-member function in the type's namespace, an extension function in the type's own file, or an extension function that makes sense only for one client and sits next to that client's code passes. Validator question: **Does this function or static helper use its one obvious receiver, a value of a concrete type the codebase defines that has behaviour of its own and is not a passive data carrier, while it is declared neither on that type nor in a placement the language's guideline sets for it and its method form would add no forbidden dependency?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-34`, severity minor, `file`, `symbol`, `code` = the function or static-method declaration line, quoted verbatim from the diff, `fix` = the same operation declared as a method of the receiver type with the receiver parameter dropped, or, in a file whose language guideline places such helpers beside the type, the function moved into the type's namespace as a non-member or declared as an extension function where that guideline places it, and one call site rewritten to reach it, in the file's language, `rationale` = names the receiver type, the parameter that carries it, the fact that the type's declaration is in the codebase and can take the method, and the value the body uses).
