# A line stays within the column limit that the project's style guide or formatter sets, unless it holds a URL, a command or a string that splitting would damage

## Thesis
Where the project's style guide, formatter or linter configuration sets a column limit, each added line stays within it, and a comment or documentation line stays within the narrower limit the guide sets for such text, where it sets one. A line may run past the limit where splitting would damage the content that makes it long, such as a URL or a path, a command line meant to be copied, or a string literal that cannot easily be wrapped, like a user-visible message someone searches the code for, or where the governing guide exempts the line's kind, such as an import or a package declaration.

## Rationale
A column limit bounds the editor window that code needs. Within it, several files fit side by side, and so do the two versions of a change in a review tool that shows them in adjacent columns; past it, the reader scrolls sideways or the tool wraps the line, and default wrapping disrupts the visual structure of the code and makes it harder to understand. Long lines are also hard to read in printouts and where the editor gives part of the screen to project and class panels. In a survey of 55 students and 7 professionals choosing between functionally equivalent snippets, respondents judged snippets whose every line stays within 80 characters more legible than snippets with longer lines (two-tailed test for proportion, p < 0.001); the measure is stated preference, not comprehension or defects. The number is a project setting, not a constant across languages: the style guides set 79 characters (raisable to 99 where a team agrees), 80 and 100, checker defaults are 80, 88 and 100, and one house guide recommends a soft 99, so a line past 100 columns exceeds every one of these defaults. Comment and documentation text may carry a narrower limit: 72 characters for comments and documentation strings under one guide, which keeps that width even where a team raises the code limit to 99, and, under another, 80 characters excluding indentation or the line limit including it, whichever is smaller, for a line that is entirely a comment. Length is counted as the project's checker counts it: one column per character and a trailing comment included, while checkers differ on a tab, which one expands to 8 columns by default and another counts as one character. Splitting some content damages it: a split literal no longer turns up when its text is searched for, and a split URL or command can no longer be clicked, copied or pasted whole, so the guides exempt such lines. For the repair, one guide prefers refactoring a line that feels too long to splitting it, and others note that extracting a local variable or a routine may remove the need to wrap at all; a break that is still needed preferably comes at the highest syntactic level available, the aim being clear code rather than the fewest lines.

## Example
```python
bad:  def order_total(order):
          # Discounts add up rather than compound, as the shop's pricing rules say.
          return sum(item.price * item.quantity for item in order.items) * (1 - order.discount_rate - order.loyalty_rate)
good: def order_total(order):
          # Discounts add up rather than compound,
          # as the shop's pricing rules say.
          subtotal = sum(item.price * item.quantity for item in order.items)
          return subtotal * (1 - order.discount_rate - order.loyalty_rate)
```

## Limits
Where the governing guide sets no column limit, the column check does not apply. One language's official guidance states that it has no line length limit and wraps a line that feels too long with an extra indent; a house style guide for that language sets no fixed line length, prefers refactoring a line that feels too long over splitting it, lets a line already as short as practical stay long, and counts a line-length restriction among invalid local style choices. A project in that language is governed by a limit it adopts, as another house guide does with a soft 99 characters. Under a soft limit, authors aim to wrap before it but code is allowed to exceed it, so a finding there is a suggestion the author may decline; one guide that prefers 80 columns likewise keeps a longer line where exceeding the limit significantly increases readability and hides no information. The exempt kinds differ by guide and checker: one guide exempts long imports, URLs, paths and flags in comments, and string constants only at module level and only when they contain no whitespace, and asks for any other long string literal to be joined from shorter pieces; checkers also skip a line of one unbroken word, a line ending in a URL, a line pushed over the limit by a pragma or suppression comment, and a license identifier line. Where the project runs a formatter that wraps code to its configured width, the tool relieves the author of the lines it can fit, and the rule's remaining reach is the lines it leaves long: comments and string literals where the formatter does not reflow them, as one formatter documents for both, and an expression it cannot fit, for which refactoring, usually by extracting a local variable, is the documented way out. A column limit, or its absence, that the project context states for the file's language governs, since a project's own guide takes precedence over the language's, and a finding the stated setting allows is rejected.

## Validator
Grep the hunk for added lines of 80 characters or more, comment and documentation-text lines of 73 characters or more, and, where the project context states a tab width, tab-indented lines that reach 80 columns once each tab is expanded to it. Take the limit for the file from the project context: the column limit its style guide, formatter or linter setting gives for the file's language, any narrower limit for comment and documentation text, and whether the limit is soft. Where the project context states none, use 100 columns, the widest limit among the guides and checker defaults, and no limit at all for a language whose official guidance states it has none. Measure each candidate as the project's checker does: one column per character and a trailing comment counted, and a tab expanded to the tab width the project context states, or counted as one column where it states none, as one checker counts it. Drop a line whose excess comes from a URL, a path, a command line meant to be copied or a string literal that cannot easily be wrapped, an import or package declaration where the governing guide or checker exempts it or the project context names none, a line of one unbroken word, a line pushed over the limit by a pragma or suppression comment, and a license identifier line. Drop a line that a wrapping formatter the project context names would rewrite to fit. Validator question: **Does an added line exceed the column limit that governs its kind, code or comment text, through content that could be refactored or split without breaking a URL, a path, a command, a searchable string or another exempt token?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-55`, severity suggestion, `file`, `symbol`, `code` = the over-limit added line, verbatim from the diff, `fix` = the statement shortened by extracting a named local variable or routine, or, where that is not enough, wrapped at its highest syntactic level, or, for a comment or documentation line, its text re-wrapped at word boundaries, every resulting line within the limit that governs it, in the file's language, `rationale` = the line's measured length, the governing limit and where it comes from, the project's setting or the widest default, and that a line past it no longer fits beside a second file or the other side of a review diff).
