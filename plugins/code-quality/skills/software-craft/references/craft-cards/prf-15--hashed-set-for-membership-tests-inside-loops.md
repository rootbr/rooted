# A membership test or lookup by key that runs on every iteration of a loop uses a hashed set or map, not a linear scan of a sequence whose size grows with the input

## Thesis
A membership test or a lookup by key that runs on every iteration of a loop that runs more than a handful of times, against a sequence whose size grows with the input, goes to a hashed set or map, built once before the loop when the loop leaves the sequence unchanged and kept beside the sequence with one insertion per added element when the loop adds to it, whose test and lookup cost expected O(1) per call, in place of a linear scan that costs O(n) per call in the n elements currently in the sequence; the expected cost holds when the hash function disperses the keys among the buckets and hashing and comparing a key is O(1).

## Rationale
A membership test on a sequence checks its elements one by one until the right one is found, at O(n) per test, and a search by key on a sequence is the same scan; m such tests in a loop cost O(n·m). A hashed set offers constant-time add, remove and contains, and a hashed map an average-case O(1) get, so building the set once costs one constant-time add per element and each later test costs expected O(1). The cost is expected, not guaranteed: when every key hashes to the same value, each O(1) operation takes O(n). One language specification requires of its maps and sets only access times that are, on average, sublinear in the number of elements, so there the hashed test is guaranteed only to be sublinear on average. Redundant traversals of collections are a prevalent class of asymptotic performance bugs: a static analysis found 92 of them in 1.6M lines of widely used software packages, with 5 false positives, and the manually repaired programs were at least 2.45 times faster than the originals at an input size of 50,000. A study of inefficient loops reports search loops whose efficiency depends on the workload, such as a list filled with tens of thousands of nodes, and that such loops are often fixed by data-structure changes, for example by replacing the searched list with a hash table.

## Example
```java
bad:  List<String> ids = loadIds();
      for (Item item : items) {
          if (ids.contains(item.id())) { ... }
      }
good: Set<String> ids = new HashSet<>(loadIds());
      for (Item item : items) {
          if (ids.contains(item.id())) { ... }
      }
```

## Limits
A single test outside a loop, a loop the domain bounds to a handful of iterations (building the hashed set is itself one pass over the sequence, so a handful of scans costs the same complexity class), a sorted sequence searched by binary search, a sequence the domain bounds to a handful of elements, and elements with no hash consistent with their equality fall outside the rule; a loop nested over a second collection to match its elements, and keys chosen by an attacker to collide, are outside its scope. Whether a hashed set pays at small sizes is disputed: one linter rule, in its recommended configuration and with a default minimum size of 0, prefers a set's membership test to an array's and states that it is faster, while the same rule accepts an array checked only once and lets a project set the minimum known array size before the set is enforced; one language's core guidelines hold that, even when another container seems more suited for lookup, a contiguous array will usually still perform better for containers up to a few KB in size. The condition that separates the cases is whether the scanned sequence's size grows with the input and the loop runs the test more than a handful of times: a scan's O(n) counts the elements currently in the container, the linter rule accepts an array checked only once, one static-analysis rule says an O(n) collection method could be an expensive operation when the collection is large, and a search loop's efficiency depends on the workload.

## Validator
Grep the hunk for a call or operator that scans a sequence for a value or a key: contains, includes, indexOf, lastIndexOf, index, count, any, position, find, findIndex, some, anyMatch, noneMatch, filter, or an `in` test. Open the file and confirm the call runs inside a loop body, a stream or iterator pipeline over another collection, or a function the loop calls on each iteration, and that the loop iterates over input, a query result or a collection, not over a literal or constant of a handful of elements. Trace the receiver to its declaration and confirm it is a sequence (array, list, slice, vector) and not a hashed set, a map or a sorted sequence searched by binary search, and that its elements, or the searched field, have a hash consistent with the equality the scan uses. Trace where its elements come from: input, a query, a file, a request, or another collection whose size grows with the input, against a literal or constant of a handful of elements that the domain fixes. Validator question: **Does a loop that runs more than a handful of times test membership in, or search by key, a sequence whose size grows with the input by scanning it on each iteration?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: PRF-15`, severity major, `file`, `symbol`, `code` = the membership test or key search inside the loop, quoted verbatim from the diff, `fix` = the sequence converted once before the loop into a hashed set or a map keyed by the searched field, or, when the loop itself adds to the sequence, a hashed set or map kept beside it and updated with each added element, and the test rewritten as its membership test or key lookup, where a map keeps for each key the element the scan returns (the first match, or the list of all matches when the scan collects them), never the last one inserted, in the file's language, `rationale` = names the scanned sequence, the input its size grows with, and the O(n) cost per iteration against the expected O(1) hashed lookup).
