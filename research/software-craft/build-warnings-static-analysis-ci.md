# Research note — Build warnings, static analysis and continuous integration

Topic `build-warnings-static-analysis-ci` of group H. Tools and hygiene, domain `tooling`, id prefix `TOOL`. Formulation locators: SEG18 (Software Engineering at Google ch. 18 'Build Systems and Build Philosophy'); SEG20 (ch. 20 'Static Analysis'); SEG23 (ch. 23 'Continuous Integration'); PP 'Pragmatic Starter Kit' (The Pragmatic Programmer, 20th anniversary ed., ch. 9 'Pragmatic Projects'); SWEBOK V3 ch. 4 §3.7 'Construction Quality', which names static analysis among the construction quality techniques (ligurio/swebok-v3 master 3_software_construction.md); the 97 Things essays 'Keep the Build Clean' (thing_42), 'Take Advantage of Code Analysis Tools' (thing_79), 'Automate Your Coding Standard' (thing_04) and 'Own (and Refactor) the Build' (thing_63).

The canon (SEG ch. 18, 20, 23; PP 'Debugging' and 'Pragmatic Starter Kit'; SWEBOK V3 §3.7; 97 Things 42, 79, 04, 63) agrees on several points. Build scripts are code and must not depend on the host machine. A change keeps the build free of warnings, and the project's configured checks and tests pass before the change goes to review. A suppression is a last resort: it sits on the narrowest construct, names what it silences and says why. A failing check is not quietly switched off. The industry disagrees in five places. (1) Whether every warning must be fixed or only new ones and those on modified lines: 97 Things 42 and Code Complete say every warning; SEG ch. 20, golangci-lint, ESLint bulk suppressions and Kim & Ernst 2007 say new and modified only. (2) Whether a warning tier that lets the run pass should exist: no in the Go FAQ and SEG ch. 20, yes in ESLint and Error Prone. (3) Whether warnings-as-errors belongs in the source or in the CI invocation: the Linux kernel and Code Complete put it in the build; rust-unofficial, Gentoo and RFC 1105's view of lints as advisory point to CI. (4) How TypeScript should suppress: the TypeScript team allows ts-ignore in named cases, typescript-eslint allows only described ts-expect-error, and Google bans both. (5) Whether a failing test may be disabled: SEG ch. 23 accepts it when tracked; Zampetti 2020 and jest no-disabled-tests take the stricter line. Most of the evidence is official documentation and tool rule pages across all five languages. Each language has a way to name the silenced diagnostic, a reason field (only staticcheck requires it by default) and a report for unused suppressions. Research adds the following. Hu et al. FSE 2025 find 50.8% of suppressions useless, with a risk of hiding future warnings. Liargkovas et al. 2023 find that false positives explain only a minor share of suppressions. Zampetti 2017 finds analyzer breakages are fixed rather than disabled. Johnson 2013 finds false positives and poor presentation are barriers to tool use. Trautsch 2020 finds PMD in the build is associated with lower defect density but has a non-significant effect on warning removal. Luo 2014, Eck 2019, Costa 2022 and Durieux 2020 cover the cost of flaky tests and restarted builds. No study measures the effect of weakening a strictness setting to make a change pass.

## Formulation layer

The canon agrees that a build is reproducible and its scripts are code (SEG18, 97 Things 63, SWEBOK V3 SCM 6.1), that a change leaves the build free of warnings (97 Things 42, PP 'Debugging', Code Complete 23.5, the Go FAQ, OpenSSF), and that the project's checks and tests pass before a change reaches review (SEG ch. 9 presubmits, PP 'Coding Ain't Done 'Til All the Tests Run', Code Complete 29.4, Continuous Delivery ch. 3, eng-practices). On suppression it agrees too: a suppression is a last resort, on the narrowest construct, with a reason that can be searched for (Effective Java Item 27, Google pyguide 2.1 and 3.16.5, Google tsguide), and Clean Code G4 counts turning off warnings or failing tests as overriding a safety. It disagrees in four places: fix every warning or only new ones (97 Things 42 and Code Complete against SEG20 'Usability', which warns that fixing old warnings can add bugs, and OpenSSF's tolerance of fewer than 10 warnings); warnings-as-errors written into the source versus set as a build flag (Code Complete against the rust-unofficial #![deny(warnings)] anti-pattern); whether a failing test may be disabled (Continuous Delivery and Clean Code against, SEG23 'CI Is Alerting' and the Takeout case for disabling that is tracked with a bug); and whether @ts-expect-error is allowed (Google tsguide bans it, typescript-eslint allows it with a description). Opened: SEG ch. 8, 9, 11, 18, 20 and 23; SWEBOK V3 Construction, Quality and SCM; the 97 Things essays; Google pyguide, tsguide and eng-practices; the Uber Go guide; the Go FAQ, vet and go test docs; the rust-unofficial patterns book; the OpenSSF criteria, which quote PP's debugging passage verbatim; Zampetti 2020 and Brittany Johnson's 2022 talk on neverworkintheory; and the aposd-vs-clean-code discussion, which says nothing on this topic. Not opened, so recorded from memory as unfetched paraphrases: PP 20th ed. Topics 3 and 51, Clean Code ch. 17, Code Complete ch. 23 and 29, Effective Java Item 27, Continuous Delivery ch. 3 (my recollection of its 'ratcheting' warning count is the least certain), Fowler's CI article and Sadowski et al. CACM 2018. ## Reception layer

Every item comes from GitHub-hosted sources fetched with curl: tool rule pages, official tool and language docs, project contribution policies (Linux, CPython, Gentoo) and the CC-licensed canon (SEG ch. 20 and 23, 97 Things). The WebSearch budget was spent, so no Hacker News, Lobsters or named-blog threads and no 2024–2026 surveys were reached; freshness was checked instead against tool docs on main/master (ESLint bulk suppressions, Ruff range suppressions, PMD UnnecessaryWarningSuppression 7.14.0, clippy ignore_without_reason 1.88.0, Cargo 1.97 CARGO_BUILD_WARNINGS, javac -Werror:key, CPython's warning-count baseline). Tools agree on cleaning up suppressions. Every one of the five languages has a check for unused suppressions: TypeScript @ts-expect-error, Rust #[expect], staticcheck and ESLint report them by default, while Ruff RUF100, Pylint I0021, mypy unused-ignore and pyright leave them off, even in pyright's strict mode. These checks share one Limit: a suppression needed only on some platforms or toolchain versions, or by another tool, reads as unused. Only staticcheck requires a reason on every suppression; clippy, typescript-eslint, nolintlint and eslint-comments make it opt-in or a minimal 3-character description. The canon disagrees in four places: (1) whether a warning level that does not fail the build should exist (Go FAQ and SEG ch. 20 say no; ESLint and Error Prone keep one for uncertain checks); (2) where warnings-as-errors belongs (the Linux kernel turns it on by default; Gentoo and rust-unofficial/patterns keep it in CI, not in builds others compile); (3) TypeScript suppression directives (the TypeScript team allows @ts-ignore during upgrades; typescript-eslint allows only described @ts-expect-error; Google bans both outside tests); (4) disabling failing or flaky tests (SEG ch. 23 accepts disabling tracked with a bug, while Zampetti et al. 2020 and jest no-disabled-tests take the stricter line). The 'no new warnings' baseline (SEG ch. 20, golangci-lint new-from-rev, ESLint bulk suppressions, CPython) goes unchallenged in what was opened, except partly by Brodwall's zero-tolerance essay.

## Evidence layer

I found evidence for all eight candidate rules, mostly as language and tool documentation that can be opened, across Java, Python, TypeScript, Go and Rust. Each language has its own way to name the rule being suppressed, attach a reason, and report a suppression that no longer suppresses anything: JDK SuppressWarnings/Checkstyle/SpotBugs; Ruff/Pylint/mypy/Python warnings; typescript-eslint/ESLint/TypeScript 3.9; staticcheck/golangci-lint/go vet; and rustc/Rust Reference/clippy. Most of this is off by default or optional, so a card must not say that tools require it. The research abstracts were opened through copies hosted on GitHub, not through the publishers. They show that 50.8% of suppressions in the Hu et al. FSE 2025 sample suppress nothing and may hide future warnings, and Liargkovas et al. 2023 find false positives explain only a minor share of suppressions. Analyzer findings that break a CI build are usually fixed rather than disabled (Zampetti 2017). Testing is the leading reason builds fail, and CI does not replace running tests locally (Beller 2017). Flaky tests make test results hard to rely on, and restarting builds triples merge time (Luo 2014, Eck 2019, Durieux 2020). Several sources push back: Kim & Ernst 2007 find about 90% of analyzer warnings are likely false positives. Trautsch 2020 finds that having PMD in the build has only a small, non-significant effect on warning removal (though defect density looks better). Beller 2016 finds most projects do not enforce a strict analyzer policy. ESLint's own docs describe warn as a legitimate transitional level, and the TypeScript 3.9 notes accept ts-ignore in named cases. TypeScript's strict doc lets you turn off individual checks, and SEG ch. 23 argues for accepting test disablement that is tracked. I found no study that measures the effect of weakening a strictness setting to make a change pass. SEG ch. 18 has no statement on warnings, WebSearch was unavailable, and the authors of arXiv:2311.07482 and the DOI of Beller 2016 come from memory.

## Spine — candidate rules in source order

1. **A change to a build or check script relies on no host-specific absolute path or system binary, derives no output from timestamps or build ids, and does not write into the source tree** — Build and check scripts are code, and a change to them keeps the build isolated from the host it runs on. Pinning dependency versions belongs to dependency-management; the design of CI pipelines stays outside the corpus.
