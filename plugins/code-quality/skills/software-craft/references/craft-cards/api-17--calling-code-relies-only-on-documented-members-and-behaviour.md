# Calling code relies only on an API's documented public members and guaranteed behaviour, never on an internal member or on behaviour the documentation leaves unspecified

## Thesis
Code that calls an API from outside the API's own module uses only the members the API's documentation presents as public, and depends only on behaviour that documentation guarantees for every version the code supports. A member is internal when the documentation leaves it out or declares it internal, when its name carries its language's internal-use marker such as a leading underscore, when it sits in a package, module or class that is itself internal, or when the caller can reach it only around an access check — through reflection, through an index by name that the type checker lets past a private modifier, or through a linker directive. A name that a module only imports is internal to that module unless the module documents it as part of its interface. Behaviour the documentation leaves unspecified includes the iteration order of a hash map or a set whose documentation promises no order, the identity of a returned object where the documentation promises no single instance, and any behaviour the documentation or the release notes call an implementation detail not to be relied upon; such behaviour becomes usable once the documentation of every version the code supports guarantees it. A test that calls the API from outside its module is calling code and is held to the same rule, and a test that depends on unspecified behaviour is held to it wherever it sits.

## Rationale
An API's backward-compatibility guarantees apply only to its public interface: its maintainers commit to avoid incompatible changes to the members they expect unrelated clients to use, and make no guarantee that a non-public member stays present, keeps its type or its behaviour, or is not removed. The API of a widely used library usually outlasts its implementation. One platform's compatibility promise states the consequence for calling code: code written to its specification is intended to keep compiling and running across releases, code that depends on unspecified behaviour may break in a future release, code that depends on a bug that violates the specification may break when the bug is fixed, and the platform reserves the right to change its implementation in ways that break code depending on its internal properties. Bypassing an access check through reflection can break the internal contracts of the accessed target and lead to maintainability issues and runtime errors. Unspecified behaviour can hold where the code is written and fail elsewhere: identity checks against literals can often work by accident on one implementation although the language specification does not guarantee them, iterating over a set can produce its elements in a different order than expected, and while one language left map iteration order undefined, the order differed across hardware platforms, which made tests that iterated over maps fragile and non-portable — a test might always pass on one machine but break on another. That language then defined the order to be unpredictable even when the same loop runs several times over the same map, so that code depending on it is very likely to break early and be fixed long before it becomes a problem. Holding calling code to the documented surface keeps it inside what the API's maintainers have committed not to change incompatibly.

## Example
```python
bad:  # Catalog.tags() is documented to return a set
      first = next(iter(catalog.tags()))
      total = catalog._index.size
good: # Catalog.tags() is documented to return a set
      first = min(catalog.tags())
      total = catalog.size()
```

## Limits
Code inside the boundary that marks a member internal is not calling code: a type's own methods, including one that reads the internal member of another instance of the same type, and, for a member internal to a package or a source subtree, the code of that package or subtree. A test placed inside that boundary where the language grants it access — a test file in the same package, a test module nested in the module under test — reads internal members as the module's own code does. Whether private functions should be tested directly is debated, and one language's documentation presents index-by-name access to a soft-private field as an easier route for unit tests; a project context that lets tests read internal members from outside the module rejects the finding for those reads, while a test that depends on unspecified behaviour stays fragile wherever it sits. The documentation decides, not the spelling: a member the documentation declares public is public despite a leading underscore — a process-exit routine, the methods of a named tuple that carry the underscore only to avoid clashing with field names — and a member the documentation designates for subclasses is open to a subclass. A name that a module re-exports as an explicitly documented part of its interface, such as a package's entry module that exposes functionality from its submodules, is public. An order the documentation of every supported version guarantees is public behaviour, such as a dictionary's insertion order once the language specification declares it, for code that supports no earlier version.

## Validator
Grep the hunk's added lines for a member whose name starts with an underscore reached through a receiver other than the enclosing type's own (self, cls, this); an import of an underscore-prefixed name or through a path segment named internal; a lookup of an underscore-prefixed attribute by name; a reflective call that lifts an access check or fetches a declared field or method by name; a cast to an untyped value followed by a member access; a linker directive; an identity comparison against a literal, a call result or an empty-value factory; and a first element taken from a collection's iteration. For each hit, open the file and resolve the declaring module of the receiver's type or of the imported name. Skip an access inside the type that declares the member, inside the package or source subtree that marks it internal, or in a test file of the same package or a test module nested in the module under test, and skip a test's read of an internal member when the project context lets tests read internal members. For a member or an imported name, read the declaring module's documentation — its doc-comments, its export list, its reference pages — and skip it when the documentation declares it public, designates it for subclasses and a subclass reaches it, or re-exports it explicitly. For an iteration, resolve the collection's type and read whether its documentation guarantees an order in every version the project supports; for an identity comparison, read whether the documentation promises a single instance. Validator question: **Does an added line outside the API's own module reach a member the API's documentation does not present as public, or does an added line outside that module or in a test depend on an iteration order, an object identity or another behaviour that the documentation of a supported version leaves unspecified?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-17`, severity major, `file`, `symbol`, `code` = the added line that reaches the internal member or depends on the unspecified behaviour, quoted verbatim from the diff, `fix` = the same operation through a documented public member, or with the order or identity made explicit — a sort, a documented ordered collection, an equality or emptiness test — in the file's language, `rationale` = the member or behaviour relied on and the documentation statement that leaves it internal or unspecified).
