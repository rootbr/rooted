# Integer arithmetic that can exceed the range its type holds exactly, including an intermediate result computed in a narrower type before widening, is widened first or checked, and wraps or saturates only where that is its intended result

## Thesis
Integer arithmetic whose operands are not bounded so that the result and every intermediate result fit the type that computes them takes one of three forms. It is computed in a type that holds the result, with an operand widened before the operation, because an expression of narrow operands is computed in the narrow type even when its result is assigned, returned or converted to a wider one. It is checked: the operands are tested against the type's limits before the operation, or an overflow-detecting operation reports overflow as an exception, an absent value or a flag instead of a wrong number. Or it wraps or saturates because that is its intended result, as in a hash function, written with the explicit wrapping or saturating operation wherever the language treats reliance on implicit wrapping as an error. The range is the fixed width of a fixed-width integer type, and the exact integer range, magnitudes up to 2^53 − 1, of a number type that holds integers as 64-bit binary floating point.

## Rationale
Where ordinary integer arithmetic is defined to wrap, an operation may legally overflow: the resulting value is deterministically defined by the integer representation and overflow does not cause a run-time panic, so the program continues with that value. Where overflow is treated as a program error, a debug build panics at run time and a release build wraps, so the program does not panic but holds a value that probably is not the one expected. A number type that holds integers as 64-bit binary floating point does not wrap: the exact result is replaced by the closest representable value, and every integer above 2^53 − 1 shares its value with at least one other integer, so 9,007,199,254,740,992 and 9,007,199,254,740,993 become one value. An expression of narrow operands is computed in the narrow type and widened to the destination's type as the final step, so its intermediate results may overflow: the nanoseconds in a day, 24 × 60 × 60 × 1000 × 1000 × 1000, wrap around to −1,857,093,632 in a signed 32-bit type instead of 86,400,000,000,000, and a signed 32-bit count of seconds multiplied by 1,000,000,000 starts overflowing around 2.15 seconds. Static analysis flags both shapes: a compile-time constant expression that overflows at error severity, and an expression of 32-bit operands assigned, returned or cast to a 64-bit type as a warning. An empirical study of integer overflow with a dynamic checker, in programs of two languages where signed overflow is undefined, found over 200 distinct locations in the SPEC CINT2000 benchmarks where overflow occurs; intentional uses of wraparound were more common than widely believed, a large number of accidental overflows also occurred, overflow issues were common even in mature, widely used programs, and overflow bugs may lead to fatal errors or exploitable vulnerabilities. Since not all overflows are bugs, an explicit wrapping operation identifies code that wraps on purpose, so that overflow checks can be enabled with minimal risk of intentional overflows leading to a panic and without code that had come to rely on wrapping breaking when stricter checking is enabled. Checking every operation is not the rule: detecting overflow statically is not practical and detecting it dynamically can be costly, so the default dynamic check is tied to debug assertions as a safety check too expensive to perform on all code, and the lint that flags every arithmetic operation sits in an opt-in category whose lints may flag perfectly reasonable code. The rule therefore reaches arithmetic whose operands are not bounded so that the result fits, where widening an operand keeps the value exact and an overflow-detecting operation turns the overflow into an exception, an absent value or a flag at the point where it happens.

## Example
```typescript
bad:  function toNanos(millis: number): number {
          return millis * 1_000_000;
      }
good: function toNanos(millis: number): bigint {
          return BigInt(millis) * 1_000_000n;
      }
```

## Limits
Arithmetic whose operands the code bounds so that the result and every intermediate result fit is correct as written: choosing the type and the algorithm to avoid overflow is the documented best practice, a test of the operand against the type's bound before the operation is an accepted form, and where the guarded operation clamps at that bound its builtin saturating equivalent is preferred for simplicity and readability, and the lint that flags every arithmetic operation ignores non-constant operations that will not overflow. A type of unlimited range, a built-in integer type limited only by available memory or an arbitrary-precision integer type not limited to a bit width, does not overflow, and arithmetic in it is outside the rule. Wraparound is the desired result in a limited number of cases, such as hash functions, and many overflows are intentional. Where the language defines ordinary integer arithmetic to wrap, such a computation is correct as written: unsigned operations there are computed modulo 2^n and programs may rely on the wrap, signed overflow yields a deterministically defined value, and a standard library specifies its string hash as a polynomial computed in its fixed-width int arithmetic. Where the language treats reliance on implicit wrapping as an error, the computation uses the explicit wrapping operation instead. Checking every arithmetic operation is stricter than the rule and is a project's choice, since the lint that does so belongs to a category not meant to be enabled as a whole. A project context that states its numeric inputs are bounded at a named validation boundary, or that overflow checks are enabled in every build so that an overflowing operation panics instead of wrapping, rejects the finding for the arithmetic it covers, except a computation whose intended result is the wrapped value, which those checks turn into a panic and which keeps its finding. Floating-point results beyond a floating-point type's range, division by zero and the conversion of a finished value into a narrower type are outside the rule.

## Validator
Grep the added lines for integer arithmetic that can grow large: a multiplication, addition, subtraction or left shift whose result is assigned, returned or converted to a wider integer type; a multiplication with a literal of four or more digits; an expression next to a type's limit constant. Open the file and, for each candidate, find the type in which each operation is computed, which is the operands' type and not the destination's, and that type's range: the fixed width of an integer type, or magnitudes up to 2^53 − 1 for a number type that holds integers as 64-bit binary floating point; drop an operation in a type of unlimited range. Name the largest magnitude each operand can take, from a constant, from a range test or bound earlier in the routine, or from the quantity it holds, such as a timestamp, a duration in a fine unit, a byte count, a count with no upper limit or an identifier, and drop the operation when those bounds keep the result and every intermediate result within range. Drop an operation computed after an operand was widened into a type that holds the result, one that uses an overflow-detecting operation or follows a test of its operands against the type's limits, and one that uses an explicit wrapping or saturating operation. Drop a computation whose intended result is the wrapped value, such as a hash, where the language defines its ordinary integer arithmetic to wrap; keep it where the language treats reliance on implicit wrapping as an error. Drop arithmetic a project context exempts. Validator question: **Does an added integer operation compute a result or intermediate result that its operands' possible values can carry past the range of the type that computes it, with no operand widened beforehand into a type that holds the result, no overflow check, no explicit wrapping or saturating operation, and no intended wraparound in a language that defines its ordinary integer arithmetic to wrap?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-30`, severity major, `file`, `symbol`, `code` = the added arithmetic expression quoted verbatim from the diff, `fix` = the same computation with an operand widened before the operation, done with the language's overflow-detecting operation or behind a test of the operands against the type's limits, or written with the explicit wrapping or saturating operation where wraparound is the intended result, in the file's language, `rationale` = the type that computes the operation and its range, the operand values that can carry the result past it, and what the overflow turns the result into: a wrapped value, a panic or a rounded integer).
