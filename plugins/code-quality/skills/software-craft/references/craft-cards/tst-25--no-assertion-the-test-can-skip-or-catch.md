# No assertion in a test sits where the test can pass without running it or with its failure caught, as in a conditional branch, a catch or except block, or a callback or promise the test does not wait for

## Thesis
Every assertion a test writes executes on every run in which the test passes, and a failure it raises fails the test. Each assertion therefore sits where every passing run reaches it and where nothing traps its failure: not under a conditional branch or in a catch or except block that a passing run can skip, not in a callback or promise chain the test does not wait for, and not in the try block of a handler that catches the assertion's own failure type or a supertype of it and then neither tests a property that tells the expected error apart from the assertion's own failure nor hands it on to the runner. An expected exception or error is checked with a construct that fails when nothing is raised.

## Rationale
A runner marks a test failed only when the test raises an error or reports a failure while it runs, so an assertion placed in conditional code can leave the test passing without testing anything. A condition that is not met leaves test statements unexecuted, which leads to situations where the test fails to detect defects in the production code. When the catch block of an expected-exception check holds the assertion and nothing in the try block fails the test after the call, the test passes if the exception is never raised or if it is raised with the expected message; a construct that fails when the exception is not raised closes that gap. When the test neither awaits nor returns a promise, it completes before the promise resolves or rejects, and a test that does not wait for a callback completes as soon as the called routine returns, before the callback is ever called. A handler around an assertion that catches the assertion's failure type or a supertype of it, tests no property that tells what it caught apart from the assertion's own failure, and neither rethrows it nor passes it to the runner's completion callback traps the failure, and the test never fails. Conditional code in a test also negatively impacts the ease of comprehension: conditionals tend to make tests more brittle and complex, as they increase the effort needed to understand what is actually being tested. The rule restores the property that a passing test has run its assertions.

## Example
```go
bad:  err := Parse(input)
      if err != nil {
          if !errors.Is(err, ErrSyntax) { t.Errorf("error = %v, want ErrSyntax", err) }
      }
good: err := Parse(input)
      if !errors.Is(err, ErrSyntax) {
          t.Errorf("error = %v, want ErrSyntax", err)
      }
```

## Limits
A check written as a condition whose body reports the failure is one assertion: the condition states the expectation and the report runs whenever the expectation is false; a guard around such a check is what the rule reaches. A fail call placed right after a call expected to raise is likewise the failure report of the expectation that the call raises, and runs whenever the call returns normally. An assertion in a finally block, and a condition inside a helper or production routine that the test calls while its own assertion stays unconditional, are outside the rule. A try block that fails the test right after the call expected to raise, under a handler for a type that is neither the assertion's failure type nor a supertype of it, makes the handler's assertion run on every passing run, although the expected-failure construct is preferable and the least error prone. A handler that catches the assertion's own failure type or a supertype of it keeps the test able to fail when it goes on to test a property that tells the expected error apart from the assertion's own failure, such as its message. Where the expected-failure construct checks too little, such as the message alone, a wrapper that runs the call, returns what it raises, and returns a specific no-error-thrown error when nothing is raised lets the test assert on the error unconditionally, first checking that it is not that no-error-thrown error. A declared count of the assertions the test expects to run makes a fulfilled promise fail the test when the expected rejection's assertion is skipped; lint guidance notes that such counts combined with conditionals typically add complexity. A callback that the receiving call runs before it returns and a callback whose completion the runner waits for, such as a subtest body, are on the test's path.

## Validator
Grep the hunk for assertion calls and failure reports, and for conditional keywords, catch or except handlers, error-is-present checks, promise continuations and callbacks passed inside a test body. Open the test file and, for each assertion the hunk adds or moves, walk outward to the test body, noting each enclosing conditional branch, catch or except block, callback or promise chain, and each handler whose try block contains the assertion. Set aside a condition whose body is the failure report of that same condition, a fail call placed right after a call expected to raise, and a finally block. For a branch or handler, trace whether a run that skips it ends in a failure: a fail call after the call expected to raise, or a declared assertion count. For a callback or promise, trace whether the test waits for it: the call that receives the callback runs it before returning, the test awaits or returns the promise, or the runner waits for the callback to complete, as for a subtest, or for a completion callback that the callback calls. For a handler whose try block contains the assertion, check whether it catches the assertion's failure type or a supertype and whether it then tests a property that tells the expected error apart from the assertion's own failure or hands the error on to the runner by rethrowing it or passing it to the test's completion callback. Validator question: **Can this test pass on some run without executing one of its assertions, or with an assertion's failure caught before it reaches the runner?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-25`, severity major, `file`, `symbol`, `code` = the assertion line and the line of the condition, handler or callback that encloses it, verbatim from the diff, `fix` = the assertion moved onto every passing path, as the expected-failure construct, an unconditional check of the returned error, or the awaited or returned promise, in the file's language, `rationale` = names the run on which the test passes without the assertion executing or with its failure caught).
