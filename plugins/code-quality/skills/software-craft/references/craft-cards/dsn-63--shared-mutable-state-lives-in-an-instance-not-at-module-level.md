# Mutable state that otherwise independent components change or observe lives in an instance each client creates, not in a static, module or package-level object

## Thesis
A mutable object that two or more otherwise independent components change, or observe another component changing — a collection, registry, cache or singleton held at static, module or package level — lives instead in an instance that each client creates and passes explicitly, as a dependency, to the code that uses it. Mutable state kept at static, module or package level nonetheless, in a rare case the Limits name as warranted, is internal to its module, is reached from outside the module only through the module's functions, and carries a comment, or a document a comment links to, that states the design reason for keeping it there.

## Rationale
Functions that are otherwise independent, even ones written by different authors in distant parts of the codebase, can interact through a module-level object when they run in the same program, and independent test cases can interact through it the same way: a test that registers a replacement leaves it registered for the tests that run after it, which creates an order-dependent test case, breaks runs with test filters, and prevents tests from running in parallel or being sharded. A single module-level instance also makes it difficult to run two separately operating sets of that state in one process — two database connections open at once to compute differences during a migration, or a separate set of plugins for each of several servers — and leaves open which registration wins when two clients register under the same name. Clients may have to respect ordering requirements as well, such as whether initialization has run or flags are parsed yet, and where a language runs module-level assignments when a module is first imported, importing it can change the module's behaviour. A mutable collection held in a field declared constant can still be changed, by malicious code or by accident from another package; wrapping it as an unmodifiable collection avoids that. Professional developers interviewed about immutability stated that incorrect state mutations are a major source of bugs, for example an object thought to be immutable changed by some other object because references were reused instead of immutable copies. With an instance per client, each client instantiates the state it needs and passes it on as an explicit dependency, and a test sets a replacement on the instance it created, leaving no module-level value to overwrite and restore afterwards.

## Example
```python
bad:  handlers = {}  # every importing module adds to it
      def dispatch(event): handlers[event.kind](event)
good: class Dispatcher:
          def __init__(self): self._handlers = {}
          def register(self, kind, handler): self._handlers[kind] = handler
          def dispatch(self, event): self._handlers[event.kind](event)
      def main():
          dispatcher = Dispatcher()
          dispatcher.register("order", handle_order)
          serve(dispatcher)
```

## Limits
State that is logically constant is outside the rule, and a field declared constant counts as such only when the object it holds cannot be changed. A private module-level cache behind a function whose callers cannot distinguish cache hits from misses is outside it too, since the module's observable behaviour stays stateless, and so is state from which no caller expects predictable behaviour, such as a default source of random numbers. A registry that otherwise independent components fill is warranted at module level only when the entries they register are stateless, idempotent and pure, no test replaces an entry and registrations under one name rarely collide, and it is then internal, reached only through its module's functions and explained in a comment, or a document a comment links to; a comment alone warrants no other shared object. A module-level default instance offered for convenience is acceptable, though not recommended, where no otherwise independent components or test cases interact through it, no test swaps it for a replacement and no caller depends on the order of initialization, and four conditions hold: the module also lets clients create isolated instances of the same type, the module-level functions are thin proxies that forward to that instance, only an executable program's own code calls them — not a library, unless the library is being refactored to pass the dependency explicitly — and the module documents and enforces their invariants, such as at which stage of the program they may be called, and offers a function that resets the default instance to a known-good state. Existing module-level state elsewhere in the codebase is no tolerance: legacy code that departs from the rule is not a precedent for continuing the pattern. A project context that states the design reason for a named module-level object is a documented tolerance and rejects the finding for that object. The rule judges the mutable object a module-level name holds, not the scope, naming or reassignment of the name itself, and it does not settle whether the object is safe under concurrent access.

## Validator
Grep the hunk's added lines for state declared at static, module or package level: a static field that is not constant, a constant field initialised with a newly built collection, a module-level assignment of a list, map or set, a module-level mutable binding or package-level variable, a static with interior mutability, a `global` statement, a class-level collection, and a singleton accessor or once-initialised instance. For each such object that can change, open its usages across the repository and list the components that change it and those that read it, counting separate test cases as separate components. Skip the object when it is logically constant, when it is a private cache whose callers cannot tell hits from misses, when no caller expects predictable values from it, when it is an internal registry, reached only through its module's functions and explained in a comment or a document a comment links to, whose entries are stateless, idempotent and pure, which no test replaces and whose registrations rarely collide, or when it is a default instance through which no independent components or test cases interact, which no test swaps and whose use depends on no initialization order, whose module also offers the instance type and forwards to it through thin proxies, which is called through those proxies only from an executable program's own code or from a library being refactored to pass it explicitly, and whose module documents and enforces the proxies' invariants, such as at which stage of the program they may be called, and offers a function that resets it to a known-good state. Then check whether code outside the owning module can change the object directly — a public field or module attribute, an exported variable, a constant field holding a modifiable collection — and, for an internal object, whether two or more otherwise independent components change it or observe one another's changes; a comment alone does not excuse that interaction, though a project context that states the design reason for the named object does. Treat existing module-level state elsewhere in the codebase as no precedent. Validator question: **Is a mutable object held at static, module or package level in this hunk either changeable directly from outside its owning module, or internal to that module but changed by one otherwise independent component and changed or observed by another?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-63`, severity major, `file`, `symbol`, `code` = the declaration of the module-level object quoted verbatim from the diff, `fix` = the state moved into a type that each client constructs and passes as a parameter, in the file's language — or, where module-level state is warranted, the object made internal, changed from outside only through its module's functions, with a comment stating why, `rationale` = which components change or observe the object, or which outside code can change it directly, and what one of them sees change because of another).
