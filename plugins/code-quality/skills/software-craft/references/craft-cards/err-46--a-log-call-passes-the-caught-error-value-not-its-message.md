# A log statement that records a caught exception or error passes the exception or error value itself to the logger, not only its message string, and does not repeat that message in the text

## Thesis
A log statement that records a caught exception or a received error passes the exception or error value itself to the logging call whenever its logging facility accepts such a value: as the facility's exception argument, through a method that logs the exception being handled, or as a field that captures the value as an error. The message text taken from the value and spliced into the statement's text does not stand in for the value. With the value passed, the statement's text names the event and its context and leaves the error's message to the value.

## Rationale
An exception or error carries more than its message: a record of it can hold the message, the type of the exception and a stack trace in the natural representation of the language runtime. For a record emitted through a telemetry standard's logging API, where a language's implementation of that API supports passing exception instances to the call that emits the record, the instance should be provided rather than its parts set by hand as individual attributes, and that guidance is recommended to application developers as well as to instrumentation. An exception passed to the facility adds its exception information to the record: a method that logs the exception being handled records the exception and its traceback, while an error-level call without it leaves the traceback out, and the traceback is often useful for debugging. A record built from the message alone preserves only the message: the exception is lost to the record, and the log event is not enriched with the exception. Structured facilities offer a field for the value: a key-value pair can capture its value as an error, and one handler gives a field whose value is an error a treatment of its own, formatting it through the error's message method; for an error that wraps another, instrumentation may record the inner exception's type when the wrapper's type is not meaningful for classifying the failure. Text that repeats the message of an exception passed beside it bloats the record with a duplicate exception message: the exception is logged with the record anyway, so including it in the text again is redundant and can lead to excessive logging.

## Example
```go
bad:  if err != nil {
          slog.Error("load failed: "+err.Error(), "id", id)
      }
good: if err != nil {
          slog.Error("load failed", "id", id, "err", err)
      }
```

## Limits
The rule asks for the value where the facility supports passing it; a facility that records only formatted text, with no argument or field for an exception or error value, is outside it, and one facility's own documentation splices the error into the text where its structured values are not enabled and captures the value as an error where they are. An exception that is arguably used to indicate a nonexceptional outcome, such as a number, a date or a URL that fails to parse, or an interrupted wait, may be left unhandled, as when a failed parse falls back to a default value, and a handler for it is outside the rule; so is an artificial exception that a library, framework or runtime generates for an operation that ends with an unsuccessful error code, which instrumentation should not record where possible. One tool rule raises no issue when the exception's message is logged together with added context, taking that as a sign that the developer added context to the error message; a project that states this tolerance accepts such a record, and without it the record is a finding, since guidance for another facility marks the message logged beside a user identifier as preventing the log event from being enriched with the exception. Whether a handler records the failure or passes it on, whether it prints a stack trace in place of a log statement, at which layer and level the record is written, which identifiers its text carries, and whether the exception's message or stack trace may contain sensitive information are judged by their own rules.

## Validator
Grep the added lines for a log call inside a catch, except or rescue block, a branch taken when an error is present, or the error arm of a match, and for text taken from a caught exception or received error: a get-message call, a string conversion of the exception, an error-message method or message property, a to-string call. For each hit, read the hunk to find the handler and its exception or error variable, and read the call and its receiver in the hunk to identify the logging facility and the argument, method or field it offers for an exception or error value. Skip the call when the facility records only formatted text; when the caught exception is a kind arguably used for an ordinary outcome, such as a number, date or URL that fails to parse or an interrupted wait; when it is an artificial exception that a library, framework or runtime generates for an operation that ends with an unsuccessful error code; and when `project_context` states a tolerance for an exception message logged with added context and the call adds context. Validator question: **Does an added log statement that records a caught exception or received error, through a facility that accepts the exception or error value, pass that value through none of the facility's exception argument, exception-logging method or error field, or pass it through one of them and repeat its message in the text?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-46`, severity minor, `file`, `symbol`, `code` = the added log call, verbatim from the diff, `fix` = the same record with the exception or error value passed through the facility's exception argument, exception-logging method or error field, and text that names the event and its context without the error's message, in the file's language, `rationale` = what the record loses, the exception or error value with its type and, where the language captures one, its stack trace, or the message it duplicates).
