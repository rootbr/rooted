# A security-relevant setting stays secure by default, so an option the change adds for new behaviour defaults to its secure value and the change does not switch off an existing secure default

## Thesis
A security-relevant setting that the change introduces together with the behaviour it governs, such as certificate or hostname verification, output autoescaping, CSRF protection or access to an object, starts in its most secure state, and its unsafe value, where the API offers one at all, requires explicit acknowledgement in the API. Wherever the code handles what a protection guards, such as HTML output for autoescaping, browser requests for CSRF protection or a TLS connection for certificate verification, the change keeps each existing secure default of that protection, of its own code or of a library it calls, switched on, and each configuration it creates turns on such a protection that the library ships switched off. When an error condition is detected in a check, the check falls back to the secure state, so an entity without explicit access to an object is denied access to it.

## Rationale
A default decides the behaviour of every caller that leaves the option unset. Among 11,748 Android apps that use cryptographic APIs, 10,327 (88%) make at least one mistake; using ECB mode is the most frequent violation, and its primary cause is developers using the provider's default values. In 5,656 apps the developer specifies only a block cipher and the provider configures the cipher in ECB mode. A secure default is also lost when calling code overrides it: two payment libraries that attempted to enable hostname verification accidentally overrode the HTTP library's correct default value and disabled it, and accepted answers in a study of secure-coding posts on a programming Q&A forum contained code that disabled the default protection against CSRF attacks and bypassed certificate validation. When certificates are not verified, an attacker could intercept and modify the traffic between client and server. A protection that is off by default needs the caller to turn it on, and developers may not realize that they must explicitly choose certain options to enable certificate validation; a template engine that leaves autoescaping off by default recommends configuring a sensible default for it. Software that starts in a secure state needs no extensive user configuration to be secure.

## Example
```typescript
bad:  export function openClient(url: string, verifyTls = false) { ... }
      const agent = new https.Agent({ rejectUnauthorized: false });
      try { return acl.allows(user, doc); } catch { return true; }
good: export function openClient(url: string, verifyTls = true) { ... }
      const agent = new https.Agent({ rejectUnauthorized: true });
      try { return acl.allows(user, doc); } catch { return false; }
```

## Limits
The most secure setting is not necessarily the most user-friendly one, and what a setting's default should be is evaluated through risk analysis and usability tests. An API the change adds may still offer the unsafe value to a caller that acknowledges it explicitly; the rule keeps the default secure and leaves the explicit opt-in available. A protection is switched off only where the code does not handle what it guards: a template engine enables and disables autoescaping per template, HTML versus text, and a security framework recommends CSRF protection for any request a browser could process and says a service used only by non-browser clients likely wants it disabled. Changing a default that existing callers already depend on is contested, and projects have decided it both ways. One standard library turned on certificate verification by default in its HTTP clients, accepting that some HTTPS connections raise an exception during the handshake, and another's process-execution package stopped resolving programs relative to the current directory, keeping an environment setting that temporarily restores current-directory resolution for programs unable to apply more targeted fixes. Changing a random module's default generator, considered as an alternative, met considerable scepticism and outright opposition, including objection to a backwards-incompatible change, and the secure generator went into a separate secrets module. The separating condition is whether the behaviour a setting governs already has callers: a setting introduced together with its behaviour has no caller relying on an insecure value, so it starts secure; where callers already rely on a behaviour, through a library default or through the change's own code that ran without the protection, the change keeps a secure default on and does not weaken it, while making an insecure behaviour that callers rely on secure by default stays that project's compatibility decision. The choice of protocol versions, cipher suites and other cryptographic parameters beyond keeping verification on belongs to cryptographic and protocol design, outside the rule's reach.

## Validator
Grep the hunk for a verification, hostname, CSRF or autoescaping switch set to its off value (`verify=False`, `rejectUnauthorized: false`, `InsecureSkipVerify: true`, `CERT_NONE`, `autoescape=False`, an allow-all hostname verifier, a CSRF exemption), for an option named insecure, unsafe, skip-verify, no-verify or disable-ssl set true, for an error branch that returns true, and for a new parameter, field or option whose name carries verify, secure, validate, escape, ssl or tls with a default of false. Open each match at hunk scope and decide whether the off value is the default of a setting the hunk adds together with its behaviour, a weakened existing secure default or an override of a library's secure default, for output, connections or requests that the protection guards; a protection switched off where the code does not handle what it guards, such as escaping for a plain-text template or CSRF protection for a service only non-browser clients call, is not flagged, and an insecure default the hunk keeps for behaviour that existing callers rely on is that project's compatibility decision and is not flagged. Trace each client, template-engine or framework configuration the hunk creates for a protection the library ships off and the hunk leaves off for the output or connections that protection guards, and trace each authorization or verification check the hunk adds through its error and fall-through paths to the value it returns. Validator question: **Does the hunk give a security-relevant setting it adds together with its behaviour an insecure default, weaken an existing secure default or switch off a library's secure default for what that protection guards, leave off a protection the library ships off in a configuration it creates for what that protection guards, or allow access on a check's error path?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-09`, severity major, `file`, `symbol`, `code` = the line that sets the insecure default, switches the library's protection off or returns allow on the error path, quoted verbatim from the diff, `fix` = that line with the secure value as the default, the library's protection left on or turned on, or deny on the error path, in the file's language, `rationale` = names the setting, the insecure value and the exposure it opens, such as traffic interception, cross-site request forgery or access granted on error).
