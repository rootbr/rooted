# A field named as a constant, or declared final or read-only and visible to other modules, refers to a deeply immutable value

## Thesis
A static or module-level field or binding that is named in the style its language reserves for constants, or that is declared final or read-only and is visible to code in other packages or modules, refers to a deeply immutable value. A deeply immutable value is a primitive, a string, an immutable value type, or an immutable collection whose elements are themselves immutable. Such a field never refers to a mutable array, collection or object. Where it has to carry a table, the table is built as an immutable collection, or wrapped in a read-only view or typed as read-only with no writable reference to it left elsewhere, or kept private behind an accessor that returns a copy. A field whose contents are meant to change is named in the variable style and kept out of the reach of other packages or modules, or, in a language that names every static item in the constant style, is declared as such a static item rather than as a named constant.

## Rationale
A final, constant or read-only declaration fixes the reference, not the object behind it: the name cannot be rebound, yet the contents of the array, collection or object it refers to can still be changed through it. Declaring the field final or read-only, or naming it as a constant, signals that its value is expected to stay fixed, which is then not the case. Under the convention that reserves the constant style for deeply immutable values, intending never to mutate the object is not enough; if any of its observable state can change, the field is not a constant. Deep immutability covers the elements too: an immutable collection or a tuple that holds mutable elements is not a constant, because those elements can still change. Visibility widens the reach: once the field is visible to other packages or modules, their code can change its contents, whether by accident or as malicious code. In interviews with professional developers about language support for immutability, participants stated that incorrect state mutations are a major source of bugs, for example an object thought to be immutable being changed by some other object because references were reused instead of immutable copies. Where a language copies a named constant at every use site, a change made through a constant whose contents can change through a shared reference is lost when the copy is dropped. An immutable collection, a read-only view with no writable reference to its table left elsewhere, or a private table behind an accessor that returns a copy each leave other code no way to change what the constant holds.

## Example
```python
bad:  ALLOWED_ROLES = ["admin", "editor"]
      RETRY_DELAYS: Final = [1, 2, 5]
good: ALLOWED_ROLES = ("admin", "editor")
      RETRY_DELAYS: Final = (1, 2, 5)
```

## Limits
A null reference and a zero-length array whose length is fixed at creation are constants, since such an array has no element to change and cannot gain one; an empty array or list that can grow is not. A type that holds mutable internals but offers no way to change them through its public interface has no observable state that can change, and counts as immutable; the project context can name such types. A static or module-level field that is named in the variable style and is not visible to other packages or modules is outside this rule, even when it holds a mutable collection. So is a local variable, which is not a constant even when it is final and immutable. A binding declared with a language's general form for any name that is not reassigned is not declared final or read-only by that form, because that form fixes only the binding and style guides recommend it for every name that is not reassigned; it comes within this rule only when it is named in the constant style. Where a language names every static item in the constant style, mutable or not, and documents a static item as the form for a value meant to be modified in place, such a static item is outside this rule; a named constant item in that language stays within it. Where a language's constants can hold only booleans, runes, numbers and strings, every declared constant already satisfies the rule, and a package-level variable is neither declared nor named as a constant, because constants there share the naming style of variables. Style guides divide on what the constant style promises: one holds that a field is a constant only when its contents are deeply immutable and that intending never to mutate it is not enough, while another lets the constant style name a value that is meant not to change but is not deeply frozen, to tell users not to modify it, and a framework that requires its setting names in that style keeps its sequence settings in lists by convention. Where the project context adopts the second convention, or the file is such a framework's settings module, a field that only its name brings within this rule is outside it; a declaration that is final or read-only and visible to other packages or modules stays within it, because code there can change its contents whatever its name.

## Validator
In the hunk, take each static or module-level declaration that a trigger matched and read its name, its modifiers and its initializer. Go on when the name is in the language's constant style, unless the project context adopts the convention in which that style may name a value that is not deeply frozen or the file is the settings module of a framework that requires its setting names in that style, or when the declaration is final or read-only, not merely the language's general form for a binding that is not reassigned, and visible to other packages or modules: public or protected, exported, or a module-level name without the private-name prefix in a language that marks privacy that way. Go on when the initializer builds an array with one or more elements, an empty array that can grow, a list, map, set, dictionary, date, string builder or other standard type whose methods change its state, or an immutable collection or tuple whose elements are such objects; for a named constant in a language that copies constants at each use, go on only when its type's contents change through a shared reference, since an array or collection without such contents cannot be changed through the constant there. Skip a primitive, a string, a null value, a zero-length array whose length is fixed at creation, an immutable collection or immutable factory result, a value frozen at creation, a read-only view or read-only type with no writable reference to its table left elsewhere, and a type the project context names as immutable through its public interface. Skip a local variable, a static item in a language that names every static item in the constant style, and an initializer that calls a routine or constructor whose result's mutability the hunk does not show. Validator question: **Does a field named as a constant, or declared final or read-only and visible to other packages or modules, refer to an array, collection or object whose contents can still change?** Yes → flag.
