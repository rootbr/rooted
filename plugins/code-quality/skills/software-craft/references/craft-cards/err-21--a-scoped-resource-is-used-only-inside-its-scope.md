# A resource bound by a scoped-release construct is used only inside that scope and is not returned, stored or captured by a callback that outlives it

## Thesis
A resource bound by the language's scoped-release construct — a block or a declaration that releases the resource when its scope exits, or a release deferred to the exit of the enclosing routine — is used only while that scope is open. The code does not return the resource from the scope, alone or inside an object that keeps a reference to it, does not assign it to a field or to an outer or module-level variable, and does not capture it in a closure or callback that runs after the scope exits, because each of these holders is left with a resource that has already been released. A resource meant to outlive the scope is handed on explicitly, so that it has one owner at a time and no release of it runs when the scope exits on the path that hands it on: the routine acquires it outside the construct and registers its release, if at all, only for the paths that fail before the hand-off, or it moves the registered release out of the scope's cleanup stack before it returns.

## Rationale
The construct runs the release whichever way control leaves the scope: a block-scoped construct when its block finishes, even if an exception is raised; a scope-bound declaration when its variable goes out of scope, at the very end of the containing scope or right before an early return or a thrown error; a deferred release immediately before the enclosing routine returns, whether it executes a return statement, reaches the end of its body or panics, so the scope of a deferred release is the whole routine. A return does not hold the release back for the caller: the result is set first, the release runs next, and only then does control return to the caller. The construct ties the release to the lexical scope, not to the value, and there are many ways to keep the value after its variable is out of scope — an alias declared without the construct, a closure, an export — so the holder keeps a reference to a resource that is already released: a returned closure that uses the resource always runs on a disposed resource, and a module that exports one always hands its importers a disposed resource. Files and sockets shared throughout a program may be read from or written to after logically being closed, and once they are actually closed those reads and writes raise exceptions. Using a released resource fails: closing a file renders it unusable for input and output, and attempts to use a closed file fail. The construct gives a resource static scope and works through a stack discipline, so it does not fit a resource that has to persist beyond its scope, and a resource returned to the outside is not closed where it is returned. A transfer out of a cleanup stack runs no release: it hands the registered releases to a fresh stack, and they run when that stack is closed.

## Example
```go
bad:  func openInput(name string) (*os.File, error) {
          f, err := os.Open(name)
          if err != nil { return nil, err }
          defer f.Close()
          return f, nil
      }
good: func openInput(name string) (*os.File, error) {
          f, err := os.Open(name)
          return f, err // the caller owns f and closes it
      }
```

## Limits
A value computed from the resource inside the scope and returned that holds no reference to the resource, such as data read from it, is computed before the release runs, and returning it is correct. A generator that implements the construct by yielding the resource from inside its own protected region does not leave the scope: the caller's block runs while the generator is suspended at the yield, and the generator resumes after that block exits and releases the resource then. A closure can take over the release by binding the resource with the construct inside its own body; the resource is then released after the closure is called, and never released if the closure is never called. In a language whose compiler checks ownership, returning a value transfers its ownership to the caller, and the compiler rejects, at compile time, a reference that would outlive the data it refers to. A step between a move out of a cleanup stack and the return that fails leaves the resource with no owner: a leak on a failure path, not a use of a released resource, and outside this rule. A resource used by another thread or task started inside the scope raises a question of synchronization, whether that use ends before the scope exits, which this rule does not settle.

## Validator
In the hunk, find each scoped-release construct: a block that binds a resource and releases it when the block exits, a declaration that releases its resource when its variable leaves scope, a release deferred to the routine's exit, and a resource registered on a cleanup stack. Open the file and settle, for each, the bound resource and the scope whose exit releases it: the block for a block-scoped construct, the enclosing block for a scope-bound declaration, the whole enclosing routine for a deferred release, the stack's own scope for a cleanup stack. Trace each reference to the resource inside that scope, and each use after the scope's exit through a name that stays visible past the construct — the bound name itself, or a name that held the resource before the construct bound it. Mark a use after the scope's exit by an operation that needs the resource open, such as a read or a write, and a reference inside the scope that carries the resource past the scope's exit: a return of the resource, alone or inside a returned object, wrapper or tuple that keeps a reference to it; an assignment to a field, to an outer or module-level variable, or to a collection that outlives the scope; an export; a closure or callback that captures it and is returned, stored or registered to run after the scope exits. Skip a returned value computed from the resource before the scope exits that holds no reference to it, such as data read from it; a closure called before the scope exits; a generator that yields the resource from inside its own construct to its caller's block; a resource acquired outside any construct and returned with no release registered, or with a release that runs only on a path that fails before the hand-off, such as a deferred release guarded by the routine's error result; a closure started on another thread or task inside the scope; and a closure that binds the resource with the construct inside its own body. A release moved out of a cleanup stack, whether the moved stack is handed on or dropped, counts as a transfer: the move runs no release. Validator question: **Does a resource bound by a scoped-release construct leave that scope — returned, stored in a field or an outer variable, exported, captured by a closure or callback that runs after the scope exits, or used after the scope exits, through a name that stays visible, by an operation that needs it open — while the construct still releases it when the scope exits on that path?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-21`, severity major, `file`, `symbol`, `code` = the line that returns, stores, exports or captures the scoped resource, or uses it after the scope exits, quoted verbatim from the diff, `fix` = the use moved inside the scope, or the resource acquired outside the construct and handed to the holder that outlives the scope — returned, stored or captured — with its release registered only for the paths that fail before the hand-off, or its registered release moved out of the cleanup stack as the last step before the hand-off, in the file's language, `rationale` = the holder that receives the resource after the scope's exit has released it, and the operation on it that then fails).
