# Code that retries a failed remote call waits between attempts with a delay that grows, is capped and is randomized, from the second retry on

## Thesis
Code that retries a failed call to a remote resource or another process, as a loop or a recursive call it writes, as a task it re-enqueues or a state-machine step it leaves for an executor to re-run, or as a retry policy it configures on a client or a retry helper, waits before every retry after the first. Each wait grows with the attempt number, as an exponential backoff multiplies an initial delay by a constant factor per attempt; the growth stops at a maximum delay; and a random term (jitter) varies each wait. The first retry may run at once or after a wait of any length. A retry after the first that runs with no wait before it, and a wait before such a retry that does not grow, grows without a maximum or has no random term, each break the rule.

## Rationale
Retrying with no delay between attempts leads to request flooding at server nodes, which can cause large-scale performance degradation or even service crashes. In a study of 70 retry bugs from the issue trackers of popular open-source distributed applications, about one third concerned the timing of retry, and 10 were retries with no delay between attempts. In one of them a failing state-machine step was retried with no delay and congested the executor, so that other procedures could not progress; restarting did not clear it, because procedures retain their state across a restart, and the fix added a delay that doubles with the attempt count. When a connection fails, it is typically desirable not to retry immediately, to avoid flooding the network or the server with requests, but to back off exponentially; one RPC framework's connection protocol requires any alternative algorithm to disperse backoffs that started at the same time and not to attempt connections substantially more often than its own exponential one. The same framework's retry design applies jitter of plus or minus 0.2 to each delay to avoid hammering servers at the same time from a large number of clients, and caps the growth: after the initial retry, the n-th attempt occurs after min(initial delay × multiplier^(n−1), maximum delay) × random(0.8, 1.2). A retry policy configured with no backoff retries at once: one HTTP client library disables backoff by default, so that its sleep between retries returns immediately, recommends for production services a non-zero backoff factor together with jitter to prevent overloading servers with immediate retries, and never lets a computed backoff exceed its configured maximum. A security cheat sheet asks webhook publishers for exponential backoff with jitter and a maximum retry count. In a simulation of clients that each update one record once under optimistic concurrency and retry after a conflict, averaged over 100 runs at 190 clients, exponential backoff capped at 2,000 time units and without jitter made 5,159 calls and took 101,399 time units until every client had succeeded, the same backoff with full jitter made 1,769 calls and took 7,421, and retrying with no wait finished first, at 3,541, but made 8,000 calls; at 50 clients the same three made 625 calls in 36,706 units, 332 in 2,939, and 688 in 1,142.

## Example
```typescript
bad:  for (let attempt = 1; ; attempt++) {
        try { return await fetchOrder(id); } catch (err) { if (attempt === maxAttempts) throw err; }
        await sleep(1000);
      }
good: for (let attempt = 1; ; attempt++) {
        try { return await fetchOrder(id); } catch (err) { if (attempt === maxAttempts) throw err; }
        const ceiling = Math.min(maxDelayMs, baseDelayMs * 2 ** attempt);
        await sleep(Math.random() * ceiling);
      }
```

## Limits
The sources differ on the first retry. One RPC framework's retry design waits before it too, the initial retry occurring after the initial backoff times random(0.8, 1.2), and its connection protocol calls it typically desirable not to retry immediately; one HTTP client library applies its backoff between attempts only after the second try, because most errors are resolved immediately by a second try without a delay, and sleeps 0.0 s before its first retry. The framework itself retries once, immediately, a call that reached the server's RPC library but was never seen by the server's application logic, and hands a further failure to its configured retry policy. Both sides treat repeated retries without a wait as the defect: the library recommends backoff with jitter to prevent overloading servers with immediate retries, and the bug study counts retries with no delay between attempts. A first retry that runs at once or after a wait of any length, followed by growing, capped, randomized waits, is therefore not a finding; the connection protocol's own algorithm starts its first retry no earlier than a fixed initial backoff after the first attempt began and randomizes only the later backoffs. A delay the server specifies replaces the computed one for that retry: on a pushback the client retries after exactly that delay and later retries restart from the initial backoff, and the library sleeps for the duration a Retry-After header requests. A next attempt sent to a different replica may need no delay: the bug study counted its tool's missing-delay reports on retries where small changes were made between consecutive attempts, such as a failed block fetch retried against a different replica, as false positives. The rule does not reach which failures are retried, how many attempts are made, whether the call is safe to repeat, the timeout of each attempt, a hedged request sent while an earlier one is still outstanding, or a polling loop that waits for a state change rather than repeating a failed call.

## Validator
Grep the added lines for a sleep, delay or timer with a literal duration, a backoff of zero or a fixed or constant backoff, a power-of-two or shift computation, an attempt counter or a loop over attempts or retries, a retry count passed to a client or a retry helper, and a retry, resubmit, reattempt, reschedule or requeue word in a name or a comment. In the hunk, find the retry: a loop, a recursive call, a re-enqueued task or a state-machine step left in its state for an executor to re-run, that repeats a call to a remote resource or another process after it fails, or a retry policy configured on a client or a helper. Trace what runs between one failed attempt and the next: no wait, a delay that stays the same, or a delay that grows with the attempt number; whether a maximum bounds the growth; whether a random term varies it. For a configured policy read the backoff it sets and, where it sets none, the client's documented default, counting a default backoff of zero as no wait. Skip the first retry, run at once or after a wait of any length, when every later retry waits; skip also a wait the server specified through a Retry-After header or a pushback, a next attempt sent to a different replica, a hedged request, and a polling loop that waits for a state change. Validator question: **Does an added retry of a remote call run a retry after the first with no wait before it, or wait before a retry after the first for a delay that does not grow with the attempt number, grows without a maximum, or has no random term?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-33`, severity major, `file`, `symbol`, `code` = the wait between attempts or the retry policy's backoff setting quoted verbatim from the diff, or the retry loop's header where no wait exists, `fix` = the wait rewritten as the smaller of a maximum delay and a base delay times two to the attempt number, scaled by a random factor, or the retry policy configured with an exponential backoff, a maximum delay and jitter, in the file's language, `rationale` = the remote call being retried and which retries run with no wait or with a delay that does not grow, has no maximum or has no random term).
