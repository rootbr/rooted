# A field that its type validates or keeps consistent with other fields is changed from outside only through operations of the type, never directly or by a setter that only assigns it

## Thesis
A field that its type validates or keeps consistent with other fields (as a stored total or average is kept in step with the collection it summarizes) has the narrowest visibility the language offers for a member of the type: it is not public, not visible to subclasses, and not visible to a whole package, module or crate where the language offers a narrower scope. Outside code changes such a field only through an operation of the type that applies the type's checks and updates. A setter that only assigns the field is not such an operation, since it differs from a public field only in syntax.

## Rationale
Making a field public pins down a representation choice and prevents the type from providing any validation or maintaining any invariant on the field's contents, since clients can change it arbitrarily. When outside code can add items to or remove them from a collection directly, a stored average of that collection can fall out of sync with it; with both fields hidden, the type's operations are the only way to change them, the ones that add and remove items also update the average, and the type can later change the data structure without changing the code that uses it, as long as those operations keep their signatures. Enforcing a relation among fields means hiding them and enforcing the relation through constructors and the type's own functions. When the set of direct users of a field cannot easily be determined, the field's type or use cannot easily be changed, and for public and subclass-visible fields that is usually the case. The set of types that can touch a subclass-visible field is open, since anyone can derive a new one, so the complete set often cannot be examined, a change to the representation becomes infeasible, and no invariant is enforced on the field, much as with a global variable. A visibility scoped to a package, module or crate requires checking that greater area, potentially the entire crate, to verify that an invariant is upheld. A setter that only assigns adds no semantic value and the field could just as well be public; a setter carries meaning when it maintains an invariant or converts between an internal type and an interface type. Three signs mark a field to check: a field written both by the type's own methods and from outside, which one static check calls suspicious; a public field next to fields the type keeps hidden, flagged because most types should be either abstract data types that guard interior invariants behind an intentionally limited interface or plain data with no invariants; and setters that simply assign a field without additional semantics.

## Example
```rust
bad:  #[derive(Default)] pub struct Tally { items: Vec<i64>, pub total: i64 }
      impl Tally {
          pub fn add(&mut self, value: i64) { self.items.push(value); self.total += value; }
      }
good: #[derive(Default)] pub struct Tally { items: Vec<i64>, total: i64 }
      impl Tally {
          pub fn add(&mut self, value: i64) { self.items.push(value); self.total += value; }
          pub fn total(&self) -> i64 { self.total }
      }
```

## Limits
The rule reaches a field that its type validates or keeps consistent with other fields, the case both sides of a contested question flag; whether the type maintains such a condition on the field separates the cases. One side hides every instance field: a static check lets only static final, immutable or specially annotated members be public and requires every other member to be private unless package or subclass visibility is allowed, to enforce encapsulation; another reports public fields of public types because validation cannot be added, the internal representation cannot be changed afterwards, and values can change from anywhere in the code and may not meet the programmer's assumptions; a framework's design guidelines say not to provide public or subclass-visible instance fields. The other side accepts public fields for passive data: public fields are most appropriate for compound, passive data structures; if all fields can vary independently of each other, no invariant is possible; and requiring in general that no field be public is overkill and unrealistic. Measured on every public field, with or without an invariant, a class with at least one public field occurred in 76% of 395 releases of 30 open-source projects; classes were generally more change-prone while affected by a smell than while not, a result that held for every smell studied but four, the public-field smell among them; removing the smell had a limited effect on change- and fault-proneness; and developers shown such classes did not perceive it as an issue, 18% of industrial developers on average across three systems recognizing it as one. A field that a method of the type writes besides its constructors, initializers and finalizers, and that outside code also writes, is a sign to check for that condition, not the condition itself: the one static check that calls such a field suspicious suggests making it private with appropriate setters, and if all fields can vary independently no invariant is possible. A field of plain data whose values vary independently and that the type neither validates nor keeps consistent with other fields is outside the rule even when a method of the type writes it, and so is whether exposing such a field pins down a representation.

A field that the type only reads and outside code writes, such as a flag that affects the type's behaviour, may be public when the type neither validates it nor keeps it consistent with other fields. A field that outside code can read but not assign, because the language marks it read-only, is outside this rule; a mutable object reached through such a field can still have its contents changed from outside, which this rule does not weigh. A field that an injection framework fills and that carries the framework's annotation meets the rule, since annotations are often used by injection frameworks, which require public fields. Scoped visibility can still uphold an invariant: a lint that reports scoped fields is off by default, in a group whose lints may flag perfectly reasonable code, and the first hide-every-field check has settings that allow package and subclass visibility; a tolerance for package-, module- or crate-scoped fields documented in the project context rejects that part of the finding. Where the narrowest visibility the language offers for a field is its package, a field the package does not export meets the rule. Where the language marks non-public members only by a naming convention, the convention's non-public mark meets the rule. A write in attribute syntax that runs a property setter applying the type's checks is an operation of the type. Getters, and access control used as a security boundary, are outside this rule.

## Validator
Grep the added lines for a field declared wider than the narrowest member visibility the language offers (public, subclass-visible, scoped to a package, module or crate, exported from its package, or named without the language's non-public mark), for an assignment to a field of another object, and for a setter or property setter. Open the file and, for each field found, read the type that declares it: whether a constructor or method validates the field's value, and whether a method updates it together with another field (a total, count, size, average or cached value); a write by a method other than a constructor, initializer or finalizer is a sign to read for these two, not a finding by itself. For a setter, read whether its body does anything besides assigning the field. For an assignment to another object's field, read the declaring type in the file or among the diff's files, and leave the line unflagged when neither holds it. Confirm that the field is assignable from outside, not marked read-only, and read the project context for a documented tolerance on package-, module- or crate-scoped fields. Validator question: **Does an added line let code outside a type assign a field that the type validates or keeps consistent with another field, through a visibility wider than the narrowest the language offers that no documented tolerance admits, through a setter that only assigns it, or through a direct write from outside the type?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-31`, severity minor, `file`, `symbol`, `code` = the added field declaration, outside assignment or setter, quoted verbatim from the diff, `fix` = the field at the narrowest visibility the language offers, with an operation of the type that applies its checks and updates in place of the outside write or the plain setter and a read accessor where callers read it, in the file's language, `rationale` = the condition the type maintains on the field (the validation or the field it is kept consistent with) and the path by which outside code can assign it).
