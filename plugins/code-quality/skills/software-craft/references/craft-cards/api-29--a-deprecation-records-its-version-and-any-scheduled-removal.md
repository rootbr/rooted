# A deprecation records the version in which the element was deprecated and any removal it schedules

## Thesis
A deprecation that the change adds records the version in which the element was first deprecated. Where the deprecation marker has a version field, the version goes in that field, in the same format and namespace as the project's other since-version records and as a valid semantic version where the marker's checker requires one; where the marker has no version field, the notice text or the deprecation message carries the version. Where the marker has a removal field, a removal that the notice announces sets that field. When the removal or the incompatible change that a run-time deprecation warning announces is expected in a known release, the warning message names that release.

## Rationale
For a standard-library element, one checker compares the version a caller targets against the version that deprecated the element, which it reads from a table of standard-library deprecations that it keeps, not from the deprecation notice, and when that table lacks the element it does not flag the use at all, to avoid flagging an element deprecated in release N for a caller that targets release N-1. A version field is shown by documentation tools and may be checked by others: one checker reports a value that is not a valid semantic version, while it also accepts a placeholder that signals a future deprecation, because for checking the version of the deprecation the value must be a valid semantic version and, failing that, the information it holds is useless; that check sits in the checker's correctness group, which denies by default. A removal field set to true indicates the intent to remove the element in a future version; set to false, its default, it indicates that use is discouraged while, at the time of marking, there was no specific intent to remove the element. A compiler that reads the removal field warns by default about each use of an element marked for removal, while for other deprecated elements it shows only a summary of the source files that use or override them unless its deprecation option is given. A library's documented deprecation policy requires every deprecation to include the version number of the release in which the functionality was deprecated, and its examples of good deprecation warnings state that version in the message, as "is deprecated since" followed by the release. A language's compatibility policy holds that the message of a run-time deprecation warning should include the release in which the incompatibility is expected to become the default and a link to an issue where users can post feedback; the same language's type-system marker for deprecations leaves the content of its message to the author and allows it to include the version in which the element is to be removed.

## Example
```go
bad:  // Deprecated: Use [NewClient] instead.
      func Dial(addr string) (*Client, error) { ... }
good: // Deprecated: As of v1.4.0, use [NewClient] instead;
      // Dial is removed in v2.0.0.
      func Dial(addr string) (*Client, error) { ... }
```

## Limits
The rule reaches a deprecation the change adds; a marker the change only moves or re-indents is not a finding, since a version field cannot be required of the many existing markers that lack one. A member of a type, module or implementation that is itself deprecated inherits that deprecation and needs no record of its own, while the enclosing element still carries one. A placeholder that the version checker accepts to signal a future deprecation stands in for the version. A deprecation with no specific intent to remove follows the rule with its removal field false, explicitly or by default, or, where a regular deprecation warns at run time, as a soft deprecation that is only mentioned in the documentation, issues no warning and does not schedule a removal. When no release is yet planned for the removal, as under a policy that removes deprecated functionality after a minimum number of releases or a minimum period, a run-time warning whose message names only the release that deprecated the element follows the rule. Whether the deprecation names a replacement, explains its reason, warns at the caller's site or keeps working for a stated period is judged by other rules.

## Validator
Grep the added lines for a deprecation: a deprecation annotation, attribute or decorator, a deprecation tag or a doc-comment paragraph that opens with the deprecation keyword, a call that issues a deprecation or future-behaviour warning at run time, or a wrapper that makes a routine warn when called. Skip a marker the change only moves or re-indents, a marker on a member whose enclosing type, module or implementation carries its own deprecation in the hunk, and a warning category named in a filter or a test assertion rather than issued. For each remaining hit, read in the hunk the marker's fields, its doc comment and the warning message, and check whether the version in which the element was deprecated appears — in the marker's version field where the marker has one, otherwise in the notice text or the message; whether a version-field value is a version in the project's format, a valid semantic version where the marker's checker requires one, or the placeholder that checker accepts for a future deprecation; whether a notice that announces a removal sits on a marker whose removal field is unset or false; and whether a run-time warning's message names the release in which its removal or incompatible change is expected, when the hunk or `project_context` names that release. Validator question: **Does an added deprecation leave out the version in which the element was deprecated, put that version only in prose when its marker has a version field, hold a version-field value that is neither a version in the project's format — a valid semantic version where the marker's checker requires one — nor the placeholder that checker accepts for a future deprecation, announce a removal that its marker's removal field does not set, or issue a run-time warning whose message does not name the release in which its removal or change is expected while the hunk or `project_context` names that release?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-29`, severity suggestion, `file`, `symbol`, `code` = the added deprecation marker, notice line or warning call, verbatim from the diff, `fix` = the same deprecation with the version in which the element was deprecated in the marker's version field or, where the marker has none, in the notice text or message, with the removal field set where the notice announces a removal, and with the expected release named in the warning message where that release is known, in the file's language, `rationale` = what the deprecation leaves out — the deprecating version, a readable version value, a removal field that matches the notice, or the expected release — and what a caller or a checker cannot tell without it).
