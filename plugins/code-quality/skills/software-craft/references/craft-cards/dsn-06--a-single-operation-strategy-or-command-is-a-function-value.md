# A single-operation strategy, command or callback is passed as a function value, not as an instance of a class written only to implement that operation

## Thesis
A strategy, command or callback whose interface, declared or expected by its call site, has one abstract operation is supplied as a function value — a lambda, a method reference, a named function or a closure — rather than as an instance of a class, named or anonymous, written only to implement that operation. The rule applies when the class declares no other operation, keeps no field that changes between calls, extends no base class beyond one that declares only that abstract operation, implements no second interface and uses its own instance only to read its fields, never passing, returning, storing or comparing itself, and when no code compares the value with another, gives it a readable string form or relies on its identity, and no library exports it for its users to pass, and when the operation declares no type parameters of its own or the language's function values can be generic. The strategy's declared type is then a function type, or the single-operation interface itself, which a function value converts to directly or through a function type whose one method calls the function.

## Rationale
Even when a concrete strategy is a pure function, the classical form represents it as a separate subclass, and that obscures the intent of the pattern with extra complexities due to the inheritance-based implementation. A class with fewer than two public methods is reported so that its author makes sure it is really worth it; where its fields are set at construction and read by its one method, one documented alternative is a function that takes those values as parameters. An anonymous class whose only member is one method, that implements a single interface with one abstract operation declaring no type parameters of its own, extends nothing and does not use its own instance should become a lambda, which is significantly more readable. A named method passed by reference, in place of a constant holding such a class, avoids hard-coding a dependency on one particular interface type, and the method is easier to name and more natural to test than the constant and, where the behaviour is nontrivial, to document. A function type is generally preferred, when possible, to an interface with a single call signature, for being more succinct. Where a call site expects an interface with one method, a function type whose method calls the function turns any function of the right signature into an implementation, a cleaner way than making the function a method of some type whose value is ignored. A closure can capture values from the scope in which it is defined, which allows code reuse and behaviour customization.

## Example
```java
bad:  class HalfOff implements DiscountPolicy {
          public long apply(long cents) { return cents / 2; }
      }
      long total = checkout(cart, new HalfOff());
good: long total = checkout(cart, cents -> cents / 2);
```

## Limits
The rule is contested where the value must be compared, described or identified. The function side rests on static checks in three languages, on two languages' own documentation and on a paper on strategy implementations that names the cost of the class form, and holds the claims the Rationale states. The object side keeps an instance of a class: an interface-typed value can be compared against another in tests and mocks and can implement other interfaces, including a user-readable string form; in one language comparing closures is impossible, since its specification lets a function value compare only against the null value and never be a map key; and evaluating the same method reference twice is not guaranteed to return an identical object, so a program whose correctness depends on reference equality may break when a reference replaces a constant. The separating condition follows from both sides: the value stays an object when code compares it with another value (an equality check, a map key, a test or mock that matches it), gives it a readable string form, relies on its identity, or calls a second operation on it; with none of these, the single operation is a function value. An implementation a library exports for its users to pass is the case the object side describes: the users may compare it in their own tests and mocks, in code the file does not show, so it stays an object. Not a finding: an interface with more than one abstract operation or with overloaded call signatures, or a type that carries a property beside its call signature; an operation that declares type parameters of its own where the language's function values cannot be generic, which the anonymous-class conversion check leaves out of its count of abstract operations; a class that keeps a field changing between calls, extends a base class that declares a field or a concrete operation, implements a second interface or uses its own instance other than to read its fields, none of which the anonymous-class conversion check reports; a codebase built for a language version that has no lambdas; and a project that documents a stylistic preference for the interface form, in its lint configuration or in `project_context`.

## Validator
Grep the hunk for a class, struct or implementation block that implements an interface, trait or protocol or extends a base class, for an anonymous class created inline, for a class that defines a call operator, and for an interface with a single call signature. Open the file and read the interface the class implements: count its abstract operations and call signatures, and note whether the operation declares type parameters of its own and whether the language's function values can be generic. Read the implementing class: list its operations other than constructors, its fields and whether any is assigned outside construction, any base class it extends and whether that base declares anything beside the one abstract operation, any second interface it implements, and any use of its own instance other than reading its own fields. Trace each use of the class and its instances that a repository-wide search finds, tests included: an equality or identity comparison, a map key, a string conversion or a log of the value, a call to another of its operations, and a test or mock that matches it by equality; note whether a library exports the class or its instances for its users to pass. Read `project_context` and the lint configuration for a documented preference for the interface form. Validator question: **Is a class, named or anonymous, whose only operation is the one operation its interface or its call site requires, with no type parameters of its own unless the language's function values can be generic, no field changing between calls, no base class beyond one that declares only that operation, no second interface, no use of its own instance beyond reading its fields, not exported by a library for its users to pass, and no use that compares, prints or identifies the value, passed where a function value would serve?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-06`, severity minor, `file`, `symbol`, `code` = the class or anonymous-class declaration line and the line that passes its instance, quoted verbatim from the diff, `fix` = the operation rewritten as a lambda, method reference, function or closure passed at the same call site, adapted through a function type where the call site expects the interface, in the file's language, `rationale` = the interface's single operation, the class's lack of any other operation or changing field, and the absence of any comparison, string form or identity use).
