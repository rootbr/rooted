# A local handler catches only the error types it can handle, and a catch-all either re-raises the error or sits at an isolation point

## Thesis
A handler in an ordinary routine catches the specific error types it can handle and lets every other error propagate. A handler that receives every error, or every error of a broad family — a catch of the root error type or of a base type that spans unrelated errors, such as the base of all ordinary, all runtime or all fatal errors, a clause with no type, a catch-all clause, a recovery of every panic — does one of two things with each error it has not tested for: it re-raises the error, itself or as the cause of a new error, after any cleanup or filtering; or it sits at a deliberate isolation point that records the error and suppresses it so that the rest of the program keeps running — the outermost block of a thread or task, a loop that runs independent tasks or calls untrusted code, or a subsystem boundary in a system built to tolerate faults or degrade gracefully. Where the catch clause takes no type, catching only what the handler can handle means testing the caught error's type and re-raising every error that fails the test.

## Rationale
Few routines, if any, can handle every error that may reach them. A catch of the root type, or of a base type that spans unrelated errors, also receives errors its author never anticipated, each where the caught type includes it: programming errors such as a null dereference or an index out of bounds, which call for a fix in the code rather than a recovery at run time; resource exhaustion such as running out of memory or stack, from which a program should not try to recover and whose capture can keep the runtime from terminating properly; and the program's own exit and interrupt requests, so the program becomes harder to stop. The handler treats each of these the way it treats the failure it was written for: a bug in a parser becomes an invalid-input error, a benign error aborts the process, and the evidence that would locate the bug is gone. The catch also widens as the code grows: an error type the guarded block starts to raise later is absorbed without anyone deciding how to handle it. In 198 sampled user-reported failures of five distributed data-intensive systems, 92% of the 48 catastrophic failures came from incorrect handling of non-fatal errors the software had signalled, and 35% of the 48 from three trivial handler mistakes that inspection finds without knowledge of the system: a handler that is empty or only logs the error, a handler that aborts on an overly general exception, which brought down a whole HDFS cluster, and a handler marked TODO or FIXME; every premature abort of the whole cluster on a non-fatal error that the study counted among these mistakes sat inside such an over-catch, and a checker for the three patterns could have prevented 33% of the catastrophic failures in four of the systems. In a study relating exception-handling anti-patterns to post-release defects, the generic catch has a strong statistical relationship to defects; across projects on a public code host, catching the base type of all ordinary errors is widespread, and programmers may misjudge its risk. A narrow catch restores the property that an error nobody anticipated keeps propagating, to code that can handle it or to a crash that reports it where it happened. The two catch-all forms keep that property by other means: a re-raise passes the error on, and an isolation point has no caller left to hand the error to, so recording the error and ending one task keeps a single failure from taking down the whole process while its details still reach the log. A log line alone does not: the handler still treats the unanticipated error as the expected one.

## Example
```go
bad:  defer func() {
          if r := recover(); r != nil { err = errBadInput }
      }()
good: defer func() {
          if r := recover(); r != nil {
              pe, ok := r.(parseError)
              if !ok { panic(r) } // any other panic propagates unchanged
              err = pe
          }
      }()
```

## Limits
The rule is contested, and where the catch sits and what it does with the error separate the cases. One side rejects a catch of a generic type in any handler, since few methods can handle every runtime error, and fixes it with a specific type or, in one rule, with a rethrow as the handler's last statement (the Source entries marked narrow). The other side accepts a catch-all that re-raises and one at an isolation point that records and suppresses — a thread's outermost block, a task-processing thread that calls untrusted code, a subsystem boundary in a fault-tolerant system — and a security verification standard requires, at its highest level, a last-resort handler that catches every unhandled error (the entries marked boundary). A handler at such a point follows the rule, as does a handler that catches every error to filter sensitive details before the error leaves a trust boundary and then rethrows it. The sources still differ on a catch-all outside an isolation point that logs the traceback and carries on: one style convention and one linter accept it, while the secure-coding standard, one code-analysis rule and another style guide confine a catch-all to a re-raise or an isolation point, the weakness catalog's own bad example is such a handler, and the failure study counts a handler that only logs as one that ignores the error. The rule makes no finding on such a handler when its log record carries the stack trace and it neither aborts nor exits the process; a project context that adopts the stricter convention extends the finding to it. A catch-all outside an isolation point that aborts or exits the process is flagged whether or not it logs first. Where a callee declares only the root type, the handler has no narrower type to name; testing for the types it handles and re-raising the rest follows the rule. The rule judges the breadth of the catch and what a catch-all does with the errors it did not anticipate; an empty handler that catches a specific type, the state a handler leaves when it continues, whether a replacement error raised for a specific type keeps its cause, and the wording of a log line are judged by their own rules. A catch-all that wraps every error as the cause of a new error still folds a fatal runtime error, such as running out of memory, into that error; whether such a wrap is correct at an interface that hides a lower layer is judged by its own rule.

## Validator
Grep the added lines for a handler that receives every error, or every error of a broad family: a catch of the root error type or of a base type that spans unrelated errors, such as the base of all ordinary, all runtime or all fatal errors, an except or rescue clause with no type, a catch clause with no type or with an untyped variable, a catch-all clause, a promise rejection handler, and a panic or unwind recovery. For each hit, read the handler's body in the hunk and the routine that encloses it. Pass the handler when every error it has not tested for leaves by one of two routes: a re-raise or rethrow of the caught error, itself or as the cause of a new error, after cleanup or filtering; or a recorded suppression at an isolation point — the outermost block of a thread or a lightweight task, the body of a loop that runs independent tasks, jobs, requests or callbacks, a subsystem or plugin boundary, the program's entry point or its registered last-resort handler. Make no finding on a handler outside an isolation point whose log record carries the stack trace — an exception-logging call or exception info enabled, the caught error passed as the logger's throwable argument, a stack captured and logged with a recovered panic — and that neither aborts nor exits the process; the error value formatted into the message is not a stack trace. For a handler that tests the caught error's type, check that the branch for an unrecognized error re-raises it. Flag a handler in an ordinary routine that treats every error as the failure it expects, with no type test that lets the rest propagate: one that aborts or exits the process, whether or not it logs first, and one that goes on — returning or raising a default or a fixed error that drops the caught one, retrying, or dropping the error — without the stack trace in the log. Validator question: **Does an added handler outside an isolation point receive every error, or every error of a broad family, through the root type or a base type that spans unrelated errors, an untyped clause or a recovery of every panic, and, without re-raising the errors it has not tested for, either abort or exit the process or go on without recording them with their stack trace?** Yes → flag.
