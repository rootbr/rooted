# A numeric literal stored as a floating-point value has no more significant digits than its type holds, so it is not silently rounded to a different value

## Thesis
A numeric literal whose value is stored in a binary floating-point type converts to that type and back without loss: the stored value, printed to as many significant digits as the literal carries, reproduces the literal. That covers a literal written with a decimal point or an exponent, a literal given a floating-point type by its suffix, its declaration or a conversion, and a whole number in a language that stores it as a 64-bit float. Within the type's normal range (magnitudes from 2.2250738585072014e-308 to 1.7976931348623157e308 for a 64-bit float, from 1.1754944e-38 to 3.4028235e38 for a 32-bit float) every decimal of at most 15 significant digits converts to a 64-bit float and back without loss, and every decimal of at most 6 to a 32-bit float; outside it a literal is rejected, or silently becomes infinity, zero or a value with fewer significant binary digits, whatever its digit count; every whole number up to 2^53 − 1 (9,007,199,254,740,991) in magnitude is a safe integer, its 64-bit float value the value of no other integer. A literal past those bounds is checked digit for digit, and one that does not reproduce is written at the digits the type stores, moved to a wider floating-point type that holds it, or kept exact in an integer type that holds it or an arbitrary-precision type built from its full digits — a decimal constructed from a string, an arbitrary-size integer.

## Rationale
A binary floating-point type keeps a fixed number of significant binary digits, 24 in a 32-bit float and 53 in a 64-bit float, so a literal is rounded to the nearest value the type holds, under the IEEE 754 round-to-even rule, and the language accepts the rounding silently. Many decimals share one stored value: 0.1, 0.10000000000000001 and 0.1000000000000000055511151231257827021181583404541015625 are all approximated by the same 64-bit float. Digits beyond the type's precision are lost in the conversion and the result is unexpected behaviour: 1.9999999999999999999999999999999 stored as a 64-bit float prints 2.0, 2.718281828459045 given a 32-bit type rounds to 2.7182817, and 16,777,217 given a 32-bit type becomes 16,777,216. A value meant to be exact is then not exact, which is especially surprising when the lost precision lies to the left of the decimal point. Above 2^53 − 1 the 64-bit float value of every integer is shared with at least one other integer: 9007199254740992 and 9007199254740993 evaluate to the same number, and such integers are not guaranteed to be exactly representable or even distinguishable from each other. Writing the digits the type stores, the replacement two of the checkers suggest, makes the source show the value the program computes with, and a wider type that holds the digits keeps them. An exact decimal keeps every digit when it is built from the digits themselves, as a string or as an unscaled integer with a scale, and not from a floating-point value: built from the floating-point literal 0.1 it equals 0.1000000000000000055511151231257827021181583404541015625, built from the string "0.1" it equals 0.1 exactly. An arbitrary-size integer holds a whole number of any size.

## Example
```java
bad:  double ratio = 1.9999999999999999999999999999999;
      float limit = 16_777_217f;
      double rate = 0.12345678901234567890;
      double id = 9_007_199_254_740_993L, mask = 0x20_0000_0000_0001L;
      float cap = (float) 3.5e38;
good: double ratio = 2.0;
      double limit = 16_777_217;
      BigDecimal rate = new BigDecimal("0.12345678901234567890");
      long id = 9_007_199_254_740_993L, mask = 0x20_0000_0000_0001L;
      double cap = 3.5e38;
```

## Limits
A decimal of at most 15 significant digits for a 64-bit float, or 6 for a 32-bit float, whose magnitude lies within the type's normal range converts to the type and back without loss and is outside the rule, even though the type stores only the nearest binary approximation of a value such as 0.1. A literal held in an integer type is outside the rule, since an integer type does not round: a literal out of its range is rejected, as a compile-time error or by a lint denied by default, and an arbitrary-size integer holds a value of any size. In a language whose untyped numeric constants are exact values of arbitrary precision, a literal in an untyped constant declaration keeps every digit and is outside the rule; the same literal written into a floating-point variable, a typed constant or a conversion is inside it. One checker accepts a floating-point constant item written with 30 or more digits, on the assumption that its author is defining a constant on purpose; the other checkers have no such exemption, so a project context that states this tolerance rejects the finding for such constant items.

## Validator
Grep the added lines for a literal with a decimal point spanning 17 or more digits, separators and point; a whole-number literal of 16 or more digits and separators with no suffix or a long-integer suffix; a literal with a 32-bit float suffix spanning 8 or more characters; a literal of 8 or more characters on a line that names a 32-bit float type; a hexadecimal literal of 14 or more digits, with or without a long-integer suffix; and a literal whose exponent is 38 or more in magnitude. Drop matches inside strings and comments. For each hit, read the hunk to decide which type stores the literal: a decimal point or exponent, a floating-point suffix, a floating-point declaration, parameter or conversion, or a language that stores every such number as a 64-bit float. Skip a literal held in an integer, arbitrary-size integer or exact decimal type, a literal in an untyped constant declaration of a language whose untyped constants are exact, and a constant item of 30 or more digits when the project context accepts full-precision constants. Count the literal's significant digits, leaving out separators, leading zeros and the trailing zeros of a whole number; a decimal of at most 15 for a 64-bit float or 6 for a 32-bit float whose magnitude lies within the type's normal range, and a whole number up to 9,007,199,254,740,991 in magnitude for a 64-bit float, passes. Otherwise compute the value the type stores — the nearest value with 53 significant binary digits for a 64-bit float, 24 for a 32-bit float, or zero, a value with fewer significant binary digits or infinity outside the normal range — print it in the literal's base to the literal's number of significant digits and compare. Validator question: **Does an added line carry a numeric literal stored in a binary floating-point type, outside an exact untyped constant and a tolerated full-precision constant, whose stored value, printed to as many significant digits as the literal carries, differs from the literal as written?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-28`, severity minor, `file`, `symbol`, `code` = the declaration or expression holding the literal, quoted verbatim from the diff, `fix` = the literal rewritten to the digits its type stores, or the declaration moved to a wider floating-point type or to an exact decimal or integer type built from the full digits, in the file's language, `rationale` = naming the value the type actually stores and the digits the literal loses).

- Caveat: the checkers apply different tests at the edges. The ESLint rule prints the stored value to the literal's own digit count, zeros written after a decimal point included, and the card follows that test. The Error Prone check compares the literal's value with the shortest decimal that round-trips (`Double.toString`) and ignores trailing zeros; clippy's `excessive_precision` reports a literal with more digits than the type's guaranteed decimal digits whose shortest form is shorter. Both therefore also report a literal such as 0.10000000000000001 that reproduces at its own 17 digits and that this card passes. No source measures how often an over-precise literal causes a failure.
