# Research note — Concepts the code reviewer found uncovered

Topic `gaps-code` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: the taxonomy topics of the concepts and their canon locators: control-flow (CC14–17, CC19); variables-scope-and-numerics (CC10–13).

This topic covers four concepts that the code-domain reviewer found with no card and no pending entry. Each rests on a Code Complete section that can be opened through GitHub copies of its checklists and guideline sentences: §12.1 'Anticipate divide-by-zero errors', §12.3 'Anticipate rounding errors' (dollars and cents in binary floating point), §19.1 'Making Complicated Expressions Simple' and §19.4 'Taming Dangerously Deep Nesting'. Clean Code, Refactoring, Effective Java, PoEAA, 97 Things, The Art of Readable Code and Building Secure and Reliable Systems state the same four rules as formulations. Industry agrees on the rules and disagrees on numbers and remedies. Nesting-depth defaults are 1 in Checkstyle; 3 in Sonar Java and Go, PMD and the Linux kernel; 4 in ESLint and Sonar Python; and 5 in Pylint, Ruff and revive. Clippy checks nothing until a project sets a threshold. Boolean bounds run from 3 operators (Checkstyle, Sonar S1067) to 5 operands (Pylint, Ruff), and the C++ Core Guidelines ES.40 asks 'what should N be?'. Ousterhout disputes extracting tiny predicate routines. Single-exit rules (PMD OnlyOneReturn, Sonar S1142) pull against guard clauses. CERT NUM02-J and C++ ES.105 leave IEEE floating-point division out of the zero-divisor rule, while CERT FLP03-C calls C's silent float division an error. TC39 disputes integer cents as a general money representation. The evidence is official language documentation: the Go and Rust specs, the Python, Java, ECMAScript and .NET documentation, and the SEI CERT rules INT33-C, NUM02-J, NUM04-J and FLP02-C opened from cmu-sei/secure-coding-standards. Static-analysis rule pages add to it. Research is thin. An fMRI replication table ties a snippet's maximum nesting depth to brain activation more strongly than cyclomatic complexity. Ajami et al. find that larger predicates raise error rates, but not significantly after correction. Scalabrino et al. find that no single metric captures understandability. Both numeric bounds are therefore stated as tool conventions that a project's configured bound replaces. Each concept yields one card, ordered as Code Complete orders them.

## Formulation layer

The canon covers all four concepts. Each one rests on a Code Complete section that can be opened through GitHub copies: the CC2 checklists, published with McConnell's permission in oceord/cc2e-checklists; a transcription of the guideline sentences in liumiaowilson/world; and the CC19.4 nesting passage quoted in the Ghidra coding standards. Clean Code, Refactoring, Effective Java, PoEAA and The Art of Readable Code were also opened through GitHub copies. The 97 Things essays, PEP 20, the Linux kernel, Go, Google Go and Uber style guides, eng-practices, SWEBOK V3 and Building Secure and Reliable Systems were opened from their own repositories.

Deep nesting: the canon agrees it is a defect and that guard clauses, early continue or extraction are the cure. It disagrees on the threshold:
- Clean Code: an indent level of one or two
- Ghidra: 2 is good, 3–4 questionable, 5 or more unacceptable
- Linux kernel and Asterinas: 3 levels
- Code Complete: three or four levels
- ESLint max-depth: default 4, which matches the design note's depth-4 signal

In the aposd-vs-clean-code discussion, Ousterhout rejects Clean Code's one-line-block limit as an arbitrary number. The two authors also disagree on the labeled continue as a way out of nested loops.

Complex boolean expressions: CC19.1, Clean Code G28/G19, Fowler (Decompose Conditional, Introduce Explaining Variable), Art of Readable Code ch. 8 and the Google Go guide all say to split a long condition into named variables or a predicate function. Only Checkstyle gives a number (3 operators); Code Complete says "half a dozen terms" and Art of Readable Code says "three or four things". The Google Go guide adds a precondition the rule must keep: operands may be pulled out into variables only "if the short-circuit behavior is not required". Ousterhout limits predicate extraction through his entanglement and shallow-method argument.

Division by zero: only CC12.1 and its checklist state it in the canon. An openable standard copy was found: CERT INT33-C in github/codeql-coding-standards. The Go spec quote was confirmed.

Money in binary floating point: the sources agree that binary floating point should not hold quantities that must be exact: CC12.3, Clean Code G26, 97 Things #33, Effective Java Item 60, PoEAA Money and cpython decimal.rst. They keep the precondition "exact answers required" and differ only on the replacement: a decimal type versus integer minor units.

Could not open: the Code Complete body text itself (the CC12.3 BCD and dollars-and-cents passage is a paraphrase from memory, with only its headings fetched); the Karpilovsky Testing Blog post (named only in BSRS and the Go guide); K&P's "If a logical expression is hard to understand, try transforming it" (unfetched); SonarSource S3518 (404 under both the java-checks and sonar-java-plugin paths, so it is not cited). WebSearch was not used.

## Reception layer

Static-analysis tools agree on checking all four concepts, but they disagree on the thresholds. Nesting-depth defaults run from Checkstyle 1 (if only) through PMD and Sonar Java/Go at 3, ESLint and Sonar Python at 4, to Pylint, Ruff and revive at 5, and clippy's check is off until a project configures it. Linux kernel style draws the line at 3 indentation levels. For boolean conditions, Checkstyle and Sonar allow 3 operators where Pylint and Ruff allow 5 operands. Cognitive complexity counts only runs of mixed operators. For division by zero, the SEI CERT rules INT33-C and NUM02-J (fetched from cmu-sei/secure-coding-standards on GitHub) state a checkable guard rule, which fills the gap the earlier research note recorded ('no fetched source states the guarding rule'). NUM02-J leaves floats out; C's FLP03-C calls float division by zero a silent error. Clang's TaintedDiv separates a divisor that is proven zero from an input-derived divisor that has not been proven non-zero. Pony disputes the premise and defines x/0 = 0. For money, the Python, .NET and SEI CERT texts back a decimal type or integer minor units. NUM04-J is tagged as possibly deprecated. TC39 disputes integer cents as a general fix, and Stripe uses integer minor units plus 12-place decimal strings. Tools check only the conversion boundary (BigDecimal from a double) or use name heuristics (Semgrep). Contested points: single-exit rules (PMD OnlyOneReturn, Sonar S1142, Checkstyle ReturnCount) against the guard-clause fix that Sonar S134 itself recommends; Ousterhout against extracting tiny methods or predicates; clippy's retraction of cognitive complexity; and Scalabrino's finding that no metric captures understandability. WebSearch was exhausted, so Hacker News, Lobsters, blogs, the Google TotT post, Hillel Wayne's 1/0 post and the cwe.mitre.org pages were not opened. Papers were reached only through neverworkintheory, a GitHub replication package, or a GitHub-hosted bibliography (relayed).

## Evidence layer

All four concepts are backed by official language documentation and static-analysis rule pages opened through raw.githubusercontent.com, plus a local probe run on Python 3.13, Java 21, Go 1.24, Rust 1.97, TypeScript 6, ESLint 10 and Ruff 0.16 (/tmp/craft-research/gaps-code/probe/output.txt). Empirical research is thin and mostly unfetched. Deep nesting: ESLint, Sonar, PMD, Checkstyle, Pylint, Ruff, revive and clippy all bound block depth. They disagree on what counts and on the default: Checkstyle allows 1 nested if, PMD flags the 3rd if, Sonar Java and Go allow 3, ESLint and Sonar Python 4, Pylint, Ruff and revive 5, and clippy checks nothing until a threshold is configured. The kernel style says more than 3 indentation levels needs fixing. The only research that could be opened (Scalabrino et al., ASE 2017 and TSE 2021) is contrary: none of 121 metrics captured understandability. Johnson et al. ICSME 2019 and Muñoz Barón et al. ESEM 2020 stay unfetched. Complex boolean expressions: Checkstyle and Sonar cap operators at 3, while Pylint and Ruff cap operands in an if statement at 5. C++ Core Guidelines ES.40 disputes this: splitting a simple condition into variables is 'unnecessarily verbose', and it asks 'what should N be?'. In Ajami et al. (EMSE), more ranges in a predicate raised error rates, but not significantly after Bonferroni correction. Division by zero: every spec opened agrees that integer division by zero fails loudly, as a panic or an exception, and Go and Rust also reject a constant zero divisor at compile time. Binary floating-point division by zero instead yields ±Infinity or NaN in Java, Go, Rust and ECMAScript; Python is the exception and raises. C++ CG ES.105 limits the rule to integers and offers 'use double' as a fix, which the probe contests: a NaN mean of an empty list turns silently into 0 or the minimum int. Money: the Python decimal docs, PEP 327, the BigDecimal javadoc and SpotBugs say to use a decimal type for exact decimal quantities. The TC39 Decimal proposal disputes the integer-cents alternative, and no empirical study was found. WebSearch was not used because its budget was spent, so CWE-369, CERT INT33-C, IEEE 754 and four papers (Johnson, Muñoz Barón, Hindle, Cates) could not be opened.

## Spine — candidate rules in source order

1. **A division or remainder whose divisor can be zero at run time, in arithmetic where a zero divisor raises, panics or is undefined, is reached only after a test that the divisor is not zero or is done with a checked division** — Integer division and remainder fail on a zero divisor in every language the corpus covers. Java throws ArithmeticException, Go and Rust panic, Python raises ZeroDivisionError (for float operands too), a JavaScript BigInt throws RangeError, and C and C++ leave the behaviour undefined. Some divisors can be zero at run time: one that is not a non-zero constant and that nothing on the path shows to be non-zero, such as a count, the length or size of a collection that can be empty, a difference of two values that can be equal, a parameter or a value from input. For such a divisor, the code tests it against zero before the operation and handles that case, or it uses the language's checked division, which returns an absent value for a zero divisor. CERT INT33-C and NUM02-J require this ('the divisor in a division or remainder operation on integer types must be checked for zero prior to the operation'). The enforcement line of C++ Core Guidelines ES.105 is 'Flag division by an integral value that could be zero'. A zero test placed after the division is a misplaced guard, the pattern Clang's TestAfterDivZero and Cppcheck's zerodivcond report. Several cases are outside the rule. Binary floating-point division whose language defines the result by IEEE 754 is outside: in Java, Go (gc), Rust and JavaScript Number it yields an infinity or NaN instead of failing. NUM02-J excludes floating point explicitly, and ES.105 calls 'using double instead' good. The silent infinity or NaN belongs to the cards on NaN-failing range checks and on checked numeric conversion. A divisor whose type excludes zero, such as Rust's NonZero, is outside. So is a non-zero constant divisor; a constant zero divisor is already a compile error in Go and a deny-by-default lint in Rust. In C, floating-point division by zero is undefined behaviour, and CERT FLP03-C calls it a silent error unless precautions are taken, so it falls inside the rule. Where the divisor is an argument of a routine callable from outside its module, the shipped public-precondition card (ERR-13) also applies. This rule reaches divisors computed inside the routine as well, so it does not only narrow that card. Taxonomy topic: variables-scope-and-numerics.

2. **A quantity that must be exact in decimal, such as an amount of money, is never held or computed in binary floating point, and its decimal value is built from a string or an integer rather than converted from a binary float** — Some values have a precision set by a fixed number of decimal places, and their sums and differences must balance exactly, such as currency amounts and accounting totals. Such a value is held and computed in the language's decimal type (Java BigDecimal, Python decimal.Decimal, C# decimal) or as an integer count of the currency's smallest unit, never in float or double. The reason is that binary floating point cannot represent 0.1 or 1.1 exactly: 0.1 + 0.1 + 0.1 − 0.3 is 5.5511151231257827e-017 instead of zero. Python's documentation says these differences prevent reliable equality testing and accumulate, and that this is why decimal is preferred in accounting applications with strict equality invariants. CERT NUM04-J says that when precise computation is necessary, 'such as when performing currency calculations, floating-point types must not be used'; its compliant solutions are int cents and BigDecimal. The .NET documentation calls decimal appropriate 'when the required degree of precision is determined by the number of digits to the right of the decimal point'. A decimal value is built from a string or an integer. new BigDecimal(0.1) and Decimal(0.1) carry the binary approximation 0.1000000000000000055511151231257827021181583404541015625 into the decimal (OpenJDK javadoc, Sonar S2111, PMD AvoidDecimalLiteralsInBigDecimalConstructor, Ruff RUF032). BigDecimal.valueOf(double) is acceptable only for a double that came from a short literal, since a double produced by arithmetic already carries the error (Error Prone BigDecimalLiteralDouble). Rounding a binary float to cents can also round the wrong way, for example (2.55).toFixed(1) is '2.5' (MDN). The integer-minor-unit form fits where every amount has its currency's fixed number of decimal places. The TC39 Decimal proposal disputes integer cents as a general fix, because currencies differ in decimal places and fractional cents occur; in those cases a decimal type or a decimal library is used. Exactness is the precondition, not the look of the number. Python's tutorial says binary float is 'more than adequate for most tasks' and points to decimal only 'for use cases which require exact decimal representation', and .NET allows double 'when optimizing performance is more important than ensuring accuracy'. Measurements, estimates and statistics on amounts are therefore outside the rule. Also outside are the rounding policy of a decimal computation, the allocation of a remainder when splitting an amount, and equality between decimals of different scale. 3. **A boolean expression with more than three logical and/or operators gives its parts names, as boolean variables or predicate routines, and keeps in short-circuit order any operand whose evaluation depends on an earlier one** — Some expressions combine more than three logical operators (&&, ||, and, or, and in Java also the non-short-circuit &, | and ^ on booleans), most often in the condition of an if, while or return, and counted across lines when the expression is wrapped. The C++ Core Guidelines ES.40 asks 'what should N be?'. Ajami et al. found that more ranges in a predicate raised error rates, but not significantly after Bonferroni correction. A project whose configured linter sets another bound decides. Assigning operands to variables evaluates every one of them, so the Google Go style guide extracts operands directly only 'If the short-circuit behavior is not required'. A condition of three or fewer operators, such as the range check 0 <= x && x < max, is outside the rule; ES.40 calls splitting it 'unnecessarily verbose'. Sonar exempts the field-by-field comparison inside an equals method.
