# A resource released in the routine that acquires it is released through the language's scoped-release construct or a finally block, so that every exit, an early return and a thrown error included, releases it

## Thesis
When a routine both acquires a resource — a file, a socket, a connection, a stream, a temporary file or a cancellation function — and releases it, the release is tied to the scope that holds the resource, so that it runs however control leaves that scope: at the end of the scope, through a return, a break or a continue, or through an error thrown or propagated out of it, a panic that unwinds the stack included. The tie is the language's scoped-release construct — a block that releases the resource when the block is left, a declaration whose resource is released at the end of its containing scope, a release call deferred to the routine's return, an owned value whose destructor releases it when the value goes out of scope — or the finally clause of a protected block, and the construct or the block is in force from the statement right after the acquisition succeeds, before any other step that can fail. A release written as a plain statement after the code that uses the resource breaks the rule when an exit can occur between the acquisition and that statement, and so does a construct or a protected block that takes hold only after such an exit.

## Rationale
A release statement runs only when control reaches it. An exception raised in the code that uses the resource skips past a close call written after that code, and a block left by an exception or by a break, a continue or a return does not reach the statement that follows the block; losing the only reference to the resource with the scope could lead to a resource leak. Leak-checker documentation calls exceptions skipping past close statements a common source of bugs and the first thing to look for when a leak is reported. Duplicating the release before each early exit is clean-up that can be easy to forget, forgetting it is a mistake that is easy to make when a later edit adds a return path, and the duplicated release is still not guaranteed to run if an error is thrown. What leaks depends on the resource: a stream not closed on every exception path may leak a file descriptor; a database resource left open on an exception path may result in poor performance and could cause problems communicating with the database, and since many database servers allow only a fixed number of connections, failing to release them can exhaust the available connections rapidly; a cancellation function not called leaks the child context and its children until the parent is cancelled, and a standard checker checks that it is used on all control-flow paths. The scoped-release construct makes the language run the release on every one of these exits: the scoped block releases the resource when the block is left, even through a return or an uncaught exception, and also after a break or a continue; the scope-bound declaration releases it at the very end of its containing scope or right before an early return or a thrown error; the deferred call runs immediately before the routine returns, whichever path the routine takes, runs while a panic unwinds the stack, and keeps the release next to the acquisition; the destructor runs whenever its value goes out of scope, inserted by the compiler, and runs during unwinding as well. A finally clause releases the resource however its protected block is left, an exception included, and the standard idiom places that block right after the acquisition: allocate the resource, then protect the code that uses it with a block whose finally clause closes it. Error-handling code is also covered less by tests: in the test suites of 27 long-lived open-source libraries, instructions and branches within catch blocks and throw instructions were less covered than the overall instructions and branches, with statistical significance.

## Example
```rust
bad:  let tmp = dir.join("part.tmp");
      fs::write(&tmp, data)?;
      upload(&tmp)?;
      fs::remove_file(&tmp)?;
good: struct TempPath(PathBuf);
      impl Drop for TempPath { fn drop(&mut self) { let _ = fs::remove_file(&self.0); } }
      let tmp = TempPath(dir.join("part.tmp"));
      fs::write(&tmp.0, data)?;
      upload(&tmp.0)?;
```

## Limits
A resource the routine hands on — returns, alone or inside a returned object, stores in a field of an object that owns it, or passes to a routine that takes over its release — is not released by the routine and is outside the rule; the scoped-release construct gives a resource static scope, while a handed-on resource has to persist beyond the scope; how the hand-off is made is judged by its own rule. A closeable object backed only by memory, such as a reader over a string or a stream over a byte array, needs no release in a finally clause. A resource held by an owned value whose destructor releases it, a destructor the compiler runs when the value goes out of scope, is already released on every exit that leaves its scope, with no written release call; a value whose destructor frees only its own memory, such as a path that names a temporary file, releases nothing, and a finalizer that a runtime runs when it reclaims an object is not such a destructor. Code that releases the resource by hand on each exit, such as in a handler that catches any exception and again on the normal path, leaves no exit unreleased and passes; the construct is the form that keeps it so when an exit is added. An exit that ends the process at once without unwinding — an exit or abort call that terminates the process immediately, or a panic under an abort strategy — runs no deferred call and no destructor, and the rule does not reach it; an exit call that works by raising an exception unwinds the stack and is an exit like any other; a leak checker likewise ignores run-time errors that can occur unpredictably at most points in the program, such as running out of memory, which usually terminate the program, in which case unclosed resources do not matter. The order in which several resources are released, several releases in one cleanup block, and a resource held across loop iterations are judged by their own rules; a lock and any resource shared across threads are outside the rule.

## Validator
Grep the added lines for an acquisition — an open, a connect or a dial, a constructed stream, reader, writer, socket or channel, a database connection, a created file, a context call that returns a cancellation function — and for a release written as a statement of its own: a close, dispose, release, disconnect, cancel or stop call, or the removal of a file. Open the file, find the routine that encloses each hit, and pair each acquisition with the release of the same resource in that routine. Skip a resource the routine returns, stores in a field of an owning object or passes to a routine that takes over its release, an object backed only by memory, and a resource held by an owned value whose destructor releases it, a destructor the compiler runs when the value goes out of scope. The pair passes when the release is the language's scoped-release construct — the resource bound by a scoped block or a scope-bound declaration, its release deferred, or the resource owned by a value whose destructor releases it, a destructor the compiler runs when the value goes out of scope — or the finally clause of a protected block, and the construct or the block is in force from the statement right after the acquisition succeeds, with no exit between them but the check of the acquisition's own error. Otherwise trace the statements from the acquisition to the release, or to the point where the construct or the block takes hold, for an exit: a return, a break or a continue that leaves the scope, an error-propagation operator, a call that can throw, raise or return an error, or a panic. A release that every such exit also performs passes. Validator question: **Does a routine in the added lines acquire a resource it releases itself, with the release written so that an exit between the acquisition and the release — an early return, a break or a continue, a thrown or propagated error — leaves the routine without releasing it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-27`, severity major, `file`, `symbol`, `code` = the acquisition and the release statement quoted verbatim from the diff, `fix` = the resource bound by the language's scoped-release construct — a scoped block, a scope-bound declaration, a deferred release or an owned value whose destructor releases it — or released in the finally clause of a protected block that begins right after the acquisition, in the file's language, `rationale` = the exit that skips the release and what the resource keeps holding after it — a file descriptor, a database connection, a live context, a temporary file on disk).
