# A refactoring that changes a type hierarchy is checked against every affected subtype so that each override or implementation follows a renamed or re-signed method and keeps the calls it served

## Thesis
A refactoring that involves a type hierarchy, such as pulling a method up into a supertype or renaming, removing or changing the signature of a method that subtypes override or implement, is checked against every subtype it affects, so that each override and implementation of a renamed or re-signed method binds to that method under its new name or signature, every call that reached a subtype's override or implementation through the supertype still reaches it, and each moved member resolves to the same behaviour in every subtype.

## Rationale
In principle a refactoring preserves behaviour, yet a study that detected and manually validated 15,008 refactoring operations of 52 kinds in three systems, and estimated which ones likely induced a fault, found that while some kinds are unlikely to be harmful, refactorings involving hierarchies, such as pulling a method up, tend to induce faults very frequently; it suggests more accurate code inspection or testing when such refactorings are performed. A replication of the same research questions on 103 systems confirmed that quantitative finding, while its manual inspection of commits partially demystified the role refactoring actions play in introducing bugs. When a supertype method is renamed or deleted, a type checker sees only the new code and alerts only the call sites that use the supertype directly; the subtype method that used to override it is accepted as an unrelated method, and after a rename a caller holding a subtype instance through the supertype runs the supertype's renamed method, not the subtype's. Such code likely executes without throwing exceptions, tests are less likely to catch it, and incorrect refactors of this kind have caused several production outages in multiple typed codebases. Where a type implements an interface just by having its methods, renaming a method may leave the type no longer satisfying the same interfaces as before: a static conversion then fails to compile, but code that checks for the interface at run time still works and no longer uses the type's own implementation. An explicit binding turns the break into a static error: an override marker the checker verifies keeps subtypes from going out of sync with a renamed supertype method, a declaration asserting that a type implements an interface stops compiling when the interface changes, and a trait implementation is rejected when it defines a method the implemented trait lacks.

## Example
```go
bad:  type Store interface{ Save(r Record) error } // renamed from Put
      func (s *FileStore) Put(r Record) error { ... }
good: type Store interface{ Save(r Record) error }
      var _ Store = (*FileStore)(nil)
      func (s *FileStore) Save(r Record) error { ... }
```

## Limits
Where the override marker is optional, a checker flags a missing marker only when the project enables that check, and where no static conversion ties a type to its interface the compiler does not verify the implementation automatically; in both cases the binding is traced by hand across every subtype. A rename performed by a tool that inspects each conversion from the renamed type to an interface type, and aborts when one would no longer be valid, has already checked those conversions. The rule reaches only refactorings that involve a type hierarchy, the kind the fault study singles out. A subtype whose extends, implements, base-class or implementation clause for the supertype the hunk itself removes, as when inheritance is replaced by delegation, has no binding left to keep and is outside the rule. A subtype method that the hunk keeps as the subtype's own method after removing the supertype member it overrode or implemented, as when a method is pushed down into the subtypes that use it or an interface drops a method that no call reaches through the interface, keeps every call it served and is outside the rule. The fault evidence is an association mined from version histories, with fault inducement estimated as likely rather than observed, and the replication's manual inspection partially demystified the role refactoring actions play in introducing bugs.

## Validator
Grep the hunk for a change to a type hierarchy: a removed, renamed or re-signed method in a class, interface, trait or abstract type; a member deleted from one type and added to its supertype or a subtype; an added, removed or changed extends, implements, base-class or implementation clause. For each changed supertype member, search at scope callers for every subtype and implementer: explicit extends, implements and base-class lists, implementation blocks, and, for interfaces satisfied by method set alone, every type that declares the old method name or signature. Open each and trace whether a method still carries the old name or signature of a renamed or re-signed supertype method, whether a call through the supertype that reached a subtype's method before now reaches a different implementation or none, and, for a moved member, whether a subtype's own definition, field or call now resolves to a different member or yields a different result than before. Validator question: **Does the hunk change a type hierarchy and leave at least one affected subtype, other than one whose extends, implements, base-class or implementation clause for that supertype the hunk itself removes, with a method that still carries the old name or signature of a renamed or re-signed supertype method, with a method that a call through the supertype reached before and no longer reaches, or with a moved member that now resolves to different behaviour?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-02`, severity major, `file`, `symbol`, `code` = the changed supertype member or moved member as the diff shows it, quoted verbatim, `fix` = the subtype method renamed or re-signed to match, the call through the supertype routed back to the subtype's implementation, or the moved member reconciled, with the explicit override marker or implementation assertion the file's language offers, `rationale` = names the supertype member, the subtype left unbound, and the call that now runs a different implementation).
