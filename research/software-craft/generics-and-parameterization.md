# Research note — Generics and parameterization

Topic `generics-and-parameterization` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: SW4.3 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.3; SWEBOK V3 ch. 3 §4.3 'Parameterization and Generics'); beyond it the formulations come from the language teams' own guidance: the Go blog 'When To Use Generics' and the TypeScript handbook's guidelines for writing good generic functions.

SWEBOK V3 §4.3 only defines parameterized types, as a third way besides inheritance and composition to compose behaviour. The working canon on parameterization by type is the guidance the language teams publish themselves: the Go blog and type-parameters proposal, Google's Go, TypeScript and Python style guides, the TypeScript handbook, the Rust book and API Guidelines, and the Python typing docs and PEPs. It is backed by checks in typescript-eslint, Error Prone, clippy, rustc, pyright, mypy, Ruff and Sonar. Across Java, Python, TypeScript, Go and Rust these sources agree on seven points. A constraint is a two-sided contract and should require only what the generic code uses. A type that follows another position belongs in a type parameter, not in the top type plus casts. The unchecked dynamic type (any, Any) should give way to a specific type or the checked top type (unknown, object). A generic type is never written raw. An unused type parameter is dead. Behaviour that differs per type belongs behind an interface rather than in a branch on the type argument. A parameter that is only read from takes a read-only (covariant) collection type, which is the only form of variance that carries across languages. Three disputes split along language lines, and each has a separating condition with openable evidence on both sides. (1) When to introduce a type parameter: Go and Google say wait for a second type, while Rust C-GENERIC says minimise assumptions up front. The condition is whether every instantiation is visible in the codebase or the definition is a library's public API. (2) Whether a type parameter used in only one position should become its constraint: TypeScript, pyright and Go say yes, while Rust's impl Trait is idiomatic. The condition is whether the constraint can be the parameter's type without switching to dynamic dispatch. (3) Whether return-only type parameters are banned (Error Prone, Google TS, typescript-eslint) or idiomatic (Rust str::parse, Go errors.AsType). The condition is whether the value is produced by an operation checked against the type argument or by an unchecked cast. Go's preference for passing an element operation as a function rather than requiring a method has no sourced condition for the other languages and is held. Language mechanics go to language corpora: Java use-site wildcards (PECS, wildcard return types), variance annotations, PEP 695 syntax and TypeScript type-level programming. Direct empirical evidence on generics is thin. Parnin et al. on Java generics adoption is relayed only. Åkerblom and Wrigstad measure mostly monomorphic call sites in dynamic Python. The static-versus-dynamic typing experiments bear on the top-type rules only by extrapolation. The cards therefore rest on official documentation and static-analysis rule pages.

## Formulation layer

The canon on parameterization by type is mostly language-team guidance. SWEBOK V3 §4.3 only defines parameterized types, as a third way to compose behaviour beside inheritance and composition, following Gamma et al. ch. 1. The rules themselves come from the Go blog, the Go proposal and the Google Go style guide, the TypeScript handbook, the Rust book and API guidelines, the Python typing docs and PEPs, and checks in typescript-eslint, Error Prone, clippy, pyright, Ruff and Sonar. Seven positions recur across languages: add a type parameter only when the same code is about to be written for a second type; a type parameter should relate at least two values; a constraint covers what the body uses and is a contract with callers; a checked top type (object/unknown) is better than the unchecked any/Any, and a type parameter is better than either when output relates to input; type arguments should not be omitted (raw generics); read-only parameters should take a covariant view; don't put bounds on a type definition that it doesn't need. Four disputes remain open. Go and Google say to wait for a second type, while Rust C-GENERIC and APOSD (unfetched) favour general interfaces up front. The TypeScript rule that a type parameter must appear twice clashes with Rust C-GENERIC's single-use bounded generic. Google TS, Error Prone and Effective TypeScript ban return-only generics, while Rust's str::parse/FromStr idiom uses them. Google TS's 'simplest type construct' clashes with Effective TypeScript's type-level DRY. Several rationales are language-bound (erasure in Error Prone, Go 1.18 speed, TS inference and variance annotations, Rust derive bounds, Java raw types and wildcards; Go has no variance at all), so the cards must keep the language-agnostic core. Not opened: SWEBOK V4, the GoF, Effective Java, the JLS and the Java Tutorials, and APOSD (paraphrased and marked unfetched). WebSearch was exhausted, so no paper was searched. Featherweight Go and the Parnin generics-adoption study are evidence and are left to the evidence layer. The aposd-vs-clean-code discussion and the 97 Things essays contain nothing on generics apart from one remark on raw-type warnings. typescript-eslint no-unnecessary-type-arguments and Sonar S6796 were read and dropped as call-site or syntax style.

## Reception layer

Static-analysis tools in every target language agree on two positions. First, an unused type parameter is dead code: clippy extra_unused_type_parameters, rustc E0392 and Sonar S2326 report it. Second, a raw or omitted type argument hides errors: Sonar S3740, javac -Xlint:rawtypes, the IntelliJ raw-type inspection, mypy --disallow-any-generics, pyright reportMissingTypeArgument and Sonar S6543 report it. Raw types only exist in Java and Python, though; Go, Rust and TypeScript reject them at compile time (checked locally). Four rules are contested, and each dispute splits along language lines. (1) "A type parameter must appear twice" (TypeScript handbook, typescript-eslint, Effective TypeScript, pyright) conflicts with Rust's idiom of a type parameter used once, as in C-GENERIC and impl Trait. typescript-eslint's own page also records exceptions and a behaviour change when the parameter is removed. (2) "No return-only type parameters" (Error Prone, Google TS guide, wotan, DefinitelyTyped-tools) rests on erasure. Go's errors.AsType and reflect.TypeFor, Rust's str::parse, Mockito's any() and TypeScript's own querySelector all use return-only type parameters. (3) "Start with the concrete type and add a type parameter only when identical code appears for several types" (Go blog, Google Go style) conflicts with Rust's C-GENERIC ("minimize assumptions"), which matklad in turn disputes on compile-time grounds. (4) Use-site variance (Bloch's PECS as quoted by IntelliJ BoundedWildcard, Sonar S1452) is Java-only: the Go FAQ says Go has no variance, TypeScript infers it and warns against annotations, PEP 695 infers it because developers found it confusing, and Kotlin's docs call Java's wildcards one of its trickiest aspects. On freshness, Go surveys show 26% generics adoption in 2022 with 54% seeing no need, and complaints about generics declining by 2023 and absent from the top 2025 frustrations. One study (Åkerblom and Wrigstad), reached through neverworkintheory, finds Python call sites predominantly monomorphic. WebSearch was exhausted, so I could not open Hacker News or Lobsters threads, the Effective TypeScript and typescript-eslint blog posts, the Parnin et al. paper (relayed only), Ken Arnold's critique (unfetched), or any generics-usability paper.

## Evidence layer

The rules for this topic are backed mainly by official documentation and static-analysis rule pages, which I opened from GitHub: the Go blog, Go spec and FAQ, Google's Go, TypeScript and Python style guides, the Rust book, reference, API guidelines and std docs, the TypeScript handbook, the Python typing docs, PEP 484, mypy, pyright, typescript-eslint, Error Prone, clippy, Ruff and Sonar. They agree on four positions. Introduce a type parameter once identical code repeats over different types. Prefer a type parameter, a concrete type or the safe top type (unknown/object) over any/Any/interface{}. Give every generic type its type arguments. A type parameter should relate two or more positions in the signature. Direct empirical research on generics is thin. Parnin et al. (Java generics adoption) is relayed only through the orchestrator's snippet. Hoppe and Hanenberg (generic vs raw types) and the Java Tutorials' wildcard guidelines are unfetched memory and must not anchor a card alone. A search of the neverworkintheory bibliographies found no generics study, so the top-type rule rests on indirect static-vs-dynamic typing studies (Hanenberg 2013, Gao 2017), and Hanenberg 2010 found no effect. The canon disagrees across languages. Rust idiom uses single-use generics (impl Trait, C-GENERIC) and return-only parameters with a bound (str::parse), Rust has PhantomData phantom parameters, and Go keeps runtime type information (reflect.TypeFor). So the 'appear twice' and 'no return-only parameter' rules are partly erasure- or dispatch-dependent and may belong to language corpora. Use-site variance exists only in Java/Kotlin: Go has no co/contravariance and Rust has variance only on lifetimes, so that rule likely belongs to a Java corpus. The cross-language form is mypy's advice to accept read-only collections. Featherweight Go (arXiv denied, formal calculus with no craft claim) was dropped. Local compiler runs under /tmp/craft-research/generics-evidence/hands-on confirm the documented behaviour but are not openable until committed to evals/fixture.
