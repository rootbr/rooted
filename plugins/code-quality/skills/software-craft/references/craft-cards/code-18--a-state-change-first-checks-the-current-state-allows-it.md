# A routine that changes an object's state first checks that the current state allows the change, and an event the current state does not accept is refused or ignored by explicit design, never applied

## Thesis
A routine that moves an object from one state to another in response to an event, a call such as approve, ship or cancel, establishes, before it moves the object to the next state, that its current state accepts that event: it tests the current state, branches on it, or hands the event to the current state's own handler, which returns the next state. In a state that does not accept the event, the routine refuses it, by raising an error or by returning a result that reports the refusal, or, where the design states that the event has no effect in that state, leaves the object as it was. Each event thereby has a decided outcome in each state, the next state, a refusal or a stated no-op, and no routine applies its change whatever the current state, moving the object along a transition its state machine does not have or into a state the machine does not define.

## Rationale
An assignment of the new state that does not consult the current one applies the event in every state, including those from which the move is illegal, as setting a pin's output field takes effect while the pin is configured as an input. Setters that each write one part of an object's state with no check let it reach states its state machine does not define, such as an output that is pulled low or an input that is set high; on some hardware this may not matter, and on other hardware it could cause unexpected or undefined behaviour. An unchecked event can also skip a required step: a workflow in which a draft has to be reviewed and approved before it can be published, and only published posts return their content so that unapproved posts cannot be published by accident, specifies that a draft approved before a review was requested should remain an unpublished draft. A refusal signals that a method has been invoked at an illegal or inappropriate time, the application not being in an appropriate state for the requested operation, or that an operation is not allowed in the current state. Standard libraries refuse in this way: an iterator's remove raises an illegal-state error when next has not yet been called, or when remove has already been called after the last call to next; setting a future's result raises an invalid-state error when the future is already done; a scanner's split-function and buffer setters test whether scanning has started and panic before they assign; and cancelling a call that is being executed or has finished running returns false. An interface that checks a peripheral's state before using the hardware returns an error from its direction, input-mode and output setters when the peripheral is not enabled or its direction does not allow the change, and modifies the register only otherwise. Leaving the object unchanged is the other decided outcome, and the design states it: a workflow can specify that any other change attempted on a post has no effect, so that approving a draft leaves it a draft and requesting a review of a post already pending review keeps it pending.

## Example
```java
bad:  void ship() { this.status = Status.SHIPPED; }
good: void ship() {
          if (this.status != Status.PAID) {
              throw new IllegalStateException("cannot ship an order in state " + this.status);
          }
          this.status = Status.SHIPPED;
      }
```

## Limits
A routine that gives a new object its first state, as a blog post starts as an empty draft, has no earlier state to check. Leaving the object unchanged meets the rule where the design states that the event has no effect in that state, as a workflow states that any other change attempted on a post has no effect. Where each state is a separate type, the routine for an event is defined only on the types of the states that accept it, and the transition consumes the old state's value so that no instance of it lingers, an attempt at an illegal transition does not compile, and the routine needs no run-time check of the current state; that form gives up encapsulating the transitions entirely within the object. An interface that enforces a peripheral's restrictions at run time ends up doing a lot of runtime checking which wastes time and resources, where enforcing the same constraints entirely at compile time incurs no runtime cost. The rule does not judge three cases: an object found in a state that should be impossible, which is a broken invariant rather than a refused event; a state machine whose state is shared between threads; and a protocol state machine spanning services.

## Validator
Grep the hunk's added lines for an assignment to or a comparison of a field named for a state, status, phase or stage, a call to or a declaration of a setter or transition routine for one, a lookup in a transition table, and an illegal- or invalid-state error. Open the file and find the routine that changes the state, the set of states the field can hold, and the event the routine stands for. Trace what the routine does before the change: a test of the current state, a branch over the current state and the event, a table lookup keyed by both, or a call to the current state's own handler. Clear a routine that, in every state that does not accept its event, raises an error or returns a result reporting the refusal, and one that leaves the object unchanged in a state where a comment, a documented contract or the stated requirements say the event has no effect. Clear a constructor or initializer that sets the first state, a routine whose event every state accepts with the same outcome, and a routine defined only on the type of a state that accepts its event, when the transition consumes that state's value. Where the next state comes from a table, check that a state-event pair with no entry is refused, or leaves the state unchanged where a comment, a documented contract or the stated requirements say the event has no effect, rather than storing the null or default the lookup yields as the new state. Validator question: **Does a routine the hunk adds or changes move an object to a new state without first establishing that its current state accepts the event, so that in a state from which the move is illegal the change is applied anyway?** Yes → flag.

When the validator answers yes, the finder emits one finding (`rule_id: CODE-18`, severity major, `file`, `symbol`, `code` = the state assignment or setter call verbatim from the diff, `fix` = the routine with a check of the current state before the change that raises an error naming the current state and the event, returns a result reporting the refusal, or leaves the object unchanged where the design documents a no-op, in the file's language, `rationale` = a state from which the hunk's change is illegal and the undefined state or skipped step the object reaches when the event is applied there).
