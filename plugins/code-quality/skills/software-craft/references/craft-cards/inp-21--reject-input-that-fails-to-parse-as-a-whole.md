# Input that fails to parse is rejected as a whole with an error, and nothing parsed from it before the failure is acted on, stored or passed on, nor is the failure skipped, guessed around or replaced by a default

## Thesis
When input fails to parse against the format the code accepts, the code rejects the whole unit the input was read as (the request, document or message) with a clear error, and it continues with nothing parsed from that unit: no value read before the failure is acted on, stored or forwarded, and no target that the parser filled partially before reporting the error stays in use. For a fault whose handling the format does not define, rejection takes the place of skipping the faulty part, substituting a default for it, or processing it according to the sender's inferred intent.

## Rationale
When parsing and input-validating checks are mixed with and spread across processing code, the program loses the ability to reject invalid input instead of processing it: an error discovered late in the input leaves some portion of the invalid input already processed, and program state becomes difficult to predict accurately. A parser can also report an error after writing into the caller's target: one standard decoder, given a value that does not fit the target type, skips that field, completes as best it can and, if no more serious errors are encountered, returns an error describing the earliest such one, with no guarantee that the fields after the problematic one were filled. The same decoder checks the whole input for well-formedness first, to avoid filling out half a data structure before it discovers a syntax error. Ignoring faulty or ambiguous input is almost always the incorrect answer to an imperfect specification, and negative consequences to interoperability accumulate over time when implementations silently accept faulty input. Where the implementation that produced the input can be updated, choosing a fatal error for an unspecified condition instead of attempting error recovery can ensure that the fault receives attention, and that error is best sent as an explicit error message to the party that made the error.

## Example
```python
bad:  records = []
      for line in lines:
          try: records.append(parse_record(line))
          except ValueError: continue
      save_all(records)
good: records = [parse_record(line) for line in lines]  # one bad line rejects all
      save_all(records)
```

## Limits
Handling that the format itself defines is outside the rule: a format can explicitly allow a range of valid expressions of the same semantics, with precise definitions for error handling, which is distinct from relying on the robustness principle. The URL standard is such a format: a validation error there does not mean that the parser terminates, and every termination is stated explicitly. A first pass that checks the whole unit for well-formedness before a later pass builds values from it is within the rule. Field rules on a value that parsed are a separate step, checked after decoding according to the protocol. Continuing past a failure only to collect further errors in the same unit, and then rejecting the unit with all of them, is within the rule; a standard source-code parser returns the syntax errors it found as one sorted error list. A tool whose job is to work on a unit while a person is still writing it, such as an editor or language server that highlights, completes or diagnoses source code being typed, treats broken input as a normal state rather than an error condition and works on the partial tree the parser returns; it is outside the rule as long as it does not run, store as valid or forward that unit. The mitigation for improper syntactic validation names one alternative to rejection: transforming the input into something that strictly conforms to the specification; the rule counts such a transformation as conforming where the stated format defines it, and a default or a guess the format does not define is the tolerance the rule rejects. Protocol-maintenance guidance applies its intolerance only where deployments can be improved through timely updates of their implementations, and it grants that problems in other implementations can create an unavoidable need to temporarily tolerate unexpected inputs, a course that carries risks; code that transforms one known fault of a producer that cannot be updated in time into input that conforms is outside the rule. A stateless endpoint that receives messages from unauthenticated senders might need to discard them silently, because sending an error message in response to every such message might generate a denial-of-service attack. The rule is contested. The robustness principle, as the Internet's architectural principles state it, tells a receiver to tolerate faulty input and, when in doubt, to discard it silently without returning an error message unless the specification requires one. Protocol-maintenance guidance holds that tolerating unexpected inputs is not considered best practice in all scenarios, and it scopes that judgment to cases where handling is not defined or where the specification is ambiguous. That is the separating condition: where the format defines how a fault is handled, the code follows that handling; where the format defines none, the code rejects the unit, unless it transforms one known fault of a producer that cannot be updated in time into input that conforms. A substitute a caller chooses for the result of a failed remote call, after the malformed response was rejected with an error and the failure recorded, is judged by its own rule; this rule asks that nothing parsed from the rejected unit is acted on and that the rejection is reported.

## Validator
Grep the hunk for a handler that catches a parse, decode, format or syntax error, for a parse call whose error is turned into an optional or a fallback value, and for a decode into a caller-supplied target. Open the file and trace the failure path: whether it continues a loop over records and then uses the records it kept, returns or assigns a default, logs and proceeds, keeps using the target after the error, or drops the unit without raising, returning or reporting an error. Then trace whether values parsed from the same request, document or message before the failure reach a store, a response, a queue or another component. Where the code relies on an error-handling rule of the format, read the format's specification or the parser's documentation, and treat handling the format defines as conforming. Validator question: **After input fails to parse, does the code act on, store or forward anything parsed from that unit, accept the unit by skipping, defaulting or guessing past the failure where the format defines no such handling, or drop the unit without an error?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-21`, severity major, `file`, `symbol`, `code` = the handler, fallback or continued use of the target that follows the parse failure, quoted verbatim from the diff, `fix` = the parse of the whole unit completing before any value is used and its failure raised as one clear error for the unit, in the file's language, `rationale` = the unit that was partly processed or silently altered and what reached state, storage or another component).
