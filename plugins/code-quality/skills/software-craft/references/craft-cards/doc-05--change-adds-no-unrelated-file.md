# A change adds no file that does not relate to what the change is trying to achieve, such as a build output, an editor or local-environment file or a leftover scratch copy

## Thesis
Every file a change adds relates to what the change is trying to achieve. Before asking for review, the author reads through the entire diff, checks it for unrelated and accidental changes, and removes each extra file that does not relate to the change. Such extra files include the kinds that version control documents as intentionally untracked: files generated as part of the project build, backup or temporary files generated by the user's editor, and auxiliary files that live inside the repository but are specific to one user's workflow.

## Rationale
Reviewing one's own change before asking others to review it helps catch mistakes early and shows reviewers that the change is ready for their attention; a self-review is respectful of reviewer time and can sometimes save a review round trip. Ignore patterns exist to leave such files intentionally untracked: a project normally includes in its repository the patterns for files generated as part of its build, patterns for auxiliary files specific to one user's workflow belong in the repository's local exclude file, and patterns for backup or temporary files generated by the user's editor generally go into the user's own excludes file, so neither of the last two is committed with the repository. A read of the diff before review is where the author checks for such accidental changes.

## Example
```python
bad:  added_files = ["orders/export.py", "tests/test_export.py",
                     "orders/__pycache__/export.cpython-312.pyc",
                     "orders/export_old.py.bak", ".vscode/settings.json"]
good: added_files = ["orders/export.py", "tests/test_export.py"]
```

## Limits
A file that the change's own edits regenerate and that the project commits by convention relates to the change, such as a dependency lock file that its package manager generates whenever it modifies the manifest and documents as intended to be committed into source repositories. The rule reaches whole files the change adds: commented-out debugging code and unrelated edits inside a file the change needs are separate defects, and a committed credential is a security finding rather than an extra-file finding. A document that describes what the change adds or alters relates to the change, whether or not another file links to it or a description mentions it.

## Validator
List the files the diff adds: the new-file headers, where the old side is `/dev/null`, and the copy targets, where the header reads `copy to`, since a diff made with copy detection shows a scratch copy of a file the change also edits under `copy from` and `copy to` headers with no `/dev/null` side. Grep each added path for build-output, editor, IDE, operating-system, log and backup patterns (`__pycache__`, `.pyc`, `.class`, `.o`, `target/`, `dist/`, `build/`, `.idea/`, `.vscode/`, `.DS_Store`, `.swp`, a trailing `~`, `.bak`, `.orig`, `.log`, `_old`, `copy`). Open the project's ignore files and check whether a pattern there matches the path. Trace whether the file is an input that the change uses (the project's build compiles it as a source, the project's test runner collects it as a test, code or a script in the change imports or runs it, a test reads it as a fixture or snapshot, code or a build file reads it as configuration, or a document links to it) and whether the change's description accounts for it. A file that the change's sources or build files produce is output and never counts as an input, whatever later reads it: it relates to the change only when the project commits it by convention, as a lock file updated with its manifest or generated code regenerated by its generator does. Validator question: **Does the change add a file that nothing in the change uses as an input, that the change's description does not account for, and that is not output of the change's own edits that the project commits by convention?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DOC-05`, severity minor, `file`, `symbol`, `code` = the added file's path as the diff's new-file or `copy to` header shows it, `fix` = the change without that file, plus a pattern for its path in the project's ignore file when the project build generates it, or in the author's own excludes file or the repository's local exclude file, neither of which the change commits, when an editor, the operating system or the local environment generates it, `rationale` = what the file is, such as build output, an editor or local-environment file or a backup copy, and that nothing in the change uses or describes it).
