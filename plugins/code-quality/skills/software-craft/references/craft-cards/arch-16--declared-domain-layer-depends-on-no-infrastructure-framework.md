# A type in a component the project declares as its domain model layer or application core, the inner layer of a DDD, onion, hexagonal or clean layering, imports, derives from, implements and is annotated with no type of a data-access, web or other infrastructure framework

## Thesis
A type in a component the project declares as its domain model layer or application core, the inner layer of a DDD, onion, hexagonal or clean layering recorded in a project layout that shows which way the dependency runs, in layer annotations, in an architecture test or in an architecture document, takes no direct dependency on an infrastructure framework. It imports no data-access, web or other infrastructure framework type, and, wherever the chosen store admits it, the component's entities are plain types: they derive from no framework base type, implement no framework interface, carry no attribute the persistence technology requires and do not save themselves. Packages that are not data-access, web or other infrastructure frameworks stay allowed, the platform's own libraries included; a data-access, file-system or network operation reaches the core only through an interface the core declares and an infrastructure component implements, so a direct call into a database or HTTP client package, standard library included, sits outside the core as well.

## Rationale
A required base class, a required interface implementation, a class responsible for saving itself and a persistence-specific required attribute each add coupling between the type to be persisted and the choice of persistence technology, which makes a new data access strategy harder to adopt. A persistence-ignorant model can be persisted in several ways, and that matters because persistence choices may change from one database technology to another or gain a cache or a second store. In the inverted arrangement dependencies flow toward the innermost circle: the core defines the interfaces for data access, file system access and network calls, and infrastructure types implement them. Because the core does not depend on infrastructure, automated unit tests for it are easy to write. Building each layer as its own library may make the rule easier to enforce, because the dependencies between libraries become visible, and an architecture test checks that neither the domain nor the application packages contain a dependency on any adapter package.

## Example
```go
bad:  package domain
      import "gorm.io/gorm"
      type Order struct { gorm.Model; Total int64 `gorm:"not null"` }
good: package domain
      type Order struct { ID string; Total int64 }
      func (o *Order) Add(price int64) { o.Total += price }
```

## Limits
The rule holds where the project declares the component as a domain model layer or application core kept independent of infrastructure, and the declared style decides the direction: an annotation-driven architecture rule set lets the domain layer of its layered style access the infrastructure layer, while its onion rules let no ring access the infrastructure ring. DDD layering is reserved for complex services with significant business rules; a simpler responsibility such as a CRUD service is managed with a simpler approach and built as a single web API project whose classes hold the data model, the business logic and the data access code, where the rule does not apply. Two full-stack web frameworks document the opposite default: a model encapsulates every aspect of an object as an Active Record class that carries both data and behaviour, and the model layer represents data and business logic. In the layered DDD variant the application layer depends on the domain and infrastructure layers and is commonly the web API project itself, so there the rule reaches the domain model layer alone. The domain model layer's ban on a direct infrastructure-framework dependency is firm; the entity-level ban on deriving from or implementing a framework type is the ideal, because plain entities are not always possible with certain NoSQL databases and frameworks, and persistence ignorance does not license ignoring how the physical data model maps to the entity model. The rule governs what a declared component depends on; translating a foreign model into domain types and declaring an interface at its consumer are module-level questions outside it.

## Validator
Grep the hunk for an import of a data-access, web or cloud-service package, a persistence or framework annotation, attribute or field tag, a framework base type that a type extends, embeds or implements, and a save, update or delete call an entity makes on itself. Open the file's component and the project's layout, build files, layer annotations, architecture tests and architecture document, and establish whether the project declares this component as its domain model layer or application core kept independent of infrastructure; a component of a layered style whose domain may reach infrastructure, a single-project CRUD service and a project whose framework models carry the domain logic stay outside the rule. A layout records the declaration only where it shows which way the dependency runs, through rings named for an onion, hexagonal or clean layering, such as core, ports and adapters, or through a domain built as a unit of its own whose build file references no infrastructure component of the project; a domain package beside an infrastructure package, with nothing else that records the direction, stays outside the rule, because the layered style uses the same package roles and lets its domain reach infrastructure. For each hit in a declared component, trace the type to its package: a standard-library or helper type that belongs to no infrastructure framework passes, while an infrastructure framework type, an attribute the persistence technology requires and a self-saving entity fail whichever library supplies them. Check the project's documentation for a recorded exception where the chosen store requires framework base types; a type that exception covers passes. Validator question: **Does a type in a component the project declares as its domain model layer or application core import, extend, embed, implement or carry an annotation of a data-access, web or other infrastructure framework type, or save itself, outside an exception the project records for a store that requires framework base types?** Yes → flag.
