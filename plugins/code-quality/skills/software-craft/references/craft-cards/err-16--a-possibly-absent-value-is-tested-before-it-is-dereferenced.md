# A value that its declared type, its producing call or a null test elsewhere in the routine says can be absent is tested for absence on each path before it is dereferenced

## Thesis
A value can be absent on a path when its declared type marks it as possibly absent (an optional or nullable type, a union with null, None or undefined, or a nullable annotation), when the call that produced it documents an absent result, such as a map lookup with no entry for the key, a search with no match, a find that finds nothing or a line read at the end of input, or when the routine tests the same value for absence elsewhere. On each path where such a value can be absent, the code tests it for absence before an operation that the language does not define on the absent value uses it, such as a member access, a method call, an index or an iteration, and before it is passed to a parameter that requires a present value. The test keeps the absent case away from the use: the branch for the absent case does not continue to the use, because it returns, throws, panics or exits, or the use sits inside the branch where the value is present. A use that comes before a test of the same value on the same path, sits inside the branch for the absent case, or follows a test whose absent branch falls through to it, is unguarded.

## Rationale
Where the operation is not defined on the absent value, using that value fails at run time, as a null pointer exception, a run-time panic or another unexpected runtime error. The lack of checking for absent values tends to be a major source of bugs. In over 6,000 exception stack traces from over 600 open-source Android projects, null pointer exceptions were the most common source of problems; in the fixed defects of 210 open-source projects in a dynamically typed language, incorrectly handled null objects were one of the three most common causes of type-related faults. A test placed after the use does not protect it: the use and the test disagree about whether the value may be absent, so either the test is redundant or the use is erroneous, and such a disagreement is commonly the result of improperly ordered code or a missing return statement. A test whose absent branch records the failure and carries on lets the next line use the absent value. The check is local: once the fields, parameters and return values that may be absent are declared, a series of type-based, local checks serves to ensure that no dereferenced value can be absent, and one checker built on such local checks, while it does not prevent every null dereference, catches most of those its authors observed in production. A type checker that models absence reports such a use as an error only in its null-aware mode; with that mode off, absent values are effectively ignored by the language and code can be written as though a find always finds, so a clean compile does not show that the test is there.

## Example
```typescript
bad:  function ownerOf(items: Item[], id: string): string {
          return items.find((item) => item.id === id).owner;
      }
good: function ownerOf(items: Item[], id: string): string {
          const item = items.find((candidate) => candidate.id === id);
          if (item === undefined) throw new Error(`no item with id ${id}`);
          return item.owner;
      }
```

## Limits
An operation that the language defines on the absent value is outside the rule: in one language, ranging over an absent slice or map runs zero times, the length of either is zero and an index into an absent map yields the element type's zero value, while following an absent pointer causes a run-time panic and stays inside the rule. A path on which the value cannot in fact be absent is outside the rule: an earlier test of the value on the same path that keeps the absent case away from the use, a present value assigned on it, or a guarantee from the producing call, such as an error result whose absence guarantees a present value. Whether such a path is feasible can be beyond a tool to decide, so the finder reads the guarantee in the code. Where every reference or pointer type admits an absent value, the bare type does not mark a value as possibly absent: such a value is possibly absent only when a nullable annotation marks it, its producing call documents an absent result, or the routine tests it for absence elsewhere. A test whose absent branch calls a routine that never returns, such as a wrapper around a process exit, guards the use even where a tool cannot see that the routine stops. When the declared type and the producing call both rule absence out, a later test of the value is the redundant side of the disagreement and the use is not flagged; when neither says, the routine's own test is the evidence that the value may be absent. Whether a value must be present at a routine's entry as part of its contract, a forced-unwrap or non-null assertion that states the value is present, the validation of a value that crosses a trust boundary, and which value or error the absent branch produces are judged by their own rules.

## Validator
Grep the added lines for a call whose result can be absent followed directly by a member access or an index, for a test of a value against null, nil, None or undefined, and for a declared type, parameter or field marked as possibly absent (an optional or nullable type, a union with null, None or undefined, or a nullable annotation). Open the file and, for each value involved, read the routine that uses it and list its uses: member access, method call, index, iteration, and passing it to a parameter that requires a present value. Set aside a use that the language defines on the absent value, such as ranging over or taking the length of an absent collection that the language treats as empty. Establish whether the value can be absent: its declared type marks it as possibly absent (a bare reference or pointer type, where every such type admits absence, does not), the call that produced it documents an absent result (a map, environment or header lookup, a search or match, a find, a read at the end of input), or the routine tests it for absence elsewhere. Trace each path from where the value is set to each use. Count the use as guarded when a test for absence precedes it on that path and the absent branch returns, throws, panics, exits or calls a routine that never returns, or when the use sits inside the branch where the value is present; a test whose absent branch only logs or records the failure and falls through does not guard it. Skip a path on which the value cannot be absent: an earlier test that keeps the absent case away from the use, a present value assigned on that path, or a guarantee from the same call, such as an error result whose absence guarantees a present value. Skip a forced-unwrap or non-null assertion, and a parameter whose presence the routine's contract requires at entry. When the declared type and the producing call rule absence out and the only signal is a later test, leave the use unflagged. Validator question: **Does an added or changed line use a value, by member access, method call, index or iteration or by passing it to a parameter that requires a present value, on a path where the value's declared type, its producing call or the routine's own test says it can be absent and no preceding test keeps the absent case away from that use?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-16`, severity major, `file`, `symbol`, `code` = the line that uses the value, and the later test of the same value where there is one, quoted verbatim from the diff, `fix` = a test for absence placed before the use, its absent branch returning, throwing, returning an error or stopping, and the use on the present branch, in the file's language, `rationale` = what says the value can be absent (its declared type, the producing call's documented absent result, or the routine's own test) and the path on which it reaches the use untested).
