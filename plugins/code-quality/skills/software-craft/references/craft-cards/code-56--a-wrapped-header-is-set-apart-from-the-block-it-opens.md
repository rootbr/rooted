# A wrapped control header or signature is set apart from the block it opens by deeper indentation or a separating line

## Thesis
When a control header (a condition, a loop header, a case label list, a handler clause) or a routine signature wraps onto continuation lines and an indented block follows it, the wrapped header stays distinguishable from that block: either no continuation line starts at the column of the block's first line, as when a hanging or continuation indent puts the continuation lines deeper than the block, or a separating line comes after the continuation lines and before the block. A separating line is a line at the header's indentation that begins with the header's closing bracket, followed only by the rest of the header such as a return type, a colon or the block's opening brace, or that holds only the block's opening brace; a blank line; or, after a condition whose continuation is aligned with its opening parenthesis, a comment line. A continuation line at the block's own indentation with no separating line after it and before the block is the defect.

## Rationale
A routine signature or a control header precedes a change in indentation, so a continuation line that starts at the block's indentation is aligned with the code within the block and looks like part of it: the wrapped condition or parameter list and the block's first statement are not distinguishable by indentation. The collision follows from the arithmetic of indentation: with four spaces per level, a two-character keyword, a space and an opening parenthesis put a continuation aligned with the parenthesis four columns in from the keyword, where the block's statements also sit, and a hanging continuation indented by one level lands there too. The documented styles restore the distinction in three ways. The first indents further: a hanging indent in a signature takes four more spaces, an extra level, so its parameters sit at eight columns over a block at four; or every continuation line is indented at least +4 from the header's first line while a block is indented +2, so a wrapped header always sits at least two columns deeper than its block. The second keeps the continuation lines at block indentation and adds a line at the header's indentation: a broken control line puts its opening brace on a line of its own, not indented, and a broken signature breaks before its closing parenthesis too, so that the closing parenthesis, the return type and the opening brace share a line. The third avoids the break: a signature stays on one line, the operands of a long condition are extracted into local variables where the short-circuit behaviour is not required, and where a break that aligns the rest of the line with an indented code block is unavoidable, a blank line separates the block's code from the wrapped line. A linter checks the collision mechanically: two checks, both enabled by default, report a header whose last continuation line has the indentation of the block that follows it, whatever blank or comment line comes between, one for a hanging continuation and one for a continuation aligned with its opening delimiter.

## Example
```typescript
bad:  if (order.isPaid && order.isPacked &&
        order.hasAddress) {
        ship(order);
      }
good: if (order.isPaid && order.isPacked &&
          order.hasAddress) {
        ship(order);
      }
```

## Limits
A condition whose continuation is aligned with its opening parenthesis, where the keyword, the space and the parenthesis happen to put that column at the block's indentation, is accepted unchanged by one language's official style document, which takes no explicit position on whether to distinguish it further from the block and lists no extra indentation, an added comment, and extra indentation all as acceptable; a default-enabled check of a linter for the same language reports it. Where the project context or the project's linter configuration accepts that form, the finding is rejected; a hanging continuation at the block's indentation stays a finding, since the same style document marks it wrong. A wrapped statement that no indented block follows, such as a call or an assignment, is outside the rule. Headers the change neither adds nor rewraps are outside the finding: bringing existing code to current style is not required, it is a trade-off between churn and consistency, and opportunistic style fixes are not to muddle a change's focus. A layout tolerance stated in the project context rejects the finding.

## Validator
Grep the added lines for a control header or a routine signature that does not end its line with the block opener: a line that ends in an opening bracket, a comma, a logical operator or a line-continuation backslash, or a line that begins with a logical operator or closes a bracket opened on an earlier line and ends with the block opener, with at most the rest of the header between them. Read the hunk from the header's first line to the first line of the block it opens, and note the indentation column of the header's first line, of each continuation line and of the block's first line. For each continuation line at the block's column, look after it and before the block's first line for a separating line: a line at the header's column that begins with the header's closing bracket or holds only the block's opening brace, a blank line, or, after a condition whose continuation is aligned with its opening parenthesis, a comment line. Skip a condition continuation aligned with its opening parenthesis when the project context or the project's linter configuration accepts that form. Validator question: **Does an added or rewrapped control header or routine signature have a continuation line that starts at the same column as the first line of the block it opens, with no separating line after that continuation line and before the block?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-56`, severity suggestion, `file`, `symbol`, `code` = the wrapped header's lines and the block's first line, quoted verbatim from the diff, `fix` = the same header in the form the file's other wrapped headers use, in the file's language: its continuation lines indented deeper than the block, or a line at the header's indentation that begins with its closing bracket or holds only its opening brace, or, where the language's formatter resets continuation lines to the block's column and its syntax keeps the opening brace on the header's last line, the header rejoined onto one line, its operands extracted into local variables, or a blank line between the wrapped header and the block, `rationale` = the continuation line and the block line that share a column, and the separation the fix uses).
