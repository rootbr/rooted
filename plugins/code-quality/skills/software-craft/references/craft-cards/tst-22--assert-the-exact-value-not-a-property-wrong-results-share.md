# Tests check the exact value and each effect the behaviour must produce for a fixed input, not only a property such as presence, non-emptiness, a length or a sign that a wrong result also satisfies

## Thesis
Where the behaviour under test fixes its result for the test's input, the test compares that result with the exact expected value, computed by hand and written into the test, or with the full expected structure, constructed in the test and compared in one deep comparison. The exact comparison takes the place of a check on a property alone — a sign, an order, a bound, presence, non-emptiness, a length, a type — which a wrong result that shares the property also passes. Where the behaviour has several effects, such as a returned value and a written file, each effect is checked by a test of that behaviour, in the same test or in a sibling test, so that a version that drops any one effect fails at least one test.

## Rationale
An assertion on a property of the result rather than its value cannot tell the correct result from a wrong one that shares the property. Turning the subtraction in a mean absolute deviation into an addition moves the result for the inputs 1, 3, 5 around the centre 3 from 4/3 to 6; both are non-negative, so a non-negativity assertion passes on the broken code, while an equality assertion against 4/3, computed by hand, fails. The pattern is common in tests generated by language models that check what is obviously true about a result — that it is positive, that it is numeric — rather than what is specifically correct. A mutation-testing tool probes the same gap by replacing a function body with a value of the right type — 0, 1 or -1, an empty or a placeholder string, an empty or a one-element collection, a present or an absent optional, a success wrapping such a value — and the mutant survives unless the tests distinguish return values and observe the function's side effects. A function that writes a file and returns a success result can be covered by a test that checks only the return value, and then the mutant that returns success without writing is caught by no test; coverage records which lines ran, not whether the test checks anything about the behaviour. A mutant that deletes one field from a struct literal falling back to default values survives unless the tests verify that each field is set correctly; a deep comparison against the expected value constructed in full checks every field. The exact check restores what review asks of the tests: that they fail when the code is broken, and that each test makes simple and useful assertions.

## Example
```java
bad:  Receipt receipt = checkout.pay(cart);
      assertNotNull(receipt);
      assertTrue(receipt.total() > 0);
good: Receipt expected = new Receipt("R-1", 1150);
      assertEquals(expected, checkout.pay(cart));
      assertEquals(List.of(expected), ledger.entries());
```

## Limits
Fields irrelevant to the behaviour under test stay out of the comparison when including them would obscure the test's intention. A value that needs approximate or semantic equality, or that holds a field that cannot be compared for equality, can be compared with a comparison adjusted for approximate equality or set to ignore that field. Output whose exact form depends on a package the project does not own, such as serialized bytes or a formatted string, is compared on the semantically relevant information that is stable, for instance by parsing it and comparing it with expected data. The rule reaches results the behaviour fixes for the test's input; a value that differs from run to run, such as a randomly generated identifier or the current time, lies outside it.

## Validator
Grep the hunk's test code for the triggers: assertions of presence, truthiness, type, length, sign or a bound, and absence checks. For each hit, open the enclosing test in the file, find the call to the behaviour under test and read whether its input is fixed in the test; skip a test whose inputs are generated, a check on a value that differs from run to run, and a check that a test double was called. Trace the same result through the rest of the test for an equality or deep comparison against a written-out expected value, and trace each effect of the behaviour visible in the hunk — returned value, written file, changed state — for a check of it in any test of that behaviour in the file, the hunk's own tests and the unchanged sibling tests alike. Validator question: **Does a test whose input fixes the behaviour's result check that result only through a property a wrong result also satisfies, or does an effect of the behaviour visible in the hunk go unchecked by every test of that behaviour in the file?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-22`, severity minor, `file`, `symbol`, `code` = the property-only assertion, or the call whose effect goes unchecked, quoted verbatim from the diff, `fix` = the assertion rewritten to compare with the expected value worked out by hand or with the full expected structure, plus a check of each unchecked effect, in the file's language, `rationale` = names a wrong result or a missing effect that the current assertion lets pass).
