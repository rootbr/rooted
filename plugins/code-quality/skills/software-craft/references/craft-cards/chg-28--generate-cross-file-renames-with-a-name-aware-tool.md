# A rename or API replacement across many files is generated by a tool that resolves names and syntax, unless every match of the substituted text denotes the target or is reviewed before it is applied, every use the text misses still works through an alias, and no other declaration of the new name is in scope where a match is rewritten

## Thesis
A rename or replacement of an API across many files is generated by a tool that parses the code and resolves names. Text substitution, or a rewrite that matches syntax without resolving names, generates such an edit only when every match denotes the target or is shown as a diff and accepted before it is applied, only when its matches cover every use of the target or the old name has first been made an alias of the new one, so that both spell the same type and a use left unmatched still denotes the target, and only when no other declaration of the new name is in scope where a match is rewritten, since one of the two declarations would then shadow the other and a rewritten reference could resolve to the wrong one.

## Rationale
Text substitution is often complicated by nested expressions, comments and strings: a regular expression can hardly match the contents of a nested expression and only those, and a comment or a string can hold the matched text without denoting the target. A rename tool that resolves names can detect when changing the name would cause a symbol to become shadowed so that existing references are no longer in scope, and report an error naming the shadowed reference. A rewrite template can list several forms of the old code, and it replaces each one however the expression it applies to is written. Finding every location of a systematic edit by hand is tedious and error-prone: developers confirmed that a tool which learned the edit from examples found edit locations they had missed, and on an oracle suite of systematic edits that tool found locations with 99% precision and 89% recall and transformed them with 91% accuracy. A compiler front end combined with a parallel processor was built to let maintainers transform large collections of code easily and correctly, and was used in an API update across a large codebase.

## Example
```go
bad:  //go:generate sed -i "s/Load/ReadConfig/g" config.go
      //go:generate perl -pi -e "s/Load/ReadConfig/g" cache.go
      //go:generate gofmt -r "Load -> ReadConfig" -w cache.go
      //go:generate codemod --accept-all --extensions go Load ReadConfig
      src = strings.ReplaceAll(src, "Load", "ReadConfig")
good: //go:generate gopls rename -w config.go:6:6 ReadConfig
```

## Limits
A regular-expression substitution is sometimes good enough. It is acceptable where every match denotes the target, every use of the target matches the text, and no other declaration of the new name is in scope where a match is rewritten. Once the old name is defined only as an alias of the new type, the two names are the same type, so respelling every reference is safe even across API boundaries and a reference left in the old spelling still denotes the target; the alias does not make a match in a comment, a string literal or a longer identifier a reference. It is also acceptable for a refactor that can be partially automated but still requires human oversight, when each match is shown as a diff and accepted, rejected or edited before it is applied. The cases separate on whether every match of the substituted text denotes the target, every use of the target matches the text, and the new name has no other declaration in scope where a match is rewritten: where the text also occurs in comments or strings without denoting the target, or a match must span a nested expression, the edit is generated by a tool that parses the code and resolves names unless each match is accepted one by one; where the target is written in more than one form, it is generated by such a tool unless an alias makes the old and new names one type, because accepting matches one by one never shows a use the text does not match; where another declaration of the new name is in scope at a rewritten match, it is generated by a tool that resolves names and reports the shadowing, because neither the text nor a diff of each match shows which declaration a rewritten reference resolves to. A rename tool that resolves names and checks for name conflicts such as shadowing should never introduce a compilation error, but it may introduce a run-time error where the target is reached through reflection or through a conversion to a broader type followed by a type assertion, so judgment and testing still apply to each rewrite. The rule governs how the edit is generated; how the change is split into pieces that land independently, and whether each rewrite preserves behaviour, are judged separately.

## Validator
Grep the hunk for an in-place regular-expression or string substitution over source files, a formatter's rewrite-rule mode, or a codemod tool, and for a diff that changes the same name in many files. At scope callers, list every occurrence of the old text in the files the change reaches: occurrences in comments and string literals that do not name the target, in longer identifiers that contain the name, and in members of other types that share it; then list uses of the target written another way, qualified, aliased, re-exported or reached through an expression, that the text does not match; then list declarations of the new name, other than the renamed one, that are in scope where a match is rewritten. Trace whether the old name is an alias of the new one, so that both spell the same type, and whether the substitution ran in a mode that shows each match as a diff for acceptance. Validator question: **Is a rename or API replacement across many files produced by text substitution, or by a syntax rewrite that does not resolve names, while some match does not denote the target and the matches were not each accepted one by one, while some use of the target escapes the rewrite and no alias makes the old and new names one type, or while another declaration of the new name is in scope where a match is rewritten?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-28`, severity major, `file`, `symbol`, `code` = the substitution command or call and one line where a match fell outside the target, a use of the target was left unchanged, or a rewritten reference falls in the scope of another declaration of the new name, `fix` = the same rename generated by a tool that resolves names, such as a language-server rename, a rewrite template or an inline directive, shown in the file's language, `rationale` = which occurrence the rewrite got wrong: a comment or a string literal that does not name the target, a longer identifier, a same-named member, a use written another way, or a reference that another declaration of the new name now shadows).
