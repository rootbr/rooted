# A quotient used as a fractional value is computed by a floating-point or decimal division, not by integer division

## Thesis
When both operands of a division are integers, fixed-width or arbitrary-precision, and the operator yields an integer quotient — truncated toward zero, or rounded toward minus infinity by a floor-division operator — a quotient the code uses as a fractional value is computed instead with an operator that returns a floating-point quotient for integer operands, or with at least one operand converted, before the division, to the floating-point or decimal type the result is meant to have and divided by an operator that is not a floor division. The code uses a quotient as a fractional value when it gives the quotient a floating-point target (a variable, constant, return value or parameter of floating-point type), casts or converts it to a floating-point type, or combines it with a floating-point operand in the same expression; a division of two integer literals whose quotient is zero counts as well.

## Rationale
When a division of two integers yields an integer, the fraction is discarded at the division, before the quotient reaches the variable, return value, cast or conversion that receives it: the precision is lost before the assignment, and a conversion applied afterwards converts a value that has already lost its fraction. With operands 2 and 5 the floating-point result is 0.0 where 0.4 was meant; a floating-point constant written as 1 / 2 holds 0, and one written as 3 / 2 holds 1.0, while 3 divided by a floating-point 2 holds 1.5. A floating-point target makes an integer division suspicious, a cast of the quotient to a floating-point type suggests that its precision should have been retained, and a quotient of two integer literals that is zero is highly unlikely to be an intended truncation. An integer quotient can be intended, so the defect is the fractional use of the quotient and not the division itself: a lint that flags every integer division ships disabled by default, and flagging literal divisions that truncate to a nonzero quotient met deliberate uses. Truncation and flooring discard the fraction in different directions for a negative quotient: -7 divided by 4 is -1 under truncation and -2 under flooring. Converting an operand before a division that is not a floor division keeps the fraction — 2 divided by 5, with the 5 converted to floating point, is 0.4 — and so do a division operator that returns a floating-point quotient for two integers and decimal arithmetic, in which 1 divided by 7 is 0.142857 at six digits of precision; a floor division keeps no fraction whatever its operands, since it yields a whole number for floating-point operands and the integer part of the true quotient for decimal ones. Where a binary operator requires its operands to have one type, converting one operand is not enough: a floating-point value divided by an integer is then a compile error or a runtime type error, so both operands are converted.

## Example
```python
bad:  def share(part: int, whole: int) -> float:
          return float(part // whole)
good: def share(part: int, whole: int) -> float:
          return part / whole
```

## Limits
A division with a floating-point or decimal operand is outside the rule, whose operands are integers, though a floor division of such an operand still yields a whole number and is no fix for an integer one, and a division operator that returns a floating-point quotient for two integers keeps the fraction and is outside it too; in a language whose ordinary division keeps the fraction, the rule reaches the operators that still yield an integer quotient, such as floor division or the truncating division of an arbitrary-precision integer type. An integer quotient that is wanted is correct, such as a count of whole weeks in a number of days: binding it to a named integer variable before the floating-point arithmetic that uses it makes the intent clear and leaves no integer division with a floating-point target. A division of two constants that divides exactly loses nothing and is outside the rule. A division of integer literals whose quotient is not zero and whose target is an integer, such as the `1969/4` term of a standard time library's constant, can be deliberate and is outside the rule. A tolerance stated in `project_context` for a module whose algorithm relies on integer quotients rejects the finding.

## Validator
Grep the added lines for a division (`/`, or a floor-division `//`) inside a floating-point declaration, annotation, cast, conversion or rounding call, a returned quotient, an assignment or compound assignment, a parenthesized quotient cast to a floating-point type, a division of two integer literals, and a quotient multiplied by 100. Open the file and find the declaration, annotation or literal form of each operand: keep the division when both operands are integers — declared or annotated as integers, integer literals, or results of calls that return integers — and the operator yields an integer quotient; drop it when an operand is floating-point or decimal or when the operator returns a floating-point quotient. Trace the quotient to what receives it — the enclosing declaration, the declaration of the variable or field it is assigned to, the routine's declared return type, the parameter type of the call it is passed to, a cast or conversion, the other operands of its expression — and keep it when that is floating-point; for two integer literals, keep it when the quotient is zero. Drop a division of two constants that divides exactly and a quotient bound to an integer variable. Validator question: **Does an added line divide two integer operands with an operator that yields an integer quotient and then give the quotient a floating-point target, cast or convert it to a floating-point type, or combine it with a floating-point operand, or divide two integer literals to a quotient of zero?** Yes → flag.

## Finding output
