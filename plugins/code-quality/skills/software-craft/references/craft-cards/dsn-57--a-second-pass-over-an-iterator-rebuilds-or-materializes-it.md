# Code that traverses an iterator or stream more than once rebuilds it from its source or materializes it first unless the iterator is documented as re-walkable

## Thesis
A sequence is re-walkable when a new walk over it starts from its first element: a collection, which hands out a fresh iterator for each walk, or a sequence whose type or producing routine documents that walking it again walks the sequence again. The rule treats every other sequence as single-pass, among them a stream, an iterator, a generator or generator expression, a group handed out by a grouping iterator, and a value whose producer documents it as single-use. Code that walks a single-pass sequence from the beginning more than once rebuilds it from its source for each walk, or materializes its elements once into a collection and walks that. Code that keeps a group past the grouping iterator's next step materializes the group before that step. A routine that walks an argument more than once takes a collection, or materializes the argument before its first walk, whenever the iterable type it accepts is also satisfied by single-pass iterators and carries no documented convention that a new walk starts over. Code that adapts a stream or an iterator into a general iterable hands the result only to a receiver known to walk it once that cannot take the stream or the iterator itself. A routine that returns a single-use iterator under a sequence type whose documented convention is re-walking says in its doc comment that the result is single-use.

## Rationale
An iterator keeps its position in the sequence as internal state, and walking it consumes it: each step uses up an element, and going back, resetting or copying is not part of the iterator protocol. A second walk over a consumed single-pass sequence therefore does not see the elements again. Some implementations may detect the reuse and throw, though reuse cannot always be detected, because some operations may return their receiver rather than a new object. Others hand back the same exhausted iterator, so the second walk looks like a walk over an empty container: each further request for the next element signals the end again, or the walk yields no values at all. A stored group consumed after its grouping iterator has moved on yields an empty sequence every time, whether or not it was walked before; the code then processes empty sequences instead of the grouped data, raises no exception and produces wrong output, which makes the defect hard to debug. A single-use iterator called again after a walk that stopped early may continue the stream rather than start over. The type does not always tell the two kinds apart. Where iterators are themselves iterable, an iterator is accepted in most places that take an iterable, the one notable exception being code that makes more than one pass; a general iterable may be walkable more than once or only once, and knowing which is left to the programmer. Many interfaces that take a general iterable assume it allows several walks, so a one-shot iterable handed to one of them can work until a minor change makes the interface walk it twice and fail. Under a sequence type whose documented convention is that calling it again walks the sequence again, a single-use value has the same type as a re-walkable one, and the convention is that the doc comment of the routine returning it says so. Generating a new stream or a new iterator from the source is how the same elements are revisited; materializing instead holds the whole contents in memory at once.

## Example
```typescript
bad:  function spread(values: Iterable<number>): number {
        const low = Math.min(...values);
        return Math.max(...values) - low;
      }
good: function spread(values: Iterable<number>): number {
        const all = [...values];
        return Math.max(...all) - Math.min(...all);
      }
```

## Limits
A walk meant to carry on from where an earlier walk stopped early is not a second walk from the beginning, and the rule does not reach it. Where the language moves an iterator into the loop or the consuming call that walks it, a use after that call does not compile, so the compiler already enforces the rule for that iterator. A re-walkable sequence meets the rule, though each new walk starts the sequence again and repeats whatever setup that takes; the cost of that repetition is outside the rule. A fork that returns independent iterators from one source, one for each consumer, meets the rule; it may need significant auxiliary storage, and when one consumer uses most or all of the data before another starts, materializing into a list is faster. A stream adapted into an iterable and handed to a receiver known to walk it only once, which cannot take the stream or the iterator itself, meets the rule, and a suppression at that call that records this rejects the finding. The rule covers sequential walks; walks of one source from several threads at once are outside it. The project context can reject the finding by stating that a named producer's results are re-walkable.

## Validator
Grep the added lines for a stream adapted to an iterable, a grouping or forking call, an iterator, iterable, generator or stream type, a sequence type that may be single-use, and a generator expression stored in a name. Open the file. For each sequence these lines produce, store or receive — a parameter, a local, a field, a stored group — list every walk of it: a loop over it, a consuming call such as a sum, a count, a maximum, a join, a spread or a conversion to a collection, and a call that passes it to a routine that walks it. Decide whether it is single-pass: a stream, an iterator, a generator or generator expression, a group from a grouping iterator, a stream or iterator adapted to an iterable, a value whose producer documents it as single-use, or a parameter whose declared type — or, where none is declared, whose callers in the file — admits single-pass iterators and carries no documented convention of re-walking. Skip a collection and a sequence whose type or producer's documentation says a new walk starts over. Skip a walk meant to carry on where an earlier one stopped early, an iterator the language moves into its first consuming walk, and a fork that gives each consumer its own iterator. For an adapted iterable, find the receiver and check whether it is known to walk it once and cannot take the stream or the iterator itself. For each added routine that returns a sequence type whose convention is re-walking, read its body and its doc comment and decide whether it returns a single-use iterator. Validator question: **Does the code walk a single-pass sequence from the beginning more than once, keep a group past its grouping iterator's next step, or hand an adapted one-shot iterable to a receiver that is not known to walk it once or that can take the stream or the iterator itself, without rebuilding it from its source or materializing it first — or return a single-use iterator under a re-walkable sequence type with no doc comment saying so?** Yes → flag.
