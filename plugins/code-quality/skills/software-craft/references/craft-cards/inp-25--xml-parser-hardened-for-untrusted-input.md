# An XML parser that reads untrusted input rejects DOCTYPE declarations, or where DTDs are needed or cannot be rejected resolves no external entity or external DTD and limits entity expansion, by its documented default or by explicit configuration, and an unsupported hardening setting stops the parse

## Thesis
An XML parser, schema validator or style-sheet transformer that the change creates or configures for XML from outside the trust boundary rejects DOCTYPE declarations where the parser supports it and keeps XInclude disabled unless the application explicitly requires it; where the application needs DTDs or the parser cannot reject them, it disables external entity resolution and external DTD loading and limits entity expansion, and schema validation and style-sheet processing restrict external access as parsing does. The parser meets this either by the default that the library's current documentation states for the interface in use at a deployed version the repository or the code shows, or by configuration written in the code. A hardening setting the parser reports as unsupported is a configuration failure, and processing of the untrusted XML stops there.

## Rationale
An external-entity attack occurs when XML input containing a reference to an external entity is processed by an improperly configured parser: an attacker can point the entity's URI at local files holding passwords or private user data, or use the reference for denial of service or server-side request forgery, and out-of-band data retrieval may let an attacker steal sensitive data even when the parse result is not returned to the user. Recursive entity references declared in a DTD are a denial-of-service vector of their own (XML entity expansion), and the mitigation is, if possible, to prohibit DTDs or to use a parser that limits the expansion of recursive DTD entities. Rejecting the DOCTYPE is the first choice: disabling external general and parameter entities alone improves security but still leaves the code at risk of denial of service and server-side request forgery. XInclude can load resources independently of DTDs, so it is switched off on its own. How much configuration a parser needs turns on its default, because inclusion of an external entity's replacement text is optional for an XML processor and controls and defaults vary by parser: most of one platform's many XML parsers are vulnerable because their default settings enable parsing of external entities, and that platform's shipped configuration permits DTD processing with a limit on the number of entity expansions, while the Expat parser library accesses no local file and creates no network connection by default, with versions lower than 2.7.2 possibly open to the "billion laughs", "quadratic blowup" and "large tokens" attacks. A factory can select a third-party provider whose settings differ, so a required setting the provider does not support leaves the parse partially hardened unless the code fails on it. An entity resolver that throws for external references covers the external half only, because a resolver does not limit internal entity expansion, and secure-processing mode alone is not a portable replacement for external-access restrictions.

## Example
```python
bad:  parser = etree.XMLParser(load_dtd=True, resolve_entities=True)
      order = etree.fromstring(request_body, parser)
good: from defusedxml.ElementTree import fromstring
      order = fromstring(request_body, forbid_dtd=True)
```

## Limits
The attack needs someone outside the trust boundary to control the XML being processed, so XML that no such party can control is outside the rule. XInclude stays on where the application explicitly requires it, and an application that needs DTDs keeps them with external entities and external DTD loading off and entity expansion limited. The rule covers the parser's configuration only: bounding input size and decompressed data independently, the XML resource risks other than entity expansion that preventing external entities does not cover, and sanitizing the XML a hardened parser accepts are separate controls. Higher-level interfaces and custom handlers built on a parser whose default loads no external resource still need their own external-resource policy.
Contested: whether a parser whose documented default already complies needs replacing or explicit configuration anyway. For the default: its parser library does not access local files or create network connections by default, and versions lower than 2.7.2 may be vulnerable to expansion attacks; recent standard-library XML parsers of that language disable entity expansion by default, so unless entity expansion was explicitly enabled no further action needs to be taken, while the hardened wrapper package is recommended against both external-entity and expansion attacks; and a platform's reader classes process no in-line DTD by default from version 4.5.2. For replacing or configuring regardless: that same standard library's guidance is to use hardened wrapper interfaces in place of the standard-library parsing functions for untrusted XML; linters flag standard-library parsing calls and recommend the wrapper, and the language's documented recommendation holds only up to its 3.12 release; and a third-party parser constructed with default settings is marked noncompliant. The separating condition is the default that the library's current documentation, its change log included, states for the parsing interface in use at the deployed version: where it states that the interface rejects DTDs, or that it resolves no external entity or DTD and limits expansion while the interface offers no setting that rejects DOCTYPE or the application needs DTDs, the default complies once the repository or a run-time check in the code shows that library version, which the runtime's version alone does not establish; where it states that the default at that version resolves external entities or external DTDs or leaves entity expansion unlimited, or an analysis tool's documented finding says so where that documentation is silent, or nothing in the repository or the code shows the deployed library version, the code configures the parser or parses through a hardened wrapper. On the remedy, secure-processing mode and DOCTYPE rejection are offered as alternatives ("You can set one feature or both"); the requirement that secure processing alone is not a portable replacement for external-access restrictions is followed.

## Validator
Grep the hunk for XML parser, factory, reader, schema-validator and transformer construction and for hardening feature and property names. Open the file and trace where the parsed bytes come from: a request body, an upload, a message from another service, a path or URL a caller supplies. For a source outside the trust boundary, identify the parsing interface, the library version the repository or a run-time check in the code shows is deployed, and what the library's current documentation, its change log included, states that interface's default does at that version with DOCTYPE, external entities, external DTDs, XInclude and entity expansion; then read the configuration the code applies, including any handler around a feature or property setter that logs or ignores an unsupported setting and goes on to parse. Validator question: **Does XML from outside the trust boundary reach a parser, schema validator or transformer that, by its documented default at the deployed version together with its configuration in the code, accepts DOCTYPE although the parser offers a setting that rejects it and nothing in the file uses a DTD, accepts DOCTYPE while resolving external entities or external DTDs or leaving entity expansion unlimited, has XInclude on that the application does not require, or lets schema validation or style-sheet processing reach external resources without restriction, or that goes on parsing after a hardening setting was reported unsupported, or that relies for any of these on a default while nothing in the repository or the code shows the deployed library version?** Yes → flag.
