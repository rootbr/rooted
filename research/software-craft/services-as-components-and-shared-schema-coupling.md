# Research note — Services as components and shared-schema coupling

Topic `services-as-components-and-shared-schema-coupling` of group K. Architecture, domain `architecture`, id prefix `ARCH`. Formulation locators: Clean Architecture ch. 27 'Services: Great and Small' (services are components; the kitty problem) and Appendix A (the shared-state 'distributed monolith'); SWEBOK Guide V4.0 ch. 2 'Software Architecture' (service-oriented and microservice styles); The Pragmatic Programmer 20th ed. Topic 10 'Orthogonality'. Marked contested in the design note.

Clean Architecture ch. 27 treats a service as one kind of component, the unit of deployment, and denies that a split into services is an architecture by itself. In that chapter services that share data records or tables stay coupled, and a cross-cutting feature that edits every service (the kitty problem) exposes the decomposition. The microservices canon (Lewis and Fowler, relayed; the Azure Architecture Center, the .NET microservices guide, Zalando's and Google's API guidelines, all fetched) agrees on the coupling and places the decoupling device at the boundary: each service owns its tables, and a consumer depends on a published, machine-readable contract. The industry disagrees on four points: whether services may share a database (Spinellis, EIP, and the shared-database-server pattern used during migration), when to split (monolith first against separate from the start), whether services share libraries (Azure and Dahan against twelve-factor), and whether every API carries a version (AIP-185 and Azure against Zalando). arXiv and SciTePress answered in this run, so three papers were fetched rather than relayed: Neri et al. 2020, Laigner et al. 2021 and Taibi, Lenarduzzi and Pahl's CLOSER 2018 paper. They support per-service ownership of tables, with one sourced exception, a monolith's schema reused unchanged as a step of migration off it. They also support the fact both camps accept: units that share tables change together and cannot be deployed atomically (HotOS'23 C5). Nine rules have card evidence. The versioning default and shared libraries stay pending because no source gives a condition that separates their cases. The tolerant-reader card separates the client side from the server side (Zalando #108 against #109, Pact's philosophy), and that split also supplies the condition the parsing-and-grammar-based-input pending entry on unknown fields asked for.

## Formulation layer

The canon splits on where the coupling between services sits. Clean Architecture ch. 27, read here from memory and from relayed summaries, holds that services are not an architecture by themselves. In that chapter the data records services share couple them as tightly as function calls do, and a cross-cutting feature (the kitty problem) forces every service of a functional decomposition to change. The microservices canon instead treats services as components (Lewis and Fowler, relayed) and puts the coupling in a shared schema. Its official documents, fetched from the Azure Architecture Center and the .NET microservices guide, say each service owns a private store reached only through its API. They add a precondition: sharing one physical database server is fine, and sharing a schema or tables is not. Google AIP-215, the Zalando guidelines, OpenAPI 3.1.0 and SemVer, all fetched, state that the boundary carries a contract document and that a consumer depends on it rather than on the provider's internals; AIP-180 limits its strict compatibility rules to APIs with consumers the producer does not control. The canon disagrees openly on three points. Spinellis (97 Things #48) recommends one database used by several applications. Twelve-factor prescribes moving shared code into libraries, while Azure and Dahan (97 Things #07) call libraries shared between services tight coupling. Sironi disputes Martin's claim that independently deployable jars are enough for most systems. I could not open Clean Architecture, The Pragmatic Programmer, SWEBOK V4, A Philosophy of Software Design, Building Microservices or Lewis and Fowler, all denied or not on GitHub. The Appendix A 'distributed monolith' locator in the design note is unverified, and the SWEBOK search found nothing.

## Reception layer

Reception splits into two camps on this topic. The first holds that the service boundary and the component boundary are separate decisions: Clean Architecture ch. 27, the HotOS'23 paper by Ghemawat et al. ("microservices conflate logical boundaries ... with physical boundaries"), and the Thoughtworks Radar's advice to start with a well-factored monolith. The second defends separately built parts from the start (Tilkov, unfetched). The shared-schema position is contested: microservices.io lists development-time and runtime coupling as drawbacks. Spinellis (97 Things #48, fetched) and a TechTarget note defend a shared database as a safe integration point or a migration step, so a card can state that services sharing a schema change together but cannot ban the sharing outright. "Consumers depend on the contract, not the internals" meets Hyrum's Law (fetched via hacker-laws). Pact's consumer-driven contracts, semver's public-API clause and the oasdiff and buf breaking-change checks are the industry's answers, and Pact's FAQ adds that a published OpenAPI document needs enforcement on both sides. At the component level the industry checks two things mechanically: no cycles between modules and access only through a module's API package (Spring Modulith, ArchUnit, Nx, import-linter, dependency-cruiser, eslint-plugin-boundaries). Between services MSANose flags shared persistency, unversioned APIs, cyclic dependencies and shared libraries, though as I read its code the shared-persistency pair test compares object references. I could not open the Clean Architecture text, the Taibi 2018 catalog, Newman, Tilkov, the Segment post or the original Prime Video post. The kitty-problem search and a first Hyrum's Law search found nothing, and a 42% "CNCF survey" consolidation figure has no traceable source.

## Evidence layer

The rule that two deployable units sharing a schema or its tables are one component has openable backing. Microsoft's .NET microservices guide and the Azure Architecture Center (both sourced on GitHub) state it, and two research detectors check it: microFreshener-core's SharedPersistency sniffer, which offers "merge services", "split the datastore" and "add a data manager" as fixes, and MSANose's sharedPersistency endpoint. Azure scopes the rule: sharing a database server is safe, and the problem starts with a shared schema or shared tables. The contract side also has openable backing: OpenAPI 3.1.0, AsyncAPI, SemVer §1, Google AIP-180/185, Zalando's guidelines, the oasdiff CI breaking-change check and the Pact specification. Change-together cohesion is backed by Azure ("functions likely to change together should be packaged and deployed together") and Service Cutter's CC-9; dependency cycles, shared libraries and hard-coded endpoints have tool backing only (MSANose, microFreshener, AIP-185). The research papers were reachable only as search summaries. Taibi & Lenarduzzi 2018 (72 developers, 11 smells), Neri et al. 2020 (7 smells, 13 refactorings), Bogner et al. 2019 (17 interviews, service cutting the main challenge) and Mo et al. 2021 (19 projects) are relayed, and none of those summaries names shared persistence as a measured effect. The canon disagrees on versioning: AIP-185 and Azure require a major version and parallel versions, while Zalando says SHOULD avoid versioning and MUST NOT use URL versioning. The contrary evidence on shared databases (the shared-database pattern in Taibi/Lenarduzzi/Pahl CLOSER 2018, and Laigner et al. PVLDB 2021) could not be opened; I searched for both and neither summary stated it. SWEBOK V4 ch. 2 stayed unopened.

## Spine — candidate rules in source order

1. **A separately deployed service is a component whose boundary is architecturally significant only where it separates parts that change independently** — Clean Architecture treats a service as one kind of component, the smallest unit a system is deployed in. It denies that splitting a system into services defines an architecture by itself: the boundaries that matter separate policy from detail and parts that change independently, and they can run through a service as well as between services. The .NET microservices guide and the HotOS'23 paper likewise separate the logical boundary (a bounded context) from the physical one (a separately deployed process). The principle has no checkable form on a diff.
   - formulation: Clean Architecture ch. 12 'Components', opening section (components are units of deployment); Clean Architecture ch. 27 'Services: Great and Small', sections 'Service Architecture?', 'Cross-Cutting Concerns', 'Conclusion'; Lewis and Fowler, 'Microservices' (martinfowler.com 2014), 'Componentization via Services' (relayed); SWEBOK Guide V4.0 ch. 2 'Software Architecture' (unopened)
   - reception: contested — services are not an architecture by themselves (Robert C. Martin, Clean Architecture ch. 27; Ghemawat et al., HotOS'23): Architecture is defined by boundaries and dependencies, not by how elements are deployed; microservices conflate logical and physical boundaries.; evidence: Clean Architecture unfetched (chapter content relayed through Goodreads and CodingBlocks summaries); HotOS'23 abstract fetched from the ServiceWeaver repository (research) / services are the components (Lewis and Fowler 2014; Azure Architecture Center, 'Microservices architecture style'): A microservice is an independently replaceable and upgradeable component that owns its data.; evidence: Lewis and Fowler relayed through secondary summaries (formulation); Azure page fetched: 'Microservices are small, independent, and loosely coupled components'
   - evidence: Microsoft, .NET Microservices: Architecture for Containerized .NET Applications, 'Data sovereignty per microservice' (dotnet/docs, ms.date 2018-09-20) — docs/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice.md, section 'The relationship between microservices and the Bounded Context pattern' (fetched, official-documentation); Ghemawat, Grandl, Petrovic, Whittaker, Patel, Posva, Vahdat, 'Towards Modern Development of Cloud Applications', HotOS '23, ACM 2023, doi:10.1145/3593856.3595909 — Abstract (fetched, research)
   - disposition: held-not-checkable — No checkable form on a diff: whether a boundary separates independently changing parts needs a component map the hunks do not carry. Feeds the Rationale of shared-tables-owned-by-one-service and change-together-in-one-service.; searched: Searched for SWEBOK V4 ch. 2 on service-oriented and microservice styles (no result; computer.org denied). A check would need a declared map of components to deployable units.
   - facets: step ['design'], applies_to ['service-boundary'], triggers [], scope callers, semantic, suggestion
2. **A system is split into separately deployed services only where the deployment independence gained outweighs the cost of remote calls and of changes that span services** — Clean Architecture ch. 15 and 16 prefer to keep decoupled components in one address space until a service is needed. Azure warns that overly granular services increase complexity and reduce performance, and HotOS'23 proposes a modular monolith deployed atomically. Tilkov argues for separate parts from the start. No source gives a threshold, and the decision is taken outside any one diff.
   - formulation: Clean Architecture ch. 15 'What Is Architecture?', section 'Deployment'; Clean Architecture ch. 16 'Independence', sections 'Decoupling Mode' and 'Decoupling Modes (Again)'; Robert C. Martin, 'Microservices and Jars', Clean Code Blog 2014-09-19 (relayed); Randy Stafford, 97 Things #41 'Inter-Process Communication Affects Application Response Time' (fetched, formulation)
   - reception: contested — start with a well-factored monolith and split later (Martin (Clean Architecture ch. 16; 'Microservices and Jars'); Ghemawat et al., HotOS'23; Thoughtworks Radar 'Spring Modulith' blip; Azure 'Microservices architecture style'): Keep components in one deployable until a service boundary pays; avoid overly granular services.; evidence: HotOS'23 fetched (research, vision paper); Azure fetched (official documentation); Martin blog relayed; Thoughtworks relayed (reception) / build separately deployed parts from the start (Stefan Tilkov, 'Don't start with a monolith' (2015); Giorgio Sironi, 'Microservices are not jars' (2014)): A monolith's internal boundaries erode and are hard to cut apart later; jars are not equivalent to services.; evidence: Tilkov unfetched (martinfowler.com denied); Sironi relayed search summary whose direction I have not verified (reception)
