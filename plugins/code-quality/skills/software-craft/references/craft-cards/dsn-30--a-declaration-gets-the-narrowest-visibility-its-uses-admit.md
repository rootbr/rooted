# A declaration gets the narrowest visibility the language offers that still admits the code that uses it and the module's published interface

## Thesis
Each declaration that a change adds or widens, whether a type, field, method, function, constant, interface or module, takes the narrowest access level that admits every use of it. Where the language offers the level, that is the level of its own type or file when only that type or file uses it, the subclass level when only the type and the subtypes designed to extend it use it, and the level of its enclosing module, package or library when only code inside that unit uses it. It takes the public or exported level only when code outside the unit uses it, when a declaration it overrides or implements, a framework or a serializer that reaches it requires that level, or when it belongs to the interface the unit publishes. Where the language makes a declaration public unless told otherwise, the narrower level is written out. Where the language enforces no access level, the narrower level is marked by the non-public naming convention on every name outside the public interface and by the unit's declared list of public names. A declaration declares a level no wider than the level that takes effect: where the language bounds a member's or an item's reach by its container's level, a public member of a non-public type, or a public item inside a non-public module, that no re-export publishes and no public signature exposes is declared at the level its container allows.

## Rationale
A public declaration carries a commitment to avoid incompatible changes for the clients expected to use it, while a non-public one carries no guarantee that it will not change or even be removed. Compatibility guarantees apply only to the public interface, so users need to be able to tell the public parts from the internal ones. When in doubt, the non-public level is the one to choose, because a declaration is easier to make public later than a public one is to make non-public. With hiding as the default, the owner knows which parts of the inner code can change without breaking the outer code, and a directory whose packages other modules cannot import leaves its owner free to refactor their API and move things around without breaking external users. Exporting an interface type that only its own package uses commits the owner to maintaining that API for external callers, and restricting the visibility of properties, methods and entire types helps keep code decoupled. A public level marker both states an intent that the declaration be publicly available and makes it accessible, and where containers bound reach, the intent holds only where every container of the declaration is accessible too or a re-export or a public signature such as a return type exposes it. A public member of a non-public type therefore misleads its reader, and if the type is later made public, every member declared public is exposed with it. Where levels are a naming convention the same holds: a name is internal when any namespace that contains it is internal. Where the language's default level is public, a member written without a level is public, so the narrower level exists only where it is written.

## Example
```go
bad:  type Fetcher interface{ Fetch(id string) (Item, error) }
      func NormalizeID(id string) string { ... }
      func (s *Store) Get(id string) (Item, error) { return s.src.Fetch(NormalizeID(id)) }
good: type fetcher interface{ Fetch(id string) (Item, error) }
      func normalizeID(id string) string { ... }
      func (s *Store) Get(id string) (Item, error) { return s.src.Fetch(normalizeID(id)) }
```

## Limits
A declaration that overrides or implements an inherited one is exempt, and a public member that a non-public type inherits from its supertype belongs to the supertype's design. A public member of a non-public type that a public subtype inherits is part of that subtype's public interface, so narrowing it changes that interface. Where the language exports a field or method name on its own, whatever the level of its type, the container sets no bound and such a member is judged by its uses alone. Where non-exported names in different units are different names, a method of a non-exported interface that types in other units implement keeps its exported name. Where levels are a naming convention, the language's linters treat the non-public marker on a member as admitting uses inside its own type and subtypes only, so a member that code outside its type uses keeps its name without the marker, and a member of an internal type is internal through that type. A framework or serializer that reaches a declaration sets the lowest level that admits that use: an encoder that writes only exported fields needs the fields it writes exported. A method that only a framework calls takes the narrower level the framework accepts, rather than a public one. A declaration widened only so that a test can reach it meets the rule when it carries the project's marker for test-only visibility. The rule weighs the level of access, not the mechanism that enforces it: a level that the language's static checks enforce meets the rule even where the language also offers a runtime-enforced form of the same level. A declaration that code outside the unit uses, or that the unit's documentation other than the doc comments on its declarations, or its declared list of public names, publishes, stays public: the compatibility promise applies to it, and narrowing it is an incompatible change that this rule does not ask for. The rule judges the declarations a change adds or widens, and it weighs who can reach a declaration, not which operations a published interface offers, how many it has, or whether a value it returns lets a caller reach internal state. A visibility tolerance stated in the project context rejects the finding.

## Validator
Grep the added lines for declarations at a level above the narrowest the language offers: an export, a public or protected modifier, a visibility keyword that reaches outside the unit, a name in the exported form, a name without the non-public marker where the language marks levels by naming, a class member written without a level where the language's default is public, and an entry added to a declared list of public names. In the hunk, also take a declaration whose removed line carried a narrower level than its added line. For each, search the repository for its uses and note where each lies: the same type, the same file, subtypes, the same module, package or library, other units, or tests only. Read the enclosing type and module and note the level that takes effect, which a container bounds only where the language bounds a member's or an item's reach by its container's level. Count as a use a declaration it overrides or implements, a framework or serializer that reaches it and requires its level, the unit's documentation other than the doc comments on its declarations, its declared list of public names, a re-export or a public signature exposing it, or the change description publishing it, and the project's test-only visibility marker on it. Skip a public member of a non-public type that a public subtype inherits. Validator question: **Does an added or widened declaration take an access level wider than the narrowest one that admits its uses and requirements, or declare a level wider than its enclosing type or module lets take effect?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-30`, severity minor, `file`, `symbol`, `code` = the added or widened declaration line quoted verbatim from the diff, `fix` = that declaration at the narrowest level that admits its uses, with the level written out where the language's default is wider, and with the name and its uses renamed where the language marks the level by naming, in the file's language, `rationale` = where the declaration's uses lie, the level they need, and the level it declares or, for a level wider than its container allows, the level that takes effect).
