# A subclass neither disables an inherited operation its base type does not mark optional nor redefines more than half of the methods it inherits

## Thesis
A subclass performs every inherited operation that its base type's documentation does not mark optional, and redefines at most half of the methods it inherits. It refuses an operation when it overrides it only to fail, by throwing an unsupported-operation or not-implemented error or by panicking, or to do nothing where the operation's documentation specifies an effect for it; it refuses its base's implementation when it redefines more than half of the inherited methods, not counting the overrides its base type's documentation invites, which signals a wrong hierarchy.

## Rationale
Inheritance gives a subclass every characteristic of its base, including methods that do not apply to it, and so opens the possibility of calling methods on the subclass that do not make sense or that cause errors because they do not apply to it. An override that only fails, or does nothing where the operation has a specified effect, marks such a method: a caller that uses the subclass in the same places as its base type, which is one of the two reasons to inherit, calls it and gets no effect or an error. A class redefining most of the methods it inherits signals a wrong hierarchy. Found by taking every class that overrides more than half of the methods inherited from a superclass as a candidate, a rule built to overestimate the smell, and keeping the candidates two of the study's authors confirmed by hand, this smell affected 58% of 395 releases of 30 open-source projects written in one language, and the median change-proneness of the affected classes, the number of changes made to a class between two consecutive releases, was 43 while they had the smell and 26 while they did not. Fault-proneness differed less between those periods, though the difference was still present, and the study rates the effect of removing the smell as high on change-proneness and limited on fault-proneness, while stating that it cannot claim a direct cause-effect relation between the presence of the smell and a class's change- or fault-proneness, since other changes made between the releases might have produced the difference.

## Example
```python
bad:  class ReadOnlyStore(Store):
          def put(self, key, value):
              raise NotImplementedError("not supported: read-only")
          def delete(self, key): pass
good: class ReadOnlyStore:
          def __init__(self, store):
              self._store = store
          def get(self, key):
              return self._store.get(key)
```

## Limits
Whether a refused operation is a defect turns on the base type's documented contract. A base type's documentation may specify some methods as optional and direct an implementation that does not support one to throw an unsupported-operation error, as collection interfaces do; an override that throws there follows the documented contract and is outside the rule. Where the documentation marks no such option, the refusal leaves callers with a method that does not apply to the subclass, and the rule applies. Where a language has no implementation inheritance, the rule reaches a method that implements a trait or interface method only to fail or to do nothing, as a class refuses an operation of an interface it implements, and it counts as redefinitions a method that overrides a default method of a trait or interface, the counterpart of a child class overriding a method inherited from its parent, and a method of an outer type that hides a method of an embedded type, since the embedded type's methods become the outer type's methods. A count of overrides above half is a candidate, as it was in the study that measured the cost, and the overrides a base type's documentation invites do not count: a skeletal implementation documents that each of its non-abstract methods may be overridden when the subclass admits a more efficient implementation. An empty override refuses nothing when the operation's documentation specifies no effect for the subclass to produce, as a flush has nothing to write when the subclass keeps no buffer.

## Validator
Grep the hunk for an override whose body throws an unsupported-operation or not-implemented error, panics, marks itself unimplemented or is empty, and for a class that names a base type, a type that implements a trait or interface, or a type that embeds another. Open the base type at its declaration and read the documentation of the overridden operation for a mark that it is optional. Count the methods the subclass inherits with a body and the ones it overrides: a method the base declares abstract, without a body or with a body that only raises not-implemented is implemented, not redefined, an override the base type's documentation invites, such as a more efficient implementation of a skeletal base's method, is not counted, and an empty override of a base method that is itself empty, or of an operation whose documentation specifies no effect for this subclass to produce, disables nothing. A count above half is a candidate: read the overrides and confirm that they redefine what the subclass inherits, which signals a wrong hierarchy. Open the callers that hold the subclass as its base type and note which of them reach a refused operation. Validator question: **Does the subclass override an inherited operation that its base type's documentation does not mark optional so that it only fails or omits the effect that documentation specifies, or redefine more than half of the methods it inherits by a confirmed count?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-43`, severity minor, `file`, `symbol`, `code` = the refusing override, or the subclass declaration with its overridden methods, verbatim from the diff, `fix` = the subclass rewritten in the file's language to hold the former base as a field and forward only the operations it supports, or the refused operation moved out of the base into a narrower base type, `rationale` = the refused operation and the base type's documentation that does not mark it optional, or the count of overridden against inherited methods, and the callers that reach the refusal through the base type).
