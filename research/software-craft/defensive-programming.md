# Research note — Defensive programming

Topic `defensive-programming` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: CC8 (Code Complete 2nd ed. ch. 8 'Defensive Programming'); SW4.4 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.4; its V3 counterpart, ch. 3 §4.4 'Assertions, Design by Contract, and Defensive Programming', is openable in the ligurio/swebok-v3 transcription master 3_software_construction.md).

Code Complete ch. 8 (read through reading notes) and SWEBOK V3 §4.4–4.5 (the openable counterpart of SW4.4) define defensive programming as protecting a routine from invalid inputs. In that view a routine checks its parameters and decides on purpose what a failed check does. It uses error handling for conditions that can occur and assertions for conditions that cannot. The program has a barricade, so code inside it trusts what the entry points checked, and the code does not check everything everywhere. The industry splits on four questions. (1) Are assertions compiled out of production builds (SWEBOK, Code Complete) or left on (Rust's assert!, Guava Verify, The Pragmatic Programmer)? (2) Does a failed check stop the program (Rust book, Google Go best practices) or does the program keep running (Effective Go, Go FAQ)? ERR-06 and ERR-12 already carry this split. (3) Is a bad value rejected (Rust C-VALIDATE, RFC 9413) or substituted or defined away (Code Complete's robustness techniques, APOSD ch. 10)? (4) Does the callee check its preconditions (SWEBOK, Guava, .NET CA1062) or rely on its callers (Meyer's Non-Redundancy principle, unfetched; The Pragmatic Programmer; Clean Code)? On the fourth question, Guava's 'it's the context' and CA1062 give an openable separating condition: who can call the routine. Most of the evidence is official documentation and static-analysis rule pages, and it covers Java, Python, TypeScript, Go and Rust. These sources show three things. Python's assert, Java's assert and Rust's debug_assert! do not run in default or optimized builds. Forced unwraps add no check (TypeScript's !, typing.cast) or abort (unwrap, Go's single-value type assertion). Tools flag unchecked and degenerate null checks. The research is thin and was read only through It Will Never Work in Theory (NWIT) reviews and abstracts. Missing precondition checks are a frequent bug-fix pattern in mined Java fixes (Campos & Maia ESEM 2017), and mishandled null is a leading defect cause (Coelho ESE 2017; Khan TSE 2022). The one study that tied assertions to fewer defects (Casalnuovo ICSE 2015) lost the effect in its authors' replication, where it reversed sign and became negligible, so no card may claim that assertions reduce defects. The spine yields six cards: a precondition check on entry at a module boundary; no removable assertion for a condition that can fail in real life; no degenerate presence check; a possibly-absent value checked before dereference; a forced unwrap only with a stated local guarantee; and one condition per precondition check. One rule stays pending without a separating condition: how much internal checking stays on in release builds. The barricade is held as the design idea behind two of the cards. Six candidates fold into this topic's cards or into ERR-06, ERR-08 and ERR-09.

## Formulation layer

The canon agrees on four points. A routine checks its inputs, and it fails where an assumption breaks instead of carrying on with bad data. Assertions are for the impossible and error handling is for the expected. A forced unwrap needs a stated reason. Sources: Code Complete ch. 8 (through reading notes), SWEBOK V3 §4.4–4.5 (fetched), Pragmatic Programmer topics 24–25 (through a summary), 97 Things thing_21/26/84, Rust book ch. 9.3, the Guava precondition docs, Effective Java Item 49, and the Google TS guide and TS handbook on the `!` operator. None of Code Complete, The Pragmatic Programmer, APOSD, Clean Code, Effective Java, Meyer's OOSC2 or SWEBOK V4.0 could be opened. Their items rest on third-party reading notes on GitHub (relayed), on one WebSearch snippet carried over from the error-handling run, or on memory (unfetched). WebSearch was unavailable, and neither the aposd-vs-clean-code discussion nor Software Engineering at Google takes a position on defensive programming. The canon splits on four questions. (1) Are assertions compiled out of production (Code Complete, SWEBOK V3) or left on (Pragmatic Programmer, Rust assert!, Guava Verify, Duffy)? (2) Does a broken contract crash the program (Pragmatic Programmer, Rust book, Google Go best practices, Duffy) or does it keep running (Effective Go, Go FAQ, Uber 'Don't Panic')? (3) Is a bad value rejected (Rust C-VALIDATE, RFC 9413, Guava) or substituted or defined away (Code Complete's robustness techniques, APOSD ch. 10)? (4) Who checks a precondition: the callee (Code Complete, SWEBOK, Effective Java, Guava) or only the caller (Meyer's Non-Redundancy principle, the Pragmatic Programmer's design-by-contract section, Clean Code's no-null convention)? The official language docs make 'checks that vanish' checkable across languages: Python drops assert under -O, Java runs assertions only with -ea, Rust skips debug_assert! in release builds, TypeScript's `!` never runs, and Go has no assertion.

## Reception layer

I couldn't search the web this run: WebSearch had used up its budget. So this layer comes almost entirely from GitHub-hosted tool rule pages, style guides, library docs and practitioner essays. No Hacker News or Lobsters thread, paper abstract or vendor page could be opened. Sonar S2259, and the other symbolic-execution rules, are no longer in the public sonar-java repository. Tool rules in all five languages check three things: unchecked dereferences and forced unwraps; assertions that vanish in optimized builds (they must not carry validation or side effects); and checks the types already prove redundant. Most of these rules are off by default: clippy's restriction group, Ruff S101, Error Prone AssertFalse, forcetypeassert in golangci-lint, and typescript-eslint's strict config. SA5011 is disabled on staticcheck master. Four positions are disputed by name: forced unwraps (clippy and typescript-eslint against Andrew Gallant and the Google TypeScript guide's comment-justified `!`); Python assert used for type narrowing (mypy's docs against the Google Python guide and Bandit/Ruff); keep running versus crash (Effective Go and the Go FAQ against Google's Go best practices, Tiger Style, Verity Stob and The Pragmatic Programmer); and whether a routine re-checks its own precondition (CA1062 and Rust C-VALIDATE against Meyer's non-redundancy principle, unfetched). ## Evidence layer

The evidence for defensive programming is mostly official documentation and static-analysis rule pages, with thin and contested research behind it. Seven claims have openable support across Java, Python, TypeScript, Go and Rust. (1) Check preconditions on entry and fail where the violation happens: SWEBOK V3 §4.4, Guava, Objects.requireNonNull, Rust C-VALIDATE, the Google Python guide and SpotBugs, plus Campos & Maia ESEM 2017 (29% of 4M+ Java bug fixes add a missing precondition check, relayed through the NWIT review). (2) A precondition check must not be a construct that vanishes in a default or optimized build: CPython -O, the java launcher's -ea default, Rust debug_assert!, Ruff S101 and Sonar S4274/S3346, confirmed by a local run. (3) Use a forced unwrap only where local logic guarantees the value, and write the reason at the site: typescript-eslint, the TypeScript handbook, the Google TS guide, clippy, Rust core docs, the Rust book, the Go spec and the Uber guide. (4) Unchecked dereference is flagged by SpotBugs NP_*, nilness, SA5011, pyright and strictNullChecks; Coelho 2016 (via NWIT) and Khan TSE 2022 report null mishandling as a leading defect cause. (5) Validate at the boundary and use assertions inside: Guava 'it's the context', the Rust book's validation types, Google Go's package-boundary panics. Two research positions are contested. Casalnuovo ICSE 2015's small assert-reduces-defects effect reversed sign and became negligible in the authors' own replication, both read from PDFs on the author's GitHub Pages. And the fail-versus-continue choice splits the canon: Effective Go and the Go FAQ favour keeping servers running; the Rust book, Google Go best practices and RFC 9413 (draft source) favour failing over masking; SWEBOK V3 says assertions are normally compiled out, while Rust's std says assert! is always on and debug_assert! only after profiling. Not opened: Osman SANER 2016 and Estler FM 2014 (no GitHub-hosted copy, WebSearch exhausted), Sonar S2259 (absent from the public sonar-java tree and from SonarSource/rspec), the CERT and CWE pages (named only through Sonar's resource lists), and the SWEBOK V4 text.

## Spine — candidate rules in source order

1. **A routine callable from outside its module checks, on entry and before any side effect, each condition on its arguments or its object's state that its correctness needs and its parameter types do not enforce, and fails there when one is violated** — This applies to a public or exported routine or constructor whose correctness depends on an argument being present (non-null), within a range or index bound, or on its object being in a required state. It checks that condition at the start of its body, before its first side effect. A violation fails there with the language's precondition failure: an invalid-argument, null-argument or illegal-state error, or a returned error or documented panic where the language reports contract violations that way. A violating call is then reported at entry as the caller's mistake and does not break the routine. A condition that the parameter's type already rules out (a non-optional type, a validating type) needs no runtime check. A non-public routine reached only through checked entry points may rely on its callers' checks. A value that crosses a trust boundary is judged by security-hygiene-in-ordinary-code. Whether the failure stops the program or returns an error is judged by ERR-06 and ERR-12.
