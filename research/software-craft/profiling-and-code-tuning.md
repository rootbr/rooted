# Research note — Profiling and code tuning

Topic `profiling-and-code-tuning` of group G. Diagnostics and performance, domain `performance`, id prefix `PRF`. Formulation locators: CC25 (Code Complete 2nd ed. ch. 25 'Code-Tuning Strategies'); CC26 (Code Complete 2nd ed. ch. 26 'Code-Tuning Techniques'); PoP7 (The Practice of Programming ch. 7 'Performance': a bottleneck, timing and profiling, strategies for speed, tuning the code, space efficiency, estimation); SW4.14 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.14).

The canon (Code Complete ch. 25–26 and The Practice of Programming ch. 7, read through third-party notes and a transcription) states one cycle almost word for word. Confirm there is a performance need. Profile to find where the time goes, change one thing, and re-measure against a simple baseline you kept. Revert what does not pay, and keep records. SWEBOK (V3 §4.14/§5.4 fetched; V4.0 unfetched) defines code tuning as modifying correct code at the hot spots a profile shows. The admissible evidence is mostly official documentation and tool rules, and it covers all five languages. It includes the CPython FAQ and the profiling and timeit docs; Go's diagnostics page, the testing B.Loop doc, benchstat and the contribution guide; Google's and Uber's Go style guides; Rust's core::hint, black_box and debug_assert docs and clippy's lint pages that say to measure; JMH's samples and defaults, Criterion, pyperf, Node's compare.js guide and LLVM's benchmarking tips; the C++ Core Guidelines Per.1–Per.6; Google eng-practices; and Abseil's Performance Hints and fast tips. Two research items were fetched: Costa et al. (TSE 2019) on bad JMH practices and the Stabilizer abstract (ASPLOS 2013). Mytkowicz 2009/2010, Burchell 2023, Georges 2007, Jin 2012 and Nistor 2013 are relayed only. Knuth 1974/1971, Barrett 2017 and Selakovic 2016 are unfetched. The industry disagrees on five points. (1) Should performance wait for a profile (CC2 §25.2, Fowler), or should the faster form be chosen whenever it is just as clear (Dean & Ghemawat, APOSD ch. 20, C++ Core Guidelines P.9)? The sources split on whether the faster form adds complexity. (2) Which statistic should summarise repeated runs: timeit's minimum, benchstat's median with a confidence interval, or pyperf's mean ± std dev? No source gives a condition that separates them. (3) Can warm-up reach a steady state? Criterion and JMH assume so; pyperf, relaying Barrett, says some benchmarks never get there. (4) Should noise be suppressed (LLVM disables ASLR) or the setup randomised (Mytkowicz, Stabilizer)? (5) How far can a profile's ranking be trusted? PoP calls profile statistics only approximate, relayed studies find that profilers disagree, and Coz says a profile does not measure payoff. Separately, the relayed studies find that many performance bugs are discovered by reasoning about code rather than by profiling. The evidence supports eight cards a finder can check on a diff. (1) Complexity added for speed needs a measurement that shows the cost matters. (2) A performance change records its measured before-and-after result. (3) A claimed gain rests on repeated runs against the base version and exceeds their variation. (4) A benchmark keeps the measured work alive and its setup out of the timing. (5) A benchmark keeps its harness's warm-up, forks and repetition. (6) Tuning that does not pay is reverted. (7) Restructuring of code marked performance-critical is re-measured. (8) A tuned rewrite is tested against the plain version. The rest of the canon is held, pending or folded: estimation, the levels above code tuning, trust in profiles, noise control, peer review of benchmarks, and the boundary where a faster form is just as clear.

## Formulation layer

The canon agrees on one cycle: confirm there is a need, profile to find where the time goes, change one thing, re-measure against a simple baseline you kept, revert what does not pay, and record the result. PoP ch. 7 states it most fully; I opened it through a third-party transcription. It also appears in CC2 §25.6 (relayed through reading notes), APOSD ch. 20 (relayed through a summary), Pike's rules, Effective Java Item 67 and openable engineering-practice documents: Dean & Ghemawat's Performance Hints and the Abseil tips, go-perfbook, the Rust Performance Book, the Google and Uber Go style guides, Google's eng-practices, Software Engineering at Google, the C++ Core Guidelines and the Python FAQ. Several primary texts could not be opened, so they reach this layer only as notes, quotations or memory: the Code Complete chapters, with §32.5 'document surprises' from memory only; the APOSD ch. 20 text, Refactoring and Effective Java, all through third-party notes; SWEBOK V4, with V3 §4.14/§5.4 fetched instead; Knuth 1974 and Ousterhout's CACM 2018 article, through quotations; and the profiler-accuracy and performance-bug papers, through the orchestrator's snippets. The canon disagrees on three points. First, whether to set performance aside until a profile exists (CC2 §25.2, Fowler) or to pick the faster alternative whenever it is just as clear, so that no flat profile forms (Dean & Ghemawat, APOSD ch. 20, Sutter, CppCoreGuidelines P.9); in the APOSD-vs-Clean-Code exchange, a readability refactor caused a measured 3-4x slowdown. Second, which statistic a benchmark should report: timeit's minimum, pyperf's mean ± standard deviation, or Advanced R's minimum and median. Third, how far a profiler can be trusted (PoP: 'only approximate'; Mytkowicz 2010 and Burchell 2023, relayed) and whether profiling is how performance bugs are found at all (Nistor 2013, relayed: through code reasoning). Warm-up is nearly absent from the classic canon, which predates JIT concerns, so that part of the benchmark rule must rest on research and harness documentation in the evidence layer.

## Reception layer

This layer covers how practitioners receive the rules, using sources hosted on GitHub: books, discussions, harness and style-guide docs, tool rule pages, and PMD and clippy issues read through the GitHub API. WebSearch was out of budget and HN and Lobsters were unreachable. Sources broadly agree on measuring before and after tuning: the Knuth and Pike formulations, Bakhvalov, Nethercote, JMH, benchstat, Rust's core::hint docs, clippy's measure-first lint pages and PMD's maintainer in 2025. They also agree on putting benchmark data in the change description: the Go contribution guide, Google eng-practices, and comments that cite profiles. Sources disagree on five points. (1) How to summarise repeated runs: CPython timeit and Julia BenchmarkTools favour the minimum; Stinner and pyperf use mean plus or minus stdev; benchstat uses the median with a CI. (2) Whether to suppress noise (Google Benchmark disables ASLR) or keep the environment representative (Stinner, Bakhvalov). (3) Whether to wait for a measured need (Knuth, Pike, Martin) or plan for performance early (Muratori, Bakhvalov, SWE at Google's latency history). (4) Whether small speedups are worth chasing (Pike vs Nethercote and Bakhvalov; Ruff calls its perflint rules negligible). (5) Whether a profile's ranking tells you what to tune (Coz), and whether one-shot instruction counts can replace repeated wall-clock runs (Gungraun vs Nethercote). Not opened: the Knuth paper (quoted through a third-party page), Hyde 2009, Muratori's article, Tratt's posts, and every forum thread.

## Evidence layer

Every rule this topic owns has openable evidence. Official documentation in all five languages supports measuring before tuning and profiling to find hot spots: the CPython FAQ and profiling docs, Go diagnostics, the Google and Uber Go guides, Rust's debug_assert! docs and SWEBOK V3 §4.14/§5.4. Benchmark method is backed by fetched harness docs: benchstat (at least 10 runs, median with CI, interleaved runs, no rerunning until significant), Criterion (warmup, bootstrap comparison against the saved run), JMH samples (forks, run-to-run variance, dead code, loops), pyperf, Node's compare.js guide, Rust black_box and Go b.Loop. Costa et al. (TSE 2019, opened through neverworkintheory) and the Stabilizer abstract (ASPLOS 2013, opened in its GitHub README) are the research anchors in this set that are fetched. Mytkowicz 2009/2010, Burchell 2023, Georges 2007, Jin 2012 and Nistor 2013 are relayed only. Knuth 1971/1974, Barrett 2017 and Selakovic & Pradel 2016 are unfetched, so none of them can be a card's only anchor. The sources disagree in four places: (1) Python timeit says report the minimum, while benchstat, Criterion, pyperf and Node say report a median or mean with a confidence interval and a significance test. (2) Warm up to a steady state (Criterion, JMH) against 'on some benchmarks performances are never stable' (pyperf, relaying Barrett). (3) Reduce noise by disabling ASLR (LLVM) against randomizing the setup to remove measurement bias (Mytkowicz, Stabilizer). (4) 'Profile before optimizing' is qualified by studies showing that profilers disagree on the hottest methods and that most performance bugs are found by code reasoning or pattern rules, not by profiling. No openable source backs PoP7's estimation rule, and the space-efficiency rule rests only on tool documentation.

## Spine — candidate rules in source order

1. **Speed is one quality among several, and the levels above code tuning are considered before code is tuned** — CC2 §25.1 treats performance as only loosely related to code speed: time spent on speed is not spent on other qualities, and work on speed can hurt overall performance. A change at a higher level may pay more. No threshold is given.
   - formulation: CC25 §25.1 'Performance Overview' (Quality Characteristics and Performance; Performance and Code Tuning), via michaelbaly/code_complete chapter notes
   - reception: not contested
