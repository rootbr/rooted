# A random value that must be unguessable comes from a cryptographically secure random generator, never from a general-purpose generator, a UUID or a clock

## Thesis
A random number or string that is intended to be non-guessable, such as an encryption key, an IV, a session id, a CSRF token or a password reset token, is generated by the platform's cryptographically secure pseudo-random number generator and, unless it is an IV or nonce used with an encryption key, a lookup secret or an out-of-band authentication code, has at least 128 bits of entropy. Output of a general-purpose generator and a clock reading do not meet this condition, and a UUID does not meet it wherever the 128-bit floor applies.

## Rationale
A general-purpose pseudo-random generator provides low-quality randomness that is much faster, and it is often possible for attackers to guess or predict its output: an attacker who knows or can guess its internal state may predict the next value it generates. Standard libraries document their default generators as not cryptographically secure, as designed for modelling and simulation rather than security or cryptography, or as possibly easily predictable regardless of how they are seeded. A predicted value may let an attacker guess session tokens, encryption keys, password reset links or other secrets, leading to unauthorized access or impersonation, and a key or IV from such a generator weakens the cryptographic scheme, potentially making it trivially breakable. A cryptographically secure generator is designed to produce a greater amount of entropy, which makes it safe to use for security-sensitive functionality. The floor of 128 bits of entropy is a Level 2 application security verification requirement, which notes that UUIDs do not respect it. Predictable random numbers are classed, with exposed secrets and vulnerable certificate verification, among the cryptographic API misuses that seriously threaten software security.

## Example
```java
bad:  Random rng = new Random();
      String resetToken = Long.toHexString(rng.nextLong());
good: SecureRandom rng = new SecureRandom();
      byte[] bytes = new byte[16];
      rng.nextBytes(bytes);
      String resetToken = HexFormat.of().formatHex(bytes);
```

## Limits
The value's purpose decides which generator is right. One tool rule checks for uses of the general-purpose generator's drawing functions and calls such generators insecure because they are easily predictable; its documented example is a bare draw of a number below ten with no context showing a security use. A general-purpose generator can be used for non-security functionality such as ordering results on a page or randomizing UI elements, and applications such as scientific simulations and replaying gameplay require the ability to seed the generator into a known state, which a cryptographically secure generator lacks by design. A cryptographically secure generator is slower and more CPU-intensive and can block in some circumstances when large amounts of random data are requested, so it may not be appropriate for large amounts of non-security randomness. A version-4 UUID is randomly generated, and whether by a cryptographically secure generator depends on the implementation; one standard lists some platforms' random-UUID functions among the secure functions and advises that, unless the implementation is known to be secure, the randomness of UUIDs should not be relied upon, while the 128-bit requirement excludes UUIDs outright. For a nonce, IV or other single-use number used with an encryption key, the method of generation must be appropriate for the algorithm being used, so the 128-bit floor does not apply to it, while a nonce that serves as a non-guessable token keeps the floor; choosing that method is cryptographic design, which this rule does not reach. A lookup secret or an out-of-band authentication code also comes from the secure generator, and its own floor is 20 bits of entropy, typically six random digits, so the 128-bit floor does not apply to it either; for a time-based one-time password the secure generator supplies the seed.

## Validator
Grep the hunk for a call to the platform's general-purpose random generator, a seeded or small fast generator, a UUID constructor or a clock reading, and for a byte buffer the secure generator fills. Open the hunk around each hit and trace where the value goes: into an encryption key, an IV, a session id, a CSRF or password reset token, a generated password or another secret, or into a name that says so. Pass a hit whose value orders results, randomizes UI elements, drives a simulation or replays a seeded run. Validator question: **Does a random number or string intended to be non-guessable come from anything other than the platform's cryptographically secure generator, or, unless it is an IV or nonce used with an encryption key, a lookup secret or an out-of-band authentication code, carry fewer than 128 bits of entropy from it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-12`, severity major, `file`, `symbol`, `code` = the generator call, UUID or clock expression together with the name it is assigned to, `fix` = the value drawn from the platform's cryptographically secure generator with at least 16 random bytes, or for an IV or nonce used with an encryption key, a lookup secret or an out-of-band authentication code the length its algorithm or requirement sets, in the file's language, `rationale` = the value's security purpose and the predictability of its current source).
