# A handler that suppresses an unexpected error, letting execution continue without raising or returning it, records the error in a log statement

## Thesis
A handler that receives an error the code has no designed response for, caught by a clause or callback that accepts every error or returned by an operation the code expects to succeed, and that lets execution continue without handing the failure on, by substituting a value, skipping the work or moving on to the next unit of work, records the error in a log statement at warning severity or higher before execution continues. Handing the failure on means rethrowing or raising it, returning it or an error value, or setting a flag or a special value from which later code learns of the failure. A record at a debug or informational level does not count; a record through a facility that has no levels counts.

## Rationale
Once a handler neither raises nor returns an error, no caller learns of it, and a routine that must tell an external system about an error without propagating it to its callers has logging as an obvious channel. Debuggers are all too often inapplicable in production settings, which has made logging a principal way to record runtime information for postmortem analysis; a system that fails in the field without any evidence in its logs is significantly harder to diagnose, and about 96% of 54 experienced developers surveyed at one company called logs a primary source for problem diagnosis. A last-resort handler that catches every unhandled error, so that one error does not take down the whole process, exists in part so that error details that must go to the logs are not lost. The level tells the reader what the record means: a warning marks something unexpected while the software still works as expected, an error marks a more serious problem that kept the software from performing some function, and reporting the suppression of an error without raising an exception, as an error handler in a long-running server process does, takes a logger's error, exception or critical method as fits the error and the application domain. A debug record carries detail typically of interest only when diagnosing problems, an informational one confirms that things are working as expected, and a convention for recording exceptions assigns debug to exceptions that do not indicate an actual issue, so neither level describes an error the code did not anticipate. Logs are noisy: in 73 failures of distributed data-intensive systems reproduced with a minimal configuration and workload, the median failure printed 824 log messages, the vast majority at informational level, and a reader who wants only the error symptoms cuts that noise with a selective search on the error levels.

## Example
```typescript
bad:  const settings = await loadSettings(accountId).catch(() => DEFAULT_SETTINGS);
good: const settings = await loadSettings(accountId).catch((err) => {
        logger.error("loading settings failed; using defaults", { accountId, err });
        return DEFAULT_SETTINGS;
      });
```

## Limits
An error the code anticipates is outside the rule: some exceptions are expected in normal operation and others are satisfactorily handled or recovered without impacting the user, so not every exception is unexpected. The code shows the anticipation in three ways. A handler matches a specific error type and gives it a designed path, such as a parse of input that turns out not numeric and falls through to reading it as text, or a retry of the same or an alternative operation until it succeeds, such as rebuilding an address with a default scheme. A handler that names no error type guards a call that can fail only in the anticipated way, such as a parse or conversion of input. A comment in the handler explains why taking no action is justified. A handler that hands the failure on leaves the logging decision to the code that receives it, the reason for an unlogged catch block that most surveyed developers called common, 34 of 54. The rule is contested from both sides. Practice leaves most handlers without a record: in two industrial systems of 2.5 million and 10.4 million lines, 58% to 70% of catch blocks held no logging statement, mainly because the logging decision passed to later operations, the exception was recoverable, or it was not critical. A conservative strategy records more, logging every generic exception and function-return error for failure diagnosis, while developers asked why not log all exceptions answered that it "would produce a ton of garbage and make it hard to zoom in on real issues". What separates the cases is whether the error is unexpected: a verification standard requires an application to log unexpected errors from its second level, a language's logging documentation assigns a logger's error, exception or critical method to reporting a suppressed error, a static-analysis rule asks that a caught exception's message and stack trace be logged or passed forward but exempts parse and malformed-address exceptions as arguably indicating nonexceptional outcomes, and the studies explain the unlogged majority by exceptions that are expected, recoverable or not critical. The same static-analysis rule raises no issue for a handler that catches every exception through an unnamed error variable and returns a default value, reading the unnamed variable as making explicit that the exception is caught but not needed; the rule here does not read an unnamed or omitted error binding as a sign that the error is anticipated, since the binding shows only that the handler does not use the error, and the style guide's own example of a justified empty handler pairs its unnamed variable with a comment that explains why taking no action is justified. That an exception is not critical, having no critical impact on subsequent execution, is the most frequent reason among 70 sampled unlogged catch blocks, 32 of them, yet the reason surveyed developers called common least often, 7 of 54, since judging whether an exception is critical is difficult and depends largely on domain knowledge; a step counts as not critical here where the project context or a comment in the handler says so. Which of warning and error fits is disputed too: the logging documentation assigns error, exception or critical to a suppressed error, while a style guide asks for the error level sparingly, since error-level logging causes a flush and costs more than lower levels, and holds that messages at the error level should be actionable rather than more serious than a warning; a project context that states a level convention decides between the two. The floor is contested as well: the convention for recording exceptions lets application developers record exceptions at informational or trace level, and the static-analysis rule's compliant handler logs the exception at informational level, while the logging documentation defines information as confirmation that things are working as expected and assigns error, exception or critical to a suppressed error; the rule keeps warning as the floor, since warning is the level that marks something unexpected. A record does not make continuing safe: a study of production failures counted a handler that only logs an error as ignoring it, and traced a data loss to a handler that was empty except for a logging statement. Whether execution may continue after the handler, what the record must contain and where it is written are separate questions.

## Validator
Grep the added lines for a handler: a `catch`, `except` or `rescue` clause, a rejection callback, a branch on a returned error, a match arm or conditional binding on an error variant, and a call that turns a failed result into a default, an empty value or nothing, such as an unwrap-or, ok-conversion or suppress form. Keep each one after which execution continues without the failure handed on: the handler neither rethrows, raises nor returns the error or an error value, and sets no flag or special value that later code in the hunk reads as the failure. Judge whether the error is unexpected. It is when the handler accepts every error, through a bare or base-type clause or a callback or branch that never inspects which error arrived, or when the failed call is one the code expects to succeed, and the handler substitutes a value, skips the work or moves on to the next unit. It is anticipated, whatever clause, callback or branch receives it, when the handler matches a specific error type, kind or variant and gives it a designed path, when the failed call can fail only in the way the handler's designed path covers, such as a parse or conversion of input that turns out malformed, when a comment in the handler explains why taking no action is justified, or when the project context marks the step best-effort. Read the handler's body for a log statement that records the failure at warning severity or higher through a logger, an error reporter or the console stream the hunk's code uses for its other errors; a record at a debug, trace or informational level does not count, a record through a logger or stream that has no levels counts, and where the project context states which level a suppressed error takes, the record uses that level. Validator question: **Does an added handler or fallback let execution continue past an error it does not anticipate, substituting a value, skipping the work or moving on to the next unit without raising, returning or flagging the failure, with no log statement that records the error at warning severity or higher?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-45`, severity major, `file`, `symbol`, `code` = the handler or fallback call and its body quoted verbatim from the diff, `fix` = the same handler in the file's language with a log statement at error severity, or at warning where the project context reserves error for actionable records, that records the error before execution continues, `rationale` = why the error is unexpected, naming the catch-all or the call the code expects to succeed, and how execution continues without it: the substituted value, the skipped work or the next unit).
