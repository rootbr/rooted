# A forced unwrap, non-null assertion or unchecked cast is written only where the surrounding code guarantees the value is present and of the asserted type, and the site states that guarantee

## Thesis
A forced form tells the compiler or type checker that a value is present, or is of a given type, without handling the other case: a non-null assertion, an unchecked unwrap, and a type assertion or cast that insert no runtime check; an unwrap, an expect, or another accessor that throws or panics when the value is absent; a downcast that no type test confirms; and a single-value type assertion. A forced form is written only where other logic in the surrounding code ensures the value although the compiler does not understand that logic, and the site states the guarantee: the expect message describes the reason the value is expected to be present, or a comment explains why the assertion or cast is safe, unless the reason is obvious, as for a literal fixed in the code that can be seen to be valid. Where the value can be absent or of another type, as when it came from a user rather than being fixed in the code, the code checks and handles that case instead, with a runtime check, pattern matching, the two-value form of a type assertion with its flag tested, a default value, or propagation to the caller.

## Rationale
A non-null assertion, a type assertion and a cast that the runtime does not check only silence the type checker: the value passes through unchanged, no runtime check is inserted, and an assertion that turns out wrong can crash the program at runtime; an unchecked unwrap of an absent value is undefined behaviour. An unwrap, an expect, a single-value type assertion, a downcast and an optional's accessor fail at the site instead, with a panic or an exception when the value is absent or of another type, and a panic may abort the entire program. Either way the forced form is correct only while the logic that ensures the value holds: the operation underneath can still fail in general, even where failure is logically impossible in the particular situation, and the forced form silences the checker that would otherwise report that case. Stating the guarantee at the site records the assumption: an expect message conveys intent and assumptions, which makes tracking down the source of a panic easier, and naming the assumption, such as a value being fixed in the code, prompts a change to better error-handling code when the value later comes from another source. Where nothing ensures the value, a checked form handles the other case without a crash: a runtime check lets the type checker see the type in the code it guards, pattern matching or a default handles the absent case, and the two-value form of a type assertion reports a wrong type in a boolean and yields the zero value with no run-time panic.

## Example
```go
bad:  func label(decoded map[string]any) string {
          return decoded["name"].(string)
      }
good: func label(decoded map[string]any) (string, error) {
          name, ok := decoded["name"].(string)
          if !ok {
              return "", fmt.Errorf("field name is %T, not a string", decoded["name"])
          }
          return name, nil
      }
```

## Limits
The rule is contested, and whether the surrounding code ensures the value and the site says why separates the cases. A forced form is acceptable where a local property of the code ensures the value and the reason is in the expect message or a comment, or is obvious (the Source entries marked allow); without that guarantee, the same sources say to write a runtime check or to handle the result more robustly. The lints that forbid the forced form outright say to structure the program so the type checker sees the absent case, to handle the absent or failed case, and to check every type assertion, one of them calling a forced form often a sign that code is not fully type-safe (the entries marked avoid). Those bans are opt-in: the unwrap and expect lints sit in a restriction group that is allowed by default, and the unwrap lint itself accepts an expect with a more helpful message; the non-null assertion lint is in the strict configurations, not the recommended one; and the forced type assertion linter is outside its runner's default set. The outright ban is thus a project's choice: where the project context states it, a stated guarantee does not set the finding aside. A guarantee well known in the context of the code, such as fields a backend is known always to provide, may go without a comment; a project context that names it rejects the finding. Tests, examples and prototype code may unwrap without a stated guarantee: in a test a failed call should fail the whole test, and in an example or a prototype the unwrap is a placeholder for error handling not yet decided. Whether an unwrap or expect that stops the process on an expected, recoverable failure should return an error to the caller instead, how a value crossing a trust boundary is validated, a dereference of a possibly absent value with no forced form written, and an assertion statement that tests a condition at run time are judged by their own rules.

## Validator
Grep the added lines for a postfix non-null assertion, an unwrap or expect call, an argument-free accessor that throws on an empty optional, a type assertion, a cast operator, a cast function call and a parenthesized cast to a named type. Set aside a hit that is no forced form (a macro, an import alias, a constant assertion, a numeric conversion, a test framework's expect), the two-value form of a type assertion, a type switch, an unwrap or expect in a test file, an example or code the project context marks as a prototype, and an unwrap or expect on data from outside the program, whose stop on that expected failure is judged by its own rule. For each remaining hit, open the file, name the forced value and read the enclosing routine for where it comes from. Mark it ensured when the routine shows the value guaranteed on every path to the site: constructed, assigned, or parsed from a literal fixed in the code that can be seen to be valid, or tested just before the site by a check that leaves the path on the other case. Otherwise look at the site for a stated guarantee: an expect message that says why the value should be present, or a comment on the line or just above it that says why the assertion or cast is safe; a message that only names the failure states no reason. Mark it unguarded, whatever its message or comment says, when the routine shows the value coming from outside the program — input from a user, or data a file, the network or another service supplied, whether read directly, parsed or decoded from it, or looked up by a key taken from it — and no check in the routine before the site rules the other case out on every path; a value from any other source, such as a field, or a lookup or call that logic elsewhere in the code keeps from yielding the other case, counts as guarded when the site states that logic and nothing in the file contradicts it. Where the project context bans the forced form, treat every remaining hit as unguarded. Validator question: **Does an added non-null assertion, unwrap, expect, throwing accessor, type assertion or unchecked cast force a value that the enclosing routine shows coming from outside the program with no check before the site ruling the other case out, or a value that the routine neither shows to be ensured nor explains with a stated reason that the file bears out?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-17`, severity major, `file`, `symbol`, `code` = the added line carrying the non-null assertion, unwrap, expect, throwing accessor, type assertion or cast, quoted verbatim from the diff, `fix` = the checked form that handles the other case — a runtime check or pattern match, the two-value type assertion with its flag tested, a default value, or propagation to the caller — or, where the surrounding code does ensure the value, the same forced form with an expect message or a comment that says why the value is present or of the asserted type, in the file's language, `rationale` = where the forced value comes from and which case — absent, failed or of another type — the site neither rules out nor explains).
