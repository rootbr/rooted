# A type parameter that appears in a routine's result and in none of its parameters is declared only when the routine produces the result through an operation checked against the type argument

## Thesis
A routine declares a type parameter that appears in its result and in none of its parameters only when each value of that type the result carries is produced by an operation checked against the type argument: an operation that the parameter's bound provides, or a run-time test of the type argument that fails or reports the mismatch. Where the value would come from a cast or type assertion that nothing tests at run time and that the checker does not verify for every type the bound admits, from a value of a top type the checker does not check, or from an unsafe reinterpretation of memory, the routine instead returns the parameter's constraint or a top type the checker checks, whose value has to be narrowed or asserted before it is used as the chosen type, or takes a type token as a parameter and casts through it, so that the cast is either checked or written at the call where the reader sees it, rather than hidden behind a typed signature.

## Rationale
No argument fixes a type parameter that appears only in the result and in no bound of a type parameter that a parameter uses, so each call chooses the result type, by naming the type argument or by letting the compiler infer it from the call's context, and the body has to produce a value of whatever type is chosen. Where the body produces it through an operation of the parameter's bound, such as a parse that every admissible type implements, or through a run-time test of the type argument, the value has the chosen type or the call reports the mismatch: it returns an error, returns false with the zero value, or fails at the test. Where the body produces it through an unchecked step, nothing tests the value against the chosen type: a cast to an erased type parameter always succeeds, a type assertion that the language removes at compile time carries no run-time check, a value of the unchecked top type is assignable to every type, and an unsafe reinterpretation steps around the type system and is a valid use only provided that the chosen type is no larger than the data and shares its memory layout. The signature then promises the caller's type for a value that may have another: where the language inserts a cast at the call, the failure appears there, at the caller rather than in the routine that made the wrong value, and where it inserts none, the value is returned unchanged under the promised type. A typed signature over an unchecked step thus disguises an unsafe type assertion. Returning the constraint, or a top type the checker checks, leaves any assertion to the call, where the reader sees it; taking a type token lets the routine check the value against the type the caller asked for.

## Example
```go
bad:  func Decode[T any](buf []byte) *T {
          return (*T)(unsafe.Pointer(&buf[0]))
      }
good: func Decode[T any](buf []byte) (*T, error) {
          v := new(T)
          err := binary.Read(bytes.NewReader(buf), binary.LittleEndian, v)
          return v, err
      }
```

## Limits
Whether a type parameter may appear in a routine's result alone is contested, and one condition separates the cases: whether each value of that type is produced by an operation checked against the type argument. Against such parameters, a tool rule asks that a routine's type parameters always be referenced in the declaration of one or more formal parameters, a style guide advises against creating APIs whose generics appear only in the return type, and a language handbook asks to strongly reconsider a type parameter that appears in one location; the tool rules name the cost: operations on the type are unchecked once the type parameter is erased, unsafe casts occur where the routine is called, and the parameter can disguise an unsafe type assertion. The examples they give produce the value by a cast or by returning a parse result typed with the unchecked top type (the Source entries marked against). For such parameters, standard libraries declare them where a check produces the value: a parse into any type that implements the parsing interface its bound names, which returns an error when the text cannot be parsed into the desired type, and an error lookup that returns the first error matching the requested type, by a type assertion to that type, or else the zero value and false, which that library recommends for most uses over its form that takes a target of the top type (the entries marked for). The type-safety cost the first side names comes from the unchecked step, so the rule flags that step and lets the checked case stand. Both sides name one cost that a check does not remove: the routine is so general that inferring its type argument can cause problems and can make a call to an overloaded routine ambiguous, which both meet by naming the type argument at the call; how a call names it is outside the rule. A result that carries no value the routine converts, such as a new or empty container of the type parameter or the type's zero value, involves no cast and is outside the rule, as are a type parameter that also appears in a parameter, a type token included, one that appears in the bound of a type parameter that a parameter uses, which the argument fixes, and one that appears in neither the parameters nor the result.

## Validator
Grep the added lines for a type parameter list followed by a result that names one of its parameters, and for a cast, assertion or reinterpretation to a single-letter type. Open the routine in the file and list the type parameters that appear in its result; set aside each one that also appears in a parameter's type or in the bound of a type parameter that a parameter's type uses, a type token (a class or type object of the parameter) included. For each remaining one, trace every value of that type the result carries back to the line that produces it. Count as checked an operation the parameter's bound declares (a parse, a default, a factory), a conversion the checker verifies for every type the bound admits, a run-time test against the type argument that panics, throws, returns an error or reports false on a mismatch, and a value with no conversion in it (the type's zero value, a new or empty container of it). Count as unchecked any other cast to the type parameter, a type assertion the compiler removes, a returned value of a top type the checker does not check, and an unsafe reinterpretation of memory. For a declaration without a body, read the implementations the file holds; where it holds none, count it unchecked when the result is the type parameter itself, the bound declares no operation that produces a value of the parameter's type and the language erases type arguments at run time, since every implementation then has to cast. Validator question: **Does an added or changed routine declare a type parameter that appears in its result and in none of its parameters, and produce a value of that type the result carries through an unchecked cast or assertion, a value of an unchecked top type or an unsafe reinterpretation, rather than through an operation of the parameter's bound or a run-time test of the type argument?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-47`, severity major, `file`, `symbol`, `code` = the routine's signature line and the line that produces the value through the unchecked step, verbatim from the diff, `fix` = the routine returning the parameter's constraint or a top type the checker checks, taking a type token and casting through it, or producing the value through the bound or a run-time test of the type argument, in the file's language, `rationale` = the type parameter that appears only in the result, the unchecked step that produces its value, and what a caller that chooses a wrong type argument receives).
