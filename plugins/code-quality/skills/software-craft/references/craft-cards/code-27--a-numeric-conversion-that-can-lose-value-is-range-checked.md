# A numeric conversion that can lose value, into an integer type that cannot hold every source value or from an integer beyond a floating-point type's exact range, is range-checked or done with a checked conversion unless the value is known to fit

## Thesis
A conversion between numeric types whose target cannot represent every value of its source is applied only to a value shown to fit the target. Three kinds of conversion qualify: an integer into an integer type whose range does not contain the source type's range, because it is narrower or of the other signedness; a floating-point value into an integer type; and an integer the code needs exact into a floating-point type whose exact integer range is smaller than the source's, a range that ends at 2^53 − 1 in magnitude for a 64-bit float. A value is shown to fit by a range test against the target's limits on every path to the conversion, by a checked conversion that reports a value that does not fit as an error, an exception or an explicit fallback instead of altering it, or by a bound the code itself places on the value: a constant within the target's range, or a remainder, a mask, a right shift, a minimum or a clamp by constants that keep it within that range. A conversion of a value the code leaves unbounded breaks the rule unless the code marks the loss as intended.

## Rationale
An unchecked conversion of a value that does not fit changes the value without any error. An integer converted into a narrower integer type is truncated to fit the result type's size; the conversion always yields a valid value with no indication of overflow, and the result can lose the magnitude of the original and even come out with the opposite sign. A negative value converted to an unsigned type wraps around to a large positive value, and an unsigned value too large for a signed type of the same size comes out negative. A floating-point value converted to an integer is truncated toward zero; a value beyond the integer type's range saturates to the type's minimum or maximum in one language and yields an implementation-dependent result in another, and in the saturating one NaN becomes 0. An integer converted to floating point becomes the closest representable value: a 32-bit float rounds 123,456,789 and 123,456,790 to the same value, and every integer above 2^53 − 1 shares its 64-bit floating-point value with at least one other integer, so 9,007,199,254,740,992 and 9,007,199,254,740,993 become one value and can no longer be told apart. Where a compound assignment converts its result back to the variable's type, a compound assignment to a variable narrower than its expression performs a narrowing conversion that the equivalent simple assignment would be rejected for at compile time. A checked conversion or a range test turns a value that does not fit into a case the code handles where the conversion happens, by an error, a default or a stop, instead of a changed value. Where the target holds every source value, a conversion form that accepts only lossless conversions keeps the conversion from becoming silently lossy if the source type later changes, and shows the reader that it is lossless. The lints that flag a possibly truncating, wrapping or rounding cast wherever it appears are off by default, since such a cast works as defined; an analyzer that flags integer conversions that may overflow treats a constant in range and an explicitly range-checked value as safe and has needed fixes for false positives. The finding is therefore a conversion whose source the code leaves unbounded, not every conversion.

## Example
```rust
bad:  fn slot(index: usize) -> u8 {
          index as u8
      }
good: fn slot(index: usize) -> Result<u8, TryFromIntError> {
          u8::try_from(index)
      }
```

## Limits
A conversion whose loss is intended is correct when the code marks it as intended: a wanted truncation with the lint for it suppressed at that conversion or, where no lint covers the conversion, a comment at it that says the truncation is wanted, or a reinterpretation of an integer's bits as the other signedness through a form that names the wrap. Rounding an integer to floating point is expected behaviour where the code uses the result as an approximation, and such a conversion is outside the rule; the finding there is an integer that may exceed the floating-point type's exact range and that the code needs exact or distinguishable from other integers. Discarding the fraction of a floating-point value within the integer type's range is the conversion's defined truncation toward zero, and the rule checks the range, not the rounding. A conversion into a type that holds every source value, such as a wider integer type of the same signedness or a 32-bit float into a 64-bit one, is outside the rule, and so is a conversion from one floating-point type into a narrower one. Overflow of arithmetic within one integer type and the choice of a decimal type for decimal quantities are outside the rule; parsing text into a number is outside it, while narrowing the parsed result is not. A project context that states its numeric inputs are bounded by validation at a named boundary, or that exempts a named module from checked conversions, rejects the finding for the conversions it covers.

## Validator
Grep the added lines for a numeric conversion: a parenthesized cast to a numeric type, a cast operator to a sized integer or floating-point type, a call-form conversion to an integer or floating-point type, a narrowing value accessor on a number object, a conversion of an arbitrary-precision integer to the floating-point number type, and a compound assignment to an integer variable from a wider integer or a floating-point expression. Open the file and, for each candidate, find the declared or inferred type of the source and of the target; drop the conversion when the target holds every value of the source type, drop a conversion from one floating-point type into another, and drop a parse of text. For the rest, trace the source value back through the routine: a constant within the target's range, a remainder, mask, right shift, minimum or clamp by constants that keep it within that range, a range test against the target's limits on every path to the conversion, or a checked conversion form shows that it fits. For a conversion to floating point, check whether the source may exceed the type's exact integer range and whether the code needs the result exact, by comparing it, using it as a key or converting it back; drop it when the code uses the result as an approximation. Drop a conversion marked as an intended truncation or wrap, and one the project context exempts. Validator question: **Does an added conversion turn an integer into an integer type that cannot hold every value the source may hold, a floating-point value into an integer type, or an integer the code needs exact into a floating-point type whose exact integer range the source may exceed, with no range test, checked conversion or bound in the code that keeps the value within the target's range or exact integer range, and with no mark that the loss is intended?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-27`, severity major, `file`, `symbol`, `code` = the added conversion expression quoted verbatim from the diff, `fix` = the conversion done with the language's checked form or preceded by a range test against the target's limits, with the value that does not fit returned as an error, thrown, or given an explicit fallback, or, where the code wants the low-order bits, the conversion marked as an intended truncation, in the file's language, `rationale` = the source and target types, the source values the target cannot represent, and what the unchecked conversion turns them into).
