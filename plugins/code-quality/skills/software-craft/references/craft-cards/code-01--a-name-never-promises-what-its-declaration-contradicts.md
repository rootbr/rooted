# A name never promises a type, a return value or a plurality that its own declaration contradicts

## Thesis
The words of a name agree with the declared type or signature of what it names. A field, property, local variable or routine whose name opens with a predicate word (is, has, can, have, should, will) holds or returns a boolean. A routine whose name opens with get or return returns a value; one that opens with set returns nothing; one that opens with to or as returns the converted value; a validation routine, one named validate, check, ensure or the like, reports whether the validation passed. A noun phrase that names what a field or property holds, or what a routine returns (alone, or after get or return), is singular for one value and plural for a collection, one that ends in a container word (list, array, map, dict, set, collection) counting as plural; and no word of the name of a field, property or routine is the antonym of a word in the name of the type it holds or returns. A mismatch that the declaration's own documentation states (the actual type or values, or where the result is left) meets the rule, except an antonym between name and type, which documentation does not cure; the undocumented mismatch is the defect.

## Rationale
A name is read at every use site, far from its declaration, so a name whose words contradict the declaration misleads wherever it is used: a predicate-named integer admits a range of values nobody documented, a get or to routine that returns nothing leaves the reader searching for where the result went, a singular name on a collection leaves it unclear whether a change touches one element or all of them, and an antonym between name and type invites a wrong assumption. These signature-level mismatches belong to a catalogue of 17 linguistic antipatterns, recurring inconsistencies among an entity's name, documentation and implementation, mined from open-source projects and abstracted over methods and attributes. Several of the catalogue's definitions make the missing documentation part of the defect (a return type "without proper documentation", a result whose place "is not clear from the documentation"), and the rule accepts a documented mismatch in every case but an antonym, which the catalogue lists with a documented routine as its example. Surveyed on the catalogue, the majority of developers judged the antipatterns poor naming practice, and in a study that measured cognitive load by functional brain imaging while developers performed comprehension tasks, the presence of linguistic antipatterns in source code significantly increased it. Agreement between name and declaration restores what a name is for: the reader can act on the name without opening the declaration. The predicate, get, set and conversion cases are decidable from the declaration alone, and a static-analysis rule checks them.

## Example
```java
bad:  int isExpired(Session session) { ... }
      void getItems(Cart cart) { ... }
      void toArray(Cart cart) { ... }
      void validate(Order order) { ... }
      List<Item> item;
good: boolean isExpired(Session session) { ... }
      List<Item> getItems(Cart cart) { ... }
      Item[] toArray(Cart cart) { ... }
      boolean validate(Order order) { ... }
      List<Item> items;
```

## Limits
The rule reads a name against its declaration; a routine whose behaviour goes beyond its signature (a getter that also creates or mutates state) and a comment that contradicts its declaration are outside it. A name fixed by a supertype or an interface, on a routine that overrides or implements an inherited member, is judged at the declaration that introduced it; the static-analysis rule skips routines annotated as overrides by default. A set routine that returns its own receiver type for chaining, the builder form, meets the rule, and the static-analysis rule exempts it. A validation routine that reports failure by an exception its declaration or documentation names reports its outcome. A promise, future or task counts as the value it resolves to, and where the language reports failure by return value, an error or result counts as the success value it carries: one that resolves to or carries a boolean is boolean, one that resolves to or carries a collection is a collection, and one that resolves to or carries nothing returns nothing; so a set routine may return a promise that resolves to nothing or an error or result that carries nothing, and a validation routine that returns an error or result reports its outcome by it. To or as inside a name rather than at its start is no conversion marker here: the static-analysis rule leaves that check off by default as prone to false positives. A boxed boolean, an atomic boolean, a predicate function and a one-bit field count as boolean, and so does a small fixed-width integer that holds a truth value in a structure whose size or layout matters. No case reaches a parameter, which neither the catalogue nor the static-analysis rule checks; the plurality and antonym cases reach fields, properties and routines, the scope the catalogue covers, and not local variables. A declaration with no declared or annotated type is judged by the value the hunk assigns or returns; where the file does not make that value's type evident, the rule does not reach it. An antonym between name and type, a plural noun on a single value and a collection type written without its element type match none of the card's patterns: the review reaches them only in a hunk that another pattern dispatches, and the developer checks them on every declaration it writes.


A container word at the end of a name meets the plurality check only: it repeats the declared collection type, so the fix for a singular name on a collection is the plural noun, items, not a container suffix such as itemList.
## Validator
In the hunk, take each added declaration whose name opens with is, has, can, have, should, will, get, return, set, to, as, validate, check, ensure or verify, whose name ends in a container word (List, Array, Map, Dict, Set, Collection) or a plural noun, whose declared type is a collection, or whose name and type name carry a pair of antonyms. Read its declared type or return type; for a routine without one, open its body in the file and read what its return statements yield. Open its doc comment and any declared exceptions, and check in the file whether it overrides or implements an inherited member. Skip parameters, and skip plurality and antonym mismatches on local variables; read a name's number only in a noun phrase that names what a field or property holds or what a routine returns, alone or after get or return. Validator question: **Does an added declaration that does not inherit its name carry a word promising a boolean, a returned value, no return value, a converted value, a validation outcome, one value, a collection or the opposite of its type, while its declared type or signature contradicts that word and, unless the word is the opposite of its type, its documentation does not state the actual type, values or where the result is left?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-01`, severity minor, `file`, `symbol`, `code` = the added declaration line carrying the name and its type or signature, verbatim from the diff, `fix` = the declaration with the name reworded to match its type or the type changed to match its name, in the file's language, `rationale` = the word of the name, the promise it makes and the part of the declaration that contradicts it).
