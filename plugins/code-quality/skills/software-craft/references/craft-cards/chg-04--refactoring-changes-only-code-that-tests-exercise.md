# A behaviour-preserving refactoring changes only code that tests exercise, adding tests of current behaviour where none exist, ideally in an earlier change

## Thesis
A change intended to preserve behaviour restructures only code that tests exercise. Ideally those tests already exist; where they do not, tests of the code's current behaviour are added, preferably in a separate change submitted before the refactoring so that they can validate the tested behaviour unchanged before and after it, otherwise in the refactoring change itself.

## Rationale
Refactoring is commonly performed by hand and supported by regression testing, the selective retesting of software or a component to verify that the modifications have not caused unintended effects, which serves as the safety net that gives confidence in the edits. Inadequate test suites may prevent developers from initiating or performing refactorings. Tests added to untested code before the refactoring increase confidence in it: submitted first, they can validate that the tested behaviour is unchanged before and after the refactoring. Performing a refactoring with an engine does not replace the tests, because a bug in the engine can erroneously change large bodies of source code: automated testing of the engines of two popular open-source IDEs exposed 21 and 24 new bugs, and testing 29 refactorings in three engines over 153,444 transformations identified 57 bugs related to compilation errors and 63 related to behavioural changes.

## Example
```java
bad:  // refactor: price() extracted from checkout(); no test calls either
      private int price(Item item) { return discount(base(item)); }
good: @Test void checkoutPinnedOnCurrentCode() {
          assertEquals(90, new Cart().checkout(new Item(100)));
      }
      // extracting price() lands later; the test passes before and after
      private int price(Item item) { return discount(base(item)); }
```

## Limits
A change generated by an automatic refactoring tool that is trusted completely may be larger than other changes, and testing still applies to it. Adding the tests in the refactoring change itself meets the rule; a separate test change submitted first is the preferred form. A change that adds or changes logic is outside the rule; it carries new or updated tests for the new behaviour. The rule asks for tests that exercise the restructured code, not proof that they suffice: in a study with 15 professional developers inspecting problematic refactorings that carried seeded anomalies, testing alone located 13 percent of the anomalies. Techniques for bringing untested legacy code under test are outside the rule.

## Validator
Grep the hunk for refactoring vocabulary (refactor, extract, inline, rename, move, restructure) and for declarations whose body moved or changed shape without new behaviour; read the change description to confirm the change is intended to preserve behaviour. At scope callers, open the repository's test files and the tests this change or an earlier change on the branch adds, and search them for calls that reach each restructured routine or type, directly or through any chain of its callers. Validator question: **Does this behaviour-preserving change restructure a routine or type that no existing test and no test added in this change or an earlier one exercises?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-04`, severity major, `file`, `symbol`, `code` = the restructured declaration line quoted verbatim from the diff, `fix` = a test in the file's language that calls the restructured routine, directly or through a caller that reaches it, and asserts its current result, to land before or with the refactoring, `rationale` = names the restructured routine or type and the absence of any test that exercises it, so nothing verifies its behaviour unchanged).
