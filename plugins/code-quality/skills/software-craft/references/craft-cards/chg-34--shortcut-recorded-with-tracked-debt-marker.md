# A workaround, stopgap or other shortcut that a change ships unresolved is recorded where it lives with the project's debt marker referencing the tracked issue for its cleanup, not left as an untracked note such as 'for now' or 'temporary'

## Thesis
Code that a change ships unresolved and that its own comment, name or message presents as temporary, a short-term solution or good enough but not perfect — in words such as "for now", "temporary", "workaround", "stopgap" or "hack" — carries the project's debt marker at that code, and the marker references a tracked issue filed for its cleanup, ideally a bug. An admission of temporariness at the code that references no tracked issue is the finding. The cleanup's owner is the tracked issue's assignee; a name inside the marker gives context, not a commitment to fix.

## Rationale
Cleanup left for later seldom happens: the more time passes after the original change, the less likely it is, and unless it follows the change immediately it usually never happens, because it gets lost or forgotten in the press of other work. Debt that code comments admit is common and long-lived: it is found in 2.4% to 31% of the files of the projects studied, only 26.3% to 63.5% of it is removed after introduction, it averages 51 instances per system and increases over time through new instances that are not fixed, and even the instances that are fixed survive over 1,000 commits on average. In an industrial interview study, pressure is one case in which debt goes undocumented: one interviewee reported that when the pressure is very high, developers usually postpone its documentation, and in most cases it is eventually forgotten. A bug is the preferable reference because bugs are tracked and have follow-up comments, and a consistent marker can be searched to find out how to get more details; interviewees link code to such issues by adding issue identifiers in code comments. When a change exposes surrounding problems it cannot address right now, filing a bug for the cleanup and assigning it to oneself keeps the cleanup from getting lost. A name inside a marker typically points at the person with the most context, and it is not a commitment that this person will fix the problem.

## Example
```go
bad:  // Temporary workaround for now: retry until the upstream timeout is fixed.
      resp, err := withRetry(fetch, 3)
good: // TODO: tracker.example/issue/123 - Drop the retry once the upstream timeout is fixed.
      resp, err := withRetry(fetch, 3)
```

## Limits
Whether the shortcut may ship at all is outside this rule, as is the marker's wording: complexity a change introduces is cleaned up before submission unless it is an emergency, and a reviewer may insist on the cleanup now instead of a marker. A shortcut whose real fix lands in a later commit of the same change does not ship unresolved: a project may use a marker that blocks landing to signal from one commit a bug that a later commit fixes. Developers who expect debt to be solved in the near future may leave it undocumented, as one interviewee does with a quick workaround for an old release whose actual solution lands in the mainline immediately; that workaround still ships in the old release. Projects differ on whether a marker may stay in merged code, and the project's stated marker policy decides. On one side, temporary code keeps a marker that links a resource holding the context, ideally a bug (Google's style guides), and Ruff TD003 reports a marker without an issue link. On the other side, ESLint no-warning-comments advises fixing or reviewing the code and then removing the comment before the code counts as production-ready, Ruff FIX001, FIX002 and FIX004 advise resolving the issue before deploying while FIX003 accepts, at minimum, a more descriptive marker, CWE-546 advises removing such comments before deploying, and godox asks for tasks for the markers that cannot be fixed in the current merge request; under that policy the task filed for the cleanup is the record. Ruff FIX002 itself may not suit a project that uses markers as documentation of future work, and the rustc-dev-guide keeps one marker that blocks landing and another for notes left in the codebase. Not every marker needs a ticket: filing one for every item that comes to a developer's mind is held too burdensome (PEP 350, rejected), and interviewees admit debt they judge small in code comments alone, while others hold that every marker left in the code also has an issue; this rule reaches code the change presents as temporary, not a passing note, and a stated project policy that keeps small debt in comments decides where it exists.

## Validator
Grep the added lines of the hunk (comments, identifiers, log and error messages) for an admission of temporariness: "for now", "temporary", "temporarily", "stopgap", "workaround", "hack", "quick fix", "kludge", "band-aid", or a name such as tempFix or quickHack, and for the project's debt marker. For each hit, read the code it annotates and the marker on that code, and check for a reference to a tracked issue in the project's form: an issue URL, a tracker key or an issue number. Skip a hit whose fix lands in a later commit of the same change, a passing note that admits no shortcut, code under a stated project policy that keeps such notes in comments alone, and, under a stated project policy that keeps no markers in merged code, a hit whose tracked cleanup issue the change's description names. Validator question: **Does the hunk add code that its own comment, name or message presents as temporary or a workaround, with no debt marker at that code referencing a tracked issue for its cleanup?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-34`, severity minor, `file`, `symbol`, `code` = the added line that admits temporariness, quoted verbatim from the diff, `fix` = the same code under the project's debt marker referencing the tracked cleanup issue, in the file's language, or, under a stated project policy that keeps no markers in merged code, the tracked cleanup issue to name in the change's description, `rationale` = names the shortcut and the missing issue reference).
