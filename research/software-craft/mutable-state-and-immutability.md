# Research note — Mutable state and immutability

Topic `mutable-state-and-immutability` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'Shared State Is Incorrect State' (The Pragmatic Programmer, 20th anniversary ed., topic 34, ch. 6 'Concurrency'), read for its design claim that shared mutable state is a cost, not for its semaphore and transaction mechanics.

The canon agrees on one design claim: mutable state that more than one component can reach is a cost. Sources: PP Tip 57 read only for its design claim, PP Tips 47 and 48, Fowler's Mutable Data and Global Data smells, Out of the Tar Pit, Hickey and 97 Things. The canon and the style guides turn this into checkable practices. Keep mutable state out of static, module and package scope. Do not keep or hand out a mutable object across a boundary without a copy, a read-only view or an ownership transfer. Treat values that several components hold as immutable. Declare fields that never change final or readonly. Treat constants and immutable types as deeply immutable. Make copies that isolate deep enough. Never share one mutable default. Never mutate a hash key. The industry disagrees on how absolute the rule is, not on the claim itself. Airbnb's 'never mutate parameters' meets Effective Go's Read idiom and Rust's &mut, and whether the mutation is declared where callers look (Rust book ch. 4.2, typescript-eslint, ESLint) separates the two. Immutable value objects meet Goetz's mutable data holders, Stylos and Clarke's usability result and Van Roy and Haridi's modularity argument, and whether another holder can observe the change (React docs, Error Prone Immutable, Python FAQ) separates them. Final or const on locals splits by language convention with no sourced condition, so it stays pending. The strongest evidence is official documentation and static-analysis rule pages fetched from GitHub. These are the Google and Uber style guides, the JDK, Python, TypeScript, MDN, Rust and Go docs, and the SpotBugs, PMD, Error Prone, Sonar, ESLint, typescript-eslint, Ruff, Pylint and Clippy rules. They also supply the shared Limit that final, const, readonly, records, frozen dataclasses and unmodifiable views are all shallow. The research is thin. The Coblenz et al. 2016 and 2017 papers and Weber et al. 2017 are relayed snippets that report developer statements and one case study, not defect rates. The plume-bib abstracts state mutation errors as motivation, not as a measured finding. Most checks ship off by default. Concurrency correctness stays outside the corpus: PP topic 34's semaphores and transactions, Rust's data-race rationale and Winder's essay yield no rule.

## Formulation layer

The canon agrees on one design claim: mutable state that more than one component can reach is a design cost. That state may be a global or singleton, a collection a getter hands out, an argument stored or changed without a copy, or a shared default. Sources: PP Tips 47 and 57, Clean Code ch. 3, Refactoring 'Mutable Data' and 'Encapsulate Collection', Effective Java Items 17 and 50, APOSD §7.5, Out of the Tar Pit, Hickey, 97 Things. The style guides turn this into checkable rules: copy slices and maps at boundaries (Uber); no mutable exports and no shared-object default parameters (Google TS, Airbnb); const/readonly/val by default (Google TS, Kotlin); constants must be deeply immutable (Google Java); no module or package mutable state unless it is logically constant or unobservable (Google Go and Python). Opened and quoted: the 97 Things essays, the aposd-vs-clean-code discussion, APOSD chs. 7 and 19 from a third-party copy of the book text, Out of the Tar Pit (papers-we-love), the Hickey transcripts, the Effective Java and Fluent Python example code, and the style guides and language docs. PP, Clean Code and Refactoring were reached only through third-party GitHub chapter notes (relayed). Effective Java's prose, Code Complete, DDD, Liskov and Guttag, Fowler's bliki, Carmack, CERT/CWE and Stevens et al. are unfetched paraphrases. The sources disagree on how absolute the rule is and how to apply it, not on the claim. Airbnb's 'never mutate parameters' is contradicted by Effective Go's Read idiom, by clean-code-javascript's own caveat and by Code Complete, which only asks that changed parameters be documented. Bloch and Fowler make defensive copying depend on trust and cost; Rust's C-CALLER-CONTROL hands the copy decision to the caller through ownership. Fowler, Hickey and Go best practices allow mutation that stays within a few lines or that no other component can see. Several stated reasons are about concurrency and fall outside the corpus: PP topic 34's examples, Clean Code ch. 13, Rust's borrowing rule, Uber's Snapshot example and Winder's essay. In all five languages the built-in immutability is shallow (records, unmodifiable views, readonly, const), so a card must not overstate it. SE at Google and SWEBOK V3 have no rule on shared mutable state. 97 Things 'Beware the Share' is about shared code, not shared state, and is excluded.

## Reception layer

Most of what the industry says about this topic is in tool rules. Every ecosystem checks the narrow, mechanical forms: mutable default arguments (Pylint W0102, Ruff B006/RUF012, Sonar S5717), storing or returning internal mutable arrays and collections without a copy (SpotBugs EI_EXPOSE_REP/REP2, PMD ArrayIsStoredDirectly/MethodReturnsInternalArray, Sonar S2384, the Uber Go guide) and mutable static fields (PMD MutableStaticState, SpotBugs MS_MUTABLE_COLLECTION, Error Prone MutablePublicArray). Most of these rules ship off by default (PMD quickstart, eslint:recommended, the shared typescript-eslint configs, revive defaults, clippy nursery), and SpotBugs has spent its 2021–2026 releases fixing false positives on fields that are already immutable. The canon is split on marking locals and parameters that are never reassigned as final/const/val. Checkstyle sun_checks, the Kotlin conventions, rustc unused_mut, ESLint prefer-const and the Google TypeScript guide are for it. Error Prone UnnecessaryFinal ('weakly discouraged'), Checkstyle's own ParameterAssignment rationale, Dan Abramov and Niko Matsakis dispute it, and point out that blocking reassignment is not immutability. Several named sources put the hazard in mutation through a shared or aliased reference, not in mutation itself (Matsakis; Racordon et al., JOT 2022 on mutable value semantics; React's 'local mutation is fine'; Rust interior mutability), so rules should be worded about shared state. The opposing positions on record are these. Moseley and Marks relay Van Roy and Haridi's argument that state buys modularity. In Python, the rejection of PEP 416 (2012) and the acceptance of PEP 814 (2026) show the dispute over enforcing immutability versus relying on convention. Pankratius et al. (ICSE 2012) refute the claim that the functional style lowers debugging effort. Official documentation supplies Limits: unmodifiable views, readonly, frozen dataclasses, records and final fields are all shallow. Not opened: Hacker News and Lobsters threads and 2024–2026 surveys (WebSearch budget used up, hosts denied); SpotBugs issue threads (GitHub API not enabled for that repository); the Coblenz and Weber papers beyond the orchestrator's relayed snippets; Carmack's 2012 essay; the Sonar Java default profile and Ruff default-rules pages (both 404).

## Evidence layer

The rules this topic will likely produce are well documented. The strongest sources are official documentation and static-analysis rule pages, all fetched from GitHub: the Rust book, Python FAQ, tutorial and dataclasses docs, the JDK javadoc, the TypeScript handbook, Effective Go and the Go blog, the Google and Uber style guides, and the SpotBugs, PMD, Error Prone, Sonar, ESLint, typescript-eslint, Pylint, Ruff and clippy rules. They cover five themes: aliased mutation surprises the other holder; store or return a copy, a read-only view or an owned value at a boundary; a field never reassigned can be declared final, readonly or const; final and readonly are shallow; a hash key must not be mutated. The research is thin and mostly not opened. The three Coblenz/Sunshine papers (ICSE 2016, ICSE 2017, SecDev 2017) are available only as the orchestrator's relayed snippets, and their interview and case-study statements are not measured defect rates. The other research items are abstracts fetched from Michael Ernst's plume-bib on GitHub (Javari, IGJ, OIGJ, the Correa tool paper, Potanin's survey, Pechtchanski's 82% figure). Most of these state mutation errors as the authors' motivation, not as a measured finding. Contrary evidence: Stylos & Clarke (ICSE 2007, via NWIT) found programmers were more effective with parameterless constructors, which immutable classes give up; Boyland (FTFJP 2005) argues readonly qualifiers mismatch the problems they target; Pankratius et al. (ICSE 2012) refute lower debugging effort for Scala's mixed style, though in a multicore setting; and the Rust book leaves mutability to the author's judgement. Every check that flags argument or field mutation is off by default (ESLint props:false, PMD quickstart, Error Prone FieldCanBeFinal, clippy nursery). The Python mutable default argument is documented only as Python semantics, so it fits only as an Example. Not found: no statement of the claim in SWEBOK V3 Construction or Software Engineering at Google; the CERT and CWE pages could not be opened; and no paper was reachable beyond the relays, plume-bib and NWIT.

## Spine — candidate rules in source order

1. **Mutable state that independent components change lives in an instance each client creates, not at static, module or package level, unless no caller can observe its changes** — Sometimes two or more otherwise independent components change, or observe changes to, a mutable object held at static, module or package level: a collection, registry, cache or singleton field. That object belongs in an instance that each client creates and passes explicitly. Where shared state is warranted, it stays internal and changes only through the owning module's functions. Logically constant state is outside the rule, and so is a private cache whose hits and misses no caller can tell apart. The global variable as a name (its scope, naming and reassignment) belongs to variables-scope-and-numerics; this rule holds the shared mutable object.
   - formulation: Hunt and Thomas, The Pragmatic Programmer, 20th anniversary ed. (2019), Topic 10 'Orthogonality' (Coding, 'Avoid global data') and Topic 28 'Decoupling', Tips 47 'Avoid Global Data' and 48 'If It's Important Enough to Be Global, Wrap It in an API'; Fowler, Refactoring, 2nd ed. (2018), ch. 3 'Global Data' and ch. 6 'Encapsulate Variable'; Ousterhout, A Philosophy of Software Design, 2nd ed. (2021), §7.5 'Pass-through variables'; McConnell, Code Complete, 2nd ed.
