# A method that overrides or implements a supertype method carries the language's explicit override marker

## Thesis
A method that overrides or implements a method declared in a supertype carries the language's explicit override marker wherever the language accepts the marker on that method, including a class method that implements an interface method and an interface method that restates a superinterface method. Where the check that requires the marker is opt-in, such as a compiler or type-checker option that is off by default or a linter rule, the project's configuration turns it on, so that the check reports an override that lacks the marker.

## Rationale
The marker declares that the method is intended to override a supertype method, and the compiler or type checker reports an error when the marked method does not override or implement one. Without the marker, renaming or deleting the supertype method leaves the subtype's method behind as an unrelated method, and the checker alerts only to the call sites that use the supertype directly: after a rename, a call through the supertype runs the supertype's method, not the subtype's, and the two methods fork, so that a later change to the renamed method is likely to go unrecognised as one the subtype's method also needs. The refactored code is type-safe and likely runs without throwing, tests are less likely to catch the change, and several production outages in multiple typed codebases have been reported as caused by such refactors. With the marker, the same rename turns the left-behind subtype method into a compile or type-check error. The marker also catches a method that was meant to override and never did: a name that differs from the supertype method's only in capitalisation or by a letter, or a parameter type that does not exactly match the supertype's, such as a type of the same simple name from another package, or an equality method declared over its own class rather than the root object type. Where the requirement is opt-in, the marker guards only the methods that carry it: refactors can be trusted as override-safe only when the marker is used throughout the project, and only the requirement catches the reverse case, a supertype that gains a method with the name of an existing subtype method, which silently makes that subtype method an override that a call through the supertype can invoke. In some languages the compiler never requires the marker and widely used linters can warn when it is missing; elsewhere the compiler or type checker requires it only under an option that is off by default, and even a strict preset may leave that option off, so the option is turned on by name. The marker also shows a reader at once which methods override base-class behaviour, which otherwise only a static analysis tool shows quickly.

## Example
```java
bad:  class Shape { public double area() { ... } }
      class Circle extends Shape {
          public double area() { ... }
      }
good: class Shape { public double area() { ... } }
      class Circle extends Shape {
          @Override public double area() { ... }
      }
```

## Limits
A position where the language rejects the marker carries none, such as a method that implements an interface member in a language whose marker applies only to members inherited from a base class that the class extends. A method that overrides a deprecated supertype method may omit the marker, and a project whose checker is configured to exempt an interface method restating a superinterface method accepts that omission. An override of the constructor or of the instance-creation hook is outside the rule; one type checker exempts both by name. Where the requirement is opt-in, adopting it is the project owners' decision, weighed against the more verbose code the marker brings; a project context stating that the project does not use the marker rejects the finding. Code built for a language version that predates the marker takes it from the backport module that the language's type-checker documentation names, and is outside the rule where no backport exists. A language with no implementation inheritance has no override to mark: a method of an outer type hides an embedded type's method of the same name, and the embedded type's methods, when invoked, run with the inner type as receiver, not the outer one. A trait implementation block that names its trait already rejects a method the trait does not declare, so a renamed or misspelled trait method, one that replaced a default implementation included, fails to compile without any marker. The rule weighs the marker alone: whether a subtype should inherit at all, whether it honours the supertype's behaviour, and how a class is designed for extension are outside it.

## Validator
Grep the added lines for method declarations inside a class and for a class header that names a base class or an interface. For each added or renamed method, open the supertypes its class extends or implements, searching the repository for their declarations, and decide whether a supertype declares a method that the added method overrides or implements, or one it nearly matches: a name that differs only in capitalisation, a parameter type that differs only by a type of the same simple name, or the root object type's equality method declared under a name missing a letter or over the class's own type in place of the root object type. For a supertype method the hunk renames, removes or adds, search the repository for subtypes that declare a method under the old or added name. Skip a constructor or instance-creation hook, a method overriding a deprecated supertype method, a position where the language rejects the marker, an interface method restating a superinterface method where the project's checker configuration exempts it, and a language that has no implementation inheritance or whose implementation block names its trait. Read the project context for a statement that the project does not use the marker. Validator question: **Does a method the change adds override, implement or nearly match a supertype method without the language's override marker where the language accepts it, or does a supertype method the change renames, removes or adds detach or capture a subtype method that lacks the marker?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-37`, severity minor, `file`, `symbol`, `code` = the method's declaration line quoted verbatim from the diff, or for a subtype method detached or captured by a supertype change the supertype's renamed, removed or added declaration line, `fix` = the declaration with the language's override marker added — with the name or parameter type corrected to the supertype method's for a near miss, the left-behind method renamed for a rename, and a captured method renamed where it was not meant to override the added method — plus, where the project's configuration leaves the requirement off, the compiler or type-checker option that turns it on, in the file's language, `rationale` = the supertype method the declaration overrides or was meant to override and the supertype change that would detach or capture it silently).
