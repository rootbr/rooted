# An expected, recoverable failure is returned or raised to the caller, and code outside the entry point and start-up does not panic, exit or abort the process on it

## Thesis
When a routine meets a failure that is expected in normal operation — malformed data handed to a parser, a remote reply saying a rate limit was hit, values from a caller that make no sense where continuing is neither insecure nor harmful — it returns an error or raises one to its caller, so that the caller decides how to handle it. A routine other than the program's entry point and its start-up code, library code and the code that serves a request or a task in particular, does not panic, exit or abort the process, call a logging routine that exits, or force-unwrap a fallible result on such a failure, a transient one least of all. Stopping the process on a failure belongs to the entry point, which turns an unhandled error into an exit status, to the start-up code of a program that owns its process, when it cannot set the program up, and to a state that has become irrecoverable.

## Rationale
Stopping the process on a failure decides, on behalf of every caller, that the failure cannot be recovered from, and a stop cannot be taken back. A returned or raised error keeps the choice with the caller, which can recover in the way its situation calls for, retry a transient failure, report it, or turn it into a stop itself; an error that every caller passes up still reaches the entry point, which ends the process with a non-zero status, so where no caller recovers, returning or raising the error ends the same way an exit would. The stop costs more than the caller's choice. It takes down every other request and task sharing the process — in a shared application server, every other application on it; a stop that ends the process on the spot, without unwinding the stack, also gives the rest of the program no chance to respond, skips the cleanup scheduled to run as routines return and ends the test run that calls the routine, so the routine is hard to test; and a package whose functions can exit is hard to reuse. Where a problem can be masked or worked around, letting the program continue is better than taking it down. Stopping on a failure the program was meant to handle is a measured cause of outages: in production failures of five distributed data-intensive systems, almost all catastrophic failures (92%) came from incorrect handling of non-fatal errors the software had signalled, and 8% of all catastrophic failures came from aborting the entire cluster on a non-fatal exception — in one, an exit meant for a version mismatch sat under a catch of the most general exception type, so a glitch that made a remote registration call fail brought down every data node of a distributed file system. In high-severity production cloud incidents caused by software bugs, the error handlers that contributed over-reacted as often as they ignored the error report, 35% of the cases each. A failure is expected when it will happen occasionally in normal operation rather than reveal a mistake in the code — bad input from outside, a remote refusal, a lookup that misses — and such a failure is the one a caller is placed to handle.

## Example
```typescript
bad:  export function parsePort(text: string): number {
          const port = Number(text);
          if (!Number.isInteger(port)) process.exit(1);
          return port;
      }
good: export function parsePort(text: string): number {
          const port = Number(text);
          if (!Number.isInteger(port)) throw new RangeError(`invalid port: ${text}`);
          return port;
      }
```

## Limits
The entry point may stop the process: the program's main routine, the top level of a script, and the one part of the program that turns a returned error into an exit status. Start-up code may stop when the program or a library truly cannot set itself up and the program owns its process: a module or package initializer that runs as the program starts, and a helper that stops on failure and is applied only at start-up to fixed values, such as a constant pattern or template. Code hosted in a shared container or application server leaves every stop to the container, even at start-up, and the same helper applied to user input is inside the rule. Tests, examples and prototype code are outside the rule: in a test a failed call should fail the test, and in an example or a prototype an unwrap marks where the handling will go once it is decided; a project context that declares a prototype or script tier rejects the finding. An unwrap on a result that other logic guarantees to succeed, such as a parse of a hard-coded valid literal, meets no expected failure, provided its message states why failure cannot occur. The rule does not reach a stop on a broken assumption, contract or invariant — a documented contract whose violation reveals a bug in the caller, a value on which continuing would be insecure or harmful, an invalid state returned by external code the routine cannot fix, an internal state that has become irrecoverable — where stopping is the right response. A module that panics internally and always recovers at its own public boundary, returning the panic as an error, follows the rule while no such panic escapes that boundary. Whether and how the caller retries, times out or falls back, how broad a handler's catch is, and what a handler logs are judged by their own rules.

## Validator
Grep the added lines for a panic, a process exit or abort, a raise of the exit signal, a logging call that exits or panics, an unwrap or expect on a fallible result, and a call to a helper that stops on failure. For each hit, open the file, name the enclosing routine and note the file's path. Set aside a hit in the program's entry point or in the one place that maps a returned error to the exit status; in the start-up code of a program that owns its process — a module or package initializer that runs as the program starts, or a stop-on-failure helper applied only to fixed values at start-up; in a test file, an example, or code the project context marks as a prototype; and an unwrap or expect on a result that other logic in the code guarantees to succeed, such as a parse of a hard-coded valid literal, whose message states that guarantee; a message alone, on data from a user, a file, the network or another service, sets nothing aside. For the rest, name the failure that leads to the stop and classify it: expected in normal operation (data from a user, a file, the network or another service, or a parse of such data; a lookup that can miss; a remote status such as a rate limit or a timeout; a caller's argument that can be wrong and is safe to refuse) or a broken invariant, a documented contract whose violation is a caller's bug, a value on which continuing would be insecure or harmful, or an internal state that has become irrecoverable. For a panic, check in the file whether the same module recovers it at its public boundary and returns it as an error. Validator question: **Does an added line outside the program's entry point, its tests and the start-up code of a program that owns its process stop the process — a panic, an exit, an abort, a fatal log, an unwrap or a stop-on-failure helper — on a failure that is expected in normal operation, where the routine could return or raise an error to its caller instead?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-12`, severity major, `file`, `symbol`, `code` = the added panic, exit, abort, fatal-log, unwrap or stop-on-failure helper line quoted verbatim from the diff, `fix` = the same routine returning an error value or raising an error that names the failure, its signature declaring the failure where the language records it, and any stop the program still needs left to the entry point, in the file's language, `rationale` = the expected failure that triggers the stop and what the stop takes from the caller: the choice to recover, retry or report, and every other request or task sharing the process).
