# A type presented as immutable holds only immutable components or its own copies of mutable ones

## Thesis
A type presents itself as immutable when it is a record, a frozen data class, a tuple or named tuple whose elements cannot be reassigned, a type declared read-only or frozen as a whole, or a type annotated, documented or named as immutable. Such a type holds in each field either a value of an immutable type, or a mutable object — a collection, an array, a map, a date with setters, a buffer — that no code outside the type can reach: one the type created, copied for itself when the instance was constructed (copying every mutable element it holds as well), or received by a move or a by-value copy that leaves the sender no reference to it; it hands out such an object only as a copy or through an unmodifiable or read-only view, and never a reference to a mutable element of it. A collection or other container counts as immutable only when it cannot be modified and its elements are immutable as well. The type's state then cannot be observed to change after construction.

## Rationale
Read-only and final fields, records, frozen data classes, tuples and unmodifiable collections are shallow: each stops a field or an element from being replaced, not a change inside the object it refers to. A read-only property means only that the property itself cannot be re-written; a record is a shallowly immutable carrier of its components; a frozen data class raises an exception on assignment to its fields; an unmodifiable list rejects every add, remove and replace, yet its contents may appear to change when its elements are mutable; and the value of a container whose own references cannot be replaced, such as a tuple, changes when a mutable object it refers to changes. Declaring a non-empty array public, static and final indicates that the developer expects a constant, which it is not, since clients can modify the array's contents. A type that relies on a shallow declaration alone can change state by two paths. A type that stores a mutable object it received, rather than a copy, takes an externally mutable object into its internal representation, so the caller's own reference still changes it; a read-only property can change through an alias in the same way, and a slice or a map shares its underlying data with every copy of the reference. A type whose accessor returns the stored mutable object exposes its internal representation, and a caller that changes the returned object changes the type's state. An unmodifiable view over a collection that another reference can still change is not necessarily immutable either, because changes to the backing collection show through the view. A copy that the type takes when the instance is constructed, down to every mutable element, and that is reachable afterwards only through an unmodifiable or read-only view that yields no mutable element, leaves no outside reference through which the state can change: such a view can be considered effectively immutable. An unmodifiable collection whose elements are mutable is itself mutable, so a copy that keeps the sender's mutable elements, or a view that yields them, still lets the contents change. Where passing an object moves it, leaving one owner at a time, or copies it by value, the sender keeps no usable reference to what the type holds. Performing defensive copies on mutable components is one of the primary reasons a record declares its canonical constructor or accessors explicitly. Requiring every reference field to be of an immutable type ensures deep immutability, meaning all contained state is also immutable, and an object is immutable when its state cannot be observed to change after construction. Professional developers interviewed about immutability stated that incorrect state mutations are a major source of bugs, for example an object thought to be immutable changed by some other object because references were reused instead of immutable copies. Refactoring a spreadsheet's code to use a tool for transitive class immutability took approximately twenty hours and found two previously unknown bugs, one in a copy method and another in code that improperly used a cache.

## Example
```typescript
bad:  type Route = Readonly<{ name: string; stops: string[] }>;
      function makeRoute(name: string, stops: string[]): Route {
        return { name, stops };
      }
good: type Route = Readonly<{ name: string; stops: readonly string[] }>;
      function makeRoute(name: string, stops: readonly string[]): Route {
        return { name, stops: [...stops] };
      }
```

## Limits
A type may keep internal mutable state, such as state initialized lazily to improve performance, as long as callers can never observe changes to that state; such a field is outside the rule. A generic container may be shallowly immutable by design and hold elements of its type parameter that are mutable, as an immutable list may; an instance of it counts as immutable only when every type argument is immutable, so the rule judges the type that holds the container with a mutable type argument, not the container itself. Where a reference not declared mutable forbids any change through it, the rule reaches a component with interior mutability, which allows change even through immutable references and leaves the outer value only outwardly immutable, such as one the type shares with another owner who can still change it. Where read-only access is checked only at type-checking time, or immutability can only be emulated, the rule asks for that check or that emulation over the type's own copy, not for a guard against code that bypasses it. A suppression on the type or the field that marks its mutable state as unobservable, or a project context that names the type as shallow by design, rejects the finding. Whether the type is safe under concurrent access is outside the rule.

## Validator
Grep the hunk's added lines for a declaration that presents a type as immutable — a record header, a frozen data-class decorator, a named tuple, a read-only or frozen wrapper, a const assertion or freeze call, or an annotation, comment, doc comment or type name that says immutable — and for a read-only field of a collection, array, map or date type, or a shared component with interior mutability. Open the file, find the type each matched line belongs to, and skip it unless the type presents itself as immutable. List the type's fields with their declared types and mark each field whose type is mutable: a collection, an array, a map or a buffer, a date or any other type with a setter or another mutating method, a component with interior mutability, or a container whose element type is mutable. For each marked field, trace every place the type receives the object — the constructor, the canonical or compact constructor, the factory function or the literal that builds the instance — and every place it hands the object out — an accessor, an implicit record accessor, a public or exported field, a method that returns it. Skip the field when the type creates the object, copies it on receipt together with every mutable element it holds, or receives it by a move or a by-value copy that leaves the sender no reference to it, and hands it out only as a copy or through an unmodifiable or read-only view that yields no mutable element, when it is internal state whose changes no caller can observe, when it holds a generic container's own type-parameter elements, or when a suppression or the project context names the type as shallow by design. Validator question: **Does a type that presents itself as immutable store a mutable object, or a mutable element of one, that the sender can still reach, or hand out a stored mutable object or element through which a caller can change the type's state?** Yes → flag.
