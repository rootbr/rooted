# Research note — Resource management and ownership

Topic `resource-management-and-ownership` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: PP 'How to Balance Resources' (The Pragmatic Programmer, 20th anniversary ed., ch. 4 'Pragmatic Paranoia', topic 26: finish what you start, act locally, deallocate in the opposite order of allocation).

Resource management and ownership covers the lifetime of a non-memory resource (a file, socket, connection, stream, cancellation function or temporary file) from acquisition to release. The canon is The Pragmatic Programmer topic 26, alongside The Practice of Programming §4.6, Effective Java Items 8-9, Effective C++ Items 8, 13 and 14, The Go Programming Language §5.8 and Code Complete §8.4. It says four things. The routine or object that acquires a resource releases it. A resource stays open no longer than its use. Several resources are released in reverse order. Release survives an exception through a scoped construct, or through a finally clause entered after the acquisition. Official documentation in all five languages states these rules in openable form: AutoCloseable and try-with-resources, PEP 343 and contextlib, Effective Go and the Go spec on defer, the TC39 proposal and TypeScript 5.2 using, and the Rust book and Reference on Drop. Tool rules check them in Java, Python and Go: SpotBugs, PMD, Error Prone, Infer, the Checker Framework, CodeQL, Pylint, Ruff, go vet lostcancel and httpresponse, staticcheck and revive. TypeScript has no such rule yet; the typescript-eslint proposal is still open. The industry disagrees in four places. (1) PP's object wrapper counts garbage collection as a release. Every official source rejects that for non-memory resources. Go's runtime and Java's Cleaner accept a cleanup that closes a forgotten resource as a backstop, while the TC39 WeakRefs README wants such a cleanup only to log. (2) Sonar, Ruff and Pylint want the scoped construct instead of any try/finally, while PEP 8 and Error Prone accept a try/finally. The cases separate on whether one hand-written cleanup block releases several resources. (3) CodeQL and Joe Shaw require checking the close error of a written file, while gosec and golangci-lint accept unchecked close errors. The cases separate on whether the resource was written to (CERT ERR00-J-EX0). (4) Code Complete's 'avoid throwing from constructors' against C++ Core Guidelines C.42, and the Linux kernel's goto unwinding against its own cleanup.h, both resolve into one rule: a failed construction releases what it already holds. The research could not be opened here. Weimer and Necula (OOPSLA 2004), Kellogg et al. (ESEC/FSE 2021) and Ghanavati et al. (EMSE 2020) stay unfetched. The Ghanavati figures conflict with README entry 74, so no card states them. The only fetched study, Lima et al. 2021, finds that exception-handling code is less covered by tests. The hands-on runs in all five languages are not yet admissible evidence; they count once committed under evals/fixture/.

## Formulation layer

The Pragmatic Programmer's topic 26 sets out the core of this topic. Where possible, the function or object that allocates a resource deallocates it (Tip 40). The scope of open resources stays short (Tip 41). Resources are released in the opposite order of allocation. Release survives exceptions through variable scope or a finally clause, with the acquisition placed before the try. The book could not be opened from here, so its wording comes from third-party study notes and tip lists hosted on GitHub, marked relayed, and its errata were unreachable. Several other books say the same things in their own words: The Practice of Programming §4.6, Code Complete §8.4, Effective C++ Items 8/13/14, Effective Java Items 8–9, Effective Python, The Go Programming Language §5.8 and Clean Code ch. 7. Openable official documents state the same rules: the Google Python, Java and Go guides, the Uber Go guide, Effective Go and the Go context and runtime docs, PEP 8, PEP 343, the CPython docs including contextlib, the JDK javadoc, the Rust book, std and API guidelines, the TC39 proposal, the TypeScript 5.2 notes, the C++ Core Guidelines, and the Linux kernel's coding style and cleanup.h. The canon disagrees in four places. (1) PP's object-wrapper passage also counts reclamation by the garbage collector, while Effective Java, the Google Python guide, the Python reference and the Go runtime docs say finalizers and GC must not be relied on. (2) Code Complete says to avoid throwing from constructors, while C++ Core Guidelines C.42 says to throw. (3) The Linux coding style teaches goto unwind labels, while the newer cleanup.h calls that pattern notorious for leaks. (4) Ousterhout and Martin disagree on whether acquiring a lock and doing the work belong in one method. None of the 97 Things essays, the Software Engineering at Google chapters, the Google TypeScript guide or Google's eng-practices covers resource release.

## Reception layer

The industry checks scoped release mechanically in Java (PMD CloseResource, SpotBugs OS/ODR/OBL, Error Prone MustBeClosed and StreamResourceLeak, CodeQL, Infer, the Checker Framework Resource Leak Checker), in Python (Pylint R1732, Ruff SIM115, CodeQL, Semgrep) and in Go (go vet lostcancel and httpresponse, bodyclose, sqlclosecheck, revive and staticcheck defer checks). TypeScript has no such rule yet: the typescript-eslint require-using proposal (#8255) has been open since January 2024. Every Java and Python checker that was opened treats returning the resource as a legitimate transfer of ownership, and the Checker Framework makes the transfer explicit with @Owning. Infer's documentation openly disputes the claim that try-with-resources "solves" the resource problem, because escaping resources cannot use a stack discipline. The sharpest live dispute is over close errors on writable files. Joe Shaw (relayed through a GitHub-hosted copy) and CodeQL's go/unhandled-writable-file-close say a bare defer f.Close() can lose data. gosec retired G307 as "more inconvenience than fixing a security issue", golangci-lint's std-error-handling preset excludes unchecked Close errors as "in most cases it's ok", and Go 101 defends defer as less bug-prone. Rust's File drop also ignores close errors, and the API Guidelines prescribe an explicit fallible close with Drop as a fallback. On finalizers, Java deprecates finalize and Google's Java and Python guides, Checkstyle, Error Prone, Node.js and CPython all warn against relying on GC cleanup. Go's runtime docs and Java's Cleaner, however, endorse GC cleanup as a backstop for non-memory resources, and Go 1.23 moved tickers from must-release to GC-reclaimable. Not opened: WebSearch was exhausted, so no Hacker News or Lobsters thread was read and no named critique of the Pragmatic Programmer's 'How to Balance Resources' was found. The SonarSource S2095 rule page was not found in sonar-java, and Joe Shaw's original post is known only through a third-party quotation.

## Evidence layer

I opened the source text of 44 official documents, tool rules and standards through raw.githubusercontent.com. They cover Java, Python, TypeScript/JavaScript, Go and Rust, plus SEI CERT FIO04-J, FIO03-J and MET12-J and the C++ Core Guidelines. Every candidate tool rule and official document was confirmed except SonarSource S2095, which returned 404 at both sonar-java resource paths; S2093 is used in its place. All five languages document a scoped-release construct (try-with-resources, with, defer, using, Drop). Each releases on every exit path, including the exceptional one and a failed second acquisition, and in reverse order of acquisition. Local hands-on runs in all five languages showed this, plus descriptor counts showing that garbage collection does not release unclosed files. These runs are not openable until committed under evals/fixture/, and JLS §14.20.3 is still unopenable, so Java's reverse close order rests on that run alone. None of the three candidate papers (Weimer and Necula 2004, Kellogg et al. 2021, Ghanavati et al. 2020) could be opened: there is no GitHub-hosted copy and the WebSearch budget is spent. They are listed as unfetched. I also flag a conflict: the candidate summary says most leaks are on error-free paths, while README.md entry 74 says leaks on error paths dominate. The sources disagree on one point. Go's runtime documentation and the JDK Cleaner accept a finalizer or cleaner that closes a discarded resource as a backstop, while the TC39 WeakRefs proposal says closing files through a finalizer is not a good idea and CERT MET12-J says not to use finalizers at all. All of them agree that release must not depend on finalization.

## Spine — candidate rules in source order

1. **A routine that acquires a resource releases it before it returns, unless it hands the resource on to its caller, to an object that owns it or to a routine that takes over its release** — A routine that opens a file, socket, connection or stream, creates a temporary file, or obtains a cancellation function releases that resource itself before it returns. The exception is a hand-off: the routine returns the resource, stores it in an object that owns and releases it, or passes it to a routine documented to take over its release. A resource that is released nowhere leaks: a stream opened and read inline, a discarded cancellation function, a temporary file never removed, a value whose destructor is deliberately skipped. So does one released only if some other routine happens to run later. Two cases fall outside the rule: an object that implements the closing interface but holds no operating-system resource, such as a collection-backed stream, and a shared resource the program opens once and keeps, such as a connection pool; what a routine borrows from such a pool it returns.

- A resource is freed in the same library, package or interface layer that allocated it — folded: Folded into acquirer-releases, which states the same concept at routine level. The half about aggregates is carried by owning-type-provides-release.
- A cancellation function returned with a derived context is called on every path once the work it covers completes — folded: Folded into two cards: acquirer-releases covers a discarded cancellation function, and release-on-every-path covers one that is called on some paths only. The cancellation function is one of the resource kinds both cards name, and a Go-only rule would not hold across the five languages.
- A routine that creates a temporary file or directory removes it, or states in its interface that its caller must — folded: Folded into two cards. Under acquirer-releases, removing a temporary file is its release. Under transfer-stated-in-interface, mkstemp and os.CreateTemp state the caller's duty.
- A release that runs at function exit is not registered inside a loop that acquires a resource on each iteration — folded: Folded into release-when-use-ends. It is the Go form of releasing a per-iteration resource within its iteration. A Go-only rule would not hold across the five languages, whose other scoped constructs are block-scoped.
- A closeable resource is released through the language's scoped-release construct rather than a hand-written try/finally — folded: Folded into several-resources-released-separately, which carries the separating condition. A single resource in a finally entered right after the acquisition satisfies release-on-every-path.
- An automatic release never fails, and a release whose failure the caller must see is offered as an explicit operation — folded: Folded into two cards. release-operation-frees-everything carries the implementer's side: tear down, ignore or log, never fail during unwinding. written-resource-close-checked carries the caller's side: the explicit fallible close is called and checked.
