# Research note — Test-first and test-driven development

Topic `test-first-and-test-driven-development` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: SW4.16 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.16; its V3 counterpart, ch. 3 §4.16 'Test-First Programming', is openable in the ligurio/swebok-v3 transcription master 3_software_construction.md); PP 'Test to Code' (The Pragmatic Programmer, 20th anniversary ed., ch. 7 'While You Are Coding', topic 41); johnousterhout/aposd-vs-clean-code main README.md §'Test-Driven Development' and §'TDD Summary' (the public discussion of the two positions); Beck, Test-Driven Development: By Example, as the formulation the discipline side follows (trade book, never evidence). Marked contested in the design note.

The canon disagrees about order but agrees on a floor. On the discipline side, SWEBOK V3 ch. 3 §4.16 (the openable counterpart of SW4.16), Beck, Martin's three laws, the Pragmatic Programmer ('Test First ... is probably your best choice'), McConnell and the Rust book write a failing test before the code, in cycles of seconds to minutes. On the other side, Ousterhout's 'bundling', the PP's 'Test During', Sommerville's 'think-first' and Heinemeier Hansson's backfilling write a small unit of code first and test it straight away. In the aposd-vs-clean-code discussion both men agree that unit tests are essential and that small units tested immediately afterwards can match TDD. Martin also concedes, there and in his 2016 reply to the ESEM replication, that the size of the cycle is the effective part, not the order. They still disagree about TDD's average and worst-case design outcomes, and no data exist on those. The evidence follows the concession. Fucci et al. (TSE 2017, arXiv:1611.05994) find that sequencing has no important influence, while granularity and uniformity are associated with quality and productivity. The ESEM 2016 replication, Tosun et al. (TSE 2021) and the Santos et al. family of experiments (EMSE 2021, relayed) find no advantage for TDD, or a slight advantage for iterative test-last. Nagappan et al.'s 40–90% lower defect density compares TDD with ad-hoc post-coding testing, so it cannot separate order from testing discipline. The 2022 interns experiment favours TDD. A diff shows no trace of the order in which code and tests were written, and no static-analysis rule checks it. The ordering, cadence, just-enough-code, refactor-step, design-planning and test-list rules are therefore held or pending. The topic cards only the order-neutral floor that both camps and both kinds of official documentation state. First, tests for new or changed behaviour ship in the same change as the code (google/eng-practices, CPython devguide). Second, each such test fails without the change and passes with it (Rust book ch. 12.4 and 11.1, Go 'Add a test', eng-practices, rustc-dev-guide); this second card also covers the regression test for a bug fix. Three ownership points must be settled at merge. Google's 'Small CLs' §'Keep related test code in the same CL' is guidance that small-steps-and-minimal-diffs may also cite. The bug-fix test-first rule appears in the PP under Topic 20 'Debugging' Tip 31, so the debugging topic must not card it again. Assertion strength in general stays with unit-testing-and-test-quality.

## Formulation layer

I opened SWEBOK V3 word for word: ch. 3 §4.16 and §3.4, and Testing KA §5.1.5. SWEBOK V4 §4.16 itself would not open, so only a third-party summary of it and its reference list are recorded. I also read the full aposd-vs-clean-code discussion, Robert Martin's own blog repository (eight posts on TDD), the Rust book, google/eng-practices, rustc-dev-guide, Software Engineering at Google, 97 Things, and GitHub copies of APOSD ch. 19, Clean Code ch. 9, Sommerville §8.2, Beck's Canon TDD, Fowler's bliki entry and Sommerville's 2016 post. The Pragmatic Programmer, Beck's book, McConnell and DHH's posts were reachable only through excerpts, so they are marked relayed; WebSearch was not used. The canon splits two ways. The discipline side writes the test first in cycles of seconds to minutes: Beck, Martin's three laws and cycles, Fowler, McConnell, the PP's "Test First is probably your best choice", the Rust book and SWEBOK. The other side writes a small unit of code first and tests it right after, before the code counts as working: Ousterhout's 'bundling', the PP's 'Test During' fallback, Sommerville's 'think-first', and DHH's 'backfilling'. The two sides converge on cycle size rather than order: Martin concedes in the discussion, and again in his 2016 reply to the Fucci ESEM replication, that 'the really effective part of TDD is the size of the cycle, not so much whether you write the test first'. That matches the Fucci TSE 2017 abstract, which found granularity and uniformity associated with quality and productivity and sequencing with no important influence; this is the candidate separating condition for the contested rule. Several points are disputed by no one: write a failing test that reproduces a bug before fixing it (APOSD 19.4, PP Tip 31, rustc-dev-guide, SWE at Google ch. 12), and add tests in the same change as the production code (eng-practices). The book's own TDD description in APOSD 19.4, writing all the tests for a class first, is retracted by Ousterhout in the discussion and named as a mistake in Beck's Canon TDD.

## Reception layer

Reception splits the way the design note expects. On the discipline side are Martin (in the aposd-vs-clean-code README and nine of his blog posts, opened from unclebob/unclebob.github.io), Percival's Testing Goat, Chris James's Learn Go with Tests, and the 2025–2026 coding-agent artifacts (obra/superpowers, Kent Beck's BPlusTree3 prompt, tdd-guard/Probity). They hold that you write the test first, and their distinctive argument is that a test you have watched fail is a test you can trust. The critics are Ousterhout, DHH and Sommerville (the last two as quoted by Martin) and Greg Wilson's reading of six studies at neverworkintheory. They hold that the order adds nothing over writing small units and testing them right afterwards, and that it can crowd out design. The two sides agree on more than they dispute. Martin concedes that 'the really effective part of TDD is the size of the cycle, not so much whether you write the test first', and that small units tested immediately after are indistinguishable from TDD. Fucci's own talk says the benefit comes from fine-grained cycles, not from test-first. Ousterhout says bundling's benefit 'doesn't come from writing tests later'. Official documentation does not prescribe an order: the Rust book teaches both orders, Go's tutorial writes the test after the code, and Google's review guide asks only for tests in the same change that 'fail when the code is broken'. The Go and Rust tutorials deliberately break the code to watch a test written afterwards fail, which makes 'seen to fail', not 'written first', the condition that separates the positions. Only the SWEBOK V3 text claims an advantage for test-first. No static-analysis rule checks ordering: PMD's JUnit rules and clippy's lints concern test structure and stubs, and only agent hooks (Probity) check the order, from session history. I could not open DHH's own posts, Beck's 'Canon TDD', Fowler's 'Is TDD Dead?', the Pragmatic Programmer or APOSD book text, any Hacker News or Lobsters thread, or any 2024–2026 practitioner survey: the hosts are denied and the WebSearch budget is exhausted, so those items are marked unfetched or none found.

## Evidence layer

I opened the evidence through raw.githubusercontent.com: SWEBOK V3 ch. 3 §4.16 and ch. 4 §5.1.5 (ligurio/swebok-v3); the full text of Nagappan et al. 2008 (tpn/pdfs; the hinted filename 404s, the real one ends "- 2008 (nagappan_tdd).pdf"); the TSE abstracts for Fucci 2017 (the dissection paper), Wilkerson 2012, Rafique & Mišić 2013, Latorre 2014, Beller 2019, Karac 2021, Tosun 2021 and the 2022 interns study (maxxbw54/Paper-Repository); the abstracts for Fucci ESEM 2016 and Borle 2018 (neverworkintheory tex/nwit.bib and _posts); and the official docs on both sides (the Rust book ch. 12.4 TDD steps, the Go 'Add a test' tutorial, google/eng-practices, the CPython devguide, the rustc-dev-guide). The research is split. Nagappan's industrial case studies (40–90% lower defect density) and the 2022 interns experiment (1.8 fewer bugs) favour TDD. Wilkerson, Fucci ESEM 2016 (p = .82 for quality), Borle and Tosun 2021 (iterative test-last scored higher) find no benefit or the reverse. Rafique & Mišić find a small positive quality effect and little to no productivity effect. Fucci 2017 gives the separating condition: test-first order had no important influence, while fine-grained, uniform cycles went with better quality and productivity. Karac 2021 and Tosun 2021 add that breaking the task into small subtasks drives quality. Nagappan's comparison groups did ad-hoc post-coding testing, so that study does not separate test order from testing discipline. Santos 2021 (family of experiments), Tosun EMSE 2017, Ghafari ESEM 2020, Baldassarre JSS 2021, Erdogmus 2005 and the SWEBOK V4 text could not be opened: WebSearch is exhausted, no GitHub copy was found, and the orchestrator's search gave only URLs for them, with no snippet. They are marked unfetched and must not be a card's only anchor. No research and no static-analysis rule backs 'watch the new test fail' or 'write only enough code to pass'; only official docs back them. The 'unit tests ship in the same change' floor is uncontested: docs on both sides state it, and the Martin–Ousterhout summary agrees.

## Spine — candidate rules in source order

1. **A failing unit test is written before the production code that makes it pass** — Test-first programming writes a unit test that fails because the code it exercises does not yet exist or does not yet behave as required, and only then writes the production code that makes the test pass. The standard claims the practice can usually detect defects earlier, and expose requirements and design problems sooner, than traditional programming styles. Against iterative test-last development in fine-grained cycles, order showed no important influence on quality or productivity in the measured data. Against unit testing done as an informal post-coding activity, teams practising test-first had 40–90% lower pre-release defect density.

2. **Test code and production code are written in alternating steps of small and steady size whichever of the two comes first in each step** — Developer testing alternates between a small piece of production code and the tests for it. The steps are kept fine-grained and of uniform size, so the time between inserting a fault and detecting it stays short, and the order within a step is free. In data from professionals, granularity and uniformity were associated with quality and productivity while order had no important influence. No source states a step length, and the canon disputes how small a step should be: seconds to about a minute on the discipline side, a few tens to a few hundred lines in bundling. For novices practising TDD, receiving the task as finer-grained subtasks raised functional quality with a medium to large effect.
