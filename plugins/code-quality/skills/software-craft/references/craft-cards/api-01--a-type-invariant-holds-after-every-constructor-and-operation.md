# A type's invariant is established by every constructor and preserved by every public operation, so no caller can create or leave an instance that breaks it

## Thesis
A type whose correctness rests on a condition over its state — a value within a range, an index within the bounds of the type's own buffer, a count that matches the elements the type holds, a relation between two fields — keeps that condition true in every instance that code outside the type can reach. Every path that creates an instance, whether a constructor, a factory or a deserialization, establishes or checks the condition before the instance is returned. Every public operation leaves the condition true when it returns and when it exits by a thrown or returned error; the condition may lapse only inside the type's own code, while one of its public operations is in progress or in a non-public helper that operation calls. No code outside the type can write the state the condition covers without that check: the fields the condition covers are private or immutable, a public setter or mutator checks the condition before it writes, no accessor returns a mutable internal component, and a mutable object a caller passes in is copied before it is checked and stored. Code outside the type is code beyond the scope the language's access control gives the type's private members: outside the class, or outside the module or package where the language scopes privacy there.

## Rationale
An invariant is a consistency constraint in the type's contract, and it applies to all public operations at once: it is added to the precondition and the postcondition of every exported routine. Each operation can rely on the condition on entry because every operation owes it on exit, and a function that takes an instance can use it without any additional check in its body. A public field, or a field that cannot be reassigned but refers to a mutable object, can be altered by other code independently of the operations that maintain the condition, so the type cannot enforce it; values subject to change from anywhere in the code may not meet the assumptions the type's code was written on, which can lead to unexpected changes and hard-to-trace bugs. A returned reference to an internal mutable component gives callers the opportunity to corrupt the object's state, which violates the invariant, and a mutable input whose value passed the check can change before it is used. Deserialization is equivalent to construction, yet a deserializer can create the instance without running the constructor that checks the condition, so a check that only that constructor runs is bypassed there. An exit by error leaves the same damage when the operation had already modified the state: in a documented case, a method that pads an object's three dimensions, fails a check and returns an error code before its revert runs makes later calls of the same method return incorrect results. Checking before modifying, working on a copy and committing only after success, or rolling back on failure keeps the object consistent.

## Example
```go
bad:  type Span struct{ Lo, Hi int } // invariant: Lo <= Hi
      func (s *Span) SetHi(hi int) { s.Hi = hi }
good: type Span struct{ lo, hi int } // invariant: lo <= hi
      func NewSpan(lo, hi int) (*Span, error) { s := &Span{lo, lo}; return s, s.SetHi(hi) }
      func (s *Span) SetHi(hi int) error {
          if hi < s.lo { return fmt.Errorf("span: hi %d below lo %d", hi, s.lo) }
          s.hi = hi
          return nil
      }
```

## Limits
A type with no associated behaviour or invariant, a compound and passive record whose fields may take any combination of values, may expose its fields; so may a type visible only inside its own package or nested privately in another type, and a constant that refers to an immutable value. A field whose own type admits only valid values, such as an unsigned integer for a quantity that is never negative or a wrapper whose constructor checked the value, needs no further check. Where the language lets any caller create the zero value of a type without running a constructor, a type designed so that its zero value is usable without further initialization keeps the condition there too; a type whose zero value is not good enough relies on an initializing constructor, and its zero value alone does not break the rule. A creation path, mutator or accessor that skips the check by design passes when it sits beside a checked one, is marked as unchecked or raw by its name, its module or a marker for operations whose correctness the caller must guarantee, and documents the condition its caller must then ensure; it serves a caller that cannot afford the check and is otherwise confident the values are valid. Invariants of state that several threads access concurrently are outside this rule; a field there can also be corrupted by concurrent access from multiple threads. How a precondition on an argument is checked and with which error, whether an invariant check may be an assertion the build can strip, and how the contract is documented are judged by their own rules.

## Validator
Grep the added lines for a constructor, an initializer or a factory; a setter, a property setter or another mutator; an accessor; a write to the instance's own state; a throw, raise or error return; and a field declared public or exported. Keep a write or an error exit only when it sits inside a constructor or a public operation of a type. Open the file and name the type's invariant: a condition its constructor or factory checks, its documentation or an assertion states, or its operations rely on without checking, such as a bound on a value, an index into the type's own storage, a count of the elements it holds or a relation between two fields; skip a type with no such condition. Count a field as private when the language's access control or its documented naming convention for non-public members marks it so, and count code within the scope that privacy covers — the class, or the module or package where the language scopes privacy there — as the type's own code. List every way code outside the type can obtain an instance or write the governed state: each constructor and factory, a deserialization path, a public or exported field, a setter or mutator, an accessor that returns a mutable internal component, and a constructor or setter that stores a mutable object the caller still holds. For each creation path, check that it establishes or checks the condition before the instance is returned. For each public operation that changes the governed state, trace every exit, including each throw, raise and error return, and check that the condition holds there because the operation checks before it modifies, works on a copy, or restores the state on failure. For each field, setter and accessor, check whether code outside the type can change the governed state without passing the check. Skip a passive record, a type visible only inside its package or nested privately, a constant holding an immutable value, a field whose own type admits only valid values, the zero value of a type that relies on an initializing constructor, and a creation path, mutator or accessor marked unchecked or raw by its name, module or declaration, beside a checked one, whose documentation states the condition the caller must ensure. Validator question: **Can code outside the type create an instance that breaks its invariant, or leave one broken, through a creation path that skips the check, a public operation that returns or fails with the condition false, or a field, setter, accessor or stored caller-owned object that changes the governed state without the check?** Yes → flag.
