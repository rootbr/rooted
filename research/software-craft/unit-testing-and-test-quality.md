# Research note — Unit testing and test quality

Topic `unit-testing-and-test-quality` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: CC22 (Code Complete 2nd ed. ch. 22 'Developer Testing'); SEG12 (Software Engineering at Google ch. 12 'Unit Testing': test via public APIs, test state not interactions, test behaviors not methods, don't put logic in tests, write clear failure messages, DAMP not DRY); the 97 Things essays 'Test Precisely and Concretely' (thing_81) and 'Write Tests for People' (thing_95).

The canon agrees on the shape of a good unit test: it checks one behaviour, asserts the required outcome precisely enough to fail when the code is broken, produces a failure report that can be diagnosed without reading the test, does not depend on other tests or on shared state, and treats coverage as a pointer rather than a target. Here the canon is Code Complete ch. 22, Software Engineering at Google chs. 11 and 12, and the 97 Things essays 80, 81 and 95. The industry checks the "a test must be able to fail" family mechanically in every target language. PMD, SonarSource (Java, JS/TS, Python), Error Prone, eslint-plugin-jest, Ruff, clippy, testifylint and go vet flag these cases: a test with no assertion, an assertion that compares a value with itself or never reaches its matcher, an assertion a branch, catch or un-awaited promise can skip or swallow, an expected-failure check that accepts any failure, and a test the runner never collects. This family is uncontested. The disagreements are about thresholds and absolutes. Assertion caps differ between tools (PMD 1, jest 5, Sonar 25), set against "one concept per test". Mandatory assertion messages conflict with frameworks that already print the compared values (pytest, assert_eq!, Go got/want). Any loop in a test (tsDetect) conflicts with the table-driven idiom (Google Go style, Go blog, CPython subTest). DAMP conflicts with parameterization (Sonar S5976, Go wiki). Testing private code is allowed by the Rust book and the Google Go style and rejected by the testpackage linter and SEG12. Coverage as a target is rejected by Inozemtseva & Holmes and SWEBOK V3 and treated as a gauge or gate by Gopinath et al., Coverage.py and Jest. The test-smell vocabulary itself is defended by Spadini 2018 and Bavota 2015 (relayed) and challenged by Panichella 2022 and Pecorelli 2020. For that reason every card rests on a failure mechanism, not on a smell name, and adopts the documented condition that separates the contested cases: count behaviours, not assertions; add a message only where the framework's output shows only true or false; allow a loop only over a table of cases that share the same straight-line checks; pin raised failures but not returned errors. No openable source supports these: test names that state the behaviour, values made visible in the test body, and focused validation helpers. These are contested with no sourced separating condition: public-interface-only testing and coverage targets. Notes for the orchestrator: (1) The boundary-value card comes from the CC22 locator, but test-input selection is not named in the topic notes, so it may belong elsewhere. (2) The test-can-fail card leaves an assertion whose single condition is a literal to the shipped assertion-literal card; it covers self-comparison, two fixed values and incomplete assertion calls. (3) The SWEBOK citations are V3 and must be mapped to V4.0 sections. (4) The evidence layer reproduced the always-runs, independence and expected-failure failure modes locally in Python, Go and Rust. Those runs become admissible hands-on evidence only once committed under the skill's evals/fixture/.

## Formulation layer

Fetched and quoted these sources: Software Engineering at Google ch. 12 'Unit Testing' (all ten TL;DR positions plus shared values, setup and helpers) and ch. 11 (hermetic tests, no control flow, the note on code coverage); the 97 Things essays 81, 95 and 80; the Ousterhout–Martin discussion; the google/eng-practices 'Tests' section; and the official guidance that spans the five languages (Google Go style decisions and best practices, the Go subtests blog, Rust book ch. 11, CPython unittest, the JUnit execution-order page, Jest async and setup docs, pytest assert, Google Java and Python naming). I also fetched SWEBOK V3 ch. 4 on coverage and mutation score, and the tsDetect test-smell catalog. Code Complete ch. 22, Clean Code ch. 9, xUnit Test Patterns, TDD by Example, GOOS, Fowler's TestCoverage and Khorikov 2020 could not be opened, so they appear only as paraphrases marked unfetched. Every item here is a formulation. None of them is evidence. The canon agrees on these points: one behaviour per test, given/when/then structure, a name that states the behaviour, precise outcome assertions, failure messages that show expected, actual and inputs, independence from order and shared state, and coverage as a pointer rather than a target. It disagrees in five places. (1) Loops in tests: SEG chs. 11–12 discourage them, while the Go style guide and CPython subTest endorse loops over a table of cases (both still keep conditionals out of the loop). (2) One assertion per test: tsDetect's Assertion Roulette and Clean Code's guideline against SEG12's examples and Go's 'keep going'. (3) Testing private functions: SEG12 says no, while the Rust book records a debate and allows it. (4) Assertion helpers: SEG12's focused validation helpers against Go's 'assertion helpers are not idiomatic'. (5) Named constants against concrete literals: tsDetect's Magic Number Test against 97 Things essay 81 and SEG12. Ousterhout and Martin also disagree on whether tests count as documentation, and on TDD, which belongs to test-first.

## Reception layer

WebSearch was out of budget, so this reception layer was built from GitHub-hosted sources. The industry checks the "test must be able to fail" family mechanically in every target language: PMD, SonarSource (Java, JS/TS and Python), eslint-plugin-jest, Error Prone, Ruff, testifylint and pylint flag tests with no assertion, assertions that never reach a matcher, assertions that cannot fail, and assertion failures that are swallowed (catch AssertionError, assert in except, conditional expect, setup inside assertThrows/pytest.raises). This family is uncontested. The contested rules are these: (1) how many assertions a test may hold, where tool defaults disagree (PMD 1, jest max-expects 5 and off by default, Sonar S5961 25) and Clean Code relaxes "one assert" to "one concept"; (2) mandatory assertion messages (PMD, Sonar S2698, the tsDetect Assertion Roulette definition), against pytest introspection and Go's got/want convention; (3) assertion libraries, which the Google Go style guide and the Go wiki forbid while testifylint documents testify as Go's most popular framework; (4) loops and branches in tests, where tsDetect counts any loop as Conditional Test Logic but Go's table-driven idiom is a loop and the Uber guide allows one shouldErr branch; (5) DAMP versus DRY, where the Go wiki and Sonar S5976 push parameterization and the Google Go guide and Kent C. Dodds defend duplication or "mindful" abstraction; (6) testing unexported code, which the testpackage linter forbids but the Google Go guide and the Rust book allow ("there's debate"); (7) tests as documentation (Ousterhout against Martin and Meszaros); (8) the test-smell vocabulary itself, which Panichella et al. (EMSE 2022) found "highly mismatched to real concerns", against Spadini 2018 and Bavota 2015 (relayed). On coverage, the Inozemtseva and Holmes abstract (fetched from the neverworkintheory bib), Greg Wilson's review, SEG ch. 11 and cargo-mutants agree that coverage points to untested code and is not a quality target. Coverage.py's framing ("gauge the effectiveness of tests"), Jest's coverageThreshold gate and Google's 60/75/90 guidelines (unfetched) represent the opposing practice. Not opened: Hacker News, Lobsters, martinfowler.com, Google Testing Blog, Coplien, Marick, Beck's Test Desiderata, and Kent C. Dodds' "Testing Implementation Details" (wrong path). These are recorded as unfetched or none-found items. The 2024–2026 freshness signal comes only from current tool sources: the PMD 7.7.0 renames, PMD 7.25.0 AssertStatementInTest, Ruff's pytest 8.4 check= support, and Sonar Python S3415's consistency-only rule.

## Evidence layer

I found evidence that can be opened for most rules in this topic. Every source below was opened over raw.githubusercontent.com. Research papers came from GitHub-hosted author and tool sites: Spadini ICSME 2018, Tufano ASE 2016, Grano ICSME 2020, Pecorelli EMSE 2020 and Palomba and Zaidman EMSE 2019 from fpalomba.github.io; Peruma CASCON 2019 from TestSmells.github.io; Gopinath ICSE 2014 from rahulgopinath.github.io; the abstract of Panichella EMSE 2022 from apanichella.github.io; and the Inozemtseva ICSE 2014 abstract from the neverworkintheory source. Tool rules come from PMD, Error Prone, SonarSource (Java and Python), eslint-plugin-jest, Ruff and clippy. The official documentation is the CPython unittest docs, the Rust book, JUnit, the go command, pytest, the Google Go style guide and google/eng-practices. The standard is SWEBOK V3, chapter 4. I also ran three local hands-on demonstrations (Python, Go, Rust) that confirm specific failure modes. They are not openable until they are committed as evals/fixture tests. Bavota EMSE 2015 is available only as the orchestrator's relayed snippet, plus restatements in the papers I fetched, and those restatements disagree (86% of JUnit tests versus 82% of JUnit classes). No openable research was found for 'name states the behaviour' or for 'test via public API'. I also found nothing openable for Code Coverage at Google, Zhang ISSTA 2014 on test independence or Luo FSE 2014. The sources disagree on five points. (1) Coverage: Inozemtseva, SWEBOK V3 §4, Grano and Pecorelli say coverage is a poor target or predictor, while Gopinath finds statement coverage predicts mutation kills well, with R2 = 0.94 across projects. (2) Test smells: Bavota and Spadini find smells harmful, while Panichella 2022 finds the smell vocabulary mismatched to real concerns, with over 70% misclassification by the older tool, and Pecorelli finds that test-related factors have a limited link to defects. (3) Assertion count: the default limits differ (PMD 1, Sonar 25, jest 5), and the Go style guide says to keep going and report every mismatch. (4) Logic in tests: jest no-conditional-in-test and Smell of Fear oppose it, but Go table-driven tests loop by design and the CASCON survey respondents rejected removing conditionals outright. (5) Private testing: the Rust book says the matter is debated and that unit tests can test private interfaces.
