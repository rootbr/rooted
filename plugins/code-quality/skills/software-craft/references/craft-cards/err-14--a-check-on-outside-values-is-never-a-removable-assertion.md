# A check on a condition that can fail while the module holding it and the code it trusts are correct, such as a public routine's argument, user input or an untrusted dependency's result, runs in every build and launch and fails with an error, never as an assertion that a default launch or an optimized build leaves out

## Thesis
A check on a condition that can be false while the class or module holding the check, and every dependency it trusts, is correct runs in every build and every launch configuration, and fails with an error when the condition is false. Such a condition is one that may fail in real life: an argument passed to a routine callable from outside its module, or object state that such a routine requires its caller to have set up; user input and other data that reaches the program through a user or system-to-system interface; a result from a dependency the code lacks high confidence will meet its specification, such as a remote service's reply; and a result that reports an outcome no code is at fault for, such as a lookup that finds nothing or no free port, even when the module's own routine returns it. The check is an explicit test followed by a raised or returned error or a panic, or an assertion routine or macro that is always enabled; it is not an assertion form that the default launch configuration or an optimized build leaves out, since a build or launch setting would then remove the check and let the bad value through. The removable assertion form keeps its place for a condition that cannot be false unless the module's own code or a dependency it trusts is badly broken.

## Rationale
A removable assertion is left out by a default or common build or launch setting. One language's code generator emits no code for its assertion statement when optimization is requested, and the same option removes any code conditional on its built-in debug flag; running with optimization requested is a common practice in production environments. Another language's launcher disables assertions in all packages and classes by default. A third does not execute its debug-only assertion macro in an optimized build unless a compiler flag turns it on, and its debug-build flag can be used to enable extra debugging code in development but not in production. A condition that may fail in real life can then fail in a run where its check is gone: a bad operational setting has completely eliminated the intended check, the bad value passes, and an unchecked assertion lets a program in an inconsistent state keep running, which might have unexpected consequences. A check written as an explicit test that raises, or as an always-enabled assertion, halts execution regardless of runtime configuration. The litmus test for a removable assertion is that it could be removed without breaking the code, and an assertion form that is off by default is in effect a compiled comment; a check whose removal lets a bad value through fails that test. The removable form serves a check too expensive to be present in a release build that may still help during development, and it is compiled out so that it does not degrade performance. Where the cost of a check on a real-life condition matters, the explicit test with a raise keeps the check in every build and builds its message only when the check fails.

## Example
```java
bad:  public void withdraw(long amount) {
          assert amount > 0 : "amount must be positive";
          balance -= amount;
      }
good: public void withdraw(long amount) {
          if (amount <= 0) throw new IllegalArgumentException("amount must be positive: " + amount);
          balance -= amount;
      }
```

## Limits
The rule is contested, and whether the condition can be false while the class or module holding the check, and the dependencies it trusts, are correct separates the cases. One side asks for an always-enabled check whenever a check may fail in real life, bars assertions on the parameters of a public method, on user input and on interface constraints, and holds that an assertion must not be critical to the application logic, so that it could be removed without breaking the code (the Source entries marked always-on). The other describes assertions as often used in defensive programming to check input values, normally compiled in during development and later compiled out, and documents an assertion that a value is not null as a way to work around a type checker that does not see that a method's attribute is no longer null (the entries marked removable). Of the always-on entries, the library documentation itself keeps the removable assertion for a check that should only fail if the class holding it, or in some cases its package, is broken: a postcondition, a class invariant, and a precondition of a non-public routine, since the public routines' precondition checks should have stopped a bad value before it got that far. An assertion on such an internal condition follows the rule, and so does an assertion that only narrows a type where the module's own logic guarantees the value, a condition that cannot fail unless surrounding code is later modified; a narrowing assertion that the code after it relies on, on a value that a caller, the input, a dependency or an outcome no code is at fault for, such as a lookup that finds nothing, can leave absent, is inside the rule. Assertions in test code are outside the rule, since there they verify that the code under test meets its specification. Code that a debug-build flag keeps out of production is outside the rule while it holds extra debugging aid, such as a check too costly for a release build on the module's own state, and inside it when it holds a check of a condition that may fail in real life. Whether a value crossing a trust boundary is validated enough, which error type the check raises, whether it returns the error or stops the process, the text of its message, and how the routine documents its preconditions are judged by their own rules.

## Validator
Grep the added lines for an assertion statement, a debug-only assertion macro, and a block conditional on a debug-build flag. Set aside a hit in a test file or a test routine, a call to an assertion function or macro that the language or its library runs in every build, and a debug-only block that holds only logging or other debugging aid. For each remaining hit, open the file, read the enclosing routine, name the value the condition tests, and trace it back through that routine to its origin: a parameter of a routine callable from outside its module (a public or exported routine) or object state that such a routine requires its caller to have set up (an initialization call), user input or other data received through a user or system-to-system interface (a parsed request, file or message), a result from a dependency such as a remote service, or a result that reports an outcome no code is at fault for (a lookup that finds nothing, no free port, end of input), even from the module's own routine; or else a value the module's own logic guarantees, a parameter of a non-public routine that its public callers already checked, a postcondition, or an invariant of the module's own state. When the file does not show where the value comes from, leave the hit unflagged. Validator question: **Does an added assertion or debug-only check that a default launch or an optimized build leaves out test a condition that can be false while the module holding it is correct, namely an argument of a routine callable from outside the module or state that routine requires its caller to have set up, user input or other received data, a result from a dependency the code does not trust to meet its specification, or a result that reports an outcome no code is at fault for?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-14`, severity major, `file`, `symbol`, `code` = the added assertion or debug-only check line verbatim from the diff, `fix` = the same condition as an explicit test that raises or returns an error naming the condition and the offending value, or as an assertion routine or macro that is always enabled, in the file's language, `rationale` = where the checked value comes from and which build or launch setting removes the check and lets the bad value through).
