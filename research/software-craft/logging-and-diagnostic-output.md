# Research note — Logging and diagnostic output

Topic `logging-and-diagnostic-output` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: no canon chapter; researched from the evidence layer. The topic is usually formulated from practitioner texts: The Twelve-Factor App, factor XI 'Logs' (heroku/12factor master content/en/logs.md, openable), the 97 Things essay 'Verbose Logging Will Disturb Your Sleep' (97-things/97-things-every-programmer-should-know master en/thing_90/README.md, openable), and Nygard's Release It! (2nd ed.) on logs in production — formulation only; the Python Logging HOWTO's 'When to use logging' is official documentation and belongs to the evidence layer.

Logging and diagnostic output has no canon chapter. The rules are worded after practitioner texts: Twelve-Factor factor XI, the 97 Things essays 21, 25 and 90, Release It!, clig.dev, go-kit, McCune and Cheney. Each rule rests on an evidence layer of four kinds. Official documentation: the CPython Logging HOWTO and logging reference, Go's log and log/slog docs, Rust's std print macros and log crate, java.util.logging, and Google's and Uber's style guides. Standards: OpenTelemetry's log data model and exception conventions, the OWASP Logging Cheat Sheet and ASVS 5.0 V16. Tool rules: Pylint, Ruff, PMD, SonarJava, Error Prone, ESLint, clippy and go vet. Descriptive studies: Yuan et al. ICSE 2012 and OSDI 2014, Fu et al. ICSE SEIP 2014, Zhu et al. ICSE 2015 and LogEnhancer (ASPLOS 2011). The sources agree on seven points. A failure record says what failed and carries the identifiers and values needed to diagnose it. A caught exception is logged as the exception or error value, not as its message. A record's level matches its event. A disabled level should not pay for expensive arguments. Libraries log through a facade and leave the backend to the application. A location spelled out in message text goes stale. A log argument is not guaranteed to be evaluated. Five disputes are carded only under the condition their own sources give: stdout versus stderr (separated by whether stdout carries the program's primary output), print versus logger (separated by whether the output is a diagnostic record or the program's own output to its user), eager formatting (separated by what the deferred work costs), what ERROR means (separated by whether the failure is expected and handled in routine operation), and whether a suppressed error needs a record (separated by whether it was unexpected). Two disputes stay pending. One is logging an error and then rethrowing it: the Go guides, Kubernetes, Flogger and Sonar S2139 oppose it, while the Python tutorial calls it 'the most common pattern'. The other is splicing values into the message text: the Python HOWTO, Google pyguide and slog oppose it, while Pylint calls f-strings 'another reasonable option' and Ruff files its checks as Pedantic. The research is descriptive. It measures how often developers revise levels, variables and stale text, and which catch blocks they leave unlogged; none of it is a controlled test of a rule.

## Formulation layer

The formulation layer rests on texts I opened: Twelve-Factor factor XI and its 2024 update branch, the 97 Things essays (90 'Verbose Logging Will Disturb Your Sleep', 21, 25), the Google Python/Go/Java style guides, the Uber Go guide, the Rust Book ch. 12-06, the Python tutorial, clig.dev, the go-kit log docs, brandur's logfmt essay, the SLF4J FAQ, SWE at Google ch. 20 and the SWEBOK V3 transcription. Several sources I could not open are stated from memory and marked as paraphrase: Release It!'s Logging section, Clean Code ch. 7, Effective Java Items 73/75, TPOP, K&R §7.6, TAOUP's Rule of Silence, and the blogs by Wiggins, Cheney, Bourgon, McCune and Hodgson. On four points the sources agree. The error level is for conditions someone must act on. A log message must say what failed and carry the values and identifiers needed to diagnose it. A log call takes a literal pattern plus arguments rather than a string built in advance, so that work is skipped when the level is off. Key/value fields carry values better than values spliced into prose. The canon splits in three places. Twelve-Factor sends a service's log stream to stdout, but K&R, the Rust Book, clig.dev and TPOP send diagnostics to stderr; what decides it is whether stdout carries the program's primary output. Google's and Uber's Go guides, McCune and Cheney log an error once where it is handled, but the Python tutorial calls log-and-re-raise the most common pattern. Release It!, 97 Things and Google keep ERROR/WARN levels, but Cheney and Bourgon argue that debug and info are enough. The aposd-vs-clean-code discussion was fetched and has nothing on logging. Log routing, rotation and storage, Release It!'s Steady State, and request-level canonical log lines fall outside the statement-level scope.

## Reception layer

Reception contests four of the topic's candidate rules. (1) Twelve-Factor, structlog and Node.js Best Practices send a service's log stream to stdout, while clig.dev, the Rust book, Google's shell guide and the Go and Python logger defaults put a command-line program's diagnostics on stderr, so a card must name the program kind. (2) Print bans are walked back: ESLint dropped no-console from recommended for CLI false positives, Error Prone SystemOut and clippy print_* ship off by default, and Ruff T201 and the Python HOWTO keep print for CLI output, so 'logger, not print' holds for diagnostics only. (3) For lazy formatting, Pylint enables W1201-W1203 by default but its docs call f-strings 'another reasonable option', and Ruff files G001-G004 as Pedantic; PMD's GuardLogStatement guard is a 'last resort' for Flogger and 'old-school' for Log4j, while Google's Go guide prefers it for expensive arguments. All agree on doing no expensive work that a disabled level discards, and on a constant message template (Google pyguide, Log4j, CA2254, sloglint). (4) Uber, Google Go, Kubernetes, Flogger and Sonar S2139 say log or return, not both, but the Python tutorial calls log-and-re-raise 'the most common pattern'. Level meaning is split too: actionable (Brodwall, Google Go, Kubernetes) versus severity (Python HOWTO, OpenTelemetry), and logr, following Cheney, rejects the named warning level that slog keeps. The sources disagree on five points. (1) stdout versus stderr: the Twelve-Factor App and Node's console.log send to stdout, while the Rust, Python and Go defaults use stderr. (2) Log-and-rethrow: ErrLog's log-every-exception approach is questioned by Fu and Zhu, and the Google Go guide names a downside of leaving the log to the caller (line coordinates). (3) Lazy formatting: Pylint's own docs call f-strings 'another reasonable option', and slog ties its advice to profiling. (4) What ERROR means: 'more serious problem' (Python), 'actionable' (Google Go) or 'expected impact' (OpenTelemetry). (5) Print-versus-logger rules exclude a CLI's primary output. The stack-trace rule does not carry over to Go or Rust error values, which hold no stack. The form that holds across languages is to pass the error value itself, not its message string.

## Spine — candidate rules in source order

1. **A program whose standard output carries its primary output writes its error, warning and progress messages to standard error, not into standard output** — When a program's standard output carries its primary output (the results a user reads or the next command in a pipe consumes), its error, warning and progress messages go to standard error, so that redirecting or piping standard output still shows them and does not pass them downstream. A long-running service whose standard output carries only its log event stream is outside the rule; the Twelve-Factor App sends that stream to stdout. The default console destination of Go's standard logger and of Python's logging is already standard error.
