# A test body runs the same statements on every execution, branching on no case field, result or environment, and a loop in it only repeats identical straight-line checks over a table of cases or re-tests one awaited condition under a deadline

## Thesis
All the setup, action and assertion logic of a test body runs on every execution: no conditional statement or conditional expression in the body chooses which of them run, whether its condition is a field of the current table row, a result of the code under test or a property of the environment. Cases that need different logic go to separate tests, even at the cost of duplication between them. A loop in a test body is admitted only when it iterates over a table of cases and runs the same straight-line statements and checks for every row, or when it re-tests one awaited asynchronous condition at a poll interval until the condition holds or a timeout that bounds the test runs out.

## Rationale
A condition in a test alters the test's behaviour and its expected output: when the condition is not met, the statements it guards do not execute, which can lead to situations where the test fails to detect a defect in the code it exercises. Conditional code in a test also makes it harder to comprehend, and a table test whose subtests contain conditional assertions or other branching logic can be difficult to read and maintain, while the readers of a large, complex table test may have difficulty debugging the failures that occur. Depending on the path executed, the test environment may or may not be properly set, which can make the outcome depend on the order in which tests run. In a study of 19,532 test methods of 18 software systems, 5% of flaky tests co-occurred with conditional test logic and 4% were actually due to it, so this smell appeared less harmful than the other test smells considered, though it can sometimes explain flakiness; the refactoring that removed it created a new test for each portion of code belonging to a different condition, so that each test method contained the code to test one specific path. Conditional logic in a test is usually a sign that the test covers too much, and each branch is usually better served by a test devoted to it, and the extra clarity from the duplication between test cases is necessary for readability. A loop that runs one straight-line body over every row keeps comparable cases together: the table form suits many test cases tested with similar testing logic, and when behaviour changes only with the input, grouping similar cases in one table may better illustrate how behaviour changes across all inputs than splitting them into separate tests that are harder to compare and contrast.

## Example
```java
bad:  for (Case c : cases) {
        if (c.warm) service.run(c.input);
        Result r = service.run(c.input);
        if (r.isCached()) assertEquals(1, r.hits());
        else assertEquals(0, r.hits());
      }
good: @Test void firstRunMisses() { assertEquals(0, service.run(input).hits()); }
      @Test void secondRunHits() {
        service.run(input); assertEquals(1, service.run(input).hits()); }
```

## Limits
Whether loops fall under the rule is contested. A test-smell catalogue counts every control statement in a test, for, foreach and while included, as conditional test logic. Style guides for table-driven tests and a unit-test framework's subtest facility document a loop over cases that share one testing logic, and surveyed developers could not agree to the outright removal of conditional statements from test methods, judging them case by case. The separating condition is whether the control flow changes which statements run for a case, and two documented forms take a loop out of the catalogue's count: a loop over a table of cases that applies the same straight-line checks to every row is documented practice, and so is a polling loop that re-tests one awaited asynchronous condition at a poll interval under a timeout, documented for a subject that sends a message to an external broker, where the assertion cannot run until the message has gone through; any other loop, such as one that repeats a setup step or walks a collection the code under test returned, stays a finding; a branch on row values, results or setup that decides what runs is the defect, since cases checked with different logic are appropriately written as multiple test functions, and an extra case is permissible in a table only when it is simple and does not introduce conditionalized code flow in the loop body. A comparison whose only branch reports the failure is the assertion itself, the form the documented minimal table-driven test uses for every row. A guard on the environment whose only body skips the whole test through the framework's skip call is not branching either, and neither is a guard on a generated input whose only body discards the case through a property-based framework's assumption or discard call, which the framework counts apart from passing cases: the framework reports the test as skipped rather than passed, and framework documentation shows this guard for a test skipped in short mode, when an external resource is unavailable, or when the configuration is unsupported. When the test body is short and straightforward, a single branching pathway for success versus failure cases is a documented tolerance, whether it branches on an expected-error field of the row or, after a failure-reporting comparison has checked the returned error against that field, on the returned error to skip the value check; the alternative documented as the best approach, when a routine is tested both for exact outputs and for errors on invalid input, is two table tests, one for normal outputs and one for error outputs. A failure inside a loop is hard to troubleshoot when the assertion does not give enough information, and a per-iteration subtest or a failure message that identifies the input distinguishes the failing row.

In a fuzz target whose engine is budgeted by duration or by executions and documents an early return as an alternative to its skip call, a guard on the fuzzed input whose only body returns early skips that input as the skip call would and is not branching.

A condition inside a callback the test hands to the code under test, whose only body signals the awaited event, such as counting down a latch when the matching message arrives, is the wait's completion signal and not a branch among the test's setup, action and assertion statements.

## Validator
Grep the hunk for a conditional statement, a conditional expression or a loop inside a test routine. Open the test file and read the whole routine. For each conditional, trace its condition to a field of the current table row, a value or state returned by the code under test, or a probe of the environment, and check whether its outcome decides which setup, action or assertion statement runs. Set aside a branch whose only body reports a failure, a guard on the environment whose only body skips the whole test through the framework's skip call, a guard on a generated input whose only body discards the case through the framework's assumption or discard call, and a single expected-error branch in a short table test, on the row's expected-error field or on the returned error after a failure-reporting comparison has checked it against that field. For each loop, check that it iterates over a table of cases and runs the same statements for every row, or re-tests one awaited condition at a poll interval under a timeout. Validator question: **Does a conditional or a loop in a test body decide which setup, action or assertion statements run for a case, or does a loop iterate over anything but a table of cases or a polling re-test of one awaited condition under a timeout, beyond a failure-reporting comparison, an environment guard whose only body skips the test, a guard whose only body discards the generated case through the framework, or a single expected-error branch in a short table test?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-17`, severity minor, `file`, `symbol`, `code` = the conditional or loop header and the statements it guards, quoted verbatim from the diff, `fix` = one test per path, each with straight-line setup, action and assertion, in the file's language, `rationale` = the statements a path leaves unexecuted and the condition that selects them).
