# Hypotheses of the committing-changes skill

The claims of this skill that no test backs yet, keyed `H-<id of its line>` and named by that line's record in `rules-provenance.md`. Each names its measure and the outcome that would refute it, and in `beside` the published sources found so far, with what they showed and how they bear on the claim in `beside-result` and the conditions they ran under in `beside-bounds`. A hypothesis whose test is planned as our own also names its threshold, its runs and the file that holds the test, and is committed here before the test runs. A hypothesis that a test settles keeps its line, with the result and the new standing.

- **H-Rules-4-what-and-why-not-how** · A commit body that an agent writes to say what changed and why, leaving out how the code does it, lets a later reader state the purpose of the change correctly more often than a body for the same change that describes how the code was changed · kind: claim · standing: hypothesis · measure: share of readers, people or models, who after reading the message and the diff state the purpose of the change in agreement with the purpose its author recorded · against: the same changes committed by the same agent with bodies that describe how the change was made · scope: commits and commit messages an agent writes in a git repository, with 2026 Claude models in Claude Code · refuter: the share with what-and-why bodies is equal to or lower than the share with how bodies · beside: external doi:10.1109/ICSE48619.2023.00076 first-hand; external arXiv:2602.14611 first-hand · beside-result: Li and Ahmed compared the share of messages with What, Why or both among the commits preceding defect-introducing and other commits and found a difference at every window size (Welch's t-test against a Bonferroni-adjusted 0.006, Cohen's d 0.02565 to 0.14742), which the authors read as commit message quality having an impact on defect proneness though the table prints no group means, under other conditions: the measure is the defect-proneness of later commits and no arm leaves how out; Pirouzkhah, Wurzel Gonçalves and Bacchelli compared pull requests with and without each description element and found for those whose description explains the code changes odds ratios of merge of 1.123 in the baseline and 1.206 in the controlled model, significant in both (mixed-effects logistic models, Holm-corrected p-values), which the authors word as approximately 12–20% more likely to be merged, while the purpose of the pull request was significant in neither (odds ratios 0.978 and 1.010) and the 57 valid survey respondents valued purpose and reason in most pull requests and code explanation only moderately, under other conditions: pull-request descriptions written by people and the merge decision, an element's presence against its absence across different pull requests and no arm that sets what and why without how against how, so the study bears neither for nor against the claim · beside-bounds: human-written commits of 17 of 32 Apache projects, 91,926 commits after filtering, labelled by a classifier of What and Why, with defect-introducing commits found by SZZUnleashed (Li and Ahmed, ICSE 2023); 80K GitHub pull requests of 156 projects in five programming languages with descriptions written by people, their elements labelled by LLaMA 3.1-70B, and a survey with 57 valid responses (Pirouzkhah, Wurzel Gonçalves and Bacchelli, MSR 2026)
- **H-Rules-5-footer-references-issues** · A commit that an agent writes with a footer referencing the issue it serves is connected to the right issue later more often than the same commit without the reference, whose link must be recovered from its text, files and dates · kind: claim · standing: hypothesis · measure: share of commits that a later reader or link-recovery tool connects to the issue the change was made for, checked against the task's issue · against: the same commits with the issue reference left out of the message · scope: commits and commit messages an agent writes in a git repository, with 2026 Claude models in Claude Code · refuter: the share connected to the right issue with the footer reference is equal to or lower than the share recovered without it, as when an agent's references name wrong issues · beside: external arXiv:2507.09199 first-hand; external doi:10.1145/1595696.1595716 abstract; external doi:10.1007/s10664-014-9314-z relay · beside-result: Huang et al. removed the explicit issue tags from the commit messages behind 9,319 issues across 20 projects and found the best recovery tool, EasyLink, at an average Precision@1 of 75.03% with 50.75% recall and ReLink at 10.92% precision, against links taken from those tags, the source names no test of the gap between tagged and untagged commits, in the claim's direction, under other conditions: tools rather than readers recover the links and the commits are human-written; Bird et al. report in their abstract that only a fraction of bug fixes are labelled in version histories and find strong evidence of systematic bias in which fixes are labelled, the abstract names no figures and no test, in the claim's direction on what an unreferenced fix loses, under other conditions: bug-fix datasets built for defect prediction; Mäder and Egyed, relayed and unopened, report a controlled experiment with 71 subjects who performed maintenance tasks 24% faster with requirements trace links than without, under other conditions: links between requirements and code rather than commit footers · beside-bounds: human-written commits and issues of 20 open-source projects whose explicit issue tags were removed, links recovered by tools (Huang et al., ICSE 2026); bug-fix datasets of several open-source projects (Bird et al., ESEC/FSE 2009); 71 subjects on maintenance tasks with and without requirements trace links (Mäder and Egyed, Empirical Software Engineering 2015, relayed)
- **H-Grouping** · commits an agent groups by one bug, one feature or one module refactor and splits by unrelated features, a fix mixed with a feature and different layers lead their reviewer to find more of the change's defects than the same change in one mixed commit · kind: claim · standing: hypothesis · measure: defects of the change found per reviewer · against: the same change committed as one commit that mixes its concerns · scope: commits an agent writes in a git repository, with 2026 Claude models in Claude Code, reviewed by people · refuter: reviewers of the split commits find no more of the change's defects than reviewers of the one mixed commit · beside: external arXiv:1805.10978 Table 2 and Table 3 first-hand; external https://yidatao.github.io/paper/tao_msr2015.pdf Table V first-hand; external arXiv:2610.11593 Table 2 and Table 3 first-hand · beside-result: one pull request holding a single commit with a refactoring and a new feature against two pull requests split by concern, 14 developers and graduate students per arm, found 20 against 17 defects (mean 1.42 against 1.21, Mann–Whitney U p = 0.6), no difference, as the refuter names, while issues wrongly reported fell from 6 to 1 (p = 0.03, Cliff's d = 0.36) and review net time stayed level (median 831 s against 759 s, p = 0.66), under other conditions: pull requests rather than commits, a change the experimenters wrote; repair agents given agent-written regression patches without untangled commits against with RucTangle's ordered commits and git bisect results reached pass@1 26.9% against 31.3% and 30.8% against 36.0% for two models on 453 patches and 29.3% against 36.0%, 50.0% against 53.3%, 61.3% against 61.3% and 50.0% against 48.7% for four models on 150 patches, the source names no test, under other conditions: a repair agent rather than a reviewer, pass@1 rather than defects found, and the history bundled with bisect results · beside-bounds: human reviewers of Java changes, 28 professional developers and graduate students on GitHub pull requests in 2019 and 18 computer science students in a review website in 2015; six open and hosted models as repair agents on Python projects of SWE-CI, the patches written by six models with Claude Opus 4.6 among them, in 2026
- **H-Gotchas-4-never---no-verify** · an agent that commits under the rule bypasses the repository's pre-commit and commit-msg hooks less often, so fewer of its commits enter history failing the checks those hooks run, than the same agent committing the same changes without the rule · kind: claim · standing: hypothesis · measure: share of the agent's commits that fail at least one of the repository's pre-commit or commit-msg hooks when those hooks are run again on them · against: the same changes committed by the same agent and model without the rule · scope: commits and commit messages an agent writes in a git repository with pre-commit or commit-msg hooks installed, with 2026 Claude models in Claude Code · refuter: the share with the rule is equal to or above the share without it · beside: external arXiv:2610.32578 Tables 3 and 4 first-hand; arXiv:2608.29460 compared a baseline with an anti-reward-hacking policy referenced from the system prompt and reward hacking fell from 23.6% to 9.7%, mixed-effects logistic OR 4.10, 95% CI 2.51–6.70, p = 2.6 × 10−8, while a one-sentence prompt instruction gave 16.9%, for which against the baseline the source as I read it names no test;
