# A declaration visible outside its module names the abstraction its callers need in its signature, and keeps a type that is only its implementation choice inside the module

## Thesis
A function, method or constructor visible outside its module declares its parameters and its results with types that promise what its callers need, separate from the details of how the module realizes them, and keeps a type that is only its implementation choice inside the module. A parameter whose routine uses only the essential features of a collection is declared with the collection interface or the borrowed view, such as a slice, that covers those features, not with the concrete class chosen for its performance characteristics; a result built from a chain of adapters is returned as a wrapper type that promises only the abstraction, such as an iterator over a given item type. A factory — a function visible outside its module that creates and returns a value — returns the interface when the type it creates exists only to implement that interface and will have no exported methods beyond it, and that type need not be exported; a language-level constructor, which can only yield its own class, is outside this clause.

## Rationale
A concrete collection class is chosen for the performance of its data structure — fast random access in one, cheap insertion at any position in another — and that choice is an implementation detail the interface should not expose. Coupling a routine's parameters to the implementation class limits the ability to use alternate implementations as requirements change, and a parameter that requires the specific type makes the routine less useful for no benefit, since a borrowed view such as a slice usually suffices and can be obtained from other types too. A result whose type spells out how it was built promises the client how it is constructed and represented; a wrapper that promises less hides that, so the representation can change in the future without breaking client code. A factory that returns the interface makes clear the value has no interesting behaviour beyond what the interface describes, spares repeating the documentation on every instance of a common method, and lets one implementation replace another by changing only the factory call, the rest of the code unaffected.

## Example
```typescript
bad:  export class MemoryStore implements Store { ... } // no methods beyond Store
      export function createStore(): MemoryStore { return new MemoryStore(); }
good: class MemoryStore implements Store { ... }
      export function createStore(): Store { return new MemoryStore(); }
```

## Limits
For results the guidance is contested. A result declared with a concrete collection class is outside the rule: one analyzer flags it as an implementation detail an API should not expose, while one language's typing guidance prefers concrete types for the return values of concrete implementations and abstract types for arguments, and no source states a condition that separates the two positions. For other results, what separates the cases is whether callers use what the concrete type offers beyond an abstraction or the type is only how the module does its work. Returning the concrete type is the default where callers use what it offers: it gives the caller every public method and field of that implementation, not only the subset a pre-chosen interface defines, and the caller can still pass it to any function that expects an interface. Hiding a returned type is warranted where the type exists only to implement an interface and will have no exported methods beyond it, where a wrapper lets the module promise less about how a result is constructed or represented, or where the extra details would let callers bypass safety checks or exposing the concrete type would make it impossible to change the underlying provider later without a breaking change; the rule flags the first two of these, and encapsulating by rote, without such a reason, is outside the rule. Parameters are not contested in this way: the guidance that defaults to concrete results also advises taking interfaces as arguments. The rule asks for an abstraction that already exists — a collection interface, an iterator, the interface a type implements — or for a wrapper; it does not ask for an interface created only to hide a type, since an interface is created when a real need exists. Where no more general type is available that covers what is done with the value, the concrete type is the one to declare. Declarations not visible outside the module, such as a private field or a local, are outside the rule, whose concern is the module's surface; the implementation class is chosen where the collection is instantiated. An opaque result type is more concise than a wrapper but limited in what it can express, such as a result that must also be cloneable or printable for debugging, so it probably suits an internal interface and may suit a public one, though probably not every one. A returned interface limits the default surface rather than hiding the implementing type strictly, since its exported methods stay reachable through a type assertion; the rule is a design rule, not a security boundary. Changing a type in a signature that is already published can break callers — a reference typed with the old signature no longer compiles — and code outside the repository may reference it, so such a change goes through deprecation first. Whether a field is visible outside its module at all, whether a caller may mutate an internal object it receives, which operations a public interface offers, and which members a type gains by inheriting, embedding or dereferencing to another type are judged by their own rules.

## Validator
Grep the added lines for a declaration visible outside its module whose parameter type is a concrete collection class or whose result type is a chain of adapter types, a factory that returns a named implementing type, and an exported class declared as implementing an interface. Open the file and set aside a declaration that is not visible outside its module by the language's rule (exported, public, or named without the language's non-public marker). For a collection parameter, name what the routine's body does with it; for an adapter-chain result, name what callers do with it, from the routine's documentation and any callers in the file; and name the more general type the language offers that covers it, if there is one. For a factory's result type, or an exported implementing type that a factory in the file returns, list the type's exported methods and fields beyond the interface it implements. Set aside a concrete result whose extra members callers use; a result declared with a concrete collection class; a value for which no more general type covers what is done with it; a language-level constructor, which can only yield its own class. Validator question: **Does an added declaration visible outside its module name, as a parameter type or a result type, a type that is only its implementation choice — a concrete collection class as a parameter type where a more general type covers what the routine does with it, an adapter chain as a result type, or, as a factory's result type, an implementing type with no exported behaviour beyond its interface?** Yes → flag.

## Finding output
