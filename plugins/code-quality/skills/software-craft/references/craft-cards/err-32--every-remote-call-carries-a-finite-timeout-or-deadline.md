# Every call to a remote service or another process carries a finite timeout or deadline, set at the call or on the client it goes through, so the caller cannot wait forever

## Thesis
Every awaited or blocking call to a remote resource — an HTTP request, an RPC, a database or socket connection, a call into another process — runs with a finite timeout or deadline in effect, passed at the call or configured on the client, connection or context the call goes through. A timeout is the longest the call may take and a deadline is the point in time it may not go past; either one meets the rule. A bound on connecting alone does not, since the wait for the response once the connection is open stays unbounded. The bound in effect is what counts: a call that passes none inherits its client's documented default, which meets the rule when it is finite and breaks it when it is no limit, and a timeout set explicitly to a value the client defines as no limit, such as zero or none, breaks the rule as a missing one does.

## Rationale
A caller that waits with no bound on another component that hangs, or whose node is disabled, gets no error code back: it waits endlessly for a response that will not come, and an outage of the remote resource can make the caller hang. In a study of 156 real-world timeout bugs in 11 cloud server systems, 42 came from missing timeout checking, 26 of them on network communication — socket connections including reads and writes, RPC calls and HTTP requests — and a missing timeout can cause a system hang or crash that often produces no timeout-related error message; 83 of the 156 bugs produced no error message, 16 a misleading one and only 40 a correct one, which makes timeout bugs hard to diagnose. In a study of high-severity incidents in production cloud services, 31% of software-bug incidents came from not detecting or handling component faults correctly, and 29% of those were an unresponsive component — a hanging job or a disabled node that never returned an error code and surfaced as a timeout perceived by users or watchdogs; where a fault went undetected, the waiting component in most cases waited infinitely for an operation that would never occur. A call that passes no bound inherits its client's default, and several standard and widely used clients document that default as no limit: an HTTP client whose zero timeout means no timeout, a request builder whose unset timeout blocks forever, a socket whose default timeout is none, HTTP libraries whose default is no timeout, and an RPC framework that sets no deadline, so that a client can end up waiting for a response effectively forever. An explicit zero or none means the same where the client defines that value as an infinite timeout, and it is the same weakness as an omitted timeout. A finite bound turns the hang into an error the caller receives — a timeout exception or a deadline-exceeded status. It can sit on the client, where it applies to every request the client makes, or on a context that carries a deadline across API boundaries and between processes. Static checkers flag a request with no timeout argument because the program can hang indefinitely, and one also flags a timeout set explicitly to none.

## Example
```python
bad:  reply = requests.get(url)
      conn = socket.create_connection(address)
      client = httpx.Client(timeout=None)
good: reply = requests.get(url, timeout=10)
      conn = socket.create_connection(address, timeout=5)
      client = httpx.Client(timeout=10)
```

## Limits
A client whose documented default is finite meets the rule with no bound at the call: one documented client raises a timeout error after 5 seconds of network inactivity by default, and one checker flags a call through it only when its timeout is set explicitly to none. A per-read or inactivity timeout meets the rule too, but it bounds the wait between bytes rather than the whole call, so the call as a whole can take longer than the value; a total timeout or a deadline bounds the call from the start of connecting to the end of the response body. A wait on a lock, a latch or another synchronization within one node is outside the rule, although the same bug study counts 16 bugs from a missing timeout for synchronization, file system and process or thread synchronization among them. Choosing the value is outside the rule as well: a value too small can make the system or application fail and one too large can degrade performance, and a misused value is the largest class in that study, 65 of its 156 timeout bugs. One client's guide asks for the bound in nearly all requests of nearly all production code and documents an explicit unbounded wait for a remote server that is very slow; a project context that accepts an unbounded wait for a named call rejects the finding for that call.

## Validator
Grep the added lines for a call that sends a request or opens a connection to another component — an HTTP request or the construction of an HTTP client, an RPC client or stub, a socket or database connection, a call into another process — and for a timeout set to zero, null, none or infinity. For each hit, open the file and trace where the call's bound comes from: an argument at the call; the client, session or connection it goes through, where that object is built or configured; an enclosing deadline, cancellation context or timeout scope the call honors; a default the file or the project sets. Where none is set, take the client's documented default: a finite default passes, a default of no limit does not. Count zero, null or none as unbounded only where the client documents that value as no limit, count a per-read or inactivity timeout as a bound, and a timeout that bounds only connecting as no bound on the wait for the response. Skip a wait on a lock, a latch or another synchronization within one node, and a call the project context accepts as unbounded. Validator question: **Does an added line make or configure an awaited or blocking call to a remote resource or another process with no finite timeout or deadline in effect on its wait for the response — none at the call, on its client, connection or context, nor from a finite documented default, a bound on connecting alone counting as none — or with one set explicitly to a value the client defines as no limit?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-32`, severity major, `file`, `symbol`, `code` = the call or client construction quoted verbatim from the diff, `fix` = the same call or client with a finite timeout or deadline passed at the call or configured on the client, connection or context, in the file's language, `rationale` = which remote resource the caller waits on and why no finite bound is in effect: no argument, a client default of no limit, or an explicit value the client defines as no limit).
