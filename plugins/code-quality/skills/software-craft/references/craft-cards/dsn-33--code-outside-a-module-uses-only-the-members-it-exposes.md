# Code outside a module uses only the members the module exposes, never one it marks non-public by a modifier, a naming convention or an annotation

## Thesis
Code reads, writes, calls and imports another class, module or library only through the members that owner exposes, and uses a non-public member only from inside the scope its mark grants. A member or name is non-public when an access modifier narrower than public marks it, when a naming convention the language documents for non-public names marks it, such as a leading underscore, or when an annotation marks it internal, test-only or visible only for testing; a name inside a non-public module, package or class is non-public as well, and so is a name a module only imported, unless that module documents it as part of its interface. The scope a mark grants is the declaring class, with its descendants for a member meant for subclasses; the declaring module for a module-level name, and the containing package for a non-public module; the declaring library for a member annotated as internal; test code for a member annotated as test-only, and test code and the declaring class for one annotated as visible for testing; and, for a mark the language enforces, the scope the language defines for it. Outside that scope, code neither uses the member directly nor reaches it around the declared visibility: not through reflection, string-keyed or bracket access, a reinterpretation of the owner's memory or a linker directive that aliases the owner's symbol, and not through any other construct that bypasses the visibility, such as a cast or a comment that switches off the type check.

## Rationale
A non-public mark declares the member an implementation detail that its owner may change or remove without notice. Compatibility guarantees apply only to public interfaces, and a non-public member carries no promise that it will be present in a later version, keep its type or keep its behaviour, so code that uses it can behave incorrectly when the owner's internals change. A hidden field is also what lets its owner validate the field's contents and maintain invariants on them: outside code that writes the field directly, as reflection can, bypasses the controls in the owner's setter and can break the owner's internal contracts, with runtime errors among the results. The mark speaks to tools as well as to readers: a private declaration states that every access lies in the methods of the declaring class, so an unused-code check flags a private member as unused even when another file reaches it around the restriction, and such a bypass can break when the build rules are rearranged. Where the language enforces the mark only during type checking, or not at all, bracket notation, a plain property lookup or a mangled name still reaches the member at run time; the mark is then a convention that callers follow rather than a barrier. The routes around an enforced mark step outside the language's own guarantees: a linker directive that aliases another package's symbol lets one package access a symbol in another even when that violates the usual encapsulation of unexported declarations, or even type safety, and is enabled only in files that import the facility for unsafe operations, whose importers are not protected by the language's compatibility guidelines; one toolchain refuses new such references to internal symbols of its standard library that are not marked for them on their definitions, keeping the uses already found in a large open-source corpus working only for backward compatibility. Reinterpreting an object's memory to reach its fields depends on a layout the language leaves unspecified for ordinary types, and where the layouts differ, the wrong fields are filled with the wrong data. The public interface keeps the caller inside the owner's compatibility guarantee; where it lacks what the caller needs, the owner can make a member public, which is easier than making a public member non-public later.

## Example
```python
bad:  from billing.rates import _TAX_RATE
      total = cart._subtotal * (1 + _TAX_RATE)
      setattr(cart, "_subtotal", 0)
      vars(cart)["_items"] = []
good: from billing.rates import TAX_RATE
      total = cart.subtotal() * (1 + TAX_RATE)
      cart.clear()
```

## Limits
A member meant for subclasses is open to the declaring class's descendants, a module-level non-public name to its whole declaring module, and a member annotated as internal to the whole library that declares it, including the packages a project's analysis configuration lists as its own. A name its owner documents as public is public whatever its form: a documented interface is public unless its documentation declares it provisional or internal; a name listed in a module's declared export list is public even with a leading underscore; names a package's entry module exposes from its submodules as part of its documented interface are public; and some types give public members a leading underscore to avoid conflicts with field names, as the extra methods and attributes of a named tuple do. A name that begins and ends with a double underscore, or a name bracketed in single underscores that a standard type reserves, such as an enumeration's, is not marked non-public. A test's access to the code it tests is outside the rule: one rule admits test code for members annotated as test-only or visible for testing, and one reflection rule checks main code only; whether a test should reach past the public interface of the code it tests is a question of test design. A test's access to the non-public members of other code is judged like any other code. A symbol whose own definition carries the linker directive that names it is opened to outside access by its owner, and a reference to it is not a bypass. Code that only a debugger runs is outside the rule: a debugger is a special circumstance in which reaching a non-public member can be useful. Names the project's linter configuration lists as ignored for this check, and a tolerance stated in the project context, reject the finding. Which members an owner exposes, how widely, and whether it hands a caller a mutable internal object are questions of the owner's design, judged by their own rules.

## Validator
Grep the added lines for a member with a leading underscore read, written or called on a receiver other than the current instance, the current class or the parent-class call; an import of a name with a leading underscore, or from a module or path with one; reflection that opens a member's accessibility, looks up a declared member, or reads or writes an attribute by an underscore name; string-keyed or bracket access to a member; a cast to an unchecked or unrelated type followed by a member access; a comment that suppresses a type-check error; an unsafe pointer or memory reinterpretation; and a linker directive that aliases another package's symbol. For each hit, open the file and identify the member and its owner: read the mark from the member's name, from its declaration where the file holds it, or from the reflection or bypass call itself, and decide whether the member is non-public by a modifier, a naming convention, an annotation, a non-public containing module, or because its owner only imported it. Then decide whether the accessing code lies inside the scope the mark grants: the declaring class and, for a member meant for subclasses, its descendants; the declaring module for a module-level name and the containing package for a non-public module; the declaring library for an internal annotation; test code, and for a visible-for-testing annotation also the declaring class. For a suppressing comment or a cast, flag it only when the access it enables is to a non-public member. Skip a test file's access to the code it tests, names wrapped in double underscores on both sides, a name its owner documents as public (a documented interface, a name in a declared export list, a named tuple's underscore members), a linker directive whose target's own definition carries the directive, code that only a debugger runs, and names the project's linter configuration or the project context tolerates. Validator question: **Does an added line outside the scope a member's non-public mark grants read, write, call or import that member, directly or around the declared visibility, with no documentation making it public and no linter configuration or project context tolerating it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-33`, severity minor, `file`, `symbol`, `code` = the added line that reads, writes, calls, imports or reaches the non-public member, quoted verbatim from the diff, `fix` = the same operation through the owner's public interface, or through a public member the owner adds for it, in the file's language, `rationale` = the member and its owner, the mark that makes it non-public, and the scope that mark grants, which the accessing code lies outside).
