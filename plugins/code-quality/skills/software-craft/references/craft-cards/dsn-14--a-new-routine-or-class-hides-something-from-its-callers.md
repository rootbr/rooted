# A new routine or class hides something its callers would otherwise handle, so a routine that only passes its parameters unchanged to a routine they can already call, or a stateless class used only as a namespace or holding only a constructor, where the language has free functions, is not added

## Thesis
Every routine or class that a change adds hides something its callers would otherwise handle themselves — a step, a computation or a decision, several steps behind one name, or state or behaviour that its instances carry — so that it repays the name and the interface it adds. Two kinds of added unit hide nothing. The first is a routine whose whole body is one call passing the routine's own parameters, not counting a receiver it declares among them, to another routine unchanged and in order, with no other argument, on no object that the routine's own instance holds, with no conversion or adjusted type and nothing else in the body, where every caller of the routine can already call that other routine directly; outside overrides of an inherited method, implementations of an interface or trait member, constructors that pass their parameters to a parent's constructor, routines that a subclass overrides or a test replaces, routines that a decorator, annotation or attribute wraps with behaviour or registers, and entry points that a runtime, framework or test runner calls by name, it is replaced by the routine it calls. The second, in a language with module-level functions, is a class or type that extends or implements no other, that no other class extends, that no declaration or type argument names as a type, that no library or framework reads by its name or receives as an object, and that serves only as a namespace — its members are all static routines and constants, none taking a receiver — or whose one member is a constructor that stores no field; it is replaced by module-level functions and constants, and a constructor-only class can generally be replaced by one standalone function.

## Rationale
An abstraction removes information from the place where it is used, so each one has to provide sufficient benefit, and simple code has no unnecessary levels of abstraction. A routine whose well-picked name is a summary of several lines provides that benefit: a reader first takes the high-level view of what the code does, then goes deeper by opening the called routines. A routine whose body is a call on its own parameter list provides none: it can be replaced by the routine it calls, a reader who opens it finds only a call to a second routine, and creating it adds code for no benefit. A class used only as a namespace adds cognitive complexity without any structural improvement, since the functions and constants put on it are already organized by the module that holds them.

## Example
```java
bad:  static int parse(String text) { return Integer.parseInt(text); }
      int count = parse(input);
good: int count = Integer.parseInt(input);
```

## Limits
A unit whose body holds more than the one forwarding call meets the rule however short it is: a routine that checks, converts, defaults, reorders or adds an argument, adjusts a type on the way, or locks, logs or handles an error around the call hides that step. The forwarding case does not reach a routine whose callers cannot call the routine it forwards to directly, such as one that keeps another module's routine or type out of a public interface, nor overrides, interface or trait implementations, constructors that pass their parameters to a parent's constructor, routines that a subclass overrides or a test replaces, routines that a decorator, annotation or attribute wraps with behaviour or registers, or entry points that a runtime, framework or test runner calls by name, since replacing any of these with the routine it calls changes what runs. A routine that calls an operation on an object its own instance holds, a field or a member reached through one, hides that object from callers that would otherwise reach through it, and meets the rule. The namespace case rests on a module that already groups functions, so in a language whose functions must belong to a class a class of static members is where functions live and meets the rule. A namespace class also meets it where it is forced on the code or serves as more than a namespace — a class that a library or framework reads by its name or receives as an object, such as an inner options class, a class that another class extends or that a declaration or type argument names as a type, a static routine that integrates with an API an existing library defines, or a decorated class, which one tool rule exempts by option — and where the project context documents such a tolerance, since rewriting any of these as module-level functions and constants changes what the library, the subclass or the type declaration reads. The rule judges the units a change adds, so a routine kept under a name the code already declared, whose body forwards to a replacement so that existing callers go on working, is outside it, whether the change leaves its declaration in place or moves it and whether or not it carries a deprecation marker. Whether to extract small named units is contested. One position holds that a well-picked routine name is a summary of multiple lines of code, so extracting named pieces lets a reader explore the high-level view first and go deeper by opening the called routines; the other holds that an abstraction removes information from where it is used and must provide sufficient benefit, that simple code has no unnecessary levels of abstraction, and that wrapper classes add cognitive complexity without structural improvement. The positions separate on whether the unit's body holds more than its name and signature already say: a body of several lines or steps is the summary the first position defends, and a body that is one call on the unit's own parameters, or a class of nothing but static members, is the unit without benefit the second names. The rule does not decide how far a longer routine is split into smaller ones.

## Validator
In the hunk's added lines, find each added routine whose body is a single call, returned or not, and each added class or type declaration. For a routine, compare the call with the signature: go on only when the call passes every one of the routine's parameters, a receiver the routine declares among them not counted, unchanged, in the same order, with no other argument, on no object the routine's own instance holds, and the body holds nothing else — no check, conversion, default, adjusted type, lock, log or error handling. Open the routine's declaration and skip it when it overrides an inherited method, implements an interface or trait member, is a constructor passing its parameters to a parent's constructor, is overridden by a subclass or replaced by a test, carries a decorator, annotation or attribute that wraps it with behaviour or registers it, or is an entry point, a test or a handler that a runtime, framework or test runner calls by name. Skip a routine whose signature line is hunk context rather than an added line, whose name a removed line of the hunk declares, or that carries a deprecation marker, since each keeps an earlier name working for existing callers. Open the routine's callers and the routine it calls, and skip it when any caller cannot call that routine directly because it or its type is private to the routine's module or is kept out of a public interface. For a class or type, skip it in a language whose functions must belong to a class; otherwise go on only when it extends nothing, implements no interface or trait, and its members are all static routines and constants with no receiver, or its one member is a constructor that stores no field; open its usages and skip it when another class extends it, a declaration or type argument names it as a type, a library or framework reads it by its name or receives it as an object, it carries a decorator, a static routine on it integrates with an API an existing library defines, or the project context tolerates it. Validator question: **Does the hunk add a routine whose whole body passes its own parameters, unchanged and in order, to one other routine that all its callers can already call directly, or, in a language with module-level functions, a class used only as a namespace for static members or holding only a constructor that stores no field?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-14`, severity minor, `file`, `symbol`, `code` = the added routine's signature and its one-call body, or the class declaration with its static members or its constructor, quoted verbatim from the diff, `fix` = in the file's language, the callers calling the forwarded-to routine directly with the added routine removed, or the class's members rewritten as module-level functions and constants, or its constructor as one standalone function, `rationale` = the routine it forwards to and that every caller can already call it, or that the class holds no instance state and serves only as a namespace).
