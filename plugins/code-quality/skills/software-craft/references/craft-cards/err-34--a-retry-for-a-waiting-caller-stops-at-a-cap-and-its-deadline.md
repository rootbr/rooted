# A retry made for a waiting caller stops at a finite cap on attempts or total time and at the caller's deadline, so the failure reaches the caller

## Thesis
Every loop, decorator or policy that repeats a failed call while a caller waits for its result has a finite cap in effect on the number of attempts or on their total duration, and, where the caller has a deadline, stops retrying once that deadline passes, however many attempts remain, so that the failure reaches the caller. A loop whose only exit is success, a retry decorator or policy left on a default that retries forever, and a configured cap that the stop condition can never reach, such as a negative maximum that the attempt count is compared with for equality, each break the rule. The rule asks for a finite cap, not for a particular number.

## Rationale
In a study of 70 retry-related incident reports from 8 open-source applications, 13 issues were retry attempts conducted endlessly, without a cap on their total number or duration, and infinite retry attempts can cause jobs to hang and even crash the application with out-of-memory errors. Some of those retries had no cap at all; in others a configuration made them infinite: a job gave up retrying only when the attempt count equalled the configured maximum, which never happened once the maximum was set to a negative value. A retry library may default to no cap: one documents its default behavior as retrying forever without waiting when an exception is raised, and with a stop condition set it raises an error to the caller when the function fails its final time. The caller waits for all attempts together: in a study of 156 timeout bugs in 11 cloud server applications, an RPC client's default of 45 retries, with a 20-second timeout on each retry, made the client wait 900 seconds before it was notified of the job failure, and the fix adjusted the retry number to 3 so that the client could detect the failure in a more timely fashion; excessive retries waste resources, prolong the execution time and slow down the whole system. One RPC framework's retry design applies the call deadline across all attempts, so that the call fails once the deadline passes regardless of how many attempts were configured or attempted, and requires the maximum number of attempts to be specified as an integer greater than 1, treating values greater than 5 as 5. In one language, an endless loop that performs blocking I/O but never checks its cancellation signal is impossible to cancel, and a deadline reaches running code through that signal, which is closed when the deadline expires. A security verification standard asks that, where retry logic is implemented, the documentation specify retry limits, delays and back-off algorithms, and that for synchronous HTTP request–response operations it mandate short timeouts and either disable retries or strictly limit them to prevent cascading delays and resource exhaustion. The cap is a chosen value rather than the smallest one: the same timeout study found eight cases where, without a sufficient number of retries, jobs eventually failed, among them a table deletion whose retry number should be multiplied for a large table, for example to ten times that for a normal-sized one, because each retry deletes only a limited number of columns; and the retry study found attempt tracking that capped retries below the configured value, a counter incremented twice that halved the configured maximum.

## Example
```go
bad:  for attempt := 0; ; attempt++ { // config MaxAttempts: -1 means no limit
          if err = send(ctx, req); err == nil { ... }
          sleep(ctx, backoff(attempt))
      }
good: for attempt := 0; ctx.Err() == nil; attempt++ {
          if err = send(ctx, req); err == nil || attempt+1 >= maxAttempts { return err }
          sleep(ctx, backoff(attempt))
      }
      if err == nil { err = ctx.Err() }
      return err
```

## Limits
The rule is contested for a loop that no caller waits on. A loop that keeps a connection open in the background may retry until it succeeds, provided its delay is capped and jittered: one RPC framework's connection-backoff protocol repeats the connection attempt until it succeeds, backs off exponentially up to 120 seconds with a jitter of 0.2, and requires an alternative algorithm to disperse backoffs started at the same time and not to attempt connections substantially more often. What separates the cases is whether a caller's wait depends on the loop beyond the caller's own bound: in that framework the reconnecting is hidden from application code, a call issued while the channel is in transient failure should by default fail immediately, a call that opts to wait for the connection should still fail when its deadline is reached, and a retry made within a call has its attempt limit and the call's deadline across all attempts. A retry that runs while a caller waits is therefore capped, and a background reconnect loop whose callers fail immediately or at their own deadline is outside the rule when its delay has an upper bound and jitter. The rule fixes no number of attempts: too many retries delay the failure the caller waits for and too few fail jobs, so the cap is a value chosen for the call, and for a value read from configuration the rule asks only that no configured value make the stop condition unreachable. Which failures are retried, whether the call is safe to repeat, the delay between attempts, the layer at which the retry sits, and whether a substitute result may stand in for the failure after the last attempt are judged by their own rules. A loop that the project context names as intentionally unbounded rejects the finding.

## Validator
Grep the added lines for an endless loop (a while on a true constant, a bare loop or for, a for with an empty condition), a retry decorator, wrapper, policy or backoff helper, a retry or attempt counter being incremented, and a maximum-attempts or retry-limit setting given a negative, null, none, infinite or maximum-integer value. For each hit, open the file and decide whether the code repeats a failed call while a caller waits for its result: a failed attempt at a remote or blocking call leads to another attempt on a path that returns to a caller. Find what stops it: an attempt count compared with a finite maximum, an elapsed-time check, a library stop condition, or a deadline that the code sets or requires of every caller, checked before each attempt and observed during each delay; a cancellation check with no deadline behind it is no cap, since nothing may ever cancel it. Where a library call sets no stop, take the library's documented default, and count a default that retries forever as no cap. A maximum read from configuration counts as a cap unless the stop condition can miss it: an equality test that a negative or zero maximum never meets, or a value such as minus one or infinity that the code or the library documents as no limit. Skip a background reconnect loop that no caller waits on beyond the caller's own bound, its callers failing immediately or at their own deadline, when its delay has an upper bound and jitter, and skip a loop the project context names as intentionally unbounded. Validator question: **Does an added or changed loop, decorator or policy that repeats a failed call while a caller waits run with no finite cap on attempts or total duration in effect (none in the code, a library default that retries forever, or a configured maximum its stop condition can never reach), or keep retrying, by starting an attempt or sleeping before one, after the caller's deadline has passed?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-34`, severity major, `file`, `symbol`, `code` = the loop header, retry decorator, policy construction or maximum-attempts setting quoted verbatim from the diff, `fix` = the same retry with a finite cap on attempts or total duration and a check of the caller's deadline or cancellation before each attempt and during each delay, in the file's language, `rationale` = which call the retry repeats, which caller waits on it, and why nothing stops it: no cap, a library default that retries forever, a configured value the stop condition never reaches, or a deadline the loop does not check).
