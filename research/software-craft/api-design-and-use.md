# Research note — API design and use

Topic `api-design-and-use` of group C. Interfaces, domain `interface`, id prefix `API`. Formulation locators: SW4.1 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.1; SWEBOK V3 ch. 3 §4.1 'API Design and Use'); the 97 Things essays 'The Golden Rule of API Design' (thing 35) and 'Make Interfaces Easy to Use Correctly and Hard to Use Incorrectly' (thing 55).

The canon treats an API as its exported signatures plus statements of their semantics, and asks that it be easy to learn, readable at the call site, hard to misuse, extensible and complete. Its sources are SWEBOK V3 ch. 3 §4.1 (V4 ch. 4 §4.1 not opened), the 97 Things essays by Meyers (thing 55) and Feathers (thing 35), Blanchette's Little Manual, and the book-length forms by Bloch, Meyers, McConnell, Martin and Ousterhout. The openable evidence is almost entirely official documentation and checker rule pages: the Rust API Guidelines, Rust Reference and std policy, Effective Go, the Google Go/TypeScript/Python guides, PEP 8, OpenJDK Javadoc, the TypeScript handbook, the .NET design guidelines, Error Prone, SpotBugs, Sonar, PMD, clippy, go vet/staticcheck, typescript-eslint and Ruff. Research supports only three claims. Call-order and precondition constraints cause misuse that detectors catch poorly (Amann et al. MSR 2019). Required constructor parameters lowered usability (Stylos & Clarke ICSE 2007). Documentation is among the worst API-learning obstacles (Robillard & DeLine EMSE 2011). The sources agree on these points: types should rule out argument swaps and illegal values; a call order should be enforced or rejected, never left to memory; the exported surface should be small; parameters should take general types; absence should be marked in the return type; results that are the point of the call should be kept; shared parameters should stay in the same position across overloads; callers should rely only on the documented contract. They disagree on construction (required data and builders against parameterless constructors and useful zero values) and on concrete against interface return types. They also disagree on command-query separation (against Rust C-INTERMEDIATE), on rejecting invalid input against defining errors out of existence, and on explicit types at module boundaries (typescript-eslint against the Google TS guide). On how broadly to mark results must-use, they disagree only on the default: both sides mark a result whose discard is almost certainly a bug. Thirteen rules are carded. The contested rules without a sourced separating condition, and the rules whose only support is trade books, stay pending. Four candidate rules are already shipped as CODE-02, CODE-06, ERR-07 and ERR-10 and are folded there.

## Formulation layer

I opened the SWEBOK V3 §4.1 text, eight 97 Things essays and the aposd-vs-clean-code discussion, and I read Blanchette's Little Manual of API Design in full. The manual is a PDF kept in the papers-we-love repository. SWEBOK §4.1's list of criteria (easy to learn and memorize, readable code, hard to misuse, easy to extend, complete) matches the manual's chapter 2, so the manual is the closest openable form of the formulation SW4.1 follows. I also opened the official documentation that covers the topic's sub-rules: Rust API guidelines, Rust core Result docs, Effective Go, Google Go decisions and best practices, Go spec, PEP 8, Python stdtypes, TypeScript handbook, Google TS guide, .NET Framework Design Guidelines, the JDK Optional source and Software Engineering at Google ch. 1 (Hyrum's Law). These are quoted as fetched. The main canon books (Bloch's OOPSLA 2006 talk-paper and Effective Java, Meyers' Effective C++ Item 18, Code Complete, Clean Code, APOSD, The Pragmatic Programmer, Design Patterns) and SWEBOK V4 §4.1 could not be opened and are recorded as marked paraphrases. Stylos & Clarke (ICSE 2007) was fetched as an abstract through the neverworkintheory bibliography. The factory-pattern and method-placement studies have relayed titles only. The canon disagrees in several places: required constructor parameters and builders (Bloch, Rust C-BUILDER) against property-based create-set-call (Blanchette §4.11, Stylos & Clarke's result); static factories against Ellis et al.; accept-interfaces-return-concrete (Google Go) against returning the interface (Effective Go 'Generality'); command-query separation against returning intermediate results (Rust C-INTERMEDIATE); fail fast and validate (Rust C-VALIDATE, Bloch) against Postel and 'define errors out of existence'; how much an interface must be documented and whether mocking reshapes interfaces (Ousterhout against Martin, and Feathers against the Go guides). Quotes from the PDF and from HTML sources have ligatures, line-break hyphenation, markup and doubled spaces normalized.

## Reception layer

Static-analysis tools in all five languages check whether a caller uses a function's result, but they disagree on how far the check should reach. Error Prone treats @CheckReturnValue as a default-on ERROR and allows a package-wide default. The Rust std policy allows #[must_use] only where ignoring the result is "almost certainly a bug", and clippy's must_use_candidate is off by default (pedantic) with "many false positives". Go vet only checks a fixed list and has no way to declare must-use. Python has only opt-in checks for specific types, and the asyncio documentation shows fire-and-forget can itself be a documented misuse. Four positions are openly contested between named sources: (1) return concrete or abstract types (PMD LooseCoupling and Sonar S1319 against Error Prone PreferredInterfaceType and Google Go's "return concrete types", which Effective Go contests in turn; on parameter types all sources agree: use the most general type); (2) Go functional options (Uber) against option structs (Google); (3) a separate builder (Rust API guidelines) against matklad's builder lite; (4) explicit types at module boundaries (typescript-eslint) against Google TS ("not a general requirement"). Stylos and Clarke (ICSE 2007, abstract fetched via the neverworkintheory GitHub source) found that required constructor parameters were less usable, which limits any card that forces valid construction through required arguments. Several checks that sound like canonical rules are off by default: InconsistentOverloads, PreferredInterfaceType, and unified-signatures ("too opinionated to be recommended"). WebSearch was exhausted and HN, Lobsters and the practitioner blogs on commandcenter.blogspot.com and dave.cheney.net were not reachable, so the thread-level and 2024–2026 freshness checks could not be run. The Ellis et al. factory study and Bloch's API talk appear only from memory and are marked unfetched.

## Evidence layer

Most of the evidence for API design and use is official documentation and static-analysis rule pages, all opened through raw.githubusercontent.com and checked quote by quote against the downloaded text. The sources are the Rust API Guidelines, the Rust Reference and core::result docs, Effective Go, the Google Go, TypeScript and Python (PEP 8) guides, OpenJDK Javadoc, the TypeScript handbook, Python typing docs, the .NET design guidelines, and the rule pages of Error Prone, SpotBugs, Sonar, PMD, clippy, go vet and typescript-eslint. The research items come only from what neverworkintheory's bib files and review posts carry: Stylos & Clarke ICSE 2007, Robillard & DeLine EMSE, Amann et al. MSR 2019, Brun et al. TOSEM 2022, Fischer & Hanenberg DLS 2015, and Hanenberg's two typing studies. The Ellis/Stylos/Myers factory study, Stylos & Myers on method placement, Piccioni et al. and Myers & Stylos are relayed only by title or by a description of their method, so they state no finding. The argument-selection-defect research (Rice et al. OOPSLA 2017) is unfetched, and SWEBOK V4.0 §4.1 and CWE-252 could not be opened. Four disagreements need care. (1) Return types: Go's 'accept interfaces, return concrete types' goes against PMD LooseCoupling, Sonar S1319 and Effective Go's 'Generality'. (2) Construction: Stylos & Clarke found programmers more effective with parameterless constructors, which goes against 'require mandatory data at construction'; Effective Go's useful-zero-value guidance sides with them. (3) Explicit return types: typescript-eslint asks for them, while the Google TypeScript guide leaves them to the author, and Hanenberg 2010 found no effect of static types on development time. (4) Must-use marking: clippy's must_use_candidate and Error Prone's set.add example show that not every result must be used, and SpotBugs PZLA keeps null for 'no answer' as distinct from an empty result.

6. **A call does not discard a returned value that is the call's only effect or that the API documents the caller must keep, call or release** — A statement that calls an operation and drops what it returns is a defect in two cases. The first is when the operation changes nothing and hands back a new value: a method on an immutable value, a lazy sequence adapter, a formatted string or a constructed error. The second is when the API's documentation puts an obligation on the returned value: a cleanup function to call, a resource to close, a task to keep referenced.
