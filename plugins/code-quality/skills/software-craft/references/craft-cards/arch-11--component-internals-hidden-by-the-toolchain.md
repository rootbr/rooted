# A package, module or build target that a change adds for its own component's use is placed where the toolchain hides it from other components, such as an internal directory, an unexported package or a private build target, and, where its toolchain takes a declaration of public parts, the component names them explicitly rather than exposing everything by a blanket default

## Thesis
A package, module or build target that a change adds, and that only its own component uses, is placed in a hidden area whose boundary the toolchain enforces: a directory named `internal`, a private module at the root of the compiled unit whose items are public inside it, a package the module declaration leaves unexported or exports only to named modules, a build target at private or allow-listed visibility, or a path left out of the package's entry-point map. Where the toolchain takes a declaration of public parts, such as a module declaration's exports, a target's visibility or an entry-point map, the component's public interface is the set of packages, targets or entry points it lists explicitly, and its package-wide default visibility is private or an allow-list rather than public; where the toolchain hides by directory placement, the public interface is what the component keeps outside the hidden area. An entry-point map lists each public subpath one by one while the package has few of them; for a package with many subpaths, a pattern over the public folders with each private subfolder mapped to nothing is the documented alternative.

## Rationale
The toolchain checks the boundary at the point of use. Code in or below an `internal` directory is importable only by code that shares the import path above that directory. A target fails to build during the analysis phase when it violates the visibility of one of its dependencies. A public member is inaccessible outside its module unless its package is exported and the user reads that module. Once an entry-point map is defined, every other subpath of the package is encapsulated and an import of it raises an error. Because other components cannot import a package in the hidden area, its owner is free to refactor its API and move it without breaking external users. Declared visibility helps other developers distinguish the public API from the implementation details and helps enforce structure as the workspace grows, while under a public default the risk of inadvertently creating public targets increases as the codebase grows. The design principle behind both is encapsulation and information hiding, which makes the internal details of an abstraction inaccessible to external entities, together with a component defined by a public interface known to its clients and separate from the details of how it is realized. A language platform's own base module follows the practice: every package it exports to all modules is a standard-API package, and every internal package it exports goes only to a named list of modules.

## Example
```go
bad:  // example.com/app/cache, imported only by example.com/app/server
      package cache

      func Get(key string) []byte { return nil }
good: // example.com/app/internal/cache, importable only from within example.com/app
      package cache

      func Get(key string) []byte { return nil }
```

## Limits
A package that other components are meant to depend on is one the component chooses to expose and support for external use, so it belongs in the public interface; the hidden area is the initial home of a supporting package. A public default visibility may be convenient for prototyping or in a small codebase, and the build's visibility check may be switched off for prototyping, though not for production use in submitted code. An entry-point map is not a strong encapsulation, because loading a file of the package by its absolute path still succeeds; the map provides more reliable guarantees about the package's interface for tools and when handling semantic-version upgrades. Where the toolchain offers no hidden area for a whole package or module and hides parts only by a modifier on each type or member, scoped to the unit compiled together, such as an assembly or a set of files compiled together, hiding is set per type and member and falls outside this rule, which reaches directory placement, module declarations, private root modules, build files and entry-point maps. Where the project declares no module, build-visibility or entry-point boundary for the component and its toolchain enforces none by directory placement or by a private module at the root of the compiled unit, the placement falls outside this rule: on a class path without module declarations every package is exported, and in a source tree whose packages are all importable a leading underscore is only a weak indicator of internal use.

## Validator
Grep the hunk for added files, for a new package clause, for a public default or target visibility in a build file, for an unqualified export in a module declaration, and for an entry-point map or a wildcard subpath pattern in a package manifest. For each package, module or build target the change adds, open its importers and dependents across the repository, list the components they belong to, and read the change description and the part's own documentation for an intent to offer it to other components. Where the project declares a module, build-visibility or entry-point boundary for the component, or its toolchain enforces one by directory placement or by a private module at the root of the compiled unit, trace where the added part sits: inside the toolchain-enforced hidden area (an `internal` directory, a private root module, an unexported or friend-only package, a private or allow-listed target, a path outside the entry-point map) or at a path every component can import. Where the project declares no such boundary and its toolchain enforces none by directory placement or by a private root module, or where the toolchain offers no hidden area for a whole package or module and hides parts only by a modifier on each type or member, the placement is outside this rule and the answer is no. Check whether the change sets a package-wide public default visibility, or adds a subpath pattern that also exposes the package's private folders. Validator question: **does the change place a package, module or build target where every other component can import it although only its own component uses it and neither the change description nor the part's documentation offers it to other components, or set a public default visibility or a subpath pattern that exposes private folders?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-11`, severity minor, `file`, `symbol`, `code` = the added package clause, import path, visibility line or export entry quoted verbatim from the diff, `fix` = the part moved into the hidden area, in the file's language: the package under an `internal` directory, the target narrowed to private or a named allow-list, the export removed or qualified to named modules, the module made private at the root of the compiled unit, or the subpath left out of the entry-point map, `rationale` = the components that import the added part and the hidden area the toolchain offers for it).
