# Research note — Contracts, assertions and invariants

Topic `contracts-assertions-and-invariants` of group C. Interfaces, domain `interface`, id prefix `API`. Formulation locators: PP 'Design by Contract' (The Pragmatic Programmer, 20th anniversary ed., topic 23) with 'Assertive Programming' (topic 25); SW4.4 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.4; SWEBOK V3 ch. 3 §4.4 'Assertions, Design by Contract, and Defensive Programming'); CC8 (Code Complete 2nd ed. ch. 8 'Defensive Programming', §8.2 'Assertions').

The canon agrees on the core. The locators are Pragmatic Programmer topics 23 and 25, SWEBOK V3 Construction §4.4 (the openable stand-in for the V4.0 §4.4 text that could not be opened) and Code Complete §8.2. A routine's contract is its preconditions, postconditions and invariants. A type's invariant holds after construction and across every public operation. A subtype may require no more and promise no less than the type it replaces. An assertion states a condition that can only fail through a bug: it is not error handling and must have no side effects. Standards, language documentation and tool rules carry the mechanical core. Assertions can be switched off (Python -O, Java without -ea, Rust debug_assert! in optimized builds), so a side effect inside one is lost (CERT EXP06-J, Sonar S3346, SpotBugs ASE, clippy debug_assert_with_mut_call, Ruff RUF018). An assertion on a constant either checks nothing or vanishes (Pylint W0199, Sonar S5905/S5914, clippy assertions_on_constants, Ruff B011, Error Prone AssertFalse). An assertion on a condition that can fail in normal operation is a weakness (CWE-617, Ruff S101, Bandit B101, the Rust book, Guava's conditional-failure taxonomy). An override must not strengthen a precondition or weaken a postcondition (Jakarta Bean Validation, PEP 316, the Liskov–Wing abstract, Sonar S2638, mypy), and Dietrich et al. count 1,368 strengthened preconditions in Java overrides. The industry splits on four points. First, whether assertions stay on in production: PP, the Rust docs and Chromium say yes; SWEBOK V3, OpenSSF and the Linux kernel disagree. Second, whether a debug-only assertion should also be handled: SQLite and the kernel say yes, Chromium says no. Third, strict versus forgiving contracts. Fourth, assertions as such, which the Go FAQ rejects as a crutch for missing error handling; Google's Go style still prescribes invariant checks that stop the program. The evidence on defects is mixed. Kudrjavets 2006 and Casalnuovo 2015 found fewer faults where there were more asserts. The Casalnuovo replication, as Dietrich et al. report it, found no evidence of an effect, and Catolino et al. tie assertion density to team experience. The cards therefore rest on fault detection and on the documented behaviour of each language's mechanism, not on a claim that assertions reduce defects. Loop invariants, preconditions the caller can check, and an assertion-density threshold have formulations but no openable source that states them as rules.

## Formulation layer

The canon agrees on the core of the contract: preconditions the caller must meet, postconditions the routine guarantees, and a class invariant that every constructor establishes and every public operation preserves. Sources that say so include The Pragmatic Programmer (Topic 23), SWEBOK V3 Construction §4.4 and SEMM §1.4, Meyer's OOSC, PEP 316, the Rust book and Guava. They also agree that an assertion checks something that should never happen, is not error handling, and must not have side effects (PP Topic 25, CC §8.2, CERT EXP06-J, PEP 316). Both SWEBOK V3 and the Pragmatic Programmer could only be opened in part. SWEBOK V3 (both sections) and every official document, style guide, CERT rule and 97 Things essay were fetched from GitHub. The Pragmatic Programmer, Code Complete, OOSC, Effective Java, Programming Pearls, APOSD ch. 10, the SWEBOK V4 text, Oracle's 'Programming With Assertions' and the Liskov–Wing paper could not be opened, so those items are paraphrases from memory and must not be a card's only anchor. The canon splits on four points. (1) Leaving assertions on in production: PP says yes; CC §8.2, SWEBOK V3 §4.4, Rust debug_assert! and Swift assert say they are compiled out, and Java and Python -O disable them. (2) Asserting public-method arguments: SWEBOK V3 §4.4 says assertions are often used to check input values, while the JLS (via CERT MET01-J), the Google Python style guide, Sonar S4274 and Ruff S101 say no. (3) Checking preconditions again inside the routine: Meyer's Non-Redundancy principle says never, CC's 'assert and handle anyway' says do. (4) Strict versus forgiving interfaces: PP and Rust C-VALIDATE favour strict, APOSD ch. 10 favours defining errors out of existence. The Go FAQ rejects assertions outright, and Ousterhout holds that a contract cannot be stated in code. Software Engineering at Google and Google's eng-practices yielded nothing on contracts.

## Reception layer

Static-analysis tools agree on one point. Because assertions can be switched off (Python -O, Java without -ea, Rust debug_assert! in release builds), nothing the program needs may sit inside an assertion. Sonar S3346, SpotBugs ASE_ASSERTION_WITH_SIDE_EFFECT, clippy debug_assert_with_mut_call, Ruff RUF018, Ruff B011, Error Prone AssertFalse, the Chromium checks guide and the C++ working draft's contract evaluation semantics all say so, and a local run in Python, Java and Rust reproduced the effect. The contested ground is what to do when an assertion fails and whether checks stay on in production. TigerBeetle's TIGER_STYLE, Chromium (prefer CHECK, do not handle DCHECK failures) and Rust's always-on assert! favour crashing. The Go FAQ and Effective Go (no assertions, let servers keep running), the Linux kernel (WARN_ON_ONCE plus recovery code, never BUG) and SQLite (ALWAYS/NEVER: assert in debug builds, handle in release) favour staying up. Code Complete's 'assert, then handle the error anyway' is disputed head-on by Chromium. A second dispute is whether a public precondition may be an assertion: Sonar S4274, Ruff S101, Bandit B101 and the Google Python guide forbid it where asserts can be disabled; the Rust book, C-VALIDATE and TigerStyle allow it where checks are always on; the Guava taxonomy reconciles the two by context. Substitutability is checked mechanically only in part: Sonar S2638 checks nullability annotations and override signatures, and mypy checks contravariant parameters and covariant returns; TypeScript deliberately leaves method parameters bivariant. Hacker News, Lobsters, named-practitioner blogs outside GitHub, 2024–2026 surveys, the Oracle assertion guide, the CERT EXP06-J page, NASA's Power of Ten and the C++26 contract objections could not be opened (no WebSearch budget; hosts denied). They are recorded as unfetched and must not anchor a card. The assertion-density studies (Kudrjavets 2006, Casalnuovo 2015) are relayed only, and Catolino 2019 (fetched) raises team experience and ownership as a confound.

## Evidence layer

Of the 69 items, 66 were opened with curl from raw.githubusercontent.com, 1 is relayed (the orchestrator's search snippet for Kudrjavets 2006) and 2 record searches that found nothing. The papers came through GitHub-hosted copies (Hoare 1969 in papers-we-love, the Dietrich et al. ECOOP 2017 preprint, the Catolino et al. ICSME 2019 PDF) or through GitHub-hosted metadata dumps that carry the abstracts. Standards, language documentation and tool rules agree on four points. Assertions can be switched off (Python's -O, the JVM's default without -ea, Rust's debug_assert! in optimized builds). Assertion expressions must have no side effects (CERT EXP06-J, Sonar S3346, SpotBugs, clippy). An assertion must be able to fail (Pylint, Sonar S5905, Ruff B011, clippy). An override may not strengthen a precondition or weaken a postcondition (Liskov–Wing, Jakarta Bean Validation, PEP 316, Sonar S2638, mypy); Dietrich et al. count 1,368 strengthened preconditions in Java overrides, and TypeScript checks parameter contravariance only for function-syntax types. The sources disagree on three points: (1) whether a disableable assertion may check a public method's arguments: MET01-J quoting JLS §14.10, Sonar S4274, Ruff S101 and the Google Python guide say no, while SWEBOK V3 §4.4 and the deferred PEP 316 accept contract checks that run only while debugging; (2) whether a contract violation should panic: the Rust book says yes, while the Go FAQ, Effective Go and the Uber guide advise against it; (3) whether asserts reduce defects: Kudrjavets 2006 and Casalnuovo 2015 found fewer faults where there were more asserts, Dietrich et al. report that the Casalnuovo replication found the opposite and no evidence of an effect, and Catolino et al. describe the same replication without a reversal and tie assertion density to team experience. I could not open SWEBOK V4.0 ch. 4 §4.4, JLS §14.10, the Oracle assertion guide, the Counsell et al. 2017 or Kochhar & Lo 2017 abstracts, or the body of the Liskov–Wing paper. No empirical study tests loop-invariant annotations or side-effect-free assertions, so those rules rest on Hoare 1969, Furia et al. 2014, standards and tool documentation.

## Spine — candidate rules in source order

1. **A routine's contract consists of the preconditions its caller must meet, the postconditions it guarantees and the invariants it keeps** — Design by contract attaches three kinds of condition to each routine. Preconditions must hold before a call and are the caller's obligation. Postconditions are guaranteed once the call completes successfully and are the routine's obligation. Invariants persist across the call. A caller that meets the preconditions is owed the postconditions, and stating them is the most rigorous way to tell a caller how to use the routine. The definition has no check of its own on a diff.

2. **A type's invariant is established by every constructor and preserved by every public operation, so no caller can create or leave an instance that breaks it** — Some types are correct only while a condition over their state holds, such as a range, an ordering, a relation between two fields or a non-empty collection. For such a type, every constructor or factory establishes or checks the condition before the instance can be used. Every public method leaves the condition true when it exits, including when it exits by signalling an error. Only the type's own non-public code may break the condition, and only for a moment. A public setter, an exposed mutable field or a constructor path that skips the check lets callers produce instances that the type's other operations, written on the assumption of the invariant, will mishandle. The rule covers state with one owner; invariants of state shared between threads belong to concurrency correctness.
