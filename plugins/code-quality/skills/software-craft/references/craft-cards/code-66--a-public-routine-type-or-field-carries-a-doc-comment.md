# A public or exported routine, type or field carries a doc comment, unless it is a marked override that keeps its parent's contract or a simple member its language's convention or linter configuration exempts

## Thesis
Every item in a public or exported interface (a routine, a type, a field, and a module or package where the language's convention asks for a module-level doc comment) carries a doc comment in the language's documented doc-comment form, the form its documentation tools extract, placed where that convention puts it. The doc comment gives a caller what they need to use the item without reading its code: what an instance of a type represents or provides, what a routine returns or, for a routine called for its side effects, what it does, and what an exported field or grouped declaration means, which the convention may let the enclosing type's or group's doc comment, a comment on the item's own line or a comment heading its group explain. A comment that merely restates the item's name, a placeholder, or an ordinary implementation comment in place of the doc-comment form does not satisfy the rule. Two kinds of item may go without one: an override that the code explicitly marks as an override and that does not materially refine its parent's contract, whose documentation is found in the parent; and, where the language's documented convention or the project's documentation-linter configuration grants that exemption, a simple, obvious member, such as a plain getter, when there really and truly is nothing worthwhile to say beyond its name. Neither exemption covers relevant information a typical reader might need: an override that materially refines its parent's contract or has details to add, such as additional side effects, carries a doc comment with at least those differences, and a member whose name uses a term a typical reader may not know is documented. Items below the public interface are outside the rule.

## Rationale
Doc comments are extracted into the reference documentation that callers read (a documentation site, a command-line lookup, the editor), so they should be written for anyone using the code. That documentation shows the doc comments of public items to programmers who want to know how to use the code rather than how it is implemented. Items without documentation can be difficult for users to understand how to use properly: callers spend extra time reading and understanding the source code, and they are more likely to make mistakes that lead to bugs when the intent or the error handling of an API is not clear. A field study of developers at one company learning new APIs, which collected through surveys and interviews the opinions and experiences of over 440 professional developers, found that some of the most severe obstacles pertained to the documentation and other learning resources, and named documentation of intent as one of five factors to consider when designing API documentation. Backward-compatibility guarantees apply only to public interfaces, so users need to tell public from internal ones; one convention considers documented interfaces public, unless their documentation declares them provisional or internal, and assumes every undocumented interface internal. A comment that just restates the name, or the parameter name and type, adds no information, which is why it does not count. The two exemptions drop only comments with nothing to carry: the documentation of a marked override can be found in its parent, the common practice being to document a method on the parent and not on the overriding method, and the accessor exemption holds only when there is really and truly nothing worthwhile to say beyond the name.

## Example
```java
bad:  public long balance(String accountId) { ... }
      @Override public String toString() { ... }
good: /**
       * Returns the settled balance in cents; pending transfers are excluded.
       *
       * @throws NoSuchElementException if no account has the given id
       */
      public long balance(String accountId) { ... }
      @Override public String toString() { ... }
```

## Limits
The case turns on visibility. For an item in the public or exported interface the documented conventions agree: doc comments for all functions and classes a module exports and for public methods, a doc comment for every exported name, documentation for every public item, documentation on every visible class, member and record component, documentation of all top-level exports of modules, and a mandatory doc comment on every function that is part of the public API. Below that interface they split. One side asks for documentation below the public interface too, at least where the item is not obvious: doc comments on unexported type or function declarations with unobvious behaviour or meaning, documentation of properties and methods, exported or not, whose purpose is not immediately obvious from their name, a doc comment on every function of nontrivial size or non-obvious logic, a comment that describes what a non-public method does, and an opt-in lint that enforces documentation of private items. The other side asks for less there: doc comments are not necessary for non-public methods, other classes and members carry documentation as needed or desired, sometimes the name and type of a non-exported function or parameter is enough, and the compiler's missing-documentation lint, allowed by default because it can be noisy, and a linter's missing-method-documentation check, scoped to public by default, cover public items only. The rule therefore checks public and exported items only, and a project that enables a private-item documentation check decides the rest. Practice divides on the accessor exemption: one convention makes documentation optional for a simple, obvious member such as a getter, one tool rule skips getters, setters, empty constructors and static constants, one linter allows a missing comment on accessors only when configured to, and other conventions ask a doc comment of every exported name and every public item. Without a documentation-linter configuration the accessor exemption holds only under a convention that grants it; a project's configuration decides the accessor case in either direction: an accessor allowance, an excluded scope or an ignored-name pattern rejects the finding, and a configuration that requires accessor documentation keeps it. An override the code does not mark as one is not exempt: one convention requires a doc comment on an overriding method that lacks the override decorator, and two linter exemptions key on the override annotation or decorator. Outside the rule: test modules, test classes and test methods, which carry a doc comment only when it adds information, such as how the test is run or an unusual setup; symbols exported only to be consumed by tooling; an item the code explicitly hides from the generated documentation, which one compiler lint counts as documented; a module whose convention leaves a module-level doc comment optional; a package documented in another of its files, since a multi-file package keeps its package comment in one source file; and a public item whose declaration the change leaves untouched. The rule judges that the doc comment is present and says more than the item's name; which sections the convention asks for (parameters, return value, errors, panics, examples) and whether the comment still matches the code are outside it.

## Validator
Grep the added lines of the hunk for a declaration of a routine, type, field, constant or module. Open the file and decide for each declared item whether it is in the public or exported interface by the language's own visibility rule: an export keyword or an entry in the module's export list; a public or protected modifier on a member of a type that is itself visible; a capitalized name where capitalization exports; a name without the leading underscore that marks it internal, in no internal module or class; a public modifier on an item whose enclosing modules are public as far as the file and the diff show, an enclosing module declared outside them counting as public. Skip test files, test classes and test routines, items exported only for tooling, and items the code explicitly hides from generated documentation. For each remaining item, look where the language's doc-comment convention puts documentation (immediately before the declaration with no blank line between, or as the first statement of its body; for a field or a member of a grouped declaration, also the enclosing type's or group's doc comment, a comment on the item's own line or a comment heading its group, where the language's convention accepts these as explaining it) for a comment in the documented doc-comment form; for a module or package the change adds, look for its module-level doc comment where the language's convention asks for one, and accept a package comment kept in another of its files. Skip an item with an explicit override marker (an override annotation, decorator or keyword, or membership in an implementation block for an interface or trait) unless the hunk shows it materially refining its parent's contract or adding a side effect. Where the language's documented convention or the project's documentation-linter configuration exempts simple, obvious members, skip a member that really and truly has nothing worthwhile to say beyond its name, such as a getter returning a field or a setter assigning one, unless its name uses a term a typical reader may not know. Where the project context states a documentation-linter configuration, apply its scope within the public interface, its accessor allowance and its ignored names. Count as missing: no comment, an ordinary implementation comment in place of the doc-comment form, a placeholder such as TODO or an ellipsis, and a sentence that only restates the item's name. Validator question: **Does a declaration on an added line put an item in the public or exported interface without a doc comment in the language's documented form that says more than the item's name, the item being neither a marked override that keeps its parent's contract nor an exempt member with truly nothing to say beyond its name?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-66`, severity suggestion, `file`, `symbol`, `code` = the added declaration line, with the name-only, placeholder or ordinary comment above it when one is present, verbatim from the diff, `fix` = the declaration preceded or opened by a doc comment in the language's documented form that says what the item represents, returns or does for a caller, in the file's language, `rationale` = how the item is public or exported and what a caller cannot learn from its name and signature alone).
