# A benchmark consumes the results of the code it measures, keeps setup out of the timed region and leaves the repetition loop to its harness, to limit dead-code elimination, constant folding and hoisting of the measured work

## Thesis
A benchmark hands the result of the measured code to its harness, by returning it, passing it to the harness's sink or computing it inside the body of the harness's keep-alive loop construct, or, inside a loop over the iteration count the harness supplies, which keeps nothing alive, by passing each iteration's result to the harness's sink or the opaque identity wrapper, or, where the platform has neither, by storing or accumulating it into a sink the benchmark keeps, and reads every input the compiler could treat as a constant from mutable harness state or through an opaque identity wrapper applied inside any loop around the call. It runs setup, fixtures and cleanup outside the timed region, in the harness's setup and teardown phases, before or after the harness's keep-alive loop construct, or, around a loop over the iteration count the harness supplies, behind a timer reset after setup and a timer stop before cleanup, and leaves repetition to the harness: the measured call sits in no loop the benchmark writes around it unless every iteration takes a distinct dataset element or a wrapped input and hands its result to the harness's sink or the wrapper.

## Rationale
An optimizing compiler can deduce that a computation whose result is never used is redundant, for instance once it has inlined the call, and eliminate it completely; the benchmark then measures how long it takes to do nothing, and partial dead-code elimination can yield results that look reasonable but still do not measure what was intended. When the result of the computation is the same no matter what, the compiler can fold it and move it outside the harness's loop; reading the inputs from mutable harness state prevents this, and wrapping them in an opaque identity tries to keep the compiler from optimizations that would be unrealistic in real-life use. Looping inside the benchmark in the hope of minimizing the overhead of calling the measured method lets the optimizer merge the loop iterations: the loop is heavily unrolled and pipelined and the measured operation hoisted out of it, so the larger the repetition count, the lower the perceived cost, down to 1/20 ns per addition, well beyond what hardware can actually do. A loop the benchmark writes still measures every call in full when each iteration takes a distinct input and sinks its result, while saving each result into one variable lets the compiler evaluate only the last call, accumulating lets software pipelining merge otherwise distinct calls, and an input wrapped once outside a loop over a run-time iteration count leaves the call loop-invariant, so the compiler can hoist it and leave nothing to time. Setup and cleanup left in the timed region are included in the overall time measurement and silently skew the result, while the harness excludes from the timing the setup and cleanup it runs in its setup and teardown phases or before and after its keep-alive loop construct; around a loop over the iteration count the harness supplies it can only time the entire benchmark function, so setup and cleanup there count unless the benchmark resets the timer after setup and stops it before cleanup. A static-analysis study of the benchmarks of 123 open-source systems, all written for one harness, found each of five bad practices with that harness prevalent, among them not using a returned computation (dead-code elimination), using accumulation to consume values inside a loop (loop optimization), a final primitive as benchmark input (constant folding) and running fixture methods for each invocation (harness overhead), and its experiments found that bad practices often significantly impact the benchmark results.

## Example
```java
bad:  static final int SIZE = 42;
      @Benchmark public void measure() {
        int[] data = buildData(SIZE);
        for (int i = 0; i < 1000; i++) { compute(data); }
      }
good: @State(Scope.Thread) public static class Fixture {
        int size = 42; int[] data;
        @Setup public void setUp() { data = buildData(size); } }
      @Benchmark public int measure(Fixture f) { return compute(f.data); }
```

## Limits
A loop over the iteration count the harness supplies is the harness's own repetition protocol; a benchmark uses either that loop or the harness's loop construct, not both. Inside the harness's keep-alive loop construct, arguments to and results from calls written in the loop body are kept alive and need no further sink; this holds only for statements syntactically between the loop's braces, with the loop condition written exactly as the harness specifies, and keeping a value alive blocks dead-code and dead-store elimination, not the folding of a call on literal inputs, so the input clause holds there too. A single result is returned; several results are either merged into one returned value, which suits a relatively heavyweight computation whose merging does not offset the results much, or each handed to the harness's sink. A loop inside the measured routine is part of the measured work; the rule reaches the loop a benchmark writes around the measured call, and a loop whose every iteration takes a distinct dataset element or a wrapped input and hands its result to the harness's sink or the wrapper is no finding. Per-invocation work that should not count as payload belongs in the harness's per-invocation setup level, used with care, since its timestamping and synchronization might significantly offset the measurement, or between a timer stop and a timer start inside the harness's loop. The opaque identity wrapper is best-effort, and the extent to which it blocks optimizations may vary with the platform and code-generation backend. In a benchmark whose result goes unused, a sub-nanosecond time is a clear red flag of dead-code elimination. The result, input and loop clauses guard against an optimizing compiler; where the timed code runs on an implementation that executes every call it is given, a dropped call result, a literal argument to a call or a loop around the call removes nothing from the timing and is no finding, while an operator expression on literals can still be folded there, and the setup clause holds everywhere.

## Validator
Grep the hunk for a benchmark declaration, a harness registration or a timer call. Open each benchmark body the hunk adds or changes, and each interval between paired timer calls. Trace the measured call's result: returned, handed to the harness's sink or produced inside the body of the harness's keep-alive loop construct, or, inside a loop over the harness-supplied iteration count, passed to the harness's sink or the opaque identity wrapper each iteration, or, where the platform has neither, stored or accumulated into a sink the benchmark keeps; or instead dropped, or saved or accumulated across the iterations of a loop the benchmark writes itself. Trace each input of the measured call, inside a keep-alive loop body too, to mutable harness state, a distinct dataset element or an opaque identity wrapper applied inside any loop around the call, or to a literal, a final constant or a value wrapped once outside that loop. Check whether data construction, fixture setup or cleanup runs inside the timed body or interval rather than in the harness's setup or teardown phase, before or after its keep-alive loop construct, or between a timer stop and a timer start; setup before, or cleanup after, a loop over the harness-supplied iteration count is inside the timed body unless a timer reset follows the setup and a timer stop precedes the cleanup. Check whether the benchmark wraps the measured call in a loop of its own, other than a loop over the harness-supplied iteration count or the harness's loop construct, whose iterations do not each take a distinct dataset element or a wrapped input and hand the result to the harness's sink or the wrapper. Validator question: **Does the benchmark drop the measured result, feed the measured call a constant input, time its own setup or cleanup, or repeat the measured call in a loop of its own without sinking every iteration's result?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: PRF-08`, severity major, `file`, `symbol`, `code` = the benchmark line that drops the result, reads the constant input, runs the setup or opens the hand-written loop, `fix` = the benchmark returning or sinking the result, reading inputs from harness state, with setup moved to the harness's setup phase or before its keep-alive loop construct and cleanup to its teardown phase or after that loop, or fenced by a timer reset and stop, and the hand-written loop removed or made to sink every iteration's result, or a hand-timed interval moved into a benchmark harness, in the file's language, `rationale` = which of dead-code elimination, constant folding, loop hoisting or timed setup the benchmark exposes its timing to).
