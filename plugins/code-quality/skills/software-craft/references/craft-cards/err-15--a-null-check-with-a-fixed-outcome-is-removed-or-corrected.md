# A null, nil, None or undefined check whose outcome the routine's own code or a compile-time type already fixes is removed, or changed to test the value it was meant to test

## Thesis
A comparison of a value with the language's absent value (null, nil, None, undefined), a library call that tests a value for it, or an optional-chaining or null-coalescing operator applied to it, is degenerate when its outcome is fixed before it runs. The routine's own code fixes it when the value was just constructed or assigned a value that cannot be absent, when an earlier use on every path to the check would already have failed on the absent value, or when an earlier check of the same value left the path on one of its outcomes. A compile-time type fixes it when the type excludes the absent value, the type checker tracks absent values, and the value was produced inside the type-checked program. A degenerate check is either redundant, and is removed together with the branch its outcome never takes, or incorrect, and is changed to test the value it was meant to test, such as an error result just returned. A check whose outcome only a static type would fix, where that type may not match the runtime value, is a verification and stays.

## Rationale
A comparison whose outcome is fixed is an impossible or a tautological condition, so the branch for the other outcome never runs; an optional chain on a value that is never absent, or a null-coalescing operator whose left side is never absent, is unnecessary in the same way. Such a comparison can be a programming error, especially in control flow related to errors. When an earlier use would already have failed on the absent value, the check and that use disagree about whether the value may be absent: either the check is redundant or the earlier use is wrong. A condition is necessary only when it can evaluate either way, so removing a redundant check, or changing a mistaken one to the value it was meant to test, leaves no condition at that point whose outcome is decided in advance. The compile-time route depends on the type matching the runtime value: a type checker that does not track absent values erases them from the types and cannot tell that a value might be absent, and where the types do not match the runtime behaviour a verdict drawn from them may be inaccurate.

## Example
```python
bad:  if item is None:
          raise ValueError("item is required")
      label = item.name if item is not None else ""
good: if item is None:
          raise ValueError("item is required")
      label = item.name
```

## Limits
The rule is contested, and where the value's presence is established separates the cases. A check is degenerate where the routine's own code, or the compile-time type of a value produced inside the type-checked program, fixes its outcome (the Source entries marked redundant). A check is a verification and stays where the static type it would rest on may not match the runtime value (the entries marked verification): a value typed any or unknown, or of a bare type parameter; a value whose type a cast or type assertion gave it with no runtime check, such as a parsed or received value; an indexed or keyed read that the type system optimistically assumes present; a parameter that callers outside the type-checked code can reach, in a language whose runtime does not enforce type annotations; code not yet accurately typed; and a result from a dependency the code lacks high confidence will meet its real or implied specification. The routine's own code fixes the outcome only while nothing can change the value in between: a variable that a call between its last assignment or check and this check may modify is checked again legitimately, and so is a field or shared variable that another thread can change, such as a re-check after acquiring a lock; whether such a re-check is free of races is concurrency correctness, a reserved specialty outside the rule. A project may intentionally use checks to ensure that runtime values do indeed match their static types, especially in test code; a check carrying a comment that says why it runs despite appearing unnecessary follows the rule, and such a tolerance stated in the project context rejects the finding. An assertion is outside the rule, and so is an impossible-condition check, one that cannot fail unless surrounding code is later modified and that fails with an assertion failure; both are judged by their own rule. Where an earlier use and the check disagree because the value can in fact be absent, the defect is the earlier use, not the check, and is judged by its own rule.

## Validator
Grep the added lines for an equality or identity comparison with the absent value (null, nil, None, undefined), a library call that tests a value for it, an optional-chaining operator and a null-coalescing operator. For each hit, open the file at the enclosing routine and trace the checked value backward along every path that reaches the check: name its last assignment and every use and check of it between that assignment and the check. Mark the outcome fixed when the value was constructed or assigned a value that cannot be absent, when every path reaches the check through a use that fails on the absent value (a member access, a method call or an index that would fail on it), or when an earlier check of the same value returns, throws, raises, breaks or continues on one of its outcomes; or when the value's declared type excludes the absent value under a type checker the project runs with absent values tracked, and the value was produced inside the type-checked code. Clear a mark that rests on the type when the value is typed any or unknown or by a bare type parameter, got its type from a cast or type assertion (parsed or received data), comes from an indexed or keyed read, is a parameter that callers the type checker does not see can reach, comes from a dependency the code does not trust to meet its specification, or sits in a file not accurately typed. Clear any mark when a call or closure between the last assignment or check and this check may modify the value, when the value is a field or shared variable another thread can change (a re-check after acquiring a lock), or when a comment or suppression at the check says why it runs. Skip an assertion and a check that fails with an assertion failure. Skip a check whose disagreeing earlier use is itself the error because the value can be absent there. For a marked check, read the lines just before it for the value it was meant to test: a second error or result variable assigned there while the check names an earlier, already settled one marks a mistaken check. Validator question: **Is the outcome of this added comparison with the absent value, library call that tests for it, optional chain or null-coalescing operator fixed before it runs by the routine's own code, or by the compile-time type of a value produced inside the type-checked code, with no verification case applying?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-15`, severity minor, `file`, `symbol`, `code` = the added comparison, library check call, optional-chaining or null-coalescing expression quoted verbatim from the diff, `fix` = the code without the check, keeping only the branch its fixed outcome takes, or, for a mistaken check, the check rewritten to test the value it was meant to test, in the file's language, `rationale` = what fixes the outcome — the construction, assignment, earlier use or earlier check, or the compile-time type — and, for a mistaken check, the value it was meant to test).
