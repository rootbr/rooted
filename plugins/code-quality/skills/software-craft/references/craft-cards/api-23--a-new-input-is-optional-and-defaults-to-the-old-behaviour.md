# A new input to a published function is added with a default that preserves the old behaviour, and never as a new required parameter

## Thesis
A change that gives a routine of a published interface a new input leaves every call written before the change working and doing what it did. The input arrives as a new field of an options type the routine already takes, as a parameter with a default value, or through a new routine or overload that the old one forwards to, and not as a new required parameter, unless the change ships as a new major version. What a caller gets by not setting the input — the parameter's default, the unset value of the new field, the argument the old routine passes when it forwards — reproduces the routine's behaviour before the change. Where code uses the routine other than by calling it, call compatibility is not enough: for a method that subclasses are meant to override, the input goes into a new method whose default implementation calls the old one; and where adding a parameter, even one that every call may omit, gives a function a type that a function type it fitted before no longer accepts — its old function type, or a callback type that passes more arguments than the function declared — or hands one of those extra arguments to the new parameter, code that holds the function as such a value breaks, so the input goes into an options field or a new function that the old one forwards to. Where clients link against the routine's compiled parameter list without being rebuilt, any added parameter, even one that every call may omit, breaks them, so the input goes into a new overload or routine that the old one forwards to.

## Rationale
Adding a required parameter can break callers at once: a call written before the change does not pass the new argument and fails with an immediate error, and the published compatibility rules of two platforms list adding a parameter to a published method as a breaking change. Under semantic versioning an incompatible change to a public interface takes a new major version, while functionality added in a backward compatible manner takes a minor one. A new major version is hard on callers: they have to find it, learn a new interface and change their code, and some never update, which leaves the maintainer keeping two versions forever. Changing the interface in a compatible way — adding, not changing or removing — is therefore usually better. A new field of an options type is backward compatible almost always, and an options type can grow over time without touching any call site; a new routine that the old one forwards to lets callers move to it at their own pace, and the old routine calling the new one avoids copying code. The value a caller gets without asking carries the old behaviour: the unset field or the omitted argument preserves it so that existing code that does not set the new input keeps working, while changing a value a caller gets by default — a parameter's default, or the value an overload passes on the caller's behalf — can break callers silently, with no immediate error, which can make the fault hard to detect. Calls are not the only use of a signature: the position and expected types of arguments and the conditions under which overridden methods are called belong to the published interface as well, so call compatibility is not enough for backward compatibility.

## Example
```typescript
bad:  export function fetchPage(url: string, timeoutMs: number): Promise<string> { ... }
      fetchPage(url); // an existing call: Expected 2 arguments, but got 1
good: export interface FetchOptions { timeoutMs?: number }
      export function fetchPageWith(url: string, options: FetchOptions): Promise<string> {
          const timeoutMs = options.timeoutMs ?? 30_000; // the timeout every call had before
          ...
      }
      export function fetchPage(url: string): Promise<string> { return fetchPageWith(url, {}); }
      fetchPage(url); urls.map(fetchPage); // existing calls and callbacks keep the old timeout
```

## Limits
The rule reaches the published interface of a library or module, the routines other code depends on. A routine outside it — not exported or public, marked private by convention such as a leading underscore, or documented as private — can change at any time in any way, and in an interface in initial development, versioned 0.y.z, anything may change at any time. A breaking change released as a new major version, or under a new module path, is outside the rule. A field added to an options type is backward compatible almost always, provided its unset value preserves the old behaviour so that existing code that does not set it keeps working. Whether a parameter with a default keeps a change compatible is contested, and how other code uses the signature separates the cases. Where code only calls the routine and is built from source against the new version, a default value for the new parameter delays or avoids the breakage that a required one causes, and existing calls keep working. A caller compiled against the old parameter list and run against the new version without being rebuilt no longer links once any parameter is added, even one that every call may omit; where the interface ships as compiled code that clients link against, the input goes into a new overload or routine that the old one forwards to, or into a field of an options type the routine already takes. Where code uses the signature other than by calling it, call compatibility is not enough. Code that holds the function as a value of a function type it fitted before — its old function type, or a callback type that passes more arguments than the function declared — stops compiling where that type no longer accepts the function with the added parameter, even a parameter that every existing call omits, or keeps compiling while one of those extra arguments reaches the new parameter in place of its default; where either can happen no change to a function's signature is backward compatible, and the input goes into an options field or a new function that the old one forwards to. Adding an argument to a method that subclasses override changes the conditions under which the pre-existing overrides are called, and where methods are told apart by their parameter lists it leaves those overrides overriding the wrong method; there the new method's default implementation calls the old one, so pre-existing overrides and every call to the old method keep working. Where an interface cannot carry a default implementation, the new method goes into a new interface, and the code that receives a value of the old interface checks at run time whether the value also implements the new one.

## Validator
Grep the added lines for a routine signature. For each, open the base version of the file with `git show <base_sha>:<path>` and find the same routine. Set aside a routine that is new in the change; one that is not part of a published interface (not exported or public, marked private by convention, or documented as private); and a change that the diff releases as a new major version, under a new module path, or in an interface versioned 0.y.z. For the rest, list each parameter the base signature lacks and whether it has a default, and each field added to an options type the routine takes. Read the routine body at the base and in the change, name what a caller who does not set the new input gets — the default, the unset field's value, or the argument the old routine passes when it forwards — and compare it with the base behaviour. For a new parameter with a default or one that every call may omit, check whether clients link against the routine's compiled parameter list without being rebuilt (the interface ships as compiled code), whether the routine is a method meant to be overridden (abstract, an interface or protocol method that callers implement, documented as an extension point, or overridden by a subclass in the repository) and whether a function type the old routine fitted — its old function type, or a callback type that passes more arguments than the old routine declared — rejects the new routine or hands one of those extra arguments to the new parameter. Validator question: **Does the change give a routine of a published interface a new parameter without a default, a new input whose unset value changes what an existing call does, or a new parameter on a routine that clients link against by its compiled parameter list, on a method meant to be overridden, or on a function whose new type no longer fits a function type the old one fitted or whose new parameter an extra argument of such a callback reaches?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-23`, severity major, `file`, `symbol`, `code` = the changed signature or options-field line quoted verbatim from the diff, `fix` = the new input as an optional field of the routine's options type or a parameter whose default reproduces the old behaviour, or a new routine that the old one forwards to — for a method meant to be overridden, a new method whose default implementation calls the old one, or, where an interface cannot carry a default implementation, a new interface holding the new method that the receiving code checks for at run time — in the file's language, `rationale` = the existing calls, compiled callers, function values or overrides that the change breaks, or the existing calls whose behaviour the new input's default changes).
