# A type parameter's constraint requires every operation the generic code performs on its values and nothing that code does not use

## Thesis
The constraint on each type parameter of a routine or a type grants every operation the generic code performs on values of that parameter, and the code reaches each of those operations through the constraint, not through a cast or a type assertion to a type the constraint does not name. The constraint requires nothing more: each interface, method, operator or other bound it names is one the code uses on those values, directly, by passing them to code whose own constraint requires it, or by passing them to code that requires it only at run time and fails there on a value without it. On a generic data structure, the declaration carries only bounds that the structure's own code requires or that state what the structure is for. Where the language lets an implementation carry bounds of its own, a general capability such as cloning, equality, ordering, printing, default construction or serialization is bounded on the implementation that uses it, which then applies only to the type arguments that have the capability, and not on the declaration.

## Rationale
A constraint sets limits in two directions: callers may pass only type arguments that satisfy it, and the generic code may use the values only in the ways it permits, so it both defines the set of permissible type arguments and controls the operations those values support. A type parameter with no constraint, or with the one that admits every type, grants only the operations permitted for values of any type. An operation the constraint does not grant is one the body cannot count on, because the values might be of some other type that lacks it: the body then won't work for all the types the parameter could be, and the fix is to restrict the parameter to the types that have the operation. A cast or a type assertion that reaches the operation anyway leaves the set of permissible type arguments as it was, so a caller can still pass a type without the operation and the body does not work for it; a checked cast or assertion compares against the value's dynamic type, known only at run time, and panics or throws there when it fails. In the other direction, the fewer assumptions a routine makes about its inputs, the more widely usable it becomes, so each requirement the code does not use shuts out type arguments the code would handle. The constraint is declared rather than derived from whatever the body happens to do, so that a minor change to the body cannot change it and break code far away that calls it; changing it is a deliberate decision that forces callers to change. Adding a bound to a data structure is, generally speaking, a breaking change, because every user of the structure must start satisfying it; a structure that repeats on its declaration the bounds its generated implementations already carry turns each further generated implementation into a breaking change, where without the repetition it is not one. In one language's checker, a constraint where none is needed can also make the inference of type arguments less successful, frustrating callers.

## Example
```java
bad:  static <T extends Comparable<T>> T longest(T a, T b) {
          return ((CharSequence) a).length() >= ((CharSequence) b).length() ? a : b;
      }
good: static <T extends CharSequence> T longest(T a, T b) {
          return a.length() >= b.length() ? a : b;
      }
```

## Limits
A bound that relaxes a requirement the language puts on every type parameter by default, rather than adding one, requires nothing and passes. A data structure's declaration carries a bound where the declaration refers to a member type that the bound provides, and where the language requires the declaration to repeat a bound that the structure's cleanup routine needs. A bound on a data structure that its definition does not strictly require but that states the behaviour the structure is for, as a reading or writing capability can, is a grey area and passes: it may communicate the intended behaviour better, though it also limits future extensibility, and it is less of a problem than a bound for a capability an implementation can be generated for. The constraint is its owner's to change deliberately, forcing callers to change; a requirement that the interface's documentation or a project context states is kept on purpose is such a deliberate decision and passes. A run-time type test that keeps a working path for type arguments without a capability, or that chooses between behaviours that differ per type, is outside this rule's reach; the rule concerns an operation the code performs on a value as though the constraint granted it.

## Validator
Grep the added lines for a type-parameter declaration: a type-parameter list on a routine, a type or an implementation, a bound written with `extends` or a colon, a `where` clause, a type-variable constructor. Open the file and, for each declared type parameter, list the requirements its constraint names — each interface, trait, method, operator set or base type — and the operations the code performs on values of that parameter: method and property access, operators and comparisons, use as a map key, iteration, and passing a value to a routine or a type whose own constraint requires something. Count a requirement as used when one of those operations needs it, including through a callee's constraint, through a capability a callee requires only at run time, as a serializer whose parameter admits every type does, and, on a type, through any of its methods; where the language lets an implementation carry its own bounds, count a general capability that only implementations use, generated or written by hand, as unused on the declaration. Then look for the reverse: a cast, a type assertion or a dynamic attribute access that reaches on such a value a method or property the constraint does not name, or, in code no type checker runs on, an operation outside the constraint; a type parameter without a constraint grants only the operations permitted for values of any type. Skip a signature that has to match one it overrides or implements, a bound that relaxes a default requirement, a bound a data structure's declaration refers to, that the language requires the declaration to repeat for the structure's cleanup routine, or that states what the structure is for, a run-time type test that keeps a working path or chooses between per-type behaviours, and a requirement the documentation or a project context keeps on purpose. Validator question: **Does a type parameter's constraint name a requirement that no operation of the generic code on its values needs, or does the generic code perform on those values an operation the constraint does not grant?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-44`, severity minor, `file`, `symbol`, `code` = the type-parameter declaration with its constraint, and the cast or call that reaches an operation outside it where there is one, quoted verbatim from the diff, `fix` = the declaration rewritten in the file's language with the unused requirement dropped or moved to the implementation that uses it, or with the used operation added to the constraint and the cast removed, `rationale` = the requirement no operation needs and the type arguments it shuts out, or the operation the constraint does not grant and the type arguments it admits that lack it).
