# A change that alters behaviour reformats only the lines it changes for that purpose, and reformatting, re-indenting or re-wrapping of lines it does not otherwise change goes in a separate change

## Thesis
In a change that adds a feature or fixes a bug, each line the change does not otherwise modify keeps its existing layout, and the lines the change modifies are formatted to the project's standard inside it, following the existing formatting where formatting them by hand would change subsequent lines; where the project enforces a formatter, the lines that formatter re-aligns or re-wraps because of the edit belong to the change. Reformatting, re-indenting, re-wrapping or whitespace edits to the other lines go in a separate formatting-only change that is not intended to change functionality, ideally landed before the functional change.

## Rationale
Major style changes combined with other changes make it hard to see what is being changed, and make merges and rollbacks more complex. A patch that fixes a critical security bug, rearranges a few structures and reformats the code has a good chance of being passed over, with the important fix lost. Some common editors strip trailing whitespace on save, which causes unrelated changes to appear in diffs and commits. Kept apart, the formatting change is a commit whose message states that it is not intended to change functionality, and blame can ignore that revision as if the change never happened, attributing the lines it changed to the previous commit that changed them or nearby lines. Ignoring a revision ignores every change it made, so blame can be instructed to ignore reformatting commits that do not otherwise change functionality, and the separation is what lets the formatting be ignored while the behaviour change stays attributed. The threshold is the line: a patch reformats only the lines it is changing, and where reformatting them by hand would change subsequent lines it follows the existing formatting; where the project's format check runs a formatter over each patch, the patch carries what that formatter does to the region an edited line falls in.

## Example
```typescript
bad:  // fixes the cap and re-wraps the untouched log call
      const rate = Math.min(discount, MAX_RATE);
      log(
        "order", orderId, rate,
      );
good: // fixes the cap; the untouched log call keeps its layout
      const rate = Math.min(discount, MAX_RATE);
      log("order", orderId, rate);
```

## Limits
The separating condition is whether the line is one the behavioural change modifies anyway. A line the change edits is formatted to the standard inside it, as the touched-lines rule asks of a patch unrelated to formatting and as a partial formatter does when it reformats only regions that have changed; that formatter keeps each contiguous reformatted chunk an edited line falls in, so it can also re-wrap neighbouring lines the change does not edit, and its documentation says it is often unable to minimize the changes as carefully as a developer could by hand, so the line threshold is stricter than its output where formatting is by hand. Where the project's format check enforces a formatter, as the compiler project's pre-commit check runs that partial formatter over each patch, the lines the formatter re-aligns or re-wraps because of the edit belong to the change: restoring them fails the check, and no formatting-only change landed before the edit can produce a layout that depends on it. A line the change does not edit keeps its layout, under the policies that try to separate formatting or whitespace changes from functional changes and keep cosmetic changes to unrelated code out of a feature or bug-fix commit. The review guidance's own qualifier is "major style changes", with reformatting the whole file as its example; the line threshold comes from the touched-lines rule, which is stricter. One coding guideline calls fixing style violations while working on a real change "as a preparatory clean-up step" good and otherwise discourages churn for the sake of style; it does not say whether that clean-up shares the commit, and a preparatory formatting commit landed before the functional one meets both it and the separation policies. Formatter documentation recommends, when adopting a formatter, reformatting everything, preferably in one massive commit whose identifier goes into a blame-ignore file; that commit is a separate formatting-only change at whole-codebase reach. How far a formatting-only change reaches is outside this rule: the compiler project's policy and one coding guideline ask to avoid formatting-only churn in code nobody is about to change, while formatter documentation reformats the whole codebase once when the formatter is adopted. The rule covers layout alone: a change that is formatting-only is the separate change it asks for, and renames or moved code are outside it.

## Validator
Grep the hunk for removed and added line pairs that differ only in indentation, whitespace, line breaks, bracket placement or trailing separators; for added lines that end in an opening bracket or a comma or hold only closing brackets; for re-wrapped import lists; and for trailing whitespace added or removed. Open the hunk and confirm the change also alters behaviour: a changed condition, value, computation or control flow; a rename, a move or another edit that keeps behaviour does not count. For each layout-only line, trace whether the behavioural edit modifies that line; a line the change edits, a line re-indented because the change adds or removes the block around it, and a line the project's enforced formatter re-aligns or re-wraps once the edit is applied to the old file belong to the change, while re-wrapping the other lines of an edited statement by hand does not. Skip a change whose diff alters no behaviour; a description that calls the change formatting-only or not intended to change functionality does not exempt a diff that alters behaviour, because blame ignoring that revision would also hide the behaviour change. Validator question: **Does a change that alters behaviour also re-indent, re-wrap, reformat or change the whitespace of a line it does not otherwise modify?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-13`, severity minor, `file`, `symbol`, `code` = the reformatted lines the change does not otherwise modify, quoted verbatim from the diff, `fix` = the hunk with those lines restored to their original layout in the file's language and the reformatting moved to a separate formatting-only change, `rationale` = names that layout edits to untouched lines hide what the behaviour change alters and keep the formatting out of a commit that blame can ignore).
