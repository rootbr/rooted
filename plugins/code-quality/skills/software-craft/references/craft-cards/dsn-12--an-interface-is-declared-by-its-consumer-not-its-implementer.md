# An interface that lets one module use another without depending on its implementation is declared in the consuming module with only the methods that consumer calls, unless the interface is a common protocol that many implementations follow

## Thesis
When one module uses a capability of another through an interface, trait, protocol or abstract base type rather than through the implementing type, the consuming module declares that interface with only the methods it uses, and the implementing module returns concrete types that satisfy it. The interface is introduced once a real use exists, not ahead of one, and is not declared on the implementing side for mocking. The exception is an interface that is the product: a common protocol that many different implementations follow, such as a writer or a hash, which the module providing it declares and exports.

## Rationale
Interfaces generally belong in the module that uses values of the interface type, not the module that implements those values. Declared by its consumer, an interface can be held to the methods that consumer actually uses; the larger an interface, the harder it is to implement and to write code that takes advantage of it, and the bigger the interface, the weaker the abstraction. An implementing module that returns concrete types can add new methods to them without extensive refactoring, and its callers reach every public method and field of the type, not just the subset a pre-chosen interface defines, while they can still pass the concrete value to any code that expects an interface the type satisfies. Where a test of the consumer needs a double, the double implements the consumer's own interface, and the implementing module is tested through the public API of its real implementation rather than through an interface declared on its side for mocking. Without a realistic example of usage, it is too difficult to see whether an interface is even necessary, let alone what methods it ought to contain. In a large system, an interface that lives inside a huge implementation module forces every client to import that module just to reference the interface. Where interfaces are satisfied structurally, a type satisfies an interface by implementing its methods, nothing more, so a consumer declares and uses an interface without modifying the implementing code, which names no base type for it. Where a type must be stated to implement an interface, by explicit subclassing, registration or an implementation declaration that names the interface, the module that writes that statement depends on the module that declares the interface and brings it into scope. Written in the implementing module, the statement makes a consumer-declared interface point the dependency from the implementation to the consumer; where an implementation declaration may sit beside the interface for a type from another module, the consuming module may write it there, and the implementing module then names nothing of the consumer. Explicit subclassing or registration is particularly difficult for library types, whose type objects may be hidden deep in the library's implementation; a structural interface declared by the consumer is satisfied by such a type without an explicit base class.

## Example
```python
bad:  class Store(ABC):  # in storage, beside DiskStore(Store), its only implementation
          @abstractmethod
          def load(self, key: str) -> bytes: ...
          @abstractmethod
          def save(self, key: str, data: bytes) -> None: ...
      def render(source: Store, key: str) -> str: ...  # in report, which calls only load
good: class Loader(Protocol):  # in report; DiskStore satisfies it without importing report
          def load(self, key: str) -> bytes: ...
      def render(source: Loader, key: str) -> str: ...
```

## Limits
Contested. One position declares the interface in the module that uses it, with only the methods the consumer uses, and has the implementing module return concrete types; its evidence is a language project's official code review guidance and a style guide's decisions and best practices. The other position has the producer export the interface when a module's primary purpose is to provide a common protocol that many different implementations must follow, and leaves unexported a type that exists only to implement an interface and will never have exported methods beyond it, its constructor returning the interface value, so that substituting one hash algorithm for another changes only the constructor call; its evidence is the same language's official effective-use guide and the same style guide's best practices. Whether the interface is the product separates the cases: an interface that one consumer needs from an implementation is declared by that consumer with the methods it uses, and a common protocol that many different implementations follow, whose critical behaviours — expected use, edge cases, concurrency — need to be documented centrally and canonically, is exported by the module that provides it. An interface generated from a schema, which defines the boundary between a service and its clients, is such a product, and a product interface may live in a standalone module that holds no implementation, avoiding unnecessary symbols and potential import cycles. Where many modules use the same service and would each declare an identical interface, the providing module may export one, since maintaining mirrored interfaces across many modules can create an unnecessary burden. Where returning a concrete type would require importing a module that already imports the producer, the producer returns an interface to break the cycle, though introducing interfaces to break dependency cycles is often a signal of improperly structured modules. Returning an interface is sometimes acceptable for encapsulation, as with the standard error interface, and in command, chaining, factory and strategy constructions; the finding is where the interface is declared and which methods it holds, not a returned interface alone. An interface used only inside its own module stays unexported, and its place beside its implementations is outside the rule's reach; its methods are still held to the ones that module calls. A project context that names an interface or a module as a common protocol rejects the finding.

## Validator
Grep the hunk for the declaration of an interface, trait, protocol or abstract base type. Open the declaring module, then search the repository for the types that implement or satisfy it and for the code that uses values of its type as a parameter, field or return type, reading the callers of the changed symbols; note which module each sits in and which are tests. Where the interface sits in the module of its only non-test implementation, check whether the code that uses it is in other modules, only in tests, or nowhere yet. Where a consumer declares it, compare its methods with the methods that consumer calls. Before flagging, check whether the interface is the product — a module whose primary purpose is to provide a common protocol that many different implementations follow, an interface generated from a schema, one in a standalone module that holds no implementation, one exported so that many modules using one service do not each declare an identical copy — or whether a producer returns it because returning its concrete type would close an import cycle. Validator question: **Does the hunk declare an interface, trait, protocol or abstract base type in the module that holds its only implementation while the code using it sits in other modules, only in tests or nowhere yet, or a consumer's interface with methods that consumer never calls, where the interface is not the product — a common protocol that many different implementations follow, a boundary generated from a schema, or one interface exported to spare many modules identical copies — and does not break an import cycle?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-12`, severity minor, `file`, `symbol`, `code` = the declaration line of the interface, trait, protocol or abstract base type, quoted verbatim from the diff, `fix` = the interface declared in the consuming module with only the methods that consumer calls and the implementing module returning its concrete type, or, where only tests use the interface or nothing uses it yet, the interface removed and the implementing module returning its concrete type, in the file's language, `rationale` = the module that holds the interface's only implementation, the modules or tests that use it or the absence of any use, and the methods the consumer does not call).
