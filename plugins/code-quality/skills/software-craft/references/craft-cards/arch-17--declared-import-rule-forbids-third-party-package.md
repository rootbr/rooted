# Code a change adds to a component imports no framework, ORM or other third-party package that the project's declared import rules forbid for that component or confine to other components, and an exception the change adds to admit such an import is stated as a change to that rule

## Thesis
Where a project declares, in a rule a checker enforces, which of its components may import a named external package — a forbidden-modules contract that lists the package with external packages included, a deny list scoped by file globs, a banned-external-imports constraint on a project tag, a disallow rule from an element type to an external module, a banned-API or restricted-imports entry, a dependency ban that names the components allowed to depend on the banned package directly, or an architecture test that confines a dependency to one namespace — code a change adds imports only the packages that rule admits at the code's location. Where the rule counts indirect imports, the added import also reaches no forbidden package through a chain of the project's own modules. An ignore entry, an allow entry, a narrowed scope or an inline suppression directive that the change adds to admit its own new import is stated in the change as a change to that rule. An import that no declared rule forbids at the code's location — no deny entry covering the location names the package, and no allow list in force there leaves it out — is outside this rule.

## Rationale
A declared import rule writes the intended dependency structure down where a checker enforces it: the project lists the imports a component may not make, or the only ones it may make, and the checker reports each import that breaks that list. Patterns left to convention tend to rely on a rigorous and consistent process of code review, and that discipline often breaks down as projects grow, use cases become more complex and developers come and go; a rule written as a test can be incorporated into a build pipeline instead. A forbidden contract checks indirect imports unless it is configured to allow them, so an import of an own module that already imports the forbidden package breaks the contract as a direct import would; a dependency ban with wrappers checks direct dependencies only: every component that depends on the banned package directly must be a named wrapper, and a component that reaches the package through a wrapper passes. An exception entry silences the check for the import it lists: once an import that would break a contract is added to the ignored imports, the contract is kept instead. An entry added beside the new import therefore changes what the rule admits, and the check passes on an import the rule forbade before. Checkers give such an exception a place for its reason — a reason field beside an allow or deny entry, a description after a disable directive — and offer rules that report a suppression directive carrying no explanation.

## Example
```rust
bad:  // deny.toml: deny = [{ crate = "diesel", wrappers = ["store"] }]; this file is in crate `domain`
      use diesel::prelude::*;
      pub fn open_total(conn: &mut PgConnection) -> QueryResult<i64> { ... }
good: // crate `domain` owns the trait; crate `store` implements it with diesel
      pub trait OrderTotals { fn open_totals(&self) -> Vec<i64>; }
      pub fn open_total(totals: &impl OrderTotals) -> i64 { totals.open_totals().iter().sum() }
```

## Limits
Framework-native model code is the documented default where no declared rule forbids the package. One web framework's design notes ask models to include all relevant domain logic and to encapsulate every aspect of an object following the Active Record pattern; another framework's guide places its Active Record in the model, the layer of the system responsible for representing data and business logic; a vendor guide builds a simple data-driven CRUD microservice as a single web API project that holds its data model, its business logic and its data access code. The separating condition is the project's own declaration: a forbidden contract forbids an external package only when it lists the package and the configuration includes external packages, a deny list applies to the files its globs match, banned-API and restricted-imports rules report the names configured, banned external imports apply per project tag, and a strict allow list denies every package it leaves out. An import that no declared rule forbids at its location is therefore the framework-native default and falls outside this rule. Translating a foreign model into domain types at a boundary and declaring an interface on the consumer's side are module-level rules outside this one.

## Validator
Grep the hunk for added import, use, using, require and from lines and for quoted package paths added inside an import block, and for added or edited import-rule configuration: `forbidden_modules`, `include_external_packages`, `ignore_imports`, a depguard section with `files` and `deny`, or with `allow` under a strict list mode, `banned-api`, `bannedExternalImports` or `allowedExternalImports`, `no-restricted-imports`, a disallow rule to an external origin, a dependency ban with `wrappers`, an architecture test calling `HaveDependencyOn`. Open every declared import rule of the repository and keep the ones whose scope — source modules, file globs, project tag, element type, namespace, permitted wrapper components — covers the file each import is added to. For each added import of an external package, check whether such a rule forbids it there or confines it to other components. Where the rule counts indirect imports, open each own module the change newly imports and follow its imports to see whether the chain reaches a forbidden package; a dependency ban with wrappers counts only the banned package's direct dependents, so a chain through a named wrapper passes. Read a dynamic import against the same list, since one restricted-imports checker applies to static imports only. Where the change adds an ignore entry, an allow entry or an inline suppression directive for the import checker, or narrows a rule's scope, check whether it admits an import the same change adds, and whether the change states it as a change to the rule — in its description, its commit message, or a reason field or directive description beside it; an import that an exception stated this way admits is not flagged as forbidden. Skip a package that no declared rule covering the file forbids, either by naming it in a deny entry or by leaving it out of an allow list in force there. Validator question: **Does the change add an import that a declared import rule covering its file forbids and no exception stated in the change admits, directly or through a chain the rule counts, or add an exception entry or suppression directive that admits its own new import without stating it as a change to that rule?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-17`, severity minor, `file`, `symbol`, `code` = the added import line and, where present, the added exception entry or suppression directive, quoted verbatim from the diff, `fix` = the import moved to a component the rule admits behind a type the restricted component owns, or the exception restated as a change to the rule, in the file's language, `rationale` = the declared rule, where it is declared, and the package it forbids for that component).
