# A call does not discard a returned value that is the call's only effect or that the API documents the caller must keep, call or release

## Thesis
A call to an operation that changes nothing and only returns a new value has that value used: assigned, returned, passed on, thrown or driven to a result. Such operations include a method on an immutable value such as a string, a number or a date; an arithmetic method that leaves its left-hand side unchanged; a lazy sequence adapter, which does nothing until the sequence is driven; a function with no side effects that formats a string or builds an error; and the construction of an exception object. A call whose returned value the API's documentation obliges the caller to call, close or keep holds on to that value so the obligation can be met: a returned cancellation or cleanup function is kept to be called, a returned resource is kept to be closed, and a reference to a returned task is saved. Leaving the result of either kind of call unused breaks the rule, and so does discarding an obliged value explicitly, as when a returned cancellation function is assigned to a blank identifier instead of being called. A returned value that callers typically do not need, such as whether an added element was already present, may be dropped, and so may the handle of work the API documents as legitimately fire-and-forget.

## Rationale
A call to an operation that changes nothing is a no-op once its result is ignored: the new value it returns for the caller to use goes unused, so either the call is useless and should be dropped or the code does not behave as expected. One common cause is a call on an immutable value made in the belief that it updates the value, such as trimming a string; an ignored result may also indicate that the caller did not realise an arithmetic method leaves its left-hand side unchanged, or that a lazy sequence adapter does nothing unless something drives it. For a function with no side effects, such as one that formats a string or builds an error, discarding the result is always a mistake, and an exception created without being thrown is unlikely to be correct, the assumed intent being to throw it. Where the documentation places an obligation on the returned value, dropping the value leaves the obligation unmet: a cancellation function that is never called leaves its context live until the parent context is cancelled; a returned resource is left for garbage collection instead of being managed carefully; and where the event loop keeps only weak references to tasks, a task that nothing else references may be garbage collected at any time, even before it is done. Checkers in four language ecosystems report these discards, as errors enabled by default, as correctness bugs or as warnings. Using the value restores what the call was for: the new value reaches the code that uses it, and the cleanup call, the close or the saved reference that the documentation requires can take place.

## Example
```typescript
bad:  label.trim();
      items.map(render);
      new Error("stale");
      feed.subscribe(render);
      new WriteStream(path);
good: label = label.trim();
      const unsubscribe = feed.subscribe(render); // documented: must be called, or the listener is never released
      ...
      unsubscribe();
```

## Limits
A result that callers typically do not need, such as the flag telling whether an added element was already there, may be dropped, and a callee that the project context lists as one whose result may be ignored rejects the finding for that callee. Work that the API documents as legitimately fire-and-forget, such as a spawned thread that is not waited on, may drop its handle; where the documentation asks even background work to stay referenced, as for a task that the event loop holds only weakly, the reference is saved, for instance in a collection. For an operation that changes nothing, a value discarded explicitly into a variable named as unused is a deliberate discard and passes, as when the call is made only to fail fast on a bad argument, such as an early check that a format string is valid. A call that parses, decodes, formats or converts its argument only to learn whether the argument is valid, made inside a try block whose handler catches the call's failure, also passes. An early-exit search whose callback assigns to an outer variable, such as a find whose callback records the element it stops on, leaves its result unused by design; a lazy sequence adapter runs its callback only when the sequence is driven, so its callback never exempts it. A call in a test that expects it to throw, a call that programs or verifies a mock, and a call in a benchmark are outside the rule. The obligation case reaches only a duty the API documents; a returned handle that carries no documented duty falls under neither case. The rule judges the call that drops an obliged value; whether a held cleanup function is called, or a held resource closed, on every later path is judged by its own rule. A returned value that signals the call's own failure, such as an error value or a failure status, is judged by its own rule, while an error the call builds as its product is within this one. A discarded handle to a resource, or a discarded cancellation function, that the routine then never releases or calls is judged by its own rule.

## Validator
Grep the added lines for a call whose value nothing takes — no assignment, return, throw, argument position or further call on it — to a method of a string, a number, a date or another immutable value, a lazy sequence adapter, a formatting or error-building function, or an error constructor; and for a call that returns a cancellation or cleanup function such as an unsubscribe function, a closable resource or a scheduled task, whether its value is left unused or assigned to a blank or unused-named variable. Read the hunk around each hit. Decide from the callee's declaration or doc comment where the hunk shows it, and otherwise from the library's documented behaviour, whether the callee changes nothing and only returns a new value, or whether its documentation requires the caller to call, close or keep what it returns; a callee that does neither is outside the check. Skip a result the API documents callers need not use, the handle of work the API documents as fire-and-forget, a value of an operation that changes nothing discarded into an unused-named variable, a parsing, decoding, formatting or converting call made only to validate its argument inside a try block whose handler catches its failure, an early-exit search whose callback assigns to an outer variable (never a lazy sequence adapter, whose callback runs only when the sequence is driven), a call in a test that expects it to throw or that programs or verifies a mock, a call in a benchmark, a callee the project context lists, and a returned value that signals the call's own failure. For an obliged value, a blank identifier or a wildcard pattern that releases the value at once drops it, and so do a cancellation or cleanup function bound to a variable named as unused and a task held only by a local variable whose scope ends before the task is awaited or stored; any other binding keeps it whatever the variable is named, as a resource declared in a statement that closes it when its block ends does. Validator question: **Does an added line call an operation and drop the value it returns, where the operation does nothing but return that value, or where the API's documentation obliges the caller to call, close or keep that value?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-08`, severity major, `file`, `symbol`, `code` = the call statement or the discarding assignment quoted verbatim from the diff, `fix` = the same call with its value assigned back, returned, passed on, thrown or driven to a result, or with the returned cleanup function called, the resource closed or a reference to the task saved, or the call deleted where it does nothing, in the file's language, `rationale` = that the callee changes nothing and only returns the dropped value, or the obligation its documentation places on that value, and what the following code assumed the call had done).
