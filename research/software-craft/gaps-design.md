# Research note — Concepts the design reviewer found uncovered

Topic `gaps-design` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: the taxonomy topics of the concepts and their canon locators: domain-modeling-and-domain-language (PP "Domain Languages", SWEBOK ch. 3 §5.10).

The canon agrees that code about a problem domain speaks that domain's language. Sources include PP Tip 22 and Topic 45, Evans's DDD Reference (Ubiquitous Language, Bounded Context, Intention-Revealing Interfaces, Modules), North's 97 Things essay 11, Code Complete §11.1 and §34.6, and Clean Code ch. 2 'Use Problem Domain Names'. SWEBOK V4 §5.10 lists the shared language of domain-driven design, but it was reached only through third-party summaries. Official documentation states the claim directly. Microsoft's .NET microservices guide calls 'using the same business terms (ubiquitous language)' the important part of code organized around business problems, and it scopes DDD approaches to complex services with significant business rules. The Azure Architecture Center (2026) says teams use the language 'in conversations, documentation, and code', each within its own bounded context. A .NET sibling page names entity changes in the ubiquitous language. Swift's 'Embrace precedent' and the Microsoft Graph and Azure REST API guidelines tie names to the domain's precedented terms, product-UI names and industry standards. Research is indirect. Haiduc and Marcus (ICPC 2008) argue for domain-literature terms in identifiers but measure only how common they are. De Lucia et al. (TSE 2011) show that tool feedback raises identifier consistency with requirements. Lawrie et al. (ICPC 2006) find identifiers to be readers' main carrier of domain information. No study measures the effect of domain terms over generic ones, and the DDD reviews report too little empirical evaluation. The industry disagrees on scope and form. Clean Code keeps CS terms for solution concepts, and jMolecules and Coplien reject building-block words. The .NET guide exempts CRUD services and Khononov does not. PP keeps one project glossary, while Evans, .NET and Azure scope terms to a bounded context. Practice splits on domains whose natural language is not English. Binkley et al. (ICPC 2008) and Swift's 'Avoid obscure terms' warn against specialized vocabulary. The separating condition resolves this: the rule asks for a term the domain's recorded vocabulary has already established, never for coined jargon. The earlier topic run folded domain terms into CODE-06. This run cards the rule because CODE-06 asks only for the word the codebase already uses and prescribes none for a concept the codebase does not yet name, while this rule says where that first word comes from. Its bounded-context limit also bears on CODE-06's Limits, which compare names across the whole repository. The DSL sense of 'Domain Languages' stays out. It is contested (Kosar et al. EMSE 2018 against the Google Go guide) and has no checkable form on a diff.

## Formulation layer

The canon agrees on one core position: design and code in the problem domain's language. This appears as PP Tip 22, Evans's ubiquitous language and intention-revealing names, North's 97 Things essay 11, Code Complete §11.1 and §34.6, and Clean Code §2.15 (for code about problem-domain concepts). Microsoft's dotnet/docs and the Azure Architecture Center state it as official guidance. Both scope it: dotnet applies DDD only to complex services with significant business rules, and both keep terms consistent only within each bounded context. Opened directly: the Evans DDD Reference (CC BY), the 97 Things essays, SWEBOK V3 chs 3 and 9, dotnet/docs, Azure, the Swift API Design Guidelines, PEP 8, the .NET naming guidelines, the Cucumber docs, the Google Go style guide and the aposd-vs-clean-code discussion. That discussion and SWE at Google say nothing on domain vocabulary. The Pragmatic Programmer, Code Complete and Clean Code were reached only through third-party notes or transcriptions on GitHub (relayed). SWEBOK V4 §5.10 and §4.5 were reached only through paraphrasing summaries. Evans's 2003 book and Fowler's bliki were not opened; the Reference carries the same formulation. The canon disagrees at three points: Clean Code names solution concepts with CS terms and uses problem-domain names only where no programmer term exists, while Code Complete prefers problem-oriented names over computing terms; PP keeps one glossary per project, while Evans, dotnet and Azure keep terms consistent only within a bounded context and tell large systems not to unify them; PP and Hunger encourage internal domain languages, while the Google Go guide says not to invent DSLs with generics or for testing. Neighbouring cards already hold part of the ground (CODE-06 one name per concept, CODE-08 role names, DSN-44/45/46 domain types and translation at the boundary, DOC-14 user terms in user documents). The earlier topic run folded a 'domain terms in names' rule into CODE-06, so the spine must say what a domain-language rule adds beyond consistency with the codebase's existing words.

## Reception layer

Practitioners agree on the core of the domain-language rule. Where code stands for domain concepts, it uses the business's own terms. This is said by Evans (quoted by Steyer), Fowler, North (CUPID 2022), Khononov, Kvamme, Millett, the GitLab contributor guide, the kgrzybek and Sairyss reference projects, jMolecules, the 2026 Azure page and the 2026 agent-skill authors (Pocock, citypaul). Even the 2026 skeptic in the DDD debate agrees on 'use the same words in code that you use in specs'. The disputes are about scope and form, and they should shape the card's Limits: (1) Clean Code's 'Use Solution Domain Names' gives technical concepts CS and pattern names, while Coplien and jMolecules reject DDD or programmer vocabulary (BankAccountEntity, CurrencyVO) in domain names; (2) the .NET guide and Łabaj limit DDD to complex domains and accept CRUD, while Khononov holds that ubiquitous language is 'not optional' in any subdomain; (3) a non-English domain splits practice three ways: Brion says always English, Messerli uses English for abstractions, and the DigitalService ADR of 2026 keeps German domain terms in code; (4) Evans, Fowler and the Azure page scope consistency to a bounded context, while AIP-190 asks for unambiguous names across a whole API ecosystem; (5) Poupko and Coplien warn that a language is more than a word list, which limits any glossary-based check. No static-analysis tool checks identifiers against a domain glossary. The mechanical checks found are generic-name denylists (ESLint id-denylist, Pylint disallowed-name, clippy disallowed_names, revive package-naming), cspell flagWords, which can be repurposed to forbid deprecated terms, ArchUnit naming conventions, and jMolecules' structural DDD rules. Contextive only shows glossary definitions, and its warnings are still on the backlog. Not opened: Hacker News and Lobsters threads (hosts denied, WebSearch budget exhausted), martinfowler.com itself (a 2015 GitHub clipping was used instead) and Tilkov's talk (only a third-party digest was read). It Will Never Work in Theory reviews nothing on ubiquitous language.

## Evidence layer

Official documentation states the domain-language claim directly. The dotnet/docs DDD-oriented-microservice page puts it as "using the same business terms (ubiquitous language)" and limits it to complex services with significant business rules. Four sibling dotnet pages, the Azure Architecture Center, the Swift API Design Guidelines (Embrace precedent, sin(x)) and the Microsoft Azure and Graph API guidelines add checkable forms and limits: entity changes as methods named in the ubiquitous language, past-tense event names, consistency only within a bounded context, and no one-to-one mirroring of the domain model in a public API. GitHub-hosted IEEE Xplore metadata dumps (NicolasV15/CIRDC-Pro) and an arXiv RSS dump made new research abstracts openable. They include Haiduc and Marcus ICPC 2008, which argues for domain-literature terms in identifiers and measures 42% of domain terms in code and 11% in identifiers alone, plus Antoniol et al. TSE 2002, De Lucia et al. TSE 2011, Deissenboeck and Pizka IWPC 2005, Lawrie et al. ICPC 2006, Ratiu and Deissenboeck ICPC 2007, the Özkan et al. DDD review and Zhong et al. TSE 2024. None of these measures what using domain terms rather than generic or invented ones does to comprehension or defects; the DDD reviews say empirical evaluation is lacking. The canon pulls two ways: Binkley et al. ICPC 2008 (158 programmers) concludes that good naming "reduces the need for specialized vocabulary", while Swift and Google C++ limit jargon to terms that carry crucial meaning or that readers outside the team know. The DSL sense of 'Domain Languages' remains split between Kosar et al. EMSE 2018 and the Google Go guide. Could not open: the SWEBOK V4 §5.10 original (only two third-party summaries, and the GitHub text copy stops at ch. 1), the Abebe et al. SCAM 2011 lexicon-smell abstract, and any tool rule that checks identifiers against a project glossary; SWE at Google and the NWIT posts hold nothing on the claim.

## Spine — candidate rules in source order

1. **In code that implements business rules, a type, operation or module added for a business concept the codebase does not yet name takes the term that the project's glossary, requirements or product documentation uses for it within its bounded context, not a generic, CRUD or framework word or a coined synonym** — In code that implements a domain's significant business rules (a domain model or domain layer, not a CRUD service that the official guidance leaves to simpler approaches), a type, operation or module that a change adds for a business concept the codebase does not yet name takes the business term from the domain's recorded vocabulary for that concept, an operation that changes a domain entity is named for the business change it performs, and a generic, CRUD, storage or framework word or a synonym of the author's own in its place is the finding. The recorded vocabulary is the project glossary, the requirement or change description, the product's user interface or user documentation, or an industry standard. The term is the one used within the bounded context the code belongs to, so another context's different word for the same entity is not a finding. A technical construct with no business meaning keeps its programming term, a CRUD verb passes where the domain itself speaks of creating or deleting the thing, and where the codebase already names the concept its existing word governs under CODE-06. The rule asks for a term the domain has already established, never for an obscure term of art coined where a common word conveys the meaning as well.
