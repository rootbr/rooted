# Research note — Concepts the input reviewer found uncovered

Topic `gaps-input` of group J. Input and security hygiene, domain `input`, id prefix `INP`. Formulation locators: the taxonomy topics of the concepts and their canon locators: parsing-and-grammar-based-input (SW4.9, PoP9); security-hygiene-in-ordinary-code (PP "Stay Safe Out There", SWEBOK ch. 3 §3.7).

The five concepts the input reviewer found uncovered differ in how settled they are. The canon frames them and standards state four of them as checkable rules. SWEBOK V3 §3.7 places security faults in ordinary construction, §4.5 sends full error detail to a central exception reporter, and §3.2.4 defines fuzzing. BSRS ch. 1, 12, 13, 14 and 15, 97 Things #21 and #28, and, from memory, The Pragmatic Programmer Topic 43, Code Complete ch. 8 and Effective Java Item 75 supply the wording. (1) XML parser hardening rests on the OWASP XXE Prevention Cheat Sheet's General Guidance: reject DOCTYPE; where DTDs are needed, disable external entities and external DTD loading and limit expansion; treat an unsupported setting as a failure. ASVS 5.0 1.5.1 (Level 1), CWE-611/776, CERT IDS17-J and CodeQL java/xxe back it, and a scratch JDK 21 run shows the default DOM parser resolving a file entity. The industry disputes the defaults, not the goal. CPython 3.13+ says Expat loads no external resources, while Ruff, Bandit, Semgrep and the cheat sheet's Python section still prescribe defusedxml. find-sec-bugs accepts secure-processing mode, which OWASP calls no portable replacement. The parser's documented default at the deployed version separates the cases, with openable evidence on each side. (2) Log content rests on the OWASP Logging Cheat Sheet, ASVS 16.2.5 and 16.4.1, CWE-532/117 and CERT FIO13-J and IDS03-J. CodeQL checks clear-text logging at high precision, and one SecDev 2025 study found PII leaking into the logs of about 6% of 3,885 Android apps. The sources hedge ('usually') and allow masking or hashing. They accept encoding by the logging component as well as at the call, and the card follows OWASP over CodeQL's example: replace the bad field and keep the event. (3) The generic error message at a trust boundary meets agreement: ASVS 16.5.1 and 16.5.4, the Error Handling Cheat Sheet, CWE-209, CERT ERR01-J, RFC 9457 and CodeQL and find-sec-bugs all support it. ASVS's 'unexpected or security-sensitive' scope and AIP-193 keep actionable messages for expected client errors, and framework defaults (Spring Boot NEVER, Go net/http) already comply. (4) How a secret reaches the running program stays contested. OWASP Proactive Controls C2, systemd, Docker and CLIG reject environment variables, and the Secrets Management Cheat Sheet allows them only as a last resort. Sonar S2068/S6437, Ruff S105, find-sec-bugs and CWE-526 accept a configuration file or the environment, practitioner studies (Basak et al.) find environment variables recommended most often, and Kubernetes and ASVS 13.3.1 leave the channel open. No openable source states a separating condition, so it is held pending. (5) A fuzz test for a hand-written parser rests on google/fuzzing ('parsers of any kind'), the Go, libFuzzer, Atheris and OSS-Fuzz documentation, which define the crash, panic, hang and out-of-memory oracle and the seed corpus run as regression tests, and on research. Miller et al. (TSE 2020) found 12-19% of utilities crashing or hanging, and Ding and Le Goues (MSR 2021) found 30% of OSS-Fuzz timeouts flaky, which bounds what a saved hang input can promise. No empirical study of XXE prevalence, log injection or error-message disclosure was found. NISTIR 8397 could not be reopened here, and every hands-on test is scratch-only until it is committed under evals/fixture/.

## Formulation layer

The canon states four of the five concepts plainly and leaves concept 4, where a secret is supplied at run time, in open dispute. On XML hardening (1), BSRS ch. 12 says to use an XML parser without XXE enabled and defers to the OWASP XXE cheat sheet and CERT IDS17-J. The Python, JDK and Go documentation show that defaults differ by parser and version, so a card needs the precondition that the parser in use enables DTDs or external entities; PP Topic 43, PoP ch. 9 and SWEBOK §4.9 are silent on parser configuration. Keeping secrets and personal data out of logs (2) is stated by BSRS ch. 1 and ch. 15, the Go style guide, SWE at Google and, from memory, Effective Java Item 75, PP and Code Complete; log-injection encoding comes only from the standards (ASVS 16.4.1, the Logging cheat sheet, CERT IDS03-J, Proactive Controls C9, which prefers escaping to dropping), and Go's slog shows both redaction and quoting inside the logging library. The generic-message rule (3) is shared by PP 'debugging info', Code Complete §8.3/§8.6, 97 Things #21, BSRS ch. 12, Zalando #177, AIP-193, ASVS 16.5.1, CERT ERR01-J and the Error Handling cheat sheet; 97 Things #28 warns it must not license swallowing errors, and SWEBOK V3 §4.5's full-information message belongs to the log side. Secret supply (4) splits the canon: PP (recalled, unverified), the Twelve-Factor App and Sonar S2068's compliant example accept configuration files or environment variables, while CLIG and Proactive Controls C2 reject environment variables, the Secrets Management cheat sheet makes them a last resort, BSRS ch. 14 prefers a secret manager 'whenever possible' and the SCP checklist accepts an encrypted configuration file, with no source stating a separating condition. On fuzzing parsers (5), BSRS ch. 13, SWEBOK V3 ch. 4 §3.2.4, google/fuzzing, the Go fuzzing docs, The Fuzzing Book (Miller's crash-or-hang criterion), Crafting Interpreters and King agree that crashes, panics and time-outs are failures, failing inputs become regression tests, and long campaigns run continuously rather than gating each commit. PP Topic 43, PoP, Code Complete, Effective Java, Secure by Design, Release It! and SWEBOK V4.0 could not be opened and are recorded as unfetched paraphrases (Secure by Design and Release It! at low confidence); the aposd-vs-clean-code discussion was fetched and holds no position on any concept.

## Reception layer

Tools already check all five concepts mechanically. Reception shapes two of them sharply. (1) XML hardening is the most contested concept, and the dispute concerns platform defaults, not the goal. Since Python 3.13 the CPython docs say Expat by default does not access local files or the network, and they no longer recommend defusedxml. The OWASP XXE cheat sheet, Ruff S313–S319, Bandit B313–B319, Semgrep use-defused-xml and CodeQL's xml-bomb help all still recommend it. lxml switched to resolve_entities='internal' in 5.0. Ruff and Bandit then retired their lxml checks, but Sonar S2755 still flags the default lxml parser, and lxml 6.1 (CVE-2026-41066) found that iterparse still resolved external entities. Java's JDK still allows DTDs by default (jdk.xml.dtd.support=allow; entity-expansion limit 2500). Go's encoding/xml returns DTD directives without processing them, and .NET 4.5.2+ XmlReader does not process DTDs. A card therefore has to be written against each parser's own defaults, and it risks folding into INP-09 (each configuration turns on the protection a library ships switched off) and INP-24 (parser limits). (2) How a secret reaches the program at run time stays contested in 2024–2026 sources. The twelve-factor rewrite (next branch), Ruff S105, Sonar S2068/S6437 and GitHub Actions use or accept environment variables. OWASP Proactive Controls C2, the OWASP Secrets Management cheat sheet, Docker and systemd advise against them. Kubernetes supports both. ASVS 13.3.1 and OWASP Top 10:2025 A02 require a secrets-management solution, or platform identity and short-lived credentials, without settling the channel. (3) Logs: tool confidence splits. CodeQL's clear-text-logging queries (Python, Go and JavaScript) run at high precision in the default suite. Java sensitive-log and every log-injection query run at medium precision, so they appear only in security-extended. Structured handlers that quote values (Go slog TextHandler and JSONHandler, which gosec G706 exempts) meet the encoding requirement, while slog's default handler writes the message verbatim. Log4j warns that concatenating untrusted data into the message is exploitable. GitHub says log redaction is not guaranteed. (4) Generic error messages meet agreement rather than dispute: CodeQL, Sonar S4507, find-sec-bugs, RFC 9457 §5, Spring Boot's NEVER defaults, Django DEBUG=False and Go net/http's panic recovery all support it. Express finalhandler returns err.stack unless NODE_ENV is production, and AIP-193 limits the rule to unexpected errors, because client errors must stay actionable. (5) Fuzz tests: Go and Jazzer run them by default as unit tests over the seed corpus. Atheris and Jazzer count an uncaught exception as a failure, so a target must catch the parser's documented error. cargo-fuzz needs nightly Rust, and Scorecard counts property-based testing libraries as fuzzing. This overlaps TST-43 and TST-54. Not opened: Hacker News and Lobsters threads (WebSearch budget spent; the hosts are denied), Diogo Mónica's blog on environment-variable secrets, and The Pragmatic Programmer's 'Stay Safe Out There'.

## Evidence layer

I opened sources for all five uncovered concepts. Four of them rest on standards that state a checkable rule: ASVS 5.0 1.5.1 and the OWASP XXE cheat sheet (XML parser hardening), ASVS 16.2.5 and 16.4.1, CWE-532, CWE-117 and CERT FIO13-J and IDS03-J (secrets and personal data kept out of logs, and log encoding), and ASVS 16.5.1, the Error Handling cheat sheet, CWE-209, CERT ERR01-J and RFC 9457 §Security Considerations (a generic message for the consumer, with the details kept in the server log). Tool checks from CodeQL, find-sec-bugs, Semgrep, Sonar and Ruff back each of these; the research is thin: one SecDev 2025 measurement of PII in Android logs. For the parser fuzz test, the Go, libFuzzer, google/fuzzing and OSS-Fuzz documentation states the failure conditions (crash, panic, hang, OOM). Three papers bear on it: Miller et al. (TSE 2020), whose crash-or-hang criterion is the same one the rule uses; Ding and Le Goues (MSR 2021, 23,907 OSS-Fuzz bugs, 30% of timeouts flaky); and Klooster et al. (15-minute campaigns in CI). Sources disagree in four places: (a) where a secret is supplied at run time: OWASP Proactive Controls C2, ASVS 13.3.1 (L2 only), the Secrets Management cheat sheet, systemd and Docker advise against environment variables; CWE-526 prefers a protected config file; Sonar S2068 and S6418 accept a config file or a database and use os.getenv in their compliant example; Kubernetes supports both; and Basak et al. (2022, 2023) find that practitioners recommend environment variables most often, so no separating condition beyond assurance level and client-side delivery was found; (b) Python XML: the current CPython docs say Expat loads no external entities by default, while Semgrep, Ruff and the OWASP cheat sheet still prescribe defusedxml; (c) log injection: CodeQL's good example drops the whole entry, but the OWASP Logging cheat sheet says to omit or replace only the bad field; (d) Java XXE: find-sec-bugs offers FEATURE_SECURE_PROCESSING alone, OWASP says it is not a substitute, and CERT IDS17-J uses an allowlisting resolver. I also ran local tests under /tmp/craft-research/gaps-input/hands-on/. They show that the JDK 21 DOM default resolves a file entity while Python 3.13 with Expat 2.6.1 does not; that Python logging and Go log forge a second log line from a newline, while slog escapes it; and that a Go hang found by fuzzing was saved as an input that did not reproduce when minimization was on. These tests are not yet in an openable form. Not opened: the WOOT 2016 'SoK: XML Parser Vulnerabilities' and SWEBOK V4's security section; I found no empirical study of XXE prevalence, log injection or error-message disclosure.

5. **A parser written in the change for input from outside the program has a fuzz test that feeds it generated input and fails when the parser crashes, panics, hangs or exhausts memory instead of returning a value or an error** — A parser that the change writes for input from outside the program, such as a tokenizer or a recursive-descent or state-machine parser for a file format, a protocol or a little language, has a fuzz test that feeds it generated and mutated input and fails when the parser crashes, panics, raises an error other than its documented parse error, exceeds the engine's per-input time limit or exhausts memory, instead of returning a value or an error. The fuzz target lives in the repository, is built with the other tests, is deterministic and fast, and its seed corpus, including every input that once failed, runs as an ordinary test in the normal test run; the fuzz test adds to the parser's functional tests and does not replace them. A standard or established parser the code only calls is outside the rule (google/fuzzing lists parsers of any kind as targets, but the change's own parser is the one its tests can reach). How long an open-ended fuzzing campaign runs, and that it stays out of the gating run, is TST-54's; a round-trip property is TST-41's and a result check TST-43's; the per-input hang bound is the engine's (Go 1 second, libFuzzer 1200 seconds by default), and a saved hang input need not reproduce, since timeouts are the flakiest fault class. A property-based test that feeds generated input and fails on the same conditions serves where the language has no coverage-guided fuzzer, without coverage guidance.
