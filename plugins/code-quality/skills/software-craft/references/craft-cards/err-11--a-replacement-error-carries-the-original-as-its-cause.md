# An error raised or returned in place of a caught or returned one carries the original as its cause, or copies the original's relevant details when the chain is cut on purpose

## Thesis
An error created in place of a caught or returned error — in a handler, in an error branch or in an error-mapping step — carries the original as its cause: through a cause argument or option, a cause setter, an explicit chaining clause, a wrapping format verb, or a field, source or suppressed-error list that holds the original, so that the original's stack trace, type and message stay reachable from the replacement; a link the runtime attaches on its own to any error raised during handling is not a cause. The replacement cuts the chain only on purpose, and then its message or fields carry the original's relevant details, such as the original's text, the key or input it named, or, at a system boundary, the canonical code the original translates to. A cut is on purpose when it is an explicit suppression of the chain, a translation into a canonical error at a system boundary that must not expose the original, a replacement for a caught error that only signals an ordinary outcome such as a failed number, date or URL parse, a catch variable named to mark the original as unused, or, where errors carry no stack trace, a formatted error that embeds the original's text because callers are not meant to inspect the original. Outside such a cut the cause travels with the replacement even when its message already quotes the original's text.

## Rationale
A replacement error is created at the handler, so its stack trace starts there; unless the caught error travels with it as its cause, the trace ends at the handler, and the frames where the failure happened, the original's type and its message are gone from the replacement, which makes debugging a fault in the guarded call far harder than necessary. Copying only the original's message keeps the text and still drops the trace. The replacement itself is often right: an upper layer that let a lower layer's error propagate would expose an error generally unrelated to its own abstraction and, where the language checks declared exceptions, tie its interface to its implementation, and a replacement that contains the original as its cause lets the upper layer avoid both while still communicating the details of the failure to its caller. In result-based code the same loss happens when an error is mapped into a new value with the original discarded, which throws it away rather than letting the new error contain and report its cause; a wrapping error type either exposes the underlying error as its source or renders it in its own message. Where errors carry no stack trace, a wrap keeps the original reachable to a caller that inspects the chain for a known error or type, while formatting the original's text into a new error drops its structured information and keeps the text. Where the language attaches the handled error implicitly to any error raised during handling, a replacement without an explicit cause still prints both tracebacks, but it presents the replacement as a second failure during handling rather than as a direct consequence of the first, and the cause field stays unset, which may make debugging slightly more difficult. A cut on purpose has its own reasons: at a system boundary such as RPC, IPC or storage, translating an error into a canonical error space and hiding the specifics of the original is beneficial, and a failed number, date or URL parse arguably signals a nonexceptional outcome. A catch variable named to mark it unused states that the author chose not to propagate the original. Replacing a runtime's reflective-invocation or privileged-action wrapper with the error it wraps discards only runtime-internal frames, which are not very useful. When a replacement deliberately cuts the chain, the relevant details transfer to the new error, such as the attribute name when a key-lookup error becomes an attribute error, or the text of the original embedded in the new message. A study of exception-handling anti-patterns in 16 open-source libraries and applications in two exception-based languages found destructive wrapping among the few anti-patterns commonly identified across its subjects.

## Example
```python
bad:  try:
          data = path.read_bytes()
      except OSError:
          raise ConfigError(f"cannot load {path}")
good: try:
          data = path.read_bytes()
      except OSError as err:
          raise ConfigError(f"cannot load {path}") from err
```

## Limits
A cut the Thesis admits follows the rule when the replacement carries the original's relevant details: an explicit suppression of the chain whose message embeds the original's text or the key it named; a catch variable named to mark it unused (an underscore, `unused`, a name starting with `ignored`), where the replacement carries the input the failed call received, while an omitted catch parameter is no such mark; a translation into a canonical error at a system boundary such as RPC, IPC or storage that must not expose the original, where the canonical code chosen for the original is the relevant detail; a replacement for a failed number, date or URL parse, where the input value is the relevant detail. Replacing a runtime's reflective-invocation or privileged-action wrapper with the error it wraps discards only runtime-internal frames and follows the rule. Where errors carry no stack trace and the project's convention reserves wrapping for errors callers are meant to inspect, a formatted replacement that embeds the original's text follows the rule; the finding there is a replacement that carries neither the original's text nor, at a boundary, a canonical code chosen for it. Where the language attaches the handled error implicitly, a project whose linter configuration turns off the explicit-cause check tolerates a replacement raised inside the handler without an explicit cause; that stated tolerance rejects such a finding, and a deliberate suppression that carries none of the original's details stays a finding. A throw inside a handler that reports a failure other than the caught one, such as one raised in a routine the handler defines for later, is not a replacement. A handler that logs the original and then creates a replacement without it keeps the original in the log but not in the replacement, and stays a finding. The rule judges whether the original travels with its replacement; what else the replacement's message names, an empty or swallowing handler, the breadth of the catch, and what an external consumer is shown at a trust boundary are judged by their own rules.

## Validator
Grep the added lines for a created error: a throw of a new error, a raise of an error class or call, an error-format or error-constructor call, an error-struct literal or a rejection with a new error, an error-mapping closure that ignores its argument, a match arm on an error that binds nothing, and an error constructed from a caught error's message. For each hit, open the file and read the enclosing handler, branch or closure, and establish whether a caught or returned error is in scope: the line sits in a catch, except or rescue handler, in a branch taken when a returned error is non-nil or an error variant, in an error-mapping closure or in an error match arm. Skip a hit with no such error in scope, a bare re-raise and a return of the original unchanged. Check whether the new error receives the original: a constructor cause argument or cause option, a cause setter call, an explicit chaining clause naming the caught variable, a wrapping format verb with the error operand, or a field, variant, source or suppressed-error list that holds it; a link the runtime attaches on its own to an error raised during handling does not count. When it does not, check whether the cut is one the Thesis admits — an explicit suppression of the chain, a catch variable named to mark it unused, a boundary translation into a canonical error, a failed parse, or a formatted error that embeds the original's text where errors carry no stack trace — and whether the new error's message or fields carry the original's text, the key or the input it named, or, for a boundary translation, a canonical code chosen for the original. Validator question: **Does an added line create an error in place of a caught or returned one that neither carries the original as its cause nor, under a cut on purpose, carries the original's relevant details in its message or fields?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-11`, severity minor, `file`, `symbol`, `code` = the added line that creates the replacement error, verbatim from the diff, `fix` = the same statement passing the original as its cause through the cause argument or option, the chaining clause, the wrapping verb or a source field, or, for a cut on purpose, the explicit cut with the original's text, key, input or, at a boundary, canonical code in the new error, in the file's language, `rationale` = the handler, error branch or mapping closure that held the original, what the replacement drops — the original's stack trace, type or message — and where a reader of the replacement would need it).
