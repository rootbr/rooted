# Research note — Composition root and dependency wiring

Topic `composition-root-and-dependency-wiring` of group K. Architecture, domain `architecture`, id prefix `ARCH`. Formulation locators: Clean Architecture ch. 26 'The Main Component' and ch. 11 (factories at boundaries); Seemann and van Deursen, 'Dependency Injection Principles, Practices, and Patterns' (composition root, service locator as an anti-pattern — formulation); Fowler, 'Inversion of Control Containers and the Dependency Injection pattern' (formulation); SWEBOK Guide V4.0 ch. 3 'Software Design' (design patterns). Marked contested in the design note.

The canon agrees on where the object graph is built. Clean Architecture ch. 26 and ch. 11, Seemann and van Deursen, and Fowler (all as formulation) say that concrete implementations are composed in one place at the process entry point and that application code receives its collaborators instead of resolving them. I could locate nothing in SWEBOK V4 ch. 3 that states it. The documentation of the containers themselves says the same, fetched verbatim and re-checked for this spine: .NET, Spring, Guice, Dagger and the Google and Uber Go guides. It also gives the boundary conditions a card needs. .NET qualifies its rule with 'when you can use DI instead' and says 'exceptions are rare, and are mostly special cases within the framework itself'. Spring recommends container-aware interfaces only 'for infrastructure beans that require programmatic access to the container'. Guice allows injecting the injector only 'in framework code' that does not know the type until run time. The industry disagrees in four places. (1) The service locator: Fowler treats it as roughly equivalent to DI for application classes (unfetched), the Google Go guide objects only to a global locator, Angular prefers an ambient inject() inside an injection context, and the JDK ships ServiceLoader. (2) Injected factories: .NET calls a factory that resolves dependencies at runtime a locator variation, yet it also documents factories that receive the container; Guice recommends factories for runtime arguments; Dagger calls wiring factories duct tape. (3) Conditional bindings: Guice and Dagger split environments into separate modules, while Spring Boot builds library auto-configuration out of conditions. (4) Framework annotations on business classes: Clean Architecture ch. 32 rejects them, while Spring documents annotation-based configuration as standard. The research does not support the premise that DI lowers coupling. Razina and Janzen 2007 (relayed) found no correlation across 20 project pairs. Sun and Kim 2022 (relayed) found a gain only under their own DI-weighted metric. The ASWEC 2008 abstract could not be retrieved. None of this research bears on where the graph is built, so the cards rest on failure mechanisms that the vendor documentation states. A second container creates duplicate singletons. A lookup in application code defers a missing binding to run time. A captive lifetime stretches a scoped service to the whole application. Conditional bindings leave configurations untested. Nine rules become cards. Two rules (the injected factory, annotations in core classes) lack a sourced separating condition. Three rules (no container in a library, no shared root, a creation hook in frameworks) rest on Seemann's blog alone. Eager graph verification feeds a Rationale. Shipped cards TOOL-23, TOOL-28, TOOL-29 and the module-load card already state the rule that configuration is read at the edge.

## Formulation layer

The canon agrees on one formulation: concrete implementations are composed in one place at the process entry point, and application code receives its collaborators instead of resolving them. That place is Seemann's Composition Root, Martin's Main, the composition root in the .NET docs' Program.cs, and Guice's single createInjector call in main; access to a container or locator stays inside it (Seemann 2010/2011, .NET DI guidelines, Spring reference, Guice wiki). Configuration is read at the edge and passed in as values or typed options: Seemann's primitive dependencies, the .NET options pattern, Google Go's rule that flags live only in package main, and Twelve-Factor. The canon disagrees in two places. Fowler 2004 treats Service Locator as roughly equivalent to DI for application classes, while Seemann calls it an anti-pattern. Framework conventions also allow container access or framework annotations outside the root: Spring's annotation-based component classes, .NET background services that resolve services from an IServiceScopeFactory, and Guice injecting the Injector in framework code. Clean Architecture ch. 32 and Seemann reject that for business code, so a rule needs the condition that separates the two. I could not open Clean Architecture, the Seemann–van Deursen book, Fowler's article or SWEBOK V4. Their positions come here as paraphrase from memory, three relayed search snippets, and Seemann's own blog posts, which I fetched from their GitHub source. No SWEBOK text on DI turned up, and this layer did not search for the ASWEC 2008 counter-study.

## Reception layer

The framework vendors' own documentation agrees on the core of this topic, and all of it was fetched from GitHub. .NET, Guice, Spring, Dagger, Wire and the Google and Uber Go guides all say the same things: build the graph in one place at the entry point, resolve from the container at most once ("Use the Injector as little as possible (preferably only once)"), keep static or global access out of services, and confine flags and configuration to package main. Each source names its own boundary condition. .NET says "when you can use DI instead", Spring keeps container lookup for "infrastructure beans", Google's Go guide applies its rule most strictly to libraries offered to other teams, and Guice says "static state" is bad but the static keyword is fine. Mechanical checks exist only for framework mechanics, not for where the graph is built. Those checks are field injection (Sonar S3306/S6813, ArchUnit), a single injectable constructor (Sonar S6818, Error Prone ERROR), the ASP.NET analyzer ASP0000 against a second BuildServiceProvider during configuration, and .NET scope validation for captive lifetimes. Four positions are contested. First, Fowler 2004 (unfetched) treats the service locator as a valid alternative, while Seemann 2010 (relayed) calls it an anti-pattern. Second, .NET calls "injecting a factory that resolves dependencies at runtime" a locator variation, and Dagger calls factory classes "clumsy duct tape"; both cut against the factory-at-boundary candidate. Third, Angular now prefers inject() over constructor parameters, within an injection context. Fourth, the Wire authors call runtime DI (Uber Fx/dig) hard to debug. On evidence, Razina and Janzen 2007 (relayed) found no correlation between DI and coupling. Sun and Kim 2022 (arXiv:2205.06381, relayed) found a gain only on their own DI-weighted metric. The ASWEC 2008 Yang/Tempero abstract could not be retrieved, so the design note's "no evidence DI reduced coupling" remains unconfirmed. DHH's 2013 critique and Weiher's rebuttal came through only as search summaries. The searches found no 2024–2026 survey or debate thread, and the dates of the practitioner pieces they did find are unconfirmed.

## Evidence layer

Official documentation with GitHub sources backs most candidate rules and was fetched verbatim: .NET (composition root by name, avoid service locator, avoid static access to services, options pattern, scope validation, ValidateOnStart), Spring Framework and Spring Boot (no getBean in application code, constructor injection, eager singleton pre-instantiation so wiring errors surface at startup, typed @ConfigurationProperties), the Guice wiki (one createInjector in main, never inject the Injector, side-effect-free modules), Dagger (component as graph root, well-formed acyclic graph), Wire, the Google and Uber Go guides (flags only in package main, no mutable globals, no environment access in init(), package-level APIs only for binaries), plus Sonar and ArchUnit checks on field injection. I could open no paper, because arXiv, IEEE and the publishers are denied, so the research items are search relays. Razina and Janzen 2007 found no correlation between DI use and coupling or cohesion, apart from a trend in projects with 10% or more DI. Sun and Kim 2022 report a significant maintainability gain under their DCBO metric but none under plain CBO. Laigner et al. report 12 DI anti-patterns, at least nine of them frequent. Xu et al. (OSDI 2016) relate latent configuration errors to missing checks at initialization. I found no abstract of the Yang, Tempero and Melton ASWEC 2008 study, so the design note's 'no evidence' claim stays unverified and backs no card. The canon disagrees on the service locator: .NET, Spring and Guice say to avoid it, the Google Go guide says only a global locator is the problem, Angular's style guide prefers the ambient inject() lookup inside an injection context, the JDK ships ServiceLoader as a platform facility, and Fowler (formulation, unfetched) treats the choice as secondary to separating configuration from use. Injected factories are disputed too: .NET calls a factory that resolves dependencies at runtime a service-locator variation, while the Guice FAQ and .NET's own disposable guidance recommend factories.

## Spine — candidate rules in source order

1. **A process builds its dependency-injection container once in its composition root, and no other code, registration code included, builds a second container from the application's registrations to resolve a service** — The composition root at the process entry point builds the application's root container once, whether that container is a service provider, an injector, an application context or a generated component. Registration code and all other code build no further container from the same registrations to resolve a service. Each container built creates its own copies of the singleton services, which can make the application behave incorrectly. A registration that needs another service uses the container's overload that hands it the provider. Scopes, child containers and subcomponents derived from the root are not second containers, and neither is a component a test builds for itself.

2. **Code that declares a wiring module's bindings opens no connection, starts no server or background work and performs no other I/O, and the application starts its services after the container is built** — A wiring module's binding declarations only describe the object graph. Three problems follow when the module connects to a database or starts an HTTP server while it runs: the resource has no hook to close it, the module is hard to unit-test, and an override of that production service has no effect. That work belongs in a service with start and stop operations. The entry point starts the service after it creates the container and adds shutdown hooks that release resources when the application stops. The rule covers code that runs while the bindings are declared. A factory function that the container calls to create a service is kept fast and synchronous.

3. **An application's own wiring binds each key the same way in every environment, choosing whole modules per environment at the composition root, and no branch inside a module binds a key to a different implementation or only sometimes** — Inside the application's own wiring modules, no branch on the environment, a flag or an optional value binds a key to different implementations or binds it only in some cases.
