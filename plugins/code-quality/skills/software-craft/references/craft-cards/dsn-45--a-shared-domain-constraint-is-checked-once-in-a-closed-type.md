# A primitive whose domain constraint many routines rely on is replaced by a type that checks the constraint once where a value is created, and no code can create or change a value of that type without the check

## Thesis
When the program must operate only on values that satisfy a domain constraint — a number between two bounds, a byte whose highest bit is zero — and many routines require that constraint of a primitive, the primitive is replaced by a domain type, and the check runs once, in the one function that creates a value of that type. The type's representation is closed: its fields cannot be set from outside the module that defines it, so code elsewhere obtains a value only through that function, and no value of the type holds a primitive the check has not passed. Routines that require the constraint take or return the type in their signatures and need no additional check in their bodies. A check that one routine alone needs may stay inline in that routine.

## Rationale
A check written into every routine that requires the constraint is tedious and might impact performance. Placed once in the function that creates the type, the check makes the type safe to use in signatures, and a routine that takes the type uses the values it receives with confidence. The guarantee rests on the representation: code that uses the type is not allowed to set its private field directly, so code outside the defining module must call the creating function, and no value of the type holds a primitive that function has not checked. An argument type that rules out bad inputs usually comes at little run-time cost, because it pushes the cost to the boundary where a primitive is first converted into the type, and, where the language or its type checker checks argument types, it catches bugs early, during compilation, rather than through run-time failures. A carrier type that holds each component in a private final field is only shallowly immutable; its explicitly declared constructor is where the arguments are validated and where a mutable component is copied defensively.

## Example
```rust
bad:  fn discount(price: u64, pct: i32) -> u64 { if pct < 0 || pct > 100 { panic!("pct {pct}") } ... }
      fn surcharge(price: u64, pct: i32) -> u64 { if !(0..=100).contains(&pct) { panic!("pct {pct}") } ... }
      // ...and the same check again in every other routine that takes a percentage
good: pub struct Percent { value: i32 }
      impl Percent {
          pub fn new(value: i32) -> Result<Self, String> { if value < 0 || value > 100 { return Err(format!("percent {value} not in 0..=100")); } Ok(Self { value }) }
          pub fn value(&self) -> i32 { self.value }
      }
      fn discount(price: u64, pct: &Percent) -> u64 { ... }
      fn surcharge(price: u64, pct: &Percent) -> u64 { ... }
```

## Limits
The rule is contested, and the number of routines that rely on the constraint separates the cases. A range check written inline in the one loop that reads the value serves that loop: after it, the code proceeds knowing the value is in range (the Source entry marked inline). When the program must operate only on valid values and many functions share the requirement, a check in each of them is tedious and might impact performance, and the type with one creating function is called for (the entry marked type). Some properties are difficult or impossible to express using types; such a property is validated as the input is processed. A sibling function that deliberately skips the check, marked by a name suffix such as `_unchecked` or placed in a `raw` submodule, is a documented opt-out to be used judiciously where performance dictates avoiding the check and the caller is otherwise confident the input is valid; the rule does not flag it. Where the language lets any user of a type create its zero value without calling a constructor, that zero value is outside the closure this rule asks for, and it is helpful to design the type so that its zero value can be used without further initialization. Where the language has no enforced private fields, a field named non-public by the language's convention, on a type that emulates immutability by rejecting assignment to its fields, counts as closed, and code elsewhere that sets such a field directly goes around the check. Whether untrusted input is validated where it crosses a trust boundary, and how the creating function reports a value that fails the check, are outside this rule, which decides only which type carries the constraint and where its one check runs. A tolerance the project context states for a named type or module rejects the finding.

## Validator
In the hunk, find each check of a domain constraint on a primitive: two comparisons of one name against two bounds, a bound-first or chained range comparison, a range-containment test, a regular-expression match on a string, or a raised invalid-argument error. Name the constraint and the domain quantity the primitive stands for. At the callers' scope, search the repository for the other routines that take, return or store the same primitive for the same quantity, and read whether each repeats the check or relies on the constraint without checking it; count them. Where a domain type for the quantity already exists, read its declaration and its uses in the diff: a field settable from outside its defining module, a public constructor, factory, conversion or setter that skips the check, or a mutable component stored without a defensive copy is a path around the check. Skip a check that one routine alone needs, a property that cannot be expressed through a type, a sibling marked as opting out of the check, a zero value the language creates without a constructor, and a tolerance the project context states. Validator question: **does the change check or rely on one domain constraint of a primitive in many routines rather than in the one creating function of a closed type, or add a path that creates or changes a value of such a type without its check?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-45`, severity minor, `file`, `symbol`, `code` = the repeated check, or the field, constructor, conversion or setter that goes around the type's check, quoted verbatim from the diff, `fix` = a domain type with a closed representation and one creating function that runs the check, with the routines' signatures taking that type and their own checks removed, in the file's language, `rationale` = the constraint, the routines that repeat or rely on it, and the path that lets an unchecked value through).
