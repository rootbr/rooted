# A call that changes state is retried only when it is idempotent, carries a client-generated idempotency key reused on every attempt, or failed in a way that shows it was never applied

## Thesis
A retry that repeats a call changing state at the callee — a write, a payment, a message send — runs only when one of three things holds. The operation is idempotent: repeating it has the same intended effect on the callee as performing it once, by the standard definition of its method or by the callee's documentation. Or the request carries a unique key that the client generated once for the logical operation, outside the retry, and sends unchanged with the same payload on every attempt, to a callee whose interface or documentation accepts such a key. Or the failure indicates that the request was not processed: an error raised before the request was sent, such as a refused connection, a failed name resolution or a timeout while connecting, or a status the callee documents as meaning the request was not processed. A timeout, a read error or a closed connection after the request was sent does not show that the request was never applied, and a key generated afresh for each attempt is not a key for the operation; when none holds, the failure goes to the caller instead of into another attempt.

## Rationale
A request that times out leaves the client uncertain whether the resource was created or updated, or whether the server even completed processing the request, and so whether it can safely retry. What looks to the caller like a crash of the callee may be only a lost or long-delayed acknowledgement, and the callee may have applied the request before the failure occurred; a retry then makes the request a duplicate that only the application can discover, and repeating a non-idempotent request can result in duplication or incorrect updates. In a set of 156 timeout bugs across 11 cloud server systems, an update whose correct semantics required at-most-once execution was retried on timeout: resubmitting it led to undesired results, and the correct handling was to abort the operation. The communication layer cannot suppress such duplicates, because a duplicate the application originates in its own retry procedure looks to that layer like a different message; suppression has to be done by the application, with knowledge of how to detect its own duplicates. An idempotent request can be repeated automatically after a communication failure that occurs before the client reads the response, because repeating it has the same intended effect even if the original succeeded. An idempotency key is a unique value generated by the client which the callee uses to recognise later retries of the same request, answering a duplicate with the result of the earlier operation so that the request is processed once. A key the callee has not seen is processed as a first request, so a key generated afresh for each attempt makes every retry a first request. Without prior knowledge, a general client cannot assume that the callee respects a key; the callee may purge a key upon its expiry, and a key is not to be reused with a request that has a different payload. Errors raised while connecting are the ones a client is fairly sure the server did not receive, so they should be safe to retry, whereas errors raised after the request was sent, such as a read timeout, are treated as though the server began processing it, since the request may have had side effects. A request that never left the client, or reached the server but never its application logic, is always safe to retry, so a client library may retry it transparently, whatever the retry configuration says. Retrying a non-idempotent request because the connection closed before any part of the response arrived is the riskier approach, a guess at when an automatic retry is possible.

## Example
```typescript
bad:  for (let attempt = 1; ; attempt++) {
        try { return await payments.create(order, { idempotencyKey: randomUUID() }); }
        catch (err) { if (attempt === 3 || !isTransient(err)) throw err; await backoff(attempt); }
      }
good: const idempotencyKey = randomUUID();
      for (let attempt = 1; ; attempt++) {
        try { return await payments.create(order, { idempotencyKey }); }
        catch (err) { if (attempt === 3 || !isTransient(err)) throw err; await backoff(attempt); }
      }
```

## Limits
A call that changes nothing at the callee, such as a read, is outside the rule, and so is a request whose method the HTTP standard defines as idempotent: PUT, DELETE and the safe methods. Idempotence belongs to a request's semantics rather than to its method or name: a request whose semantics are idempotent by design passes whatever its method, while an RPC named delete is idempotent only where its owner says so, because a non-idempotent delete can have adverse side effects when called more than once. A caller that, after the failure, checks the target's state, reverts or fixes any change that was partially applied, and then repeats the request has a means of detecting what the original did, and is not flagged. A client library's own transparent retry of a request that never left the client, or never reached the server's application logic, is outside the rule. A transactional request is retried by application logic that repeats the entire transaction block from its start, not by an automatic retry of the single request; a retry of the whole block on a transaction abort or another failure the callee documents as meaning the transaction was not committed is not flagged, while a retry after a commit whose outcome is unknown is judged like any other retry. A project context that declares a callee's operation idempotent, or names the key its interface honours, rejects the finding for that callee. How many attempts a retry makes, which failures count as transient, the delay between attempts, the timeout on each call and the layer at which the retry sits are judged by their own rules.

## Validator
Grep the added lines for a retry — a loop with an attempt counter, a retry decorator, annotation, policy, helper or library call, a retry configuration that admits every method or widens the retried status codes — and for idempotency vocabulary and identifier generation. Open the file and, for each retry, name the call it repeats; decide from the callee's name, its HTTP method or its documentation whether that call changes state at the callee: a create, write, update, delete, payment, send or enqueue. Skip a read, an HTTP PUT, DELETE or safe method, an operation the callee's documentation or the project context declares idempotent, a client library's transparent retry, a repeat that follows a check of the target's state, and a retry of a whole transaction block from its start on a transaction abort or another failure the callee documents as meaning the transaction was not committed. For each remaining state-changing call, look for an idempotency key or request id: it passes when it is generated outside the retried block — before the loop, outside the decorated or wrapped routine, or received as a parameter — sent through the callee's own key parameter, field or documented header, and left unchanged across attempts; a key generated inside the retried block fails. Without a passing key, read which failures trigger the retry: it passes when they are limited to errors raised while connecting (a refused connection, a failed name resolution, a timeout while connecting) or to statuses the callee documents as meaning the request was not processed; a retry on any error, on a generic or read timeout, or on a connection closed after the request was sent fails. Validator question: **Does an added line retry, or configure a retry of, a call that changes state at the callee when the call is not idempotent, carries no key generated once and sent unchanged on every attempt, and is retried on a failure that can arrive after the callee applied the request?** Yes → flag.
