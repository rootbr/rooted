# A parameter, option or setting that most callers pass with the same value, or rarely set, gets that value as its default, while one each caller must set for its own environment stays required

## Thesis
A parameter, constructor argument, option or setting that most of a module's callers pass with one and the same value, or would rarely set at all, has that value as its default where the default simplifies the common call, so that a call names the value only to choose another one, which every caller still can. Where every caller passes the same constant, the module may instead drop the parameter and use the constant itself. A value that each caller must set to match its own runtime environment, such as where its data lives, is hard to give a default in advance and stays required, with no value the module would use in its place. A default the module gives results in neither a security hole nor terribly inefficient code.

## Rationale
A default hides information that is irrelevant to the common call, and a call that needs no configuration then carries none. Settings most users leave alone are not free: users have tremendous difficulty knowing which parameters to set among many. In a study of the configuration of a commercial storage system with thousands of customers and of widely used open-source system software, only 6.1%–16.7% of the parameters were set by the majority (50+%) of users and up to 54.1% were rarely set by any user, while 17.3%–48.5% of users' configuration issues were difficulties in finding or setting the parameters that give the intended behaviour. In the storage system, 51.9% of the parameters could be hidden or removed and 19.7% of the rest converted to simpler types with impact on fewer than 1% of its users, and the two open-source systems showed similar reduction rates. A hidden setting still accepts any value a user insists on, and a caller can override one option while keeping the other defaults. A parameter that every caller passes as the same constant can be replaced by that constant inside the routine, which may simplify the routine, and even a value many callers set can sometimes be eliminated where the module can infer it from its runtime environment. A type whose zero or default state can be used without further initialization lets its user create one and get right to work, and a simple constructor, with very few parameters and ideally none, increases usability. The parameters left without defaults are usually the ones more essential to what a routine does, and a builder's constructor takes as parameters only the data required to make the value.

## Example
```go
bad:  func NewClient(addr string, timeout time.Duration, retries, bufSize int) *Client { ... }
      var a = NewClient(addrA, 30*time.Second, 3, 4096)
      var b = NewClient(addrB, 30*time.Second, 3, 4096)
      var c = NewClient(addrC, 5*time.Second, 3, 4096)
good: type Option func(*Client)
      func WithTimeout(d time.Duration) Option { ... }
      func NewClient(addr string, opts ...Option) *Client { ... }
      var a, b = NewClient(addrA), NewClient(addrB)
      var c = NewClient(addrC, WithTimeout(5*time.Second))
```

## Limits
Whether one value is right for most callers separates the cases, and the same configuration study measured both sides. Where callers leave a setting alone, the module gives it a default or decides it: up to 54.1% of the parameters studied were rarely changed from their default by any user; where most callers pass one value, that value is the candidate for the default. Where each caller must set a value to match its own runtime environment, a default is hard to know in advance and the value stays required: 1.8%–7.8% of the parameters studied were set by more than 90% of users, many of them carrying information about the runtime that is hard to give a default in advance, and 17.5%–53.3% of the configuration errors examined came from users keeping a default that failed the constraints of their runtime environment, very few of them on rarely set parameters, as when data-directory settings left at defaults under /tmp lost data when the machines rebooted. Required names no mechanism: a constructor parameter and a setting the caller supplies before first use differ in no semantics, and a comparative study found programmers strongly preferred and were more effective with APIs that did not require constructor parameters, which caused premature commitment. Hiding a value from the common call does not take it from the tests and developers that need to set it; the explicit form stays reachable for them. In a language without default arguments a default takes a mechanism, such as a shorter overload, an options value whose omitted fields take the default, variadic options or a builder; such mechanisms apply primarily to an exported interface, which is held to a higher standard than an unexported one, and may be unnecessary for an unexported routine, and variadic options need substantial extra code and pay only where their advantages outweigh that overhead. A project may limit the check to routines up to a given visibility, or to parameters passed the same value at a minimum number of call sites, as the inspection that reports such parameters provides; such a tolerance stated in the project context rejects the finding. A default that opens a security hole is a security defect, judged outside this rule's finding. The rule decides on which side of a module's interface a value is chosen; configuration files and how they are loaded, and how many parameters a routine takes, are outside it.


On a published interface, a new input whose default keeps the behaviour the routine had before the change is outside the rule; making it required waits for a breaking release.
## Validator
Grep the hunk for an added or changed signature of a constructor, a factory or a routine, or for an options type, and for parameters or fields that hold a tuning value such as a timeout, a retry count, an interval, a size, a limit or a worker count. For each parameter, option or field the change adds without a default, open its call sites at scope callers, the ones the diff adds included, and count, among the call sites outside test code, those that pass one and the same literal or constant; where the call sites are few, also read the routine's documentation and the change description for the uses it expects. For each default the change adds, check whether the value describes each caller's own runtime environment, such as where its data lives. Set aside a parameter without a default for which no single value is passed at more than half of its call sites outside test code, a parameter whose only call sites are in test code, a parameter whose callers all lie outside the repository with no documented expected use, a parameter whose shared value, made the default, would open a security hole or make the code terribly inefficient, and any routine or parameter the project context exempts by visibility or by a minimum count of call sites. Validator question: **Does the change make callers supply a parameter, option or setting that every call site outside test code, or more than half of them, passes with one and the same value while the module offers no default for it, or give a default to a value that each caller must set to match its own runtime environment?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-17`, severity minor, `file`, `symbol`, `code` = the added signature, options field or default quoted verbatim from the diff, `fix` = the value most call sites pass made the default through a default argument, a shorter overload, an options field or option whose omission takes it, with the explicit form kept for callers that need another value, or, where every call site passes it, the parameter dropped and the value used by the module itself; or, for a value each caller must set to match its environment, the default removed and the value required, in the file's language, `rationale` = the value and how many of the call sites outside test code pass it, or the environment-dependent value the default would hide).
