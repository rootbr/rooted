# Where results can be marked must-use, an operation whose discarded result is almost certainly a bug is marked and one whose result callers legitimately drop is not

## Thesis
Where an operation's result can be marked as must-use — by an attribute or annotation on the operation, or on its returned type where the compiler or checker reports a discarded value of a marked type, by a default on its enclosing type or package with per-operation exemptions, or by a list of the codebase's own operations that its checker is configured with — each added public operation whose discarded result is almost certainly a bug is covered by the mark: one that returns a new value and has no other effect, a lazy computation that does nothing until its result is driven, one that reports failure through its returned value, or one that returns a cleanup operation the caller has to call. An added public operation whose result callers commonly and legitimately ignore, such as an incidental status or a handle to fire-and-forget work, is left uncovered: unmarked, exempted from the default, or absent from the list.

## Rationale
Dropping a result of these kinds can mean the caller did not realise what the call does: that the operation can fail, so its error goes unhandled; that it returns a new value instead of changing its receiver, so the call is a no-op; that the computation is lazy and does nothing until something drives it; or that the returned cleanup operation has to be called. The mark makes the compiler or the checker report a call statement that discards such a result, as a warning or, in one checker, as an error. A checker needs the code to say which operations these are: a check on ignored results is useful only once it knows which operations are like a string concatenation, whose new value has to be used, and which are like adding to a set, whose returned flag, false when the element was already present, callers typically do not need. A lint that proposes the mark for public functions that have no mutable argument and mutate no statics cannot decide whether a function is meant to be called for its side effect or for its result, and expects many false positives. A mark on an operation whose result callers legitimately drop forces each of them to discard it explicitly, which could be a nuisance rather than an indication of a bug; where such legitimate uses are common, the mark is probably not appropriate. Where the compiler or checker reports a discarded value of a marked type, an operation whose returned type carries the mark is covered through that type and needs no bare mark of its own, since not using the result is already reported; a mark that makes only a type's own methods must-use does not cover an operation of another type that returns it.

## Example
```go
bad:  // go vet -unusedresult.funcs=fmt.Errorf,...,example.com/geom.Add ./...
      func Scale(v Vec, k float64) Vec { ... }
      func Add(s Set, x int) (added bool) { ... }
good: // go vet -unusedresult.funcs=fmt.Errorf,...,example.com/geom.Scale ./...
      func Scale(v Vec, k float64) Vec { ... }
      func Add(s Set, x int) (added bool) { ... }
```

## Limits
Sources differ on the default. One checker lets a class or package make every method's result must-use, with an annotation that exempts specific methods, and holds that most methods are like the string concatenation; one standard library adds the mark item by item, where failing to consider the output is almost certainly a bug, and its ecosystem's lint that proposes the mark on public functions with no mutable argument sits in a group allowed by default. Both sort operations by the same test — the concatenation, the saturating addition and the lazy iterator combinators carry the mark, while the flag returned by adding to a set and the fire-and-forget thread handle do not — so a finding names an operation on the wrong side of that test under whichever default the codebase uses, and the choice of default stays the codebase's. Adding a mark to the declaration of an operation that is already published raises new warnings, or errors where the checker reports at error level, at existing call sites that drop the result, so it is weighed as a change to a published interface and not flagged here. Where the language has no declaration for the mark, the codebase's means is a checker's configured list of operations, and a codebase that configures no such list is outside the rule, as is an operation the list cannot name, such as a method whose signature differs from the one signature the list accepts for methods. A configured list reports a discarded result only in code checked with that list, so it guards the codebase's own call sites and not callers elsewhere who run the checker with their own configuration.

## Validator
Grep the added lines for a must-use attribute or annotation, an exemption annotation, an entry in a checker's list of operations whose results must be used, and an added public operation that returns a value of its own type or a converted or adjusted value. Open the file and, for each added public operation, find what covers its result: a mark on the operation, a mark on its returned type where a discarded value of a marked type is reported, a default on the enclosing type, a default on its package read from the file that declares the package, or an entry in the codebase's checker list; for a list entry, open the file that declares the listed operation. Read the operation's body and doc comment and classify its result: a new value with no other effect, a lazy computation, a failure value, a cleanup operation to call, or a result callers commonly and legitimately drop, such as an incidental status or a handle to fire-and-forget work. Skip a private operation, an operation the codebase's means cannot mark, such as a method that the checker's configured list cannot name, an operation covered through a marked returned type whose discarded values are reported, a mark added to the declaration of an operation whose signature the hunk leaves unchanged, and a file whose language has no must-use declaration when neither the file nor the hunk shows the codebase's must-use annotation, default or checker list in use. Validator question: **Does an added public operation whose discarded result is almost certainly a bug go uncovered by the codebase's must-use mark, or does an added mark or list entry cover an operation whose result callers commonly and legitimately drop?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-09`, severity minor, `file`, `symbol`, `code` = the operation's signature line, or the added mark or list entry, quoted verbatim from the diff, `fix` = the signature carrying the codebase's must-use mark or the list entry added, or the mark or list entry removed or replaced by the exemption, in the file's language, `rationale` = what a caller who drops the result loses — a no-op update, an undriven computation, an unhandled failure, an uncalled cleanup — or why callers legitimately drop it).
