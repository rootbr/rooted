# A regular expression that a backtracking engine runs on untrusted text has no ambiguous repetition and a bounded text length, and an untrusted pattern runs size-limited on a non-backtracking engine

## Thesis
Where a regular expression engine backtracks and the matched text can come from outside the trust boundary, the expression has no repetition whose repeated part can match the same string in more than one way while a later part, an end anchor or a whole-text match can still fail: no inner and outer quantifier that can consume the same characters, no repeated alternation whose branches overlap, and no two overlapping quantified parts where one reaches the other directly or by skipping an optional part, a search without a start anchor counting as a repetition of any character before the pattern. The text's length is bounded before matching, and where the regular expression library in use offers a non-backtracking mode or a match timeout, the code uses it and treats a timeout as a failed validation. An ambiguous repetition kept behind a length bound meets the rule only where the bound is measured against the pattern's worst-case input. A pattern built from a value outside the trust boundary is replaced by a fixed pattern; where it has to come from input, it runs on a non-backtracking engine with limits on the pattern's length, its compiled size and the text's length.

## Rationale
A backtracking engine tries all possible execution paths of the pattern against the text. When a repeated part can match the same string in more than one way, every repetition adds a choice, and a suffix that makes the match fail sends the engine back through the other choices: nested quantifiers over the same characters and repeated overlapping alternations take worst-case exponential time on a mismatch, overlapping adjacent quantified parts worst-case polynomial time. A search without a start anchor can begin a quantified part anywhere inside a run of the characters it matches, so a failing suffix makes the engine process the run once per character, quadratic in its length. A crafted input of around 20 characters can trigger exponential backtracking, ten more characters of a certain shape may make matching about 1000 times slower, and the matching thread's CPU time keeps the application from serving legitimate users. Such expressions are common: about 1% of unique regular expressions in two package ecosystems were super-linear, including some in two platforms' core libraries; only 38% of surveyed developers knew of the vulnerability; and of 355 live web services that published their input-sanitization expressions, 17 published unsafe ones and 6 were vulnerable through their interfaces. A length bound limits the amount of backtracking only when it is chosen against the pattern's worst case: trimmed too short it rejects valid input, too long and the vulnerability remains, and one of eight historic length-limit fixes stayed vulnerable for two years because the first limit was too generous. An engine with a documented linear-time guarantee runs in time linear in the text's length; one documents its worst case as the pattern's size times the text's length, and iterating over all matches as the pattern's size times the square of the text's length. On such an engine a pattern taken from input gives the caller control over the pattern's size, and the only defence left is a limit on the pattern and on the text: nested counted repetitions multiply, so a short pattern that nests six repetitions of five expands like a single repetition of 15625, and the compiled size is limited along with the pattern's length. With unbounded backtracking it can be very difficult to know whether a particular pattern will backtrack catastrophically, and an engine without backtracking is one of the few effective solutions for user-provided patterns.

## Example
```rust
bad:  let re = Regex::new(pattern)?;      // pattern and text come from the request
      let found = re.is_match(text);
good: if pattern.len() > MAX_PATTERN_LEN || text.len() > MAX_TEXT_LEN {
          return Err(Error::InputTooLong);
      }
      let re = RegexBuilder::new(pattern).size_limit(MAX_COMPILED_SIZE).build()?;
      let found = re.is_match(text);
```

## Limits
The rule is contested and holds only where its conditions meet. First, the ambiguity and text-length clauses hold only where the engine backtracks: an engine documented to run in time linear in the size of the input, or bounded by the pattern's size times the text's length, takes them away, while the pattern clause holds on every engine, because worst-case search time still depends on the size of the compiled pattern. Second, the text or the pattern can come from outside the trust boundary: the impact belongs to an attacker who can control the input matched against a vulnerable expression, and the vulnerability is only relevant where the expression may match malicious input, so a pattern and a text that the program or its trusted configuration fixes are outside the rule. One side treats a catastrophically backtracking expression as a vulnerability of critical severity, citing the crafted input of around 20 characters and the 1% prevalence; the other holds that the vulnerability is only relevant where malicious input reaches the expression, that a star-height detector has both false positives and false negatives, and that many mainstream engines have introduced partial or full defences, rendering many threat models obsolete. A nested or overlapping construct is a signal to trace, not a finding by itself: such anti-patterns, the overlap tests included, appeared in 81–86% of super-linear expressions, yet 91–95% of the expressions that carried them were not super-linear, and none of the tests checked for a suffix that forces a mismatch, which is what makes the engine explore the redundant choices. The finding is an ambiguous repetition that a later part, an end anchor or a whole-text match can fail after. A possessive quantifier or an atomic group keeps no backtracking positions, and a bounded quantifier such as {1,5} limits repetitions; both are fixes where the engine supports them.

## Validator
Grep the hunk for calls that compile or run a regular expression and for pattern literals with a quantified group, a quantified alternation, or two unbounded quantifiers close together. Open the file and establish whether the engine that runs the pattern backtracks or is documented to run in time linear in the input; a platform's default engine can be either. Trace the matched text and the pattern back to their origin; a request, a message, an uploaded file or another tenant's data lies outside the trust boundary, a literal or trusted configuration inside it. On a backtracking engine with such text, decide whether a repeated part can match the same string in more than one way (the inner and outer quantifier consume the same characters, two repeated branches overlap, or two overlapping quantified parts follow each other directly or across an optional part, a search without a start anchor counting as a repetition of any character before the pattern) and whether a later part, an end anchor or a whole-text match can fail after it, and look for a length check on the text before the match; a nesting whose parts cannot match the same string, or an ambiguity that nothing after it can fail, is not by itself a finding, and an ambiguous repetition kept behind a length check stands unless the code or a test shows the limit measured against the pattern's worst-case input. Note whether the regular expression library in use offers a non-backtracking mode or a match timeout, and how the code treats a timeout. For a pattern built from such a value, look for a fixed replacement, or for a non-backtracking engine with limits on the pattern's length, its compiled size and the text's length. Validator question: **Does text from outside the trust boundary reach a backtracking engine with no length check before the match, or through a repetition that can match the same string in more than one way, with a later part, an end anchor or a whole-text match that can fail after it, behind a length check not shown to be measured against the pattern's worst-case input, or does such text reach a backtracking engine although the regular expression library in use offers a non-backtracking mode or a match timeout, or pass validation when a match times out, or does a pattern from outside the boundary reach a backtracking engine, or a non-backtracking one without limits on the pattern's length, its compiled size and the text's length?** Yes → flag.
