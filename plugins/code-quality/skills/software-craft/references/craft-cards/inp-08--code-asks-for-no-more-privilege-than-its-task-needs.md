# Code asks for no more privilege than its task needs in file modes, token and permission scopes, database rights and process identity, and holds elevated rights only for the step that needs them

## Thesis
Every access right that code requests or sets — a file or directory mode, a token's permissions or scopes, a database account's grants, the account a backend connection or a process runs under — is the minimum the code's function needs. A file is created with access permissions that prevent unauthorized access, rather than created first and restricted afterwards. An automation workflow's token is read-only at the top level, and each write permission is declared on the job that requires it. An application's database account holds only the access rights it requires: an account that needs only read access is granted read access only to the tables it needs, and no application account holds DBA or admin access. Communication between backend components — local or operating-system services, APIs, middleware, data layers — runs under accounts assigned the least necessary privileges. Web-server, process and service accounts are restricted to the least privileges possible, and where the application must run with elevated privileges it raises them as late as possible and drops them as soon as possible.

## Rationale
A mode set after creation leaves a window: when a program creates a file with insufficiently restrictive access permissions, an attacker may read or modify the file before the program can modify the permissions. A compromised token with write access can let an attacker push malicious code into the project, for example; and when permissions are defined only per job, a job added later can have its permissions left undefined by human error. Minimal database rights minimize the potential damage of a successful query injection, and reduce the likelihood of unauthorized access by an attacker who changes a parameter to a value unauthorized for them that the application itself might be authorized to access. Rights are worked out from the ground up, by what the account requires, rather than by deciding what access rights to take away. Out of the box, most database servers run under a very powerful system account. Overprivilege is common even where developers intend least privilege: of 940 Android applications analysed, about one-third were overprivileged, with evidence that developers try to follow least privilege but sometimes fail due to insufficient API documentation. A retrospective analysis of the SolarWinds Orion update and Log4j lists least privilege among the common principles that were not observed where observance could have mitigated the embedded vulnerabilities. The backend-account requirement is a Level 2 verification requirement. Analysers disagree on the numeric file-mode threshold — one expects files written at 0600 or less and directories at 0750 or less by default, configurable per project; another's stable rule flags only the world-write and group-execute bits, and its preview flags world-write, world-execute, group-write and group-execute — so the rule names the principle and leaves the number to the project's tool.

## Example
```python
bad:  os.setuid(0)
      path.write_text(api_token)
      path.chmod(0o644)
      cur.execute("GRANT ALL ON orders TO report_app")
      session = OAuth2Session(client_id, scope=["admin"])
good: path.touch(mode=0o600, exist_ok=False)
      path.write_text(api_token)
      cur.execute("GRANT SELECT ON orders TO report_app")
      session = OAuth2Session(client_id, scope=["orders:read"])
```

## Limits
A file or directory meant to be read or executed by others — a published asset, an installed executable, a directory several services share — gets the access that use needs; the rule flags access beyond the function's need, not every group or others bit. A job that publishes a package, pushes commits or uploads results declares the write permission it needs on that job, which is the rule's intended shape. Where two parts of a system need different rights on the same table, such as a login lookup that reads and a sign-up that inserts, the restriction can be enforced only when they connect as different database users. The token clause rests on a check limited to repositories hosted on one forge; other automation systems' tokens fall under the general minimum-rights clause. The actual permissions a requested mode yields are platform-specific. Designing an authorization scheme, a role model or a threat model is a reserved security specialty: the finder names it and stops at the hygiene above.

## Validator
Grep the hunk for calls that create a file or directory or change its mode with an explicit mode or permission set, for workflow `permissions` blocks, for database grant statements and role options, for requested scope strings, and for process-identity settings (a setuid call, a container user, a privileged or privilege-escalation flag). For a file mode, read in the hunk what the file holds and who must read it, and check whether the mode is passed at creation or applied by a later mode change after the file exists. For a workflow, check whether the top level is read-only and each write permission sits on the job that uses it. For a grant or a scope, list the operations the code in the hunk performs and compare them with the rights requested. For a process identity, trace whether a step that needs elevated rights keeps them after it finishes. Validator question: **Does the hunk request or set access — a file or directory mode, a token permission or scope, a database grant, a process identity — broader than the code's function uses, or restrict a file's mode only after the file exists?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-08`, severity major, `file`, `symbol`, `code` = the line that sets the mode, permission, scope, grant or identity, quoted verbatim from the diff, `fix` = the same call narrowed to the rights the code uses — the restrictive mode passed at creation, a read-only top level with the write permission on its job, a grant limited to the tables and operations the queries use, or elevated privileges dropped right after the step — in the file's language, `rationale` = the access requested beyond what the code uses and who gains it).
