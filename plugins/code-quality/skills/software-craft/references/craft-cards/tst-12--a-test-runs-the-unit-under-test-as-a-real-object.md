# A test runs the unit under test as a real object and never stubs the unit's own methods or chains a double that returns a double

## Thesis
In code the team can change, a test runs the unit under test as a real object. It does not turn the unit into a partial double — a spy around the unit, a double of the unit's own type set to call some real methods, or a test subclass of the unit that overrides one of its methods — to stub or verify some of the unit's own methods while the others run. A double returns real values and real objects: the test does not stub a double to return a second double that it then stubs in turn to reach the value the code under test needs, and no double stands in for a value object or a data holder in such a chain. The exceptions are the cases where the tool is documented: legacy code, for a partial double or a chain of doubles; a third-party interface the team cannot easily change and an interim step while refactoring legacy code, for a partial double only; and a factory method of the unit, overridden in a test subclass to return a double of the collaborator it creates.

## Rationale
A partial double runs a hybrid the program never runs: some of the unit's methods are replaced while the rest execute, so the replaced methods' real behaviour, and how the rest of the unit depends on it, go untested. Object-oriented design divides complexity among separate objects with one responsibility each; a test that has to stub one method of the unit to test another usually means that complexity has been moved into a different method of the same object, which in most cases is not the design the application wants — the stubbed work belongs in a collaborator the test can double. A real method called on a double of the unit runs against state the double never set up, and when it throws or depends on that state the test fails or passes for a reason the program never meets. In a study of four systems (three open source, one industrial) that counted mocks and left spies out of scope, the unit under test was never mocked across roughly 38,000 analysed dependencies, and a developer of a mocking framework interviewed for the study named not mocking the unit under test, and never mocking data-holder classes, as good practice. A double stubbed to return a double, stubbed to return a double, until something meaningful comes back hints at one of two faults: a violation of the Law of Demeter in the code under test, which reaches through its neighbour into the neighbour's structure, or a mocked value object, a well-known anti-pattern, since a data holder such as a string or a list is easy to build with the values the test needs. An object that navigates a network of objects is likely to be brittle because it has too many dependencies, and its tests are complex to set up and hard to read because they construct a matching network of doubles; tests work best when they set expectations only on the nearest neighbours, and the remedy may be to check that the right object is under test, to introduce a role that bridges the unit and its surroundings, or to have the double return a real value object. Partial doubles belong to code that cannot easily change and chains of doubles to legacy code; in new, test-driven code the rule restores a unit that runs whole and a test that does not build a network of doubles to mirror the objects the unit navigates.

## Example
```go
bad:  store.EXPECT().Account("a1").Return(mockAcct)
      mockAcct.EXPECT().Owner().Return(mockOwner)
      mockOwner.EXPECT().Email().Return("ann@example.com")
good: owner := User{Email: "ann@example.com"}
      store.EXPECT().Account("a1").Return(Account{Owner: owner})
```

## Limits
Legacy code is where a partial double or a chain of doubles is the accepted tool, and a third-party interface the team cannot easily change or an interim step while refactoring legacy code is where a partial double is; when the project context or a comment at the site names the one that fits the double found, the finding is rejected. A factory method of the unit whose only work is to create a collaborator, overridden in a test subclass to return a double of that collaborator, replaces the creation of a neighbour rather than the unit's own work and is outside this rule. A chain of doubles hints at a design fault rather than proving one: where the unit obtains an object by design from a factory, a pool or a connection and then works with it directly — a session, a transaction, a writer — the unit creates that object through its neighbour rather than navigating to it, and a factory double that returns a double of the new instance is the documented way to test the unit's interactions with an object it creates; the rule reaches the chain that navigates through objects to reach a value, and a double that stands for a value object or a data holder. A returned double that the test only verifies, without stubbing it in turn, is outside the chain the rule names, and so is a dummy that neither the test nor the unit calls, standing for a type the test cannot yet build a real instance of; where a real instance can be built with the needed values, the rule applies. A spy, a spy-on or a patch applied to a collaborator's method replaces a neighbour rather than the unit and is outside this rule. How many doubles a test may need, which of the unit's collaborators or of their own dependencies it doubles, and whether its interaction checks pin too much, are not judged here.

## Validator
Grep the added lines for a partial double or a spy (a spy wrapping a real object, a spy-on or a stub or patch applied to one method of an existing object, a double whose default answer calls real methods or returns further doubles, a call-real-method stubbing, a subclass the test declares or creates anonymously) and for a stub that returns a double (a returned mock variable or a new mock as the return value, a chained return-value attribute). Open the test file and name the unit under test: the type or function the test file is named after, which the test constructs and acts on. For a spy or partial double, check whether its target is the unit under test and whether the test stubs or verifies one of the unit's own methods; also look for a test subclass of the unit that overrides one of its methods. For a double returned from a stub, follow it: check whether the test stubs a method of the returned double in turn to reach a value, or whether the returned double stands for a value object or a data holder. Skip a spy or patch on a collaborator, a test subclass that overrides only a factory method of the unit to return a double of the collaborator it creates, a returned double the unit obtains by design from a factory, a pool or a connection and then uses directly, a returned double the test only verifies, a returned dummy that neither the test nor the unit calls and whose type has no instance the test can build, code the project context or a comment marks as legacy, and a spy or partial double in code the project context or a comment marks as an unchangeable third-party interface or as an interim step while refactoring legacy code. Validator question: **Does an added line stub or verify a method of the unit under test through a spy or a partial double, or stub a double to return a further double that the test stubs in turn to reach a value or that stands for a value object or a data holder, outside legacy code and, for a spy or partial double, outside an unchangeable third-party interface and an interim step while refactoring legacy code?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-12`, severity minor, `file`, `symbol`, `code` = the added line that creates or stubs the spy or partial double of the unit under test, or that stubs a double to return a double, verbatim from the diff, `fix` = the unit under test constructed as a real object with the stubbed method's work moved into a collaborator the test doubles, or the stub returning a real value object built with the needed values, or the neighbour offering the needed value directly, in the file's language, `rationale` = which of the unit's own methods the test replaces or which chain of doubles it builds, and the design fault it points to: complexity moved into another method of the same object, a navigated chain of objects, or a doubled value object).
