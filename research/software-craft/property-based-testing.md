# Research note — Property-based testing

Topic `property-based-testing` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: PP 'Property-Based Testing' (The Pragmatic Programmer, 20th anniversary ed., ch. 7 'While You Are Coding', topic 42), which draws its properties from the contracts of PP 'Design by Contract' (ch. 4, topic 23).

The canon's formulation is The Pragmatic Programmer's Topic 42, which takes properties from the contracts and invariants of Topic 23. It generates inputs and turns each failure into a regression example. Wlaschin's seven property patterns and Henney's essays on full postconditions and concrete examples formulate how to choose properties. The official documentation of the frameworks in all five target languages agrees on the mechanics: Hypothesis (Python), fast-check (TypeScript), junit-quickcheck (Java), proptest (Rust) and Go's testing and fuzzing packages, plus QuickCheck, the Haskell original. Research supports several of these rules. Goldstein et al. (ICSE 2024, 30 interviews) report differential and round-trip properties as the most used, find no-crash properties easy but weaker, show that shrinkers break invariants, and describe strict run budgets. Etna (ICFP 2023) measured generators that are valid by construction against generate-and-filter, and how sparse the precondition is separates the cases. Tyche (UIST 2024) shows that seeing the input distribution improves judgement. Polikarpova et al. (ICSE 2013) found that testing against strong specifications detects twice as many bugs. Ravi and Coblenz (OOPSLA 2025) found 76% of mutations within the first 20 inputs. The sources disagree in four places that no openable source separates: whether a committed failure record holds the value or the seed (QuickCheck, Hypothesis and Go against proptest); whether the run that gates each commit is derandomized (Hypothesis against the fresh-seed defaults of proptest and fast-check); whether examples or properties specify more clearly (Henney against Wlaschin, both formulation only); and exhaustive enumeration against random sampling (Etna's mixed results). Two disputes do separate. Whether random sampling reaches a known edge case depends on whether the generator in use is documented to favour that value (proptest against Hypothesis and fast-check). Whether an early return is an acceptable skip depends on whether the framework runs a fixed number of cases (Hypothesis against Go's tutorial). Metamorphic relations have no openable source. No static-analysis rule checks property quality; the frameworks' runtime health checks, discard limits and flakiness detection are the nearest tool evidence. Fourteen rules are carded.

## Formulation layer

The canon names a short list of property sources: round trip, equivalence with a simpler oracle or model, preserved invariants and 'does not crash'. Wlaschin and Hughes add commutation, idempotence, induction and metamorphic relations. On the mechanics the sources agree: build valid inputs by construction rather than filtering them; filter rather than use assume; never return early to skip an input; let shrinking stay inside the generator's domain; keep failing inputs as permanent regression cases; and bound the run in CI with a separate nightly budget. The official documentation for Python (Hypothesis, whose docs now live under hypothesis/docs, not hypothesis-python/docs), Rust (proptest book), TypeScript (fast-check), Go (testing/quick, native fuzzing) and Haskell (QuickCheck Haddock) was fetched and quoted. The Pragmatic Programmer topics 42 and 23 could not be opened, so they appear as marked paraphrases; Hughes's 'How to Specify It!' and the QuickCheck paper are also unfetched, and Nelson Elhage's 'Two kinds of testing' post was not reachable. jqwik's user guide was not mined because the project says it is not meant to be used by AI agents. The canon disagrees in six places: whether to persist a seed (proptest) or the failing value (QuickCheck, Hypothesis, Go); whether CI runs should be derandomized (Hypothesis default) or random with a reported seed (fast-check, proptest); whether concrete examples (Henney) or properties (Wlaschin) make the clearer specification; whether fuzzing counts as property-based testing; whether shrinking should be integrated or type-based; and whether 'sorted and same length' is a sufficient sort property (the Pragmatic Programmer example, recalled from memory) or whether it must also be a permutation (Henney).

## Reception layer

Across Python, Go, Rust, TypeScript, Java and the Haskell original, the frameworks' own documentation and runtime checks agree on four points. Inputs should be generated valid by construction rather than filtered: Hypothesis raises filter_too_much once 50 inputs are filtered out before 10 valid ones are generated, proptest caps global rejects at 1024, and QuickCheck's cover/checkCoverage shows how few non-trivial cases a filtered generator leaves. The test body must be deterministic (Hypothesis Flaky, Go F.Fuzz). Shrinking is a core feature, though MacIver's threshold-problem post limits what a minimal counterexample tells you, and his integrated-shrinking post disputes QuickCheck's type-based shrinking. The canon disagrees in four places. (1) Persisting a failure: proptest stores the seed and asks for the regression file to be committed, while QuickCheck, Hypothesis (prefer @example) and Go (testdata/fuzz) save the value itself. (2) Determinism in CI: Hypothesis's ci profile derandomizes and fast-check offers a constant seed; jqwik guards against committed fixed seeds and proptest seeds randomly with committed regressions; Elhage's two-kinds split and CPython's non-blocking Hypothesis job are the practical resolution. (3) Run length: defaults are 100, 256 or 1000 cases, the 2026 Hegel skill asks for thousands, and Ravi and Coblenz (OOPSLA 2025, abstract fetched via SIGPLAN OpenTOC) found 76% of mutations within the first 20 inputs. (4) Examples versus properties: Henney's concrete-examples critique and Wlaschin's EDFH stand against fast-check's hybrid stance, and proptest's claim that random testing misses single-value edge cases is disputed by boundary-biased generators. WebSearch was exhausted, so HN/Lobsters threads, Elhage's and Hillel Wayne's blogs, and the ICSE 2024, Tyche and How-to-Specify-It full texts were not opened; no static-analysis rule checks property quality (Ruff/Pylint/Semgrep searches were empty, and go vet checks only fuzz-test shape).

ICSME 2023 (reached only through ICSE 2024's related-work statement) and the original QuickCheck papers (only the orchestrator's relayed snippet). The sources disagree in three places. First, fixed seed versus fresh seed: Hypothesis derandomizes in CI and suggests a separate randomized nightly run, while proptest and fast-check default to random seeds. Second, keeping a failure as a seed versus as the value: proptest persists seeds, while QuickCheck and Hypothesis say store the value as an explicit example because seeds and blobs are not stable across versions. Third, who controls the input distribution: Hypothesis refuses user control, while ICSE participants wanted realistic or tuned distributions. 'Construct valid inputs rather than filter' is backed by measurement (Etna) only for sparse preconditions, and ICSE OB5 records the cost of hand-written generators.

9. **A generator yields inputs that meet the property's precondition by construction, through its own bounds, a mapping or a composition, whenever a filter or discard would reject a large share of draws, and keeps a filter only for a condition that random draws rarely violate** — Constrain the generator rather than discard its values. Use the generator's own bounds (a minimum length, a numeric range). Map a freely generated value into the valid domain: an even number as twice an integer, an interval as the min and max of two draws, a sorted list by sorting. Or compose a valid value from its parts. Filtering is rejection sampling. It spends generation on values that are thrown away and can distort the distribution, every framework warns or aborts past a rejection limit, and in proptest a rejection during shrinking stops the search for a simpler counterexample. Where some discarding remains, Hypothesis and proptest tolerate a filter on the generator better than a discard of the whole case. Answer the framework's filtering health check by fixing the generator; Hypothesis advises suppressing a health check only individually, as it is encountered, never wholesale. Limits: hand-written generators cost effort, which practitioners resent, so the rule binds only where the filter rejects a large share.
