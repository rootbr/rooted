# Research note — Information hiding and encapsulation

Topic `information-hiding-and-encapsulation` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: CC5 (Code Complete 2nd ed. ch. 5 'Design in Construction': the heuristics 'Hide Secrets (Information Hiding)' and 'Encapsulate Implementation Details'); CC6 (Code Complete 2nd ed. ch. 6 'Working Classes': good class interfaces, abstraction and encapsulation); APOSD ch. 5 'Information Hiding (and Leakage)' as a second formulation.

The canon agrees on Parnas's criterion: a module hides behind its interface the design decisions that are difficult or likely to change, the same decision known to a second module is leakage (Code Complete's excessive distribution, A Philosophy of Software Design's information leakage), and every declaration gets the narrowest visibility its users need (Code Complete ch. 6, Effective Java Item 15). Official documentation and tool rules in all five languages back narrow visibility (PEP 8, Rust's private default and unreachable_pub, Go internal packages, Google Go and TypeScript style, IntelliJ WeakerAccess, PMD, Error Prone) and forbid reaching into members marked non-public (Pylint W0212, Ruff SLF001, the Python tutorial, PMD InternalApiUsage, Google TypeScript style). The industry splits on four edges, and each is resolved here by a sourced condition. Checkstyle, Sonar S1104 and the .NET guidelines hide every field, while Rust C-STRUCT-PRIVATE, clippy partial_pub_fields, C++ C.2, SpotBugs PA_* and Java records accept public fields for passive data; whether the type keeps an invariant separates them. Code Complete, Effective Java and Sonar treat getter and setter pairs as encapsulation, while APOSD, Clean Code, C++ C.131 and the Google Python and TypeScript guides call trivial ones useless; whether the language has uniform access separates them. PMD DataClass, Refactoring and Tell-Don't-Ask move behaviour into the data holder, while records, Rust's passive data and Hickey accept transparent carriers. Guava and Google Go forbid widening to public for tests, while Sonar S2039, Checkstyle and Effective Java tolerate package-level access. Google Go style also contests returning interfaces over concrete types. Research is thin. Lampson 1983 and the relayed abstract of Mo et al. 2021 (files that change together without a structural dependency are more bug- and change-prone) back the leakage card. Palomba et al. 2018 back the data-holder card only indirectly, through Feature Envy's factor-8 fault-proneness, a method-level measure shared with coupling-and-dependency-direction. The same study and Palomba 2014 count against a blanket field rule: classes with a public field were common, no more change-prone, and not seen as a problem by developers. Parnas 1972, Khomh 2012, Sjøberg 2013, Wong 2011, Zoller and Schmolitzky 2012 and Vidal 2016 could not be opened, and no openable study measures the harm of Data Class or of over-exposed access modifiers.

## Formulation layer

The sources agree on Parnas's criterion: a module hides a design decision, its secret, behind its interface, and no second module may know that decision. APOSD calls the failure information leakage; McConnell calls it excessive distribution and semantic violation. They also agree on narrow visibility: Effective Java 15, McConnell, PEP 8, the Google TypeScript and Go guides, Go internal packages, Rust's private-by-default, and Software Engineering at Google's minimal module visibility all ask for it. The main split is over accessors. McConnell, Effective Java 16, .NET field design and Rust C-STRUCT-PRIVATE treat accessor methods as the encapsulated alternative to public fields. APOSD, Clean Code, C++ Core Guidelines C.131 and the Google Python and TypeScript guides hold that trivial pass-through accessors add nothing: make the field public, or design operations at the level of the abstraction. Meyer's uniform-access principle accounts for much of this split, because languages with properties can keep field syntax and still change the representation. Data holders split the same way, and so does widening visibility for tests. 97 Things, Refactoring's Data Class smell and Tell-Don't-Ask move behaviour into the class that owns the data. Clean Code's data/object anti-symmetry, C++ C.2, Java records and Rust's 'passive data structures' accept transparent carriers, and Clojure rejects encapsulating information outright. On tests, Effective Java and Clean Code allow package scope as a last resort, while Software Engineering at Google says to test through the public API. Code Complete, APOSD, Clean Code, Effective Java, Refactoring, The Pragmatic Programmer, OOSC, The Mythical Man-Month, Fowler's bliki and Parnas 1972 could not be opened from this environment: no GitHub copy was found and the WebSearch budget is spent. They are recorded as unfetched paraphrases. The aposd-vs-clean-code discussion was fetched, but it does not take up information hiding, visibility or accessors directly.

## Reception layer

The reception mostly argues about two edges of information hiding, not about the principle. Using the narrowest visibility is uncontested and checked mechanically in all five languages: Checkstyle VisibilityModifier, IntelliJ WeakerAccess, rustc unreachable_pub, Pylint protected-access, Ruff SLF001, Go's capitalised export rule and internal directories, and Google's TypeScript and Go guides. The limits are that Python hides only by convention, TypeScript `private` holds only during type checking, and ESLint and Google's TypeScript style disagree on #private. The first live dispute is whether a private field behind a getter and setter for each field counts as encapsulation. Sonar S1104 and the .NET Framework Design Guidelines prescribe accessors; C++ Core Guidelines C.131, Google Python 3.15, Google TypeScript and PEP 8 say a trivial accessor adds nothing over a public field; Holub and Bugayenko reject accessors outright, against Bozhanov and Fowler. The second dispute is whether a data holder without behaviour is a smell: PMD DataClass and Landre say yes, while Goetz (records), Rust C-STRUCT-PRIVATE, clippy partial_pub_fields, C++ C.2, Clean Code's DTOs, the Jerzyk catalogue and Hickey exempt passive data, and Moseley and Marks doubt that encapsulation suits constraints spanning several objects. Guava, Software Engineering at Google and Google Go style resist widening visibility for tests, but Checkstyle and Sonar defaults tolerate it, and Hyrum's Law marks where visibility stops hiding anything. With WebSearch exhausted, Hacker News, Lobsters, martinfowler.com, Holub's article, Muratori's post and the SpotBugs EI_EXPOSE_REP issue thread (#1601, refused by the GitHub API) could not be opened: Fowler and Muratori are unfetched paraphrases from memory, and Holub and Bozhanov are relayed only through Bugayenko's fetched post.

## Evidence layer

Documentation and tool rules back the core rules with fetched text in all five languages: fields stay hidden (Checkstyle VisibilityModifier, Sonar S1104, Rust book ch. 18.1, Rust C-STRUCT-PRIVATE), visibility starts narrow and is widened on demand (PEP 8, Rust book ch. 7.3, rustc unreachable_pub, Go internal packages, Google Go best practices, the TypeScript handbook), no reaching into members marked non-public by convention (Pylint W0212, Ruff SLF001), and tests do not justify wider visibility (Guava @VisibleForTesting, Google Go "back doors"). On research, fetched: Lampson 1983 ("Keep secrets of the implementation") and Mo et al. TSE 2021 through its neverworkintheory abstract, whose "modularity violation groups" (files that change together with no structural dependency) are the measurable form of leakage. Also fetched are two Palomba et al. preprints, which contest the field-privacy rule: Class Data Should Be Private appears in 76% of 395 releases, yet classes do not become more change-prone while affected, removing it has "Limited" effect, and developers mostly do not see it as a problem. The canon also disagrees on accessors. Sonar S1104 prescribes a getter and setter per field. PMD DataClass counts accessors as a smell, and the Google Python guide and PEP 8 say to make a trivial getter/setter attribute public. Rust C-STRUCT-PRIVATE, clippy partial_pub_fields and Java records all allow fully public fields for passive data that has no invariants. Parnas 1972, Khomh 2012, Sjøberg 2013, Wong 2011, Zoller & Schmolitzky 2012 and both Vidal et al. 2016 papers (including the "at least 20% of methods over-exposed" figure) could not be opened (WebSearch exhausted, no GitHub copy found), so they are unfetched and must not be the only anchor for any card. No openable study measures the effect of the Data Class smell itself.

## Spine — candidate rules in source order

1. **Each module hides behind its interface a design decision that is difficult or likely to change, so that changing the decision changes only that module** — Draw module boundaries around design decisions that are difficult or likely to change, such as a data structure, a file format, an algorithm or a platform dependency, and keep each decision in one module's implementation, out of its interface. Callers then see the module only at the level of its abstraction, and a change to the hidden decision touches that module alone. Lampson attaches the condition that hiding trades against exposing power and performance, so where the boundary goes is a judgement, not an absolute.

2. **A design decision such as a data format, an encoding, a record layout or an identifier scheme is encoded in only one module, and other modules reach it through that module's interface** — When added code reads, writes or assumes a decision that another module already embodies, such as the same file or wire format parsed in two places, the same byte layout or delimiter, the same key names or identifier scheme, or a reader and a writer that each know the format, the decision has leaked: changing it means changing every module that knows it, and no interface shows that they must change together. Route the new code through the owning module's operations, or move the shared knowledge into one module that both use, which also covers a split by execution order (read, modify, write) that spreads one format over several classes. Using a standard format through a common library is not a leak by itself, since what leaks is the project's own decision, such as which fields a record carries and what they mean; and a decision a module states in its published interface is a commitment of that interface, not back-door leakage. The evidence ties files that change together without a structural dependency to higher bug- and change-proneness, as a correlation at file level.
