# A declaration uses the unchecked dynamic type only where the type system cannot express the value, and otherwise uses a specific type or the checked top type

## Thesis
Where a language has both an unchecked dynamic type — every type is assignable to it, it is assignable to every type, and any operation or method call on its value passes without a check — and a checked top type, to which every value is assignable but which admits almost no operation and no assignment to a more specific type until the value is narrowed, a declaration that a change writes gives its parameters, results, fields, variables, type arguments and constraints a type other than the unchecked one wherever another type expresses the value appropriately without being unergonomic to write. A value of a known type is declared with that type. Where the code does not care what type the caller operates on, as when it hands back an element of the caller's list, the value is declared with a type parameter. A parameter that accepts literally any value, a callback result that is ignored, and a value of unknown shape that the code narrows before use are declared with the checked top type, and a constraint that would admit every type is left out. The unchecked type is kept for a type that the type system cannot express appropriately or whose correct type would be unergonomic to write, for a value from code that has no types yet, and for a partial test double; where it is written, a comment beside it, or the lint suppression, states why it is legitimate, unless the reason is obvious, as for the unchecked type written as the type argument of an invariant generic type to admit any instance of it, or as the value type of a string-keyed map whose value types depend on the keys.

## Rationale
Every type is assignable to the unchecked dynamic type and it is assignable to every type, so a checker allows any operation or method call on such a value and performs no check when the value is assigned to a more precise type: a variable declared as a string can receive an integer at run time with no error reported. Returning such a value from a routine, or passing one as an argument, creates a potential type-safety hole and source of bugs. As such the unchecked type can mask severe programming errors, its use undermines the value of having static types in the first place, and it disables many type-checking rules. The checked top type expresses the same concept, a value that might be any kind of data, but the checker rejects arbitrary member access, almost every other operation and any assignment to a more specific type until a type guard narrows the value, so the value is used in a type-safe manner. Where the type is known, a specific type is preferable, and where the code does not care what type the caller operates on, a type parameter: either is explicit about the type of the expression, where the unchecked type lets every operation on it pass. Switching an unchecked type to the checked one is safer but is likely to cause additional type errors: the checked type requires the value to be narrowed to a more specific type before it is used, so the fix narrows it with a type guard where it is used.

## Example
```typescript
bad:  function label(value: any): string { return String(value); }
      function priceOf(item: any): number { return item.price; }
      function first(items: any[]): any { return items[0]; }
good: function label(value: unknown): string { return String(value); }
      function priceOf(item: Priced): number { return item.price; }
      function first<T>(items: T[]): T | undefined { return items[0]; }
```

## Limits
The unchecked type is used where a type cannot be expressed appropriately with the current type system or the correct type is unergonomic to write, and where particularly complex or nuanced code cannot yet be represented in the type system. It is also used for a value from an external package that has no type declarations yet, pending their addition, and temporarily in a project not yet fully moved onto static types, in places where types are not yet known or representable. It is legitimate in a test that needs only a partial implementation of a type, cast through the unchecked type as an intentionally unsafe partial double, where anything overlooked makes the test fail in an obvious way. A result whose precise type would be a union that every caller has to narrow with a runtime type check may be declared with the unchecked type, alone or in a union with the one member type that callers rely on, where necessary. Two linters offer an option, off by default, that exempts variadic parameters from this check; a project that turns it on tolerates the unchecked type on a variadic parameter, and that setting rejects the finding. Where the language's no-result type accepts a callback that returns a value, an ignored callback result declared with that type meets the rule as well, since that type also keeps the result from being used unchecked. The rule reaches the types a change writes: a parameter or result left without a type, which a checker treats as the unchecked type implicitly, is outside it, and a compiler option that prevents that implied form does not prevent the written form this rule addresses. The comment beside a legitimate unchecked type is a style-guide expectation rather than a requirement of the language documentation: a project whose style guide or linter configuration does not require a documented reason beside a legitimate use rejects a finding that rests on the missing comment alone, and the finder then reports only an unchecked type that another type would express.

## Validator
Grep the added lines for the unchecked dynamic type in a type position, written bare or qualified by its module: after a colon or a return arrow, including the arrow of a function type, as an array or tuple element type or a type argument in any position, as a type parameter's constraint or default, as the target of a type alias, and in an import that brings it into scope for annotations, in which case check the declarations in the hunk that use it. Confirm that the name is the file's language's unchecked dynamic type — assignable to and from every type, with every operation on its value unchecked — and set aside a checked top type that shares the spelling, a trait or interface named Any used as a bound, a cast, and a parameter or result written with no type. For each declaration that writes it, read in the hunk how the value is used: members read on it, an initializer, arguments or a stored shape that show one type call for that type; a value handed back to the caller with the caller's own type calls for a type parameter; a value that is only passed to something that accepts anything, ignored, or narrowed by a type guard before use calls for the checked top type; a constraint of the unchecked type alone is dropped. Where none of these serves — a type the hunk shows cannot be written or would be unergonomic to write, a value from a module or package without types, a partial test double, a result that would otherwise be a union every caller narrows — look beside the declaration for a comment or a lint suppression that states why; the unchecked type as the type argument of an invariant generic type admitting any instance of it, or as the value type of a string-keyed map whose value types depend on the keys, needs none. Set aside a variadic parameter that the project's linter configuration exempts. Validator question: **Does an added declaration write the unchecked dynamic type where a specific type, a type parameter or the checked top type expresses the value without being unergonomic to write, or write it, where the reason is not obvious, with no comment stating why it is legitimate?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-46`, severity major, `file`, `symbol`, `code` = the added line that writes the unchecked dynamic type, verbatim from the diff, `fix` = the declaration with the specific type, the type parameter or the checked top type that the uses in the hunk support, or without a constraint that admitted every type, with a type guard where a checked top type value is used, or, where no other type serves, the unchecked type kept with a comment stating why it is legitimate, in the file's language, `rationale` = the uses in the hunk that show which type fits, or the legitimate case the missing comment has to name, and the checks the unchecked type turns off).
