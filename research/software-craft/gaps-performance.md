# Research note — Concepts the performance reviewer found uncovered

Topic `gaps-performance` of group G. Diagnostics and performance, domain `performance`, id prefix `PRF`. Formulation locators: the taxonomy topics of the concepts and their canon locators: algorithm-and-data-structure-choice (PoP2, PP "Algorithm Speed"); profiling-and-code-tuning (CC25–26, PoP7, SW4.14).

The canon states four of the five gap concepts directly and the fifth only as a cost principle. Kernighan and Pike say a hand-grown array grows by doubling, because growing it one element at a time is O(n^2) (PoP §2.6, §4.3; GOPL §4.2.1 and Pike's Go blog agree). They say a hash function must spread keys uniformly, and that a hash which reads only part of the key gives long chains and O(n) lookups (PoP §2.9, §5.3; Effective Java Item 11 is the classic formulation of the constant-hash and one-field cases). They say buffering spreads the cost of an I/O operation over many values (PoP §7.4; CC §25.3 on system calls, relayed). Compiler optimization changes timings, and the optimizer is turned on before measuring (PoP §7.3, §7.6; PP Topic 39; CC §25.2, relayed). Unnecessary I/O in speed-critical code is a major source of inefficiency (CC §25.3, relayed), but no locator book names per-record queries: 97 Things #41 calls them ripple loading and credits Fowler's Lazy Load, which could not be opened. Official documentation states each concept in checkable form. The Rails, Django, SQLAlchemy and Hibernate docs cover N+1 queries and their eager or batched fix, and SQLite's own page (opened through a packaging mirror) says per-statement round trips make N+1 an anti-pattern for client/server engines but not for in-process SQLite. The JDK, Rust, Python, Go and C++ Core Guidelines docs cover buffering small repeated writes unless prompt output is required. The CPython list source, folly, the JDK, Rust Vec, C++ [vector.overview] and the Go runtime show that proportional capacity growth gives amortized constant appends. The JDK, Python, .NET, Rust and C++ docs say a key hash should mix the fields equality compares, and that many keys sharing a hash slow any table to O(n). The Rust Book and the Visual Studio profiling docs say to time the optimized build, and BenchmarkDotNet and Google Benchmark check this. The industry disagrees in four places. N+1 is a defect for a database server but not for an embedded engine. Buffering trades prompt output for throughput, and some runtimes already buffer. The growth factor is disputed (folly against 2; CPython about 1.125; Go 2 to 1.25), though proportional growth itself is not. Hibernate recommends a constant hashCode for entities whose only identity is a generated id. Each of these disputes either has a sourced separating condition or falls outside the rule as worded. No static rule flags constant-step growth, a poorly dispersing hash or unbuffered writes. No openable empirical study measures any of the five concepts, and the local hands-on runs (quadratic Vector(10,16) and constant-hash maps, about 3-10x for unbuffered writes, 27x for a Rust dev build, about 8x for per-record SQLite queries) are not yet committed as fixtures. So four cards default to minor, and the N+1 card defaults to major on the documentation's own description of the failure.

## Formulation layer

The canon states four of the five concepts directly. It states the fifth, I/O issued once per element, only as general guidance on what operations cost: none of the locator books (CC25–26, PoP2, PoP7, PP 'Algorithm Speed', SW4.14) names N+1 queries. 97 Things #41 names the pattern 'ripple loading' and credits Fowler's Lazy Load, which could not be opened. Array growth: PoP §2.6 and §4.3, Kernighan's GOPL appendInt and Pike's Go blog all double the capacity, and folly's FBVector doc agrees that any factor above 1 gives amortized O(1) appends but disputes the factor 2 itself. Hash dispersion: PoP §2.9 and §5.3, Effective Java Item 11 ('return 42'; do not leave significant fields out of the hash) and Dean and Ghemawat's Performance Hints say that a hash sending many keys to the same values turns lookups into O(n) and n inserts into quadratic time. Buffered output: PoP §7.4, CC §25.3 (via reading notes), C++ Core Guidelines SL.io.50 and the Rust Performance Book state buffering, and PoP §5.3 names the limit (log files and stderr may stay unbuffered when output must survive a crash). Build under measurement: PoP §7.3 and §7.6, PP Topic 39, CC §25.2 (notes) and Performance Hints say the optimization level changes timings and production binaries are built optimized, but among the formulations only the Rust Performance Book tells the reader outright to use the release build. Code Complete was reached only through two third-party reading notes (marked relayed). SWEBOK V4 §4.14 was not openable, and V3 §4.14 says nothing on these concepts. The APOSD–Clean Code discussion takes no position on them, and a search for PoP errata found nothing.

## Reception layer

I built the reception layer without WebSearch, because the budget was used up and Hacker News, Lobsters and vendor sites are denied. It rests on tool rule pages, framework and runtime documentation, and practitioner texts hosted on GitHub. No forum thread was opened, so contested positions come from named projects and documents instead. Coverage of the five concepts by tools is uneven:
- I/O per element: checked mechanically, but in narrow framework-specific forms. PMD Apex OperationWithLimitsInLoop is in the quickstart ruleset and Semgrep mirrors it; Semgrep has a Django foreign-key rule; Bullet and nplusone detect N+1 at runtime; ESLint no-await-in-loop is off by default and lists its own exceptions.
- Unbuffered output: no rule found for writes. Clippy unbuffered_bytes covers only Read::bytes.
- Constant-step growth: no rule found.
- Hash dispersion: no rule found, and Sonar S9362 explicitly declines to flag it.
- Release-build benchmarking: enforced by benchmark harnesses rather than linters. BenchmarkDotNet refuses non-optimized assemblies by default, Google Benchmark warns about a DEBUG library build, and cargo bench inherits the release profile.

The canon disagrees on four points:
- I/O per element: whether N+1 is a defect at all. Cloudflare's Cap'n Web docs and the SQLite page they cite say it is not when the database is in-process. Bullet and nplusone also flag eager loading that is never used.
- Unbuffered output: buffering trades prompt output for throughput. The BufferedWriter Javadoc, the Rust Stdout FIXME and the Node process-I/O note each say why output is flushed promptly.
- Growth factor: folly argues that 2 is the worst factor for memory reuse, against gcc, Go's small-slice doubling and the Go blog example. Proportional growth itself is not disputed. Java's legacy Vector still offers a fixed capacityIncrement.
- Constant hash: the Hibernate user guide and the JHipster/Mihalcea entity pattern recommend a constant hashCode for entities with generated ids, and SpotBugs recommends a constant for types never put in a hash table. Separately, CPython's dict and the perf-book argue that a regular or low-quality hash is acceptable as long as unequal keys rarely share a hash.

Dean and Ghemawat deliberately ran one benchmark in DEBUG mode because the code under test runs only there, which is the one recorded exception to the release-build rule.

## Evidence layer

I found openable sources for all five concepts. No empirical SE study could be opened from here for any of them, so each candidate rule rests on official documentation, standards, tool rules and local hands-on runs. (1) I/O per element: the Rails, Django, SQLAlchemy and Hibernate docs plus three tool rules (fb-contrib SIL_SQL_IN_LOOP, Semgrep batch-import, Bullet) state the N+1 cost and the batched or eager-load fix. Their own limits are the SQL-count/complexity/data trade-off, unused eager loading and bulk_create caveats. SQLite's "many small queries are efficient" page disputes the cost for an in-process engine but could not be opened. (2) Unbuffered output: JDK BufferedWriter/BufferedOutputStream, Rust File/BufWriter and Python io state the rule, with conditions: small repeated writes, flush before drop, and "on Linux unbuffered disk I/O can be as fast". JDK's own OutputStreamWriter doc and a local run show that a Java FileWriter already buffers bytes, which contests the BufferedWriter wording; a raw byte stream or a flush per write is where the cost appears (about 5-10x locally). (3) Array growth: CPython, the Python FAQ, Rust Vec, ArrayList, C++ [vector.overview], folly and Go's growslice all use or require proportional growth for amortized O(1) append. Java's Vector(capacityIncrement) is a real fixed-increment API that ran quadratically locally. folly contests factor 2 against 1.5, not proportional growth itself. Fixed-increment growth through glibc realloc ran in linear time locally, matching CPython's "poorly-performing realloc" condition. (4) Hash dispersion: HashMap, Object.hashCode, Python __hash__, .NET GetHashCode/ValueType, Rust Hash and C++ [hash.requirements]/[unord.req] state it. Java 8+ tree bins soften constant hashes for Comparable keys, which the local Java run confirms. SpotBugs recommends a constant 42 only for classes never hashed. No static rule flags a constant or one-field hash. (5) Release build: the Rust Book, Visual Studio profiling docs, BenchmarkDotNet's validator and Google Benchmark's DEBUG warning state it. VS adds that I/O-bound problems differ little between the builds, which a local C run confirms. A local Rust run showed 27x and a ranking flip between two alternatives. Papers not opened (unfetched, never sole anchors): Chen et al. ICSE 2014, Yang et al. ICSE 2018, Crosby & Wallach 2003. The Rust Performance Book and Abseil Performance Hints are included only as formulation.

## Spine — candidate rules in source order

1. **An array or buffer whose capacity the code grows by hand enlarges it by a factor of its current size, not by a fixed number of elements, when its final size grows with the input** — This applies where code manages an array's or buffer's capacity itself: a reallocation to the old size plus a constant, a copy into a new array a fixed step longer, a vector constructed with a positive fixed capacity increment, or an exact reservation of a few more elements before each append. There, each growth enlarges the capacity in proportion to the current size, by any factor greater than 1. CPython states that its list over-allocates proportional to its size, which gives linear-time amortized appends even with a poorly performing realloc. Folly states that a vector grows at a constant factor to avoid quadratic growth performance, and that any factor greater than 1 gives O(1) amortized append. The Java, Rust and C++ standard growable arrays promise amortized constant-time append. Java's Vector, by contrast, documents that a positive capacityIncrement grows the array by that fixed amount, and its grow method copies the whole array each time. The factor itself is disputed (folly argues 2 is the worst for memory reuse, CPython uses about 1.125, and Go moves from 2 towards 1.25), so the rule fixes no factor. Several cases are out of scope: a library growable array left to its own policy, a capacity reserved once to a known final size, a buffer the domain bounds to a few growths, and copying a whole immutable value on every append, which PRF-17 owns.

2. **A hash function that a type defines for its use as a map key or set element combines the fields its equality compares, and does not return a constant or hash only a field that many unequal keys share** — A type whose instances serve as keys of a hashed map or elements of a hashed set computes its hash from the components that take part in its equality, for example by hashing a tuple of them. It does not return a constant, and it does not hash a single field whose value many unequal keys share. The JDK says that using many keys with the same hashCode is a sure way to slow down any hash table, and that distinct hash codes for unequal objects may improve hash-table performance. Python advises mixing the hashes of the components used in comparison. .NET states that a poor hash makes a search O(n), and that a default hash over only some fields of a value type is unlikely to suit use as a key. Rust asks unequal values to feed different sequences to the hasher. The C++ draft asks the probability of equal hashes for different values to be very small and gives a worst case of O(size) for lookups. Several cases are outside the rule: a type never put in a hashed collection (SpotBugs recommends a constant with an assertion there); a single field that alone decides equality; fields that equality ignores, which must stay out of the hash; and a fast but lower-quality hash algorithm or a regular integer hash, since the defect is many unequal keys sharing one value, not imperfect randomness. In Java, tree bins bound the cost to O(log n) when the colliding keys are Comparable, which the Limits must say.

4. **Code that handles each element of a collection whose size grows with the input does not send one statement per element to a client-server database where one batched, joined or eager-loading statement would fetch or write the same data** — Two shapes are covered: a loop over records that issues one query per record to load related data (the N+1 queries problem), and a loop that writes rows one at a time. The fix is to load the related records in advance with one batched, IN-list, joined or eager-loading query, and to write with the bulk methods. Rails, Django, SQLAlchemy and Hibernate document the N+1 pattern and its eager or batched fix. Hibernate calls it the most common cause of poorly performing data access code and says it affects handwritten JDBC code as well. SQLite's documentation explains the cost: in a client/server database each statement is a message round trip, and many of them in sequence are a serious performance drag and an anti-pattern. Several cases fall outside the rule. An in-process engine such as SQLite is excluded, because there a query is a function call and SQLite states that many small queries are not a problem. A statement whose parameters depend on the previous result, a loop the domain bounds to a handful of elements, and associations the loop does not read are also excluded: Bullet reports unneeded eager loading as waste, and SQLAlchemy frames the choice as a trade-off between the number of statements, the complexity of the SQL and the amount of data fetched, so the fix may be a second IN query rather than a join. Remote calls per element other than database statements rest only on formulation sources (Stafford, Dean and Ghemawat), so they are recorded in the research note and kept out of the Thesis. 5. **Many small repeated writes to a file, socket or other stream that does not buffer go through a buffered writer that is flushed when the writing ends, and are not flushed one by one, unless the output is required to appear promptly** — A loop or routine that makes many small write calls to a destination that does not buffer wraps it once in a buffered writer and flushes or closes it after the last write. Such destinations include a raw file handle, a socket, a file descriptor written with a system call, a file opened with buffering disabled, or a stream set to flush after every write (an autoflush writer, endl, print with flush). The Rust File documentation advises wrapping a file in a BufWriter for many small write calls unless unbuffered writes are required. BufWriter's documentation says each write on a TcpStream is a system call, that buffering helps small repeated writes, and that the writer must be flushed before it is dropped. The JDK says a buffered output stream avoids a call to the underlying system for each byte, and recommends a BufferedWriter around costly writers unless prompt output is required. Python calls buffered I/O almost always preferable for binary data, while noting that the gain depends on the OS. The C++ Core Guidelines say endl slows output by redundant flushes and that a file rarely needs flushing. Go's bufio requires Flush after all data is written. Several cases fall outside the rule. Streams the runtime already buffers are excluded: Python files and non-interactive stdout, and a Java OutputStreamWriter or FileWriter, which accumulates encoded bytes so that a BufferedWriter there only saves converter calls. Also excluded are a few large writes, an in-memory destination, and output required promptly, such as interactive prompts, progress, and logs or error streams that must survive a crash.
