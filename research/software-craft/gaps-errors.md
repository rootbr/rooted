# Research note — Concepts the errors reviewer found uncovered

Topic `gaps-errors` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: the taxonomy topics of the concepts and their canon locators: error-and-exception-handling (SW4.5, CC8, PP "Dead Programs Tell No Lies"); fault-tolerance-retries-timeouts-fallbacks (SW4.5).

The four concepts the errors reviewer found without a card sit at very different levels of evidence. (1) Catch and release, a handler that only re-raises the error it caught, is framed by The Pragmatic Programmer (Topic 24, in its log-then-re-raise form) and by C++ Core Guidelines E.17, which uses the do-nothing-then-rethrow handler as its bad example. Default-on tool rules agree that such a handler has no effect and should be removed: Ruff TRY203, ESLint no-useless-catch, Sonar S2737, PMD AvoidRethrowingException, Pylint W0706 and detekt RethrowCaughtException. They also share one precondition: a bare re-raise placed ahead of a later handler for a supertype is a deliberate carve-out. The log-then-rethrow fix that Sonar suggests is the separate dispute already held in pending-evidence, so the card names removal as the fix. No empirical study measures the pattern, so it ships as a minor card. (2) Leaving a finally block through return, break, continue or an explicit throw is the best-supported concept. The rule is stated by language standards and specifications (ECMA-262 try evaluation, the C# standard §13.11, which makes the jumps compile-time errors, Swift defer, the Python reference, and PEP 765, which is Final and adds a 3.14 SyntaxWarning), by CERT ERR04-J, and by lint rules nearly everywhere. One public analysis (Katriel: 149 of 203 such statements in 121M lines of top PyPI code were exception-swallowing bugs) adds measured harm. The 2019 PEP 601 rejection treated the rule as a style issue, and PEP 765 superseded that rejection with the data. Two preconditions hold: a jump whose target stays inside the finally block, or inside a function nested in it, is fine; and Python chains the saved exception as context on a raise in finally, so the throw form applies only where the language discards the pending error. Implicit throws from cleanup calls belong to the resource-release cards. (3) Telling errors apart by type, identity or fields rather than message text rests on official documentation: Google Go best practices and decisions, Node.js error.code, MDN, the Go 1.16 net.ErrClosed note and Effective Go. No tool rule and no empirical study was found. The canon disagrees at the edge: MDN's own example switches on messages the same code defines, and Google allows tests to check properties of their own package's messages. The card therefore rests on a separating condition, namely whose message is matched. Dave Cheney's objection to sentinels and types is unfetched, and Go has since deprecated his flagship behaviour method. The producer half of the concept already lives in ERR-09. (4) Circuit breaking is described in Azure's Retry and Circuit Breaker patterns and in library documentation. Azure's own not-suitable list, AWS and Brooker (breakers are modal and turn partial failures into total ones in sharded systems), and Netflix's move to adaptive limits all contest it. The term is overloaded (Envoy uses it for concurrency limits), library thresholds disagree, the breaker is configured per client or in the mesh rather than at a call site, and no tool checks it. It is held as not checkable, consistent with the fault-tolerance topic having held circuit-breaker architecture outside the corpus.

## Formulation layer

(1) Bare re-raise: the canon calls it catch-and-release. The Pragmatic Programmer's Topic 24 (unfetched) frames it through an example that logs before each re-raise. C++ Core Guidelines E.17 (fetched) has exactly the do-nothing-then-rethrow handler as its bad example. The candidate Ruff TRY203 checks out. Its all-handlers condition and Pylint's try-except-raise details page give the precondition a card needs: a bare re-raise placed ahead of a broader handler is a deliberate carve-out. Sonar S2737's compliant example logs and then rethrows, so the log-and-rethrow dispute stays separate. (2) A finally that returns, throws, breaks or continues is undisputed. The candidate ESLint no-unsafe-finally checks out, and the Python reference, PEP 8, PEP 765 (resting on Katriel's analysis: 149 of 203 instances in 121M lines were bugs), ECMA-262, the C# standard (compile-time errors), Swift, javac -Xlint:finally, Error Prone and the .NET guidelines all state it. Two preconditions apply: a jump that leaves only a function or loop nested inside finally is fine, and .NET accepts exceptions thrown implicitly by methods called from finally. (3) On distinguishing errors by type or fields rather than message text, the candidate Google Go best-practices text checks out. Effective Go, the Go 1.13 blog, Uber, PEP 8, Node.js, MDN, .NET and C++ E.14 agree. Scope preconditions apply: Go tests may check properties of their own package's messages, and MDN switches on messages the same code defines. Cheney (unfetched) contests only the sentinel/type half. (4) For circuit breaking, the candidate Azure retry paragraph checks out, and the Azure Circuit Breaker page, Hystrix and Polly describe the closed/open/half-open machine. However, the Azure page's own not-suitable list and Brooker's 2022 posts contest it as a general rule (breakers turn partial failures into complete ones in sharded systems), and Envoy uses the same name for concurrency limits. No source states a form checkable at the call site, and the fault-tolerance note held circuit-breaker architecture outside the corpus. Not openable here and given as unfetched paraphrases: Code Complete, Clean Code, APOSD, Effective Java, Java Puzzlers, Release It! and the JLS. The APOSD-vs-Clean-Code discussion and Software Engineering at Google say nothing on these concepts.

## Reception layer

Static-analysis rules agree on two of the four concepts. A handler that only re-raises the caught error is flagged by Ruff TRY203 (now a Ruff default), Pylint W0706, ESLint no-useless-catch (eslint:recommended), PMD AvoidRethrowingException, Sonar S2737 and detekt RethrowCaughtException (active by default). Pylint, PMD, Ruff and detekt all exempt one case: a re-raise that keeps a subclass away from a later, broader handler. Sonar's suggested fix (log, then rethrow) runs into the pending log-and-rethrow dispute (Uber 'Handle Errors Once'), and in C# `throw ex;` actively destroys the stack trace (CA2200). Control flow that leaves a finally block is flagged almost everywhere: ESLint and Biome, Ruff B012, Pylint W0150, Sonar S1143, Error Prone Finally, PMD, CA2219, detekt, javac -Xlint:finally and CERT ERR04-J. C# and Swift ban it in the language. Python's own history records the dispute: PEP 601 was rejected in 2019 as a style issue (Guido: 'a conditional return ... may be useful'), then PEP 765 (Final, 3.14 SyntaxWarning) reversed that on Katriel's data, which found 149 of 203 uses in 121M lines were bugs. A `throw`/`raise` in finally is treated differently by language: Python chains the saved exception as context, so the Python tools leave raise alone, while Java, JS and C# flag throw. ESLint names a legitimate generator use. On matching error message text, Go (Google best practices, Uber, the Go 1.13 blog, Go 1.16 net.ErrClosed), Node.js ('error.message ... may be changed in any versions. Use error.code') and PEP 3151 all point callers to types, identities or fields. Google's Go decisions carve out one Limit: tests may check properties of messages from the package under test. No tool rule that checks message matching was found. Dave Cheney (unfetched) disputes sentinels and types in favour of behaviour checks, and Go itself deprecated net.Error.Temporary as 'not well-defined'. Circuit breaking is contested. Brooker ('Circuit breakers are designed to turn partial failures into complete failures') and the AWS Builders' Library ('modal behavior ... difficult to test') prefer retry token buckets. Netflix moved off Hystrix toward adaptive limits. Google SRE uses adaptive client throttling, and gRPC throttles only retries. Microsoft's own pattern page lists where breakers are unsuitable. The term is overloaded (Envoy uses it for concurrency limits), library defaults disagree widely, and no static-analysis rule checks it. The fault-tolerance topic run had already held circuit-breaker architecture outside the corpus. Not opened, because the WebSearch budget is spent and these are not GitHub-hosted: HN/Lobsters threads, Cheney's blog, Fowler's bliki (read only as quoted by Brooker), Release It!, The Pragmatic Programmer, McCune's antipatterns and the metastable-failure papers. Overlap for the spine: ERR-09's Rationale already says message matching is 'error-prone and hard to maintain', and ERR-02 counts a rethrow as acting on an error.

## Evidence layer

All four candidate sources opened over raw.githubusercontent.com and state their claims as given. Each concept also gained further tool-rule and documentation anchors. Concept 2 (an abrupt exit from a finally block) has the strongest support. It rests on standards and language specifications (SEI CERT ERR04-J/ERR05-J, the C# standard §13.11, ECMA-262 try evaluation, Swift defer, the Python reference with its 3.14 SyntaxWarning, and PEP 765, status Final) and on one empirical analysis with public scripts (Katriel: 203 control-flow statements in finally blocks across 120,964,221 LOC of the top 8,000 PyPI packages, 149 of them (73%) clearly incorrect), and local runs in Python 3.13, Node 22 and javac 21 confirm the override. Concept 1 (catch and release) rests only on tool rules (Ruff TRY203 and ESLint no-useless-catch, both on by default; Sonar S2737; PMD AvoidRethrowingException; Pylint W0706), whose behavior was confirmed by a local run. Pylint and Ruff carry one precondition: a re-raise clause placed before a broader handler of the same try is not useless. In C#, `throw ex` is not equivalent, because it resets the stack trace (CA2200). Concept 3 (tell errors apart by type, identity or fields, not message text) rests on official documentation: Google Go best practices and decisions, the Go 1.16 net.ErrClosed note, Node's error.code, MDN, Sonar S112 and the .NET guidance. No empirical study was found. The canon disagrees at the edges: MDN's own application-code example switches on err.message, Google Go permits message checks in tests of the package's own messages, and string matching was the only option before Go 1.16 added ErrClosed. Concept 4 (circuit breaking) has official documentation (Azure Retry and Circuit Breaker patterns, the .NET microservices guide, Resilience4j, Hystrix, Polly) and a standard that names it only as one option (OWASP ASVS 5.0 16.5.2). It is contested by the AWS Builders' Library and Marc Brooker (modal behavior that is hard to test; sharded or cell-based services turn partial failures into total ones), by Netflix's move to adaptive limits, and by Envoy using the term for concurrency limits. A breaker is configured per client rather than at the call site, and the fault-tolerance topic note already held circuit-breaker architecture outside the corpus. Not opened: arXiv:2512.16959, arXiv:2608.25403 and arXiv:1609.05830 (unfetched; the WebSearch budget is exhausted and arxiv.org is denied), CWE-584 (cwe.mitre.org denied), and the full texts of the de Pádua and Shang and Barbosa et al. papers, reached only through neverworkintheory reviews. No empirical study of bare re-raise handlers, message-string matching or circuit breakers was found in the NWIT bibliography, papers-we-love or the Morning Paper archive.

## Spine — candidate rules in source order

1. **A handler whose only statement re-raises the caught error unchanged is removed so the error propagates on its own, unless it keeps that error away from a later, broader handler of the same try** — A catch, except or rescue clause is removed when its body only re-raises the error it caught, unchanged: a bare raise or throw, or a raise or throw of its own bound variable, with no cause, no wrapping and no work before it. Such a handler has the same effect as no handler, and in C# the `throw ex;` form also restarts the stack trace. The try goes with it when no other handler or finally remains, except a try-with-resources or with statement, which still manages its resource. The clause is kept when a later handler of the same try catches a supertype of the type it names, because the immediate re-raise then keeps that subtype away from the broader handler. A handler that does any work before re-raising, re-raises only after testing a condition, or wraps the error or raises it as the cause of a new one is outside the rule. The fix is removal, not a log call added before the rethrow; whether to log and then rethrow is the separate log-and-rethrow dispute held in pending-evidence. ERR-02 counts a rethrow as acting on the error and ERR-08 accepts a catch-all that re-raises; this rule judges only whether the handler does anything at all. It applies to languages with try/catch; in Go and Rust, propagation is an explicit return or `?` and has no counterpart.
