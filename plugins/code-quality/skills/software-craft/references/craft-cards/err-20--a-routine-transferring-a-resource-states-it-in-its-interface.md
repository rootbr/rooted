# A routine that hands a resource to its caller, or takes over the release of a resource it is passed, states that transfer in its interface through documentation, an ownership annotation or its type

## Thesis
A routine that other code depends on, such as an exported or public routine or one in a library, states in its interface each transfer of a resource's release across its boundary: a resource it returns that its caller has to release, and a resource it is passed whose release it takes over. The statement says which side releases the resource and, where the way to release it is potentially unclear, how, as for a temporary file that has to be deleted as well as closed or a resource held inside the value the routine returns. The statement is a sentence in the routine's documentation, an ownership or must-close annotation that the project's checker reads, or a parameter or result type through which the language tracks who releases the value. A routine that takes over a resource it is passed and can fail after receiving it also states whether it releases the resource when it fails, because a failure it does not cover leaves the release with the caller.

## Rationale
When an interface leaves a cleanup requirement unstated, its callers do not use it correctly, which leads to resource leaks and other possible bugs. A program may leak resources when it is unclear which part of it is responsible for releasing them. A resource passed to or returned from a routine is reachable through more than one reference, yet it needs releasing only once, and an ownership statement says which of those references is responsible for the release. A leak checker that reads ownership annotations treats an unannotated routine's result as the caller's to release and never assumes that passing a resource to an unannotated routine releases it, so without the annotation on a parameter that the routine closes, the checker still requires the caller to close it. Under that checker's convention a routine takes over an annotated parameter only when it returns normally; if it fails, the caller has to catch the failure and release the resource, unless the routine is marked as releasing it on failure as well. A must-close mark lets an analyzer carry the obligation from routine to routine: it accepts a call to a marked routine where the result is held by the scoped-release construct or closed in a cleanup clause, or where it is returned from another routine that carries the same mark. In a language whose types move ownership with a value, the signature states the transfer: as a general rule no resource type can be implicitly copied, so passing a resource moves it into the routine, returning one moves it to the caller, and a reference lets the routine use a value without taking ownership. Standard-library documentation states such transfers in a sentence: a routine that creates a temporary file makes its removal the caller's responsibility, and an HTTP client says that, when the call succeeds, the body of the response it returns is the caller's to close and that the request body it is passed is closed by its transport, even on errors. Where the scoped-release construct cannot manage a resource's lifetime, the code's documentation explains clearly how that lifetime is managed.

## Example
```typescript
bad:  export async function openLog(path: string): Promise<FileHandle> {
        return open(path, "a");
      }
good: /** Opens the log for appending; the caller must close the returned handle. */
      export async function openLog(path: string): Promise<FileHandle> {
        return open(path, "a");
      }
```

## Limits
A routine that only uses a resource it is passed and leaves the release with the caller transfers nothing, and neither does a routine that releases what it acquires before it returns; the rule asks no statement of either. The way to release needs stating only where it is potentially unclear: where the value the routine returns or is passed is itself the resource and has one evident release operation, the statement of which side releases it is enough. The project context can reject the finding by stating an ownership convention that the project's leak checker enforces, such as results owned by the caller and parameters left with the caller; under it, the convention states the transfer of every routine that follows it, and only a routine that departs from it needs a mark.

## Validator
In the hunk, find each added routine signature whose result type or parameter type is a resource — a stream, reader or writer, a file handle or raw handle, a socket, a connection, a result set or transaction, a temporary file or directory, or a disposable type — each added return of a call that opens, connects to or creates one, each added hand-over of an existing reference to the scoped-release construct, and each added ownership or must-close annotation. Open the file and read the routine around each match. Continue only when the routine is exported, public or part of a library, and when it either returns the resource unreleased or takes over the release of a resource it receives as a parameter: it calls a close, dispose, delete or release operation on the parameter, hands the parameter to the scoped-release construct, or stores it in a field that its object's own release operation releases. Skip a routine that only uses a parameter and leaves its release to the caller, and one that releases what it acquires before it returns. Read the routine's documentation comment, its annotations and its parameter and result types. Count as the statement a sentence saying which side releases the resource, an ownership or must-close annotation, or a parameter or result type through which the language tracks who releases the value. Where the way to release is potentially unclear, such as a temporary file to be deleted as well as closed or a resource held inside the returned value, require the statement to say how. For a routine that takes over a parameter and can fail after receiving it, look for what the statement says about that failure. Skip the routine when the project context states an ownership convention that its checker enforces and the routine follows it. Validator question: **Does this routine return a resource its caller has to release, or take over the release of a resource it is passed, without its documentation, annotations or types stating which side releases it, how where that is potentially unclear, and, for a take-over that can fail, whether it releases the resource when it fails?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-20`, severity minor, `file`, `symbol`, `code` = the routine's signature line, or the return or release statement that makes the transfer, quoted verbatim from the diff, `fix` = the routine's documentation comment or ownership annotation stating which side releases the resource, how where that is potentially unclear and, for a take-over that can fail, what happens on failure, in the file's language, `rationale` = the release that neither the caller nor the routine is told it holds, and the resource leak that follows when each leaves it to the other).
