# A change that alters how users build, test, run, configure or release the code updates the repository documents that describe that behaviour in the same change

## Thesis
When a change adds, removes or alters a command, flag, environment variable, configuration key, or a build, install, test or release step — anything that changes how users build, test, run, configure or otherwise interact with, or release the code — the same change updates the associated documents in the repository that describe that behaviour, READMEs, in-repository documentation pages and generated reference documentation included, and where documentation for the changed behaviour is missing, the change adds it.

## Rationale
In a taxonomy built from 878 documentation-related artifacts drawn from four sources, up-to-dateness problems accounted for 39% of the issues about documentation content; in 21% of those, the inconsistency lay between a system's behaviour and its description in the documentation, and the discrepancy was usually triggered by a code change that required changing parts of the documentation or adding or removing content. Of the 78 practitioners who answered the issue survey, one of two surveys with 146 practitioners in all, 69% considered missing documentation for a new feature or component important, and it was the most recurring up-to-dateness issue; 59% perceived inconsistency between code and documentation as important, and it is one of the top recurring issues they face. README files frequently become outdated: manual annotation of an automated recommender's temporally matched README-update recommendations found that 21.5% identify updates developers overlooked, or 6.1% under the most conservative interpretation. Changing the documentation in the same change as the code keeps the documentation fresh and is a good place to explain to the reviewer what the change does; the reviewer checks that the change updates the associated documentation, can insist that READMEs and other documents get updated alongside it, and asks for documentation that is missing. Some developers guard against outdated documentation by putting the documentation update on the contribution checklist, or by making an API-documentation update mandatory for pull-request acceptance, and maintainers are expected to update documentation as baselines change. The property restored is a document that stays fresh with the code it ships with and is reviewed alongside it.

## Example
```typescript
bad:  program.option("--config-file <path>", "configuration file");
      const port = Number(process.env.APP_PORT ?? 8080);
      // README.md in this change: untouched, still documents --config and PORT
good: program.option("--config-file <path>", "configuration file");
      const port = Number(process.env.APP_PORT ?? 8080);
      // README.md in this change: documents --config-file and APP_PORT (default 8080)
```

## Limits
The rule reaches documents that describe the changed behaviour to the people who build, test, run, configure or release the code. Practitioners considered most outdated-documentation issues important, with four exceptions — outdated version information, outdated screenshots, outdated licence or copyright information and outdated translations — so a stale instance of these four raises no finding, except a version requirement stated in installation instructions, which stays in scope because practitioners rated outdated installation instructions important (54%). The practice is contested, and where the documents live and the project's documented workflow separate the cases. Unless the project's documented workflow accepts a separate documentation change, documents in the same repository as the code change in the same change, and the reviewer insists on it (google/styleguide docguide 'Update Docs with Code'; google/eng-practices 'Documentation'). Where the documents live in a separate repository, a feature's documentation is a pull request to the documentation repository's development branch whose description links the code pull requests and which is merged by the release deadline, or the feature may be removed from the milestone (kubernetes/website 'Documenting a feature for a release'); where the project's documented workflow accepts documentation in a separate merge request, that merge request is merged as close as possible to the code merge and should be completed before the milestone release (gitlabhq 'Documentation workflow'). In both of these cases a separate documentation change merged before the release meets the rule. The second workflow still strongly encourages documentation in the same merge request as the code and lets a team make that mandatory. The card's triggers reach command-line flag declarations and environment-variable reads; a change confined to a configuration-key read, a build, install, test or release script, a package manifest or a container file falls outside them. A changelog or release-note entry, an accepted decision record or proposal, and a design document whose code is implemented record history and keep the old name; the rule reaches documents that describe the current behaviour.

## Validator
Grep the hunk for an added, removed or renamed command-line flag or subcommand, environment-variable read or configuration key, and for edits to build, install, test or release scripts; drop a hunk whose user-facing names and steps stay as they were. For each changed name or step, search the repository's documents — README files, the documentation directory, guides, generated reference pages — for the old and the new name, and read each document that mentions either name as it stands after the change. Documents in another repository fall outside this search. Where the project's documented workflow accepts documentation in a separate change, read the change description for a link to that change; an open linked change counts, since whether it merges before the release is left to the project's release workflow, not to the reviewer of this change. Drop a stale screenshot, licence or copyright text, translation, or version string outside installation instructions. Validator question: **Does the change alter a command, flag, environment variable, configuration key or build, install, test or release step while, after the change, a repository document still describes its old behaviour or lists its siblings without it, and the change description links no separate documentation change that the project's documented workflow accepts?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DOC-11`, severity minor, `file`, `symbol`, `code` = the diff line that adds, removes or renames the flag, variable, key or step, quoted verbatim, `fix` = the document's path with its stale line rewritten to the new behaviour, or the line to add beside its siblings, in the document's own markup, `rationale` = names the document and the behaviour it misstates or omits).
