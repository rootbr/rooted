# A public operation declares each parameter with the most general type that offers the operations it uses, not a concrete implementation type

## Thesis
Each parameter of a public operation is declared with the most general available type that provides the functionality the operation's body requires of the argument, rather than with a concrete implementation type. A collection interface or an abstract collection type stands in place of a concrete collection class, a slice or a string view in place of a reference to an owned growable container or string, and an interface type in place of one concrete type that implements it. When the body requires functionality that only the concrete type provides, the concrete type is already the most general type for that parameter.

## Rationale
Requiring the argument to be of one specific implementation type makes an operation less useful for no benefit when a more general type would do: the fewer assumptions an operation makes about its inputs, the more widely usable it becomes. A slice or a string view usually suffices where a reference to an owned container or string is declared, and it can be obtained from other types too. Excessive coupling to an implementation type also limits the ability to use alternate implementations in the future as requirements change. A caller that holds the concrete type can still pass it to an operation that expects the interface.

## Example
```java
bad:  public int countOf(HashMap<String, Integer> counts, String key) {
          return counts.getOrDefault(key, 0);
      }
good: public int countOf(Map<String, Integer> counts, String key) {
          return counts.getOrDefault(key, 0);
      }
```

## Limits
The rule asks for a general type that is already available, in the language's standard library or in the codebase. It does not ask for a new interface to be created only to type the parameter: an interface is worth creating once a real need for it exists, such as two or more concrete types that the same logic must handle. A project can name types that it treats the same as interfaces, and a parameter of such a type is not flagged. The finder flags only a parameter declared with a concrete implementation type; a parameter declared with an interface or abstract type that offers more than the body uses, such as a list interface where the body only iterates, is not flagged.

A type parameter bounded by the operations the body uses can be more general still than a slice or a view, and one guideline prefers it where the body only iterates over the argument. It has costs: heavy use of type parameters makes a signature more difficult to read and understand, and where generic code is specialized per type the body is duplicated. The rule is met by the non-generic general type and does not demand the type parameter.

The rule does not reach return types, on which the guidance divides: one style guide has functions take interfaces as arguments but return concrete types, so that the caller has access to every public method and field of the implementation, while an analyzer's preferred example declares a returned set with its interface type.

On an operation that is already published, changing a parameter's declared type can break code that refers to the operation by its type with a compile error, and that code may live in other packages its author is not aware of; that change goes through deprecation first. The rule does not flag a parameter whose declared type the hunk leaves unchanged. Where the language makes an operation that overrides or implements an inherited declaration repeat that declaration's parameter types, the override keeps them and the rule applies to the inherited declaration.

## Validator
In the hunk, find each added parameter declaration whose type is a concrete collection class, a reference to an owned growable container, string or path, a concrete built-in collection in a type annotation, or a pointer to a concrete file, buffer, builder, reader or writer type. Go on only when the operation that declares it is visible outside its module or package. Skip the parameter when a removed line of the hunk declared it with the same type, and skip a signature whose body the hunk does not show in full, whose body passes the parameter to an operation of the codebase whose declared parameter type the hunk does not show, or whose body stores the parameter in a field or variable whose declared type the hunk does not show. Read the body and list what it requires of the parameter: the operations it calls on it, the operations it passes it to with their declared parameter types, the declared type of each field or variable it is stored in, the declared result type when the operation returns it, and any ordering or other guarantee it relies on. Name a more general type that the standard library or the codebase already provides with all of that. Skip when no such type exists, when the body requires functionality that only the concrete type provides, when the operation overrides or implements an inherited declaration whose parameter type the language makes it repeat, and when the project context lists the concrete type as one it treats the same as an interface. Validator question: **Does this public operation declare a parameter with a concrete implementation type although an available, more general type provides everything its body requires of that parameter?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-16`, severity minor, `file`, `symbol`, `code` = the parameter declaration quoted verbatim from the diff, `fix` = the signature with that parameter declared as the more general type that provides everything the body requires of it, in the file's language, `rationale` = the general type named and the operations the body uses that it provides, and the other implementations the concrete type shuts out).
