# An application or service commits the lock file its package manager generates, or the ecosystem's equivalent, to version control

## Thesis
A project that builds an application or service, an end product installed and run from its own repository rather than a package other projects declare as a dependency, keeps under version control the lock file its package manager generates, the file that records the exact resolved version of every direct and transitive dependency; a change leaves that file tracked, and neither deletes it, adds it to the version-control ignore list, nor sets the package manager to stop writing it. A requirements file that pins every top-level and transitive package to one exact version is such a lock file. Where the resolver is deterministic without a lock file, as minimal version selection is, the committed manifest and checksum file are the equivalent; where locking is enabled per dependency configuration, the lock state file that locking writes is the lock file.

## Rationale
A dynamic version range in the manifest can resolve to a different exact version over time, which can break a build unexpectedly. The lock file describes the exact tree that was generated, so that later installs produce an identical tree regardless of intermediate dependency updates: teammates, continuous integration and deployments install exactly the same dependencies, and a developer can return to a previous state of the installed tree without committing the tree itself, as reproducing a previous release for recovery, testing or maintenance requires. A range that admits only non-major updates still admits breaking ones: in a study of npm client packages, around 12% of the dependent packages and 14% of their releases were impacted by a breaking change during updates of non-major releases of their dependencies, and of all the manifesting breaking changes, 44% were introduced in both minor and patch releases, which in principle should be backward compatible. Deterministic builds help a bisection find the root cause of a bug and keep a continuous-integration failure due to new commits rather than external factors, and the lock file lets installs skip repeated metadata resolution and verify the integrity of resolved packages.

## Example
```python
bad:  ignored = [".venv/", "uv.lock", "package-lock.json", "go.sum", "*.lock"]
      Path(".gitignore").write_text("\n".join(ignored) + "\n")
      Path(".npmrc").write_text("""
      package-lock=false
      """)
      Path("pnpm-workspace.yaml").write_text("lockfile: false\n")
good: ignored = [".venv/"]
      Path(".gitignore").write_text("\n".join(ignored) + "\n")
```

## Limits
A library's lock file does not affect the projects that depend on it: they resolve the library's dependencies from the constraints in its manifest, so the lock gives the library's own builds a determinism its users do not get, and a library whose lock falls behind a new dependency version that breaks its users is likely to be the last to find out. The condition that separates the cases is whether the project is at the end of the dependency chain: application developers commit the lock file to get more reproducible builds, and a project producing an application is asked to check its lock files in, while for a library, omitting the lock trades away some reproducibility and performance, a trade-off this rule leaves open. In an ecosystem whose resolver is deterministic and saves no lock file, the absence of a separate lock file is correct, and the rule asks only that the manifest and checksum file stay in the repository. A change that only deletes the lock file adds no line for a trigger to match; the rule is dispatched by an added ignore entry or by a setting that stops the lock file being read or written, and the finder then also checks whether the same change deletes the file. An ignore entry that names the lock file of a package manager the project does not use, or a change that moves the project to another package manager and commits that manager's lock file in place of the old one, leaves the project's own lock file tracked and is outside the rule.

## Validator
Grep the hunk's added lines for a lock-file name or pattern (package-lock.json, yarn.lock, pnpm-lock.yaml, bun.lock, Cargo.lock, poetry.lock, uv.lock, Pipfile.lock, pdm.lock, pylock.toml, go.sum, gradle.lockfile, `*.lock`) that goes into the version-control ignore file, whether the line sits in that file or in code that writes it, never into an ignore file that only a formatter, linter or packager reads, and for a package-manager setting that turns lock-file reading or writing off. Open the ecosystem's manifest and the build, packaging and deployment files at the project root and decide whether the project builds an application or service installed from this repository, or a package that other projects declare as a dependency; when those files leave the role undecided, do not flag. Read from the manifest and the lock files at the project root which package manager the project uses, and treat as its lock file only the one that package manager generates: an ignore entry that names another package manager's lock file, or a pattern that does not cover the project's own lock file, is not a finding. Check whether the same change deletes that lock file or removes it from version control without committing the lock file of a package manager it moves to. Validator question: **Does the change ignore, delete or switch off the lock file that the package manager of a project building an application or service generates?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TOOL-05`, severity major, `file`, `symbol`, `code` = the added ignore entry or setting line, verbatim, `fix` = the ignore file or configuration without that line, with the lock file regenerated and committed beside the manifest, `rationale` = names the lock file, the application it belongs to, and the installs, by teammates, continuous integration, deployments or a rebuild of an earlier commit, that stop resolving the same tree).
