# A parameter of a public routine is named with a word, not a single letter, unless the letter is the conventional name for its role

## Thesis
Every parameter of an exported or public routine carries a name longer than a single letter that says what the argument is, however short the routine body. A one-letter parameter name on a public signature stays only where the letter is the conventional name for its role: a familiar letter for a common type that stands for no domain value, such as `x` for a generic floating-point operand like the argument of a square root, `p` for a generic pointer, `r` for a stream reader or an incoming request and `w` for a stream writer or a response writer, or a one- or two-letter method receiver where the language names the receiver explicitly. A letter that stands for a domain value (an amount, a customer, a deadline, a count of something specific) is replaced by the word for that value. Parameters of private or unexported routines and of lambdas not bound to an exported name are outside the rule.

## Rationale
A public routine's parameter names reach every caller away from the body: in the signature, in generated reference documentation, in the editor's parameter hints and, where the language lets callers pass arguments by name, in the call itself. The caller reads the name out of context and has the signature, not the body, to learn what to pass. In a controlled experiment in which nine professional developers read six methods from production utility classes, either with the original names or with the names replaced by meaningless single letters, parameter names proved more significant for comprehension than local-variable names; in three of the six methods no significant difference appeared because the original names were themselves poor or misleading, so the benefit depends on the name saying what the argument is. Names on a public interface are much more likely to be encountered out of context than names inside a body. A documented allowance for short names in a scope of ten lines or fewer covers local variables and the arguments of routines that are not part of an exported interface; it stops at the public signature because the caller reads that name outside those ten lines. A letter that is the conventional name for its role is documented as conventional and non-confusing in a restricted scope, with a declared square-root operand as the example, as a familiar name for a common type, or as the preferred form for a method receiver, which is why it stays; a letter standing for a domain value carries nothing to the caller. Where callers pass arguments by name, a released parameter name becomes part of the contract and renaming it breaks them, so the descriptive name costs least when the signature is added.

## Example
```python
bad:  def charge(c, a): ...
      charge(c=buyer, a=total)
good: def charge(customer, amount): ...
      charge(customer=buyer, amount=total)
```

## Limits
The case turns on whether the letter is the conventional name for its role. It stays on a public signature when it is: `p` for a pointer and `x` for a floating-point variable are documented as conventional and non-confusing in a restricted scope, `r` for a reader or a request and `w` for a writer or a response writer as familiar names for common types, and a one- or two-letter name as the preferred form for a method receiver. It is replaced when it stands for a domain value: one-character parameter names in public methods are documented as to be avoided, the short-name allowance for scopes of ten lines or fewer is documented as covering only arguments that are not part of an exported interface, and parameter names proved more significant for comprehension than local-variable names in an experiment that replaced names with meaningless single letters. In mathematically heavy code a letter matching the notation of a cited paper or algorithm is preferred inside the implementation, while the public signature still prefers the descriptive name, because public names are much more likely to be encountered out of context. Outside the rule: parameters of private or unexported routines and of lambdas and closures not bound to an exported name, where the short-name allowance reaches arguments in scope for ten lines or fewer, and type parameters, for which a single capital letter is a documented style. The rule reaches one-letter names only; a style that avoids every one-character parameter in public methods, conventional letters included, and a linter default of three characters for every parameter are stricter and are the project's choice. A project tolerance rejects the finding: a linter's allowed-short-parameter-name pattern (one linter's default ignores `n`) or a documented list of domain letters. A one-letter name the change carries over unchanged from the base signature is not introduced by the change and is outside the finding; where callers may pass arguments by name, renaming a released one breaks them, so its fix goes through the language's deprecation path. A parameter name fixed by an inherited or implemented declaration is judged at that declaration: an override that keeps the inherited letter introduces nothing, and renaming it in the override alone breaks callers that pass the argument by name through the inherited type and is itself flagged by a linter rule for parameters renamed from the overridden method.

## Validator
Grep the added signature lines of the hunk for a parameter whose name is one letter. Read the signature and decide whether the routine is public by the language's own visibility rule: a public, protected or exported modifier, a capitalized name where capitalization exports, a name without the private underscore prefix where that prefix marks privacy; skip nested helpers and lambdas that are not bound to an exported name. Open the base version of the file and compare the changed signature against it: a one-letter name the base signature already carried is not introduced by the change, so skip it. Skip a parameter of a routine that the hunk or file shows overriding or implementing an inherited declaration (an override keyword or annotation, or a supertype in the file that declares the routine) whose same parameter carries the same letter; its name is judged at that declaration. For each remaining one-letter parameter, name the role the letter plays from its type and its uses in the hunk: a familiar letter for a common type that stands for no domain value (a generic floating-point operand, a generic pointer, a stream reader or writer, an incoming request or its response writer), a method receiver, a type parameter or a letter the project's linter configuration allows keeps its name; a letter that stands for a domain value is the finding, whether the value is passed directly or through a pointer or reference. Validator question: **Does an added public routine signature introduce a one-letter parameter that stands for a domain value rather than the conventional name for its role?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-12`, severity minor, `file`, `symbol`, `code` = the added signature line carrying the one-letter parameter, verbatim from the diff, `fix` = the same signature with each flagged parameter renamed to the word or words for the value it carries, in the file's language, `rationale` = the domain value the letter stands for and that callers read the parameter name through the signature, documentation and parameter hints without the body).
