# An error returned as a value, a status result, a future or a promise is checked, propagated, or discarded explicitly with a comment stating why that is safe

## Thesis
Every call whose returned value signals failure — an error value, a failure status or sentinel such as false, -1 or null, a result type, a future or a promise — has that value handled by a deliberate choice: checked and acted on, returned to the caller, awaited so that its failure propagates, or, in exceptional situations, turned into a deliberate termination. A value bound to a variable counts as checked only when a later statement tests, returns, awaits or hands it on before it is overwritten or leaves scope. Discarding the value is rare and takes an explicit form — an assignment to the blank identifier or the underscore pattern, a cast or operator to void, a variable named as unused — with an adjacent comment stating why dropping the failure is safe, such as a callee documented never to fail. A call statement that leaves such a value unused, and an explicit discard with no stated reason, both break the rule.

## Rationale
A return value is easy to ignore, and an ignored one fails silently: when the call fails, nothing handles the error and the program carries on in a state its author assumed impossible. Two common assumptions behind an unchecked result are that the call can never fail and that its failure does not matter; when either is wrong, the statements that follow run on work that did not happen — a file still present after a delete that returned false, privileges still held after a drop that failed — and the failure surfaces later, far from its cause, as an unexpected state, a crash or undefined behaviour. Checking the result is the mitigation the weakness catalogue rates as highly effective. A deferred computation fails the same silent way: a future or a promise signals failure by completing exceptionally or rejecting, and when nothing awaits it, returns it or attaches a rejection handler, the code that started it never learns of the exception, the next statement runs before the operation has finished, and an unobserved rejection can crash the process. Compilers and checkers report an unused error-signalling value, and an explicit discard silences them by design; the comment then carries the proof the check no longer asks for, and it turns an omission into a decision a reviewer can dispute. Marking a promise as discarded does not handle it — its rejection is still unhandled at run time — so the stated reason has to cover the rejection: the promise catches its own failures, cannot reject, or rejects into a handler the comment names.

## Example
```typescript
bad:  saveDraft(doc);
      void audit.record(doc.id);
good: await saveDraft(doc);
      // record() catches and logs its own failures, so it never rejects
      void audit.record(doc.id);
```

## Limits
A returned value that signals no failure, such as a call that returns its own argument, is outside the rule, and so is a failure the callee raises as an exception, which propagates with no check at the call site. A callee that cannot fail, such as an in-memory buffer write documented never to return an error, is discarded with that comment. A print to the standard output or error stream, whose result is traditionally unchecked, is outside the rule; a project context that lists excluded callees rejects the finding for those callees. Sources differ on the bare explicit discard: one checker accepts a blank assignment without a comment by default, and one language reference calls the underscore binding the idiom for a purposeful discard, while a style guide asks for the comment; a project context that accepts an uncommented explicit discard rejects the finding for it, and a value left unused is still flagged. When related operations run as a group that fails or is cancelled together, keeping only the first error is a documented exception. In a test, a future created only for its side effect may be held, without a comment, in a variable named as unused. A promise marked as discarded that can reject needs a comment naming where its rejection is observed; a project that registers a process-wide unhandled-rejection handler and states that tolerance accepts the mark alone. What a handler does with an error it has received, the release of a resource on a cleanup path, and retries of a remote call are judged by their own rules.

## Validator
Grep the added lines for a call's result assigned to the blank identifier or an underscore binding, a call's result bound to an error or status variable or to a variable named as unused, a call marked void, a bare call statement, a promise chain with no rejection handler, and a process runner. For each hit, open the file and find the callee's declaration, its documented signature or its other uses in the file, and decide whether its returned value signals failure: an error value, a failure status or sentinel, a result type, a future or a promise. Skip a callee whose result signals no failure, a print to the standard output or error stream, a future held in a test in a variable named as unused, and a callee on an exclusion list the project context states. For a bare call statement, the value is unused. For a value bound to a named variable, trace it to a test, a return, an await or a hand-off; an overwrite or the end of scope before any of these leaves it unchecked. For an explicit discard, read the adjacent comment: it passes when it states why dropping the failure is safe — the callee is documented never to fail, the promise handles its own rejection or its rejection reaches a handler the comment names, the call belongs to a group that keeps its first error — and fails when it is absent or only labels the line. Validator question: **Does an added line call something whose returned value signals failure and leave that value unused, overwrite it before any test, or discard it without a comment stating why dropping the failure is safe?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-07`, severity major, `file`, `symbol`, `code` = the call statement or discarding assignment quoted verbatim from the diff, `fix` = the same call with its result checked and acted on, returned to the caller, awaited or given a rejection handler, or — where dropping it is safe — discarded explicitly with a comment stating why, in the file's language, `rationale` = which failure the callee signals through the ignored value and what the following code assumes succeeded).
