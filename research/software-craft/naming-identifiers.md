# Research note — Naming of identifiers

Topic `naming-identifiers` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC11 (Code Complete 2nd ed. ch. 11 'The Power of Variable Names'); PP 'Naming Things' (The Pragmatic Programmer, 20th anniversary ed., topic 45); PoP1 (The Practice of Programming ch. 1 'Style', §1.1 Names); SEG8 (Software Engineering at Google ch. 8 'Style Guides and Rules'); the 97 Things essays on naming.

The canon (Code Complete ch. 11, The Practice of Programming §1.1, The Pragmatic Programmer Topic 44 — the design note's 'topic 45' appears to be Topic 44 — and SEG ch. 8, with Clean Code and APOSD as the contested pair and the 97 Things essays) agrees on five positions: a name describes its entity accurately, descriptiveness scales with scope, one word per concept under one convention, abbreviations only in widely known forms, and the language's own casing. The industry disagrees on absolute length (Code Complete's 10-16-character average from one 1990 COBOL study and tool minimums of 2 or 3, which Pylint dropped as surprising, against the short locals of Go and Kernighan-Pike), on routine-name length (Martin's inverse scope law and long names against Ousterhout's shorter names plus comments, with no sourced separating condition), and on scope and kind markers and acronym casing, where the official conventions contradict one another so only 'the language's documented convention' is language-agnostic. The evidence is strongest for linguistic antipatterns: a 17-item catalogue mined from open source, judged poor practice by 69% of external and 51% of internal developers, with a measured rise in cognitive load, and shipped checks in PMD LinguisticNaming and clippy misnamed_getters and wrong_self_convention. It is moderate and contested for words over single letters and abbreviations (Hofmeister 2017, 19% faster; Lawrie 2006; Schankin 2018, 14% for experienced developers; against Scanniello 2017 and Beniamini 2017), resolved by conventional letters and by whether an abbreviation is known outside the project. Casing studies are split and training-dependent, so the convention card rests on official documentation and on lints tools run (rustc warn-by-default, Ruff, Pylint, Sonar S117); scope-proportional length, no type encoding, placeholder names and confusable names rest on official documentation and tool rules alone, since no study of scope-proportional length or of Hungarian notation was found. Every paper was read through abstracts or relays, none in full. Twelve rules card, four are pending (two without a separating condition, two without evidence), two are held as not checkable, and ten fold into the cards.

## Formulation layer

The canon agrees on five positions. (1) A name must describe its entity accurately, and a misleading name is a defect: CC11 §11.1, PoP 'Be accurate' (the inTable example), Clean Code 'Avoid Disinformation' and N7, APOSD §14.3, and the aposd-vs-clean-code exchange on isMultipleOfNthPrimeFactor all say this. These are the canon's version of the linguistic antipattern. (2) How long and descriptive a name is should scale with its scope or with the distance to its uses: CC, PoP, Clean Code N5, the Google Go/C++/Python/TS guides (Go gives line-count bands, TS allows single letters within 10 lines), Go CRC and Gerrand. (3) Use one word per concept and keep one convention: CC §11.3, PoP, APOSD §14.4, Clean Code, SEG8 and PP. (4) Abbreviate only with widely known forms, and never by deleting letters: CC §11.6, Google C++/TS/Python, Swift and .NET. (5) Follow the language's own documented casing: PEP 8, Effective Go, Rust C-CASE/RFC 430, Google Java, Swift, Kotlin, and SEG8's CamelCase case study. Fetched from the reachable host: the 97 Things essays, johnousterhout/aposd-vs-clean-code, SEG ch. 8 (abseil.github.io source) and fifteen official style documents. Code Complete, The Pragmatic Programmer, The Practice of Programming, Clean Code and APOSD were not openable, so those items come from WebSearch summaries, fetched third-party reading notes (flagged as such), or marked paraphrases. The canon disagrees in four places. On absolute length, CC's 10–16-character average (one 1990 COBOL study) runs against the brevity of Go, PoP and Gerrand, and Ousterhout rejects the Go short-name culture. On function names, Martin's inverse scope law and long method names run against Ousterhout's preference for shorter names plus comments. On member and type prefixes, Clean Code, Google Java and .NET FDG are against them, while the C# docs (_, s_, I) and Google C++ (kName) use them. Acronym casing differs by language. The design note's PP locator 'topic 45' appears to be Topic 44.

## Reception layer

The industry agrees on less about identifier naming than the canon suggests. There are two exceptions. Tools everywhere enforce the language's own casing convention; rustc does it with warn-by-default lints, and every major linter has a casing check with a regex. Every official guide also rejects Hungarian notation, the one exception being .NET's 'I' interface prefix. Name length is openly contested: the Go Code Review Comments ('Prefer c to lineCount'), the Linux kernel style and Kernighan/Pike/Pike's Notes defend short local names. Code Complete, the .NET guidelines ('favor readability over brevity'), Robert Martin and the Hofmeister study defend descriptive words. neverworkintheory reads the 2017 studies (Hofmeister vs Beniamini vs Scanniello) as conflicting, with a small effect. The tools reflect this. Pylint 3.0 dropped its minimum-length check as 'surprising'. PMD leaves ShortVariable/LongVariable/LinguisticNaming out of its quickstart. clippy puts its length lints in pedantic/restriction. staticcheck ST1003 and Error Prone IdentifierName are off by default. The one position shared across the reception is to scale descriptiveness with scope (Google Go/Python/TS guides, PoP, Nystrom, Martin for variables), though Martin applies the opposite to method names. Acronym casing is a per-language convention that the guides contradict each other on: Go 'appID' vs Google Java/TS 'customerId' vs .NET 'IOStream' vs Rust 'Uuid'. That supports wording the rule as 'the language's documented convention'. I could not open papers, blogs or HN threads directly; those items are relayed through search summaries. ## Evidence layer

The evidence splits by rule. Several controlled experiments support using whole words over single letters. Lawrie 2006 (over 100 programmers) found full words best but often no better than abbreviations. Hofmeister 2017 (72 C# developers) found words 19% faster than letters and abbreviations. Schankin 2018 (88 Java developers) found about 14% faster detection of semantic defects, for experienced developers only. The words-versus-abbreviations part is contested: Scanniello 2017 (100 participants) found no difference, Beniamini 2017 found single letters can carry meaning, and Aman 2015 linked long local names to change-proneness. On camelCase versus under_score the studies disagree (Binkley 2009 against Sharif and Maletic 2010), and the SCANL summary of Binkley 2013 finds no difference once developers are trained in a style. So 'follow the language's documented convention' rests on the documentation and on tool rules (PEP 8, Effective Go, Rust C-CASE, rustc and Ruff lints, Google Java §5.2, Sonar S117), not on proof that one casing is better. The documentation also shows that acronym casing (Go URL, Rust Uuid, .NET IOStream) and interface prefixes (.NET requires I, Google TS forbids it) differ by language. Linguistic antipatterns rest on Arnaoudova 2013/2016, Fakhoury 2018 (antipatterns raise cognitive load) and on shipped checks (PMD LinguisticNaming and BooleanGetMethodName, clippy wrong_self_convention and misnamed_getters). Scope-proportional length and 'no type encoding' rest on documentation only: I found no study for either. What I could not open: WebSearch was out of budget (200/200) at the first call, and every publisher host is denied. I read no paper's full text. Every paper statement is an abstract or excerpt from a third-party GitHub mirror (IEEE Xplore metadata in NicolasV15/CIRDC-Pro, dblp abstracts in maxxbw54/Paper-Repository, Google Scholar scrapes, neverworkintheory), marked relayed. For the Arnaoudova 2016 study, the mirror truncates the abstract before the developer-perception numbers, so I have none of them.

## Spine — candidate rules in source order

1. **A name never promises a type, a return value or a plurality that its own declaration contradicts** — The words of a name agree with the declared type or signature of what it names: a predicate-shaped name (is, has, can, should, will) belongs to a boolean field, variable or boolean-returning routine; a routine named get or return returns a value; a routine named set returns nothing unless its return is documented; a to or as conversion returns the converted value; a validate, check or ensure routine reports its outcome; a singular name holds one value and a plural name a collection (a collection is named with a plural phrase, not a singular noun plus List); and no word of the name is the antonym of what the declaration returns or holds. A contradiction counts when it is undocumented: the catalogue defines several of these as a mismatch left without documentation of the actual type or return.
