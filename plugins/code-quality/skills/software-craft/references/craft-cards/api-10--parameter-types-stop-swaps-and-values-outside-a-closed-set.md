# A public operation's parameter types stop a caller from swapping two arguments of different meaning or passing a value outside a closed set

## Thesis
A public operation that takes two or more parameters of one primitive representation (an integer, a floating-point number or a string) whose values differ in meaning or unit, such as the identifiers of two different entities or a distance in miles beside one in kilometres, gives each of them a distinct type that the type checker does not accept in place of the others, or has every caller name each argument at the call site, which makes the arguments harder to swap. A public parameter that accepts only a closed set of values, a fixed set of named alternatives such as a mode, a kind or a unit, takes a type that admits only those values, such as an enumeration or a union of literal values, rather than an open string or integer. Both apply whenever practical.

## Rationale
API design should try to make an interface hard to misuse. As a signature grows, adjacent parameters of the same type become easier to confuse, and the underlying type alone does not let the checker tell one interpretation of it from another: an order identifier from a depot identifier, or miles from kilometres. A distinct type for each interpretation makes that distinction statically: an operation that takes miles cannot accidentally be called with kilometres, and the checker asks for the conversion. The mistake is caught early, when the code is compiled or type-checked, rather than through a failure at run time, and the cost moves to the boundary where a raw value is first converted into the distinct type. Choosing an argument type that rules out bad inputs ranks first among the ways to enforce valid input, ahead of validating the input as it is processed, which can add run-time overhead, delays the detection of bugs and introduces failure cases that client code must then handle. Where the arguments are named instead, a call that writes each field beside its value is self-documenting and makes the arguments harder to swap. A core type such as a byte-sized integer has many possible interpretations, and a deliberate type, such as an enumeration, conveys the interpretation and its invariants. An enumeration requests exactly one choice from among many, and where the checker admits only the enumeration's members, an operation that takes it rather than an integer is guaranteed well-formed inputs, even if it later views them as integers. A union of literal values accepts only a certain set of known values, and the type checker reports a misspelled member as an error. One static check for swaps without distinct types works from names: when permuting the arguments makes their names a better match for the parameter names, that might indicate an accidental swap.

## Example
```rust
bad:  pub fn ship(order: u64, depot: u64, priority: &str) { ... }
      ship(depot_id, order_id, "expres");
good: pub struct OrderId(pub u64);
      pub struct DepotId(pub u64);
      pub enum Priority { Standard, Express }
      pub fn ship(order: OrderId, depot: DepotId, priority: Priority) { ... }
      ship(order_id, depot_id, Priority::Express);
```

## Limits
Some properties are difficult or impossible to express in types; a value with such a property is validated as the input is processed, and that run-time check is outside the rule. An operation whose only job is to convert one raw value into its distinct type or enumeration, such as a parser of that value, takes the raw value by design: it is the boundary where the conversion happens, and it is outside the rule. A type alias that the checker treats as exactly equivalent to its underlying type does not satisfy the rule, because an alias cannot create a distinct version of the same type; the distinct type is one the checker refuses to accept a variable of the underlying type or a value of another of the distinct types for. Where the language checks such types only through a separate static type checker, the distinction holds only where that checker runs; at run time the distinct type returns its argument unchanged. Where the checker compares types by their members, two wrapper types of the same shape accept each other's values unless each declares a private member, which the checker matches only against a private member that originated in the same class. In a language that lets an untyped constant convert implicitly to any defined type that can represent it, a defined type over an integer or a string stops a variable of another type but still accepts any literal its underlying type can represent, so it separates kinds of value without fully closing a set. Where the checker treats an enumeration over numbers as compatible with numbers, that enumeration accepts any number held in a variable, so it too separates kinds of value without closing the set. Two values of one kind that differ only in role, such as the width and the height of an image, are outside the rule; a deliberate swap of the two can be correct, as when the image is rotated. The rule covers public operations: argument-list guidance applies primarily to exported interfaces, which are held to a higher standard than unexported ones. An operation that overrides or implements an inherited declaration takes the parameter types that declaration fixes, and is judged at that declaration. It does not reach a boolean parameter that selects a behaviour, the number of parameters an operation takes, or the run-time rejection of an invalid argument. A tolerance in the project context that keeps primitive parameter types at a named interface, such as one generated from an external schema, rejects the finding. A parameter type the change carries over unchanged from the base signature is not introduced by the change and is outside the finding; changing the parameter types of a released operation changes its published signature for every caller.

## Validator
Grep the added signature lines of the hunk for an operation with two or more parameters of one primitive type (an integer, a floating-point number or a string), and for a parameter of string or integer type whose name denotes a mode, a kind, a status, a level, a unit or another closed set. Decide whether the operation is public by the language's visibility rule; skip private, unexported and local operations. Skip an operation that overrides or implements an inherited declaration (an override keyword or annotation, or a method of a trait or interface implementation block) with the same parameter types; its types are judged at that declaration. Open the base version of the file and compare each matched signature against it: a pair of parameters, or a string or integer parameter, that the same operation's base signature already carried with the same types is not introduced by the change, so skip it. Count a parameter typed with an alias that the language treats as identical to its primitive as that primitive. For each pair of parameters of one primitive type, read their names, the doc comment and their uses in the hunk, and decide whether they stand for different kinds of thing: the identifiers of different entities, an identifier and a quantity, or quantities in different units. Skip a pair of one kind that differs only in role, and skip parameters that the signature forces every caller to name at the call site. For a parameter of string or integer type, read the doc comment, the body and the constants in the hunk, and decide whether it accepts only a fixed set of named alternatives; skip a parameter whose values are open, such as a name, a path or free text, or bounded by a range, and skip an operation whose only job is to convert one raw value into its distinct type or enumeration. Validator question: **Does an added public signature take by position, in one primitive type, two parameters that stand for different kinds of thing, or take an open string or integer for a parameter that accepts only a fixed set of named alternatives?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-10`, severity minor, `file`, `symbol`, `code` = the added signature line quoted verbatim from the diff, `fix` = the signature with a distinct type for each parameter of a different kind or with those arguments named through an options value, and an enumeration or a union of literal values in place of the open string or integer, in the file's language, `rationale` = the two kinds of value a caller can swap without the checker objecting, or the values outside the fixed set of alternatives that the open type admits).
