# Code is split into a separately versioned component only when it is to be versioned independently of the code it leaves, such as code other projects reuse, or when its clients need it with a smaller set of dependencies than the rest, and otherwise stays in one component

## Thesis
Code gets a component of its own, a unit with its own name that is released under its own version, when that code should be versioned independently of the code in the component it leaves. Documented cases for such a split are packages that become useful for sharing with other projects, and a client API whose set of dependencies is smaller than the complex set of dependencies of the rest of the repository. Code that meets no such need stays inside the one component, because a single component per repository keeps maintenance simpler and is almost always easier and simpler to manage than several. Where the ecosystem's own documentation holds that a module proxy mostly equals the performance and download-size benefits a split would bring, a split considered only for those benefits is tried first with the proxy.

## Rationale
Adding, removing and versioning several components inside one repository require considerable care and deliberation. In one ecosystem's build tool, a test command run from the root of a repository that holds several components does not test everything in the repository, and the relationship between the components may need routine management through override directives. A single component at the repository root keeps maintenance simpler over time, as new minor and patch versions are published and new major versions are branched. Where the dependency specifications between separately versioned packages are too tight, the system is in danger of version lock, the inability to upgrade a package without releasing new versions of every dependent package. On the other side, dependencies that a client never uses cost upkeep. In a study of 9,639 artifacts and their 723,444 dependency relationships, 75.1% of the dependencies were bloated, not needed to compile and run the code, and the study identifies transitive dependencies and the complexities of dependency management in multi-module projects as the primary causes of that bloat. A longitudinal study found that 22% of the dependency updates developers performed were made on bloated dependencies. The rule keeps a version boundary only where code is versioned independently, and lets a client API with a smaller dependency set carry that smaller set to its clients.

## Example
```typescript
bad:  // packages/formatting/package.json: its own name, published to the registry on its own
      "name": "@app/formatting",
      "publishConfig": { "access": "public" },
      // the app is its only importer: no reuse elsewhere, no client needing fewer dependencies
      import { formatTotal } from "@app/formatting";
good: // the code stays a folder inside the app's one package
      import { formatTotal } from "./formatting";
      export const label = formatTotal(12.5);
```

## Limits
A separate manifest is also documented for usage examples whose own set of dependencies is complex, such as an example that uses a small package with a large platform; it can then make sense for an example directory to carry a manifest of its own. A workspace whose members share one lock file and one output directory is documented as letting a growing project work with smaller, easier-to-understand components than one big blob of code, and keeping parts that are often changed at the same time in one workspace can make their coordination easier. Members of a workspace fall outside the rule while they are not published; a member that is published to a registry is published separately and is then a separately versioned component that the rule reaches. Which classes or modules belong together inside one component, and which imports its clients must take together, are module-level questions that rules at the module level govern; this rule judges only the boundary of a component that is released and versioned on its own. Code that the language's build rules require to sit in a package of its own, such as a compile-time code generator that must reside in its own package with a special package type and is then published separately, falls outside the rule. Reception is split. Build-tool documentation of one ecosystem holds that one component per repository keeps maintenance simpler and that several components take considerable care. The same documentation recommends a split for packages useful to other projects and holds that one can make sense in some cases for a client API with a smaller set of dependencies, and two dependency-bloat studies measure how many dependencies are not needed to compile and run the code and how many updates are spent on them. Another build tool's documentation recommends a workspace of smaller components that share one lock file. The condition that separates the cases: split off a separately versioned component when its code is to be versioned independently, as with packages other projects reuse, or when a client API needs a smaller set of dependencies than the complex set of the rest; keep one component otherwise, and, where the ecosystem's documentation holds that a module proxy mostly equals a split's performance and download-size benefits, first try the proxy when those benefits are the only motive.

## Validator
Grep the hunk for a new or changed component manifest: a module declaration, a package or project table, a package name field, a workspace members list, a module entry in a parent build file, an include line in a build settings file. Open the manifest of each component the hunk creates or splits off, and open its callers at scope callers: list every importer inside the repository, and take any reuse by other projects from the hunk and its description. For each importer other than the component it left, check whether it takes the new component to avoid the larger dependency set of the component it left. Trace whether the new component is released on its own: its own publish step to a registry, its own release tag, or a version range for it in the component it left; a version field alone does not settle it, because a member of a workspace that shares one lock file can carry a version field of its own while it is not published. Read the hunk and its description for the stated reason to version the code independently. Validator question: **Does the hunk give code a separately versioned component of its own while its only importer is the component it left, no other project reuses it, no client takes it for a smaller dependency set, no build rule of the language requires the code to sit in a package of its own, and the hunk states no reason to version it independently other than download size or performance?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-03`, severity minor, `file`, `symbol`, `code` = the manifest line that names the new component and the import that is its only consumer, quoted verbatim from the diff, `fix` = the code kept as a directory inside the component it left and imported by a relative path, in the file's language, `rationale` = names the missing reason to version the code independently, no reuse by other projects and no smaller client dependency set, and the upkeep each separately versioned component adds).
