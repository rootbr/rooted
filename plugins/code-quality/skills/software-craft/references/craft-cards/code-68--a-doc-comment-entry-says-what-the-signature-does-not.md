# Each parameter, return or error entry in a doc comment says something the signature does not, and an entry that only repeats a name or a type is filled in or removed

## Thesis
Each parameter, return and error entry in a routine's doc comment says something a caller needs that the signature does not show: why a parameter is interesting or error-prone, a constraint its value must meet, what the returned value means, when the error occurs. Four forms say nothing beyond the signature: an entry whose description only restates the parameter's name and type, such as "format is the format"; a type written into an entry for a parameter or result whose type the code already declares; a block tag with no description; and a one-line summary written as the signature, reiterating the parameter list. A duplicated type is dropped from its entry; an entry that says nothing more is filled with what a caller needs or deleted; a signature summary is replaced by one that says what the routine does and what it returns. Where a checker the project runs reports a parameter or result that has no entry, the entry stays and is given content. The opening summary sentence that the language's documented doc-comment convention requires is outside the rule, even when it begins with the routine's name and seems a little redundant.

## Rationale
Block tags for parameters, results and errors are meant to provide additional information about the routine; without a description, a tag is no more informative than the signature. Where the code declares types, the type system does a good job of defining what the routine takes and returns, and one documentation generator links every type in the signature, so writing the types again in the comment brings no benefit. An entry that restates a parameter's name and type adds little useful information to the reader. A summary written as a signature repeats parameters that introspection already gives, while the nature of the return value, which introspection cannot determine, is what the summary should mention. A caller needs enough to write a call without reading the routine's code, and the signature leaves out why a parameter is interesting, a constraint on its value, the semantics of the return value and the condition under which an error is raised. The remedy has two forms, a description after the tag or deletion of the tag, and one convention requires parameter and return lines only when they add information. A checker that by default reports a parameter, or a non-void result, with no matching tag leaves only the first remedy, so under it the entry is kept and filled. Each entry that remains then carries the additional information block tags exist to provide.

## Example
```typescript
bad:  /** Finds a user.
       * @param {string} id The id.
       * @returns The user. */
      function findUser(id: string): Promise<User | undefined> { return db.find(id); }
good: /** Finds a user.
       * @param id Account id issued at sign-up, never the email address.
       * @returns Resolves to undefined when no account has this id. */
      function findUser(id: string): Promise<User | undefined> { return db.find(id); }
```

## Limits
Where the code declares no type for a parameter or result, a type in its entry is not a duplicate: one convention asks a parameter's description to include the required types when the code has no corresponding type annotation, and a return description to include any type information the annotation does not provide. A summary written as a signature is appropriate for a routine implemented natively, such as a built-in, whose signature introspection cannot obtain. The required opening sentence is outside the rule: one convention asks that a declaration's doc comment be a full sentence that begins with the name of the thing described, even if that seems a little redundant, and others ask for a short sentence or a verb phrase saying what the routine is, does or returns. The rule judges entries that are present and asks for no entry per parameter: not every parameter must be enumerated, and method, parameter and return descriptions may be omitted when they are obvious from the rest of the doc comment or from the name and signature. A project's documented doc-comment convention can prescribe what the rule would flag: one convention describes each parameter together with its type, and one checker enables its signature-summary check under two conventions and disables it under that one. A project whose documented convention prescribes a type in every entry or the signature as the first line rejects that part of the finding. A comment inside a routine body is outside the rule.

## Validator
Grep the hunk's added lines for a doc-comment opener, a block tag or field for a parameter, result or error, a section heading for parameters, results or errors that the language's documented doc-comment convention defines, or a sentence of the form "x is the x". For each added or changed doc comment, read in the hunk the routine signature it documents: its parameter names, their declared types and the declared result. Where the hunk does not show that signature, leave a type in an entry unflagged and judge the other forms from the entry alone. Check each parameter, return and error entry, and keep one whose description repeats only the parameter's name, its type or both; one that writes a type the signature already declares; one with nothing after the tag and the parameter or error name it documents; and a one-line summary that is the routine's name followed by its parameter list. Set aside the opening summary sentence the convention requires, including one that begins with the routine's name; a type in an entry where the code declares no type for that parameter or result; a signature summary on a natively implemented built-in; and any part the project's documented doc-comment convention prescribes. Where the project context names a checker that reports a parameter or result with no entry, the fix fills the entry rather than deleting it. Validator question: **Does an added or changed doc comment carry a parameter, return or error entry, or a one-line summary, that says nothing beyond the routine's signature — a restated name or type, a type the code already declares, a tag with no description, or the signature written out as the summary?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-68`, severity suggestion, `file`, `symbol`, `code` = the doc-comment entry or summary line that says nothing beyond the signature, verbatim from the diff, `fix` = the entry rewritten to state what a caller needs — why the parameter matters, a constraint on its value, what the result means, when the error occurs — with any type the code declares dropped, or the entry deleted where no checker the project runs requires it, in the file's language, `rationale` = the part of the signature the entry repeats and the information a caller still lacks).
