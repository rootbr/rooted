# A closure that runs after its loop iteration ends reads a per-iteration binding, not a variable the loop reassigns

## Thesis
A function literal, lambda, arrow function or nested function created in a loop body or a comprehension and run after its iteration ends — stored for a later call, deferred, scheduled as a callback or a timer, launched to run concurrently, or handed to a lazy pipeline stage consumed later — reads each value that changes from one iteration to the next only through a binding of its own iteration: a loop variable the language makes fresh for each iteration, a copy declared in the loop body's own block scope, or a value bound when the closure is created, as a parameter default or a partially applied argument. Such a closure never reads directly an iteration variable that is one binding for the whole loop, nor a variable that outlives one iteration and is assigned in the loop — one declared before the loop, or one assigned in a loop body that gives it no scope of its own. A closure that runs before its iteration ends is outside the rule.

## Rationale
A closure captures the variable, not the value it held when the closure was created: it reads the variable when it is called. A loop whose iteration variable is one binding for all iterations overwrites that binding each time round, so the closures created in the loop and called after it all read the same last value: five stored closures meant to square 0 to 4 all return 16, and ten stored closures meant to return 0 to 9 all return 10, the counter's last value. Nothing at the creation site signals the problem, and the code can still pass its tests: in one large code base, a checker that reports closures which may outlive their iteration flagged tests in 20 of 8,000 test packages with no false positives; about 95% of the flagged tests were not testing what they intended, and the rest hid a failing case because every subtest checked only the final one. A lazy pipeline stage defers the call the same way: a mapping or filtering step built in the loop runs its function only when its result is consumed, so a refactoring or a dependency update that turns an eager step lazy moves the read past the loop. A closure launched to run concurrently with the loop also races with the loop's writes to the variable. Binding the value when the closure is created gives each closure the value the variable had in its own iteration, which is what such a loop looks like it does; a variable is shared between iterations by accident far more often than on purpose.

## Example
```typescript
bad:  for (var i = 0; i < jobs.length; i++) {
        handlers.push(() => run(jobs[i]));
      }
good: for (let i = 0; i < jobs.length; i++) { // one i per iteration
        handlers.push(() => run(jobs[i]));
      }
```

## Limits
A closure that runs before its iteration ends reads the current value and is correct: one called directly, or one passed to a callee that runs it and discards it, such as a sort key or an eager search callback. A closure returned directly from the loop body, which ends the loop, is correct as well, since no later iteration reassigns the variable. A variable that the language creates afresh for each iteration — a declaration in the loop body's own block scope, or a loop-header variable that the language at the declared version makes per-iteration — is outside the rule, while a variable that outlives one iteration stays shared: one declared before the loop, a loop-header variable that the declared version reuses across iterations, or one assigned in a loop body that gives it no scope of its own; a language that rejects a closure referencing a local that is not final or effectively final leaves no local to flag, while a field that the loop assigns is still read when the closure runs. A variable shared across iterations on purpose, so that a closure reads its latest value, is correct when a comment says why the closure reads it. Contested — checkers differ on a closure that a callee runs within the iteration. One family reports every function or lambda that references a variable defined in an enclosing loop unless it is called directly in that loop, because such a capture makes the code difficult to understand and a later refactoring or dependency update, such as a library call that turns lazy, can make it run late. The other reports only a closure that may outlive the iteration, because disallowing every loop-variable capture would invalidate essentially every existing program of the measured language, the vast majority of them correct, to catch about 1 buggy loop in 20,000 in the measured code base, and some checkers that err toward reporting showed false-positive rates over 90% in real code bases. The separating condition is when the closure runs: a closure that can run after its iteration ends is flagged; one that a callee runs and discards within the iteration is not, unless the project context adopts the stricter policy.

## Validator
Grep the added lines for a function literal, lambda, arrow function or nested function that is appended, assigned into an indexed slot, deferred, launched, scheduled or registered as a callback, for a lambda inside a comprehension, and for a loop header that declares a function-scoped variable. For each closure, find the enclosing loop or comprehension in the hunk and list the variables the closure reads that the loop reassigns: the iteration variable, a comprehension variable, a variable or field declared before the loop and assigned in it, or a variable assigned in a loop body that gives it no scope of its own. Skip a variable created afresh for each iteration — a declaration or copy in the loop body's own block scope, or a loop-header variable the declared language version makes per-iteration; when that version decides the case and neither the hunk nor the project context states it, do not flag. Skip a value bound at creation through a parameter default or a partial application, and a variable a comment declares shared on purpose. Trace where the closure goes: stored in a collection, a field or a map, deferred, scheduled as a callback, a timer or a promise continuation, launched to run concurrently, submitted to an executor, or passed to a lazy pipeline stage whose result is consumed after the iteration means it runs late; called directly, passed to a callee that runs and discards it within the iteration, or returned directly from the loop body, ending the loop, means it does not. Validator question: **Does a closure created in a loop read a variable that the loop reassigns after the closure's iteration, and can the closure run after that iteration ends?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-62`, severity major, `file`, `symbol`, `code` = the loop header and the line that creates or stores the closure, quoted verbatim from the diff, `fix` = the same loop with the value bound per iteration — a loop variable the language makes per-iteration, a copy declared in the loop body's own block scope, a parameter default or a partial application — in the file's language, `rationale` = which variable the closure reads, where the closure runs after its iteration, and which value it will see there).
