# A deprecated element carries the language's machine-readable deprecation marker rather than only a comment, so that compilers, type checkers and linters can warn at each use

## Thesis
An element the code declares deprecated carries the deprecation marker its language's tools read — an annotation or attribute, a doc-comment paragraph or tag in the form the tools recognise, or a decorator that type checkers read — and the marker's message or the documentation beside it explains the deprecation. A comment in another form, a note elsewhere in the documentation, or a run-time warning raised from the element's body does not stand in for the marker wherever the marker can express the deprecation; a run-time warning may accompany it. Where the language keeps the annotation the compiler reads apart from the documentation tag, each is present whenever the other is.

## Rationale
The marker is what the tools key on. A compiler warns where an element carrying it is used or overridden in code that is not itself deprecated; a type checker is specified to report each usage of an object marked deprecated, imports and calls reached through an operator or a property setter included; where the compiler itself reports nothing, editors typically strike the name through and a linter reports each reference to code marked deprecated; for the doc-comment paragraph form, some tools warn when the identifier is used, and one package documentation site hides its documentation by default; a documentation generator shows the deprecation with its version and note. The text attached to the marker travels with the warning: a type checker is to show the decorator's message when it encounters a usage, and an attribute's note is specified to be included in the deprecation message and typically explains the deprecation and the preferred alternatives. A comment in another form gives these tools nothing to key on: a checker that reads the paragraph form skips every doc-comment paragraph that does not begin with the marker word and its colon, and a decorator that raises only a run-time warning is not detected by type checkers. A run-time warning is shown when the deprecated functionality is used, and that mechanism is often insufficient to ensure that users update their code in time: users may run their test suites with warnings disabled for practical reasons, and a deprecation may be triggered in a code path no test covers. One standard library had to revert the removal of long-deprecated features to give users more time to update their code. A marker that static checkers read gives users another way to learn of the deprecation — the checker reports usages a single text search could not find, and many checkers show the warning in the editor — and more ways to find out about a deprecation can speed up the migration; the decorator form also raises the run-time warning by default. The annotation and the documentation tag serve their own purposes — the annotation lets compilers and development tools warn about each reference, the tag documents why the element is deprecated and what, if any, alternative exists, and can explain when it was deprecated and how references should be refactored — so both forms are present to mark a deprecation properly.

## Example
```python
bad:  def fetch(key):
          # deprecated: use fetch_many() instead
          warnings.warn("fetch is deprecated", DeprecationWarning, stacklevel=2)
          ...
good: @warnings.deprecated("fetch is deprecated; use fetch_many() instead")
      def fetch(key):
          ...
```

## Limits
A soft deprecation is outside the rule. One language project's general convention leaves an element that still works and has no significant downside formally unmarked and updates its documentation to point to the preferred element; another's compatibility policy defines a soft deprecation — an element no longer to be used in new code, safe to keep in existing code, with no removal scheduled — that issues no warning and is only mentioned in the documentation. A notice that states such a status, or a project context that states a soft-deprecation convention, rejects the finding. Where the marker cannot express the deprecation, the run-time warning and the documentation carry it; an older language version whose standard library lacks the decorator reaches it through the back-port module for new typing features, so the version alone does not put the marker out of reach. A decorator that covers classes, routines and overloads leaves out whole modules, module-level constants, object attributes and a parameter except through an overload: of the deprecations surveyed in one standard library, 74 were routines and classes the decorator covers and 9 were parameters it reaches through overloads, while 28 whole modules, 1 constant and 38 deprecations not easily detectable in the type system fell outside it. On a local variable, a parameter or a package the annotation has no effect on one compiler's warnings, and for a package the documentation tag is the only way to say why it is deprecated and what to use instead; one language's attribute cannot be applied to the items of a trait implementation. A member of a class, interface, module or implementation that itself carries the marker needs no marker of its own: one language's attribute is inherited by every item such a container holds, and one tool rule exempts the members of a deprecated class or interface while still checking the class or interface itself. What the explanation names — the replacement, the release that removes the element — how long the element keeps working, and new uses of an element already marked deprecated are judged by their own rules.

## Validator
Grep the added lines for a comment, doc-comment or docstring line that calls an element deprecated, a deprecation annotation, tag, attribute or decorator, and a run-time deprecation warning. For each hit, read the hunk for the declaration it belongs to and check that the declaration carries the marker its language's tools read: an annotation or attribute on the declaration; a doc-comment paragraph of its own that begins with the capitalised word Deprecated and a colon, where that paragraph is the form the language's tools read; a deprecation tag inside the documentation block comment directly above the declaration; a deprecation decorator that type checkers read. Where the language keeps a compiler-read annotation apart from a documentation tag, check that both are present. Check that the marker's message or the declaration's documentation explains the deprecation. A run-time warning raised from the body passes only together with the marker, unless the deprecated thing is one the marker cannot express: a whole module, a module-level constant, an object attribute, a parameter outside an overload, a behaviour of a call, a local variable, parameter or package where the annotation has no effect on the compiler's warnings, or an item of a trait implementation. Skip a member of a container that carries the marker, a notice that states a soft deprecation, and a comment that mentions the deprecation of some other element, such as a call site of a deprecated element. Validator question: **Does the hunk declare an element deprecated by a comment, documentation of another form or a run-time warning alone where the language's tool-read marker could express that deprecation, by only one of a split annotation and documentation tag, or by a marker with no text explaining the deprecation?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-27`, severity minor, `file`, `symbol`, `code` = the comment, docstring line, run-time warning call, or lone annotation or tag that declares the deprecation, quoted verbatim from the diff, `fix` = the same declaration carrying the language's tool-read marker with its explanation — the annotation together with the documentation tag, the attribute with a note, the doc-comment paragraph in its recognised form, or the decorator with a message, any run-time warning kept beside it unless the marker itself raises one — in the file's language, `rationale` = names the deprecated element and that no compiler, type checker or linter warns at its uses because the deprecation is stated in a form those tools do not read, or that the split annotation or tag leaves either the warning or the explanation out).
