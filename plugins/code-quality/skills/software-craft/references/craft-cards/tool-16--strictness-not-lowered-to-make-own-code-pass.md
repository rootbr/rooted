# A change does not lower a compiler, type-checker, analyzer or test-run strictness setting, or switch a check off, as the means of making its own code pass

## Thesis
A change makes its own code pass the project's compiler, type checker, configured analyzer and test run at the strictness the base revision sets by changing that code, not the settings. Whenever code the change adds or modifies raises a diagnostic or failure under a base setting, the change keeps that setting at least as strict as the base: the lint level, the strict-mode flag, the rule ignore list, the committed suppression baseline, the analyzer step of the test command, the warning filters of the test configuration and the blocking status of the check step.

## Rationale
Projects are advised to be maximally strict with warnings where practical and to strive to enable warning flags where they can, so that errors are detected early. Lowering one of those settings so that the change's own code passes hides a failure, and a catalog of 79 continuous-integration bad smells in 7 categories, built from interviews with 13 experts and more than 2,300 Q&A-site posts, with the smells' perceived importance surveyed among 26 professional developers, draws the implication for practitioners "do not ignore nor hide build failures". In 20 open-source projects that run static analysis in their pipelines, build breakages caused by the analyzers were quickly fixed by actually solving the problem rather than by disabling the warning, and were often properly documented. Each relaxation switches off a documented guard: a test command that runs the analyzer first does not run the tests when the analyzer finds a problem, and one flag disables that step; a bulk-suppression baseline keeps a rule enforced for new code while existing violations go unreported, so a new violation recorded in it goes unreported as well; one language runtime ignores deprecation warnings by default outside the main module, and its documentation tells developers to test with typically ignored warnings made visible in order to receive timely notifications of future breaking API changes. Some tools hold the line themselves: one type checker's strict mode lets per-rule overrides only increase the strictness, and one compiler's 'forbid' lint level cannot be overridden to anything lower than an error, though a command-line cap can still lower it to a warning. No study measures the defect cost of such a relaxation; the support is tool documentation and descriptive studies of pipeline practice.

## Example
```java
bad:  List<String> names = (List<String>) value;   // unchecked cast
      List<String> javacOptions = List.of("-Xlint:all", "-Xlint:-unchecked", "-Werror");
good: List<String> names = ((List<?>) value).stream().map(String.class::cast).toList();
      List<String> javacOptions = List.of("-Xlint:all", "-Werror");
```

## Limits
The rule turns on one condition: whether the relaxation is the means by which the change's own new diagnostics or failures pass. One type checker documents turning off individual strict-family checks as needed, another lets a directly given flag override its strict bundle regardless of order, and a best-practices criterion grants that some warnings cannot be effectively enabled on some projects; a relaxation that no code of the same change fails is outside the rule. On the other side, a relaxation in the same change as code that fails the relaxed check hides a build failure, against the practitioner implication "do not ignore nor hide build failures" and the observed practice of fixing analyzer breakages by solving the problem rather than by disabling the warning. Tightening runs in the opposite order: a bulk-suppression baseline records the violations that already exist while the rule is enforced for new code, and a checker upgrade that adds stricter checks under an existing strict flag can report new errors in code the change does not touch; those are existing violations, not the change's own. The defect a given analyzer rule reports, an inline suppression of a single construct and the design of the pipeline are outside the rule.

## Validator
Grep the hunk for edits to a build, lint, type-checker, test-runner or pipeline configuration that lower a level or switch a check off: a level moved from error to warning or off, a strict flag set false or a strict mode replaced by a basic one, a rule added to an ignore or disable list, entries added to a committed suppression baseline, the analyzer step removed from or disabled in the test command, an ignore entry added to the test configuration's warning filters, a check step marked allowed to fail, or a command-line cap on lint levels. For each, open the setting at the base revision and at the head revision and confirm the head is less strict. Trace the relaxed check to the change's own code: match the rule ids, warning categories and file paths the relaxation names, and the baseline entries it adds, against the lines the change adds or modifies, and check whether those lines raise that diagnostic or failure under the base setting. Validator question: **Does the change lower a strictness setting or switch a check off, and does code added or modified by the same change raise the diagnostic or failure that the base setting would report?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TOOL-16`, severity major, `file`, `symbol`, `code` = the relaxed setting line verbatim from the diff, `fix` = the setting restored to its base value and the change's own code corrected so that it passes the check, in the file's language, `rationale` = the relaxed check and the diagnostic of the change's own code that the relaxation hides).
