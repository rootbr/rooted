# An added import follows the dependency direction the project declares between its layers and modules, and an exception added to let it through is stated as a change to that rule

## Thesis
Where a project declares which of its modules may depend on which — in a layers or independence contract, an architecture test, a restricted-import zone, a component dependency map or an invariant of its architecture document — every import a change adds follows that declaration. Under a layers declaration a lower layer imports nothing from a layer above it, and where the declaration names the layers that may access a layer, no other layer accesses it, so a higher layer does not bypass the layer between. Under a ports-and-adapters declaration the domain imports neither the application nor any adapter, the application imports no adapter, and no adapter imports another. Modules declared independent import none of each other in any direction, and a file in a restricted zone imports nothing from the paths the zone forbids. Where the declaration counts indirect imports, the added import also forms no link in a chain of imports from a declared module to one it may not import, whether the chain runs on through the imported module's own imports, back through the modules that already import the importing file, or both. The change adds no exception entry to admit its own new import unless it states the new entry as a change to the declared rule, since such an entry — an ignored import, an excepted path, an ignored package, a legalized dependency, a violation recorded as known — keeps the check passing while the forbidden dependency is in the code. Where the new dependency is needed, it travels the declared way: through an interface declared on the side the direction allows and implemented on the other side, or through a counterpart type on the allowed side with an explicit conversion between the two; between modules that may import each other in neither direction — modules declared independent, one adapter and another — the interface is declared in a module both may import, as the domain is for two adapters, since an implementation in one of them that names the interface would import the other.

## Rationale
A declared direction often states what is deliberately absent from the source: a module shows the imports it has, not the ones it is meant never to have, so the desired dependency graph lives in the declaration, the checker compares the code's actual graph with it, and one added import breaks the contract. The breach can be indirect: under a layers contract that counts chains of imports, a lower layer that imports a module outside every layer, which itself imports a higher layer, breaks the contract as a direct import of the higher layer would. What the direction protects is the declaration's purpose: code meant to run in one environment kept out of another, as server-only files are kept out of client code; a domain that knows nothing of the driving adapters or of a specific technical infrastructure, and adapters that know nothing of each other; a module kept independent of the rest so that useful tooling can be built on it alone. When architecture rules are introduced in a grown project, there are often hundreds or even thousands of violations, way too many to fix immediately. Two checkers document a baseline for that case: one records the violations present when a rule is introduced, then reports only new ones and shrinks the record as violations are fixed; the other has the found violations legalized in its configuration, marked to fix, and the configuration cleaned up to the target state after the fixes. An exception entry added for a new import turns a new violation into a known one: the contract is kept although the import that breaks it is in the code.

## Example
```java
bad:  package com.app.domain;  // declared: no dependency from domain to adapter
      import com.app.adapter.persistence.SqlOrderStore;
      class OrderService { private final SqlOrderStore store; ... }
good: package com.app.domain;
      public interface OrderStore { Order load(String id); }
      class OrderService { private final OrderStore store; ... }
      // adapter side: class SqlOrderStore implements OrderStore { ... }
```

## Limits
The rule reaches only a direction the project declares: the checkers compare the code's actual dependency graph with the one the project declares — an ordered list from the higher to the lower layers, a map of which component may depend on which, a description of the ideal architecture, or a built-in layered or onion architecture whose layers the project assigns to its packages — so which module ought to depend on which, where nothing is declared, is outside the rule. A layers declaration lets a higher layer import a lower one unless it names which layers may access that lower layer; an adapter may use both the domain and the application; siblings in one layer may import each other where the declaration marks them non-independent; and where the same layers repeat in several containers, a lower layer of one container may import a higher layer of another. An exception the declaration itself designs is part of the rule, such as a zone allowed to import the other side's configuration although it imports none of that side's other code; a change whose stated subject is the declaration — a new layer order, a component moved, an exception the design admits — revises the rule rather than evading it, and a change description or project context that states the new entry as such a change rejects the finding. A declaration may leave test files out, as when a test of an application service imports an in-memory implementation from the infrastructure layer; an import in a file the declaration excludes is outside it. A violation recorded as known before the change is not the change's: the rule concerns the imports and the entries the change adds.

## Validator
Grep the hunk's added lines for an import, a use, a require or a from-import, and for an added entry in a dependency declaration: an ignored import written as `importer -> imported`, an `except` path, an ignored package, a `mayDependOn` entry, a layer list, a stored known violation. Find the project's declaration: an import-contract configuration, an architecture test that builds a layered or onion architecture, a restricted-paths or boundaries setting in the lint configuration, an architecture-lint file or checker flags in the build, an architecture document whose invariants say which module knows nothing of which; where none exists, stop. Read the declaration's own diff (`git diff <base> -- <path>`) as well as its head version, since an entry the change adds there, such as a list item under an existing `mayDependOn` key or a line in a violation store, may sit in a hunk outside the slice, and an import the head version admits only through that entry is an added exception. Place the importing file and the imported module in the declaration's layers, components or zones, and check the pair against the allowed direction; where the declaration counts indirect imports, open the imported module and follow its own imports to a forbidden module, and grep the repository for the declared modules that import the importing file, directly or through other modules, and check each of them against the imported module and the modules its own imports reach. For an added exception entry, check whether the change also adds the import the entry admits, and read the change description and the project context for a statement that the entry changes the rule. Skip files the declaration excludes and violations recorded as known before the change. Validator question: **Does an import the change adds go against a dependency direction the project declares, directly or, where the declaration counts indirect imports, as a link in a chain of imports between declared modules, or does the change add an exception entry that admits its own new import without stating it as a change to the declared rule?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-11`, severity minor, `file`, `symbol`, `code` = the added import or exception entry, quoted verbatim from the diff, `fix` = the dependency carried the declared way in the file's language — an interface declared on the side the direction allows, or in a module both may import where neither may import the other, and implemented on the other side, or a counterpart type on the allowed side with an explicit conversion — with the exception entry removed, `rationale` = the declaration with its path, the direction in it that the import breaks, and for an indirect breach the chain of imports to the forbidden module).
