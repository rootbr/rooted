# A parser written in the change for input from outside the program has a fuzz test that feeds it generated input and fails when the parser crashes, panics, hangs or exhausts memory instead of returning a value or an error

## Thesis
A parser that the change writes for input from outside the program, such as a tokenizer or a recursive-descent or state-machine parser for a file format, a protocol or a small language, has a fuzz test that feeds it generated or mutated input and fails when the parser crashes, panics, overflows the stack, calls exit, raises an error other than its own parse error, runs past the engine's per-input time limit or needs more memory than the engine's limit, while a returned value or a returned parse error passes. The fuzz target resides in the same repository as the parser, is built with the other tests, is as deterministic as possible and fast, and its seed corpus, including every input that once made it fail, runs in the usual test run as a regression test.

## Rationale
Fuzz testing exercises an interface with generated data, most commonly by mutating samples from a corpus or by generating inputs from a model of the input; a guided fuzzer keeps each input that yields new signal such as new coverage, so the corpus and the coverage grow over time, and coverage guidance reaches edge cases that people often miss. It finds programming errors unrelated to the project requirements, which developers rarely write tests for and which lead to security holes and reliability problems; the kinds it typically finds include plain crashes such as null dereferences and uncaught exceptions, and resource bugs such as memory exhaustion, hangs or infinite loops and infinite recursion. Most of the kinds it typically finds are the kinds attackers use to produce exploits, from denial of service through to full remote code execution. Fuzzing is valuable for software that receives input from untrusted sources and for a high-volume interface that takes complex input even when every input is trusted, and parsers of any kind are named among the targets that consume untrusted or complicated input where it has been useful. With the classic fuzz technique and crash or hang as the failure criterion, 9 of 74 Unix utilities crashed or hung on Linux, 15 of 78 on FreeBSD and 12 of 76 on MacOS, 24 different utilities across the three platforms. The engines report as a failure a panic, an uncaught exception, an exit call, a stack overflow, an input that runs past the per-input timeout (1 second in one engine, 1200 seconds by default in another) and an input that needs more resident memory than the limit (2048 MB by default in the second); a target that returns as soon as the parser reports its parse error therefore passes every malformed input the parser rejects with that error. An input that made the target fail is added to the seed corpus as a form of regression testing; one engine writes it there itself, and the ordinary test command then runs it by default, serving as a regression test once the bug is fixed. A target that makes random decisions not based on the input bytes makes fuzzing inefficient, and one that times out or runs out of memory makes fuzzing stall quickly.

## Example
```rust
bad:  pub struct RecordParser<'a> { input: &'a [u8], pos: usize }
      pub fn parse_record(input: &[u8]) -> Result<Record, ParseError> { let key = RecordParser { input, pos: 0 }.next_token()?; ... }
      #[test] fn parses_pair() { assert!(parse_record(b"k=v").is_ok()); }
good: pub struct RecordParser<'a> { input: &'a [u8], pos: usize }
      pub fn parse_record(input: &[u8]) -> Result<Record, ParseError> { let key = RecordParser { input, pos: 0 }.next_token()?; ... }
      #[test] fn parses_pair() { assert!(parse_record(b"k=v").is_ok()); }
      fuzz_target!(|data: &[u8]| { let _ = parse_record(data); }); // Ok or Err passes; a panic, hang or memory exhaustion fails
      #[test] fn seed_corpus() { for f in std::fs::read_dir("fuzz/corpus/parse_record").unwrap() { let _ = parse_record(&std::fs::read(f.unwrap().path()).unwrap()); } }
```

## Limits
Fuzzing is not a substitute for explicitly testing functional requirements: the fuzz test adds to the parser's unit tests of what it accepts and returns, and does not replace them. A parser the code only calls, from a standard library or an established dependency, is outside the rule, because a fuzz target is maintained by the owners of the code it exercises, in the same repository as that code. The usual test run executes the target on its seed corpus, regularly tested and not necessarily fuzzed; running it continuously on fuzzing infrastructure, which the fuzzing documentation also asks for, is a separate practice the rule does not reach. Fuzzing also finds logical bugs, such as a failed round trip or an assertion failure, when the target checks for them; the rule asks only for the crash, hang and memory criteria, and a target that adds such a check meets it too. Generation-based fuzzing, which produces test data from a model of the input, is one of the two most common forms of fuzz testing, coverage guidance is an extension of the other, mutation-based form, and a fuzz target is independent of any particular engine, so a test that generates inputs from a model of the input and fails on the same conditions meets the rule, with or without coverage guidance. A saved input that once timed out need not reproduce the hang on every run: in a study of 23,907 bugs found in 316 continuously fuzzed projects, 30% of timeouts (1225 of 4054) and 20% of out-of-memory errors (424 of 2112) were flaky, against 13% of all bugs, timeout and out of memory being the most flaky fault types. The sources recommend a fuzz test for a parser of untrusted or complex input rather than require one for every parser, so the finding is a suggestion, and a parser whose input is neither untrusted nor complex is outside the rule.

## Validator
Grep the hunk for an added type or routine named as a parser, lexer, tokenizer or scanner, a parse, lex or tokenize routine, or next-token and peek-token calls. Open the routine and confirm that the change writes the grammar logic itself, as byte or character dispatch, a token loop, a state machine or recursive descent, rather than handing the input to a standard-library or dependency parser. Trace its callers to where the input enters the program: a file, a socket, a request body, a message, command-line text or an environment value. Search the repository's test and fuzz directories for a fuzz target that calls the parser, treats its returned parse error as a pass and runs in the usual test run on its seed corpus; a generation-based test that calls the parser with generated input, treats its returned parse error as a pass and runs in the usual test run counts as one. Validator question: **Does the change write a parser for input from outside the program with no fuzz target or generation-based test that calls it, fails on a crash, panic, hang or memory exhaustion and runs in the usual test run?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-28`, severity suggestion, `file`, `symbol`, `code` = the parser routine's signature line as written in the diff, `fix` = a fuzz target in the file's language that passes generated bytes to the parser, returns on its parse error and has a seed corpus that the ordinary test command runs, `rationale` = names where the parser's input enters from outside the program and the crash, hang and memory failures that only generated input reaches).
