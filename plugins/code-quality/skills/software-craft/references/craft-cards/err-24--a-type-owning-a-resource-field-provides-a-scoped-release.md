# A type that keeps an acquired resource in a field it owns provides an explicit release operation that releases it and implements the language's scoped-release protocol

## Thesis
A type — a class, a struct or an object — that acquires a resource such as a file, a socket, a connection or a stream, or takes over one it is handed, and keeps it in one of its own fields beyond a single call owns that resource and becomes a resource itself. It offers an explicit release operation — a close or dispose method, or the destructor in a language that runs one when a value goes out of scope — that releases every resource its fields own, on every path through the operation, the exceptional ones included. It implements the language's scoped-release protocol, so that its users can bind it to a scope that releases it when the scope exits, after an error as well; where the protocol is a helper that calls a close method, the close method meets it. When its constructor fails after acquiring some of those resources, the constructor releases them before the failure leaves it, because no caller ever receives the object through which to release them.

## Rationale
Garbage-collecting or de-allocating an object is not sufficient to dispose of the finite resource it holds, such as a socket, a file descriptor or a database connection; to dispose of it, the program should call a method on the object. A finalizer may be called only after an indefinite delay, or never in a runtime where finalization is disabled or removed, and there is no guarantee when the runtime invokes it; a cleanup action registered with the collector carries no guarantee of running at process exit; and an unexpected reference, from a global or an exception traceback, may keep the object alive longer than intended. Because garbage collection is not guaranteed to happen, an object that contains an external resource such as an open file also provides an explicit way to release it, usually a close method, and programs are strongly recommended to close such objects explicitly. A leak checker that enforces this idiom for an owning field assigned once per instance requires a destructor-like method that meets the field's release obligation on every path through it, the exceptional ones included, and gives the enclosing class the obligation to have that method called, so whoever holds the object has to call it. Implementing the protocol is what lets the scoped-release construct release the owner: a block that calls the close method automatically when it exits ensures prompt release and avoids resource-exhaustion errors that may otherwise occur, a helper turns a close method into a context that calls it even if an error occurs, a declaration calls the dispose method at the end of its scope, a deferred call releases a resource whichever path the function takes to return, and a destructor's code runs whenever its value goes out of scope. Nested resources that a disposable type allocates and tracks should be disposed when its instance is disposed. Inside a constructor, storing a resource in an owning field meets its obligation only if the constructor returns normally: when the constructor throws, the constructed object is not accessible afterward, so its fields need to be closed before it exits.

## Example
```python
bad:  class Reader:
          def __init__(self, path):
              self.file = open(path)
good: class Reader:
          def __init__(self, path):
              self.file = open(path)
          def close(self):
              self.file.close()
          def __enter__(self): return self
          def __exit__(self, *exc): self.close()
```

## Limits
A field that only borrows a resource whose release belongs to another owner, including one handed in through a parameter that does not mark the transfer, is outside the rule: a leak checker treats unannotated parameters and fields as non-owning and lets a parameter marked as owning take the resource over only when the routine returns normally, and a borrowed-handle type requires the resource to remain open for as long as the borrow lasts. A resource kept in a static field and used until the program exits has no good place to be released; a leak checker that warns about such a field offers an option to permit it, which retains only a small number of resources throughout execution. An object that implements the protocol in a form not backed by input or output, such as a stream over an in-memory collection, in general needs no scoped release. In a language whose destructor runs the destructors of all of a value's fields, a field whose own type releases the resource when dropped, such as an owned descriptor that closes on drop, is released with its owner without written code; a field holding a raw handle, such as a bare descriptor number, has no destructor, and its owner, as the handle's unique owner, closes it in a destructor it implements. A cleanup action the collector runs once the owner becomes unreachable can back up the release operation — the close method runs it explicitly, and the collector runs it only when close was never called — and does not replace it.

## Validator
Grep the added lines for an assignment of an opened, connected or constructed resource to a field of the current object, and for a field declaration whose type is a file, stream, reader, writer, socket, channel, connection, statement, result set, closeable interface or raw handle. Open the file and find the type that declares the field. Treat a field as owning when the type itself opens, connects or constructs the resource it stores there, or when the parameter or call that hands the resource in marks the transfer, by an owning annotation, an owned-handle type or documentation that the type takes the resource over and releases it. Skip a field that stores a resource handed in without such a mark, a field whose documentation, annotation or type marks it as borrowed from another owner, a static field kept until the program exits, a field whose object holds no operating-system resource, such as a stream over an in-memory collection, and, where the language's destructor drops each field, a field whose own type releases the resource when dropped. For each remaining owning field, find the type's release operation — a close or dispose method or a destructor — and check that it releases that field and every other owning field on every path through it, the exceptional ones included, rather than leaving the release to a finalizer or a collector-driven cleanup action. Check that the type implements the language's scoped-release protocol: a closeable or disposable interface, the enter and exit methods of a context manager or a close method a closing helper can call, a dispose method under the language's well-known symbol, a close method a deferred call can run, or a destructor. Read the constructor: where it can fail after opening, connecting or constructing a resource itself, check that the failure path releases what it has already acquired before the failure propagates; a resource handed in stays with its caller when the constructor fails, unless the interface says the constructor releases it. Validator question: **Does this type keep a resource it owns in a field without a release operation that releases every owned field on every path, without implementing the language's scoped-release protocol, or with a constructor that leaves already-acquired resources unreleased when it fails?** Yes → flag.
