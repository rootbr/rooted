# A getter and setter that only read and write one of the object's own fields are replaced by a public attribute in a language whose properties let that attribute later gain logic without changing its callers

## Thesis
In a language whose properties let callers read and assign a value with plain attribute syntax while a getter and a setter run behind it, and whose design guidelines admit a public instance field, a pair of accessors over one of the object's own fields — a getter and a setter method, or a property's get and set — whose bodies do nothing but return that field and assign their argument to it is replaced by the field itself, made public. The pair is trivial when making the field public would change nothing beyond the syntax of access. An accessor stays where it does work a public field cannot: validating the value, maintaining an invariant, converting between an internal type and an interface type, invalidating or rebuilding other state when the value is set, or computing the value lazily.

## Rationale
A getter that only returns a field and a setter that only assigns it add no semantic value: the field could just as well be public, and the pair only makes the class more verbose. The reason given for such a pair is that a public field exposes the internal representation, which then cannot be changed without impacting the code of its callers. Where properties keep attribute syntax, that reason does not hold: a simple public attribute that later needs to grow behaviour becomes a property behind the same attribute access syntax, so the class keeps its public interface while its internals evolve. A field-backed get and set pair with no extra logic is very rarely useful, and a pass-through pair defined only to hide a property gives way to the public property. With the pair gone, accessors remain where they provide a meaningful role or behaviour, and where a setter method remains, its invocation hints that a potentially non-trivial operation is occurring.

## Example
```typescript
bad:  private countValue = 0;
      get count(): number { return this.countValue; }
      set count(value: number) { this.countValue = value; }
good: count = 0;
```

## Limits
A pair whose setter is visible to fewer callers than its getter restrains which code can modify the value, a difference from a public field beyond syntax, and stays. A getter with no setter can make an attribute read-only, which a public field is not; the rule reaches pairs only, and where the language can mark the field itself read-only, that marker rather than a getter with no setter is the alternative to consider. A pair that forwards to a member of another object the class holds restricts the visibility of that internal detail and is outside the rule, which reaches the object's own field. A pair that overrides an accessor or property that a supertype defines under the same name stays, and so do a pair that implements an abstract property of an abstract base class and a pair that a subtype overrides with its own accessor: an inherited property takes precedence over an instance attribute of its name, a class stays abstract until it overrides each abstract property, and a field may not override an inherited accessor nor an accessor an inherited field, so a field cannot take the pair's place there. An accessor kept because getting or setting the value is expected to become complex or costly in a reasonable future stays where a comment or the project context states that expectation. A getter and setter method pair that existing code already calls is outside the rule unless the change rewrites each of those calls, and a method pair that code outside the repository may call stays: replacing the methods with a field changes every call, and a public member carries a commitment to avoid backwards incompatible changes. A property pair keeps its callers' syntax, so the rule reaches it wherever the change touches it.

Whether a trivial pair goes is contested, and the condition that separates the cases is whether a public attribute can later gain behaviour behind the same access syntax. Where it can and the language's design guidelines admit a public instance field, the documented guidance makes a pass-through pair's field public, since a later property keeps the public interface. Where reading a field and calling an accessor are written differently, a public field cannot later change how the value is stored without impacting the code of its callers, and the guidance divides: a first language's guideline still says to avoid trivial getters and setters, whose data item could just as well be public; a second language's analyzer rule holds that a public field exposes the internal representation, which cannot be changed afterwards; a third language's API guidelines hold that making a field public pins down a representation choice, so that outside compound, passive data structures getter and setter methods over hidden fields are worth considering; and a fourth language's documentation, noting that the language provides no automatic support for getters and setters, calls providing them often appropriate. The rule does not reach those languages. Nor does it reach a language with properties whose design guidelines forbid public instance fields and provide properties for accessing fields instead, since a public field is not the replacement there. A project convention, stated in the project context, that keeps accessors for every field is the tolerance that rejects the finding.


A pair over a field that the type validates or keeps consistent with other fields in its other operations is outside the rule: there the setter that only assigns is the defect and the field stays private. A pair whose setter no code calls is outside the rule too: the field is then assigned only at construction, so the setter goes and the field stays read-only, behind its getter or as a read-only public field.
## Validator
Grep the hunk for an accessor declaration: a property or setter decorator, a get or set accessor, or a routine whose name opens with get or set. Open the file and read the class that declares it. Take each getter and setter the class declares for one name — two accessor methods, or a property's get and set — and read both bodies. Go on only when the getter does nothing but return one of the object's own fields and the setter does nothing but assign its argument to that same field. Skip a pair whose setter is visible to fewer callers than its getter, a pair that forwards to a member of another object, a pair that overrides an accessor or property a supertype defines under the same name, implements an abstract property of an abstract base class, or is overridden by a subtype's own accessor, a getter and setter method pair that code outside the change calls, and one the change does not add unless the change rewrites each of its calls, a getter with no setter, and an accessor that a comment or the project context keeps because getting or setting the value is expected to become complex or costly. Go on only when the file's language lets callers read and assign a property with the same syntax as a plain attribute and its design guidelines do not forbid public instance fields. Validator question: **Does the class declare a getter and a setter for one of its own fields whose bodies only return the field and assign it, in a language where that field could be public and later gain behaviour behind the same attribute syntax?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-32`, severity suggestion, `file`, `symbol`, `code` = the getter and setter declaration lines quoted verbatim from the diff, `fix` = the backing field and both accessors replaced by one public field carrying the name the accessors share (for a method pair, the name after its get or set prefix), each use of the backing field renamed to it, in the class and in any subtype or other code that reads or writes it and each call of a method pair in the change rewritten as an attribute read or assignment, in the file's language, `rationale` = that neither accessor does more than return or assign the field, so a public field changes nothing beyond the syntax of access and can later gain behaviour behind the same syntax).
