# Research note — Stable dependencies and abstractness between components

Topic `stable-dependencies-and-abstractness` of group K. Architecture, domain `architecture`, id prefix `ARCH`. Formulation locators: Clean Architecture ch. 14 'Component Coupling' (ADP, SDP, SAP, the instability metric I = fan-out / (fan-in + fan-out), the main sequence, the zone of pain and the zone of uselessness); 97 Things essay 76 'The Single Responsibility Principle' (dependents of a volatile class). Marked contested in the design note.

Clean Architecture ch. 14 states three principles between components. ADP: the component graph has no cycles. SDP: depend in the direction of stability, measured by I = fan-out / (fan-in + fan-out). SAP: a component is as abstract as it is stable, measured by the distance D from the main sequence. The industry agrees on ADP. JPMS resolution, Bazel's DAG of targets and the Maven reactor reject cycles between build units, and Nx, dependency-cruiser (at folder scope), ArchUnit and JDepend check them. Two defect studies associate cycles with defects (Oyetoyan et al. 2013, abstract; Mo et al. 2021, abstract and review), and the dispute is only over the remedy: Martin, JDepend and dependency-cruiser invert a dependency, while Google's Go guidance calls an interface introduced to break a cycle a sign of badly structured packages and prefers consolidation. SDP and SAP are contested as metrics. The tools that compute I, A and D disclaim them as yardsticks, dependency-cruiser calls a fully unstable module "not a bad thing" and quotes Martin's "a metric is not a god", and no opened source measures an outcome for depending on a less stable component or for distance from the main sequence. The separating condition pending entry 81 asks for is volatility (expected change), not graph position. Martin confines the zone of pain to volatile components, JDepend's declared V=0 exempts packages not expected to change, and Mo et al.'s Unstable Interface measures volatility from revision history at file level, with thresholds unopened. In its declared form the condition is official documentation: the Rust API Guidelines' C-STABLE holds that a crate at 1.0.0 or later is stable only when every dependency whose types it exposes is stable, and RFC 1977, SemVer items 4 and 9 and Go's v0 documentation back it. The topic therefore yields two cards: component acyclicity and the declared-stability form of SDP. The metric forms of SDP and SAP and the component-level fan-out cap (Crossing) stay pending with the searches recorded.

## Formulation layer

The canon's formulation of this topic is Clean Architecture ch. 14, which states three principles. ADP: no cycles among components. SDP: depend in the direction of stability, so that I = fan-out / (fan-in + fan-out) decreases along every dependency. SAP: a component is as abstract as it is stable, measured by its distance D from the main sequence. The book was not openable, so its statements arrive as search-relayed highlights or marked paraphrases. The following were fetched: 97 Things essay 76, the JDepend, dependency-cruiser, ArchUnit and PHP_Depend documentation, the Go spec, the java.lang.module documentation, Bazel, SemVer, the Go module version documentation, the Google Go style guide and Software Engineering at Google ch. 21. The pending entry asks whether any source separates the case of a component many others depend on that itself depends on a frequently changing one. At the formulation level, Martin himself separates it. He confines the zone of pain to volatile components ("nonvolatile components are harmless in the (0, 0) zone", relayed), and JDepend puts that into practice as a per-package volatility V. Stability (structural fan-in) and volatility (expected change) are different quantities, though. Only change-history measures such as Mo et al.'s Unstable Interface measure the second, and that definition reached me only through a search summary. The canon disagrees in three places. First, the tools disclaim the metrics as yardsticks: JDepend says so, dependency-cruiser quotes Martin's own "a metric is not a god" and adds that a fully unstable module is not bad. Second, the Google Go style guide calls an interface introduced to break a cycle a sign of badly structured packages, against Martin's DIP remedy. Third, SEG ch. 21 says no node's indefinite stability can be assumed and treats stability as a promise the provider declares, as SemVer 0.y.z and Go v0 do. The aposd-vs-clean-code discussion has no exchange on component coupling. The following were not opened: Clean Architecture, APPP, Martin's 1994 whitepaper, Lakos, Knoernschild, Fundamentals of Software Architecture (no search hit) and the Mo et al. full text. All six searches are spent.

## Reception layer

Tools check acyclicity between components by default and enforce it. dependency-cruiser's recommended preset, Spring Modulith's verify(), Nx's enforce-module-boundaries, ArchUnit slices/modules and import-linter acyclic_siblings all ship the check, and the Go spec, JPMS resolution and the Maven reactor reject such cycles outright. The Stable Dependencies Principle and the main sequence get much weaker support. The only mechanical SDP check is dependency-cruiser's opt-in moreUnstable attribute, whose own page says a 100%-unstable module "is not a bad thing" and quotes Martin that "a metric is not a god". JDepend says its metrics "should not be used as yard sticks", and NDepend's 0.7 distance threshold (relayed) is the one numeric cut-off found, with no derivation. On the separating condition the pending entry asks for, JDepend's Volatility setting is the one fetched source that splits structural position from expected change: a package configured as not volatile (java.lang) is "not cause for concern" to depend on. Mo et al.'s Unstable Interface (relayed, defined in a secondary summary as a highly influential file that frequently co-changes) and CodeScene's change-coupling docs (relayed, "neither good nor bad") also measure that split from revision history. All three work at file or package level, and none gives a component-level threshold. The canon is openly split on how to remove a cycle. Martin, JDepend and dependency-cruiser's no-circular comment prescribe inverting the dependency through an interface. Google's Go best practices say "introducing interfaces to break dependency cycles is often a signal of improperly structured packages" and advise merging packages that are always imported together, and Applied Go (relayed) agrees. Sonar (relayed) exempts cycles forced by sealed hierarchies as "not a design problem". I could not open any paper full text, the Sonar, NDepend or CodeScene pages, or any Hacker News or Lobsters thread. A search for named practitioner critiques of the instability metric and the main sequence found none.

## Evidence layer

The ban on dependency cycles between components has the firmest evidence. Language and build tooling refuse such cycles outright: the Go spec, JPMS resolution, Bazel's DAG and the Maven reactor. JDepend, ArchUnit, dependency-cruiser, import-linter and Nx check cycles at the package, folder or project level. Associational studies (Oyetoyan 2013, Mo et al. 2021, MacCormack and Sturtevant 2016) put more defects in cyclic groups, while Melton and Tempero 2007 left the quality effect of cycles untested. The Stable Dependencies and Stable Abstractions principles remain contested: no opened source measured an outcome for "depends on a less stable component" (Arcan's Unstable Dependency smell has a 30% threshold but no UD-specific result was found) or for distance from the main sequence. The tools that compute I, A and D (JDepend, dependency-cruiser, ArchUnit) disclaim them as yardsticks. The candidate separating condition is change history, not structure: Mo et al.'s Unstable Interface and Crossing, the anti-patterns that contribute most, both require co-change in the revision history; Cataldo et al. 2009 find logical (co-change) dependencies explain more fault variance than syntactic ones, and JDepend's volatility flag V=0 exempts dependencies on packages not expected to change. Unopened: the Mo et al. TSE full text with Crossing thresholds, the Decoupling Level paper body, Sangal 2005, Al-Mutawa 2014 and the Oyetoyan SANER 2015 study; the six-search budget was spent.

## Spine — candidate rules in source order

1. **A dependency a change adds from one component to another, declared in a build file or module descriptor or made by an import across components, leaves the graph of the repository's components acyclic even where no cycle runs between individual files** — The components of one repository form an acyclic dependency graph. Components here are units of build or release, such as build modules, workspace packages or projects, build targets and named modules. A dependency a change declares in a build file or module descriptor is an edge between components, and so is an import from one component's code into another's. No path of such edges, direct or transitive, leads back to the depending component, even where the files along that path form no cycle; a component that depends on a cycle must be released with it. DSN-10 judges a cycle that stays inside one component. An edge the project's configured cycle check ignores by name is a documented tolerance, and calls between services over a network are outside the rule.

6. **A component released at version 1.0.0 or later uses in its public API no type or trait from a dependency at a 0.y.z or pre-release version** — Under semantic versioning, a component at 1.0.0 or later is stable only if each of its public dependencies is stable.
