# A thrown or returned error has a type that says what failed, never a string or other non-error value and never a generic exception class

## Thesis
An error that code throws, raises or rejects a promise with is an object of an error type, and that type names the failure: a specific type the standard library provides when one matches, or a type of the code's own. A routine's declared list of thrown types names those specific types too. A public routine that reports failure through a result value gives it an error type that implements the language's error interface and names the failure. Failures that callers handle differently get distinct types or variants, and the hierarchy follows the distinctions the catching code needs rather than the places the errors are raised. In a language that lets any value be thrown and whose base error object records a stack trace when it is created, that base object stays acceptable where no caller needs to tell this failure apart from others.

## Rationale
A handler selects failures by type. A generic type — `Throwable`, `Exception`, `RuntimeException`, `BaseException`, `SystemException`, `ApplicationException`, or `Error` where it names the branch of unrecoverable faults beside `Exception` — sits above whole families of unrelated failures, so the one clause that catches it also catches failures the caller did not mean to handle — for the broadest of these types, failed assertions and division by zero among them. The caller must then catch and rethrow what it does not intend to handle, the message text becomes the only way to tell failures apart — a match that is error-prone and hard to maintain — and legitimate errors may be silenced by accident. The generic type can hide the details a caller needs to choose a recovery and produce inappropriate responses to particular conditions; a declaration that a routine throws a generic type defeats checked failure lists the same way. A thrown or rejected value that is not an error object — a string, a number, a plain record, nothing — populates no stack trace, so the value carries no record of where the failure began and debugging is hard; inside an asynchronous routine, rejecting a promise with a value is equivalent to throwing it. In result-typed code a string or unit error type does not implement the error interface, so it cannot be the source of a wrapping error and stays outside the interface through which error-handling libraries abstract over error types; unit also carries no information about what went wrong. A type designed for the failure restores selection by type: the handler names exactly the failures it recovers from, the rest propagate untouched, and the code answers "what went wrong?" rather than only "a problem occurred". Throwing a generic, uninformative type where a specific one fits is one of the causes of exception-handling faults catalogued in a study of two open-source projects.

## Example
```rust
bad:  pub fn parse(line: &str) -> Result<Record, String> {
          Err(format!("bad line: {line}"))
      }
good: #[derive(Debug)]
      pub enum ParseError { BadLine(String), MissingField(&'static str) }
      impl std::fmt::Display for ParseError { ... }
      impl std::error::Error for ParseError {}
      pub fn parse(line: &str) -> Result<Record, ParseError> {
          Err(ParseError::BadLine(line.to_string()))
      }
```

## Limits
A routine that overrides or implements a declaration already naming a generic type, and a routine that only passes on a generic-type error thrown by a callee, keep that declaration; the defect sits at the inherited declaration or the callee. A test method or a test set-up or tear-down method that declares a generic type keeps that declaration. A standard-library type that matches the failure — an invalid-argument or value error — satisfies the rule; a new type is needed only when callers need a distinction the library types do not make. A project's own base error type for a package or library, with specific subtypes or variants below it, is a purpose-designed type, not a generic type. In result-typed code the rule reaches the error types of public routines; a private helper whose string or unit error is converted before it leaves the module is outside it, and a result used as a plain two-way choice rather than for a fallible operation calls for an enumeration of its own, not an error type. Where the language's convention declares its error interface itself as a routine's error result, that declaration satisfies the rule; a failure callers tell apart is then named by the returned error's own type or by a published error value callers compare against, and the base error value stays acceptable where no caller tells the failure apart. A tolerance the project context states for generated code or a throwaway-script tier rejects the finding.

## Validator
Grep the added lines for a throw, raise or promise rejection whose operand is a literal (a quoted string, a template, a number, an object literal, `null`, `undefined`), for a promise rejection with no operand, for a throw or raise that constructs a generic type, for a declaration that a routine throws a generic type, and for a result type or error return whose error is a string, a string slice or unit. Open the hunk around each match and note whether the routine overrides or implements a declaration that already names a generic type, only passes on a callee's generic-type error, or, for a declaration, is a test method or a test set-up or tear-down method; in a language that lets any value be thrown and whose base error object records a stack trace when it is created, whether the operand is that base error object, which passes unless the added lines themselves tell this failure apart from others by its message text; for a result-typed error, whether the routine is public and whether its result reports a fallible operation rather than a plain two-way choice. Validator question: **does the added code throw, raise, reject with or declare a non-error value or a generic exception type, or give a public routine a result whose error type is a string or unit, with none of the inherited-declaration, pass-through, test-method, undistinguished base-error-object, private-helper or two-way-choice cases applying?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-09`, severity minor, `file`, `symbol`, `code` = the throw, raise, reject, throws-declaration or result signature quoted verbatim from the diff, `fix` = the same site throwing or returning a matching standard-library type or a purpose-designed error type that implements the language's error interface, in the file's language, `rationale` = naming what the caller loses: selection by type, the stack trace, or use as the source of another error).
