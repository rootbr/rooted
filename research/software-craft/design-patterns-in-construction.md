# Research note — Design patterns in construction

Topic `design-patterns-in-construction` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: SWEBOK Guide V4.0 ch. 3 'Software Design' §4.4; the SWEBOK V3 Software Design chapter §3.3 'Design Patterns' as the openable transcription; CC5 heuristic 'Look for Common Design Patterns' as a second formulation.

The canon (SWEBOK V3 §3.3 and §3.5 in the openable transcription, Code Complete §5.3, GoF §1.1, §1.7, §1.8 and the pattern chapters) treats a design pattern as 'a common solution to a common problem in a given context'. It takes three positions. Apply a pattern where its problem or variation is present. Implement it so that it keeps its intent. Prefer the language's own construct where one exists. The industry disagrees in three places: when to apply a pattern (GoF ch. 6 and Effective Java Item 2 say early; Fowler and Kerievsky say not until needed), whether Singleton is legitimate (GoF 1994 against Gamma 2009, Saariste and Sonar S6548), and whether patterns compensate for missing language features (Norvig and Akhmechet against Brooker). The research is inconsistent on whether to use a pattern at all, so the 'only where the problem is present' rule stays pending. Prechelt et al. 2001 advise the pattern's flexibility. Vokáč et al. 2004 say patterns must match 'the problem and the people'. Krein et al. 2016 find the benefit depends on the pattern and on the maintainer's knowledge of it. Zhang and Budgen 2012 find no firm support, Bieman et al. 2003 find pattern classes more change-prone, and Walter and Alkhaeir 2016 find them less smell-prone. The rules that ship as cards rest on documentation, tool rules and narrower studies. A singleton's accessor returns its stored instance (PMD), and a singleton has no second creation path (SpotBugs SING_*, CERT MSC07-J, OpenJDK Enum, with the once-only constructs of Go, Rust, Python and Node as the native forms). Stateless helpers are module functions, or a non-instantiable class in Java. A one-operation strategy or command is a function value unless it must carry more operations or be compared (Sonar, Error Prone, Pylint, typescript-eslint, Effective Go, the Rust book and Bijlsma 2022 on one side; Uber Go on the other). Construction with many optional inputs uses the language's named form (Google TS, Python and Go guides, Uber, Rust C-BUILDER, PMD, clippy, Pylint). A Visitor gives way to a match the toolchain checks for exhaustiveness where the language has one (OpenJDK Amber, PEP 635, the Rust book, the TS handbook, typing.assert_never), with Go and open sets separated by the Go FAQ and PEP 443. Pattern comments in code are supported by Prechelt et al. 2002, Scanniello et al. 2015 and Wedyan and Abufakher 2020. The native-form principle itself is held as Rationale, not carded. Three rules stay pending without admissible evidence: no builder where named or default arguments exist, the one-switch factory, and decorator conformance. Ownership: two cards sit at topic edges. static-only-class-becomes-module-functions is kept here as the native replacement for the static-class idiom confused with Singleton (PMD's rule was named UseSingleton); it moves to complexity-and-deep-modules if that topic claims module organisation. checked-match-instead-of-visitor leaves the policy on default and catch-all arms to the control-flow and table-driven-and-state-machines topics.

## Formulation layer

The canon agrees on three positions. First, apply a pattern only where the problem or variation it addresses is actually present: GoF §1.7–1.8, Code Complete §5.3, APOSD §19.5, Fowler's "Is Design Dead?", Kerievsky's "patterns happy" and Sonar S6548 all say so. Second, implement a pattern so that it keeps its own intent. Sources here are the GoF Singleton intent and implementation, GoF Decorator interface conformance, Effective Java Item 3 on the creation paths that break a singleton, and PMD's two singleton rules. Third, prefer the language-native form where the language provides one: GoF §1.1 and the Visitor footnote on multiple dispatch, Norvig via Fluent Python, Effective Java Items 42/44, Fowler's "pick the function 95% of the time", Effective Go HandlerFunc, PEP 443 singledispatch, TypeScript exhaustive narrowing, the Rust book, Rhodes, Software Engineering at Google ch. 12, and Go option structs. The SWEBOK V4 text (computer.org) is not openable and is recorded as an unfetched paraphrase. GoF, Code Complete, Effective Java, Refactoring, Refactoring to Patterns, Fluent Python, Clean Code and APOSD were reached only through third-party GitHub transcriptions. Norvig's slides, the 2009 Gamma interview and Johnson's talks were reached only second-hand. The aposd-vs-clean-code discussion has nothing on design patterns. The canon disagrees in three places. On timing, GoF ch. 6 (use patterns early) and Effective Java Item 2 (start with a builder) stand against Fowler and Kerievsky (not until needed, simplest form first). On Singleton's legitimacy, GoF 1994 stands against Gamma 2009, 97 Things and Sonar. On whether patterns compensate for missing language features, Norvig and rust-unofficial stand against Brooker. Research items (Prechelt 2001, Vokáč 2004, Krein 2011, Khomh 2012, Jaafar 2016) are left to the evidence layer, since WebSearch is exhausted in this run.

## Reception layer

Most of the reception agrees on two points. Apply a pattern only where the problem it solves is present: Ousterhout's APOSD §19.5, Fowler's 'Is Design Dead?', the Rust patterns book's YAGNI page, Google's Go guidance against interfaces created for a "repository or similar pattern", and Go Code Review Comments. And where the language has a native form, use it instead of the classic class-based pattern. That second point holds for strategy and command (Sonar S1604, Error Prone, typescript-eslint prefer-function-type, Fluent Python, Effective Go HandlerFunc), for the static utility class (typescript-eslint no-extraneous-class, the Google TS and Python guides, Pylint R0903) and for the telescoping-constructor builder (Rhodes for Python, Google's TS guide). Disagreement shows up in five places. (1) The 'patterns are missing language features' school (Norvig, Akhmechet, Hudec, Atwood, Graham) is disputed by Brooker's defense, and the controlled experiments do not agree with each other (Prechelt 2001 against Vokáč 2004). Krein 2016 reconciles them through pattern knowledge: the pattern solution was preferable for Decorator, while for Abstract Factory the simpler solution was mostly equivalent. (2) Static-only classes: SEI CERT MSC07-J calls them good singleton candidates, IntelliJ says they may indicate a lack of OO design, Checkstyle, PMD and Sonar require them to be non-instantiable, and Guice prefers them for pure functions. (3) Go options: Google gives variadic options only when the advantages outweigh the overhead and often prefers an option struct, while Uber says to use them from three arguments and prefers interface-based options over closures because closures cannot be compared in tests. (4) Visitor versus sum type: PEP 635 calls matching 'complimentary' to OO, the Rust patterns book keeps a Visitor with walk_* over enums, Go has no variant types (only sealed-interface type switches checked by go-sumtype), and PEP 443 calls type inspection an anti-pattern. (5) Effective Go has constructors return interfaces while Go Code Review Comments has them return concrete types. On singletons that defeat their own intent, tools check mechanically: PMD SingletonClassReturningNewInstance and SingleMethodSingleton, and SpotBugs SING_* (added in 4.8.4, April 2024, with false-positive fixes since). Sonar's catch-all S6548 is deprecated, and IntelliJ's Singleton inspection is off by default. Could not open: WebSearch was exhausted; Hacker News, Lobsters, Atwood, Norvig's slides and Graham's essay are on denied hosts; the Khomh 2012 and Jaafar antipattern studies are not on any GitHub channel, so the Atwood, Norvig, Akhmechet and Hudec quotes come only through secondary copies; no 2024–2026 practitioner survey or reading list was reachable; and the 2025 Ousterhout–Martin discussion does not take up design patterns.

## Evidence layer

The research on whether to apply a design pattern disagrees with itself. Prechelt et al. (TSE 2001, professionals, 9 tasks) conclude that it is "probably wise to choose the flexibility provided by the design pattern" unless there is a clear reason not to. Vokáč et al.'s replication (EMSE 2004) concludes that patterns "must be used in a way that matches the problem and the people". Krein et al.'s joint replication (TSE 2016, 126 participants) finds Decorator beneficial only with prior pattern knowledge and Abstract Factory "mostly equivalent" to the simpler solution. FORRT lists the three RESER 2011 replications as mixed/failed/mixed. Zhang & Budgen (TSE 2012, 611 candidates, 10 papers) found no "firm support" for pattern claims. Bieman et al. (2003) found pattern classes more change-prone in 4 of 5 systems, while Walter & Alkhaeir (IST 2016) and others found pattern classes less smell-prone. So the "use a pattern only where its problem is present" rule is contested and should be worded conditionally. The better-supported rules rest on documentation and tool rules: (a) a singleton must not hand out a second instance (PMD SingletonClassReturningNewInstance and SingleMethodSingleton, the SpotBugs SING_* detectors, CERT MSC07-J, the JDK Enum clone guard); (b) the language-native forms. A function value replaces a one-method strategy (Error Prone, Sonar S1604, Pylint R0903, Effective Go HandlerFunc, the Rust book, typescript-eslint). A sum type with an exhaustive match replaces Visitor (PEP 635, the OpenJDK Amber design note, the Rust book, the TS handbook, typescript-eslint, clippy). An option struct, builder or keyword arguments replace a telescoping constructor (Rust C-BUILDER, the Google and Uber Go guides, PMD, clippy, Pylint, pyguide). Prechelt et al. (TSE 2002), Scanniello et al. (TOSEM 2015) and Wedyan & Abufakher (2020) support naming a pattern in the code. Hands-on runs with local compilers (not openable until committed as fixtures) show where the visitor replacement does not hold across languages. Go has no variant types and a type switch with a missing case compiles and vets clean. Python's match returns None silently without a type checker and assert_never. Running a Python module as __main__ breaks the module-as-singleton guarantee. Without WebSearch, abstracts came from GitHub-hosted metadata copies (CIRDC-Pro IEEE dumps, the neverworkintheory bib, a Santos-2018 screening bib, a thesis Zotero export, Sjøberg's bib). Not openable: the Jaafar et al. EMSE 2016 abstract (only its WCRE 2013 precursor was found), the Krein et al. RESER 2011 abstract (only the FORRT outcome code), and the SWEBOK V4 text. The SWEBOK V3 §3.3 transcription was opened.

## Spine — candidate rules in source order

1. **A design pattern is introduced only where the problem or variation it resolves is present in the code, not for a flexibility nothing in the code yet needs** — SWEBOK V3 §3.3 defines a pattern as 'a common solution to a common problem in a given context', and GoF §1.8 says a pattern 'should only be applied when the flexibility it affords is actually needed', because its extra indirection can complicate a design and cost performance; Code Complete §5.3 (force-fitting, feature-itis), APOSD §19.5 and Fowler ('not too early') say the same. The research does not settle it. Prechelt et al. 2001 found positive effects in most of nine maintenance tasks and advise choosing the pattern's flexibility unless there is a clear reason to prefer the simpler solution. Vokáč et al. 2004 conclude that patterns must match 'the problem and the people', and Krein et al. 2016 find that the benefit depends on the pattern and on the maintainer's prior knowledge of it. A check would ask whether an added pattern structure serves a variation the code has, for example an interface or factory with a single implementation or a strategy seam with one strategy.
