# A test uses the real third-party library, a test double its authors provide, or a double of a wrapper the project owns, rather than a double of the third-party type itself

## Thesis
A test of code that depends on a type, function or module from a third-party package runs that code against one of three things: the real library; a fake, testing library or test server that the library's authors provide; or a thin wrapper the project owns, which states the operations the code needs in the application's own terms and keeps the library's types, concepts and exceptions inside its boundary. In the third case the unit test doubles the wrapper, and the wrapper's own integration tests run against the real library. Where the third-party type is a client that reaches its backend over HTTP or RPC, the test keeps the production client and connects it over the real transport to a test double of the server, with no wrapper added for the sake of testing. Across the cases, whatever the code under test calls directly is real library code, a double the library's authors ship, or a type the project owns.

## Rationale
A double of a third-party type encodes the test author's expectations of an API that belongs to someone else, whose owner can and will change its signature and behaviour. After an upgrade that changes the library's logic, the suite still passes because the changed code never runs in it, and the break can first show once the software is deployed. A library that is complex to drive also needs many doubles before it works at all, which yields over-specified tests and heavy fixtures, or tests that leave code uncovered because the external system is too complex to imitate; and a test cannot drive the design of an interface the project cannot change. The need to double such a type may be a sign that the design is not decoupled enough from the library. A thin wrapper moves the dependency to one place: unit tests double an interface the project shapes to its own needs, and one set of integration tests checks the wrapper against the real library, so a changed library contract fails there. A wrapper that lets too much of the library's low-level API, concepts or exceptions through its boundary leaks the abstraction, and a test that doubles the leaked part imitates the library again. An HTTP or RPC client is the exception to wrapping: imitating a client's behaviour correctly is complex, so rather than a wrapper or a hand-implemented client, the production client talks over the real transport to a test version of the backend, which keeps as much of the real code in the test as possible, and a testing library from the service's authors is the first choice for that backend. The rule is a strong default rather than a hard line: crossing it most likely, not certainly, brings the costs above.

## Example
```typescript
bad:  jest.mock("pdf-engine");
      const engine = jest.mocked(new PdfEngine());
      engine.render.mockReturnValue(new Uint8Array(4));
      expect(new InvoiceExporter(engine).export(invoice)).toHaveLength(4);
good: // DocumentRenderer: the project's own interface; its adapter over pdf-engine has integration tests
      const renderer: DocumentRenderer = { render: () => new Uint8Array(4) };
      expect(new InvoiceExporter(renderer).export(invoice)).toHaveLength(4);
```

## Limits
The rule reads names imported from packages the project declares as third-party dependencies; the language's own standard library, and code generated in the repository from the project's own definitions, are outside its reach. A double that the library's authors ship, in the library or in a companion testing package (a fake, an in-memory implementation, a test server, a ready-made request or response object), is no finding, nor is a test double of the server end that the production client reaches over the real transport, nor a double of an interface the project defines in its own terms, even where that interface's production implementation calls a third-party client. A double of a type or interface that the library's authors document as designed for doubling in tests, such as a client whose documentation shows how to mock or stub it, is no finding either, because the library's owner sanctions that seam. A tolerance the project context states for a named library, such as a library the project doubles directly because it offers neither a fake nor a practical seam for a wrapper, rejects the finding. Contested. One position puts a third-party type the code depends on behind a thin wrapper the project owns, doubles the wrapper, and integration-tests the wrapper against the real library; its evidence is a mocking framework's official guidance and an experience report (DOI 10.1145/1028664.1028765). The other position adds no wrapper around an HTTP or RPC client for testing and connects the production client over the real transport to a test double of the server; its evidence is a style guide's official guidance, which prefers this to hand-implementing the client because imitating client behaviour correctly is complex. The kind of third-party type separates the cases: a client that reaches its backend over HTTP or RPC stays real against a test server, and any other third-party type sits behind a wrapper the project owns; both positions leave undoubled the third-party type that the code under test calls. Practice mocks library classes often: across 193 Apache projects, on average 61.1% of mocked objects replace library classes, against 39.4% in an earlier study of GitHub projects; about 79% of 105 surveyed developers always or almost always mock external dependencies, and interviewed developers mock them unless the test's focus is the integration itself. These figures count more than this rule's pattern: the project study counts every mocked class outside the project's own namespace, the standard library's included, and the survey's category also takes in the project's own classes that use a library; they describe how often such doubling occurs and measure neither its harm nor its benefit.

## Validator
Grep the hunk for the creation of a double: a mock, stub or spy factory call, a mocking annotation, a patch of a module or attribute path, a module mock by package name, a generated mock type's constructor. Name the type, function or module each one replaces; for a patch target string, resolve the object the path names, which may be a third-party name reached through a project module. Open the file and resolve that name through its imports: it is third-party when it comes from a package outside the repository (a bare package specifier, or an import path outside the project's own module or package root), and not from a relative path, a project module or the language's standard library; where the import path leaves it open, compare it with the file's own package or module path. Skip a double that the same package or its authors' companion testing package provides, a double of a type or interface that the package's authors document as designed for doubling in tests, a double of the server end that a real client reaches over a real transport, and a double of an interface or class defined in the repository. Where the doubled name is an HTTP or RPC client, the fix is the production client against a test server rather than a wrapper. Validator question: **Does the added test create a mock, stub, spy or patch of a type, function or module imported from a third-party package, other than a double that package's authors ship, a double of a type they document as designed for doubling in tests, or the server end that a real client reaches over a real transport?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-06`, severity minor, `file`, `symbol`, `code` = the line from the diff that creates the double of the third-party name, `fix` = the test running the code against the real library where it runs in a test, against a double the library's authors ship, or against a double of a thin wrapper the project owns whose own integration tests use the real library, or, for an HTTP or RPC client, the production client connected to a test server, in the file's language, `rationale` = the third-party package the doubled name comes from and the library change the double would let pass unnoticed).
