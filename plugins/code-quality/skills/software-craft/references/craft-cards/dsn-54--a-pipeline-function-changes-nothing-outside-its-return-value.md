# A function passed to a pipeline step other than a terminal for-each changes nothing outside its return value

## Thesis
A function passed to a pipeline step (a map, filter, flat-map, find, any, all, some, every or take-while step, a sort comparator, a reducer) changes nothing outside itself that its return value does not carry: no variable, collection or field declared outside it, neither an element of the source being traversed nor the source itself, no file, stream or peer. The element and condition expressions of a comprehension or generator expression, which state a map and a filter in another notation, are held to the same. A result the pipeline computes is gathered by a reduction or a collecting step, not added to an outside variable or collection from such a function. An effect that is the purpose of the iteration runs in a terminal for-each step or a plain loop over the pipeline's output, not in a map whose result goes unused. Output written for debugging, and an error that an observation step logs before a later step discards it, are the effects a step's function may carry.

## Rationale
A pipeline step does not promise to call its function exactly once for every element, so an effect placed in that function happens only when, and as often as, the step calls it. A lazy map step whose output nothing consumes never calls its function at all. A step that stops as soon as its answer is determined, such as a find, some or every step, does not call its function on the remaining elements, and a sort step may call its comparator more than once for the same element. An implementation may also skip a step's calls when it can compute the result without them: a count taken from the known size of the source traverses no element and evaluates no intermediate step. The documented exception is a terminal for-each step, whose effects are not skipped this way. A function that modifies the source being traversed can cause exceptions, incorrect answers or nonconformant behaviour unless the source is built for concurrent modification, and this holds for sequential pipelines as well as parallel ones. A function call that has no effect other than computing its result makes the order of execution irrelevant, since it can be evaluated at any time. Gathering the result through a reduction or a collecting step removes the mutable outside accumulator, and minimizing mutable state makes the code clearer. Methods that build a new collection are best used with pure functions, so a map that also keeps a running total can be split into a reduction for the total and a pure map, at the cost of a second pass.

## Example
```rust
bad:  let mut total = 0;
      let doubled: Vec<u32> = items.iter().map(|x| { total += x; x * 2 }).collect();
good: let total: u32 = items.iter().sum();
      let doubled: Vec<u32> = items.iter().map(|x| x * 2).collect();
```

## Limits
A function's assignments to its own local variables change nothing outside it. A reducer or collector that adds each element to the result container the reduction supplies performs a mutable reduction, and its result carries that effect. A terminal for-each step, or a plain loop over the pipeline's output, is where an effect that is the purpose of the iteration belongs, such as updating each element or sending it on; such a step is held only to adding, removing or replacing no entry of the source it traverses. Output written for debugging is usually harmless, though when an implementation skips a step's calls it skips that output too; an observation step may also log an error before a later step discards it. A plain loop whose body writes, sends or appends is outside the rule, which reaches only a function handed to a pipeline step and the element and condition expressions of a comprehension or generator expression. The rule states sequential semantics: the ordering, visibility and thread-safety of effects in a parallel pipeline are outside it. A tolerance in the project context that names a kind of effect a step's function may carry, such as a log line, rejects the finding for that kind.

## Validator
Grep the added lines for a pipeline step (map, filter, flat-map, find, any, all, some, every, take-while, sort, reduce, fold, peek, inspect, for-each) or a comprehension, and, within the function or expression it is handed, for an assignment, a compound assignment, an increment, a mutating call (add, push, append, put, insert, extend, update, remove, write, send) or a print. Read the whole function in the hunk; when the step is handed a named function whose body the hunk shows, read that body too. Trace each write to its target: a local of the function, the accumulator a reduction or collecting step passes in and takes back, or something outside the function, such as a captured variable, collection or field, an element of the source or the source itself, a file, a stream or a peer. Set aside writes to the function's own locals and to a reduction's accumulator, output written for debugging, and an error logged by an observation step before a later step discards it. In a terminal for-each step, set aside every effect except adding, removing or replacing an entry of the source being traversed. Validator question: **Does a function handed to a pipeline step, or an element or condition expression of a comprehension or generator expression, write to state outside itself that its return value does not carry, beyond its own locals, a reduction's accumulator, debugging output, an error logged before a later step discards it, or a terminal for-each effect that adds, removes or replaces no entry of the source being traversed?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-54`, severity major, `file`, `symbol`, `code` = the added line of the step's function, or of the comprehension's expression, that writes outside it, with the step's call line when the diff adds it, quoted verbatim from the diff, `fix` = the result gathered by a reduction or a collecting step and the step's function reduced to computing its return value, or the effect moved to a terminal for-each step or a plain loop over the pipeline's output, or a change to an entry of the source made on a copy or built as a new collection, in the file's language, `rationale` = the outside state the function changes and how the step may call the function other than once per element: never, when the step is lazy and nothing consumes it; for only some elements, when it short-circuits or the implementation skips calls; more than once, when a sort repeats a comparison; for an entry of the source added, removed or replaced while the pipeline runs, that this can cause exceptions or incorrect answers unless the source is built for concurrent modification; and when the step calls the function once per element, as a map consumed in full does, that the outside accumulator is mutable state a reduction or collecting step removes and that a method building a new collection is best used with a pure function).
