# Research note — Coupling and dependency direction

Topic `coupling-and-dependency-direction` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'Orthogonality' (The Pragmatic Programmer, 20th anniversary ed., topic 10, ch. 2 'A Pragmatic Approach'); PP 'Decoupling' (topic 28, ch. 5 'Bend, or Break': train wrecks, the Law of Demeter, global data); CC5 heuristic 'Keep Coupling Loose' as a second formulation.

The canon agrees on four rules for the dependencies between modules. Keep modules orthogonal, so that a change to one requirement touches one module (PP20 Topic 10; ISO/IEC 25010 'modularity'; APOSD 'change amplification'; Fowler's shotgun surgery). Do not reach through a collaborator's collaborators (the Law of Demeter in PP20 Topic 28, CC2 §6.3 and Clean Code ch. 6). Keep the module dependency graph acyclic (CC2 §5.2; Clean Architecture's ADP). Let the consumer own the abstraction, so that policy does not depend on detail (DIP; Agile PPP's ownership inversion; the Go style guides). The industry disagrees on five points. How strict is Demeter? PP20 narrows it to one dot with stability and pipeline exemptions, Clean Code exempts data structures, Fowler calls it the 'Occasionally Useful Suggestion of Demeter', APOSD flags the forwarding methods it breeds, and PMD's own rule page warns of many false positives. Does tell-don't-ask hold (PP against Fowler)? When is an interface owed: always under strict DIP, for volatile modules in Clean Architecture, on a real need in Go, and for reused abstractions in Seemann's view? Are coupling counts worth capping? Does TDD decouple a design (Martin against Ousterhout)? Go and the Java module system reject import cycles, but Python, JavaScript, TypeScript, Java packages and Rust modules inside a crate accept them, so acyclicity is a design rule that linters check. The evidence supports six cards. Cycles have the strongest support: two runtimes reject them, linters in four ecosystems flag them, and files in cycles carry more defects (Mo et al. 2021; Oyetoyan et al. 2013; MacCormack and Sturtevant 2016). Co-change between modules that have no structural link is error-prone (Mo et al. 2021), and logical dependencies explain most fault proneness (Cataldo et al. 2009). Message chains are associated with fault-proneness but are rare, and removing smells did not lower it (Palomba et al. 2018). Consumer-declared interfaces, declared layer directions and package granularity rest on official documentation and tool rules alone, and no empirical study of dependency inversion was found. Fan-out caps stay pending: coupling metrics lose their link to faults once class size is controlled (El Emam et al. 2001), and studies disagree on whether fan-in or fan-out matters.

## Formulation layer

The canon agrees on four rules for this topic. First, keep modules orthogonal, so that a change to one requirement touches one module (PP Topic 10, ISO/IEC 25010 'modularity', APOSD 'change amplification', Fowler's 'shotgun surgery'). Second, do not reach through another object's collaborators (PP Topic 28, CC2 §6.3, Clean Code ch. 6). Third, keep the module dependency graph acyclic (CC2 §5.2, Clean Architecture ADP, the Go spec, JPMS module resolution). Fourth, let the consumer own the abstraction so that policy does not depend on detail (DIP and Agile PPP's 'clients own the interfaces', Go Code Review Comments, Google Go style, Rust C-GENERIC). Opened directly: the 97 Things essays, the aposd-vs-clean-code discussion, SWEBOK V3 ch. 2, the Go spec, Go Code Review Comments, Google's Go style guide, Effective Go, Pike's 'Go at Google', the Python FAQ, the JDK module javadoc, the Rust API guidelines, SEG ch. 18, a UBC course textbook and Seemann's blog source. The Pragmatic Programmer (both editions), Code Complete, Clean Code, Clean Architecture, APOSD, Refactoring, Tidy First? and Fowler's bliki could not be opened; they are relayed through third-party reading notes on GitHub, ISO 25010 is relayed through the iSAQB glossary, and the Hunt & Thomas 'Art of Enbugging' column stays unfetched. The canon disagrees on five points: how strict the Law of Demeter is (PP20 replaces it with the one-dot rule plus stability and pipeline exemptions, Clean Code exempts data structures, CC2 exempts nothing, Fowler calls it the 'Occasionally Useful Suggestion of Demeter', and APOSD flags the wrapper methods the PP 1st edition accepts); Tell-Don't-Ask (PP versus Fowler); when to introduce an interface (strict DIP, Clean Architecture's 'volatile modules only', Go's 'not before a real need', Seemann's Reused Abstractions Principle, and Effective Go versus 'return concrete types'); DRY versus 'a little copying is better than a little dependency' (Pike, 'Beware the Share'); and whether TDD drives decoupling (Martin versus Ousterhout). Go and JPMS reject cycles while Python and ES modules allow them, so acyclicity is a design rule, not a compiler guarantee.

## Reception layer

Reception splits along the topic's four rules. Cyclic dependencies between modules get the widest agreement. Go forbids them in the language spec, and Pike's SPLASH 2012 talk explains why from Google's experience. JDepend, ArchUnit, import-linter, Pylint, eslint-plugin-import, Biome, Oxlint and dependency-cruiser all detect them. Two qualifications recur: the Python FAQ says circular imports work in the `import module` form and can be fixed mechanically, and nearly every JS/TS and Python tool leaves type-only import edges out of cycle detection. The Law of Demeter is the most contested rule. PMD's own rule page warns that it is 'prone to many false-positives' and has a configurable trustRadius. Fowler is relayed as calling it the 'Occasionally Useful Suggestion of Demeter'. The c2 wiki says it trades logical coupling for layers of forwarding. The 20th-anniversary Pragmatic Programmer narrows it to 'Don't Chain Method Calls', with exceptions for stable libraries and pipelines (relayed from a reader's notes, not opened). Clippy and Ruff have no such lint. Coupling-count checks with thresholds ship for Java only: PMD CBO 20 and imports 30, Checkstyle fan-out 20 and data-abstraction coupling 7, Sonar S1200 20; eslint-plugin-import's max-dependencies (default 10, off unless enabled) covers JS/TS. These tools call themselves gauges, and El Emam et al. (the NWIT review of the 2001 study) found that class size confounds OO metrics' association with faults. Dependency inversion and consumer-owned abstractions are defended by Martin (the Dependency Rule; 'senders own the interfaces') and appear as Google Go style guidance that the consumer defines the interface. They are qualified by Google's own 'avoid unnecessary interfaces' and 'interfaces to break cycles signal improperly structured packages', by Seemann's critique of 1:1 header interfaces and his 'dependency rejection' for FP, and by Ousterhout's dispute that mocks yield decoupling. Could not open: Fowler's bliki, Haack's dot-counting post, Dan North's SOLID slides, DHH's DI post, Beck's Tidy First?, the c2 wiki pages, and every HN/Lobsters thread (WebSearch budget exhausted, hosts denied). These are marked unfetched and cannot anchor a card.

## Evidence layer

The evidence for this topic splits in two. Official documentation and static-analysis rules state the checkable rules directly and can be opened: the Go spec bans import cycles; eslint-plugin-import, Biome, Pylint, dependency-cruiser and import-linter flag cycles or enforce layer direction; PMD, Checkstyle and Sonar cap fan-out at 20 or DAC at 7; the Go style guides say the consumer declares the interface; Rust C-GENERIC and PMD LooseCoupling ask for the most general type. The research is associational. It ties cycles (Oyetoyan 2013; MacCormack and Sturtevant 2016; Mo et al. 2021), dependency-network centrality (Zimmermann and Nagappan 2008, +10 points recall), coupling metrics (Briand et al. 2000; Isong and Obeten 2013), long message chains (Palomba et al. 2018) and co-change across modules (Cataldo et al. 2009; Mo et al. 2021; Palomba et al. 2015) to fault- or change-proneness. Only the Palomba PDFs (fetched from the author's GitHub Pages site) and the neverworkintheory reviews were opened as primary text. Every other paper is relayed through third-party GitHub copies of its abstract or notes quoting it, because WebSearch was exhausted and publisher hosts are denied. The Law of Demeter's empirical validation (Guo et al., WCRE 2011) and Khomh et al. 2012 are unfetched, and no empirical study of dependency inversion or consumer-declared abstractions was found. That rule rests on official documentation and tool rules alone. Several findings cut against these rules. El Emam et al. 2001 found the OO coupling metrics lose their link to faults once class size is controlled, and Rahman and Devanbu 2013 found code metrics less useful than process metrics. Melton and Tempero 2007 found cycles pervasive but left their effect on quality untested. The Python FAQ calls some circular imports fine. El Emam, Melo and Machado 2001 found export coupling (fan-in) the strongest fault predictor, while Zimmermann and Nagappan found outgoing dependencies stronger. Palomba et al. 2018 found removing smells did not change fault-proneness, and an Android developer in Palomba et al. 2015 defended direct cross-class access for performance.

## Spine — candidate rules in source order

1. **A change made for one requirement edits the module that owns the requirement and does not force matching edits in modules that serve unrelated concerns** — When a diff implements one requirement, such as a new case of a business rule or a changed record format, its edits concentrate in the module that owns that requirement. Small matching edits in several modules that serve unrelated concerns show that knowledge of the requirement has spread into modules that should not depend on it. That knowledge belongs in one owner the others call, or in a third module for the shared concern. ISO/IEC 25010 defines modularity as the degree to which a change to one component has minimal impact on other components. Groups of files that change together without a structural dependency (modularity violations) were more error-prone and change-prone across 19 large projects. In two industrial projects, logical (co-change) dependencies explained most of the variance in fault proneness. The evidence is associational, so the footprint is a reason to look. A deliberate cross-cutting change, such as a rename, a mechanical migration or a dependency upgrade, is not this defect.

4. **A method does not call through an object it obtained from another object's accessor to reach that object's collaborators, unless the chain runs through a builder, a collection, a value transformation or a plain data record** — A method calls its own object, its parameters, the objects it creates and the objects held in its fields. It does not take a collaborator's collaborator from an accessor and call methods on it (b.getC().doIt(), order.customer.address.update(...)), because that ties it to the internal structure of objects it does not own. The check counts only accessor hops into other objects. A chain of builder or fluent calls, same-kind transformations (withFoo, string, iterator and stream pipelines), collection elements or plain data records is outside the rule, and a value one step away may still be returned or passed on as an argument. The remedy is to ask the immediate collaborator for the result, not to add a forwarding method per hop. The Java check reports one accessor step beyond a trusted value and warns that it is prone to many false positives. In 395 releases of 30 Java projects, classes with chains of more than three calls were particularly fault-prone. But the smell was rare (13% of releases), and across the smells studied, classes were not substantially less fault-prone in the periods when they were free of the smell.

8. **An added import does not close a cycle in the dependency graph of modules or packages, whether directly or through other modules** — No module reaches itself again through its imports, whether the cycle is direct (A imports B and B imports A) or runs through other modules. Python, JavaScript and TypeScript modules, Java packages within one module and Rust modules within a crate accept cycles, so there the rule is kept by design and by linters. Where the runtime accepts a cycle it can still fail: a symbol can be unexpectedly undefined in JavaScript, and a top-level 'from module import name' fails in Python. Evidence across 19 large projects, six applications and two 20,000-file systems ties cycles to defects. Files in cyclic cliques or package cycles were more error-prone and change-prone. Most defects concentrated in components in or depending on a cycle. Files in a large cyclic core were 26% of the components but carried 62% of defect-related activity. Break a cycle by moving the shared code into a module both depend on, by merging modules that cannot stand apart, or by inverting one edge with an interface on the depending side. An interface added only to break a cycle often signals misdrawn package boundaries. Linters leave type-only imports out of the cycle because they have no run-time effect, though Google's Python guide calls a typing-induced cycle a code smell.

The interface is added when a real use exists, not ahead of one and not on the implementer's side for mocking. Go and TypeScript satisfy a consumer-declared interface structurally, and Python does so through typing.Protocol, so the implementer imports nothing. In Java and Rust the implementer names the consumer's interface or trait, and that import is the inverted dependency.
