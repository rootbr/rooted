# Pending evidence — rules held back for lack of an openable source

A rule listed here has no card and no id. It ships when an admissible source — academic research with an arXiv id or DOI, a technical standard by section, or verified hands-on experience in an openable form — is found to state the claim as the rule words it. Each entry keeps the rule's original wording, its domain, the unopenable source the origin checklist gave, and what was searched, so the next search starts where the last one stopped.

Entry shape: `domain · origin section · original wording · unopenable source · searched · what would unblock`.

## concurrency

- concurrency · §5.1 Thread-safety documentation · "Is the class annotated or documented as `@ThreadSafe`, `@NotThreadSafe`, or `@Immutable`? Are fields annotated with `@GuardedBy("lock")`?" · the annotations and the practice come from Goetz et al., *Java Concurrency in Practice* (the `net.jcip.annotations` package) · searched: Error Prone `GuardedBy` and `Immutable` bug-pattern pages (fetched) — they check code that already carries the annotations and do not state that shared classes must carry them; SpotBugs `IS2_INCONSISTENT_SYNC` (fetched) treats `@NotThreadSafe` as an opt-out; JDK 21 Javadoc has no such annotations; SonarSource index not reachable · what would unblock: a standard or tool rule that requires the annotation on a shared class, or a fixture test under `evals/fixture/` showing a reviewer outcome that depends on the annotation; the checkable half — every access to a `@GuardedBy` field holds the named lock — could be carded on the Error Prone `GuardedBy` page alone if the orchestrator accepts a rule that fires only on annotated code
- concurrency · §5.6 Spring / CGLIB / AOP proxy boundaries · "A `synchronized` method on a Spring-proxied bean serializes on the *proxy instance*, not the proxied target — and when the same bean calls itself (`this.method()`) the call bypasses the proxy entirely. Two threads can enter the 'same' `synchronized` method holding different monitors, or zero monitors. Rewrite as a `synchronized` block on a `private final Object lock` inside the method, use a `ReentrantLock` field, or inject a self-reference through the proxy." · cited: Spring Framework Reference "Understanding AOP Proxies"; JDK `java.lang.reflect.Proxy` Javadoc · searched: `core/aop/proxying.adoc` (fetched) — it states that "self invocation via an explicit or implicit `this` reference will bypass the advice" and says nothing about monitors; a JDK or CGLIB proxy delegates to the target instance, whose `synchronized` method locks the target's own monitor on both the proxied and the self-invoked path, so the claim as worded is not confirmed by its source and looks wrong; the real hazard near it (`@Transactional` + `synchronized`: the commit happens in the proxy after the monitor is released) is a different rule with no source located · what would unblock: a fixture test under `evals/fixture/` showing two threads holding different monitors through a Spring proxy, or a rewrite of the rule to the transaction-commit-outside-the-lock claim with a Spring reference section that states it
- concurrency · §5.7 No per-request `ExecutorService` · "An executor constructed per request leaks threads if shutdown is missed, loses back-pressure (each request has its own unbounded queue), and pays thread-creation cost on every request. Use a shared, named, bounded pool with a documented owner — or a virtual-thread executor (JDK 21+) where per-request lifetime is acceptable." · Goetz et al., *Java Concurrency in Practice* §6.2.2 · searched: `ExecutorService`, `ThreadPoolExecutor`, `Executors` Javadoc at `jdk-21-ga` (fetched) — they state that pools bound resources and that an unused executor should be shut down, not that a per-request executor is a defect; the missed-shutdown half is the executor-shutdown card · what would unblock: a JMH benchmark or a fixture test showing thread growth or the lost bound, or a SonarSource/SEI CERT rule stating the pattern
- concurrency · §5.7 Background task cannot outlive the resources it captures · "A task submitted to a long-lived pool that references a request-scoped object, a closed connection, or a GC-rooted cache keeps those objects live. Capture-by-value (copy the fields you need) or pass a short-lived cancellation token the owner can trip on teardown." · Goetz et al., *Java Concurrency in Practice* §6.2 · searched: `ThreadPoolExecutor` and `ExecutorService` Javadoc (fetched) — nothing on captured references; no jcstress sample; SEI CERT index unreachable · what would unblock: a fixture test showing retention through a queued task, or a rule page; the concept borders reliability's resource-leak ownership and may belong there
- concurrency · §5.8 Exceptions never leave shared state half-updated · "An exception from inside a `synchronized` block, a try-with-resources lock region, or a `CompletableFuture` stage releases the lock but does *not* roll back partial writes. For every multi-field mutation under a lock, the catch/finally path must either complete the invariant or restore the pre-mutation state (snapshot-and-swap, try/commit/rollback, or `AtomicReference.updateAndGet` with an idempotent updater)." · Goetz et al., *Java Concurrency in Practice* §10.1.4 (which is "Open Calls" — the section does not state this rule); Eric Lippert's exception-safety essay (a blog) · searched: JLS §14.19 (unfetched; states the lock is released on abrupt completion, not the rule); `AtomicReference#updateAndGet` Javadoc (fetched; says the function may be re-applied, not that a throwing function leaves the value unchanged, though the implementation does); SEI CERT rule list from memory — no matching rule · what would unblock: a SEI CERT or SonarSource rule on exception safety of lock regions, or a fixture test; the same-region half is the multiple-field-update card
- concurrency · §5.9 Cancellation mechanism is consistent across the call graph · "If the top of the call tree uses `Future.cancel`, the middle uses a volatile `AtomicBoolean` flag, and the bottom uses `Thread.interrupted()`, cancellation signals are dropped at each translation boundary. Pick one mechanism per scope (or use `StructuredTaskScope.shutdown()`) and verify it flows end-to-end." · Goetz et al., *Java Concurrency in Practice* §7.1 "Task Cancellation"; JEP 505 / JEP 525 `StructuredTaskScope` (the JEPs describe the scope API, not the consistency rule; openjdk.org unreachable) · searched: `Future#cancel`, `Thread#interrupt` Javadoc (fetched) — they define the interrupt path, which the cancellation card covers; no source states the mixed-mechanism defect · what would unblock: a fixture test showing a dropped signal at a flag/interrupt boundary, or a JEP section stating that a scope's shutdown relies on interruption end-to-end

- concurrency · §5.14 "No alien method invoked while a lock is held" · "A synchronized block (or held Lock) must not call: a listener, an observer, a Consumer/Runnable/lambda passed from outside, an overridable method on this, or any method on a parameter whose concrete type is not under this module's control. Every production AB-BA deadlock in Java traces back to a callback invoked under a lock, re-entering the lock graph in a different order. Snapshot the state, release the lock, then invoke the alien method." · JCIP §10.1.3 "Open Calls"; Goetz, "Java theory and practice: Safe construction techniques" (IBM developerWorks, 2004) · searched: SEI CERT Java LCK rules as the index relays them (LCK09-J covers operations that can block under a lock — the blocking subset only; no open-call rule); SpotBugs `messages.xml` at `master` (no callback-under-lock detector; `SWL_SLEEP_WITH_LOCK_HELD` and `TLW_TWO_LOCK_WAIT` are the nearest); Error Prone bug-pattern index; SonarSource rules as recalled (S2276, S3067, S2445, S2274, S2273 — none match); JDK 21 Javadoc of `Object`, `Lock`, `ReentrantLock` · unblock: an academic study that states the callback-under-lock deadlock pattern (candidate: Williams, Thies, Ernst, "Static Deadlock Detection for Java Libraries", ECOOP 2005, DOI 10.1007/11531142_26 — not fetched, statement unconfirmed), or a fixture test under `evals/fixture/` that reproduces the AB-BA deadlock through a listener invoked under a lock. Note: the blocking subset is CC-03's; the "every production deadlock" claim is unsourced and would not be carried
- concurrency · §5.11 "Lazy removal visible to readers?" · "A logically-removed node must still be traversable by concurrent reads until the GC reclaims it; code must never NPE on `null` out a field of a logically-removed node." · Herlihy & Shavit, *The Art of Multiprocessor Programming* §9.7 (lazy linked list) · searched: `ConcurrentSkipListMap` source at `jdk-21-ga` (marker-node deletion is an implementation note, not a rule); `java.util.concurrent` package Javadoc · unblock: Heller, Herlihy, Luchangco, Moir, Scherer, Shavit, "A Lazy Concurrent List-Based Set Algorithm", OPODIS 2005, DOI 10.1007/11795490_3 — openable; fetch and confirm it states that a marked (logically deleted) node stays reachable for concurrent traversal
- concurrency · §4.5 Livelocks / Q58 · "threads keep responding to each other without making progress ... Both threads may release and retry in lockstep forever. FIX: Add randomized backoff" / "For contended spin/try-locks: is there randomized exponential backoff to avoid lockstep retry storms? Applies to custom CAS loops, not to ReentrantLock (which parks)." · Herlihy & Shavit §7.4; JCIP §10.3.3 (as the checklist frames it) · searched: `Lock#tryLock` Javadoc at `jdk-21-ga` (usage idiom only, no backoff); `Thread#onSpinWait` / JEP 285 (a spin hint, not backoff); the jcstress samples index (`primitives/mutex` not fetched); SpotBugs `messages.xml` · unblock: Anderson, "The Performance of Spin Lock Alternatives for Shared-Memory Multiprocessors", IEEE TPDS 1(1), 1990, DOI 10.1109/71.80120 — openable; confirm it states randomized/exponential backoff as the remedy for lockstep retry; or a fixture test showing the tryLock/unlock livelock and its backoff fix
- concurrency · §5.15 "Monitor / ReentrantLock nesting is deliberate" · "Mixing synchronized blocks with ReentrantLock regions around the same state risks ordering and reentrance bugs — the two primitives cannot be acquired in one atomic step, and a single thread can accidentally hold both. Pick one per code path." · Doug Lea, *Concurrent Programming in Java* §2.2.3; JCIP §13.1 · searched: SEI CERT LCK03-J (synchronizing on the intrinsic lock of a `Lock` object — a different rule); SpotBugs `JLM_JSR166_UTILCONCURRENT_MONITORENTER` (synchronizing on a `java.util.concurrent` instance — different); `ReentrantLock` Javadoc at `jdk-21-ga` · unblock: an openable statement that two lock kinds guarding one state cannot be acquired together atomically and so interleave, or a fixture test demonstrating the reentrance bug
- concurrency · §5.15 "Fairness is an explicit constructor argument, not a default" · "For every `new ReentrantLock(...)`, `new ReentrantReadWriteLock(...)`, and `new Semaphore(...)`, the PR must show the fairness argument — even if that is `false`. Accepting the default without comment hides a latency/throughput trade-off from review." · `ReentrantLock(boolean fair)` Javadoc (states the trade-off, not the convention); JCIP §13.3 (trade book) · searched: `ReentrantLock`, `ReentrantReadWriteLock` and `Semaphore` class Javadoc, Java SE 21 (fetched) — they state the indefinite postponement in non-fair mode, the throughput cost of fair mode and that semaphores controlling resource access should be initialized fair, and nothing about passing the boolean explicitly; the two documented cases are carded as CC-37 · what would unblock: a SonarSource, SEI CERT or Error Prone rule requiring the explicit fairness argument, or a fixture test under `evals/fixture/` showing a reviewer outcome that depends on the boolean being visible in the diff

- performance · §4 "Loop optimizations" · "Non-counted loops (while with complex conditions, iterators): no unrolling, safepoints on every back-edge.
