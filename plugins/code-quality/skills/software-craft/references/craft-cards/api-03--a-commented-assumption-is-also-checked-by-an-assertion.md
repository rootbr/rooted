# An internal assumption that a comment states and later code relies on is also checked by an executable assertion

## Thesis
Where a comment states a condition that the code after it relies on, or that the routine guarantees to its callers in its result, and only a defect in this code or in a dependency it trusts can make that condition false, the code also checks the condition with an executable assertion at the point where the condition must hold: an assertion statement or macro, or an explicit test that fails there, by throwing, panicking or returning an error, when the condition is false. A violation is then detected at run time where the check stands, in testing and other dynamic analysis at least. A condition that can be false in normal operation is handled as an error, not asserted.

## Rationale
An assertion is an executable predicate placed in the program that allows run-time checks, in effect a comment that is compiled. Embedded assertions can detect software faults automatically at run time, during debugging, testing and maintenance and even in production versions, and they make testing, fuzzing and other dynamic analysis more effective, because they increase the number of problems, vulnerabilities included, that the analysis can detect. Such checks let programmers flush out more quickly the mismatched interface assumptions and the errors that creep in when code is modified, and contracts (preconditions, postconditions, class invariants) written as executable parts of the code help keep the specification consistent with the implementation as the program evolves. Code after the check can then rely on the condition rather than checking for the problem at every step. In two commercial components whose developers used assertions systematically, the assertions found a large percentage of the faults recorded in the bug database. The rule rests on that detection, not on a lower defect density, an effect the studies dispute.

## Example
```java
bad:  // ids is already sorted by load()
      int pos = Collections.binarySearch(ids, key);
good: // ids is already sorted by load()
      assert isSorted(ids) : "ids not sorted";
      int pos = Collections.binarySearch(ids, key);
```

## Limits
The rule is contested, and the kind of condition separates the first two positions. The objection to assertions (the Source entry marked no-assertions) is that programmers use them as a crutch to avoid thinking about error handling and reporting, and that proper error handling keeps a server running after a non-fatal error instead of crashing. The documentation of that same language uses a panic to indicate that something impossible has happened, and a style guide for it calls consistency checks on an invariant that terminate the program occasionally necessary, in general only when a failure means the internal state has become unrecoverable, and says libraries should prefer returning an error to aborting the program (entries marked assert). The rule therefore covers only a condition that a defect in this code or in a dependency it trusts can make false, the class an assertion is for; a condition that fails in normal operation, such as a parser given malformed data or a request refused for a rate limit, is an expected failure handled as an error, and where a language has no assertion statement the check is an explicit test. The third position (marked no-defect-effect) disputes an effect on defect density: one study found fault density falling as assertion density rose in two commercial components, while a study of popular open-source projects, repeated after fixing a flaw in its setup, found that assertions in a method had a small but significant effect on increasing defects and concluded that there is no evidence that non-test assertions affect defects; the rule claims no such effect and rests on fault detection. A caller's violation of a routine's contract, such as an invalid argument, is checked as that routine's precondition under its own rule. A check too costly for production may use an assertion the build removes: assertions are normally compiled in at development time and compiled out later so that they do not degrade performance, in many cases they should not be enabled in production builds, for instance because a library should not crash its callers, and running at least some testing or fuzzing with them enabled is suggested. Where a check may fail in real life, an always-enabled check is used instead of an assertion; which of the two forms a check takes, and what it does when it fails, are judged by their own rules, as is an invariant of state shared between threads. Where a type makes the condition hold, such as a non-optional type in place of an optional one, the compiler has already ensured a valid value and no run-time check is needed.

## Validator
Grep the added lines for a comment that states a condition as fact: a value assumed, never or always so, non-null, in range or sorted; something already checked, validated or normalized, true by construction or at this point; a guarantee, an invariant, a precondition or a postcondition; a branch or state that cannot happen, is impossible or is unreachable. For each hit, read the enclosing routine in the file and name the condition and the code that relies on it: a dereference, an index, a search that needs sorted input or a branch that omits a case after the comment, or a value the routine returns as guaranteed. Classify what could make the condition false: a defect in this code or a dependency it trusts (a value this code established, a state an earlier step of the same routine or type set up, a result its own logic guarantees), normal operation (user input, a file, a network reply, a lookup that can miss, the environment), or a caller's argument at a routine's entry; only the first class falls under the rule, and a condition on state shared between threads is outside it. Then look in the enclosing routine, before the code that relies on the condition, and at the declaration of the value the condition tests, for an executable check of the same condition that fails when the condition is false: an assertion statement or macro, a library check call that throws or aborts, an explicit test that throws, panics, aborts or returns an error, or a type that makes the condition hold; a call that only logs a failed condition and continues is no check. Validator question: **Does an added comment state a condition that later code in the hunk, or the routine's callers through its result, rely on and that only a defect in this code or a dependency it trusts can make false, with no assertion or explicit check before that code in the enclosing routine and no type at the value's declaration enforcing it?** Yes → flag.
