# Code that handles each element of a collection whose size grows with the input does not send one statement per element to a client-server database where one batched, joined or eager-loading statement would fetch or write the same data

## Thesis
A loop over a collection whose size grows with the input, running against a client-server database, loads the related data it reads before the loop with a joined, IN-list, batched or eager-loading fetch, and writes its rows with a bulk method, so that loading one association for N records takes one or two statements, or one statement per batch of keys where the IN list is split, against N + 1 for the per-element loop.

## Rationale
In a client-server database each statement is a message round trip from the application to the database server and back, and doing over 200 such round trips in sequence can be a serious performance drag. A loop that loads a related record or collection for each of N parent records issues N + 1 statements: one for the parents, then one for each parent. For 10 records that is 11 statements; specifying the association in advance brings it to 2, the second one an IN-list query over the 10 keys. The number of statements grows with the collection, so it may mushroom in fencepost cases. Lazy loading hides the statement: as the application iterates a result set and reads a lazily loaded attribute or collection on each member, an additional SELECT is emitted for each member, with no query call on the line that triggers it. The problem is not a bug or limitation of an object mapper: it affects typical hand-written data-access code behind data-access objects as well, where the fix is to collect the key data needed for the query for all items and issue one query with an IN clause. Writes are covered the same way: bulk create and bulk update methods reduce the number of SQL statements, and on a platform that enforces governor limits, database operations within a loop can cause limit exceptions, so the data is batched into a list and the operation invoked once outside the loop.

## Example
```python
bad:  for order in orders:
          customer = session.get(Customer, order.customer_id)
          print(customer.name)
good: ids = {order.customer_id for order in orders}
      customers = {c.id: c for c in session.scalars(
          select(Customer).where(Customer.id.in_(ids)))}
      for order in orders:
          print(customers[order.customer_id].name)
```

## Limits
The rule is contested for engines that run in the application's own process. The separating condition is whether each statement, written by hand or emitted by a mapper, is a message round trip to a database server such as MySQL, PostgreSQL or SQL Server, or a function call into an engine such as SQLite that runs in the same process address space as the application. For the in-process engine its documentation states that queries involve no message round trips, only a function call, that using a large number of queries is not the problem, and that an application issuing additional queries for each timeline element is not harmed by the pattern, which keeps the code that creates the list query separate from the code that prepares each entry for display. The batched fix specifies all the data the unit of work will need at its start and fetches it in one or two queries, which needs that data known ahead of time; a loop whose next statement takes its parameters from the previous statement's result offers no key set to collect first and lies outside the rule. Eager loading of an association the loop never reads is flagged in turn: a query detector reports eager loading that is not necessary. The fix may be an outer join or a second statement that fetches the related rows for a batch of primary keys; the choice trades the number of SQL executions against the complexity of the SQL emitted and the amount of data fetched. Some databases cap the size of an IN expression, so an IN-list fetch over a large key set is split into batches: one eager loader emits a SELECT for up to 500 parent primary keys at a time, and with batch fetching the number of batches depends on the configured batch size. A lazily loaded association that the mapping or session is configured to fetch in batches of keys, or for every instance of the result on first access, is loaded with one statement per batch and meets the rule without a fetch written before the loop. Each optimization is profiled after the change to confirm it is a benefit, and a big enough benefit given the decrease in readability, since in a given circumstance the general principle might not apply, or might even be reversed; bulk write methods carry several caveats of their own, so the replacement is checked against the use case. A loop over a collection whose size does not grow with the input, and per-element calls to remote services other than a database, lie outside this rule.

## Validator
Grep the hunk for a query or execute call, an SQL string literal, an object-mapper finder, a session get, add, execute or scalars call, or an object-mapper create, persist or merge call, and for each match check whether it sits inside a loop, a comprehension or a per-element callback over a collection. Open the file at every loop that iterates a query result and read each attribute access in its body: an access to a related record or collection that neither the originating query nor the fetch configuration of the mapping or session loads eagerly, in batches of keys or for every instance of the result emits one statement per element with no query word on the line; trace that configuration, since a loader strategy set on the mapping, a configured batch fetch size or a fetch mode that bulk-fetches a missing field for every instance of the result sends one statement per batch, not one per element. Trace the collection to its source and confirm its size grows with the input, as a query result, a request payload or a file does. Trace the connection or engine configuration and confirm the database is a server reached over a connection, not an engine running in the application's process. Check whether each iteration's statement takes its parameters from the previous statement's result; if it does, no batch can be formed. For writes, check that the loop sends one insert, update or delete per element where the data layer offers a bulk method. Validator question: **Does a loop over a collection whose size grows with the input send one statement per element to a client-server database, fetching or writing data that one batched, IN-list, joined or eager-loading statement or one bulk write outside the loop would cover?** Yes → flag.
