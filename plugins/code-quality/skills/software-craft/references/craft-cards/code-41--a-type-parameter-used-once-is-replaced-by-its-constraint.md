# A type parameter that is the type of a single parameter and appears nowhere else in the signature is replaced by its constraint wherever the constraint can serve as that parameter's type

## Thesis
A type parameter that the routine itself binds, and not an enclosing generic class or type, that is the whole declared type of exactly one parameter of the routine's signature, and appears nowhere else in that signature (in no other parameter, in no constraint of any type parameter including its own, in no declared result and in no result inferred from the body), is dropped, and that parameter is declared with the type parameter's constraint itself, or, when the type parameter is unconstrained, with the top type that stays type-checked where the language has one that takes a value of any type directly; where the closest candidate is a dynamically dispatched object that not every type implements, the unconstrained type parameter stays. Uses of the type parameter inside the routine body do not count, except a use that makes a value or a type of it at run time (a variable declared with it and left at its zero value, an allocation of it, a type read from it by reflection) where the type argument is substituted across the entire routine; such a use keeps the type parameter. The rule holds where the constraint is an ordinary type that a parameter can be declared with, without changing how calls on the value are dispatched; it does not reach a type parameter whose calls the language specializes to static, direct calls and whose bound would become a dynamically dispatched object if used as the parameter's type.

## Rationale
A type parameter exists to relate the types of several values: one argument to another, or an argument to the result. One that is used only once in the signature relates nothing. The count includes a result type inferred from the body: a type parameter written once but carried into the inferred result relates the argument to the result and is used twice. A use inside the body that only annotates or converts a value does not count, because replacing every such use with the constraint achieves the same result. Where the type argument is substituted across the entire routine, a variable declared with the type parameter and left at its zero value, or allocated, holds a value of the type argument, while declared with an interface constraint it holds a nil interface, so a body that makes a value or a type of the type parameter keeps it. A type parameter that relates nothing makes the routine harder to read and reason about, and a caller that writes type arguments explicitly has to supply one more for no reason; too many type parameters, like constraints where none is needed, can also make type-argument inference less successful. Where all the routine does with the value is call methods the constraint declares, declaring the parameter with the constraint makes the routine easier to write and easier to read, and the execution time will likely be the same. The checkers that flag a type parameter used only once name the constraint itself as the replacement; for an unconstrained one, two of them name a checked top type, and the unchecked top type is documented as disabling many type-checking rules.

## Example
```typescript
bad:  function describe<T extends Shape>(item: T): string { ... }
      const log = <T>(value: T): void => { ... }
good: function describe(item: Shape): string { ... }
      const log = (value: unknown): void => { ... }
```

## Limits
The case turns on whether the constraint can be the parameter's own type without changing how calls on the value are dispatched. Where a bound used as a type is an ordinary interface type, dropping a type parameter through which the routine only calls methods leaves it easier to write and read with likely the same execution time, and the checkers name the constraint as the replacement. Where the language specializes each use of a bounded type parameter to static, direct calls that the compiler can inline, and a bound used as a type becomes a dynamically dispatched object whose method lookup incurs a runtime cost that static dispatch does not and that prevents inlining, the once-used bounded type parameter is the documented and recommended form, equivalent to the shorthand for an argument that implements a bound, and the rule does not apply. A constraint that is not an ordinary type keeps its type parameter: an interface whose type set is not defined entirely by a list of methods, such as a union of permitted types, may only be used as a constraint and cannot be the type of a value, and a value-constrained type variable is exempted by a checker that otherwise flags a single use. A type parameter nested inside a parameter's type is outside the rule; for a type argument of another generic type, one checker counts the use as relating that type's several members together and another exempts it as a position with legitimate single uses, though the first still reports a read-only sequence or a tuple of it. Where the checker rejects excess properties in an object literal passed to a specific declared type but not to an inferred type argument, dropping the type parameter turns those errors on at call sites that pass such literals, and whether to remove the excess properties at the call sites or to let the declared type accept extra properties explicitly is a case-by-case decision. Where the language rejects type arguments on a routine that declares none, dropping the type parameter from a routine that has callers outside the hunk breaks every call that passes the type argument explicitly, and where the language rejects a routine that keeps a type parameter the routine it overrides or implements does not declare, dropping it from a routine that others override or implement breaks every such override; the finding on a routine the hunk does not add whole names that consequence. A type parameter whose only purpose is to let callers pass a type argument explicitly to test a type stays, and files that test types disable the check. Where the closest candidate for a top type is a dynamically dispatched object of a dynamic-typing trait, which a type containing a non-static reference does not implement, an unconstrained type parameter has no type-checked top type to give way to, and it stays. A project tolerance rejects the finding: one checker reports a single use as a warning by default and as an error only in its strict mode, another ships the check in its strict configuration, so a project that has turned the check off for a path or for the whole code base states that tolerance.

## Validator
Grep the added lines of the hunk for a routine signature that declares type parameters or annotates a parameter with a type variable declared outside the routine that no enclosing generic class or type binds. For each declared type parameter, count its occurrences in the signature: in every parameter's type, in the constraints of every type parameter, its own included, so that a self-referential bound counts as a second occurrence, and in the declared result; where the result is not declared, read the routine's return expressions in the hunk and count one more occurrence if the inferred result carries the type parameter. Ignore uses inside the body, except a use that makes a value or a type of the type parameter at run time (a variable declared with it and left at its zero value, an allocation of it, a type read from it by reflection) where the type argument is substituted across the entire routine; skip the type parameter when the body has such a use. Keep a type parameter that occurs exactly once, as the whole declared type of one parameter. Skip it when an enclosing generic class or type binds it, since it then relates that type's members, when it occurs only nested inside a larger type, when its constraint is usable only as a constraint and cannot be the type of a value, when it is a value-constrained type variable that must equal exactly one of several listed types (a bound that is itself a union a parameter can be declared with does not skip it), when the language specializes calls through the type parameter to static, direct calls and its bound would become a dynamically dispatched object if used as the parameter's type, when it is unconstrained and the language's closest candidate for a top type is a dynamically dispatched object that not every type implements, when callers pass its type argument explicitly to test a type, when the file is a type test, and when the hunk marks the routine as overriding or implementing an inherited declaration that carries the same type parameter. Validator question: **Does an added routine signature declare a type parameter that is the whole type of exactly one parameter, appears nowhere else in the signature or its inferred result, is not used in the body to make a value or a type of it at run time, and has a constraint, or for an unconstrained one a type-checked top type, that the parameter could be declared with directly without changing how calls on it are dispatched?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-41`, severity minor, `file`, `symbol`, `code` = the added signature line that declares the type parameter, verbatim from the diff, `fix` = the same signature without that type parameter and with the parameter declared with its constraint, or with the checked top type when it is unconstrained, in the file's language, `rationale` = that the type parameter appears once in the signature and relates no two types, and the constraint type the parameter takes instead, and, for a routine the hunk does not add whole, the explicit type arguments or overrides outside the hunk that the fix breaks).
