# Computed binary floating-point values are compared within a tolerance suited to their magnitude, never with == or !=, and the tolerance is absolute only where the domain gives a natural margin or the expected value is zero

## Thesis
Where at least one of two binary floating-point values is the result of arithmetic, the code tests them for equality by checking that their difference lies within an allowed error, rather than with an equality or inequality operator or an equivalent pair of ordering tests. The allowed error is relative to the larger magnitude of the two values when the range of the values is not known; it may be an absolute margin when the values lie in a known range with a natural threshold for close enough, such as the precision of the input; and it includes an explicit absolute margin when the expected value is zero. The allowed error is at least the spacing between adjacent floating-point values at the magnitude compared, larger than it when the comparison is strict, and machine epsilon, which is that spacing at 1, is not used as a fixed margin.

## Rationale
Most decimal fractions cannot be represented exactly as binary fractions, so a literal such as 0.1 is stored as the nearest binary fraction, and every floating-point operation can suffer a new rounding error, for a double on most machines of no more than about one part in 2^53. Because rounding takes place at each step, floating-point arithmetic is not associative, and two mathematically equivalent computations, or a calculation and a constant for the same logical result, can yield values that differ by a tiny margin: in double precision, summing three values of 0.1 does not give exactly 0.3, 0.1 + 0.2 does not give exactly 0.3, and 1000.1 + 0.2 yields 1000.3000000000001. Rounding the operands before the arithmetic cannot help, since 0.1 cannot get any closer to 1/10. An exact comparison therefore treats semantically equal values as different, and the errors accumulate as values are added onto a running total: ten additions of 0.1 do not equal 1.0. The absolute accuracy of a floating-point value decreases as the value gets larger, because the exponent grows while the precision of the significand stays the same, so the tolerance a comparison needs grows with the values: for 1000.1 + 1000.2 compared with 2000.3, a margin of 2000 times machine epsilon (2^-52, about 2.2e-16, for a double) gives enough tolerance where machine epsilon alone does not, and the next double after 3.141592653589793 is 4.44e-16 away, so a tolerance of 1e-20 there checks exact equality. One fixed tolerance used across values of different magnitude becomes a misleading equality check at the larger ones, and fails the other way at small magnitudes: about 1e-9 may suit values on the order of one and is far too large for values on the order of 1e-9 or smaller, so no default absolute tolerance is appropriate for the general case. A relative tolerance scales with the values: it needs to be greater than about 1e-16, the precision of a double; 1e-9 keeps the two values the same within about nine decimal digits, about half the precision of a double, and a good numerical algorithm is not expected to lose more than about half of the available digits; a coarser margin, such as 0.1%, fits where the use case accepts it. No value is small relative to zero: a relative test of a nonzero value against zero compares the difference with a fraction of that same value, and with a relative tolerance below one it never passes, so a comparison with an expected zero needs an absolute margin chosen for the use case. Machine epsilon is the difference between 1 and the next larger value, so it equals the spacing of values from 1 to 2, where a strict comparison within it accepts no difference at all, and it is smaller than the spacing at every larger magnitude: for values around 1000 a comparison within it reports logically equal results as different. NaN is close to no value, itself included, and an infinity is close only to itself, so a tolerance test does not cover them. Floating-point arithmetic is more than adequate for most tasks; the comparison is what has to allow for its rounding.

## Example
```go
bad:  sum := 0.0
      for _, w := range weights { sum += w }
      if sum != 1.0 { return errNotNormalized }
      if math.Abs(sum-1.0) > math.SmallestNonzeroFloat64 { return errNotNormalized }
good: const shareTolerance = 1e-9 // shares lie in [0, 1]
      sum := 0.0
      for _, w := range weights { sum += w }
      if math.Abs(sum-1.0) > shareTolerance { return errNotNormalized }
```

## Limits
The rule is contested on the form of the margin, and whether the range of the values is known separates the cases. One form compares the absolute difference against a fixed margin, with .0000001 as its example (the Source entries marked absolute); that form follows the rule where the values lie in a known range with a natural threshold for close enough, such as a length in centimetres compared within 0.1 cm or input entered in steps of 0.1 compared within 0.01, and where the expected value is zero. Where the range is not known, the other form calls for a relative margin and holds that no absolute default fits the general case (the entries marked relative), and a fixed margin used across magnitudes turns into an exact-equality check at the larger ones. Exact comparison follows the rule where no rounding error is to be allowed because the value was not produced by rounding arithmetic, and there it states the intent more clearly than a tolerance: a value stored or copied unchanged and compared with the value it was set from, or read back from an exact representation (an exact integer ratio, a hexadecimal floating-point form, the shortest decimal form that round-trips); an integer of magnitude up to 2^53 − 1 held in a double, which is represented exactly and compares correctly, with integer-level operations on such values precise; and a constant expression that the language evaluates exactly at arbitrary precision before rounding the result once to its type. A test against zero follows the same line: a value that was set to zero or received as zero compares exactly, and one lint in the Source exempts every comparison with zero, while a computed result expected to be zero takes an explicit absolute margin, since a computation may end close to but not equal to zero. A test for NaN uses the language's NaN predicate or, less clearly, compares the value with itself, and a test for an infinity compares exactly. Rounding both final results to a stated number of digits and comparing the rounded values is only a rough approximation: two results one rounding apart can fall on either side of a rounding boundary, so it does not replace an allowed error. An equality method that implements equality for a type holding floating-point fields is outside the check; one lint in the Source exempts routines named for equality. A comparison helper the project context documents, with its margin, is the comparison the finder accepts. Whether a quantity that must be exact, such as money, belongs in binary floating point at all, and the accuracy of a numerical algorithm, are judged by their own rules.

## Validator
Grep the added lines for `==`, `!=`, `===` or `!==` with a decimal or exponent literal on either side, or with an operand that the hunk declares with a floating-point type or initializes from a decimal literal; an equality assertion with such a literal among its arguments; a machine-epsilon constant, a smallest-positive-value constant, or a name containing epsilon, eps, tolerance or tol; a closeness helper (isclose, allclose, almost-equal, approx, close-to, within, in-delta, relative or ulps equality); and an absolute difference compared with a threshold. For each hit, read the hunk and settle the operands' type and origin: a floating-point value produced by arithmetic (a sum, a difference, a product, a quotient, a running total, a math-library call) is computed; a value stored or copied unchanged and compared with the value it was set from, a value read back from an exact representation, an integer-valued double of magnitude up to 2^53 − 1 produced by integer-level operations, and a constant expression the language evaluates exactly are not. Treat a pair of `<` and `>` tests that together mean not-equal as an inequality test. For an exact comparison of a computed value, flag it unless it is a NaN self-test, a test against an infinity, or the body of a type's equality method. For a tolerance comparison, read the margin and the magnitude of the values: a relative margin above the relative spacing of the values' format (about 1e-16 for a double), or an absolute margin no smaller than the spacing at the top of the range the code, a comment or the unit states, follows the rule; flag machine epsilon used as a fixed margin, a fixed absolute margin for values of unstated or varying magnitude, a margin below the spacing of values at the compared magnitude (for a double, on the order of that magnitude times 2.2e-16) or equal to it in a strict comparison, and a relative-only test whose expected value can be zero. Validator question: **Does an added line compare a computed binary floating-point value with an equality or inequality operator or an equivalent pair of ordering tests, or within a margin that is machine epsilon, a fixed absolute margin for values of unknown range, a margin below the spacing of values at their magnitude or equal to it in a strict comparison, or a relative-only margin against an expected zero?** Yes → flag.
