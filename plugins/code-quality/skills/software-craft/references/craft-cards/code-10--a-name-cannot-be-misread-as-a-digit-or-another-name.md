# A name cannot be misread as a digit or as another name in the same scope

## Thesis
Each name a change declares can be read only as itself. A variable, parameter, loop variable, routine or type is named by something other than the lone letter `l`, `O` or `I`. Every two parameters or local names visible together in one routine differ by more than one character: neither is the other with one character replaced (`splunk` and `splonk`, `checked_exp` and `checked_eap`) or with one character inserted anywhere but at the end (`orange` and `ornange`, `rows` and `rrows`). That pair check covers names of three or more characters that are not both exactly three long, and pairs that start with the same letter or with look-alike letters (`l`, `i` and `1`; `u` and `v`); it leaves out a character added at the end (`row` and `rows`), names of equal length that differ only in digits (`page1` and `page2`), a one-letter first or last part set off by an underscore (`pos_x` and `pos_y`), and conventional pairs such as `lhs` and `rhs`, `iter` and `item`, `parsed` and `parser`, `args` and `arms`, with the names that begin or end with them. No two identifiers in one file, one of them holding a non-ASCII character, render alike while differing in their Unicode code points (`total` spelled with a Latin a and with a Cyrillic a).

## Rationale
In some fonts `l` and `I` cannot be told from the numeral one, nor `O` from zero, so a lone `l` in `l + 1` reads as a constant; not every screen or printer draws every character distinctly. Readers also confuse similarly spelled and slightly misspelled words: two names one character apart are hard to tell apart on the page, so the reader follows the wrong binding, and a later edit that reaches for one name can land on the other and still compile, now reading or writing the wrong value. A different first letter is usually enough to set two names apart, unless the two letters are themselves look-alikes. Identifiers built from characters that render alike — code points the Unicode confusables data maps to one skeleton, such as a Latin and a Cyrillic a — can render identically on the page, so the reader cannot tell which binding a use refers to, and look-alike identifiers are a known means of hiding code from a reviewer. A name that resembles no digit and no neighbour restores the one-to-one match between what the reader sees and the binding the compiler resolves.

## Example
```rust
bad:  let l = rows.len();
      let row_recs = load_records(&rows);
      let row_reps = load_reports(&rows);
good: let row_count = rows.len();
      let records = load_records(&rows);
      let reports = load_reports(&rows);
```

## Limits
The checks reach the names the change declares. A keyword argument that passes a value to an existing parameter named `l` (`f(l=12)`) declares nothing: the finding, if any, belongs where that parameter is declared, and the same holds for a name an overridden signature, an external schema or a code generator fixes. A generic type parameter, which languages conventionally name with one capital letter, is outside the letter check, whose sources name variables, parameters, routines and classes. The pair check compares parameters and local names within one routine; fields, routine names and names in different routines are outside it. A non-ASCII identifier is not by itself a defect — the language may admit identifiers in any script — only a pair that renders alike is; a project that restricts identifiers to ASCII enforces that through its own compiler or linter configuration. A look-alike declared in another file of the module is outside what the card reads; a compiler or linter check that compares the identifiers of a whole compilation unit reaches it, where the toolchain has one. A tolerance stated in `project_context` for generated code, or for names that mirror an external schema, rejects the finding.

## Validator
No added-line pattern marks two names one character apart, so the card carries no trigger and reads every hunk. Grep the added lines for `l`, `O` or `I` standing alone as a declared name — before an assignment, a colon, a comma, a semicolon, a parenthesis, a brace or bar, an arrow (`->`, `=>`), `in` or `of`, a type written after the name, or the end of the line — and for a non-ASCII character inside or next to an identifier; drop matches inside string literals and comments, keyword arguments that pass a value to an existing parameter, and generic type parameters. Open the file; for each routine in which the hunk declares a name, list its parameters and local names and compare each new name with every other name visible there, applying the three-character floor, the first-letter condition and the exempt pairs. For a new identifier holding a non-ASCII character, compare how it renders with every identifier in the same file, and when the file already holds an identifier with a non-ASCII character, compare each new identifier with that one. Validator question: **does a name the change declares stand alone as `l`, `O` or `I`, sit one replaced character, or one character inserted anywhere but at the end, away from another name visible in the same routine outside the exempt pairs, or render like another identifier in the same file while using different code points, one of the two holding a non-ASCII character?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-10`, severity minor, `file`, `symbol`, `code` = the declaration of the misreadable name quoted verbatim from the diff, `fix` = that declaration and its uses renamed to a word or phrase that resembles no digit and no other name in scope, in the file's language, `rationale` = naming the digit or the other identifier the name can be read as).
