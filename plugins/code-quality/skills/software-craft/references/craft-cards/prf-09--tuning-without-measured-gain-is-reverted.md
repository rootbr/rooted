# Tuning whose measurement shows no gain beyond the variation between runs is reverted to the plainer code, unless the tuned form is itself simpler

## Thesis
A tuning change that adds complexity and is measured by a repeatable benchmark against the version before it stays only when that benchmark shows a gain whose error bars clear zero, or a gain the comparison tool marks as significant; otherwise the change is reverted to the plainer code it replaced. An older optimization is held to the same bar when re-measured after the optimizer or the platform has changed, and one that no longer shows a gain is dropped. A change that removes complexity, such as deleting an unused calculation or a dead flag, may stay without a measured gain.

## Rationale
Clear, idiomatic code is easier to read and debug and, in the long run, easier for the compiler to optimize, so a change that adds complexity carries a long-term cost, and its results are checked to merit that cost; the error bars of a very weakly positive result can overlap zero. Where a comparison tool marks significance, a row with no mark supports no conclusion about the improvement. One mark means a difference that large turns up by chance in fewer than 5% of comparisons between versions that perform the same, so among 20 benchmarks one is expected to show a mark it should not; two marks lower that rate to 1% and three to 0.1%, though that may require more runs. The bar is chosen before the data is seen, since a methodology picked afterwards is easily the one that tells the best story. Tuning without a gain still costs: an unchecked hint that a branch is unreachable gave no benchmarked benefit over the checked form while adding the possibility of undefined behaviour. A lint that suggested a single-character pattern argument for speed was moved out of the performance group, and its documentation records that benchmarks proved inconclusive; it rests the suggestion on the character form being clearer, and leaves out non-ASCII characters, for which the same change is slower on many machines. Optimizations also age: optimization equilibria chosen for older platforms may have changed since; a runtime dispatch to a "fast" routine ended up preferring the slower implementation, and paying for the dispatch, once the compiler emitted the same instruction for the plain built-in; and layers of hand-tuning added over a decade left an extra branch the optimizer missed, which removing the wrapper removed.

## Example
```python
bad:  append = out.append  # timeit: 1.8% faster, within noise
      for row in rows:     # rerun: no significant gain, inconclusive
          append(normalize(row))
good: for row in rows:
          out.append(normalize(row))
```

## Limits
A change from which no improvement is expected is not held to a significant gain: for it, no significance mark is the expected result. A change that removes complexity stays on its own merit, and any efficiency saving is a nice-to-have bonus. A change made because a performance lint suggested it is held to the same comparison: one such lint's documentation asks for one's own measurements rather than reliance on the lint alone. The rule reaches a tuning change and the comparison reported with it; the choice of complexity class or data structure lies outside it, and so do the reserved specialties of low-latency tuning (cache-line layout, lock-free structures, allocation-free hot paths, runtime and garbage-collector tuning) and parallelization under concurrency correctness, where the finder names the specialty and stops.

## Validator
Grep the hunk's added lines, their code comments and any benchmark output added in the diff for a reported comparison: a small percentage beside faster, slower or gain, "within noise", "no significant difference", "inconclusive", or a comparison row with no significance mark or a tilde in place of a delta. Open the hunk and find the change that comparison belongs to. Compare that change with the code it replaces: an alias, a cache, a hand-unrolled loop, an unchecked hint or a special-case fast path adds complexity; deleting an unused calculation or a dead flag removes it. Read the reported comparison: a gain whose spread overlaps zero, a row without a significance mark from a tool that marks significance, or a re-measurement showing that an older optimization no longer gains has shown no gain. Validator question: **Does the hunk keep a tuning change that adds complexity while the comparison reported with it shows no gain beyond the variation between runs or no significant difference?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: PRF-09`, severity minor, `file`, `symbol`, `code` = the tuned lines and the reported measurement, quoted verbatim from the diff, `fix` = the plainer code the tuning replaced, in the file's language, `rationale` = names the reported gain with its spread or missing significance mark, and the complexity the tuning adds).
