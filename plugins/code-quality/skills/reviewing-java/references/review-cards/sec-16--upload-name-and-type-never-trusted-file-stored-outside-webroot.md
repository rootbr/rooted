# An upload's client-supplied filename and content type are never trusted, the stored name is generated, the type is read from content, and the file lands outside the webroot

## Thesis
Code that stores an uploaded file gives it a name the server generates (a UUID plus an allowlisted extension), never `getOriginalFilename()` or `Part.getSubmittedFileName()` as-is; decides the file's type from its content (magic bytes through a detector) and an extension allowlist, never from `getContentType()` alone; and writes it to a directory the web server does not serve, from which a controller streams it with `Content-Disposition: attachment`. Using the original name in `transferTo` or `Files.copy`, gating on the declared type, or saving under the static-resources root is the defect.

## Rationale
The filename and the `Content-Type` of a multipart request are supplied by the client: the name can carry `..`, an absolute path, a null byte, a double extension (`.jpg.php`) or a reserved name, and the type is a header any client sets to `image/png` for a script. A generated name removes every one of those at once; an extension chosen by the server from the detected type keeps the stored name meaningful without trusting the client; a content check catches a file whose bytes are not what the extension says. Inside the webroot an uploaded `.jsp`, `.html` or server configuration file is served or executed by the container; outside it, a file is only bytes a controller returns with a disposition the browser will not render inline. A size limit and a malware scan are operational layers this card does not check.

## Example
```java
bad:  file.transferTo(new File(webRoot + "/uploads/" + file.getOriginalFilename()));
good: String type = tika.detect(file.getInputStream());                  // from content
      String ext = EXT_BY_TYPE.get(type);                                   // allowlist
      if (ext == null) throw new IllegalArgumentException("type not allowed");
      Path target = storageDir.resolve(UUID.randomUUID() + "." + ext);     // outside webroot
      file.transferTo(target);
```

## Limits
Applies to handlers that persist uploads. A handler that reads an upload into memory, parses it as data (CSV, JSON) and stores nothing on disk is out of scope. Keeping the original name in a database column for display, encoded on output, is correct; using it as the path is not. A store that is an object bucket rather than a directory still takes a generated key. A project context naming an upstream gateway that validates uploads rejects the finding.

## Validator
On the triggered hunk find each `getOriginalFilename` or `getSubmittedFileName` use, each `getContentType` comparison, and each `transferTo`, `Files.copy` or write of upload bytes. Open the file: check the stored path's name origin, the type decision's source, and the target directory's relation to served static content. Validator question: **does the client's name or declared type decide where or how the file is stored, or is the file written where the server serves it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: SEC-16`, severity major, `file`, `symbol`, `code` = the store call and the name or type source quoted verbatim from the diff, `fix` = the generated name, content-detected type and non-served directory, `rationale` naming the client-controlled field that decides the outcome).
