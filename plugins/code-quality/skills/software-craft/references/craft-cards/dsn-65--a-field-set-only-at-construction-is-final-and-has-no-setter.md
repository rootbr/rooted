# A field that is set only while its object is constructed is declared final or read-only and has no setter

## Thesis
A field that is assigned only while its object is constructed or initialized — in its declaration, or in a constructor or an initializer block of the type that declares it, the places a no-reassignment form admits an assignment — is declared with the no-reassignment modifier or annotation its language offers for fields, or belongs to a record type declared frozen as a whole, and its type has no setter or other method that assigns it afterwards. A setter that no code calls does not change this: the field's value still never changes once initialization ends. In a language whose fields take no such modifier or annotation, where the function that builds and returns the new instance does the constructing, no method assigns the field after that function returns. The declaration forbids only replacing the field's value; the object the field refers to may still be mutable.

## Rationale
Code that operates on the assumption that a value will never change may not do what it was designed to do when another part of the code changes that value, and the cause of such a bug can be difficult to track down afterwards, especially when that other code changes the value only sometimes. The no-reassignment form turns the assumption into a check: the compiler or the type checker rejects an assignment to the field outside the constructor, and a frozen record type raises an exception on an assignment to its fields, so a reader does not have to keep track of whether some code reassigns the field, and the code is easier to reason through. The mutable form tells future readers the opposite, that other parts of the code will be changing the value. A setter extends that mutability to callers: a mutable property is one that also has a setter, and the guidance for a value the caller should not be able to change is a property with a getter only. For a field private to its type the declaration is safe to add: no code outside the type may modify the field, so when the type itself never does, the field may safely be marked read-only. Immutable data is preferred to mutable, and the declared field is assigned only once, when the instance is created.

## Example
```go
bad:  type Server struct{ addr string }
      func NewServer(addr string) *Server { return &Server{addr: addr} }
      func (s *Server) Addr() string      { return s.addr }
      func (s *Server) SetAddr(a string)  { s.addr = a } // no caller
good: type Server struct{ addr string }
      func NewServer(addr string) *Server { return &Server{addr: addr} }
      func (s *Server) Addr() string      { return s.addr }
```

## Limits
A field that a framework assigns after construction — through dependency injection, a persistence identifier, a serialization binding, a command-line option binding or a test spy — is non-constant even though no line of the source reassigns it, and so is a field marked non-final for testing; an annotation that marks either takes the field out of the rule, and a project context that names such a framework is the tolerance that rejects the finding. A setter that overrides or implements a method of a supertype stays while the supertype declares it, since callers reach it through the supertype, and the field it assigns stays assignable with it. A public member may be modified by code outside its type and a protected one by subclasses; for a type published for use outside the repository those callers are not in the repository to be searched, so the rule reaches such a member only when the design intent states that its value is fixed once the object is constructed. On a field visible outside its type that holds an instance of a mutable type, the declaration half of the rule does not apply: library design guidance, written for a library's API, advises against the read-only modifier on such a field, noting that it keeps the stored instance from being replaced but not the instance's data from being modified, while the same vendor's analyzer asks for the modifier on private fields that are initialized but never reassigned. The setter half still applies there, since the same guidance asks for a getter-only property whenever the caller should not be able to change the value, and notes only that the value of a mutable reference type can still be changed through it. The rule asks only that the field keep its value: whether the object it refers to is itself immutable, and whether that object is copied when it enters or leaves the type, lies outside it.

## Validator
Grep the added lines for a field declared without its language's no-reassignment modifier or annotation (a private or protected field, a class property, a field made private by a prefix on its name), for a data class declared without being frozen, and for an added setter: a set-prefixed method, a property setter, a set-prefixed method on a mutable receiver. Take each such field, each field of such a data class, and the field each added setter assigns. Open the file, then grep the repository for every assignment to the field (plain, compound or increment, through any receiver) and for every call of each setter or method that assigns it. Set aside an assignment in the field's declaration or in a constructor or an initializer block of the type that declares it, and, in a language whose fields take no such modifier or annotation, in the function that builds and returns a new instance; when the field is assigned in one of those places, set aside as well an assignment inside a setter or method that no code in the repository calls. Skip the field when it carries an annotation for a framework that assigns it after construction, or one that marks it non-final for testing, or when the project context names such a framework. Skip a setter or assigning method that overrides or implements a method of a supertype, and the field it assigns: the supertype keeps the method in the type's contract, and its callers may be outside the repository. Skip a public or protected member of a type published for use outside the repository unless the design intent states that its value is fixed once the object is constructed, and skip the declaration, though not the setter, on a field visible outside its type that holds an instance of a mutable type. In a language whose fields take no such modifier or annotation, ask only about setters and other assigning methods. Validator question: **Is a field that is assigned only while its object is constructed, with no other assignment and no call to a setter or method that assigns it anywhere in the repository, declared without the no-reassignment form its language offers, or given a setter or other method that assigns it after construction?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-65`, severity minor, `file`, `symbol`, `code` = the field declaration, the data-class declaration or the setter's signature line, quoted verbatim from the diff, `fix` = the field declared with its language's no-reassignment form, or its record type declared frozen, and the uncalled setter or assigning method removed, with a getter kept where callers read the value, in the file's language, `rationale` = where the field is assigned during construction, the absence of any later assignment or setter call, and the reassignment that the missing modifier or the remaining setter leaves open to code that assumes the value never changes).
