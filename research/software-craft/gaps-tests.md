# Research note — Concepts the tests reviewer found uncovered

Topic `gaps-tests` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: the taxonomy topics of the concepts and their canon locators: property-based-testing (PP 'Property-Based Testing'); test-doubles (SEG13); unit-testing-and-test-quality (CC22, SEG12).

The four concepts the tests reviewer found uncovered all trace to the canon, and each has openable official documentation that states it in a form a diff can check. (1) Comparing semantic content rather than a rendering: Henney (97 Things essay 80) and SEG ch. 12 call assertions on incidental formatting or serialized strings brittle. Google's Go style guide ('Compare stable results') states the rule and limits it to output of 'a package that you do not own'. protobuf-go, Protocol Buffers, Rust Debug, Java Object.toString and Python doctest each document their rendering as unstable, and tsDetect flags Sensitive Equality. Snapshot and approval practice (Jest, insta, Jane Street expect tests, gofmt golden files) compares renderings on purpose. The two sides separate on whether the compared text is output the project owns and the behaviour under test. Spadini ICSME 2018 measured no distinct harm from Sensitive Equality, so the card rests on the documentation and not on a harm study. (2) State over interaction is the contested concept. SEG ch. 12-13, testdouble.js, Fowler and Spadini EMSE 2019 favour state. Zhu et al. FSE 2025 find that mock assertions catch faults state assertions miss, and the mockist school (GOOS, Mock Roles) expects commands. No controlled comparison exists. Both admissible sides state the same condition, though: verify a call only when the effect cannot be observed through a returned value or readable state. That condition is carded, and it is distinct from TST-09 (a verified stubbed call) and TST-10 (over-pinning). (3) A bounded per-commit budget with a separate open-ended search has broad support. Hypothesis ties its default of 100 to a regularly run suite. Plain go test runs only the seed corpus, and -fuzztime defaults to forever. ClusterFuzzLite schedules batch fuzzing and calls running it on each push 'not recommended'. Goldstein ICSE 2024 and Ravi & Coblenz OOPSLA 2025 agree. Defaults range from 100 to 1000 and CIFuzz spends 600 s per PR, so the card names no count. (4) Keeping a known single edge value as an explicit example beside a property rests on proptest's 'Limitations' page (the i64::MIN abs example) and its uniform integer generator. fast-check's 'Trust the framework' note disputes it, and jqwik and Hypothesis document edge-biased generators. The separating condition is whether the generator in use is documented to produce the value in every run. jqwik's default edge-case mixin is; Hypothesis's endpoint upweighting is not, because Hypothesis calls its distribution an internal detail it changes and points to @example for inputs that must always run.

## Formulation layer

The canon covers all four concepts, and three of them also have official documentation that states them in checkable form. (1) Henney's 97 Things essay 80 and SWE at Google ch. 12 call assertions on incidental formatting or on a serialized string brittle. Google's Go style guide ('Compare stable results') states the rule and limits it to output of a package the test does not own. Python doctest, Rust Debug, Java Record.toString and protobuf-go protojson each say in their own docs that their rendering is not stable. Jest's snapshot docs and CC22's diff-tool advice push the other way, for whole-output comparison of the project's own output. (2) SWE at Google ch. 12 and ch. 13 prefer state testing and give conditions where interaction testing is warranted (no real implementation or fake, call count or order is the behaviour, state-changing calls only); testdouble.js agrees ('only verify an invocation when there's no other way'). The Mockito wiki and the mockist canon (GOOS, Fowler's mockist school, opened here only from memory) disagree, and the aposd-vs-clean-code discussion debates mocks only as a design question. (3) SWE at Google ch. 23, 97 Things essay 82, Hypothesis's max_examples and derandomize docstrings, Go's fuzzing docs (plain go test runs the seed corpus only; -fuzz defaults to forever) and ClusterFuzzLite (600 s per PR, a separate cron batch) all keep a bounded per-commit run apart from an open-ended search. proptest (256) and fast-check (100) only state their defaults. (4) The proptest book states the i64::MIN case and keeps example tests. Hypothesis documents that st.integers upweights range endpoints, which is the exception, but calls the distribution an internal detail it changes. fast-check's 'Trust the framework' note disputes the need. Could not open (WebSearch budget spent, no GitHub copy found): The Pragmatic Programmer, Code Complete, xUnit Test Patterns, GOOS, Fowler's 'Mocks Aren't Stubs', Khorikov, Elhage's 'Two kinds of testing' and van Deursen et al. 'Refactoring Test Code'. These appear as marked paraphrases.

## Reception layer

WebSearch was exhausted, so reception came from GitHub-hosted sources only: official docs, tool sources, rule pages, authors' copies of papers and third-party verbatim clippings (Fowler, Spadini). Hacker News, Lobsters and the blogs could not be opened, and three items are relayed or unfetched. Concept 1 (compare semantic content, not a rendering from code the test does not own) rests on Google's Go style guide and on stability disclaimers in Java Record.toString, Rust Debug, protobuf-go and protobuf's non-canonical serialization guide. Snapshot and approval practice (Jest, insta, Jane Street expect tests) disputes it, and the two sides separate on whether the code that produces the rendering is owned; only tsDetect checks it mechanically (toString inside an assert, threshold 0). Concept 2 (state over interaction) is the most contested: SEG ch. 12-13, testdouble.js, Fowler and Spadini et al. favour state, while Zhu et al. FSE 2025 (full text) find mock assertions catch faults state assertions miss. Both sides converge on 'verify only what state cannot observe', and no tool rule enforces the preference (Sonar S2699 even counts verify as an assertion). Concept 3 (bounded per-commit budget, separate search) has broad support in the industry and the canon: Go's toolchain split, Hypothesis docs, Goldstein et al. ICSE 2024, ClusterFuzzLite and CPython's non-gating Hypothesis job. The size is contested (hegel-skill, CIFuzz 600 s per PR, Hypothesis's CI profile dropping deadlines), so a card cannot name a count. Concept 4 splits on the generator: proptest (uniform), QuickCheck (size-bounded) and Go's int mutator never produce i64::MIN or MinInt64 (confirmed by a local run of about 2.45M inputs), so an explicit example is needed there. jqwik documents MIN_VALUE as a default edge case and Hypothesis upweights bounded-range endpoints, yet Hypothesis calls its distribution an internal detail and still recommends @example for special values.

## Evidence layer

Each of the four concepts has openable support. Concept 1 (compare semantic content, not renderings from code the test does not own) rests on official documentation in four of the five target languages: the Go style guide, Java's Object.toString and HashMap docs, Rust's Debug stability note and Python's doctest warnings. Protobuf, go-cmp and Jest also document output instability, a local hands-on run reproduced it, and three test-smell studies supply prevalence data but no harm measurement specific to Sensitive Equality. Spadini ICSME 2018 found it no more change- or defect-prone than the other smells, and Jest's snapshot docs endorse serialized-output comparison, so the precondition 'code the test does not own' carries the rule. Concept 2 (state over interaction) is the contested one: testdouble.js and Mockito document it with a condition, and Spadini EMSE 2019 measures how mocks couple tests to production code. Against it, Zhu et al. FSE 2025 (full text fetched) found mock assertions alone detect half the faults they catch, and no controlled comparison exists; the openable sources agree only on the conditional form ('verify a call only when the effect is unobservable as a return value or state'), which TST-09/TST-10 partly cover already. Concepts 3 and 4 are well documented across Python, Go, Rust, TypeScript, Java and Haskell framework docs, plus Goldstein ICSE 2024, Ravi and Coblenz OOPSLA 2025, Etna, and two hands-on runs: Hypothesis hit a range endpoint in only 71/100 runs and a computed interior value in 0/100, and Go's fuzzer never hit MinInt64 in 1.67M executions. Not opened: arXiv/ACM/IEEE pages, the Sinon docs (path not found), Luo et al. FSE 2014, the NonDex ICST 2016 paper and Klooster et al. SBFT 2023; WebSearch was unavailable this run.

## Spine — candidate rules in source order

1. **A test compares a result by its value, fields, parsed content or kind rather than by a string rendering, formatted output or serialized bytes whose exact form comes from code the project does not own** — When a test checks a result through text that a library, the language runtime or a derived or default implementation renders, it compares the semantically relevant information instead. Such text includes a default toString or repr, a derived Debug format, the printed form of an unordered collection, and JSON, text or binary serialization from a library. The comparison uses the value or its fields with an equality or deep comparison, the parsed content against an expected structure, or the kind of an error. The documentation of each renderer says its output is not stable. Go's guide says it is 'generally not safe to assume that the output is stable'. protobuf-go output 'will change across different builds of your program'. Derived Debug formats 'may change with future Rust versions'. Object.toString output 'is not necessarily stable over time or across JVM invocations'. Python does not guarantee the print order of a set. Comparing text is the precise check when the text is the output the code under test must produce, such as the project's own formatter, a rendering the project defines, or golden files of its own output. Snapshot or approval files that are regenerated and reviewed through the tool's update workflow are a separate practice and go in Limits. A property-only assertion belongs to TST-22, whose Limits carry this sentence only as an exemption. An error checked by its message belongs to TST-23. Validator question: does an assertion compare against a literal or stored text the exact rendering of a result whose format a library, runtime, derive or default implementation produces, where that rendering is not the behaviour under test?

2. **A test checks an effect it can read as a returned value or as state, through the code under test or a usable real or fake implementation, by asserting that value or state and not only by verifying a call on a double** — The code under test may show an effect as a value it returns, as state it exposes through its own API, or as state in a dependency for which the test can use the real implementation or a fake the project already has. In each of these cases the test asserts that value or state, and does not check the effect only by verifying that the code under test called a double. Call verification stays for an effect that only the call shows: a side effect on a dependency with no usable real implementation or fake, a call that returns nothing the test can read, or a number or order of calls that is itself the behaviour. The rule rests on the condition that both admissible sides state. testdouble.js says 'only verify an invocation when there's no other way to assert that your subject is doing what you want it to do'. Zhu et al. say 'utilize mock assertions to validate program behaviors that are unobservable by traditional test assertions'. The rule does not rest on a general preference for state testing, which no controlled comparison measures. TST-09's Thesis names the condition in passing, but its title, Example and Validator flag only a verified call that the same test stubs. TST-10 bounds how much a verification pins, and TST-01 decides whether an in-process collaborator is doubled at all. This rule takes the remaining case: an unstubbed side-effect call whose effect the test could read but checks only through the call record. For the Rationale, SEG ch. 12 Example 12-4 shows the failure: verify(database).put passes when the record is deleted afterwards and fails after an equivalent refactor. For the Limits, SEG ch. 13's advice to back a fallback interaction test with a larger-scoped state test applies, and a verification kept beside a state assertion of the same effect is outside the rule, because Zhu et al. found such mock assertions detect faults the state assertions miss. Validator question: does the test check an effect of the code under test only by verifying a call on a double, while that effect can be read as a returned value, through the code under test's own API, or from a real implementation or an existing fake of that dependency?
