# Research note — Algorithm and data structure choice

Topic `algorithm-and-data-structure-choice` of group G. Diagnostics and performance, domain `performance`, id prefix `PRF`. Formulation locators: PoP2 (The Practice of Programming ch. 2 'Algorithms and Data Structures': searching, sorting, libraries, O-notation, growing arrays, lists, trees, hash tables); PP 'Algorithm Speed' (The Pragmatic Programmer, 20th anniversary ed., ch. 7 'While You Are Coding', topic 'Algorithm Speed').

The canon agrees on several points: The Practice of Programming ch. 2, The Pragmatic Programmer Topic 39 'Algorithm Speed', Pike's rules and the 97 Things essays. Most programs need only arrays, lists, trees and hash tables. The complexity class decides only at sizes that can grow. The library's sort and search come before a hand-written one. A hash table serves lookups by key. Building a string or array by repeated copying is quadratic. The official documentation of all five target languages states the operation costs these rules rest on: CPython's time-complexity page and collections, bisect and heapq docs, the OpenJDK 21 Javadoc, the Rust std/alloc doc comments, the Go stdlib docs and spec, and ECMA-262 for Map, Set and Array.prototype.shift. Tool rules run the checks in practice (Ruff, Pylint, eslint-plugin-unicorn, Biome, Sonar S2250/S1643, SpotBugs, PMD, clippy, Error Prone). Research (Olivo PLDI'15, Toddler ICSE'13, LDoctor ICSE'17) shows that repeated scans and redundant traversals inside loops are prevalent real defects. They are fixed by a hashed structure, memoization or batching, and their impact depends on the workload. The industry disagrees in four places. (1) Linked lists: PoP §2.7, Pike Rule 4 and Basios et al. FSE'18 stand against the Rust docs, clippy LINKEDLIST and Error Prone JdkObsolete. No openable condition separates them beyond the operations two class-level cards already carry, so the rule stays pending. (2) 'string += in a loop is quadratic': this is documented for Java, Go and Python, but Rust's String + reuses its buffer and V8 builds ropes. Naming the operation that copies the accumulated value resolves it. (3) Front removal: it is O(1) for Go re-slicing and CPython bytearray. Naming the operation that shifts the later elements resolves it. (4) Hashed lookup at tiny sizes: unicorn and MDN say a Set is faster at any size, while SL.con.2, Pike and Colvin say a scan competes at small sizes. The condition that the collection grows with the input resolves it. Ten cards follow, each naming an operation and its cost class for data that grows with the input. Measuring crossovers, capacity hints, hasher choice and constant-factor swaps between same-class structures yield to profiling-and-code-tuning.

## Formulation layer

This layer rests on PoP ch. 2 and PP Topic 39 'Algorithm Speed'. Both books were checked word for word against third-party GitHub transcriptions: PoP as a LaTeX re-typesetting with Chinese reader glosses, which I removed from the quotes; PP as a full-text copy with the math glyphs stripped, which I restored in brackets. The tip numbers 63 and 64 were cross-checked. Neither transcription states a licence, so cite the chapter, not the URL. Around the books I fetched Pike's 1989 'Notes on Programming in C', APOSD ch. 20 and the aposd-vs-clean-code discussion, six 97 Things essays, Effective Java Item 63 and go-perfbook. I also fetched openable formulations that can stand in for the book wording: the Google Python and Go style guides, PEP 8, the Uber Go guide, the Rust std::collections docs, the CPython time-complexity page and FAQ, the JDK 21 class docs, ECMA-262 §24.1–24.2, SWEBOK V3 §4.14, and the clippy, Ruff, unicorn, SpotBugs and Sonar S2250 rule pages (S2250 is under sonar-java-plugin/, not the mapped java-checks/ path). The canon agrees on four points. The complexity class matters only at the size actually seen (PoP §2.5 and §2.10, PP 'Best Isn't Always Best', Pike Rule 3, van Winkel's Yahtzee example). Use the library's sort and binary search before writing your own. Use a hash map for lookups by key unless you need ordering. Building a string or list by repeated concatenation in a loop is quadratic and should be avoided. The main disagreement is about linked lists: PoP §2.7 and Pike Rule 4 recommend them for frequently changing sets, while clippy LINKEDLIST, the Rust std docs and go-perfbook prefer a vector or deque almost always. Two smaller ones: Google's Go guide and Uber's guide disagree on capacity hints, and Stafford argues that remote calls, not data structures, dominate in multi-tier applications. I could not open the TPOP and PP errata (the hosts are denied), and Software Engineering at Google has nothing on algorithm choice.

## Reception layer

I built this layer without WebSearch, because the budget was used up and Hacker News and Lobsters are blocked. It therefore rests on practitioner texts and tool rule pages hosted on GitHub. Practitioners and tools agree on most of the topic's rules. Linked lists lose to arrays and deques (clippy LINKEDLIST, Error Prone JdkObsolete, Gankra, the Rust std docs, go-perfbook). Quadratic accumulation is flagged by tools in every target language (Sonar S1643 with a Temurin 21 benchmark, SpotBugs SBSC, PMD, Ruff RUF017, pylint R1713, Biome/oxc noAccumulatingSpread). Dean and Ghemawat's Performance Hints (last updated 2025-12-16) rank algorithmic changes first and include a sorted-list intersection replaced by hash lookups. The disputes are about size and runtime. Pike's Rule 3, Colvin's measurements, go-perfbook and C++ Core Guidelines SL.con.2 hold that a linear scan of a contiguous array wins for small n (SL.con.2 puts the line at a few KB), against the size-free Set-over-includes position of MDN and unicorn prefer-set-has (unicorn now has a minimumItems option, default 0). The claim that string += in a loop is quadratic in every language is weakened by CPython's in-place optimization (PEP 8 says do not rely on it) and by V8 cons-strings, while Sonar's Java 21 benchmark still shows quadratic growth. The tools also mark limits: hashed iteration order (SWE at Google, clippy iter_over_hash_type), the cost of hashing a key (Rust SipHash docs, perf-book, SpotBugs DMI_COLLECTION_OF_URLS), and clippy stable_sort_primitive, which carries a Known problems note against its own advice. Most of these checks are opt-in (clippy pedantic/nursery, commented out in PMD quickstart, Ruff PLR6201 preview and pedantic). Stroustrup's talk and Bloch's binary-search post are unfetched, and no forum thread was opened.

## Evidence layer

The official documentation of all five target languages states the operation costs the topic's rules rest on, and I opened each one from its GitHub source: CPython's new Doc/builtins/time-complexity.rst page, OpenJDK jdk-21-ga Javadoc, the Rust std/alloc doc comments, the Go stdlib doc comments and spec, and ECMA-262 for Map/Set and Array.prototype.shift. Static-analysis rules back each operation as a check that tools actually run: Ruff, Pylint, eslint-plugin-unicorn, SonarSource S2250/S1643, SpotBugs, PMD, clippy and Error Prone. Research with abstracts or full text reachable on GitHub (Olivo PLDI'15, Toddler ICSE'13, LDoctor ICSE'17, Selakovic ICSE'16, Basios FSE'18, Chameleon PLDI'09, Ding PLDI'15, Nistor MSR'13, de Gouw CAV'15) shows that scan-in-loop and redundant-traversal bugs are real and are fixed by changing the data structure. It also shows that how much they matter depends on the workload. Costa ICPE'17 stays relayed, and Jin PLDI'12 and Pattis 1988 stay unfetched. The canon disagrees in four places: (1) 'prefer array-backed lists over linked lists', where Rust docs, clippy and Error Prone conflict with Basios et al., who found ArrayList-to-LinkedList the most frequent improving swap; (2) 'string += in a loop is quadratic', which holds in Java, Go and aliased CPython but not in CPython's in-place fast path, V8, or Rust String + (local runs and the Rust docs); (3) 'removing from the front is O(n)', which does not hold for Go reslicing or bytearray; (4) 'a hash set always wins', which fails for small n in Rust with the default SipHash (Vec::contains faster up to roughly 32 elements in a local run). So each rule should name the copying or scanning operation and the observed size, not a collection type. ## Spine — candidate rules in source order

1. **A data structure is chosen among the few standard ones by the cost of the operations the code performs on it** — Most programs need only arrays, lists, trees and hash tables and compounds of them, and each structure's per-operation cost decides whether it suits an application: arrays give constant-time access but do not grow or shrink gracefully, lists take O(n) to reach a random element, and trees and hash tables combine rapid keyed access with easy growth. The principle names no defect a hunk shows by itself; its checkable forms are the topic's operation-level cards.
   - formulation: PoP ch. 2 'Algorithms and Data Structures', chapter introduction; PoP ch. 2 §2.10 'Summary', third paragraph; Pike, 'Notes on Programming in C' (1989), 'Complexity', Rules 4 and 5

   - evidence: Rust standard library documentation, module std::collections (rust-lang/rust master, library/std/src/collections/mod.rs) — module doc, '# Performance', first paragraph (fetched, official-documentation); Ohad Shacham, Martin Vechev, Eran Yahav, 'Chameleon: Adaptive Selection of Collections', PLDI 2009, pp. 408-418, DOI 10.1145/1542476.1542522 (abstract on eth-sri/eth-sri.github.io) — abstract (fetched, research); Diego Costa, Artur Andrzejak, Janos Seboek, David Lo, 'Empirical Study of Usage and Performance of Java Collections', ICPE 2017, pp. 389-400, DOI 10.1145/3030207.3030221 — abstract (orchestrator's search snippet) (relayed, research)

2. **A membership test or lookup by key that runs on every iteration of a loop uses a hashed set or map, not a linear scan of a sequence whose size grows with the input** — When a loop tests membership in, or finds an element by key in, a sequence whose size grows with the input, each test is a linear scan, O(n) per test and O(n·m) over the loop; the collection is built once as a hashed set or map, whose membership test and key lookup cost expected O(1) (in JavaScript and TypeScript, average access sublinear in the number of elements by specification). A collection the domain bounds to a handful, a single test outside a loop, a sorted sequence searched by range with binary search, and an explicit inner loop over a second collection (index-instead-of-nested-matching) are outside the rule; the hashed costs assume a hash that disperses the keys and O(1) hashing and comparison of a key.

3. **A data set searched repeatedly is sorted once and binary-searched rather than scanned on every search** — PoP §2.2 says that when repeated searches are made in a data set it is profitable to sort once and then use binary search. 14. **A linear traversal whose result does not change between iterations runs once before the loop, not in the loop condition or once per iteration** — A call that walks a whole collection or string, placed in a loop condition or body, is repeated on every iteration.
