# Research note — Domain modeling and domain language

Topic `domain-modeling-and-domain-language` of group B. Module design, domain `design`, id prefix `DSN`. Formulation locators: PP 'Domain Languages' (The Pragmatic Programmer, 20th anniversary ed., topic 14, ch. 2 'A Pragmatic Approach': programming close to the problem domain, internal and external domain languages); SWEBOK Guide V4.0 ch. 3 'Software Design' §5.10; the domain-driven-design literature (Evans, Domain-Driven Design) as the practitioner formulation of a ubiquitous language, named in the provenance map only.

The canon asks code to speak its problem domain's language. PP Topic 14 says to program close to the problem domain, SWEBOK V4 §5.10 lists domain-driven design with a language shared with stakeholders (reached only through relayed summaries), and Evans's CC-BY DDD Reference, named in the provenance map only, supplies ubiquitous language, bounded context, value objects and the anticorruption layer. From these the formulation layer draws four positions: domain vocabulary in names, domain values as distinct types, flag and optional-field combinations as sum types that make invalid states unrepresentable, and internal domain languages built from the host language. Almost all openable evidence is official documentation and tool rules: the Rust API guidelines and book, the Go spec, the Python typing and enum docs, the TypeScript handbook, clippy, Error Prone, typescript-eslint, PMD, the Uber Go guide, the protobuf style guide and an Azure architecture pattern page. Compile checks re-run in all five languages under /tmp/craft-research/dsn-dml-spine/hands confirm the effects and their limits: Go accepts untyped constants and relabelling conversions, a Python NewType is static-only, a TypeScript brand is a cast, Go and old-style Java enum switches are not checked for completeness, and Go type switches are not checked either. Research is thin and indirect. Kosar et al. measured comprehension of external DSLs against GPL APIs, general static-typing studies cut both ways, and Phys shows that unit inconsistencies compile. No openable study of primitive obsession, flags against sum types, or ubiquitous language was found. The industry disagrees on four points. On how far to wrap primitives (Landre, Fowler, Seemann and Wlaschin against King's 'Names are not type safety'), the general rule stays pending and its two agreed cases are carded: a unit or identifier distinction, and an invariant several routines rely on. On catch-all defaults over closed types, the split is separated by whether completeness is checked and whether version skew is possible. On time types against units in names, it is separated by Uber's boundary carve-out. On inventing internal DSLs (PP and Hunger against Google's Go style), the rule is held as not checkable. Domain vocabulary in names folds into the shipped CODE-06, and boolean parameters belong to routine-size-and-parameters.

## Formulation layer

The canon agrees on four positions, each available in openable form. (1) Code is written in the domain's own vocabulary: the domain language, kept consistent within a bounded context (Evans's CC-BY DDD Reference, 97 Things #11, PP Topic 14 via notes, SWEBOK V4 §5.10 and §4.5 via two relayed summaries). (2) Domain values and identifiers become distinct types instead of bare primitives (97 Things #65, Fowler's Primitive Obsession, Code Complete ch. 6 and 12, Effective Java Items 34 and 62, Wlaschin, Goetz, Rust C-NEWTYPE). (3) Flag and optional-field combinations become sum types that make illegal states unrepresentable (Wlaschin after Minsky, King, the TypeScript handbook, clippy struct_excessive_bools, 97 Things #84). (4) An internal domain language is built from host-language functions, with external languages left to the parsing topic (PP Topic 14 paraphrase, 97 Things #23). The canon disagrees on how far to wrap: Alexis King's 2020 reflection argues a transparent wrapper is only a name unless it carries a functional distinction (units, IDs) or an invariant behind an encapsulation boundary, which narrows Landre's and Wlaschin's wrap-every-domain-value advice. Preconditions a card must keep: terms need be consistent only within a bounded context (Evans), and independent on/off flags are legitimately a flag set (Rust C-BITFLAG). The unit-in-name fallback applies only where a format cannot carry the type (Uber Go), and a type alias gives no distinction in any of the five languages (Python, Go, Rust and TypeScript docs; this qualifies Code Complete's typedef advice). Not opened: the books (PP, Code Complete, Refactoring, Effective Java, Clean Code, Evans's DDD) are reached only through third-party GitHub notes (relayed) or from memory (PP Topic 14 trade-offs, unfetched); the SWEBOK V4 text was reached only through its TOC and paraphrasing summaries; Minsky's 'Effective ML' and Cunningham's CHECKS 'Whole Value' were not found. The aposd-vs-clean-code discussion touches the topic only once (addSongToLibrary with int durationInSeconds), and neither author raises domain types. The Kosar DSL-comprehension studies are research for the evidence layer and were not used as formulation.

## Reception layer

Reception splits along three lines. (1) Wrapping a primitive that stands for a domain concept in its own type is defended by Seemann, Wlaschin, Landre and North (97 Things), the Rust API guidelines, Error Prone's time checks and Uber's Go guide. Alexis King ('Names are not type safety') disputes it: a wrapper with no invariant and no encapsulation boundary is only a name, and making a type for every concept the domain names is noise. A commenter on Seemann's post also disputes it, wanting richer invariants before wrapping. TigerStyle and Uber carry units in names where no type is available, and the cost depends on the language (Rust newtype boilerplate, TypeScript brands that need assertions, a Python NewType that is checked only statically, no sum types in Go). (2) Nobody named disputes making invalid states unrepresentable with sum types (Wlaschin, King, the Elm guide, clippy struct_excessive_bools and option_option), but there are limits: the number of cases can blow up (Wlaschin's 15 combinations), and matklad's 'dissolving enum' shows an enum that only repeats a branch decision. Tools disagree sharply on default clauses. Error Prone, PMD, typescript-eslint, clippy and Go's exhaustive linter say a default on an exhaustive enum switch defeats the check; Checkstyle, Sonar S131, ESLint default-case and Google Java style want a default or exhaustiveness everywhere. Both sides make exceptions for library version skew. (3) Clippy, ruff, Sonar S2301 and revive flag boolean selector parameters, but Google's Go best practices prefer an option that takes a bool, and Error Prone accepts parameter comments instead. Internal DSLs are defended by Hunger, by Kosar 2018 (abstract via neverworkintheory) and by Greg Wilson's qualified review; Google's Go style warns against inventing DSLs. Most of these checks are off by default: clippy pedantic or restriction groups, Error Prone disabled checks, pyright strict mode only, typescript-eslint rules outside the shared configs. WebSearch was used up, so I opened no Hacker News or Lobsters threads, no Harper 'Boolean blindness', no Minsky 'Effective ML Revisited' and no Evans DDD text. I found no general primitive-obsession lint.

## Evidence layer

Most of this topic's evidence is official documentation and tool rules, all opened through raw.githubusercontent.com. The type mechanisms (Rust newtype C-NEWTYPE, Go defined types, Python NewType, TypeScript branded and discriminated unions, Java records), exhaustiveness checks (TS never, typing.assert_never, Rust match, clippy, typescript-eslint, Error Prone, Google Java style 4.8.4.3), the bool lints (clippy *_excessive_bools, Ruff FBT001), unit-carrying time types (Uber Go guide, Error Prone PreferJavaTimeOverload) and cross-API term consistency (Google AIP-190) each state their rule directly. I ran compile checks in all five languages (under /tmp/craft-research/dsn-dml-ev/hands). They confirm the effect and expose limits that cards must keep. Go accepts an untyped constant or an explicit conversion into a defined type. Python NewType is static-only and one-way. A TS brand is an unchecked assertion. Go has no sum type and no exhaustiveness check, and javac does not check an old-style enum switch statement. Research is thin and indirect. Gao et al. (15% of public JS bugs detectable by types) and Hanenberg's maintainability study support types in general. Hanenberg 2010 found no development-time or quality benefit. Kosar et al. show better program comprehension with DSLs, but they measured external DSLs against GPL APIs, not internal DSLs. I found no openable empirical study of primitive obsession, flags against sum types, or ubiquitous language. SWEBOK V4 §5.10 could not be opened and V3 has no counterpart. The sources disagree on catch-all defaults: Error Prone, typescript-eslint and Google Java style accept or require a default for library skew, which hides new variants. They also disagree on booleans: Google's Go guide prefers a bool for a truly binary option.
