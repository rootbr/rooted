# A release operation that a type implements frees every resource the object owns even when one step of the release fails, and marks the object released so that a repeated call releases nothing again

## Thesis
The release operation of a type that owns resources — a close or dispose method, the exit method of the language's scoped-release protocol, or a destructor — releases every underlying resource the object owns, on every path through it, the exceptional ones included. When one step of the release fails, such as writing out buffered data or releasing one of several owned resources, the operation still releases the remaining resources, and it marks the object as released before it reports the failure. A repeated call releases nothing a second time: it has no effect, or it reports that the object is already released. Where the language runs destructors while a failure unwinds the stack and a destructor that fails there aborts the program, the destructor does not fail: it does the teardown and ignores or logs the errors the teardown produces, and the type offers a separate operation for checking a clean teardown, such as a close, a flush or a sync, that returns those errors to the caller who needs to check them.

## Rationale
A release operation is unlikely to be called more than once, so relinquishing the underlying resources and marking the object closed before reporting a failure ensures that the resources are released in a timely manner, and it reduces the problems that could arise when the resource wraps, or is wrapped by, another resource; prompt release avoids the resource-exhaustion errors that may otherwise occur. A standard output-stream wrapper shows the shape: when not already closed, it calls its flush and then closes the underlying stream, and its implementation marks itself closed before the flush and still closes the underlying stream when the flush throws. A container of disposables shows it for several resources: when the container is disposed, each object in it is guaranteed to be disposed, barring early termination of the program, and an error any of them throws during disposal is collected and rethrown after all of them are disposed. A failure of the release can be the only report of an earlier failed write: errors of a previous write may be reported only on the final close that releases the open file, and failing to check that result may lead to silent loss of data, so a careful caller checks the result of the close, and the release operation reports the failure rather than dropping it. The failed close has nonetheless released the handle: on Linux, close always frees the descriptor early in the operation and the steps that may return an error, such as flushing data to the device, occur only later, and many other systems likewise always close the descriptor, unless it was invalid, even when they then report an error, so retrying a close after a failure may close a reused descriptor from another thread; an object marked closed before the failure is reported turns such a retry into a call that has no effect. Where destructors are executed while the program unwinds from a failure and a failing destructor in that context causes the program to abort, the destructor ignores or logs its teardown errors, and a separate operation that returns them, such as a close, a flush or a sync, is how a caller checks for clean teardown: a standard file type ignores errors detected on closing in its destructor and points to an explicit sync call when those errors must be handled, and a standard buffered writer's destructor attempts the final flush but ignores any error it hits, which makes calling flush before the writer is destroyed critical.

## Example
```typescript
bad:  [Symbol.dispose]() {
        this.file.close();
        this.conn.close();
      }
good: [Symbol.dispose]() {
        if (this.closed) return;
        this.closed = true;
        try { this.file.close(); } finally { this.conn.close(); }
      }
```

## Limits
A generic release interface may leave the behaviour of a second call undefined, or allow it a visible side effect, and let each implementation document its own; implementers are still strongly encouraged to make the operation idempotent. A disposable need not keep every later use consistent with its released state, since some disposables are reusable, such as a connection with an open method; for such a type, a release after it was opened again is not a repeated call. A base type may implement the release protocol although not all of its subtypes or instances hold releasable resources; an instance that holds none has nothing for its release operation to free. In a language whose scoped-release construct rethrows an error the release operation throws, and combines it with an error of the scope's body when both throw, the release operation may report its failure by throwing; the silent destructor and the separate operation that returns its errors apply where a destructor runs during unwinding and a failure there aborts the program. A resource the object holds without owning it, such as a stream or connection a caller passed in and releases itself, is left to its owner and is not its release operation's to free.

## Validator
Grep the added lines for the declaration of a release operation: a close, dispose, release, stop, finish or shutdown method, the exit method of a context manager, a dispose method keyed by the language's well-known symbol, or a destructor implementation. Open the file and read the whole operation and the type that declares it, and list each resource the object owns, one it acquired or received with its ownership rather than one a caller lent it: an open file, stream, socket or connection, a child object with its own release operation, or buffered data still to be written out. Trace each step of the operation that can fail — a flush or final write, the release of each listed resource — and check that a failure there still reaches the release of every resource after it, through a finally block, a deferred call, a stack of disposables or an error collected and rethrown at the end. Check that the operation marks the object released, by a flag or by clearing the fields, before it reports a failure, and that a second call returns without touching the underlying resources or reports that the object is already released; skip this check when the operation's only step is one call to a release that itself has no effect on a second call, and when the type documents that it can be opened again after a release. For a destructor the language runs while a failure unwinds the stack, where a failure in it aborts the program, check that no teardown error escapes it as a throw or a panic, and that the type offers a separate operation, such as a close, a flush or a sync, that performs or checks the teardown and returns the error. Validator question: **Does this release operation leave a resource unreleased when an earlier step fails, report a failure before marking the object released, release an underlying handle again on a second call, or, as a destructor run during unwinding, let a teardown error escape or swallow it with no separate operation that returns it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-25`, severity major, `file`, `symbol`, `code` = the release operation's declaration and the step whose failure skips a later release, or the release call a second invocation repeats, quoted verbatim from the diff, `fix` = the operation with a released flag set before the first step that can fail, an early return on a repeated call, and each later release reached through a finally block, a deferred call or a disposal stack, or, for a destructor, the teardown with its errors ignored or logged and a separate operation, such as a close or a flush, that returns them, in the file's language, `rationale` = the resource left held when the earlier step fails, or the handle released twice by a repeated call, and the failure the caller never sees).
