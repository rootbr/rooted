# An assertion's condition is never a literal that always passes or always fails, and a path that must never run is marked by an explicit stop, not by an always-false assertion

## Thesis
An assertion tests a condition that can be true or false where it stands, so its condition is never a literal whose value the source already fixes. A condition that always passes checks nothing, such as a true literal, a non-empty string literal, or a condition and its message enclosed together in one pair of parentheses after the keyword of an assertion statement, which makes them one non-empty tuple rather than a condition followed by a message. Such an assertion is rewritten to test the condition it was meant to test, with the message outside the parentheses or each enclosed value tested on its own, or it is removed where no condition was meant. A condition that always fails, such as a false literal or an empty string or tuple, is either a mistake, rewritten the same way, or meant to ensure that the program never proceeds past it, and then it is replaced by an explicit stop that halts execution whatever the build or run configuration — a raised or thrown error, a panic, or an unreachable marker that panics when reached — unless the assertion is a disableable one meant to stop in debug builds only and the code after it handles the path correctly in every configuration.

## Rationale
An assertion is an executable predicate that allows a run-time check, and it is meant to detect when code behaves as expected; one that succeeds or fails every time does not achieve this, and is either redundant or a mistake. For the enclosed pair, the assertion statement does not take parentheses around its condition and message, so the parentheses build one tuple, which tests true whenever it contains at least one element; a non-empty string literal always passes too, and in neither case is the intended condition tested. An always-false assertion may be meant to ensure that the program never proceeds past it, and where the correct execution of the program depends on that, the assertion form does not guarantee it: assertions are normally compiled into the code during development and compiled out later, one runtime disables them in all packages and classes by default, another emits no code for them when optimization is requested, and an optimized build skips a debug-only assertion by default. An always-false assertion that can be removed is therefore an unreliable means of raising its error, and an unchecked assertion allows a program in an inconsistent state to keep running, which might have unexpected consequences. A raised error halts execution regardless of the run-time configuration, an unreachable marker always panics, and if the determination that the path is unreachable proves incorrect, the program terminates at once; the marker's unchecked counterpart is no such stop, since reaching it is undefined behavior. Where the assertion form cannot be disabled and halts when its condition fails, an always-false assertion does stop, and a static-analysis check for such a form still asks for a panic or an unreachable marker in its place; an assertion call that only writes a message when its condition fails does not otherwise affect execution, so an always-false one never stops in any configuration.

## Example
```rust
bad:  debug_assert!(true, "index lies inside the buffer");
      State::Closed => assert!(false, "entry posted to a closed ledger"),
good: debug_assert!(index < buffer.len(), "index lies inside the buffer");
      State::Closed => unreachable!("entry posted to a closed ledger"),
```

## Limits
A disableable always-false assertion meant to stop in debug builds only is the one always-false form that stays: it expresses a stop in debug builds only, which the static-analysis check for a debug-only assertion macro leaves unflagged because there is no better way to express that; the checks for a disableable assertion statement flag every one whose condition is the false literal, and one of them conditions its advice to throw on the correct execution of the program depending on never proceeding past it. Where the code after it handles the path correctly in every configuration, execution continuing past it in an optimized build is intended; where the correct execution of the program depends on never proceeding past it, it is the defect. The rule reads conditions written as literals: a condition built from a named constant depends on another definition that may change independently of the assertion and is outside it, and for such a run-time assertion a static-analysis check recommends a compile-time assertion instead. Whether a check belongs in a disableable assertion at all, side effects in an assertion's condition, and the checking of the arguments a caller passes are judged by their own rules.

## Validator
Grep the added lines for an assertion statement, assertion macro or assertion call whose condition is a literal: a truth value, a number, a null, a string literal, or a condition and a message enclosed together in parentheses after the assertion keyword, on one line or across the lines that follow an opening parenthesis. For each hit, read the condition as the file's language evaluates it. Count an enclosed pair as one tuple only where the assertion is a statement that takes its condition and message without parentheses; where the assertion is a function or macro call, the parentheses hold its arguments, and the pair is a condition followed by a message. Classify the condition as always true (a true literal, a non-zero number, a non-empty string, a non-empty tuple) or always false (a false literal, zero, a null, an empty string or tuple). For an always-false assertion, decide whether its form can be disabled (an assertion statement that a run option or an optimization option strips, a debug-only assertion macro) or only writes a message and never stops; for a disableable one, read the code after it in the hunk and decide whether that code handles the path correctly in every configuration, with the assertion meant to stop in debug builds only, or relies on execution never proceeding past it. Validator question: **Does an added assertion have a literal condition that always passes, or one that always fails and is not a disableable debug-only stop followed by code that handles the path correctly in every configuration?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-07`, severity major, `file`, `symbol`, `code` = the added assertion line with its literal condition, verbatim from the diff, `fix` = for an always-true condition, the assertion testing the intended condition with its message outside the parentheses, each enclosed value asserted on its own, or the assertion removed where no condition was meant; for an always-false condition, a raised or thrown error, a panic, or an unreachable marker that panics when reached (never an unchecked unreachable hint whose reaching is undefined behavior), or the intended condition where the literal was a mistake, in the file's language, `rationale` = the literal condition, whether it always passes or always fails, and for an always-false one whether the assertion form can be disabled or only writes a message, and which code runs past it when it does not stop).
