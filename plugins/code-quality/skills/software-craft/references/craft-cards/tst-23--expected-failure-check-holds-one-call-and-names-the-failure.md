# An expected-failure check holds only the call expected to fail and names the failure by a specific kind, or by its message or a predicate when the kind is broad, whenever the failure is raised rather than returned

## Thesis
When a test expects a raised exception or a panic, its expected-failure check encloses only the one call that should fail, with setup before the check and further assertions after it, and names the failure by a type specific to it or, when the type is broad or absent, by a substring or pattern of the message the code under test produces or by a predicate on the exception. When the failure is instead returned as a value from the one call, checking that an error was returned is sufficient where the test cares only whether an error occurred, and a specific error is matched semantically, by its identity or kind, rather than by comparing its text.

## Rationale
A check that accepts any failure of a broad kind passes even when the failure arises for a different reason from the one expected, and it may catch errors unrelated to the code under test. Testing only that some failure was raised is not enough to guarantee that it was the expected one, so its type or content is tested further, by constraining the message or constraining the exception itself; a required message ensures that the intended failure is the one thrown. When the checked region holds several statements, execution stops at the first statement that raises and the rest are ignored: setup that raises the expected failure makes the test pass incorrectly, and assertions after the raising statement never run. Keeping one call in the region makes explicit which call is expected to fail and keeps another call that raises the same failure from passing the test. A substring of the message is enough when it ensures that the code took the failing branch the test targets; how much of the message to name depends on how much of it is unique or dynamic and how precise the test should be. Where a returned error carries a component meant for human eyes and a component meant for control flow, a test that compares the text may become brittle when a message is reworded, with the potential to turn into a change detector, while the semantic component is the information the test can reliably observe.

## Example
```python
bad:  with pytest.raises(ValueError):
          order = make_order(items)
          order.apply(code)
good: order = make_order(items)
      with pytest.raises(ValueError, match="code expired"):
          order.apply(code)
```

## Limits
The separating condition is how the failure reaches the test. A raised exception or panic propagates from whichever statement in the checked region raises it first, and a broad check then passes for a different failure than the one expected; the panic-testing documentation, the broad-raises and multi-statement lint rules and the throw-message rules listed under Source hold this side. An error returned as a value is read from the result of the one call under test, and when the test cares only whether an error occurred, checking that the error is present is sufficient; when a specific error matters it is checked semantically rather than by string comparison of its type, and a string comparison stays permissible for checking that a message from the code under test has a property, such as naming the parameter. The style decision on test error semantics listed under Source holds this side. A loop with an empty body that drives an iterator, to test iterator behaviour, is accepted inside the checked region. Where the check also matches subtypes of the named type, a test that needs the exact type checks the captured exception's type explicitly after the check. Which kinds count as broad is configurable in one enforcing tool, and the broad-raises lint and the panic lint sit in their linters' pedantic groups while the throw-message rule is in neither the recommended nor the style configuration and is enabled only by the configuration that turns on every rule; a check that names a type specific to the failure meets the rule without a message.

## Validator
Grep the hunk for an expected-failure construct: an assert-throws call, a raises block or context, an attribute that expects a panic, a throw matcher, or a fail-then-catch idiom. Open the enclosing test function at hunk scope. Count the statements and chained calls inside the checked region beyond the one call the test names as failing, skipping a loop with an empty body that drives an iterator. Read the kind the check names and treat it as broad when it is absent, a root exception or error kind, or a general value, I/O or OS error kind; for a broad kind, look for a message pattern, a predicate, or a follow-up assertion on the captured exception's type or message. For an error returned as a value, accept a check that the error is present and look only for its full text compared to tell which error it is. Validator question: **Does an expected-failure check on a raised failure enclose more than the one call expected to fail, or accept that failure by a broad or absent kind with no message pattern, predicate or follow-up check on the captured exception, or does the test identify a returned error by comparing its full text?** Yes → flag.
