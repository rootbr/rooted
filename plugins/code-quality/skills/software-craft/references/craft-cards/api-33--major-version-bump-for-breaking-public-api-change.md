# A version bump of a package that declares semantic versioning, or whose package manager assumes it, and is at 1.0.0 or later raises the major number whenever the changes it releases break the declared public API

## Thesis
In a project that declares semantic versioning, or whose package manager assumes it, and whose released version is 1.0.0 or later, a version bump that releases a backward-incompatible change to the declared public API raises the major version and resets minor and patch to zero. A backward-incompatible change is a change to the public interface or to its documented functionality that breaks client code, such as a removed package or function or a renamed type, unless the ecosystem's published compatibility policy classes that change as minor. Where the module path carries the major version from 2 on, the new major version is released as a module whose path ends in the matching /vN suffix, the path its importers then name.

## Rationale
A default or caret dependency requirement admits any later release whose left-most non-zero version component is unchanged, so from 1.0.0 on consumers receive minor and patch releases without editing their requirements, and package managers are often configured to apply such updates automatically. An incompatible change shipped under an unchanged major number therefore reaches dependants whose builds may stop working, while a raised major number stays outside their requirement until they migrate their code. In one package ecosystem around 12% of the dependent packages and 14% of their releases were impacted by a breaking change during updates of non-major releases of their dependencies, and 44% of the manifesting breaking changes were introduced both in minor and patch releases. Where the major version is part of the import path, a package whose path is unchanged must stay backward compatible with the old one, and the path suffix is needed to solve the diamond dependency problem: two major versions reached through different import paths do not conflict. Raising the major number for every incompatible change also makes the author think through the change's impact and evaluate its cost/benefit ratio, since the cost to upgrade dependent code can be significant.

## Example
```python
bad:  # 1.5.0 - BREAKING CHANGE: load(path) removed; the project follows SemVer
      __version__ = "1.5.0"  # mylib/__init__.py; previous release "1.4.2"
      version = "1.5"  # docs/conf.py
good: # 2.0.0 - BREAKING CHANGE: load(path) removed; the project follows SemVer
      __version__ = "2.0.0"  # mylib/__init__.py; previous release "1.4.2"
      version = "2.0"  # docs/conf.py
```

## Limits
Below 1.0.0 the rule does not bind: major version zero is for initial development, anything may change at any time, a path-versioned module system treats such a version as unstable, and its release checker does not let incompatible changes there affect its exit status. A package manager that counts versions as compatible when their left-most non-zero component is the same still confines a 0.y.z requirement to that component, many authors treat y as the breaking-change indicator, and one API-diff tool asks a removed public function to move 0.5.2 to 0.6.0; package distributions are more permissive than semantic versioning dictates for 0.y.z releases, many of which can be regarded as mature packages.

The rule is contested, and two conditions separate the cases: whether the project declares semantic versioning or its package manager assumes it, and whether it has reached 1.0.0. A project that publishes another policy follows that policy. One published backwards-compatibility policy lets an incompatible change ship once its warning has appeared in at least two minor versions of the same major version, or in one minor version of an older major version; a package may declare "loose" semantic versioning, where releases incrementing the minor version can contain backwards-incompatible API changes; and semantic versioning is described as not a suitable choice for projects with a regular time-based release cadence and a deprecation process that warns for a number of releases before removal. One ecosystem's packaging guide observes that most projects, especially larger ones, do not strictly adhere to semantic versioning, since many changes are technically breaking but affect only a small fraction of users. An ecosystem study contrasts a community where breaking changes are accepted but signaled clearly through version numbering with one whose practice is never permitting breaking changes.

What counts as a break needing the major bump is the ecosystem's published classification: all major changes are breaking, but not all breaking changes are major; a possibly-breaking change, which some projects consider major and others minor, is the project's call; and a breaking change is assumed major unless the policy states otherwise. Where the major version lives in the module path, the view that an incompatible version takes a new name rather than a new number coincides with the rule, since a new major version of a module has a different module path.

A backward-incompatible change already released as a minor version is answered by a new patch release that restores backward compatibility, and the released version is left unmodified. Before a release, the documented preference is to avoid the break: a new major version is for when it is absolutely necessary, since it represents significant churn for the author and the users. API-diff tools check differences in the API, while almost every change carries some risk to runtime behaviour, and whether such a change is incompatible is usually a judgment call by the maintainers. A network API that exposes only a major version follows the same rule in that version: existing clients are not broken by a minor or patch update, and an element is removed only by incrementing the API version.

## Validator
Grep the hunk for a version-bearing line: a manifest version field, a version constant, a changeset bump type, a changelog release heading, a module-path line in a module manifest, or a breaking-change marker. When the diff changes no version-bearing line, stop: the bump is judged in the diff that sets the version. At the base, read the previous released version and the project's declared versioning policy (versioning or contributing docs, changelog preamble); stop when the previous version is below 1.0.0, when the project publishes a policy other than semantic versioning, or when it declares no versioning policy and its package manager does not assume semantic versioning. Trace the public-API changes this bump releases, from the base's last release to the head: removed or renamed public packages, functions, types and fields, changed signatures, changed documented behaviour, and entries marked breaking; drop the ones the ecosystem's published policy classes as minor. Compare the new major number with the previous one, and for a path-versioned module the module path's /vN suffix with the new major number. Validator question: **Does this bump of a 1.0.0-or-later package that declares semantic versioning, or whose package manager assumes it, release a backward-incompatible public-API change while keeping the previous major number, or a path-versioned module without the matching /vN suffix?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-33`, severity major, `file`, `symbol`, `code` = the version-bearing line from the diff and the removed or changed public element it releases, `fix` = the version line with the major number raised and minor and patch reset to zero, or the module line with the matching /vN suffix, in the file's language, `rationale` = names the incompatible change, the previous released version, and that a 1.0.0-or-later release carries an incompatible change only in a new major version).
