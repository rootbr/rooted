# Research note — Internationalization and text encoding

Topic `internationalization-and-text-encoding` of group H. Tools and hygiene, domain `tooling`, id prefix `TOOL`. Formulation locators: SW4.8 (SWEBOK Guide V4.0 ch. 4 §4.8; the V3 section of the same number, 'Runtime Configuration and Internationalization', is transcribed at ligurio/swebok-v3 master 3_software_construction.md); PoP8 (The Practice of Programming ch. 8 'Portability', where it treats character sets and internationalization).

The canon frames this topic as a construction concern. SWEBOK V3 §4.8 (fetched; the V4.0 §4.8 locator could not be opened) asks construction to settle the character set and the kinds of strings, to keep user-visible strings maintainable without code changes, and to translate them with minimal impact on processing code. The Practice of Programming §8.8, Code Complete chs. 3 and 12, Java Puzzlers, Effective Python and Fluent Python say the same, but all are unfetched paraphrases. Pike's Go blog post (fetched), by a PoP co-author, carries the canon on to string units and normalization. Openable official documentation and static-analysis rule pages state every rule this topic owns. Sources: OpenJDK, CPython and the PEPs, the Go blog and time docs, the Rust book and std, MDN, ICU, GNU gettext, .NET Globalization, WHATWG Encoding, W3C String Matching and Working with Time and Timezones, the tz theory file, and the Trojan Source paper (arXiv:2111.00169; PDF fetched). Measured numbers are few: in PEP 597's survey, 82 of the 4000 most downloaded PyPI packages failed to install on non-UTF-8 locales because the encoding was omitted. The Rust advisory found bidi codepoints in only 5 crates on all of crates.io, none malicious. Trojan Source shows working attacks in 12 languages, and its GitHub scan returned 7,444 commits with 98.8% false positives, most of them legitimate right-to-left or localized text. The industry disagrees in five places, four of them with a sourced separating condition. (1) Name the encoding at every conversion (Error Prone, SpotBugs, PEP 597) or fix the default (PEP 686, JEP 400 as PEP 686 relays it, Pylint 4.0). This is separated by whether a supported runtime takes the default from the host locale or the data is not UTF-8. (2) Store every timestamp in UTC (Effective Python, W3C 'when in doubt') or keep the zone (tz theory, W3C, Temporal, jiff, Skeet). This is separated by whether the value records a moment or is a future wall-clock event. (3) Normalize before comparing (Python HOWTO, JDK Normalizer, Go blog) or match exactly (W3C String Matching). This is separated by natural-language text versus identifiers and syntax. (4) Count graphemes (Prokopov, Goregaokar) or count code units and scalar values (MDN, the Rust book). This is separated by what the count is for. Whether printable non-ASCII in literals should be escaped has no separating condition: clippy and PEP 8 say yes, Google Java and TypeScript say no. The language docs set cross-language limits. Python, Go, Rust and JavaScript case mapping is locale-independent by default, and Node, Go and Rust have no host-locale text codec. The explicit-locale and explicit-encoding hazards therefore fall mainly on Java, on Python before 3.15, and on locale-aware variants called on machine-readable text. Homoglyph identifiers are already carded by CODE-10 (naming-identifiers). No empirical software-engineering study of encoding, locale, normalization or string-length defects could be opened.

## Formulation layer

The SWEBOK V3 text for the design-note locator SW4.8 was opened through the ligurio/swebok-v3 transcription. It asks construction to handle the character set, the kinds of strings, keeping strings out of code and translating them with little effect on the code. It cites McConnell 2004 ch. 3 and ch. 10 for this. The V4 text and The Practice of Programming ch. 8 are not openable from here. They are recorded below as paraphrases marked unfetched, together with the Code Complete, Java Puzzlers, Effective Python, Fluent Python and Spolsky formulations. Openable official documents state every rule this topic owns, and these were fetched verbatim: the Python Unicode HOWTO and PEPs 8, 597, 672 and 686; Rob Pike's Go blog post on strings, which counts as a PoP co-author writing beyond the book; the Go text-normalization post, the time.Time docs and the Uber Go guide; the Rust book and the str docs; the JDK 21 Javadoc; MDN; the Google Java, TypeScript and C++ style guides; the .NET Globalization and string-comparison articles; the ICU user guide; the GNU gettext manual; the WHATWG Encoding standard; W3C charmod-norm; the tz theory file; the Trojan Source paper PDF from the authors' repository; and the Rust CVE-2021-42574 advisory. The 97 Things essays, the aposd-vs-clean-code discussion, Software Engineering at Google, and Google's Python and Go style guides contain no relevant formulation. The canon disagrees in four places: (1) storing UTC versus keeping local time plus a zone ID for future civil-time events (tz theory and Skeet against Effective Python's absolute rule); (2) whether to normalize when matching identifiers and syntactic content (W3C recommends no normalization; Python's identifiers are normalized; the HOWTO and the Go blog normalize natural-language text); (3) how freely non-ASCII may appear in source (PEP 8 and the Google C++ guide say sparingly; the Google Java guide says not to avoid it out of fear); (4) whether code points or grapheme clusters should be the default unit (Manish Goregaokar against Rust's code-point default). The Code Complete advice to use ISO 8859 for a single language is out of date next to WHATWG's 'UTF-8 exclusively' rule and PEP 686.

## Reception layer

The reception layer is built mostly from static-analysis rule pages and official documentation fetched from GitHub. They show that tools broadly check five practices: Java's default charset and default-locale case mapping (Error Prone, SpotBugs, PMD, Sonar), naive datetimes and the default time zone (Ruff DTZ, Sonar S6903, Error Prone JavaTimeDefaultTimeZone, gosmopolitan), bidi and invisible characters in source (rustc deny-by-default lints, Error Prone UnicodeDirectionalityCharacters as a non-disableable ERROR, Ruff, ESLint, eslint-plugin-security, bidichk, anti-trojan-source), user-visible literals (Android SetTextI18n, i18next, jsx-no-literals), and code-unit pitfalls (no-misleading-character-class, prefer-code-point, clippy string_slice). Four positions are openly contested. (1) Spelling out the encoding at every call: PEP 686 rejects forcing it, says Java rejected it in JEP 400, and moves Python to UTF-8 by default in 3.15; Pylint 4.0 stops emitting W1514 for 3.15+, while Error Prone still enables DefaultCharset. (2) Storing every timestamp as a UTC instant: the tz theory file, the TC39 Temporal docs, Andrew Gallant's jiff design notes and Jon Skeet (via awesome-falsehood) say future civil-time events need local time plus an IANA zone. (3) Length counted in grapheme clusters: Nikita Prokopov (tonsky) and Manish Goregaokar argue for it; MDN, Henri Sivonen (unfetched) and tonsky's own note that segmentation rules change every year push back. (4) Where to stop Trojan Source: Boucher and Anderson propose compiler-level defenses; PEP 672 puts the fix in editors and review tools, and the Rust WG calls the issue not a rustc flaw yet denies the codepoints by default. Clippy non_ascii_literal (prefer \u escapes) is directly opposed by Google's Java and TypeScript style guides (use the real character, escape only non-printables). Limits come from language docs: case mapping without a locale argument is already locale-independent in Python, Go and Rust, and Node, Rust and Go have no platform-default text codec. So the explicit-locale and explicit-encoding hazards are mainly Java (and pre-3.15 Python) concerns. ## Evidence layer

This layer opened 60 sources from GitHub raw and pkg.go.dev. It covers seven candidate rules: an explicit encoding at byte/text boundaries, an explicit locale for locale-sensitive operations and a locale-independent one for machine-readable text, user-visible strings kept out of code and never concatenated from fragments, length and indexing by the intended unit, normalization before comparison, timestamps as instants, and bidi or invisible characters in source. Most of the support is official language documentation (OpenJDK, CPython and PEPs, Go, the Rust book and std, MDN, ICU, the GNU gettext manual), W3C notes and static-analysis rule pages. Only three items carry measured numbers. PEP 597 and its public survey found that 82 of the 4000 top PyPI packages fail to install on non-UTF-8 locales because the encoding was omitted. The Rust advisory found bidi codepoints in only 5 crates on all of crates.io, none malicious. The Trojan Source paper (arXiv:2111.00169, fetched through the authors' GitHub README) shows bidi attacks in 12 languages, including Java, Rust, Go, Python and JavaScript. Three disputes need watching. On encoding, PEP 686 rejected deprecating implicit encoding and moves Python's default to UTF-8 from 3.15, JDK 18+ defaults to UTF-8, and JavaScript, Go and Rust never had a platform default, so the hazard is limited to an environment-dependent default. On normalization, W3C String Matching recommends no normalization for identifiers and syntactic content, and the Go blog says normalization is generally unnecessary. On time zones, tz theory and the W3C time zone note show that future civil-time events must keep the zone rather than a pre-converted instant. The searches found no empirical SE study on encoding, locale, normalization or string-length defects. The date/time bug study (MSR 2025) and the ICSE 2009 need-to-translate string work could not be opened (WebSearch budget spent, GitHub probes 404), and neither can anchor a card alone.

2. **A conversion between bytes and text at a file, network or process boundary names its encoding through the language's explicit-encoding API whenever the data is not UTF-8 or a runtime the code supports takes the default from the host's locale** — Every conversion between bytes and text uses some encoding. When a call omits it, Python before 3.15 and Java before 18 (or Java with file.encoding=COMPAT) fall back to a default derived from the host's locale, which differs between machines (PEP 597, PEP 686, JDK 21 Charset Javadoc). The conversions concerned are opening a text file, wrapping a stream or pipe in a reader or writer, decoding a process's output and turning a byte array into a string. Each names the encoding the data actually has, or names the locale encoding explicitly where that is the intent (Python's encoding="locale"). Where every supported runtime fixes the default as UTF-8 (Python 3.15+, JDK 18+, Node.js, Go, Rust) and the data is UTF-8, an omitted encoding is accepted (PEP 686, Pylint 4.0). Data in any other encoding is always decoded with its encoding named.
