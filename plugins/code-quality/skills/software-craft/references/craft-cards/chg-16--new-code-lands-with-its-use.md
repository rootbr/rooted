# A change that adds a routine, type or endpoint for other code to call includes at least one use of it or arrives in the same series as the change that uses it, rather than landing code that nothing in the change or its series calls

## Thesis
A change that adds an API, meaning a routine, type or endpoint meant for other code to call, includes at least one usage of that API in the same change, so that reviewers can better understand how it will be used and no unused API is checked in. Where the API and its first user are separate changes, both reach review together as one series: the dependent change states that it depends on the API change, and the two can be reviewed simultaneously while the API change is submitted first. Whenever possible, a change that adds new code makes that code active immediately, rather than leaving a whole infrastructure unused until the final change of a series enables it.

## Rationale
A change is kept small but not so small that its implications are difficult to understand: a new API arrives with a usage in the same change so that reviewers can better understand how the API will be used, and the usage also prevents checking in unused APIs. Infrastructure added across a series but left unused until the final change enables it misleads bisection: if the series adds regressions, bisection will finger the last change as the one which caused the problem, even though the real bug is elsewhere. When an API update and the new code that uses it are separate changes, each still makes an easily understood change that reviewers can verify, and the dependent change notes the change it depends on, since the change is complete only with both.

## Example
```java
bad:  public static long withTax(long cents) { return cents * 120 / 100; }
      long total(Order order) { return order.cents() * 120 / 100; }
good: public static long withTax(long cents) { return cents * 120 / 100; }
      long total(Order order) { return withTax(order.cents()); }
```

## Limits
The rule is contested on whether the API and its user belong in one change. One position puts the usage in the same change and makes new code active immediately whenever possible. The other separates an API update and the new code that uses it into two changes with the dependency noted, submits a protocol-buffer change before the code that uses it while both are reviewed simultaneously, and lets each change be part of a planned series of changes that works towards a development goal. The separating condition is whether the use reaches review together with the new code, either in the same change or in a dependent change of the same series that states the dependency; both cases satisfy the rule, and a new API whose user is in neither does not. A stub, shared signature or endpoint sent for review as the lower layer of a layered plan before the change that uses it is written does not meet the condition, although the guidance on splitting work horizontally endorses that order; the rule flags it, following the guidance that a change adding an API includes a usage of it. Leaving infrastructure unused until a final enabling change is the defect only where it is avoidable, since the guidance asks to avoid it if possible. A new API added as an independent precursor to a big change, with existing clients slowly migrated to it in later changes, follows migration practice and is outside this rule's reach. A routine that overrides or implements a member an existing type already declares, or that a test runner or program entry point calls by convention, adds no new API, since its callers already exist through that declaration or convention, and the rule does not reach it.

## Validator
Grep the hunk for added declarations of public or exported routines, types and classes, and for added route or endpoint registrations. For each one, search the other hunks of the change and the code at scope callers for a call, instantiation, import, client request or configuration entry that uses it, and for an existing declaration it overrides or implements. When no use is in the change and it overrides or implements no existing declaration, read the change description for a stated migration of existing clients to the new API, and read the series the change is posted in (the series summary, its position in the series and the descriptions of its later changes) for a dependent change that uses the new code and states that it depends on this one; when that user is only the final change of a series that leaves a whole infrastructure unused until it enables it, judge whether this change could itself make its new code active. Validator question: **Does the change add a routine, type or endpoint meant for other code to call that nothing in the change uses and that overrides or implements no member an existing type already declares, while no stated migration of existing clients covers it, and either no dependent change in the same series uses it and states the dependency, or its only user is the final change of a series that leaves a whole infrastructure unused until then although this change could make its code active?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CHG-16`, severity minor, `file`, `symbol`, `code` = the added declaration of the routine, type or endpoint that nothing in the change uses, `fix` = a call site in the same change that uses it, in the file's language, or the dependent change of the same series that uses it and states that it depends on this one, or, when the only user is the final change of a series that leaves a whole infrastructure unused, a use in this change that makes its new code active, `rationale` = names that the new API reaches review with no usage, so reviewers cannot see how it will be used and an unused API is checked in, or, for infrastructure left unused until the final change enables it, that bisection would blame the enabling change for a regression whose cause lies elsewhere).
