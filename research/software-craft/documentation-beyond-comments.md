# Research note — Documentation beyond comments

Topic `documentation-beyond-comments` of group I. Reading and documenting, domain `docs`, id prefix `DOC`. Formulation locators: SEG10 (Software Engineering at Google ch. 10 'Documentation': documentation treated like code, knowing the audience, documentation types (reference, design docs, tutorials, conceptual, landing pages), documentation reviews, freshness and retiring documents); the 97 Things essay 'Install Me' (thing_40) on a project's first-contact documentation.

The canon for documents outside the source agrees on a small core: SEG ch. 10 'Documentation', Google's documentation and code-review guides, Write the Docs, Diátaxis, the 97 Things essay 'Install Me', Keep a Changelog and the decision-record templates. Documents live in the repository beside the code and change in the same change as the behaviour they describe. A document whose subject is gone is deleted or marked obsolete. Each document is written for its audience. A README says what the code is for, its status and how to use it. Release notes mark breaking changes. A decision record keeps its rationale and is superseded rather than rewritten. The research behind this is mostly descriptive. Aghajani et al. (ICSE 2019, 878 mined artifacts) attribute 39% of content issues to up-to-dateness, usually after a code change; code examples account for half of the labelled correctness issues and findability for half of the usability issues. Their 2020 survey ranks missing documentation for a new feature (69%), outdated or obsolete references (64%), code-documentation inconsistency (59%), and faulty tutorials and installation instructions (65%) among the most important. Tan, Wagner and Treude found references to deleted code elements surviving in most of 3,000 projects' documentation, and Prana et al. found READMEs often lacking purpose and status. Official project documentation (Rust API guidelines, PEP 1, the Rust RFC process, the Go and CPython release-note procedures) and toolchain checks (rustdoc doctests, Go examples, doctest, Sphinx nitpicky, markdownlint, remark-validate-links) give the checkable forms. The industry disagrees in four places, and each shipping card carries the sourced condition that separates the cases. (1) Documentation in the same change: Kubernetes and GitLab accept a linked change gated at release when docs live elsewhere. (2) Deleting stale documents versus keeping history: PEP 1, the Rust RFCs and Nygard keep decision records and supersede them. (3) Changelogs: written per change, at release, or generated from commits. (4) Whether decision records are immutable: the Rust RFC process separates very minor amendments from substantial changes that need a new record. Several items have formulation but no admissible source and stay pending: the four-type documentation split (contested by Johnson), alternatives sections in design documents (two preprints disagree), tutorial step numbering, uninstall instructions and document headers. Review staffing, README-first, document length and 'incorrect is worse than missing' have no checkable form on a diff.

## Formulation layer

The formulation canon for documents outside the source agrees on a small core. Change a document in the same change as the code it describes: SEG ch. 10, Google's docguide, eng-practices, Write the Docs, and the Go and CPython release-note procedures all say this. Delete a stale document, or mark it obsolete with a pointer to the replacement (SEG, docguide). Give each document one purpose and write it for an identified audience (SEG; Diátaxis's four kinds). README, tutorial, landing-page, changelog and decision-record content all have openable formulations: Install Me, SEG, Google READMEs.md, Write the Docs, standard-readme, Keep a Changelog, Rust C-RELNOTES, Nygard/MADR templates and SWEBOK V3 on recording rationale and updating documentation. I fetched all of these through raw.githubusercontent.com, along with the aposd-vs-clean-code discussion. The Pragmatic Programmer, the SRE book (runbooks), the Agile Manifesto and Nygard's original ADR post are unfetched paraphrases, and runbooks have only that thin unfetched anchor. The canon disagrees in four places. Write the Docs says incorrect documentation is worse than missing documentation, while Ousterhout puts missing comments at 10-100x the cost of incorrect ones. Martin treats unit tests as low-level documentation and Ousterhout rejects that. Keep a Changelog wants curated changelogs, while Conventional Commits and conventional-changelog generate them from commits. The Agile Manifesto's 'working software over comprehensive documentation' is opposed by Readme Driven Development and Write the Docs 'Precursory'. A milder tension: SEG wants landing pages that only link onward, while README guides put install and usage inline. Papers (Aghajani et al. 2019/2020, Tan et al., Prana et al.) were left to the evidence layer. The only tool-rule found is Sphinx's opt-in nitpicky mode (it warns on references whose target is missing), and it lies outside the source map.

## Reception layer

Practitioners broadly agree on three positions: documentation belongs under version control beside the code (Google, Write the Docs, GitLab); stale documents mislead (Write the Docs, Google docguide); and a document should serve one purpose and one audience (SEG, Diátaxis). Practitioner surveys back the staleness problem (Aghajani et al. 2019 and 2020, whose PDFs were fetched from the first author's GitHub Pages site). Four of the canon's rules are disputed by named sources. Updating documentation in the same change as the code is disputed by Tom Johnson (2017), whose objection is about release cadence and who later endorsed docs-as-code (2022), and by Common Changelog for changelog entries; GitLab calls the practice encouraged, not mandatory, and Kubernetes keeps docs in a separate repository and gates them at release. Deleting dead documents conflicts with keeping decision records (Nygard, PEP 1, Rust RFCs keep superseded records), and Joel Parker Henderson reports that mutable ADRs worked better for his teams than immutable ones. On changelogs, Keep a Changelog and Common Changelog oppose Conventional Commits and semantic-release over generating them automatically. Diátaxis's four types are questioned by Tom Johnson for lacking a research basis, and Make a README's 'too long is better than too short' contradicts Google's brevity rule. Tools check these documents only in part: rustdoc, javadoc doclint and TypeDoc flag unresolved code references by default, Sphinx only in nitpicky mode, Go has no such check (searched), and changelog presence is checked only by bots (towncrier, Danger). Hacker News, Lobsters and vendor blogs could not be opened (denied hosts, no WebSearch budget), so the reception here comes from GitHub-hosted sources only.

## Evidence layer

The strongest evidence for this topic comes from two papers by the same research group, both fetched in full from the author's GitHub Pages copies. Aghajani et al. 2019 mined 878 artifacts: up-to-dateness accounts for 39% of content issues, usually after a code change; code examples cause 50% of correctness issues, and findability 50% of usability issues. Aghajani et al. 2020 surveyed 146 practitioners: missing docs for a new feature (69%), outdated or obsolete references (64%) and code-documentation inconsistency (59%) rank highest. Four papers were opened through mirrors: Tan, Wagner and Treude (two papers, arXiv metadata mirror on GitHub) on stale references to code elements, Prana et al. on README content, and Nogueira et al. on ADR templates (arXiv cs.SE RSS mirror). Six recent arXiv preprints were opened through the same mirror (README maintenance, README bugs, installation-instruction changes, release-note traceability, ADR content mining). Several things back the rules but are not empirical: Google's docguide and eng-practices, the Rust API guidelines (C-RELNOTES, C-QUESTION-MARK), SWEBOK V3 (V4 is not openable here), and tool documentation for the toolchain checks. Those checks are Sphinx nitpicky and linkcheck, rustdoc broken_intra_doc_links and doc tests, javadoc doclint 'reference', TypeDoc validation.invalidLink, Go testable examples and Python doctest. No equivalent check was found for Go doc links. The sources disagree in three places. On decision records, the concise Nygard template without an alternatives section scored best, yet a 550-repository mining study reports alternatives as under-documented. Practitioners ranked outdated version information, screenshots and licence text as unimportant (under 40%). On duplicated documentation, the docguide's 'Duplication is Evil' meets survey data that only 46% rate clone content as important (SEG's tolerance of duplication in conceptual docs is formulation only). Nothing openable was found for freshness dates or document owners, for runbooks, or for ISO/IEC/IEEE 42010 decision-rationale clauses. These rest on SEG ch. 10 formulation or are unfetched.

## Spine — candidate rules in source order

1. **A change that alters how users build, test, run, configure or release the code updates the repository documents that describe that behaviour in the same change** — A change may alter a command, flag, environment variable, configuration key, a build, install or release step, or other behaviour users rely on. The README, guides and other documents in the same repository that describe it are then updated in that change, and a reviewer asks for the update, or for documentation that is missing. Where the documents live in a separate repository or are published on their own cadence, a linked documentation change merged before the release meets the rule. Outdated version strings, screenshots, licence text and translations, which practitioners rate unimportant, are outside the rule. So are implemented design documents and accepted decision records, which are kept as history.
   - formulation: Software Engineering at Google (Winters, Manshreck, Wright eds., O'Reilly 2020) ch. 10 'Documentation', sections 'Documentation Is Like Code' and 'Case Study: The Google Wiki'; Write the Docs, 'Documentation principles' (docs/guide/writing/docs-principles.rst), 'Current' and 'Nearby'; Write the Docs, 'Docs as Code' (docs/guide/docs-as-code.rst); 97 Things Every Programmer Should Know, thing_62 'Only the Code Tells the Truth' (Sommerlad); The Pragmatic Programmer (Hunt, Thomas, 1999) ch. 8 'It's All Writing' (unfetched)
   - reception: contested — same change (Google documentation guide; Google eng-practices; SEG ch. 10): Documents beside the code change in the same change as the code, and the reviewer insists on it.; evidence: docguide best_practices.md 'Update Docs with Code' and eng-practices looking-for.md 'Documentation' (fetched, official documentation); Aghajani et al. 2019 report projects that put the documentation update on the contribution checklist or make it a pull-request requirement (fetched, research) / linked change gated at release (Kubernetes SIG Docs; GitLab Technical Writing; Tom Johnson (2017)): Where documentation lives in a separate repository or ships on its own cadence, a feature's documentation goes in a linked pull request merged before the release; documentation in the same change is encouraged, not mandatory.; evidence: Kubernetes 'Documenting a feature for a release' and GitLab 'Documentation workflow' (fetched, official project documentation); Johnson's blog post 'Limits to the idea of treating docs as code' (fetched, reception only); separating condition: Where the documents live decides it.
