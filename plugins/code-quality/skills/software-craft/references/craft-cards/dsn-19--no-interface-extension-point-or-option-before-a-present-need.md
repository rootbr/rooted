# A change adds no interface, abstract type, extension point or option that the system does not presently need

## Thesis
A change adds no interface, abstract type, extension point, hook or option that the system does not presently need, and through them makes no code more generic than the problem it solves now requires. A new interface or abstract type answers a need that already exists: two or more concrete types that the same logic must handle, a consumer that needs only one or two methods of a concrete type with a massive API surface, a circular dependency between two packages that it breaks, a material need to substitute a test double for the real implementation, or a concrete type returned behind an interface because its extra methods would let callers bypass safety checks or because exposing it would make it impossible to change the underlying provider without a breaking change. An interface defined before it is used, one the implementing side defines only so that tests can mock it, one that wraps a generated RPC client or server in a new manual interface only for abstraction or testing, and one added only because the design follows a named pattern such as a service or a repository wait until such a need arrives; until then the code uses the concrete type.

## Rationale
Code written for a problem that might arise is designed before that problem's actual shape and requirements can be seen: without a realistic example of usage it is too difficult to see whether an interface is even necessary, let alone what methods it ought to contain. Over-engineering is a particular type of complexity, which usually means code that readers cannot understand quickly and can also mean code into which developers are likely to introduce bugs when they call or modify it. Every exported type increases the reader's cognitive load: a test double exported alongside the real implementation makes the reader understand three entities, the interface, the real implementation and the test double, instead of one, and exporting an interface commits its module to maintaining that API for external callers. Offering too much also costs inside the implementation: an interface that undertakes to do too much will probably have a large, slow and complicated implementation. In one documented system, mapping virtual pages to file pages, which subsumed file input/output within virtual memory, took about 11,000 lines of code against about 900 for files and 500 for paging in its predecessor, and a page fault often incurred two disk accesses instead of one. Across 395 releases of 30 open-source systems, speculative generality, measured as an abstract class with fewer than three child classes using its methods, affected 80% of the releases; classes were generally more change-prone while they carried it than while they did not, and its removal had a high effect on change-proneness and a limited one on fault-proneness. Complexity is easy to add to code as needed and much harder to remove after it has been found to be unnecessary, and generalizations are generally wrong, so an interface captures the minimum essentials of an abstraction and the generality waits for the problem that needs it to arrive.

## Example
```java
bad:  interface ReportFormatter { String format(Report report); }
      abstract class ReportFormatterFactory { abstract ReportFormatter create(); }
      final class ReportFormatterImpl implements ReportFormatter {
          private final FormatOptions options = FormatOptions.DEFAULT;
          public String format(Report report) { ... }
      }
good: final class ReportFormatter {
          String format(Report report) { ... }
      }
```

## Limits
A need the change itself contains is present: a second concrete type handled by the same logic, the consumer of a narrow view, or the test that materially needs the substitute, added in the same change. An interface that is the module's product, a common protocol that many different implementations must follow or a generated service boundary, is the need itself, and the module that provides it defines it. Using an interface that already exists, a generated RPC client or server among them, is the recommended course and outside the rule. A thin wrapper the project owns around a third-party library other than an HTTP or RPC client, stating the operations the code needs in the application's own terms so that unit tests double the wrapper rather than the library's types and integration tests run the wrapper against the real library, meets the material need for a test double. An interface introduced to break a dependency cycle meets a real need, yet it is often a signal of improperly structured packages, where consolidated packages are often preferred. Complexity added deliberately where the code needs it, for additional performance, for multiple disparate customers of a particular library or service, or for planned reuse whose variation points come from a variability analysis, may be justified; it should then come with documentation, tests and examples that explain it, and such a deliberate, documented addition is outside the rule, while a variation point that rests only on a developer's speculation about the future stays inside it. A project context that requires an interface at a named boundary, such as a layer that may not depend on another, or for each injected component, rejects the finding for that boundary. An interface that only names the shape of a data value, declaring fields and no behaviour for an implementation to supply, is a type declaration rather than an abstraction over implementations and is outside the rule.

## Validator
Grep the hunk's added lines for a new interface, trait, protocol or abstract type, a factory, provider, strategy, plugin, hook or extension type, and a new option, flag, setting or parameter. Judge only what the change adds; an abstraction or option that exists at the base is outside the finding. For each new interface or abstract type that declares behaviour for an implementation to supply, search the repository for the types that implement it and the code that uses it: count the concrete implementations that the same logic handles, look for a consumer that takes it in place of a concrete type with a far larger API, check whether it removes an import cycle between two packages or modules, and check whether it is the protocol the module exists to provide. For an interface the module returns in place of its concrete type, check whether the concrete type's extra methods would let callers bypass safety checks, or whether exposing the concrete type would make a change of the underlying provider a breaking change. Where its only other implementation is a test double, open the test and decide whether the real implementation, through its public API, could serve the test instead. For each new option, flag, hook or extension point, find every caller and check whether any sets it to something other than its default or registers a hook. Read the change description: a need it states for the present change counts, and so do a planned reuse whose variation points it documents and the replaceability of a returned type's provider without a breaking change; a future it only anticipates does not. Validator question: **Does the change add an interface or abstract type declaring behaviour, other than the protocol the module exists to provide, that neither two concrete types handled by the same logic, nor a consumer needing a narrow view of a large type, nor a dependency cycle, nor a material need for a test double, nor a concrete type whose extra methods callers must not reach or whose provider must stay replaceable without a breaking change requires, or an option, hook or extension point that no present caller uses, with no documented performance need, set of disparate customers or planned reuse behind it?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-19`, severity major, `file`, `symbol`, `code` = the added declaration of the interface, abstract type, hook, extension point or option, quoted verbatim from the diff, `fix` = the concrete type used directly in place of the interface, or the unused option, hook or extension point removed, in the file's language, `rationale` = the abstraction or option the change adds, the implementations or callers the search found, and the need that is absent).
