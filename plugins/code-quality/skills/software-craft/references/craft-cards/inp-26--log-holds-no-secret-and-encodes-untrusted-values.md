# A log record holds no password, key, access token, connection string, payment data or sensitive personal data in clear text, and an untrusted value reaches it through an encoding that keeps line breaks and delimiters from forging or splitting a record

## Thesis
A log statement the change adds or changes leaves out, masks, hashes or encrypts each authentication password, encryption key or other primary secret, access token, database connection string, bank account or payment card holder datum, and each sensitive personal datum such as health data or a government identifier, and it records a session identifier only hashed or masked, in full or in part. A value from another trust zone reaches the record through a logging component that encodes it for the output format, or through a sanitizer at the call, so that carriage return, line feed and the format's delimiter characters cannot split a legitimate entry in two or insert a fake one. For a security event, a malformed field from another trust zone is omitted or safely replaced and the validation failure recorded, and the event itself is still logged.

## Rationale
A secret or personal datum written to a log entry could be exposed to an attacker who gains access to the logs, and logging it raises concerns over the privacy of the stakeholders, legal limits on collecting personal information and data exposure by insiders. The duty holds after the value has been read: an application must avoid logging a secret in the clear whether it arrived through an environment variable or a mounted volume. A build platform's automatic redaction of secrets in its workflow logs is not guaranteed: a secret value can be transformed in multiple ways, and because redaction largely relies on an exact match for the value, structured data around a secret can make it fail. Mobile app logs frequently expose personally identifiable information due to inattentive logging practices: across 3,885 Android apps, runtime analysis found such leakage in 233 apps (approximately 6%), 7,485 violations in all, and static analysis of 300,073 log statements across 3,994 apps identified 1,788 potential log-based leaks of such information in 932 apps and 97 distinct libraries. A type that controls how its values appear in logs can redact secret information such as passwords wherever a value of that type is logged.

A log message built from external input without neutralizing special elements lets an attacker insert fake log data and deceive administrators about the system's behaviour; a carriage return and line feed sequence can split one legitimate entry into two to mislead an auditor. Encoding log data correctly for its format prevents injections or attacks on the logging and monitoring systems, and user input in an entry displayed as HTML should be HTML-encoded before it is logged, to prevent forgery and other HTML injection. Encoding inside the logging component covers every call at once: a sanitizing logger saves the developer from having to worry about unsanitized messages, and a structured text handler that quotes any value containing a Unicode space character, a non-printing character, a double quote or an equals sign writes control characters as escape sequences, so a line feed stays inside one quoted value. Omitting or replacing only the malformed field, rather than discarding the security event, preserves the evidence the event carries.

## Example
```typescript
bad:  console.info(`login failed user=${req.body.user} password=${req.body.password}`);
      logger.debug(`calling api with key ${apiKey}`);
      console.log(process.env);
good: logger.info({ user: req.body.user }, "login failed"); // JSON output escapes CR and LF
      logger.debug({ key: mask(apiKey) }, "calling api");
      logger.debug({ envKeys: Object.keys(process.env) }, "environment read");
```

## Limits
Some data, such as access times, can be safely logged. The exclusion list is hedged as what should usually not be recorded directly, and further personal data, such as user names, email addresses or IP addresses, is logged according to the data's protection level as the application's logging policy sets it, some of it only to a log file restricted to particular administrators; the rule flags the named categories in clear text and defers to that policy on the rest. The sources part on whether a password or payment card data may enter a record masked, hashed or encrypted: one lists masking, hashing and encryption as remedies for every named category, while others say a password is not logged at all and a credit card number only in encrypted form, and give credentials and payment details as data that may not be logged; the rule flags the clear-text form, on which they agree, and its fix leaves a password, other credential or payment datum out. The encoding duty covers values built from external input or taken from another trust zone; a value the program itself produces is outside it. A call that hands the value to a logging component already configured to encode or strip CR, LF and the format's delimiters for all message events satisfies the rule without a sanitizer at the call. Which channel supplies a secret at run time, an environment variable or a mounted volume, is outside the rule, which applies once the value has been read; so is restricting who may read the log file.

## Validator
Grep the hunk for log, logger, console, print and tracing calls whose arguments name a password, passphrase, secret, token, API or private key, credential, session identifier, connection string, card number or government identifier, and for calls that interpolate or concatenate request parameters, headers, form fields, bodies or a dump of the environment. Open the file and trace each such argument to its origin: a named secret or sensitive personal datum, or a value from outside the trust boundary. For a secret, check whether the call leaves it out, masks, hashes or encrypts it, and for a session identifier whether it is left out, hashed or masked, or whether its type redacts itself when logged. For an untrusted value, check the logger's configuration in the file and its imports for a handler or layout that encodes values for the output format, and otherwise the call for a sanitizer that neutralizes CR, LF and the format's delimiters. Where the hunk validates such a value on the path of a security event, check that a malformed value is omitted or replaced and the validation failure recorded while the event is still logged. Validator question: **Does a log statement the hunk adds or changes write a named secret or sensitive personal datum in clear text, or a session identifier neither hashed nor masked, or write a value from outside the trust boundary through a path where neither the logging component nor the call encodes or strips CR, LF and the format's delimiters, or, for a security event, does the hunk drop the event because such a value is malformed, or omit or replace that value without recording the validation failure?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-26`, severity major, `file`, `symbol`, `code` = the log statement and the argument carrying the secret or the untrusted value, quoted verbatim from the diff, `fix` = the statement with a password, other credential or payment datum left out and any other secret or sensitive personal datum left out, masked or hashed, or with the untrusted value passed as a field to an encoding logger or through a sanitizer, or with the dropped security event logged, the malformed field replaced and the validation failure recorded, in the file's language, `rationale` = the category of the logged value or its untrusted origin, and whether exposure or record forgery follows).
