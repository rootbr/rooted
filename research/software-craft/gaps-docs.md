# Research note — Concepts the docs reviewer found uncovered

Topic `gaps-docs` of group I. Reading and documenting, domain `docs`, id prefix `DOC`. Formulation locators: the taxonomy topics of the concepts and their canon locators: documentation-beyond-comments (SEG10).

The topic holds one concept the docs reviewer found uncovered: a release-note entry written in the change itself. Neither the canon nor the standards say when or by whom a release-note entry is written. SEG ch. 10 asks that documentation change with the code, and SEG ch. 19 mentions presubmit hooks that check change descriptions so that release notes can be generated from them. Keep a Changelog's Unreleased section, towncrier's philosophy, changesets ('capture this information when submitting a PR') and reno (notes in git travel with backports) supply the formulation. SWEBOK V3 §6.2 and GNU §6.7 only define what release notes contain, and GNU frames that per release. The checkable rule comes from project procedures and the CI checks those projects run. Go's doc/README.md says to add a file to the CL instead of a RELNOTE=yes marker. CPython's devguide gives most changes a Misc/NEWS.d entry and exempts documentation, test, strictly internal and unreleased-revert changes, and bedevere fails the status check without one. Kubernetes requires a release note for any user-visible or operator-visible change, and prow labels the PR do-not-merge until it has one. GitLab requires a Changelog trailer for every user-facing change. pip, pytest and Twisted require a towncrier fragment. Projects disagree in two ways. First, they set the threshold differently: every change (Twisted), user-visible (CPython, Kubernetes, GitLab), non-trivial (pip), documented behaviour (pytest), discretionary (LLVM, except potentially breaking changes), or new features, incompatible changes and backported fixes only (Django). Second, some reject the workflow outright. Node.js compiles notes at release from commits, GitHub and semantic-release generate them, and Common Changelog §6.2 argues that a maintainer with a bird's-eye view should write them at release. The project's own documented workflow separates the cases, and each side has openable official documentation, so the rule ships as a contested card with that precondition. The research is descriptive. Wu et al. (ICPC 2022) find that release notes miss information more often than they state it wrongly, attribute this to a few people having to understand every change, and recommend spreading the work across contributors. Nath and Roy found 37% of 1,924 releases with empty notes, and Imtiaz et al. found that 61.5% of security releases document the fix. No study measures whether per-change entries improve completeness.

## Formulation layer

The project documents agree on the core position: where a project gathers release notes per change, the change that has a user-visible effect brings its own entry. Go's doc/README and its cmd/relnote check, CPython's devguide and its bedevere 'news' status check, towncrier check, Kubernetes, pip, pytest, Hypothesis, GitLab, Django's contribution checklist and changesets all state it, and the GNU Coding Standards define the NEWS file as the list of user-visible changes. Their scope rules differ, and those differences are the preconditions a card has to keep. CPython leaves out documentation, test and internal-only changes, reverts not yet released, and fixes to unreleased changes. Kubernetes and GitLab leave out tests, build infrastructure and fixes for unreleased bugs. Django asks for no note for a bug fix that lands only on the main branch. pytest skips changes that do not affect documented behaviour. The position is contested. LLVM leaves the note to the author's or reviewer's discretion and says 'preferably as part of the commit'. Node.js has the releaser compile notable changes from commits and labels at release time. Common Changelog rejects the Unreleased section and has the maintainer write entries at release. changesets advises against blocking contributions that lack a changeset. Conventional Commits and GitLab keep the per-change record in the commit message rather than in a file. Among the canon books, Software Engineering at Google ch. 10 and ch. 19 and the 97 Things essay 'Put Everything Under Version Control' were opened. Clean Code, A Philosophy of Software Design and The Pragmatic Programmer could not be opened and are paraphrased as unfetched. The aposd-vs-clean-code discussion and the 97 Things table of contents contain nothing on release notes. Folding risk: DOC-11 (documents describing behaviour change in the same change) rests on eng-practices and docguide, and neither names release notes. DOC-14 already holds how an entry is worded (CPython's 'How to write a NEWS entry'), and DOC-22 holds the breaking-change marker.

## Reception layer

Large projects broadly support writing a release-note entry in the same change that makes a user-visible change. Go (doc/next), CPython (Misc/NEWS.d, checked by bedevere), Twisted, pip, pytest, attrs, Black, Kubernetes, GitLab, Electron, Clippy, LLVM, Django and HashiCorp's providers all require or encourage it. Bots and CI checks enforce it: towncrier check, bedevere, Prow's releasenote plugin, Danger, changeset-bot, Electron's clerk, go-changelog's changelog-check, Go's TestCheckAPIFragments, and the Black, Clippy and scikit-learn workflows. Most of these give an explicit way out (skip-news or "ci: skip news" labels, "NONE", "changelog: none", trivial or misc fragments). Projects disagree about where the entry lives: a file in the repository (Go, CPython, towncrier, go-changelog), the PR description (Kubernetes, Electron, Clippy) or a commit trailer (GitLab). They also disagree on how strict the requirement is: "changes must" (Twisted), "most changes" (CPython), "non trivial" (pip), "user-facing" (Kubernetes, GitLab) and "at the author's or code reviewer's discretion, preferably" (LLVM). The workflow itself is contested by named sources. Vincent Weevers (Common Changelog §6.2) says a maintainer should write the changelog at release time with a bird's-eye view. Conventional Commits, semantic-release, release-please, GitHub's generated notes, release-drafter and Node's changelog-maker build notes from commits or PR titles. Keep a Changelog, Common Changelog §4.1 and go-changelog criticise those generated notes as noise or as mixing two audiences. So the rule holds only when the project has declared a per-change workflow. WebSearch was out of budget, and Hacker News, Lobsters and practitioner blogs are on denied hosts, so no 2024–2026 thread or survey was read; the freshness check rests on the current contributor docs and tool sources fetched on 2026-10-15.

## Evidence layer

Evidence for the one candidate rule (in a project that collects release notes per change, a change with a user-visible effect adds its entry in that change) comes mainly from official project documentation and the checks those projects run. All of it was fetched. Go's doc/README.md, CPython's devguide with patchcheck and bedevere, Twisted, pip, pytest, attrs, Hypothesis, GitLab, Kubernetes with prow, Electron with clerk, and LLVM (discretionary, "preferably as part of the commit") each ask the author of a user-visible change to add the note in that change. Each also exempts something: tests, docs, internal refactors, or fixes of unreleased bugs. Not all of them use a file. GitLab uses a commit trailer, Kubernetes and Electron a PR-description block, and Rust a label plus a tracking issue. So a check that looks only for a file in the diff misses those projects. The research is descriptive, not causal. Wu et al. (ICPC 2022, 909 RN issues from 722 repositories) find release notes miss information more often than they get it wrong, especially breaking changes. Their main reason is that a few people cannot understand all changes between versions, and from issue discussions they recommend spreading the work across contributors. Nath & Roy found 37% of 1,924 releases had empty notes. Moreno et al. found generated notes often included information missing from the manual ones. Imtiaz et al. found 38.5% of security releases had no note documenting the fix. No study measures whether per-change entries improve completeness, and that search is recorded below. The workflow choice itself is disputed. Common Changelog argues against an Unreleased section updated by each change. Node.js compiles notes at release. Conventional Commits, semantic-release and GitHub's generated notes build them from commits or PRs. So the rule needs its precondition: the project must have declared a per-change workflow. A local towncrier 26.9.0 run showed that presence checks do not test user-visibility. A test-only change failed the check, an empty .misc fragment passed it, and a branch that modified the news file skipped it.

## Spine — candidate rules in source order

1. **In a project whose documented workflow collects release-note entries per change, a change with a user-visible effect that the project's policy does not exempt adds its own entry in that change, in the form the project uses** — In a project whose documented workflow collects release-note entries per change, a change with a user-visible or operator-visible effect adds its own entry in that change, in the form the project uses. The form can be a release-notes or news-fragment directory (Go's doc/next, CPython's Misc/NEWS.d, a towncrier directory), a changelog file each change edits, a release-note block in the change description, or a Changelog trailer in the commit. A marker for the release team to write the note later does not count. A change the project's policy exempts needs no entry. Under CPython's and Kubernetes' policies these are documentation, test, build-infrastructure and strictly internal changes, a change an existing entry already covers, a fix to an unreleased change whose entry remains valid, and a revert of an unreleased change, whose entry is removed instead. Where the project compiles its notes at release time from commits or merged pull requests, the rule does not apply.
