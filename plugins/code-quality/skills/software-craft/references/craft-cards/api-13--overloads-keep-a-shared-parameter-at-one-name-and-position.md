# Overloads of one operation keep a shared parameter at the same position under the same name, and give parameters of similar type at one position one meaning

## Thesis
Where an operation has several overloads, signatures that share one name and differ in the number or the types of their parameters, a parameter that represents the same input in two overloads carries the same name in both and stands at the same position in every overload that takes it. A longer overload places the parameters it adds after the ones it shares with the shorter overloads, so that no shared parameter changes position. Where two overloads hold parameters of similar types at the same position, those parameters carry the same meaning.

## Rationale
Overloading on the number of parameters provides simpler versions of a routine, and a caller who needs the longer version most likely extends the call already written by appending the new argument. When the longer overload has put its added parameter before a shared one, the argument already written binds to the added parameter and the appended one binds to the shared parameter; where the parameters at those positions have the same types, the compiler accepts the call because the types match, and the call is a bug the overloaded interface caused. Short of such a bug, inconsistently ordered parameters make an overload set more confusing and put an additional burden on its users. The name and the position requirements chain: a parameter that represents the same input carries the same name, and parameters with the same name stand at the same position, so each input stands at one position in every overload that takes it. The rule keeps one left-to-right parameter order across the overload set, which a longer overload extends at its end, so that an argument appended to a written call fills the added parameter.

## Example
```typescript
bad:  function take(source: string, count: number): string;
      function take(source: string[], skip: number, count: number): string[];
      function take(source: string | string[], skipOrCount: number, count?: number) { ... }
good: function take(source: string, count: number): string;
      function take(source: string[], count: number, skip: number): string[];
      function take(source: string | string[], count: number, skip = 0) { ... }
```

## Limits
Parameters that represent different inputs may carry different names: the name requirement covers a parameter that represents the same input in two overloads. Overloads that take different types at one position to perform the identical operation on each type give that position one meaning and meet the rule. The rule reaches only signatures that share one name; related operations under different names, and code in a language without overloading, lie outside it. The requirements are recommendations that good library design may break in rare cases for a clear and compelling reason; where the project context or the overload set's documentation states such a reason, it rejects the finding. A variadic parameter stands last in every overload that takes it: the position requirement leaves it out, and a longer overload places its added parameters before it; the name requirement still covers it.

## Validator
Grep the added lines for an overload declaration: a signature that ends in a semicolon with no body, a signature under an overload decorator, or a public or protected method or constructor signature with one or more parameters. Open the file and collect every signature callers can call under the same name in the same type or module, leaving out a signature that only carries the shared body; when the name has a single callable signature, stop. For each parameter of an added or changed overload, find the parameters of the other overloads that represent the same input, by name or by role, and compare their names and, for a parameter that is not variadic, their positions. Then compare the overloads position by position and, where two of them hold parameters of similar types at one position, check from their names and documentation that both carry one meaning. Validator question: **Does an added or changed overload give an input it shares with another overload of the same name a different name or, for a parameter that is not variadic, a different position, or hold a parameter of similar type at a position where another overload's parameter means something else?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-13`, severity minor, `file`, `symbol`, `code` = the added or changed overload signature, verbatim, `fix` = that signature with each shared input under the name and at the position the other overloads give it and its added parameters after the shared ones, save a variadic parameter, which stays last, or, where that signature is shorter than the conflicting overload and no reordering of it puts a shared input where the conflicting overload holds it, the conflicting overload's signature with the parameters it adds after the shared ones, or, where its parameter of similar type means something else at a position another overload's parameter holds and no such reordering separates the two meanings, that signature under an operation name of its own, in the file's language, `rationale` = the conflicting overload's signature, the input, position or meaning that differs, and the call whose arguments would bind to other parameters or to the other meaning).
