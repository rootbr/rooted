# A routine's doc comment states the side effects, errors, panics, calling restrictions and special cases that apply to it and that its signature does not show

## Thesis
A routine's doc comment gives enough information to write a call to the routine without reading its code. Besides what the routine returns or, for a routine called for its side effects, what it does, the doc comment states each of the following that applies to the routine: its side effects, such as mutating one of its arguments; the errors it returns or raises, with the conditions that cause each, also where the signature declares the error type or the thrown exception; the scenarios in which it panics; the restrictions on when it can be called; for a routine the language marks unsafe to call, every invariant the caller is responsible for upholding; and the special cases of input whose result a caller needs to know, such as the result for a negative or not-a-number argument. Each item is written in prose or in the section or tag that the language's documented doc-comment convention gives it. A panic that occurs only in logic the caller supplies need not be listed. Where a failure only enforces a restriction the doc comment states, the documented doc-comment convention the code follows decides whether the failure is listed as well.

## Rationale
A doc comment describes the routine's calling syntax and its semantics, generally not its implementation, so that a caller can write a call without reading the routine's code; a routine that mutates one of its arguments as a side effect says so there. Where the signature declares an error type or a thrown exception, the doc comment still describes the kinds of errors and the conditions that cause them, which can help callers write code that handles the different kinds of errors in different ways; failing to document an exception that could be raised can mislead the routine's users. Documenting the scenarios in which a routine panics can help callers who do not want a panic avoid those situations, and an unsafe routine documents its safety preconditions so that its users can be sure they are using it safely. A study of over 6,000 exception stack traces from over 600 open-source Android projects, with a survey of 71 developers involved in those projects, indicated that developers are unaware of frequently occurring undocumented exception-handling behaviour. The items are a checklist of what a routine's users will be interested in knowing, and most doc comments do not need all of them, so each is documented where it applies. Documenting every conceivable panic is not necessary, especially one that occurs in logic the caller supplies, though when in doubt more panic cases are documented; and one convention leaves out an exception raised when the API the doc comment specifies is violated, because listing it would paradoxically make behaviour under violation part of the API.

## Example
```python
bad:  def withdraw(account, amount):
          """Withdraw money from the account."""
          if amount > account.balance: raise InsufficientFunds(amount)
          account.balance -= amount
good: def withdraw(account, amount):
          """Withdraw amount, lowering account.balance in place.

          Raises InsufficientFunds if amount exceeds account.balance.
          """
          ...
```

## Limits
A routine with no doc comment is outside the rule, which judges what a doc comment that is present states. Sections for these items can be omitted where the routine's name and signature are informative enough that a one-line doc comment describes it aptly. Conventions differ on a failure that only enforces a restriction the doc comment states: one leaves out an exception raised only because the documented API was violated, another documents the scenarios in which a routine panics, such as an index out of bounds, and one linter reports every exception the body raises directly that the doc comment omits; the documented doc-comment convention the code follows or the project's linter configuration decides, and where neither lists such failures, the stated restriction suffices. An exception that a callee raises, that the routine only lets pass and that its signature does not declare is likewise left to the convention: that linter reports only exceptions raised directly in the body, and notes that some conventions prefer such non-explicit exceptions omitted from the doc comment. A panic that cannot occur, such as an unwrap of a value the code itself guarantees present, may go unlisted; one linter lets each such panic be marked infallible. An override the code explicitly marks as one documents at least what materially refines its parent's contract or adds to it, such as an additional side effect; the override marker indicates that the rest of its documentation is found in the parent. Which methods of a type are safe for concurrent use may be stated once in the type's doc comment instead of in each method's. A write that is not relevant to the caller, such as a cache whose only effect a caller can observe is speed, is a detail of the implementation and is expressed in a comment alongside the code, not in the doc comment. Implementation details, such as the algorithm the current implementation uses, belong in comments inside the body, unless they matter to how the routine is used, as an asymptotic time or space bound that is particularly important to callers does. A doc comment that states an item wrongly or has drifted from the code, the checking of a restriction by an assertion, and a deprecation notice are outside the rule.

## Validator
Grep the added lines for a raise or throw statement, a panic call, an unwrap or expect call, a return type that declares an error or a thrown exception, an unsafe routine, and the opening of a doc comment. Open the file and take each routine that the change adds or changes and that carries a doc comment. Read its doc comment, its signature and its body, and list what applies to the routine and what the signature does not show: each assignment to, or mutating call on, an argument, state reached through an argument, or state outside the routine; each error the routine raises itself, returns or declares in its signature, a returned or declared error it propagates from a callee included, with the condition that causes it; each scenario in which it panics; each restriction on when it can be called that the body checks or relies on; for a routine marked unsafe, each invariant the caller must uphold; and each special case of input whose result a caller needs to know. Strike from the list a write that is not relevant to the caller, such as a cache or memo whose only effect a caller can observe is speed or a diagnostic log line or metrics counter that no calling code reads back; a panic that occurs only in logic the caller supplies, such as a callback or a formatting implementation; a panic that cannot occur; an exception a callee raises that the routine only lets pass and that its signature does not declare; a failure that only enforces a restriction the doc comment states, unless the doc-comment convention the code follows or the project's linter lists such failures, as a convention that documents panic conditions, such as an index out of bounds, in a section of their own does; for an override the code explicitly marks as one, an item its parent's doc comment states; and safety for concurrent use that the type's doc comment states. Count an item as stated when the doc comment says it in prose or in a section or tag of the convention; where the project context names a doc-comment convention or a documentation-linter configuration, apply its sections and exemptions. Validator question: **Does a routine the change adds or changes carry a doc comment that leaves out a side effect, an error and its condition, a panic scenario, a calling restriction, an unsafe-call invariant or a special case that the routine's body shows applies and its signature does not show?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-67`, severity minor, `file`, `symbol`, `code` = the routine's doc comment and signature, with the body line that shows the missing item, verbatim from the diff, `fix` = the doc comment with the missing item added in prose or in the section or tag the language's documented doc-comment convention gives it, in the file's language, `rationale` = which item is missing (side effect, error and its condition, panic scenario, calling restriction, unsafe-call invariant or special case) and the body line that shows it applies).
