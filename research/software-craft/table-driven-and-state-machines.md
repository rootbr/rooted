# Research note — Table-driven methods and state machines

Topic `table-driven-and-state-machines` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC18 (Code Complete 2nd ed. ch. 18 'Table-Driven Methods': direct access, indexed access and stair-step access tables); SW4.7 (SWEBOK Guide V4.0 ch. 4 'Software Construction' §4.7; SWEBOK V3 ch. 3 §4.7 'State-Based and Table-Driven Construction Techniques'); the 97 Things essay 'Thinking in States' (thing 84).

The canon holds two ideas. Code Complete ch. 18 and SWEBOK §4.7 choose data over logic: a lookup table (direct, indexed or stair-step access) in place of if and case logic, which SWEBOK says is simpler and easier to modify 'used in appropriate circumstances' and Code Complete keeps for logic that has grown complex. SWEBOK §4.7 and 97 Things #84 describe explicit state machines: named states, the state checked before acting, moves only to legal states, and tested transitions. The evidence is standards, tool rules and language documentation, not research. No study was found that measures table-driven code against conditionals or the defect effect of exhaustiveness checking. SonarSource S1479 (a map above thirty cases) and Ruff SIM116 (three equality branches) back the table, and the Go spec, Java Map, Python dict and NavigableMap documentation show that a table miss silently yields a zero value or null unless the code states it. Error Prone EnumOrdinal and Effective Go back keying a table by the member rather than its position, the Python FAQ backs closed handler tables against reflective dispatch, and clippy struct_excessive_bools and the Embedded Rust Book back one enumerated state over flags. IllegalStateException and the Rust book back refusing, or deliberately ignoring, an illegal event. Error Prone, PMD, typescript-eslint, the Rust book and PEPs 622 and 634 back exhaustive dispatch over an enumerated set, and local compiler runs confirm that a Java switch statement, a Go switch and a Python match fall out silently on an unhandled member. The industry disagrees on four points. Error Prone and typescript-eslint drop the default on a checked exhaustive switch, while Checkstyle and the Google TypeScript guide require one. Error Prone's own application-versus-library condition separates these, so that rule is carded. Three disputes have no sourced condition and stay pending: whether a computing catch-all may stand in for named members, whether transitions sit in one table or in each state (the Rust book weighs both), and whether repeated switches on one selector should give way to a single dispatch (Clean Code and Refactoring against Effective Java and Martin-Muratori).

## Formulation layer

Code Complete 2nd ed. ch. 18 is not openable here. I recovered its wording from reader transcriptions on GitHub: the chapter opening and §18.1, the §18.4 stair-step guideline headings, and the four checklist items. §18.1's "what to store" and §18.3 indexed access stay as paraphrases backed by reader notes. SWEBOK V3 §4.7 was fetched in full. For V4.0 only the table of contents was opened: it keeps §4.7 under the same title, and a third-party extraction shows it cites McConnell c18. 97 Things #84 was fetched and gives the state-machine positions: name the states, check the state before acting, move only to a legal state, test the transitions, and abort when the state is wrong. Seven practitioner texts were opened through GitHub-hosted copies or the authors' own GitHub sources: Pike, Raymond, Brooks via notes, Kernighan and Plauger via notes, Effective Java, The Pragmatic Programmer, and Wlaschin. They agree on data over logic and on tables for transitions. Within the canon, Clean Code G23 and Refactoring push conditionals toward polymorphism. McConnell offers tables as an alternative to both logic and inheritance, Fowler says most conditionals should stay plain, and Effective Java Item 34 and the Rust book treat switching on an enum as a legitimate choice with trade-offs. The style guides disagree on the runtime default: Google TS/JS require a default in every switch, Google Java requires every switch to be exhaustive by a default or full enum coverage, and Google C++ exempts enum switches. The aposd-vs-clean-code discussion has only one passing remark on switch statements, and nothing on tables or state machines. Harel, Heninger and Pooch were not opened: WebSearch was exhausted and no GitHub copy turned up (the papers-we-love link points to a denied host). They are left to the evidence layer.

## Reception layer

Reception here is mostly mechanical. Tool rule pages agree that a dispatch over an enumerated set must handle every member, but they split on whether an exhaustive enum switch should also carry a default. Error Prone UnnecessaryDefaultInEnumSwitch, and typescript-eslint when an option is set, treat that default as dead code that hides new members. Checkstyle MissingSwitchDefault, the Google TypeScript style guide and Sonar S131 for Go require the default anyway. Both camps accept a default for version or library skew, and Rust's #[non_exhaustive] forces a wildcard across crates. Python and Go have no exhaustiveness check on by default: PEP 622 rejected a runtime no-match error, pyright and mypy check only when switched on, and Go relies on the third-party exhaustive linter, which can also check that map literals are complete. So the rule must name the runtime default those languages need. Size rules push toward data over logic (Sonar S1479 suggests a map above 30 cases, Ruff SIM116 replaces if-chains with a dict, Pylint's too-many-branches fix is a dict lookup). PMD TooFewBranchesForSwitch and PEP 275 bound that push: a switch with few cases, or very little work per case, doesn't need a table. On state machines, statecharts.dev and 97 Things favour explicit states over boolean flags but admit state explosion, overkill in small code and YAGNI. Pike prefers state functions to a switch on an enumerated state, the Rust book weighs the State pattern's coupling against encoding states as types, and Martin and Muratori agree only that switches suit a stable set of types with growing operations. WebSearch was exhausted and HN/Lobsters are denied, so no thread or 2024-2026 survey was read; Code Complete, Muratori's performance article and Minsky are unfetched.

## Evidence layer

Documentation and tool rules strongly support exhaustive handling of an enumerated set in all five languages, but the mechanisms differ. Rust match and Java switch expressions fail to compile when a case is missing. TypeScript (a never check or typescript-eslint), Python (assert_never, mypy, pyright strict) and Go (the third-party exhaustive analyzer) check only when the code or configuration asks for it. Local compiler runs confirmed that a Java switch statement, a Go switch and a Python match all fall out silently on an unhandled member. The choice of data over logic rests on SWEBOK V3 §4.7, which conditions it on 'appropriate circumstances' and cites Code Complete ch. 18. Sonar S1479 (a map instead of more than 30 cases) and Ruff SIM116 back it as tool rules, and each language's documentation says what a lookup does on a missing key (Go zero value, Java null, Python KeyError). For explicit state machines the evidence is clippy struct_excessive_bools, the Rust book's state-pattern and typestate chapter, and Java's IllegalStateException. The papers could not be opened (WebSearch budget exhausted, publisher hosts denied): SWEBOK V4.0, Harel 1987, Heninger 1980, Heitmeyer et al. 1996, Pooch 1974 and Vessey & Weber 1986. The neverworkintheory bibliography gave only indirect research (Pan et al. on if-condition fixes) and one contrary diagram study (Cruz-Lemus et al. on composite states), and no study was found that measures table-driven code against conditionals or the defect effect of exhaustiveness checks. Sources disagree on three points. First, whether an exhaustive enum switch keeps a default: Error Prone and typescript-eslint say drop it so the compile-time check survives, except under library or version skew, while Checkstyle, Sonar S131 and the Google TS and Java guides require or accept one. Second, whether an illegal event is ignored (Rust book) or refused (IllegalStateException). Third, whether hierarchical states help at all (Harel against Cruz-Lemus et al.).
