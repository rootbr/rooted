# A test uses the real implementation of an in-process deterministic collaborator and replaces with a double only a dependency that reaches an external resource, slows the test or is hard to set up

## Thesis
A unit test builds the real implementation of every collaborator that runs in process, is deterministic and fast, and can be constructed in the test with ordinary setup, above all a class that encapsulates the system's domain concepts or rules. It reserves a test double (a mock, stub, spy or fake) for a dependency that makes testing difficult: one that reaches the network, a database, an external service, a file, the clock or another operating-system resource, one whose real execution makes the unit test slow, or one whose construction is too complex to set up in the test. A test that doubles an in-process, deterministic and fast collaborator it could build with ordinary setup breaks the rule.

## Rationale
A double of an in-process collaborator restates that collaborator's behaviour inside the test. When the real class changes, the double keeps the old behaviour, and the test stays green against code that no longer behaves as the double claims. Developers name keeping a mock compatible with the original class as a key challenge and report that mocking increases the coupling between test and production code; in a manual analysis of more than 300 changes to mock calls in four systems, 51% were forced by a change in production code, such as a renamed method, a changed parameter list or return type, or a renamed or refactored class. Doubling every collaborator also ties the test to the current implementation: a change to how a doubled method works inside forces its double to change, and the logic behind each double never runs under test. A dependency on the network, a database or the clock is different: it makes the test slow, nondeterministic or costly to set up, and a price rule that depends on the weekday passes on one day and fails on the next unless the clock sits behind a seam the test controls. The practice data follow the same line. Across 2,178 manually classified test dependencies, databases were doubled 72% of the time and web services 69%, against 36% for domain objects and 7% for standard-library classes such as strings and lists; developers report doubling dependencies that make testing difficult, preferring not to double classes that encapsulate domain concepts or rules, and using the real class whenever they fully control its input and output. The evidence is reported practice and official guidance; none of the cited studies compares the defect-detection or maintenance outcome of doubling an in-process collaborator against using its real implementation.

## Example
```typescript
bad:  const rules = { discountFor: jest.fn().mockReturnValue(5) };
      const checkout = new Checkout(rules as unknown as DiscountRules, new SystemClock());
      expect(checkout.total(cart)).toBe(95);
good: const clock: Clock = { now: () => fixedTuesday };
      const checkout = new Checkout(new DiscountRules(), clock);
      expect(checkout.total(cart)).toBe(95);
```

## Limits
- A domain object that is hard to set up or highly coupled, so that a real instance needs a long chain of constructed dependencies, may be doubled; developers report doing so, and also report doubling a domain object with complicated business logic, which this rule does not exempt. The practice data on domain objects show no clear trend: 36% doubled overall, about 30% to 47% by project.
- An in-process collaborator whose real execution makes the unit test slow, such as a long computation, may be doubled: developers interviewed name a class that performs a slow task among the candidates to double, and official guidance asks a unit test to run in milliseconds. Survey respondents double a slow class less often than the interviewees, 50.4% never or almost never.
- A third-party library that runs in process, such as a parser or a serializer, is often doubled in practice: third-party libraries, a category that mixes such parsers with network clients, were doubled 68% of the time, and developers report doubling a serialization library whenever the test does not target the integration. The rule keeps such a library real when it is deterministic and built with ordinary setup, following the official guidance that prefers a real object for a stateless in-process component; this departs from that reported practice.
- A fake with a working in-memory implementation of a database or service, or a double at the far end of a real transport, is a double of an external dependency and fits the rule. A larger test that exercises the real external dependency is outside this rule.
- Contested. One position doubles every collaborator with interesting behaviour, so that the doubles guide the discovery of role interfaces during test-first design; its evidence is an experience report with no measurement (DOI 10.1145/1028664.1028765), whose abstract calls the technique less interesting for isolating tests from third-party libraries than is widely thought. The other position uses the real implementation first; its evidence is official guidance that keeps a real object for an in-process, stateless component and admits a double for one that interacts with operating-system resources such as the network, plus the practice data above. The kind of dependency separates the cases: in process, deterministic and fast stays real; network, database, clock, another external resource or a slow computation may be doubled. Neither side has measured evidence that doubling in-process role interfaces improves or harms design, so a project whose documented convention is interaction-based (mockist, outside-in) test-first design with role interfaces tolerates the pattern, and that stated tolerance rejects the finding.

## Validator
Find in the hunk each line that creates or injects a test double: a mock, stub or spy factory call, a hand-written fake, stub or spy (an instance of a test-only type or a literal that stands in for the collaborator), a mock annotation, a patch of a module attribute, a generated mock or its expectation. Name the type, interface, function or module the double replaces, and open its production definition and the usages the scope reaches. Trace what the real implementation does, directly or through the dependencies it constructs: whether it reaches the network, a database, a file, a process, the environment, the clock, a random source or thread timing. Check whether a real instance can be built in the test with ordinary setup, through a constructor, a production factory or an existing test builder, rather than a long chain of constructed dependencies, and whether its own execution would make the unit test slow, such as a long computation. Check the project context for a documented interaction-based (mockist) testing convention. Validator question: **Does the test replace with a double a collaborator that runs in process, is deterministic and fast, reaches no network, database, file, clock or other operating-system resource, and can be built in the test with ordinary setup?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-01`, severity minor, `file`, `symbol`, `code` = the line that creates or injects the double of the in-process collaborator, `fix` = the test building the real collaborator through its constructor or production factory, keeping a double only for a network, database, clock or other external dependency or a slow computation, in the file's language, `rationale` = names the doubled collaborator, why it runs in process, is deterministic and fast, and that the double restates its behaviour and ties the test to the current split of the implementation).
