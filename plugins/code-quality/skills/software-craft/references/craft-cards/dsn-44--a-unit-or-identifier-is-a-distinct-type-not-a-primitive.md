# A quantity with a unit, or an identifier of one kind of entity, that shares a primitive representation with values of another meaning is declared as its own distinct type, not a bare primitive or an alias of one, so that the type checker rejects one where the other is expected

## Thesis
Where two values share one primitive representation but differ in meaning (a distance in miles and a distance in kilometres, a user id and an order id) and can reach the same parameter, field or routine, each meaning is declared as its own type, one the type checker treats as distinct from the other meaning and from the primitive. A value of one meaning passed where the other is expected, or a typed value of the bare primitive passed where either is expected, is then rejected at compile or check time. An alias of the primitive does not satisfy the rule, since an alias is the same type as the one it names; an alias that names the primitive intersected with a unique marker names a distinct type.

## Rationale
A primitive type says how a value is stored, not which of its interpretations the value carries: one floating-point type holds a quantity in miles or in kilometres, and a string or number can carry a special context, such as a user identification number, that other values of that primitive do not share. A checker that sees only the primitive accepts a value of either meaning where the other is expected, and an alias changes nothing, because the alias and its primitive are one type and mixing them draws no error. A physical unit inconsistency, a value in one unit combined with a value in another, compiles and can be difficult to detect. A distinct type moves the distinction into the checker: a routine whose parameter has that type cannot be called with a value of the other meaning or with a plain value of the primitive, the type's name states the unit of its values, and the checker's error at a mixed-up call reminds the programmer to perform the conversion, averting certain catastrophic bugs. The type can keep the primitive's underlying representation and operations, and a distinct type that exists only for the checker prevents logic errors with minimal runtime cost. How much the type protects depends on how the language makes it distinct. Where an untyped constant takes any type that can represent it, a bare literal is still accepted where the distinct type is expected, and an explicit conversion between two types with identical underlying types is accepted too, so a conversion written where a unit conversion was needed compiles. Where the runtime does not enforce type annotations, a distinct type declared for the checker is enforced only by the static type checker and is the plain value at run time, so it protects only code the checker runs on; in a study of public repositories that use such annotations the code rarely type-checked, one checker finding only 15% of 2,678 repositories type-correct, a figure that may partly reflect that checker's false positives. Where types are compared by structure, the distinct type is the primitive intersected with a unique marker, and a value takes that type through a type assertion placed where such a value is created, as in a function that converts the primitive into the type, and the assertion tells the checker the value has that meaning without verifying it; a value of the marked type can still be assigned to the plain primitive and lose the distinction.

## Example
```go
bad:  type UserID = int64
      func Cancel(user UserID, orderID int64) error { ... }
      var err = Cancel(orderID, userID)
good: type UserID int64
      type OrderID int64
      func Cancel(user UserID, order OrderID) error { ... }
      var err = Cancel(userID, orderID)
```

## Limits
A value whose primitive carries one meaning in the code it reaches, with no value of the same primitive in another unit or identifying another kind of entity passing through the same parameters, fields or routines, is outside the rule. The rule names the effect, not the mechanism: a defined type, a single-field wrapper type, a type marked by intersection and a distinct type declared for a static checker each satisfy it when the checker rejects a value of the other meaning in its place; where types are compared by structure, two wrapper types of the same shape accept each other's values, so a wrapper there satisfies the rule only when it carries a unique marker. Distinct types separate meanings and do not check the units that arithmetic produces: where the type keeps its primitive's operations, a length multiplied by itself is typed as a length or as the primitive, so a squared length added to a length is still accepted, and where the type's operations take and return the primitive, as for a distinct type declared for a static checker or a type marked by intersection, a length in one unit added to a length in another is accepted too. A value of the distinct type may still be accepted where the plain primitive is expected, as a distinct type declared for a static checker is a subtype of its primitive; the rule asks only that the other meaning and the plain primitive be rejected where the distinct type is expected. Code that no static type checker examines is outside the rule, because no declaration there makes a checker reject the mix-up. A tolerance stated in the project context for primitive identifiers or quantities, such as generated code or types that mirror an external schema, rejects the finding. A period or a point in time that an interface cannot carry as a time type, held in a number whose name states its unit, is outside the rule.

## Validator
Grep the added lines for a parameter, field or variable whose name carries a unit or an identifier suffix and whose declared type is a bare primitive, and for an alias declaration that names a primitive. Name the meaning each one holds: the unit, or the kind of entity it identifies. Open the callers of the routine and the users of the field or alias across the repository, and the other declarations of the same module, and trace whether a value of the same primitive with another meaning reaches the same code: a second parameter or field of that primitive holding another unit or another kind of entity's identifier, a caller passing a value computed in another unit or read from another kind of entity, a neighbouring routine taking the other meaning. Check whether the declared type is one the checker treats as distinct from its primitive; an alias of the primitive and the primitive itself are not, and an alias of the primitive intersected with a unique marker is. Skip code that no static type checker examines and code a tolerance in the project context covers. Validator question: **Does an added declaration hold a quantity with a unit, or an identifier of one kind of entity, as a bare primitive or an alias of one, while a value of the same primitive with another unit or identifying another kind of entity reaches the same code?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-44`, severity minor, `file`, `symbol`, `code` = the added parameter, field or alias declaration quoted verbatim from the diff, `fix` = a distinct type declared for that meaning and for the confusable meaning, and the declaration rewritten to use it, in the file's language, `rationale` = the confusable value of the same primitive, its meaning, and the caller or declaration through which it reaches the same code).
