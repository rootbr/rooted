# Added code meets every layout requirement of the project's style guide and otherwise matches its file's layout or the guide's recommendation

## Thesis
Each added or changed line meets every layout requirement of the project's style guide (indentation, line length and line breaking, blank lines, brace and statement placement, whitespace and alignment), also where the surrounding code breaks that requirement, and a new file meets those requirements throughout whatever the style of the other files in its package. On a layout point the guide does not require, because it only recommends a form, permits a form without requiring it, or says nothing, the added line takes the form the rest of its file already uses for that point or the form the guide recommends, rather than a form of the author's own that neither uses.

## Rationale
Coding standards for layout and indentation are among the development standards whose application during construction helps a project achieve its objectives for efficiency, quality and cost. Consistency with surrounding code has limits: it applies more heavily locally and on choices the guide leaves unspecified, and is not generally a justification for writing in an old style without considering the benefits of the new one or the codebase's tendency to converge on newer styles. Local style matters too: code added to a file in a form drastically different from the existing code around it throws readers out of their rhythm when they read it, and disparate or conflicting styles within one codebase cause maintenance overhead, uncertainty and cognitive dissonance, which can contribute to lower velocity, painful code reviews and bugs. Programmers do not always follow a project's coding conventions, and project members care deeply about adherence: one third of reviews of changes contain feedback about coding conventions, and programmers are often unaware of the conventions because inferring them requires a global view that aggregates the many local decisions programmers make; of 18 patches that a tool learning a codebase's style to suggest revisions toward stylistic consistency generated for five open-source projects, 14 were accepted. Of 407,097 snippets of at least six statements posted to a programming question-and-answer site under one language's tag, 93.87% contained style violations, 0.7 per statement on average; among posts with vote scores between -10 and 20, a post's vote score correlated with the average violations per statement of its snippets at r = -0.87.

## Example
```java
bad:  // guide requires braces, is silent on alignment; this file omits braces, never aligns
      if (items.isEmpty()) return;
      int    count = items.size();
      String label = prefix + count;
good: if (items.isEmpty()) {
          return;
      }
      int count = items.size();
      String label = prefix + count;
```

## Limits
The rule turns on whether the guide requires the point. Where the guide requires it, the requirement binds: the guide is the absolute authority on what it requires, a brand-new file follows it regardless of the style of other files in the same package, and new code in a file that does not follow the guide is as consistent as possible with that file without violating the guide. Where the guide states how its wording maps to requirement keywords, that mapping classifies its points; a guide that states none is read by the mapping one cited guide states for itself, in which must, must not and an imperative or declarative statement state a requirement, and should, prefer and avoid a recommendation; a form a guide permits but never requires is no requirement, and a formatting choice a guide shows only in its examples is not one of its rules where the guide declares its examples non-normative. A guide that calls its points recommendations and counts consistency with surrounding code that also breaks a guideline as a good reason to ignore it makes its points recommendations in this sense. Where the guide only recommends, the sources part and either form meets the rule: one side calls the choice a judgement call biased toward the recommendation unless the local inconsistency would be too confusing; the other ranks consistency within one module or function above consistency with the guide. Where the guide is silent, a purely stylistic point is a matter of preference bounded by what is already there: the added line matches its file, the other files in its directory are the next reference, and where neither shows an established form the author's choice stands; where the project names no style guide, every point is of this kind. Lines the change does not otherwise touch are outside the rule: code that predates a guideline and has no other reason to be modified keeps its style, existing code need not all be changed to meet the current guide, and the rule never asks for a reformat of untouched lines. Code generated by the build process is outside the rule. Where the project context records that the project brings its code under a guide a package or more at a time, so that no package mixes two styles, the guide is not yet in force in a package the migration has not reached, and added code there matches the package. The rule weighs physical layout only: identifier case and the content of comments are outside it. A layout tolerance or exemption stated in the project context or in the guide itself rejects the finding, as where the guide says a form it permits need not be kept even where existing code already uses it. No lexical pattern or structural signal marks a line whose layout departs from the guide or from its file, so the rule carries no trigger and the finder reads every added or changed line.

Code a change moves from one file to another as its base version had it counts as a line the change does not otherwise touch: it keeps its layout in the move, style violations included, and a layout fix to it goes in a separate change.


Hand padding that puts tokens into columns is not an established form an added line must follow: where a file aligns by hand and no formatter emits the columns, the added line may take the language's ordinary spacing.
## Validator
Read the project context, the repository's contributing or style documentation and any checked-in formatter or linter configuration, and name the style guide the project uses; where none is named, treat every point as one the guide leaves open. For each added or changed line, list the layout points it shows: indentation, line length and where a long line breaks, blank lines, brace use and placement, statements per line, whitespace around operators and alignment. Classify each point by the guide's wording, read by the mapping of wording to requirement keywords the guide states for itself where it states one and otherwise as follows: a requirement (must, must not, an imperative or declarative rule), a recommendation (should, prefer, avoid), a form permitted but not required, or not covered, and treat every point of a guide that calls its points recommendations and counts consistency with surrounding code that also breaks a guideline as a good reason to ignore it as a recommendation; a choice shown only in the guide's examples is not a rule where the guide declares its examples non-normative, and a point on which the guide says a permitted form need not be kept where existing code uses it is skipped. For a requirement, compare the line with the guide whatever the surrounding code does; for a new file, compare every line. For any other point, open the file at HEAD and note the form its existing code uses for that point, or, where the file is new or shows no established form, the form the other files in its directory use; compare the line with that form and with any form the guide recommends, and where neither exists the line's form stands. Skip lines the change does not otherwise touch, generated code, a package the project context records as not yet migrated, and identifier case and comment content. Validator question: **Does an added or changed line break a layout requirement of the project's style guide, or, on a point the guide does not require, take a form that matches neither the established form of its file (or, where the file has none, of its directory) nor the guide's recommendation, when at least one of those exists?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-59`, severity suggestion, `file`, `symbol`, `code` = the added or changed line whose layout departs, quoted verbatim from the diff, `fix` = that line laid out as the guide requires or, on a point the guide does not require, in the form its file already uses (where the file is new or has no established form, the form of the other files in its directory) or in the form the guide recommends, in the file's language, `rationale` = the layout point, whether the guide requires it, recommends it or leaves it open, and the form the guide, the file's existing code or its directory sets).
