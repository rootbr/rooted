# Research note — Control flow

Topic `control-flow` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC14 (Code Complete 2nd ed. ch. 14 'Organizing Straight-Line Code'); CC15 ('Using Conditionals'); CC16 ('Controlling Loops'); CC17 ('Unusual Control Structures': multiple returns, recursion, goto); CC19 ('General Control Issues': boolean expressions, compound and null statements, deep nesting, control structures and complexity).

Code Complete chs. 14-17 and 19, with Refactoring, Clean Code, The Practice of Programming and A Philosophy of Software Design, agrees that control flow keeps the normal path prominent, covers every case of a branch, gives each loop a reachable exit and an untouched counter, keeps boolean conditions simple and positive, and holds nesting shallow. Industry checks most of this mechanically, and tool rule pages and official language and style documentation back 18 cards: an unmatched value in a switch or else-if chain, case fall-through, branches that repeat code, switch for a chain on one value, loops that cannot stop or repeat, loop control variables, element iteration over hand-written bounds, mutation of the collection being iterated, an else after an exiting branch, explicit returns on every path, recursion that terminates within the stack, boolean literal comparisons, truthiness on valid falsy input, complex conditions given names, positive conditions, nested conditional expressions, assignment in conditions and nesting depth. The disagreements are sourced, and three of them separate on a condition. A default on a fully covered enum or union switch (required by Checkstyle and Google TypeScript style, rejected by Error Prone, typescript-eslint and Sonar's own exception) depends on whether the value set is closed and checked. An else after return (dropped by the Go guides, ESLint and Ruff, kept in PEP 8's own Correct example and in clippy's known problems) depends on whether the else holds the normal path. Implicit truthiness (PEP 8 against the TypeScript handbook) depends on whether a falsy value is a valid input. Four stay pending without a separating condition: single exit (PMD OnlyOneReturn, Checkstyle ReturnCount) against early return (C++ NR.2, the Go guides); continue guards (C++ ES.77 marks them bad, Uber's Go guide good); labelled jumps against extraction (the Rust book and Go guides against ESLint no-labels and Sonar S1119, Ousterhout against Martin); and complexity limits (Sonar and PMD against Checkstyle's own documentation, clippy's maintainers and Scalabrino et al.). The research that could be opened is thin, all abstracts relayed through neverworkintheory: Ajami et al. (loops with unusual bounds cause many more errors; only some negations make a predicate harder), Scalabrino et al. (none of 121 metrics captures understandability) and Nagappan et al. (goto in C serves error handling and cleanup). McCabe 1976, Munoz Baron et al. 2020, Johnson et al. 2019 and Gopstein et al. 2017 stayed unopened. The bounds for nesting depth (3 to 5), boolean operators (3 or 5) and complexity (10 to 30) are tool conventions, not measured thresholds. Goto belongs to one language, and braces, empty statements, unreachable code and return in finally belong to neighbouring topics.

## Formulation layer

The canon broadly agrees. Keep the normal path prominent and unindented. Simplify boolean conditions and state them positively, by naming predicates and never comparing against boolean literals. Cover every case of a branch (else or default, no silent fall-through). Give each loop one entry, one job, an obvious exit and an untouched index. Hold nesting to about three levels, and treat a high decision-point count as a signal to split. Opened directly from GitHub raw: the aposd-vs-clean-code discussion, 97 Things, SWEBOK V3 ch. 3, Google eng-practices, PEP 8/20, the Python tutorial and sys docs, Effective Go, Go Code Review Comments, the Google Java/Python/TS/Go guides, uber-go, the TypeScript handbook, the Rust book ch. 3.5, C++ Core Guidelines ES.70-87 and NR.2, the Linux kernel coding style and Sonar S3776. Code Complete, Clean Code, Refactoring (1st ed.), The Practice of Programming and APoSD were reachable only through third-party GitHub reading notes (relayed). Code Complete's else-clause statistic, endpoint, nesting and loop-length guidance, the section on multiple returns, the forms of boolean expressions, and the complexity thresholds are unfetched paraphrases from memory, as are Dijkstra 1968, Knuth 1974, McCabe 1976 and Refactoring 2nd ed. The canon disagrees on six points. Single exit versus early return: CC17.1 and PMD OnlyOneReturn against C++ NR.2, Clean Code, Fowler and the Go guides. Normal path first in an if-else (CC15.1) versus errors first with an early exit (Go guides). goto: Dijkstra, 97 Things and C++ ES.76 against the Linux kernel's cleanup gotos and Knuth. Labelled continue and the splitting or extraction of loop bodies: Martin, CC16 and Fowler's Split Loop against Ousterhout's entanglement argument and his measured 3-4x slowdown. Implicit truthiness: PEP 8 and Google Python against the TypeScript handbook, though all agree integers are compared explicitly. Whether cyclomatic complexity measures quality at all: CC19.6 against Checkstyle's own documentation.

## Reception layer

I opened about 60 tool rule pages, style guides and practitioner texts through raw.githubusercontent.com. WebSearch had no budget left and github.com issue threads (for example rust-clippy#3793) returned 403, so no Hacker News or Lobsters thread and no 2024–2026 practitioner survey could be read. Recent openable material (Google Java Style's exhaustive-switch wording, PEP 765, the Prettier 2023 ternary post, the golangci-lint v2 reference config, ESLint's frozen-rule policy) is the only freshness check. Industry largely agrees on a few points: guard clauses and early return to reduce nesting (Go, Google, Uber, LLVM, Mozilla, Rust let-else), no implicit switch fall-through (ESLint recommended, Error Prone, TypeScript compiler, Linux kernel, Go's explicit fallthrough), no comparison against boolean literals (PEP 8, staticcheck, clippy, Checkstyle, Ruff) and catching loops that cannot terminate. Every one of these has typed exceptions: nullable or union booleans, NumPy `__eq__`, exhaustive enum switches. The open disputes are: complexity metrics and their thresholds (defaults range from 7 to 30; clippy's maintainers disown cognitive complexity; Scalabrino et al. found no metric captures understandability; Muñoz Barón et al., from memory and unopened here, report partial validation), single exit versus early return (PMD OnlyOneReturn and Checkstyle ReturnCount against the Go, LLVM and Linux guides), else after return (clippy says 'some may prefer to keep the else'; PEP 8's own Correct example keeps it), default in an exhaustive enum switch (Checkstyle, Sonar and ESLint require it; Error Prone, PMD and LLVM say it hides missing cases), labelled break and continue (Ousterhout defends them, Martin calls them 'awful', Google Go style prescribes them), goto for cleanup (Linux kernel and Nagappan et al. against Kimchi and Dijkstra), nested ternaries (ESLint, Sonar and Airbnb against Prettier's Rattray) and always-brace (Mozilla against LLVM). McCabe 1976, Muñoz Barón 2020, Fowler's Refactoring, Holzmann's Power of Ten, Dijkstra 1968 and Knuth 1974 are from memory and unfetched, and none may anchor a card alone.

## Evidence layer

Static-analysis rule documentation and official language and style documentation back most of this topic. All of it was opened through raw.githubusercontent.com: ESLint, typescript-eslint, Checkstyle, PMD, Error Prone, Ruff, clippy, rustc, staticcheck, go vet and SonarSource, plus the Go spec, Effective Go, the Google Go, Java, TypeScript and Python style guides, PEP 8 and PEP 765, the Rust book and the Python, Go and Rust stack-limit docs. It covers complexity limits, nesting depth, guard clauses, switch default and fallthrough, boolean simplification, braces, loop-variable and loop-bound bugs, recursion termination and labels. Only four papers could be opened, all as abstracts from the neverworkintheory repository: Ajami et al. (for loops are harder than ifs; some negations hurt; unusual loop bounds cause many more errors), Nagappan et al. (goto in C is used mostly for error handling and cleanup and does not appear harmful), Scalabrino et al. (none of 121 metrics, complexity included, captures understandability), and the atom-finder classifier list for the atoms-of-confusion work. McCabe 1976, Muñoz Barón et al. 2020, Johnson et al. 2019 and Gopstein et al. 2017 stay unfetched: WebSearch was exhausted and no GitHub copy was found, so they must never be a card's only anchor. The sources disagree on four points. Complexity thresholds differ: cyclomatic 10 in Checkstyle and Ruff against 20 in ESLint; nesting depth 1, 3, 4 or 5 depending on the tool. Clippy and Scalabrino et al. deny that the metrics measure understandability. Single exit (PMD OnlyOneReturn, Checkstyle ReturnCount) conflicts with guard clauses (ESLint no-else-return, Effective Go, Google Go style), and no research on either side was found. An always-present default case (Checkstyle, Google TS) conflicts with leaving out the default on an exhaustive enum or union switch (Error Prone, typescript-eslint). Finally, Python's style guide prefers implicit truthiness, while Rust forbids it and the atoms-of-confusion list includes implicit predicates.

## Spine — candidate rules in source order

1. **When statements must run in a fixed order, the code shows the dependency, through each step taking the previous step's result, through routine names or through a comment, and never leaves it in hidden shared state** — Statements that must execute in a particular order make the dependency visible: a step takes the previous step's result as a parameter or returns what the next step consumes, routine names state the dependency, or a comment documents an unclear one. A routine that only works after another routine has initialized shared state does not leave that coupling hidden. The canon formulates the rule, but no fetched tool rule, official document or study states it; the openable checks near it measure the distance from a declaration to its first use, which variables-scope-and-numerics owns.

'Slide Statements' (unfetched)
