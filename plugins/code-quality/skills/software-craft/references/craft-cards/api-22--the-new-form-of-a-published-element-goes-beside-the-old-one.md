# Removing, renaming or changing the parameters or return type of a published element in place breaks its callers, so the new form is added beside the old one

## Thesis
A change to a published element — a function, method, type, field or module that code outside its own codebase imports, calls or names — leaves every existing use of it valid. Where the change would remove, rename or move the element, add a parameter that existing calls would have to supply, remove or reorder parameters, change a parameter's type or the return type, or rename a parameter that callers can pass by name, the change adds the new form beside the old one instead: a new function, method, overload or type, or the old name re-exported or forwarded from the element's new location. Where a function's type is its exact signature and code can hold the function as a value of that type, any change to the signature counts, an added variadic parameter included. The old form keeps working as advertised; to avoid copying code, it calls the new one. Where the old form is obsolete, it is marked deprecated and points to the new form that replaces it. An added overload takes over no call that was bound to an existing overload and gives it different behaviour.

## Rationale
The owner of a published element can do nothing about the code already using it, and since that set of users is open-ended and nobody knows which aspects of the element they count on, the only safe assumption is that every aspect matters to some of them. Removing, renaming or moving the element, adding or deleting a parameter, or changing a parameter's type or the result type therefore breaks compatibility with existing users: depending on how they are checked and built, they stop compiling, a compiled user no longer links and runs against the new release, or the import or the call fails at run time. A rename that looks minor is no exception: no user can annotate its code in advance to avoid the breakage, nor can the breakage be kept from affecting the code that depends on it. Renaming a parameter breaks the calls that pass that argument by name and the late-bound calls. A reorder of positional parameters can break users silently: each call still passes the number of arguments the routine expects and raises no immediate error, but parameters very often have specific meanings, so the call leads to incorrect behaviour. Call compatibility is not enough either: where a function's type is its exact signature, code that stores the function in a variable of the old type fails to compile once a parameter is added, even a variadic one, so no change to such a function's signature is backward compatible. A break costs every user: all of them have to be revised, or at least reviewed, anyone upgrading has to upgrade all of them at the same time, and the overall cost of invalidating existing code is usually very high. Carrying the break in a new major version is hard on users as well: they have to find the new version, learn a new API and change their code, and some may never update, which leaves two versions to maintain, so a compatible change is usually the better course. When a dependency release introduces breaking changes, dependent packages may not build anymore: in one package ecosystem, around 12% of the dependent packages and 14% of their releases were impacted by a breaking change during updates to non-major releases of their dependencies, that is, minor and patch releases, which in principle should be backward compatible. Adding the new form beside the old one leaves every existing call on the old form and lets users migrate at their own pace, unless the addition captures an existing call or obliges an outside implementation of an interface or trait to supply it; the old form calling the new one avoids copying code, and marking the obsolete form deprecated points new users at its replacement while it keeps working as advertised. An added overload breaks the existing calls that, recompiled or late-bound, now bind to it instead of the overload they were bound to, where it behaves differently. A member added without a default to an interface or trait that outside code implements breaks every such implementation, so there the new form goes on a new interface, checked for at run time wherever the old one is used.

## Example
```python
bad:  def load_items(source): ...    # renamed in place: read_items(source) no longer exists
good: def load_items(source): ...
      def read_items(source):
          warnings.warn("read_items is deprecated; use load_items", DeprecationWarning, stacklevel=2)
          return load_items(source)
```

## Limits
The rule reaches only an element of the published interface, which code outside the codebase can use. An element outside it — a private name, a name in an internal, test, example or experimental package, or one the project's convention marks as private, such as a leading underscore — and an element whose every user lives in the codebase the change updates can change in place, its name changed or its parameters reworked, provided every place it is used within the codebase is fixed up at the same time; where the codebase plays every role itself, its interface changes coincide with its own releases, which makes it feasible to change its own code to match. Compatibility is owed from the release that first makes an element public, so an element that no release has published yet has no existing users outside the codebase to break. Ecosystems differ on breaking changes, from a practice of never permitting them to one that accepts them when the version number signals them clearly: a project whose stated policy releases a breaking change under a new major version or a new module path rejects the finding when the change carries that signal, and so does a version 0.y.z, under which anything may change at any time, unless the project treats the leftmost non-zero component of a 0.y.z version as its breaking-change indicator, a common practice that one package manager's caret range presumes by admitting 0.2.5 but not 0.3.0 for 0.2.4: there a breaking change carries the signal only when it bumps that component; the later removal of an old form that an earlier release shipped working and marked deprecated is decided by the project's stated policy as well: one removes it only in a new major release, after at least one minor release that carries the deprecation, another once it has kept working as advertised for a couple more releases, and a removal that the project's stated policy admits rejects the finding. A parameter rename is outside the rule where callers can pass arguments only by position and no call binds late by name: one platform's rules class a parameter rename as binary compatible, and another's give named arguments and late binding as the reasons it breaks. A parameter added with a default value can avoid the breakage where the language supplies defaults; a policy that also guards users compiled against the previous version counts adding any parameter as a break, and a project context that states such a policy extends the finding to it. Policies also differ on a parameter or return type generalized so that every existing use still fits: one classes a type generalized to a type parameter that existing uses instantiate to the original type as a minor change, accepting the type-inference failures it can cause, but classes the same change to a method of an interface or trait that code outside the codebase may implement as major, since it can break the implementations, while one that guards compiled users disallows changing a parameter's or a field's declared type even from a narrower integer type to a wider one; the project's stated policy, or its ecosystem's, decides that case. Where the element is a member of an interface, trait or abstract type that code outside the codebase may implement, a member added beside it breaks every outside implementation unless it carries a default body: there the new form goes on a new interface that the code needing it checks for at run time, or, where the language and the project's policy accept a member added with a default body, it carries a default body that calls the old member, which existing implementations already supply, rather than the old member calling the new one. A project's public interface is what the project says it is: a project context that declares an element internal, whatever its visibility, rejects the finding.

## Validator
Grep the hunk for an added or a removed declaration of a function, method, type, field or exported name. Decide whether the element is published: exported or public in code that others import as a library, package or module, and not private, internal, underscore-prefixed — a special name with two underscores on each side, such as a constructor, is public — or in a test, example or experimental package. Where the project tags its releases or keeps a changelog, check that a released version carried the element in its base form; an element added since the last release is outside the rule. Open the base version with `git show <base_sha>:<path>`, and for a move the file the element left, and find the element's previous form: a name or location that no longer resolves, a parameter that existing calls would now have to supply, a removed or reordered parameter, a changed parameter or return type, a renamed parameter where callers can pass arguments by name, or, where a function's type is its exact signature, any change to that signature. Check whether the old form still exists and still works — kept and calling the new form, or re-exported or forwarded from the new location — and, for an added overload, whether an existing call would now bind to it with different behaviour. Set aside an element whose every user the same change updates, a change the project's stated policy releases under a new major version or module path, a change in a version 0.y.z, except where the project treats the leftmost non-zero component as its breaking-change indicator and the change does not bump it, the removal of an old form that an earlier release shipped marked deprecated where the project's stated policy admits its removal in this release, and a type generalized so that every existing use still fits, on an element that no code outside the codebase implements, where the project's or its ecosystem's policy classes that as compatible. Validator question: **Does the change remove, rename or move a published element, or change its parameter list, a parameter's type, the return type or the name of a parameter callers can pass by name, without leaving the old form working beside the new one, or add an overload that existing calls would now bind to with different behaviour?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-22`, severity major, `file`, `symbol`, `code` = the changed or renamed declaration quoted verbatim from the diff, `fix` = the new form added beside the old one, with the old form kept working by calling it, or re-exported from the new location, and marked deprecated with its replacement named where it is obsolete — for a member of an interface or trait that outside code implements, the new member on a new interface that the code needing it checks for at run time, or with a default body that calls the old member — in the file's language, `rationale` = the element's previous form in the base version and the existing uses outside the codebase that the change breaks).
