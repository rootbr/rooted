# A remote call is retried at one layer of its call path, and a retry wrapped around a client or callee that already retries turns the inner retries off

## Thesis
Along the call path of one remote operation — the code that issues it, the client library or channel it calls through, and any callee in the same codebase that calls on in turn — one layer retries the operation. A layer that brings its own retry around a client, channel or callee that already retries turns the inner retry off through the switch the client offers, or leaves the retry to the inner layer and drops its own. This holds in most cases; where a specific requirement calls for retries at more than one stage, every stage's policy limits its number of retries and its delay periods, and the consequences of the stacking are understood. The rule counts the retries of a request that may have reached the callee's application logic, and it does not decide which layer owns the retry.

## Rationale
When one component calls another that then calls the target service, a retry count of three on both calls adds up to nine retry attempts in total against the service. A task with a retry policy that invokes another task with its own retry policy adds an extra layer of retries that can add long delays to the processing. The inner retry can be one the calling code never asked for: many services and resources implement a built-in retry mechanism, and client libraries are advised to make client-side retry transparent to the user, who should not have to opt in to it explicitly. The same advice requires a way to disable client-side retry altogether, and a channel's retry support can be disabled entirely so that a library that wraps the client with its own retry implementation avoids having retries take place at both layers. An HTTP client should not automatically retry a failed automatic retry.

## Example
```rust
bad:  let client = Client::builder().max_retries(3).build();
      let reply = with_retries(3, || client.send(&request))?;
good: let client = Client::builder().max_retries(0).build();
      let reply = with_retries(3, || client.send(&request))?;
```

## Limits
A lower layer's retry of a request that never reached the callee's application logic sits beneath the owning layer and does not count against the rule. The documented case is a channel's transparent retry: regardless of any configured retry policy, a channel may retry a call that never left the client, without limit, or a call that reached the server library but was never seen by the server application logic, once, because such requests have not made it to the server application logic and are always safe to retry; the second kind still adds load to the network. Where the end points must provide their own retries for correctness anyway, a communication system's internal retry beneath them only reduces how often the end points retry and has no effect on the correctness of the outcome. A retry that resends a request the callee's application logic may have seen runs at one layer: a library that wraps a channel with its own retry implementation is the case for which the channel's retry support can be disabled entirely. Retries at more than one stage are a documented project tolerance when a specific requirement calls for them and every stage's policy limits its retries and its delay periods; a project context that records such a requirement rejects the finding. Which layer owns the retry is outside the rule, because published guidance points both ways: one guide prefers a client library's built-in retry mechanism when one is available, unless specific and well-understood requirements make a different retry behaviour more suitable; another advises implementing retry logic only where the full context of a failing operation is understood and notes that it might be better to configure a lower-level task to fail fast and report the reason for the failure to the task that invoked it; a channel's retry design means retry logic to live only in the channel and not in the libraries that wrap it; and the end-to-end argument does not say where an early retry belongs, since either layer can do that performance-enhancement job.

## Validator
Grep the hunk for a retry: a retry annotation or decorator, a retry helper or a loop with an attempt count, a retry policy or configuration object, or a client, channel or adapter setting that turns retries on or sets their count. Open the callers of the changed symbol and the code the retried call goes through: how the client or channel is built and configured, including a default that retries, and any routine in the repository that the call reaches and that retries in turn. Trace the call path of the operation and list each layer that retries it. Leave out a lower layer whose retry is limited to requests that never reached the callee's application logic, such as a channel's transparent retry of a call that never left the client; a stacking that the project context records as a requirement, with every stage's retries and delays limited; and a callee in another service whose retry policy the repository does not show. Validator question: **Does the change add or turn on a retry at one layer of a call path on which another layer visible in the repository also retries the same operation beyond requests that never reached the callee's application logic, with neither layer's retry turned off?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-35`, severity minor, `file`, `symbol`, `code` = the added retry, quoted verbatim from the diff, with the other layer's retry it stacks with named by file and line, `fix` = one layer keeping the retry and the other's retry turned off through its client switch or removed, in the file's language, `rationale` = the layers that retry the same operation and the number of attempts their product can reach against the callee).
