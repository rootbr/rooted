# A definition takes a type parameter only when it is used with more than one type or is a library's public API, and code used with one type is written for that type

## Thesis
A type parameter on a routine or a data type is reserved for code that serves, or is about to serve, more than one type, where the copies written for each type would differ only in the types they use. Where every use of the definition is in the codebase and only one type is instantiated in practice, the definition is written for that concrete type and the parameter is added when a second type arrives; a body that does not care about the type of its elements is not reason enough on its own. A parameter whose bound admits only one type is written as that type, whoever its callers are. A library's public API, whose callers outside the codebase choose the type, may take a type parameter bounded by the assumptions its body needs to make about its arguments.

## Rationale
The case for a type parameter is the same code written several times, where the only difference between the copies is the types they use; one parameterized definition then stands in for the copies. Short of that, the parameter is added complexity: in many applications a conventional approach using the language's existing features, its built-in collections and interfaces, works just as well without it, and heavy use of type parameters can make a signature more difficult to read and understand. A program started by defining type-parameter constraints, rather than by writing its routines, is probably on the wrong path. Type parameters are easy to add later, when it is clear that they will be useful, and adding polymorphism later is straightforward compared to removing an abstraction found to be unnecessary. A parameter whose upper bound is a class that cannot be extended is not generic at all, because it accepts one and only one type, and using that concrete class directly is simpler; one type-hint specification disallows the like case of a type variable with a single constraint. A less flexible but simpler and more readable definition may ultimately be the wiser choice.

## Example
```python
bad:  class Registry[T]:
          def add(self, key: str, item: T) -> None: ...
      orders = Registry[Order]()  # the only instantiation
good: class OrderRegistry:
          def add(self, key: str, item: Order) -> None: ...
      orders = OrderRegistry()
```

## Limits
The guidance is contested, and what separates the cases is whether every instantiation of the definition is visible in the codebase. Where it is, as in application code, an internal routine or an unexported type, the concrete-first rule applies as its source conditions it, on only one type being instantiated in practice. Where the definition is a library's public API and callers outside the codebase choose the type, a library API guideline drawn from building a standard library and other published packages prefers a type parameter bounded by what the function needs over a concrete collection, for example a bound on being iterable when the function only iterates, because the fewer assumptions a function makes about its inputs, the more widely usable it becomes; such a parameter passes. The concrete-first side grants the same case: replacing a specific element type with a type parameter can produce a data structure that other programs can use. The library guideline in turn lists signature verbosity among the disadvantages of generics. A definition that the same change instantiates with a second type passes. A project context that declares a module a library published for other codebases rejects a one-type finding on that module's exported definitions; a bound that admits only one type is flagged there all the same. The rule does not judge whether a type parameter or an interface with dynamic dispatch fits code that several types share, how wide a bound should be, a type parameter that appears only in a return type or not at all, a top type standing in for a parameter, or near-duplicate code across types; those are judged by their own rules.

## Validator
Grep the added lines for a declaration that introduces a type parameter: a type-parameter list on a routine, a class, an interface, a struct, an enum, a trait, an implementation block or a type alias, a type-variable declaration, or a routine or class whose signature binds a type variable declared elsewhere. For each one, read its bound and decide whether the bound admits more than one type; an upper bound on a class that cannot be extended, a constraint that names one exact type and a single constraint each admit one. Then search the repository for every use of the definition and record the type argument at each, written out or inferred from what a call passes, counting the uses the diff adds. Where a recorded type argument is itself a type parameter of an enclosing generic definition, it stands for every type that definition is instantiated with: follow it to that definition's uses and record those types instead, and treat the use as a library's public API when that definition is one. A bound that admits only one type is a finding whatever the definition's uses and callers. For the instantiation check, decide whether the definition is a library's public API, exported from a package that callers outside the repository import, and leave it out there, and leave out a definition with no use yet and one whose uses already instantiate two or more distinct types. Leave out, for both checks, a declaration whose type parameters are dictated by a declaration it overrides or implements, such as a method implementing a generic interface or trait method; that overridden declaration is judged where it is declared. Validator question: **Does an added type parameter have a bound that admits only one type, or is a definition that is not a library's public API instantiated with the same single concrete type at every use?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-40`, severity minor, `file`, `symbol`, `code` = the added declaration line that introduces the type parameter, verbatim from the diff, `fix` = the definition rewritten in the file's language with the single type in place of the parameter and the type argument dropped from its uses, `rationale` = the one concrete type found at every use with the number of uses inspected, or the bound that admits only one type).
