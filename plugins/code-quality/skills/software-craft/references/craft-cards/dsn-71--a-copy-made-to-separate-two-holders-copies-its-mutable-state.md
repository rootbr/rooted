# A copy made to separate two holders also copies the mutable objects that make up its state

## Thesis
A copy made so that a change through one holder does not reach the other — a defensive copy, a clone, a copy constructor or copy method, a spread or field-by-field copy of a record or struct — is independent of its original: besides copying the top-level fields, it copies each mutable object that makes up the copied value's internal structure, such as a nested collection, an array, the array a slice refers to, or the mutable cell a shared pointer refers to, and holds references to those copies in place of references to the originals. A field that holds a primitive or a reference to an immutable object usually needs no copy.

## Rationale
For a collection that is mutable or holds mutable items, a copy is sometimes needed so that one holder can change its copy without changing the other. A shallow copy constructs a new compound object and inserts into it references to the objects found in the original; the contents of the fields are not themselves copied. Reassigning a top-level field of a shallow copy leaves the original as it was, while reassigning a property of a nested object through the copy changes the original too: a change to either the source or the copy may change the other. Several standard copy operations are shallow: in one language every standard built-in object-copy operation — spread syntax, slicing, concatenation, building an array from another, assigning properties into a new object — creates a shallow copy; in another, the root class's clone performs a shallow copy; in a third, cloning a reference-counted pointer does not make a deep copy of the data and only increments the reference count, and a reference-counted pointer that holds a cell with interior mutability gives one value several owners that can each mutate it. To make a copy built on these operations independent of its original, it may be necessary to modify its fields afterwards: typically, to copy the mutable objects that make up its deep structure and replace the references to them with references to the copies; a value whose fields hold only primitives or references to immutable objects usually needs no field modified. The reference can also point into the value itself: where a struct holds a slice that may refer to a small array inside the same struct, the slice in a copy may alias the array in the original, causing later method calls to have surprising effects. To avoid unexpected aliasing and similar bugs, a struct from another package is copied with care. In one case study, refactoring a spreadsheet application's code to use a tool for transitive class immutability took approximately twenty hours and found two previously unknown bugs, one in a copy method and another in code that improperly used a cache.

## Example
```rust
bad:  #[derive(Clone)]
      struct Doc { items: Rc<RefCell<Vec<String>>> }
      let draft = doc.clone(); // draft.items is doc.items
good: struct Doc { items: Rc<RefCell<Vec<String>>> }
      impl Clone for Doc {
          fn clone(&self) -> Self {
              Doc { items: Rc::new(RefCell::new(self.items.borrow().clone())) }
          }
      }
      let draft = doc.clone(); // draft.items is a new vector
```

## Limits
A shallow copy suffices where every field holds a primitive, since such a copy is both shallow and deep, and usually where every field holds a primitive or a reference to an immutable object. A deep copy of everything may copy too much, such as data intended to be shared between copies; a field the type documents as shared between copies is outside the rule. A nested object that the code treats as immutable — never changed in place through either holder, only ever replaced by a new object — may stay shared, as in an update that spreads a value one level deep and copies only the nested level it changes. Cloning a reference-counted pointer so that a second owner reaches the same data is sharing by design, the kind of clone that increases the reference count rather than the deep-copy kind, and is outside the rule. Where most types' clone implementations make a deep copy of the data, a reference-counted pointer is the exception: its clone does not make a deep copy and only increments the reference count, so a field that holds one stays linked after a clone. Whether a value may be copied while other threads use it, and the copying of synchronization objects, are outside this rule.

## Validator
In the hunk, find each copy: a shallow-copy or clone call, a spread into a new object or array, a property-assignment copy, a dereference that copies a struct, a collection constructor or copy factory that takes another collection, an array copy, and each added clone, copy or deep-copy method, copy constructor or derived clone. Decide from the surrounding code whether the copy is made to keep two holders apart: it is returned or stored as a separate value, handed to a caller, kept as a snapshot, or changed afterwards while the original lives on; skip a copy that gives a second owner the same data on purpose. Open the copied type's declaration in the file and list its fields; when the type is declared outside the file, list the fields that the file's code reads or assigns on the original or the copy. For each field that holds a mutable object of the value's own state — a collection, an array, a slice, a buffer, a reference-counted pointer to a mutable cell, an object with mutating methods — trace whether the copy replaces the reference with a reference to a copy of that object; skip fields that hold primitives or immutable objects, fields the type documents as shared between copies, and fields whose object the code only replaces and never changes in place. Validator question: **does a copy made to keep two holders apart share by reference a mutable object that makes up the copied value's own state?** Yes → flag.
