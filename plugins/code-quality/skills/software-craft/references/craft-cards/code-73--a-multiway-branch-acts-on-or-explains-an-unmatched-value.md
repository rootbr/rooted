# A switch, match or else-if chain ends in a default or final else that acts on an unmatched value or states why none needs handling, unless its cases cover every member of a closed type

## Thesis
A switch or match, and an if followed by one or more else-if branches, ends in a branch for a value no earlier case named: a default clause, a catch-all arm or a final else. That branch takes the action for any such value — a default action common to all of them, or a report of the value as unexpected — or, where nothing is to be done, holds a comment stating why. When every branch of a chain ends in a return, a throw, a break or a continue, or every case of a switch or match ends in a return, a throw or a continue, the statements that follow it serve as its final else or default — those after it in the routine, or in the loop body for a break or a continue. A switch or match whose cases name every member of a closed type — an enumeration, a sealed type, a union of literal types — needs no default, provided no value outside the type can reach it; where the compiler or a configured checker verifies that coverage, leaving the default out keeps the check able to report a member added later. A value decoded from outside the program without a check that rejects unknown members, and an enumeration from another library switched on by code that can run against a later version of that library than the one it was compiled or checked against, can hold a member the static type lacks, so that switch keeps a default for the unknown value.

## Rationale
When a multiway branch has no default and its cases do not cover every value that can reach it, a reader cannot tell which of three things the author meant: the other values are impossible, execution is meant to fall out of the branch and carry on, or the missing cases are a bug. A value nobody considered can then pass through unhandled, so that later decisions rest on poor information and the failure cascades; in the documented weakness, an error code that matched neither the failed nor the passed case let execution carry on past a security check. A case is typically forgotten when a member is added to an enumeration and whoever adds it does not update every switch over that enumeration. Stating the default behaviour, even as a comment stating why none is needed, makes it clear whether the author forgot it. A default reserved for error handling covers the values whose absence cannot be assumed, while a default that silently stands for one assumed value instead of checking for invalid input is in some cases as bad as no default at all. A chain whose branches all end in a return, a throw, a break or a continue needs no else, and a switch whose cases all end in a return, a throw or a continue needs no default, because the statements after it run only for the values no branch took. Where the compiler or a configured checker verifies that the cases cover a closed type, it reports a member added later at every switch that misses it; a default on a fully covered switch is dead code, and where the check counts a default as covering every value it silences that report, so the new member falls silently into the default. A closed static type does not bound the values that arrive from outside the build: a server running a newer version can send a member the client's types do not know, and code compiled against one version of a library's enumeration and run with a later one can meet a member added there, which then falls out of a switch that has no default; where every build checks the cases against the version the code runs with, an added member breaks the build at each switch that misses it, and a catch-all would let it pass unnoticed.

## Example
```rust
bad:  if status == 200 { accept(body); }
      else if status == 404 { retry_later(); }
good: if status == 200 { accept(body); }
      else if status == 404 { retry_later(); }
      else { return Err(Error::UnexpectedStatus(status)); }
```

## Limits
Sources split on a switch whose cases already name every member of a closed type. Two linters and a style guide ask for a default in every switch, one of them so that the code is protected against a member added later, with the coverage expressed in the default by an assertion; checkers, and a coding standard that relies on a compiler warning, leave the default out because on a fully covered switch it can stop the check reporting that member, and the rule that asks a default to act or explain itself expects none when the cases use every constant of an enumeration. What separates them is whether anything verifies the coverage: the linter that gives the added-member reason exempts the switch forms the compiler checks for exhaustiveness. A fully covered switch passes this check, following the enumeration exception of the rule that asks a default to act or explain itself; where nothing verifies its coverage, a project context that requires a default in every switch extends the finding to it. Beside a checked full set of cases, a default kept for a value from outside the static type need not disable the check: one checker keeps checking the named cases when that default's comment names the version skew, and another keeps checking them unless it is configured to count a default as covering the union. Sources also differ on what an empty default must say: two rules of one analyzer ask for a comment stating why no action is taken, two style guides and a coding guideline accept a default that holds no code, two linters accept an empty default or, in its place, a comment such as `no default` after the last case, and one language's official tutorial treats an empty catch-all arm as an explicit statement that no code runs for the other values; a project context that adopts one of these forms rejects the finding for it, and a missing branch is still flagged. A syntactic check that asks every switch for a default and every else-if chain for a final else also reports a construct whose every branch exits; this check counts the statements after it as that branch, as the style guide and the linter rule that omit an else after an exiting branch do, and a project context that requires the branch itself extends the finding to it. A two-way if-else and a lone if make no multiway decision and are outside the rule; replacing a chain with a lookup table or a state machine, dispatch over an enumerated set of states, and what a reporting branch does with the error are judged by their own rules.

## Validator
Grep the added lines for a switch or match header, a case, default or catch-all line, and an else-if or elif. For each hit, open the file and read the whole construct and the statements after it in the routine. For an if followed by one or more else-if branches, look for a final else; when every branch ends in a return, a throw, a break or a continue, the statements after the chain stand as the else, and a chain with nothing after it — in the routine for a return or a throw, in the loop body for a break or a continue — has none. For a switch or match, look for a default clause or catch-all arm or, when every case ends in a return, a throw or a continue, statements after it in the routine, or in the loop body for a continue, which stand as the default; when there is none of these, find the type of the switched value and pass the construct when its cases name every member of an enumeration, a sealed type or a union of literal types — unless the value was decoded from outside the program without a check that rejects unknown members, the file is library code switching on another library's enumeration and can run against a later version of that library than the one it was compiled or checked against, or the project context requires a default in every switch. Then read the default, catch-all arm or final else: it passes when it takes an action that fits every value reaching it or holds a comment stating why nothing is needed, and it fails when it is empty or a lone break with no such comment, or when its body or comment shows that it handles one particular leftover value as though it were the only one. Accept an empty default, or a `no default` comment after the last case, where the project context adopts that form. Skip a two-way if-else and a lone if. Validator question: **Does an added switch, match or else-if chain leave a value its cases do not name with no default, catch-all arm, final else or following statements that stand for one — other than a full set of cases over a closed type that no outside value can reach — or end in such a branch that is empty without a stated reason or stands for one assumed value?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-73`, severity minor, `file`, `symbol`, `code` = the construct's header and its last branch, or the empty default, quoted verbatim from the diff, `fix` = the same construct in the file's language ending in a default, catch-all arm or final else, or followed by a statement when every branch exits, that reports the unmatched value as unexpected or takes the action common to every unmatched value — or, where nothing is needed, holds a comment stating why, `rationale` = which values can reach the construct that no case names, and what happens to them now).
