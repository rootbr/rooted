# Research note — Boundaries, adapters and framework isolation

Topic `boundaries-adapters-and-framework-isolation` of group K. Architecture, domain `architecture`, id prefix `ARCH`. Formulation locators: Clean Architecture ch. 11 'DIP' (volatile modules), ch. 17 'Boundaries: Drawing Lines', ch. 18 'Boundary Anatomy', ch. 20 'Business Rules', ch. 22 'The Clean Architecture' (the Dependency Rule), ch. 23 'Presenters and Humble Objects', ch. 30 'The Database Is a Detail', ch. 31 'The Web Is a Detail', ch. 32 'Frameworks Are Details'; The Pragmatic Programmer 20th ed. Topic 10 (a third-party product behind an own interface) and Topic 28 'Decoupling'; Cockburn, 'Hexagonal architecture' (ports and adapters); Fowler, bliki 'HumbleObject'; SWEBOK Guide V4.0 ch. 2 'Software Architecture' (architectural styles) and ch. 3. Marked contested in the design note.

The canon (Clean Architecture ch. 11, 17–23 and 30–32, Clean Code ch. 8, The Pragmatic Programmer Topics 10–11, Cockburn's ports and adapters, Fowler's Humble Object, Evans ch. 4) states one core rule. At a component boundary, source dependencies point toward the business policy, and policy code names no framework, database or UI type. Three rules hang off it: plain data crosses the boundary, a hard-to-test edge is split into a humble shell and a testable core, and a third-party product sits behind an interface the project owns. The industry disagrees in four places. Django and Rails document Active Record models as the home of the domain logic. Microsoft names Active Record a violation of persistence ignorance, but it limits its framework-free domain to complex services and builds a CRUD service in one project. Google's Go guides reject an interface created before a real need and a hand-written wrapper around a generated RPC client. DHH, James Bennett, Ayende, Seemann and later Rails writers dispute layered isolation as the default. The evidence supports the rule only where the project declares it: every architecture checker opened (ArchUnit, jMolecules, go-cleanarch, import-linter, depguard, Nx, eslint-plugin-boundaries, NetArchTest, Ruff TID251, ESLint no-restricted-imports) enforces a framework or package ban only after the project declares one. The official guides give the scope (domain complexity) but no threshold, so an undeclared import from policy code to a framework stays pending. No study I found measures whether a framework-free core or an owned wrapper lowers change cost. The research measures how often libraries and frameworks are replaced or break their clients (He et al. 2021, Venturini et al. 2023, Ferreira et al. 2021, Lin et al. 2023), and the dependency-injection studies found no coupling effect or one that depends on the metric. Component-level rules with crisp sources do exist: the public/private dependency distinction of Gradle and Cargo, and separate RPC and storage messages in Protocol Buffers. The topic yields seven cards: a framework-free declared domain; declared bans on third-party imports; the domain entity kept behind the presentation boundary; separate RPC and storage messages; humble views and request handlers; exported dependencies declared by their use in public signatures; and the bump of an exposed dependency treated as a breaking change. Three rules stay pending, one is held, and three fold into cards.

## Formulation layer

The canon states one core rule: at a component boundary, source dependencies point toward business policy, and policy code names no framework, database or UI type (Clean Architecture ch. 17–22, Cockburn, Evans ch. 4, Microsoft's .NET architecture guides, and ArchUnit's onionArchitecture check as a tool rule). Three rules hang off it: plain data structures cross the boundary; a hard-to-test edge is split into a humble wrapper and a testable core (Clean Architecture ch. 23, Fowler, Cosmic Python FCIS); and a third-party product sits behind an interface the project owns (Clean Code ch. 8, Pragmatic Programmer Topic 11, Freeman et al., 97 Things #10). The canon itself names five separating conditions: domain complexity (Evans' Smart UI, Fowler PoEAA, Cosmic Python's 'a simple CRUD wrapper needs no domain model', Microsoft's 'DDD only for complex microservices'); a stateful dependency versus a helper library (the Cosmic Python footnote: an ORM or web framework is not allowed, a helper library is); volatility, with the standard library exempt as a conscious decision (Clean Architecture ch. 11 and ch. 32); the cost of a full boundary (ch. 24–25); and a boundary the project declares and has a tool check (ArchUnit, go-cleanarch, import-linter, Brown ch. 34). The isolation canon is disputed in four places. Framework documentation puts domain logic in Active Record models (Django design philosophies, Rails guides), and Microsoft's persistence-ignorance list names Active Record as a violation. DHH's 'test-induced design damage' stands against Martin's reply. Ousterhout's pass-through-layer red flag, Google's Go guidance against wrapping generated clients in manual interfaces, and Seemann's single-implementation critique stand against wrapping everything. Spinellis' database-centric essay stands against 'the database is a detail'. I could not open the books, SWEBOK V4, ISO/IEC/IEEE 42010, Cockburn's and Fowler's pages, or Seemann's blog, so those items are unfetched paraphrases or relayed search summaries. The design note's 'Pragmatic Programmer Topic 10' locator is off by one: the search relays Topic 10 as Orthogonality and Topic 11 as Reversibility. import-linter's contract documentation returned 404 on both raw branches, so only its PyPI description was fetched.

## Reception layer

The architecture-check tools I opened (ArchUnit, jMolecules, go-cleanarch, import-linter, dependency-cruiser, eslint-plugin-boundaries, NetArchTest, Spring Modulith, Ruff TID251, ESLint no-restricted-imports) enforce a boundary only after the project declares it, as a package predicate, a layer list, a directory name, an annotation or a forbidden-module list. None of them flags a framework, ORM or vendor-SDK import that the project has not declared off-limits: go-cleanarch ignores imports whose path carries no layer name, ArchUnit's onion rule restricts only who may access each declared layer, and import-linter forbids external packages only with include_external_packages = True. Tool practice therefore backs the separating condition "the project declares the boundary". Defenders who published openable text (Microsoft's .NET architecture guides; Percival and Gregory's Cosmic Python, fetched from its GitHub source) state a second condition themselves: for a simple CRUD app, keeping the domain free of the framework is not worth the extra layer, and a Repository pays off when the domain is complex or a move off the framework or database is expected. The canon's rules are disputed by DHH (test-induced design damage, hexagonal Rails), James Bennett (no service layers in Django), Ayende (no repository over an ORM), Seemann (an interface with one implementation is a smell), Google's Go style guides (no interface before it is used, and no hand-written wrapper around a generated RPC client just for abstraction or testing), Rentea, Bogard and a 2025 Rails post (Tarkhanov); Kent Beck and CodeOpinion take middle positions. I could not open any blog, Hacker News thread or martinfowler.com page from this environment, so every practitioner critique is relayed from WebSearch summaries, and a search for a 2025 Hacker News thread on "frameworks are details" found nothing.

## Evidence layer

Linters in six toolchains enforce a framework- or vendor-import ban only where the project declares it: ArchUnit, import-linter (external packages too), depguard, Nx, Ruff TID251, ESLint no-restricted-imports, plus go-cleanarch for in-project layers. None of them, and no official guide, treats an undeclared import from policy code to a framework as a defect. On the separating condition the official canon splits. Microsoft's .NET architecture guides and Flutter's architecture guide tie a framework-free domain to complexity ("DDD approaches should be applied only if you are implementing complex microservices with significant business rules"; Flutter's domain layer is optional). Rails and Django docs put business logic in Active Record ORM models, and Microsoft names Active Record a violation of persistence ignorance. Google's Go guides reject wrapping generated RPC clients in a project-owned interface "just for the sake of abstraction or testing". The empirical side shows that third-party libraries and frameworks are replaced and break their clients (He et al. 2021: 7.96%-25.46% of 19,652 Java projects migrated a library; Venturini et al. 2023: about 12% of npm dependents hit by non-major breaking changes; Ferreira et al. 2021; Lin et al. 2023), and Mo et al. 2021 tie architecture anti-patterns to bug- and change-proneness. No study I found measures whether an owned interface or a framework-free core lowers those costs, and the DI studies found no coupling effect (Razina and Janzen 2007) or a metric-dependent one (arXiv 2205.06381). Component-level rules with crisp checks do exist: Rust's public/private dependencies (C-STABLE, RFC 1977, the exported_private_dependencies lint), Go internal packages, Spring Modulith API-package verification, and plain DTOs across a boundary (Microsoft, Spring, ASP.NET, OWASP, protobuf), which Rails and Django contest. Publisher and arXiv pages were unreachable. Yang et al. 2008 and the findings of Spadini et al. 2017 remain unfetched, and the search budget left MacCormack 2006, Garousi 2019, SWEBOK V4 ch. 2 and ISO/IEC/IEEE 42010 unsearched.

## Spine — candidate rules in source order

1. **High-level policy code depends on no volatile low-level detail, such as a web framework, an ORM, a database driver or a vendor SDK, even where the project declares no boundary that forbids the dependency** — The canon states that source dependencies across a component boundary point toward the business rules, and that policy code names nothing concrete and volatile, with stable platform types such as the standard library exempt (Clean Architecture ch. 11, 17, 18, 22). 12. **A library whose build tool separates exported from internal dependencies declares as exported each dependency with a type in its public interface, such as a supertype, a parameter or return type of a visible method or a public field, and declares every other dependency as internal** — Some build tools distinguish the dependencies a library exports to its consumers from those internal to it: Gradle's api and implementation configurations, and Cargo's public flag on a dependency. In such a build, the library declares as exported each dependency that contains a type in its public binary interface: a type used in a superclass or interface, in a public method's parameters or return type (public, protected and package-visible members in Java), in a public field, or as a public annotation type; in Rust, also a trait implementation. Every dependency whose types appear only in method bodies, private members or internal classes is declared internal, and the internal configuration is preferred where possible. An exported dependency is placed on consumers' compile classpath, where they can come to depend on it by accident. An internal one does not leak, and its changes do not force consumers to recompile. 13. **A change that moves a dependency whose types or traits appear in a published library's public API to a version incompatible with the one it replaces, or that newly exposes a dependency's types there, is released as a breaking change of the library** — A dependency whose types or traits appear in a library's public API, in parameters, return values, trait implementations and the like, is a public dependency, and its version is part of the library's own contract.
