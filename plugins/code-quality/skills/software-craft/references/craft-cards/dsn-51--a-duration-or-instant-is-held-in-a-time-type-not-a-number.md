# A duration or an instant is held in a time type rather than a bare number, and a number with its unit in the name is used only where the code or an interface cannot carry that type

## Thesis
A value that stands for a period of time — a timeout, a delay, an interval, a period, a latency, a time-to-live, a backoff — is held in a duration type, and a value that stands for a point in time — a timestamp, an expiry time — is held in an instant type, rather than in a bare integer or floating-point number. The type comes from the standard library or from a time library the code already uses. This holds at an external interface too, wherever the interface can carry the type: a command-line flag parser that reads durations, a serializer that writes an instant as an RFC 3339 string, a database driver that maps timestamp columns. Where a format or an interface cannot carry the duration type, the duration is an integer or floating-point number whose name includes its unit (intervalMillis, timeoutSeconds). Where it cannot carry the instant type, the instant is a string in RFC 3339 format unless the interface has agreed on another form, and an integer form, where its name is free to choose, names its unit as well (sendTimeMillis).

## Rationale
A bare number leaves its unit to the reader and to every caller: a call such as poll(10) does not say whether it waits ten seconds or ten milliseconds, and an integer timestamp does not say whether it counts seconds, milliseconds, microseconds or nanoseconds. A time type carries the unit as part of the value, so the call site states it (ten seconds). A number with its unit as a separate parameter has problems of its own: the pair may have to be passed through the application's layers, duration arithmetic on the number can overflow, neither half carries meaning when read alone, and splitting a duration into a number and a unit risks a unit mismatch or excessive truncation. Assumptions often made about time are incorrect — that a day has 24 hours, an hour 60 minutes, a year 365 days — so adding 24 hours to an instant does not always yield a new calendar day; a time type, with its own methods for comparing, adding and subtracting, helps deal with these assumptions in a safer, more accurate manner. An instant and a duration can share one numeric structure and still mean different things; holding each in its own type keeps that difference in the code and lets tooling act on it. A field that the code uses only to construct a time value would be clearer typed as that time value. At a boundary the type may have nowhere to go: common exchange formats such as JSON lack a native concept of time, and since a unit is stated either in the name or as part of the value, where the value cannot carry it the name does.

## Example
```typescript
bad:  function isExpired(expiresAt: number): boolean {
        return Date.now() >= expiresAt;
      }
      isExpired(1767225600);
good: function isExpired(expiresAt: Date): boolean {
        return Date.now() >= expiresAt.getTime();
      }
      isExpired(new Date("2026-01-01T00:00:00Z"));
```

## Limits
Whether a time quantity belongs in a time type or in a number whose name carries the unit is contested, and one condition separates the cases: whether the code or the interface that holds the value can carry the time type. Where it can — inside the program, and at a flag parser, serializer or database driver that supports the type — the time type is the rule: representing date and time concepts as numeric primitives is strongly discouraged, and a primitive used only to construct a time type would be clearer strongly typed, a unit suffix in its name notwithstanding. Where it cannot — a serialization format with no encoding for a duration, an API whose clients would otherwise have to implement one language's duration parsing, a separate specification that mandates integer timestamps — an integer or floating-point number whose name includes the unit is the documented form, and at such an API boundary a unit in the field name and a unit carried in the value stand as alternatives. Where neither the standard library nor a time library the code already uses offers a duration or an instant type, the type half of the rule does not reach the value, and its name includes the unit, since a unit that could be ambiguous and that neither the value nor its type specifies belongs in the name. A call to a routine that offers no overload taking a duration or an instant passes the number that routine requires, converted from the time value at that call; the time-typed form of a called routine is preferred only where one is available. A time value carried as a string at a boundary, such as an RFC 3339 timestamp, names its meaning and no unit. The project context can reject the finding by stating a wire format or an external specification that fixes the numeric form.

## Validator
Grep the added lines for a parameter, field or variable whose name names a period or a point in time (timeout, delay, interval, period, latency, ttl, backoff, expiry, deadline, timestamp, or a unit word such as millis, ms, seconds, secs) declared with an integer or floating-point type; for a number passed beside a separate time-unit parameter; and for a number turned into a duration or an instant on the line, multiplied by a unit constant or passed to a duration or instant factory or constructor, which you trace back to its declaration. Open the file and trace where the value comes from and where it goes. Decide whether the code could hold it in a duration or an instant type: the standard library, or a time library the file imports or the project context names, offers one, and the value is not a field of a serialized message, a flag or a column whose format cannot carry the type. A called routine that takes only a number, with no time-typed overload, receives that number converted from the time value at the call and does not exempt the declaration; a duration or instant factory or constructor is the construction being traced, never such a routine. Where the code could, a bare number is the finding, whatever unit its name states. Where it could not, read the name: a number whose name states its unit is correct, and one whose name does not is the finding. Set the value aside when the project context states a wire format or an external specification that fixes its numeric form. Validator question: **Does the change hold or pass a period or a point in time as a bare integer or floating-point number where the code or its interface could carry a duration or instant type, or, where neither can, under a name that does not state the unit?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-51`, severity minor, `file`, `symbol`, `code` = the added declaration, parameter or construction that holds the time value as a number, quoted verbatim from the diff, `fix` = the declaration retyped to the duration or instant type with its call sites passing a value that states its unit or, where neither the code nor the interface can carry that type, the number renamed to end in its unit, in the file's language, `rationale` = the unit the bare number leaves unstated, and whether the code or the interface could carry the time type).
