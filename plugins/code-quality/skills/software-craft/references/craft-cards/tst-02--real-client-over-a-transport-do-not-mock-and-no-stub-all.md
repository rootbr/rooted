# A test keeps the real client over a transport, uses the alternative a do-not-mock marker names, and never stubs every non-private method of a type that has more than one

## Thesis
When a test exercises code that reaches another component through a client over a transport such as HTTP or RPC, it keeps the real client and points it at a test server, built with the testing library the component's owner provides where one exists, rather than stubbing the client. A type whose owner marks it, or one of its supertypes, not to be mocked is replaced by the alternative the marker names: the owner's fake, a testing utility, or a real instance. A test that would stub every non-private method of a type that has more than one instead does one of three things: uses the type itself, uses a hand-written subclass or implementation with the behaviour the test needs, or splits into tests that each stub only the methods they need.

## Rationale
A test double is only as faithful as its imitation of the dependency's contract: the error forms, the guaranteed fields, the inputs the real code rejects. Imitating a client's behaviour correctly is complex, so a stub written inside the test re-states, call by call, behaviour the real code already implements, and where the re-statement departs from the contract the test passes against a response production never returns. A testing library from the component's authors carries their knowledge of that contract, and running the production client against a test-specific server keeps as much of the real code in the test as possible. A do-not-mock marker is the owner's statement that a mock of the type is undesirable; the marker carries the reason and the alternative; in its annotation form the default reason is "create a real instance", a static check reports such a mock at error severity, and a mocking library can refuse to create it. Stubbing every non-private method of a type that has more than one is a strong sign that the test has grown too complex or misuses the mocking mechanism; the type itself, a subclass or implementation with the expected behaviour, or smaller tests that each stub only what they need take the place of the stubs.

## Example
```go
bad:  client := NewMockDoer(ctrl)
      client.EXPECT().Do(gomock.Any()).Return(&http.Response{StatusCode: 200}, nil)
      got, err := Fetch(client, "/items")
good: srv := httptest.NewServer(http.HandlerFunc(serveItems))
      defer srv.Close()
      got, err := Fetch(srv.Client(), srv.URL+"/items")
```

## Limits
A dependency that is not a client over a transport and carries no do-not-mock marker is outside this rule unless every non-private method of a type that has more than one is stubbed. A first-party wrapper whose methods take and return the program's own types, rather than a transport client's requests and responses, is not a client over a transport for this rule. Where the client's owner documents stubbing the client in unit tests — an interface it publishes to enable mocking the client, or a narrow interface the client satisfies that its guide tells callers to define and mock — a stub built that way follows the owner and does not meet the transport condition; the condition holds for a client whose owner documents no such pattern. A type with a single non-private method, such as a one-method interface, does not meet the all-methods condition. A marker the finder cannot read in code, such as guidance kept only in a wiki, is out of reach: the rule reads an annotation, an attribute or a doc comment on the type. What the test asserts and whether it verifies calls rather than state are outside this rule.

## Validator
Grep the hunk for mock or stub creation and for stubbing calls, and name the type each one substitutes. Open that type's declaration and the declarations of its supertypes, and read any do-not-mock marker on any of them (an annotation, an attribute, or a doc comment saying the type should not be mocked) and the alternative it names. When the type is a transport client itself — a library's HTTP or RPC client, or a client generated from the component's service definition — or an interface whose methods take and return that client's requests and responses, search the component owner's module for a test server or testing library to name in the fix. Read the client's package documentation and the testing guide its owner publishes for the client (a testing page in its repository or a unit-testing page of its developer guide) for an interface its owner publishes, or tells callers to define, for stubbing the client in unit tests; a stub of such an interface does not meet the transport condition. Count the type's non-private methods and the methods the test stubs on one instance; a type with one non-private method does not meet the all-methods condition. Validator question: **Does the test mock a type marked not to be mocked, stub the client of a component reached over a transport instead of pointing the real client at a test server, or stub, on one instance, every non-private method of a type that has more than one?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: TST-02`, severity minor, `file`, `symbol`, `code` = the mock-creation or stubbing line from the diff, `fix` = the test rewritten to run the real client against a test server (the owner's testing library where one exists), to use the marker's named alternative, the real type or a hand-written implementation, or split into tests that each stub only what they need, in the file's language, `rationale` = which of the three conditions holds and the stubbed transport client, the marker text or the stubbed-method count that shows it).
