# Application code outside the composition root neither calls a dependency-injection container for a service that injection could supply nor receives the container as a dependency, leaving such lookups to the composition root and to framework infrastructure code that requires programmatic access to the container

## Thesis
Application code receives its collaborators through injection, as dependencies it declares statically, and holds no reference to the container itself. Where injection can supply a service, application code makes no call to the container's lookup, such as a get-service, get-bean, get-instance or resolve call. It implements no container-aware callback for retrieving other objects, and it takes no container, injector or application context as a constructor argument or field. The composition root, the code that creates the container, uses the container as little as possible, preferably once, to retrieve the instances it starts from. Framework infrastructure code that requires programmatic access to the container, or does not know the needed type until run time, may take the container, sparingly.

## Rationale
Where a container checks the object graph when it is created, it fails at creation, in every case, for any dependency that is not configured correctly, so long as nothing receives the injector. Code that receives the injector can get instances from it directly, so the container cannot know ahead of time that the graph is complete. A missing binding can then fail at run time, with a missing-binding error, when the code lazily asks the injector for the instance. Code that receives the container also does not self-document its dependencies. A lookup, or a reference to the container held for any other use, couples the code to the container's API and departs from the inversion-of-control style, in which collaborators are provided to the object. Declaring each collaborator restores the creation-time check of the graph and leaves the application code with no reference to the container.

## Example
```rust
bad:  struct Checkout { container: Arc<Container> }
      impl Checkout { fn pay(&self) { self.container.resolve::<dyn Gateway>().charge(); } }
      fn main() { let c = Container::new().bind::<dyn Gateway, CardGateway>(); Checkout { container: Arc::new(c) }.pay(); }
good: struct Checkout { gateway: Arc<dyn Gateway> }
      impl Checkout { fn pay(&self) { self.gateway.charge(); } }
      fn main() { Checkout { gateway: Arc::new(CardGateway) }.pay(); }
```

## Limits
The separating condition is who performs the lookup and whether injection could supply the service. Application code that calls the container for a service it could receive by injection is the finding. Framework infrastructure code is the documented exception. Registration code belongs to the composition root: a factory function registered with the container may resolve the dependencies of the object it builds through the container that the registration hands it, which is the documented way to resolve a service while registering another. Container-aware callbacks are recommended for infrastructure components that require programmatic access to the container. Framework code that does not know the type it needs until run time receives the injector, in this rare case and sparingly. Exceptions to the container's recommendations, avoiding the lookup among them, are rare and mostly special cases within the framework itself. A hosted background service that needs scoped services receives a scope factory, creates a scope and resolves the services from it, so each service takes the lifetime of that scope; this documented pattern is not a finding. Three mechanisms that resemble a lookup stay outside the rule. The first is a framework injection function that works only within the framework's injection context, such as during the construction of a class the injection system instantiates. An injector a class holds only to run a function within that context outside construction stays outside the rule when the function calls an interface the framework designed to run within the context, and is the finding when the function resolves a service the class could receive at construction. The second is platform discovery of service providers by service type, where application code refers only to the service. The third is a hand-written locator passed explicitly in code that uses no container: one style guide holds that the locator pattern itself is not problematic, rather the locator being defined as global, and this rule does not reach a hand-written locator defined as global.

## Validator
Grep the hunk for a container lookup call (get-service, get-required-service, get-bean, get-instance, or resolve and get on an injector, container, module reference or service provider), for a container-aware callback interface, and for a constructor parameter or field typed as the container, injector, service provider, bean factory or application context. Open the file and place the code: the composition root that creates the container and retrieves its starting instances, a framework infrastructure component that requires programmatic access to the container or learns the needed type only at run time, a hosted background service resolving scoped services from a scope it creates, or application code. Registration code is part of the composition root, and so is a factory function registered with the container that resolves the dependencies of the object it builds. Check that the receiver is a dependency-injection container, a factory that keeps a registry of objects and their dependencies and builds the instances it hands out; a hand-written locator that hands out only instances the code placed in it, passed explicitly, stays outside the rule. An injector held only to run a function within the framework's injection context is a finding only when that function resolves a service the class could receive at construction. For application code, trace the requested type: a type literal, generic argument or constant name fixed in the source is a service injection could supply. Validator question: **Does application code outside the composition root call a dependency-injection container's lookup for a service that injection could supply, implement a container-aware callback to retrieve other objects, or take the container, injector or application context itself as a constructor argument or field?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-28`, severity minor, `file`, `symbol`, `code` = the lookup call, the container-aware callback or the container-typed parameter or field, quoted verbatim from the diff, `fix` = the collaborator declared as a constructor parameter of its interface type and supplied by the composition root, in the file's language, `rationale` = for a lookup, the missing binding that can fail at run time when the lookup executes and the dependency the code leaves undeclared; for a container held without a lookup, the coupling to the container's API and the departure from the inversion-of-control style).
