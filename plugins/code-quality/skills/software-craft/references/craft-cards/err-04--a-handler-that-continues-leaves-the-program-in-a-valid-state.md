# A handler that lets execution continue after a failure leaves the program in a valid state, so no later step runs on the failed step's missing result or on a half-applied update

## Thesis
A handler after which execution continues — a `catch`, `except` or `rescue` clause, a rejection callback, a branch or match arm taken on a returned error, a call that substitutes a fallback for a failed result — leaves the program with its invariants holding. It recovers with a value or a state the following code is correct with; or it propagates the failure, or raises an error suited to its own level; and where the failed step had already changed state that outlives it, that state is restored, in the handler or in a block that runs on every exit, before execution recovers or the failure passes on. The code after the handler then uses no result the failed step did not produce, carries out no step the failed one existed to guard — processing a transaction after its validation raised an error is failing open — and sees no object the failed step left partly modified. Recording the error and carrying on is not recovery by itself; it meets the rule only when the code after the handler meets all three. A substituted neutral, default or previous value is a deliberate robustness choice, correct only where the following code is correct with the substitute in place of what the failed operation would have produced, and not where it needs the real value: an amount, a validation verdict, a record that was to be written.

## Rationale
An error means the statements after the failing point never ran, while the code after the handler proceeds as though they had, so what it computes with is whatever the handler left behind. A substituted zero, empty or stale value reaches the following statements as if the failed operation had produced it, and the wrong result carries no mark of the failure. A failed check turned into a fall-through becomes an acceptance: the fail-open condition, such as processing a transaction despite errors from validation logic, that an application-security verification standard requires an application to prevent from the second of its three levels. A step that had modified an object before failing leaves the object inconsistent, and every later use inherits the damage: in a documented case, a routine that pads three dimensions, throws before its revert and returns an error code gives a wrong result on every later call. Consistency survives a failure when the step does the work that can fail before it modifies the object, works on a copy and commits only after success, rolls back in the handler or in a block that runs on every exit, or leaves the object unmodified. A taxonomy of exception-handling faults in open-source projects counts improper continuation of execution as a fault category, with handling that leaves the system in an inconsistent state and execution resuming at statements after the handler that should not run once the error occurred among its sub-cases. In 198 sampled user-reported failures of five distributed data-intensive systems, 92% of the 48 catastrophic failures came from incorrect handling of non-fatal errors the software had explicitly signalled, and 35% of them from trivial handler mistakes that inspection finds without knowledge of the system — 25% from handlers that ignore the error, a handler that only logs counted among them, one of which led to data loss. A log line records that an invariant broke; it does not restore it.

## Example
```rust
bad:  if let Err(e) = debit(&mut from, amount) {
          eprintln!("debit failed: {e}");
      }
      credit(&mut to, amount);
good: debit(&mut from, amount)?;
      credit(&mut to, amount);
```

## Limits
A substitute passes where the following code is correct with it: a documented default for an optional setting, an empty collection where the failure itself means there is nothing to find, such as an optional source that does not exist, and a best-effort step — warming a cache, emitting a metric — whose result nothing after the handler reads. A partly modified object passes where no one can observe it after the failure, such as a local value that goes out of scope as the error propagates. A last-resort handler at the top of a request, job or event loop that records an unhandled error and moves on to the next independent unit keeps the process available, which the same verification standard requires at its third level; it passes where the failed unit's partial changes were rolled back or never shared with the units that follow. A project context that documents a degraded mode, such as answering from stale data while a store is down, rejects the finding for a handler that implements it. The rule judges what runs after the handler: whether a handler that drops an error silently is acceptable, how resources are released on the error path, retries, timeouts and fallbacks on a remote call, and the wording of the log line are judged by their own rules.

## Validator
Grep the added lines for a handler — a `catch`, `except` or `rescue` clause, a rejection callback, a branch on a returned error, a match arm or conditional binding on an error variant — and for a call that substitutes a fallback for a failed result, such as a get-or-default, value-or or unwrap-or call. Keep each one whose path falls through — the handler neither returns, rethrows, raises nor exits, or the fallback's value flows on — and each handler, whatever its exit, whose protected block had modified an object that outlives the routine before the failing point. Open the file and name what the failed step would have produced or done: a value assigned inside the protected block or returned by the failed call, a check whose success the following code assumes, a modification it had begun on an object that outlives the routine. Trace the statements after the handler in the same routine and what the routine returns to its callers in the file: look for a read of the value the failed step did not produce, or of a substitute standing in for a value the following code needs; a step the failed one guarded, such as a commit, a charge, a write or the second half of a paired update; and a use of an object the protected block modified before the failure with no rollback in the handler or in a block that runs on every exit. Skip a substitute the following code is correct with, a best-effort step nothing reads, an object discarded with the failure, a last-resort handler that moves to the next independent unit with the failed unit's changes rolled back or never shared, and a degraded mode the project context documents. Validator question: **Does execution continue past an added handler or fallback into code that uses a result the failed step never produced or performs a step the failed one guarded, with no propagation, or does the handler recover or pass the failure on while an object that outlives the routine stays partly modified by the failed step, with no restore?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-04`, severity major, `file`, `symbol`, `code` = the handler or fallback line and either the first following statement that depends on the failed step or the modification the handler leaves unrestored, verbatim from the diff, `fix` = the handler rewritten in the file's language to propagate the failure or raise an error suited to its level, to restore the prior state before recovering or propagating, or to recover with a value the following code is correct with, `rationale` = what the failed step would have produced, guarded or modified, and which later statement runs without it or on the partly modified state).
