# In a project that keeps a decision log, a change that adds, removes or replaces a dependency between the project's own components, or adopts, replaces or drops a framework, database, protocol or external service, adds a record of that decision to the log unless an accepted record already covers it

## Thesis
Where a project keeps a decision log, a directory of decision records that its configuration names or that already holds its records, a change that makes an architectural decision adds a record of that decision to the log in the same change, unless an accepted record in the log, or one the change links from a central documentation repository, already covers it. A change makes an architectural decision when it adds, removes or replaces a dependency between two of the project's own components, meaning its units of release, build or deployment, or when it adopts, replaces or drops a framework, a database, a protocol or an external service or vendor.

## Rationale
A decision log documents architectural decisions explicitly, together with the rationale of each nontrivial decision. As agile projects age, the reasoning behind their decisions is sometimes hard to keep track of, especially once new people join and those involved in the early stages are no longer around. The preserved reasoning lets a team about to change a choice tell whether it was made for expediency and can be changed with little impact, or whether external reasons behind it need to be factored in. A record that also names the rejected options and why they were rejected can keep a developer from taking a decision rejected earlier for forgotten reasons, or show that the conditions have changed and the decision can be revisited. Kept in version control, in the repository of the application the decision affects, the record preserves what was changed, who changed it and when. A record added in the change that enacts the decision can be checked on that change: one review gate fails a pull request that changes watched code without recording a decision.

## Example
```python
bad:  # setup.py: this change adopts a message queue; no record in docs/decisions/ covers it
      setup(name="orders", install_requires=["queue-client>=2.0"])
good: # setup.py: the same change adds docs/decisions/0007-publish-order-events.md
      #   with the context, the decision and its consequences
      setup(name="orders", install_requires=["queue-client>=2.0"])
```

## Limits
A version bump of a dependency already in use falls outside the rule, and so does a change to a lockfile alone: a pull-request gate that requires a decision record ignores lockfiles by default, and its maintainer states that a gate firing on a dependency bump gets switched off within a fortnight. Rephrasing, reorganizing and refactoring that keep every dependency between the project's components, changes whose shape changes and whose meaning does not, fall outside it; a restructuring that adds, removes or reverses such a dependency stays inside it. A change confined to one component's internals, such as an interface change in an internal package that is not visible outside it, falls outside it. A project that keeps no decision log falls outside the rule; a mining study of open-source repositories on GitHub found adoption of decision records low, though the number of repositories using them grew each year. Where the project accepts an explicit waiver, a line in the change description that states why the change needs no record satisfies the rule, and a waiver with no reason after it does not waive. Decisions that affect one application belong in that application's repository; a larger-scale decision may sit in a central documentation repository, and a change in one application then links that record. A record merged to the main branch that states no other status, such as proposed or superseded, can be taken as accepted. A third-party library that is neither a framework nor a client of a database, a protocol or an external service falls outside the rule; a project may define architectural decisions more widely, as any decision that might have an impact on the architecture, including the choice of such a library or of a tool, and its log then sets a lower threshold than this rule. The record's own contents, and the design document or change description that accompanies a change, lie outside this rule.

## Validator
Grep the hunk for an added, removed or replaced dependency declaration in a build or package manifest, a container image of a database or broker, or a new client of a framework, protocol or external service. Find the project's decision log: a directory its configuration names, or an existing directory of numbered decision records such as `doc/adr`, `docs/adr` or `docs/decisions`; with no log, stop. Compare the old and the new declaration, and stop on the same coordinate at a new version, a lockfile alone, a reshuffle that keeps every dependency, or a change confined to one component's internal package. Open the usages of the added, removed or replaced coordinate across the repository and confirm that the coordinate is another of the project's own components, a framework, a database or its client, a protocol implementation or an external service's client; stop on any other third-party library. Check the diff for a record of this decision added under the log directory, search the log for an accepted record that already covers the decision, and check the change description, where it is available, for a link to a covering accepted record held in a central documentation repository or, where the project accepts waivers, a waiver that states its reason. Validator question: **Does the change make an architectural decision in a project that keeps a decision log, while the diff adds no record of that decision, no accepted record in the log or linked from the change covers it, and the change carries no waiver with a reason where the project accepts waivers?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ARCH-41`, severity minor, `file`, `symbol`, `code` = the added, removed or replaced dependency line verbatim from the diff, `fix` = the path and title of a new decision record in the project's log, or a link to an accepted record in a central documentation repository that covers the decision, `rationale` = the decision the dependency line enacts and the log directory where its record belongs).
