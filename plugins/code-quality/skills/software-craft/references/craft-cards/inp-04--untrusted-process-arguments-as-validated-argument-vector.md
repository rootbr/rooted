# A process the change starts receives untrusted values only as separate argument-vector elements with no shell, each validated so that it cannot be read as an option, and no process is started for them where a library call does the job

## Thesis
A change that needs work done on an untrusted value outside its own process uses a library call when one does that work; otherwise it starts the program with the program and each argument as separate argument-vector elements and no shell or command interpreter in between, keeps the program and its options in the code, checks every untrusted argument against an allow-list, and, where the program supports it, ends option parsing with `--` before untrusted operands, so that no untrusted value is read as a command or as an option.

## Rationale
When a shell runs the command, the code has to quote every whitespace character and metacharacter itself, and any input containing a shell metacharacter (`&`, `|`, `;`, `$`, `>`, `<` among others) may be used to trigger arbitrary command execution. One runtime documents that an argument array handed to its shell option is not escaped, only space-separated, which can lead to shell injection. A process API that takes the program and an argument vector invokes no shell and expands no glob patterns, pipelines or redirections, so every character, shell metacharacters included, can safely be passed to a child process that does not reparse its command line by shell rules. A library call removes the command line altogether: it cannot be manipulated into a task other than the one it is meant for. The vector still leaves argument injection, and every command injection is also an argument injection: an argument that starts with `-` or `/` can be read as a switch, and where the command line is split or rejoined into one string, spaces and double quotes inside an argument count as well. Argument separation therefore does not replace argument validation. An allow-list names the permitted arguments explicitly, or the permitted characters and the maximum length with metacharacters and whitespace left out (lowercase letters and digits, 3 to 10 characters, in the standard's example); `--` ends option parsing for programs that support it; and the program and its required options stay in the code rather than in input.

## Example
```typescript
bad:  const name = String(request.query.name);
      exec(`tool --format png ${name}`, done);
      execSync("tool --format png " + name);
      spawn("sh", ["-c", `tool --format png ${name}`]);
      execFile("tool", ["--format", "png", name], { shell: true }, done);
good: const name = String(request.query.name);
      if (!/^[a-z0-9]{3,10}$/.test(name)) throw new Error("invalid name");
      execFile("tool", ["--format", "png", "--", name], done);
```

## Limits
A command whose program and arguments all resolve to constants in the code carries no untrusted value and is outside the rule; a scanner for this weakness flags a process start only when an argument does not resolve to a constant. Whether the argument vector alone makes untrusted arguments safe is contested, and the answer turns on the injection and on the target. Shell-metacharacter injection: the vector removes it on POSIX systems and for Windows programs that decode their arguments by the standard convention, which most applications use; runtime documentation on this side holds that with no shell every character, shell metacharacters included, can safely be passed to a child process. Argument injection: the vector does not remove it; the security standards on the other side call for allow-list validation and `--` on top of separation, and lint rules that flag a process start, with a shell or without one, also tell the code to sanitize or validate the input. A `cmd.exe`, `.bat` or `.cmd` target on Windows: the operating system hands the program one string and the program splits it, and these targets split it by shell rules, so the vector does not make untrusted arguments safe there; one runtime suggests turning on its shell option for a batch file with untrusted arguments so that it escapes special characters, another escapes by the interpreter's rules and returns an error at spawn for a character it cannot escape safely, and a third cannot launch such a file through its no-shell call at all. Since the vector protects nothing there, the rule rests on the other mitigation the runtime documentation names, validating untrusted input so that only a safe subset is allowed: an untrusted value may reach a `.bat` or `.cmd` file, however the file is started, only after an allow-list check that admits no shell metacharacter and no whitespace. One standard accepts contextual command-line encoding of each value as an alternative to the parameterized call, and the cheat sheet lists escaping as a defense option of its own; where the target decodes an argument vector the rule still flags an encoded value sent through a shell, because the cheat sheet asks for parameterization, where it is available, together with input validation whenever a command that incorporates user input cannot be avoided, and a shell leaves the quoting of every whitespace character and metacharacter to the code; escaping confines a value to one argument, yet an attacker can still pass that argument, so the allow-list check applies to an escaped value as well. What an accepted argument points at, such as a URL's destination, is outside the rule: argument separation does not validate the destination.

## Validator
Grep the hunk for a shell option set to true, a call that runs one command string, a shell or command interpreter followed by `-c`, `/c` or `-Command`, a template or concatenated string passed as a command, and every process-start call. For each match, trace the program, its options and each argument to its origin in the hunk: a constant in the code, or a value from a request, a file, the environment, a message or another input. For each value from outside the code, check whether it reaches a shell or interpreter, whether the code builds it into one command string that the runtime or the target splits into arguments rather than passing it as its own argument-vector element, whether it reaches a `.bat` or `.cmd` file on Windows (directly or through `cmd.exe`), whether an allow-list check on it precedes the call (for a `.bat` or `.cmd` file, one that admits no shell metacharacter and no whitespace), and whether it can start with `-` or `/` with no `--` before it. Then, for a process that receives such a value, check whether a library call already does its job, such as listing or creating a directory. Validator question: **Does a value from outside the code reach a started process through a shell or command interpreter other than the `cmd.exe` that runs a `.bat` or `.cmd` file, reach such a file without an allow-list check that admits no shell metacharacter and no whitespace, reach a process as an argument with no allow-list check before the call or one that can still be read as an option, reach a target other than a `.bat` or `.cmd` file inside one command string that the code builds and the runtime or the target splits into arguments, rather than as its own argument-vector element, or reach a process started for a job a library call already does?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: INP-04`, severity major, `file`, `symbol`, `code` = the process-start call and the line that puts the untrusted value into its command or arguments, verbatim from the diff, `fix` = the same work done by the library call that does it, or the program and each argument as separate vector elements with no shell, an allow-list check on each untrusted argument (for a `.bat` or `.cmd` file, one that admits no shell metacharacter and no whitespace) and `--` before untrusted operands, in the file's language, `rationale` = names the untrusted value, where it comes from, and whether it reaches a shell, a split command string, a batch-file target or an option position).
