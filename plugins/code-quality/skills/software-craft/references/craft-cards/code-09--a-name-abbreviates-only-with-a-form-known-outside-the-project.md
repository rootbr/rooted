# A name abbreviates only with a form known outside the project, never with a contraction coined by deleting letters inside a word

## Thesis
Every abbreviation, acronym or shortened word in a name the change declares is a form that a programmer outside the project expands one way without reading the surrounding code: as a rule of thumb, one listed in a general encyclopedia (DNS, URL, ID, FQDN); a shortening in wide use among programmers or in the problem domain with few alternate readings (db for a database, sin for sine); or a universally known letter in its conventional role (i for a loop index, T for a type parameter). A word is spelled out rather than shortened by deleting letters inside it (customer, not cstmr; Sandbox, not Sbx), unless the shortened form is itself such a known form, and shorthand that only the team can expand (wgcConnections) or that expands several ways (pcReader) is spelled out as well.

## Rationale
An abbreviation is understood only once the reader translates it back into the words it stands for, so its cost depends on whether that translation is available to the reader. A form listed in a general reference, or in wide use with one reading, translates on sight or through a web search. A contraction the writer coined by deleting interior letters is one of many possible shortenings of its word, so a reader outside the project can guess its expansion but cannot confirm it; shorthand the team invented translates only for someone who already knows the project; and a form with several expansions can be translated wrongly, the reader then carrying the wrong concept into every use. The cost grows with a name's reach: an exported name is read by callers who never see its declaration or the code that would disambiguate it. Measured against full words, abbreviations as a class give mixed results. In a study in which over 100 programmers described twelve functions written with single letters, abbreviations or full words, full words gave the best comprehension, but in many cases not significantly better than abbreviations; a family of four controlled experiments with 100 participants found no difference in the effort, effectiveness or efficiency of fixing faults between code written only with abbreviated names and code written only with full-word names; a within-subjects experiment with 72 professional developers found defects on average 19% faster with whole words than with single letters or abbreviations, and found no significant difference between letters and abbreviations. None of these separates a known abbreviation from a coined one, and the naming guidelines that admit abbreviations all reject the coined contraction and most reject the team-only shorthand, so the rule asks for the full word exactly where the reader has no way to expand the form, and leaves a known form in place.

## Example
```go
bad:  func fetchCstmr(sbx *Sandbox, cstmrID string) (*Customer, error) {
          rqPath := sbx.BaseURL + "/customers/" + cstmrID
          return sbx.get(rqPath)
      }
good: func fetchCustomer(sandbox *Sandbox, customerID string) (*Customer, error) {
          requestPath := sandbox.BaseURL + "/customers/" + customerID
          return sandbox.get(requestPath)
      }
```

## Limits
Whether abbreviations belong in names at all is contested, and one condition separates the cases: whether readers outside the project know the form. One side rejects abbreviations and contractions in identifiers altogether (GetWindow rather than GetWin) and admits an acronym only when it is widely accepted and necessary, or asks that an abbreviation's meaning be easily found by a web search while letting long precedent outweigh the avoidance (sin for sine); the experiment that timed 72 developers found words faster than abbreviations. The other side accepts an abbreviation that is probably listed in a general encyclopedia or is universally known, and the fault-fixing experiments and the description study found little or no difference between abbreviated and full-word names. Both sides reject the coined contraction and the team-only shorthand, and that is where the rule flags; a known form stays. A short name that a documented language convention prescribes or permits beside its own expansion is exempt: a method receiver abbreviated from its own type (ri for a ResearchInfo receiver), a package qualifier abbreviated from the words of the names it qualifies (gtutil in gtutil.CountGoatsTeleported), and an abbreviated loop variable in a short loop over a named collection (n ranging over nodes). A project tolerance for short names in small scopes, such as variables in scope for 10 lines or fewer, parameters outside an exported interface included, admits an abbreviation inside that scope; the tolerance is the one the project context states. A name dictated from outside the code keeps its outside form: a routine that overrides or implements an inherited declaration, generated code, a wire-format, database or configuration field mapped one to one, and a binding that mirrors a foreign library's names; an existing name the change only uses is judged where it is declared. The rule weighs abbreviated and shortened words only: whether a single letter outside the conventional roles fits its variable, how an acronym is cased, and whether a name encodes its type are outside it.

## Validator
Grep the added lines for a declared name (a variable, constant, parameter, field, routine, type or module) containing a run of three or more consonants with no vowel, a capital letter before two or more consonants, a two-consonant prefix before a further word (pcReader), or a common shortened stem (usr, cnt, mgr, btn, svc, qty, Win). Split each name the added lines declare into its words at case changes, underscores and digits, and for each word that is not an ordinary word decide whether a programmer outside the project would expand it one way without the code: listed in a general encyclopedia, in wide use among programmers or in the problem domain with few alternate readings, or a universally known letter in its conventional role. Read the hunk for the exemptions: a method receiver abbreviated from its own type, an abbreviated loop variable in a short loop over a named collection, a name fixed by an inherited declaration, generated code, a mapped external field or a foreign binding; read the project context for a documented short-name tolerance and count the variable's span against it. Validator question: **Does a name declared on an added line contain an abbreviation that a programmer outside the project could not expand one way (a contraction coined by deleting letters inside a word, shorthand only the team knows, or a form with several readings) outside a documented short-name convention or tolerance and without being dictated from outside the code?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-09`, severity suggestion, `file`, `symbol`, `code` = the added line declaring the abbreviated name, quoted verbatim from the diff, `fix` = that declaration with each unknown abbreviation spelled out as its full word or replaced with its known form, and its uses in the hunk renamed to match, in the file's language, `rationale` = the abbreviation, the word or phrase it stands for, and why a reader outside the project cannot expand it: a coined contraction, team-only shorthand or several possible readings).
