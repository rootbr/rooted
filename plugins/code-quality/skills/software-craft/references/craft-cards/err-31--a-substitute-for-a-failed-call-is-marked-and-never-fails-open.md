# A substitute for the result of a failed remote call leaves the failure marked or recorded and never grants access or passes a check the call did not

## Thesis
Code that answers a failed or timed-out remote call with a substitute (a cached or stale value, a default, an empty or degraded result) uses one whose effect is benign and whose use is visible: the substitute never decides in the permissive direction the question the failed call was to answer, so it grants no access, passes no validation and lets no transaction proceed on an error from the validation it depends on; and either the returned value tells the caller that it is a substitute or the failure is recorded as a log entry or a failure metric.

## Rationale
Fault tolerance detects an error and then recovers from it or contains its effects, and one of its most common strategies replaces an erroneous value with a phony value that will have a benign effect; continuing to operate securely when access to an external resource fails, by graceful degradation for example, is a verification requirement of application security. A handler that ignores an error report is a measured cause of production incidents: among hundreds of high-severity production incidents of cloud services, 31 % of the software-bug incidents were about faults not detected or not handled correctly, and a handler that ignores the error report was one of the three main types of fault-handling problem, at 35 %. In a study of timeout problems in 11 commonly used cloud server systems, 60 % of the bugs produced no error message and 12 % a misleading one, which made them difficult to diagnose. A substitute and a record of the failure do not conflict: a fault-tolerance library updates its failure state and metrics whether or not a fallback runs, and logging unexpected errors and security control failures, such as backend TLS failures, is a verification requirement of application security. Falling back to a state less secure than the options available, such as the most permissive access control, makes the product easier to compromise, lets intended access restrictions be bypassed and gives administrators a false sense of security; it typically comes from wanting to fail functional instead of failing safe. Processing a transaction despite errors resulting from validation logic is a fail-open condition that the same security requirements prevent. A write has little to substitute: there is not much point in a fallback for a command that writes, and its failure is probably best propagated back to the caller; a failure while filling a cache, generating a report or computing offline is usually better propagated, so that the caller can retry later, than answered with a silently degraded response.

## Example
```java
bad:  try { return client.isAllowed(user, action); }
      catch (TimeoutException e) { return true; }
good: try { return client.isAllowed(user, action); }
      catch (TimeoutException e) {
          log.warn("access check timed out for {}", user, e);
          return false;
      }
```

## Limits
The rule is contested on whether a substitute may stay silent, and the substitute's effect together with the record of the failure separates the cases. On one side (the Source entries marked substitute), returning a neutral value is listed among the error-handling techniques in use and a phony value with a benign effect among the most common fault-tolerance strategies, with no condition that the failure be visible; returning null or an empty list counts as failing silently, the equivalent of returning an empty response or removing functionality; and graceful degradation is an accepted answer when access to an external resource fails. On the other side (the entries marked visible), an application fails securely, preventing fail-open conditions, and logs unexpected errors and security control failures, while ignored error reports and timeout bugs without an error message recur in studies of cloud incidents and bugs. Silence toward the caller is accepted where the substitute only removes a feature or returns an empty response with a benign effect, provided the failure itself is recorded, whether or not a fallback runs. A static fallback that defaults a true/false answer based on user credentials to true grants access or passes a check, and that is the fail-open state that a weakness catalogue and an application security standard treat as a defect, and the rule follows them there.

## Validator
Grep the added lines for a fallback, degraded, stale or last-known value; a handler that catches a timeout, connection, I/O, HTTP or RPC failure, or every error; a promise or result handler that maps an error to a literal or a default value; an access, authorization or authentication flag set to true; and an error branch that returns a literal with no error. Open the file, find the remote call whose failure the handler answers and the value the handler returns in place of the call's result; skip a handler that retries the call, reads the same answer from another replica or propagates the error, since it substitutes nothing. Name the decision the call makes. Where it decides access, permission, authentication or a validation that the code then acts on, check whether the substitute is the permissive answer (allowed, authenticated, valid, proceed). For any other substitute, look for the mark: a log or metric call in the handler, an error reported to a tracker, a fault-tolerance wrapper around the call that records its failures, or a returned value the caller can tell from a real result (a flag, a wrapper or status type, an explicit degraded variant). Validator question: **Does an added handler answer a failed remote call with a substitute that grants access, passes a validation or lets a transaction proceed, or with a substitute that neither marks itself nor leaves the failure recorded?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-31`, severity major, `file`, `symbol`, `code` = the added handler line that returns the substitute or sets the permissive answer, verbatim from the diff, `fix` = the same handler denying the access or failing the check, propagating the error, or returning a substitute the caller can tell from a real result, with the failure logged or counted, in the file's language, `rationale` = which remote call failed, what the handler substitutes, and whether the substitute grants access or passes a check or leaves the failure unmarked and unrecorded).
