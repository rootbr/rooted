# A message that reports on a program's own operation goes through the logging facility rather than a print or console call, while a command-line program's output to its user may be printed

## Thesis
A message that reports on the program's own operation goes through the codebase's logging facility rather than a print call, a console call or a direct write to standard output or standard error. Such a message reports an event that occurs during normal operation, for status monitoring or fault investigation; a runtime event that should still be noted although the client code can do nothing about it; or an error that a handler suppresses without passing it on to its caller, and a handler that reports a caught exception logs it through the facility rather than printing its stack trace. Output addressed to the program's user, the console output of ordinary use of a command-line program with its results and its messages to that user, is not such a message and may be printed.

## Rationale
A print or console call writes its text to standard output, standard error or a browser's console, and an exception's print-stack-trace call writes the trace to the standard error stream. Such output is not configurable by the program's clients, unlike the statements of a logging facility: through a logger the output can be enabled or disabled at will and by priority, so that it need not clog the standard output. The facility takes a modular approach: loggers expose the interface the code calls and create the records, filters determine which records to output, handlers send them to a destination (the console, a file, an HTTP endpoint, email, a socket, a queue or the system log) and formatters specify their layout. A program that writes its reports directly to the standard streams does not meet what a log needs, to be easily accessible, uniformly formatted for readability and properly recorded.

## Example
```java
bad:  void refresh(Cache cache) {
          int count = cache.reload();
          System.out.println("cache reloaded: " + count + " entries");
      }
good: void refresh(Cache cache) {
          int count = cache.reload();
          logger.info(() -> "cache reloaded: " + count + " entries");
      }
```

## Limits
Whether production code prints at all is contested, and the kind of output separates the cases. On one side, production code should not print to standard output or standard error, which should only be used for debugging, and print checks exist to catch debugging remnants that people print while debugging and forget to remove; one tool files those checks in a category that is off by default and whose checks may flag perfectly reasonable code. On the other side, print is the best tool to display console output for ordinary usage of a command-line script or program, a print that produces output as part of a command-line interface program is not typically a problem, in a script runtime outside the browser the console is used to output information to the user and not strictly for debugging, and one linter removed its console check from its recommended set as not broadly applicable and a source of false positives where console output is acceptable, such as in command-line applications. The separating condition is whether the output reports on the program's own operation or is the program's own output to its user: the first goes through the logging facility, and the second may be printed, a command-line program's error messages to its user included. The facility's own handlers, which print records to the console as the simplest way of handling them, are part of the facility and lie outside the rule. The rule judges production code, the scope its sources address; a test, and a documentation example, which one checker excludes by default, lie outside it. A project may tolerate chosen console methods, as one linter's option allows chosen methods such as warn and error; a call that the tolerance stated in the project context allows is not a finding. A temporary print added while hunting a bug, the standard stream a message goes to, the level a record takes and the content it carries are judged by their own rules.

## Validator
Grep the added lines for a print call, a console call, a formatted print to a standard stream, a direct write to standard output or standard error, and a call that prints an exception's stack trace. Open the file and read the routine around each hit, the file's entry point and its imports to decide whom the text addresses. Treat the text as the program's output to its user when the file is a command-line program's entry or command code and the text is its result, a prompt, usage or help text, a progress or status message for its user, or an error message for its user. Treat it as a report on the program's operation when it states that something started, finished, changed state, was retried or failed, carries a count, an id or a timing for whoever operates or debugs the program, or prints a caught exception, in a service, a library, a background job or other code whose output no user reads at a terminal. Skip a hit inside the logging facility's own handler, in a test or a documentation example, a temporary print added while hunting a bug, and a console method the project context tolerates. Look in the file, its imports and the project context for the logger the codebase already uses, to name it in the fix. Validator question: **Does an added print, console call, standard-stream write or stack-trace print report on the program's own operation, such as its status, a noted event or a handled failure, rather than give a command-line program's output to its user?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-48`, severity minor, `file`, `symbol`, `code` = the added print, console, standard-stream or stack-trace call, verbatim from the diff, `fix` = the same report written through the codebase's logger, with a caught exception passed to the logger, in the file's language, `rationale` = which report on the program's operation bypasses the facility and what it loses: filtering by level, routing to a destination and a uniform layout).
