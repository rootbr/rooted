# A construct whose intent the code alone does not show, such as an empty routine body, a switch fall-through, a suppressed check or an unsafe block, carries a comment marking it as intended

## Thesis
Four constructs do not show from the code alone whether they are intended, or why: a function, method or constructor whose body is empty or holds only a placeholder statement that does nothing; a switch statement group through which some path reaches its end without a break, continue, return or throw, so that execution continues into the next group; a directive or attribute that silences a compiler, type-checker or linter finding; and an unsafe block. Each carries a comment at the construct that marks it as intended. The comment of an empty body sits inside the body, where a documentation string also counts, and for an intentionally blank override it explains the reason for the blank. The comment of a fall-through sits at the end of the statement group that falls through, and any comment that communicates fall-through suffices. The comment of a suppression sits on the directive's own line or in the directive's reason or description field and says why the silenced check is to be ignored where the directive applies. The comment of an unsafe block sits on the lines directly before the block and says why the operations inside are safe and which invariants they rely on. An empty body that is an unintentional omission is fixed by implementing it, and one for an operation that is not yet, or never will be, supported throws an error saying so.

## Rationale
A reader of an empty body has to guess whether it is intentional, and may take it for an implementation that fulfils a specific and identified requirement. A body is empty for one of several reasons: an unintentional omission, which should be fixed to prevent unexpected behaviour in production; an operation that is not yet, or never will be, supported; or an intentionally blank override. Commenting the intentional empty bodies makes intentional and unintentional ones easier to tell apart. In a switch whose groups fall through implicitly, the language has no way to indicate that a fall-through is intentional, so the practice is to always mark an intended fall-through with a comment; with the comment there is no confusion as to the expected behaviour, and an unmarked fall-through can be flagged as unintentional. A suppression directive without an explanation leaves the reader with no idea why it is there; its reason acts as documentation for other people reading the code, including its author later, and justifying each suppression helps readers understand the reasoning and may allow removing it once its purpose is obsolete. An unsafe block without its justification makes the code difficult to read and maintain, and writing out why its operations are safe may help in discovering unsoundness or bugs.

## Example
```go
bad:  func (memStore) Flush() {}
      sum := md5.Sum(data) //nolint:gosec
good: func (memStore) Flush() {
          // Intentionally empty: memStore buffers no writes, so there is nothing to flush.
      }
      sum := md5.Sum(data) //nolint:gosec // MD5 only buckets cache keys here; it guards no secret.
```

## Limits
An empty error handler, and whether a given suppression is justified at all rather than explained, are outside this rule. One tool rule for empty methods raises no issue for an abstract method, or an empty method in an abstract type, that subtypes are meant to override, while noting that such a method should normally carry documentation explaining how to implement it; the same rule skips non-public no-argument constructors and a public no-argument constructor declared beside other constructors, and another tool rule skips private constructors and constructors annotated for dependency injection. A statement group that terminates abruptly on every path, with a break, continue, return or throw, does not fall through; the last group of a switch has nothing to fall into and needs no comment, and neither do case labels stacked with no statement between them. A switch form without fall-through has nothing to mark, and in a language whose switch leaves a clause unless an explicit fall-through statement indicates that control flows on into the next clause, that statement marks the intent. Any comment that communicates fall-through suffices, and a linter lets a project set its own marker pattern; a project context that sets one decides what counts. One style guide asks for a suppression's explanation only where the reason is not clear from the symbolic name of the silenced check; a project context that adopts that convention rejects the finding for a suppression whose check name already makes its reason clear. A definition the language marks as declaration-only, such as an overload signature that only a type checker reads or a function in a type stub file, whose body a language standard recommends be a single placeholder, shows its intent in the code and is outside this rule, and so is a method whose annotation declares it a pointcut, which the same empty-method tool rule exempts.


Where production code reaches the routine, an operation that is not yet supported is not settled by a throwing placeholder; the throwing form answers only an operation that will never be supported, its message saying so.

A suppression whose symbolic rule name makes its reason clear at the site is outside this rule, which leaves the reason a suppression carries to the rule on suppressions.
## Validator
In the hunk's added lines, find four constructs. For an empty body — a function, method, constructor or function literal whose body holds no statement or only a placeholder statement that does nothing — read the body for a comment or a documentation string inside it. For each added case label, read the statement group that ends at that label, which an appended label turns from the last group into one with a group after it, and the statement group the label opens; also read each statement group the change edits; a group runs up to the next label, and it falls through when it holds a statement, some path through it reaches its end without a break, continue, return, throw or explicit fall-through statement, and it is not the last group; a group whose last statement is a conditional or block whose every branch ends in one of those does not fall through; look for a comment at its end that communicates fall-through. For a directive or attribute that silences a compiler, type-checker or linter finding, read its own line and its reason or description field for why the silenced check is to be ignored there. For an unsafe block, read the lines directly before it for a comment saying why it is safe. Skip an abstract method, an empty method of an abstract type, a declaration-only definition the language marks as such, such as an overload signature or a function in a type stub file, an empty private constructor, a non-public no-argument constructor, a public no-argument constructor declared beside other constructors, a constructor annotated for dependency injection, a method annotated as a pointcut declaration, an empty error handler, and a construct that follows a marker or suppression convention the project context states. Validator question: **Does the hunk add an empty function, method or constructor body with no comment or documentation string inside it, a switch statement group, added or followed by an added case label, that falls through into the next with no comment saying so, a suppression with no stated reason why the silenced check is to be ignored there, or an unsafe block with no comment directly before it saying why it is safe?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: CODE-64`, severity minor, `file`, `symbol`, `code` = the empty body, the last line of the group that falls through with the next case label, the suppression directive, or the line that opens the unsafe block, quoted verbatim from the diff, `fix` = the same construct in the file's language with the comment that marks it as intended — why the body is empty, a fall-through marker, why the silenced check is to be ignored there, or why the unsafe operations are safe — or, for an empty body left by omission or for an unsupported operation, the body implemented or throwing an error that says the operation is unsupported, `rationale` = which of the four constructs it is and what a reader cannot tell about it without the comment).
