# A routine the change adds does not re-implement a job that an existing routine of the codebase already does, unless it is a small copy and reaching that routine would add a dependency the module is kept free of

## Thesis
Before a change adds a routine such as a helper, a validation or a business rule, the codebase is searched for an existing routine that already does the same job, whatever its names, algorithm or structure. Doing the same job means giving the same results for the inputs the new code's callers pass; a routine shaped like the new code that checks or computes something else, even for some of those inputs, does another job. When such a routine exists and the new code can call it in its own language and process, the change calls it instead of adding a second implementation, whether the routine sits in the same module, in a module or library the module already depends on, or in one the module may come to depend on. The one exception is a dependency the module is kept free of, by a stated dependency policy or a stated reason beside the copy: there a small copy of the routine is accepted.

## Rationale
A second implementation of an existing job written with different code is duplication that token matching cannot find. Routines that do the same thing written differently, restructured or in another language, share no token run and no syntax tree for a token or syntax-tree pass to match. On one detector's demonstration project, with eight rules written on both sides of a two-language system and two features written twice within one language, the default scan reports no clone; only the detector's experimental semantic pass, which compares routines with a code embedding model, reports eight of the pairs, and ten with a lower bar for pairs within one language. Such pairs arise when one half of a project repeats a rule the other half enforces, and when two people in one codebase each solve the same problem their own way. The planned code can be checked against the codebase before it is written, while a token-based detector run afterwards stays silent. At the scale of a whole system, duplicated functionality has been observed as debt: along the main releases of one operating-system lineage, which has evolved for almost five decades, architectural technical debt accrued in the forms of functionality duplication and unused facilities. Calling the existing routine is construction with reuse, which creates new software with the reuse of existing assets and counts the selection of the reusable units among its tasks; systematic reuse can enable significant productivity, quality and cost improvements.

## Example
```rust
bad:  // pricing::cart_total(&cart.lines) already sums price * qty
      fn invoice_total(cart: &Cart) -> u64 {
          cart.lines.iter().map(|l| l.price * l.qty).sum()
      }
good: fn invoice_total(cart: &Cart) -> u64 {
          pricing::cart_total(&cart.lines)
      }
```

## Limits
The rule is contested where reaching the existing routine needs a dependency the module does not yet have, and the condition that separates the cases is whether the module is kept free of that dependency. Where it is not, the change calls the routine: the most popular method of reuse is to reuse code from the libraries provided by the language, the platform, the tools in use or an organizational repository. Where calling the routine would make the module depend on a package it is kept free of, a small copy is accepted. One language's standard library keeps simple file input/output and string manipulation of its own in its networking package, to avoid depending on its conversion, buffered input/output and string packages; a test in the same library checks, as a statement of policy, that some low-level packages do not have new dependencies added, and keeps large dependencies out of the networking package because that package is unavoidable when doing any networking. A published style guide for the same language states that the language often favors a little copying over a little dependency, and bounds that preference: maintaining perfectly mirrored interfaces across many packages can create an unnecessary burden. Reuse through a dependency carries a cost of its own: as a published review of that operating-system study and a companion study of the same system quotes the two, the adoption of third-party subsystems facilitates evolution through reusability but incurs technical debt. In that standard library the freedom from the dependency is stated twice, by the comment beside the copy naming the packages it avoids and by a policy a test enforces; in a project, a documented tolerance in `project_context` states it as well. Related code is not a second implementation: a client function and the server endpoint it talks to, a route and its test, and two implementations of one interface resemble each other without being duplicates. A project that configures its duplicate detection to ignore duplication between folders owned by different teams has documented that tolerance for those folders. A plain implementation kept beside a routine rewritten for speed, as the reference that a test compares the tuned routine with and the version to revert to once the tuned one outlives its usefulness, is not a second implementation of the job.


A routine that a package of at most 35 lines of code and McCabe complexity at most 10 would supply, where that package brings packages of its own into the dependency tree, is written in the project's own code without a stated reason, since the rule on new dependencies weighs such a package against the transitive dependencies it brings.
## Validator
Read each added routine the trigger matched, together with its body, and state its job in one line: what it takes, what it returns or changes, and the rule it applies. Search the repository for an existing routine with that job: grep the nouns and verbs of the new routine's name and their common synonyms, the literals, patterns and constants its body uses, and the routines it calls; open the modules the file already imports and the shared helper, utility and validation modules. Skip candidates the new code could reach only in another language or another process. For each candidate, compare its results with those of the new code for every input the new code's callers pass, edge cases included (empty, absent, boundary and malformed values), and drop it when they differ for any such input, or when it is related code rather than a second implementation: a client of an endpoint, the test of a route, another implementation of one interface, or the plain reference implementation kept beside a routine rewritten for speed for a test that compares the two. For a candidate that does the same job, establish whether the new code's module already depends on the candidate's module. Note whether the candidate is private to its module and whether its module depends on the new code's module; the fix then makes it visible or moves it to a module both may depend on. When it does not, look for a stated reason to stay free of that dependency: a comment beside the new code naming the dependency avoided, a dependency or layering rule the repository enforces, a tolerance in `project_context`, or a duplicate-detection setting that ignores duplication between the two folders; drop the candidate when such a reason exists and the added routine is a small copy of the candidate's job. Validator question: **Does the change add a routine that re-implements, rather than calls, the job an existing routine of the codebase already does for every input the new routine's callers pass, where calling that routine adds no dependency the module is kept free of, or the added routine is more than a small copy?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-26`, severity minor, `file`, `symbol`, `code` = the added routine's signature line, quoted verbatim from the diff, `fix` = the added routine's body, or each of its callers, calling the existing routine by its module path, in the file's language, with that routine made visible to the new code's module where it is private to its own, or moved to a module both may depend on where its own module depends on the new code's module or is one the new code's module is kept free of, `rationale` = names the existing routine's file and symbol, the job both do, and the dependency through which the module reaches it).
