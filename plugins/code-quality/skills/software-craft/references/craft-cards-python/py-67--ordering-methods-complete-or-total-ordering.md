# A Python class that defines one of __lt__, __le__, __gt__ or __ge__ defines the other ordering methods or is decorated with functools.total_ordering

## Thesis
A Python class that defines one or more of `__lt__`, `__le__`, `__gt__` and `__ge__` defines all four, or is decorated with `functools.total_ordering` and supplies `__eq__` beside its ordering method.

## Rationale
Beyond `__ne__` delegating to `__eq__` and inverting the result by default, Python implies no relationship among the comparison operators: the truth of `(x<y or x==y)` does not imply `x<=y`; `__lt__` and `__gt__` are each other's reflection, and `__le__` and `__ge__` are each other's reflection. The order comparisons `object` provides by default raise `TypeError`. A class with `__lt__` alone therefore answers `<`, and `>` through the reflection, while `<=` and `>=` find neither a method nor its reflection and raise `TypeError`; sorting may fail or produce incorrect results, and code that expects symmetric comparisons may behave unexpectedly. Given a class defining one or more rich comparison ordering methods, `functools.total_ordering` supplies the rest; the class must define one of `__lt__`, `__le__`, `__gt__` or `__ge__` and should supply `__eq__`. With every operation implemented or generated, the class no longer relies on other code to exercise only a particular comparison.

## Example
```python
bad:  class Version:
          def __eq__(self, other): return self.key == other.key
          def __lt__(self, other): return self.key < other.key
      first <= second  # TypeError: '<=' not supported
good: @functools.total_ordering
      class Version:
          def __eq__(self, other): return self.key == other.key
          def __lt__(self, other): return self.key < other.key
```

## Limits
The rule applies to a class that defines one or more of the four ordering methods; a class that defines equality alone is outside it. `functools.total_ordering` makes no attempt to override methods declared in the class or its superclasses, so if a superclass defines a comparison operator, the decorator does not implement it again, even if the original method is abstract. The decorator comes at the cost of slower execution and more complex stack traces for the derived comparison methods; where performance benchmarking indicates this is a bottleneck, implementing all six rich comparison methods instead is likely to provide an easy speed boost.

## Validator
Grep the hunk for `def __lt__(`, `def __le__(`, `def __gt__(`, `def __ge__(` and for `total_ordering`. Open the file at the class that holds the match: list which of the four ordering methods it defines or inherits from a base class other than `object`, read the decorators above the `class` line, and look for `__eq__` in the class, in its bases, or generated by a `@dataclass` whose `eq` is left true. Validator question: **Does a class that defines at least one of `__lt__`, `__le__`, `__gt__`, `__ge__` lack one of the four without a `functools.total_ordering` decorator, or carry that decorator with no `__eq__` beyond the one `object` provides?** Yes → flag.
