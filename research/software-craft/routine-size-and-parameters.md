# Research note — Routine size and parameters

Topic `routine-size-and-parameters` of group A. Code inside a function, domain `code`, id prefix `CODE`. Formulation locators: CC7 (Code Complete 2nd ed. ch. 7 'High-Quality Routines': §7.4 'How Long Can a Routine Be?', §7.5 'How to Use Routine Parameters'); APOSD ch. 9 'Better Together Or Better Apart?' (splitting and joining methods); johnousterhout/aposd-vs-clean-code README.md, section 'Method Length'; the 97 Things essay 'Write Small Functions Using Examples' (thing 94). Marked contested in the design note.

The canon agrees that a routine does one cohesive job, that long parameter lists, boolean flags that choose a code path, output parameters and reassigned parameters make routines harder to read, and that related routines take shared parameters in the same order (Code Complete ch. 7, Clean Code ch. 3, Refactoring, Effective Java Item 51, A Philosophy of Software Design ch. 9). It splits on routine length and on how far to decompose. Bounds run from Clean Code's two to four lines, through Google's prompt to reconsider at about 40 lines, to Code Complete's 100 to 200 lines. In the aposd-vs-clean-code README, Martin and Ousterhout agree that decomposition is good and that over-decomposition is possible, but they weigh entanglement differently. It also splits on the strictness of the parameter rules: the count bound runs from three to seven, booleans are banned outright or accepted when they carry a value, and output parameters are preferred for status or avoided. Industry practice shows the same disagreement. Tool defaults run from 50 to 150 lines and from 3 to 13 parameters, most length checks are off by default, and RuboCop is moving MethodLength and ParameterLists to disabled by default. The evidence is observational and uneven. Chowdhury, Uddin and Holmes (MSR 2022, arXiv:2205.01842) find that change- and bug-proneness rise with method SLOC across about 785K Java methods, and that groups of small methods are less change- and bug-prone than one large method of the same total size. Hermans and Aivaloglou (ICPC 2016) find that Long Method lowers understanding. But El Emam et al. (TSE 2002) find no threshold effect of size, and Fenton and Ohlsson (TSE 2000) find no link between module size and fault density, so a length bound is a prompt, not a measured threshold. Rice et al. (OOPSLA 2017) give the only parameter bound measured against defects: argument selection defects rise markedly above five arguments. DeepBugs shows that swapped arguments are a real bug class. Flag parameters, output and in-out parameters, parameter reassignment and parameter order rest only on official documentation and on rule pages of tools run in practice; no empirical study of them could be opened. Nine rules ship as cards. Each contested card carries a sourced separating condition: separability for length, value versus selector for booleans, and caller-owned data for output parameters. How far to decompose a routine stays pending without a separating condition. Pass-through parameters and a single level of abstraction stay pending without evidence.

## Formulation layer

The canon agrees that a routine should do one cohesive job, that long parameter lists, boolean flags passed as literals, output parameters and reassigned parameters make routines harder to read, and that related routines should take parameters in the same order (McConnell CC2 ch. 7; Clean Code ch. 3; Fowler's Long Function, Long Parameter List, Remove Flag Argument and Remove Assignments to Parameters; Bloch Item 51; Google C++/Go, Uber Go, Rust API Guidelines, .NET design guidelines). The canon splits on two questions. The first is routine length: Clean Code says 2–4 lines and hardly ever 20, 97 Things #05 says 5–10, Google says to rethink at about 40 with no hard limit, Power of Ten caps at 60 lines, McConnell lets routines grow to 100–200 lines, JSF AV caps at 200 LSLOC, and Ousterhout says length alone is rarely a reason to split. The johnousterhout/aposd-vs-clean-code README (fetched) records this as a disagreement about weighting. Both authors agree that decomposition is good and that over-decomposition is possible. They disagree on the One Thing Rule, on entanglement ('conjoined methods') and on how far to decompose. The second question is how strict the parameter rules are: the count threshold (Martin 3, Bloch 4, McConnell and JSF 7), whether booleans are always bad (Martin) or acceptable when the routine name makes them clear (Bloch), when they initialize boolean properties (.NET), or as option values (Google Go), and whether output/status parameters are acceptable (McConnell prefers them; Martin, Google C++, Rust C-NO-OUT, .NET and the Python FAQ advise against). The books themselves were not openable. Code Complete, A Philosophy of Software Design, Clean Code, Refactoring, Effective Java and Beck reached me only as third-party GitHub copies or notes, so those items are 'relayed', and Meyer's Operand Principle is unfetched (GitHub code search for it found nothing). Code Complete §7.4 lists studies that are leads for the evidence layer. 97 Things #94 does not state a line-count rule despite its title, and the TypeScript handbook (More on Functions), PEP 3102 and PEP 570 document parameter mechanisms only (Example-level). SWEBOK V3 Construction and Software Engineering at Google contain no rule on routine length or parameter count.

## Reception layer

On routine length the canon openly disagrees. In johnousterhout/aposd-vs-clean-code, Martin defends decomposing code under the One Thing Rule, and Ousterhout holds that this over-decomposes into shallow, entangled methods. Practitioner sources take both sides: the Linux kernel, TigerBeetle's 70-line hard limit and clean-code-javascript favour short functions, while matklad and Google's style guides ("no hard limit… think at about 40 lines") call for judgment. RuboCop 1.91.0 (2026-09-10) disables MethodLength and ParameterLists under its Preview channel, ahead of turning them off by default in 2.0, and notes that a third and a fifth of projects reject them. Tool defaults vary widely and most of these rules are off in the default rule sets, so a default is never evidence of a threshold. For length: ESLint 50 lines or 10 statements, Pylint and Ruff 50 statements, funlen 60 lines, Sonar 75/100/120, clippy 100, Checkstyle 150. For parameter count: ESLint 3, Pylint and Ruff 5, Checkstyle, clippy and Sonar Java/Go 7, revive 8, PMD 10, Sonar Python 13. On parameter shape no named source objects. Boolean selector parameters are discouraged by Sonar S2301, clippy, Ruff FBT, revive, Rust C-CUSTOM-TYPE, Uber and .NET, with carve-outs for two-state constructor booleans and literal comments at the call site. Output parameters are discouraged by Google C++ and .NET CA1021, and TigerBeetle's out pointers for in-place initialisation are a named counter-position. Reassigning a parameter is flagged outright by PMD, Checkstyle, ESLint and revive, while Sonar S1226 flags only reassignment before the first read. WebSearch was exhausted and HN, Lobsters, Medium, martinfowler.com and the publishers were unreachable. So Sridharan's, Carmack's and Fowler's positions and the Hatton 1997 and Chowdhury 2022 papers are recorded unfetched. Only the Hermans & Aivaloglou 2016 and Barbosa et al. 2022 abstracts were opened, through the neverworkintheory bibliography.

## Evidence layer

Research backs the length rule only with observational studies. The strongest is Chowdhury, Uddin and Holmes (MSR 2022, arXiv:2205.01842; the candidate list had the wrong co-authors). It covers about 785K Java methods and finds change- and bug-proneness rising with SLOC, with 24 SLOC as a benchmark-derived bound and decomposed methods less maintenance-prone. It is supported by a controlled experiment (Hermans 2016, Long Method hurts understanding in Scratch novices), an fMRI study (Peitek 2021, textual size drives attention) and class-level smell studies (Palomba 2018, Khomh 2012). The parameter-count rule rests on Rice et al. (OOPSLA 2017): defects where the wrong argument is passed, measured on 200M lines at Google, rise markedly above five arguments. DeepBugs shows swapped arguments are a real bug class. Flag parameters, output and in-out parameters, reassigning a parameter and keeping parameter order consistent have no empirical study I could open. They rest on official documentation (Google C++/Go/Python guides, Effective Go, Python FAQ, .NET design guidelines, Rust API guidelines, Uber Go) and on rule pages of tools run in practice (Checkstyle, PMD, ESLint, Pylint, Ruff, clippy, Sonar, Error Prone, revive, funlen). Their default bounds disagree widely: 3 to 13 parameters, 50 to 150 lines. The canon disagrees in two places. Hatton 1997 says medium-sized components are more reliable than small ones, El Emam 2002 calls that U-curve a statistical artifact and finds no threshold, and Fenton and Ohlsson 2000 find no link between module size and fault density, so a length threshold has no research basis even where a trend does. Ousterhout's over-decomposition position has only indirect research support (Letovsky and Soloway's delocalized-plans abstract). Woodfield 1981 and the papers behind Stevens/Myers/Constantine and Pradel and Gross 2011 could not be opened. WebSearch was exhausted, so papers were reached only through copies on GitHub (full texts, abstract dumps, neverworkintheory posts).

## Spine — candidate rules in source order

1. **A routine is split only into pieces that can each be understood without reading the code of the others** — Extract a piece of a routine only when the piece and what remains can each be read without the other's implementation. Pieces that force a reader to flip back and forth between them are conjoined, and they read better joined. The opposing position extracts every piece that can be given a descriptive name and does less than the original, down to routines a few lines long, and relies on callee names to keep callers readable. Both positions agree that decomposition is good and that over-decomposition is possible. They disagree on how far to go.

3. **A routine performs one cohesive job and does not bundle operations whose results and effects share no data** — Each routine is responsible for one task.
