# Changing the documented or declared return value, raised errors, side effects or defaults of a published element for inputs callers already pass is a breaking change even when every call still compiles

## Thesis
For the arguments and state existing callers already use, a published element keeps the released behaviour that its documentation or its declaration states: its return values, its side effects and the events it fires, the exceptions it raises or the errors it returns, its default values, the values of its enumeration constants, and the conditions under which it calls overridable methods. A change to any of these is a breaking change although every call still compiles, so it ships either as an addition that leaves existing calls alone — a new element, a configuration method, or a new option or field whose default keeps the released behaviour — or as a declared breaking change: a new major version or module path, or the end of a deprecation period where the project's compatibility policy runs one. A fix that brings the element in line with its specification is exempt, as are the narrow refinements compatibility policies allow, such as raising a more derived error or rewording an error message.

## Rationale
Behaviour changes can break callers even when their code continues to compile: a caller that relied on the released behaviour can start receiving errors where it did not before, or a condition it tests on the result is no longer entered. A changed default is the silent case — a caller that omits the argument still receives a default, now the new one, with no immediate error, and the incorrect behaviour that follows can be difficult to detect, understand and fix. The compatibility promise of a public interface therefore covers more than names, types and argument positions. Given a set of arguments, it covers the return value, side effects and raised exceptions; the documented exceptions and the semantics that lead to their raising; the returned values and the precision of a numeric result; the default value of a property, field or parameter; the value of an enumeration member; the order in which events are fired and the number of times they are called; and the conditions under which overridden methods are called. Removing a call to an overridable member is breaking; so is widening the inputs an overridable member accepts, since existing overrides will not function correctly for the extended range. An addition keeps the promise: a caller that does not call the new configuration method keeps the old behaviour, and a new field whose zero value preserves the old behaviour lets existing code that does not set it continue to work. When the change cannot be an addition, the version carries it: a backward incompatible change to the public API increments the major version or moves to a new module path. Breaking changes shipped outside a major version reach dependents whose package managers update automatically; in one package ecosystem, around 12% of the dependent packages and 14% of their releases were impacted by a breaking change during updates of non-major releases of their dependencies.

## Example
```rust
bad:  pub fn parse_port(s: &str) -> Result<u16, PortError> {
          if s.is_empty() { return Err(PortError::Empty); } // released and documented: Ok(DEFAULT_PORT)
          ...
      }
good: pub fn parse_port(s: &str) -> Result<u16, PortError> {
          if s.is_empty() { return Ok(DEFAULT_PORT); }
          ...
      }
      pub fn parse_port_strict(s: &str) -> Result<u16, PortError> { ... }
```

## Limits
Elements outside the public interface are outside the rule: names the code's visibility declarations or a leading underscore mark as internal, elements documented as private, and elements documented as provisional; an element that is simply undocumented is not private for that reason. Under semantic versioning, major version zero is initial development, where anything may change at any time. A fix for a bug that violates the element's specification may break a caller that depends on the faulty behaviour, and compatibility policies reserve the right to make such fixes within their compatibility promise. A correction from the value an element returns to the value its author intended, rather than to one its specification states, is still a change of returned values and counts as breaking; and where restoring the behaviour the public interface specifies would drastically impact a large audience, a major version may be the better signal even though the fix could strictly be a patch. These changes keep compatibility: raising a more derived error than the one already raised; raising a new error only on a code path that new argument values or new state reach; ceasing to raise because an element that cannot be overridden now supports inputs it used to reject; returning a value of a more derived type without changing the static type; changing the text of an error message; and a change meant to improve performance that leaves the element's other behaviour unchanged, although code that relies on the current speed of an operation can still break. Behaviour that neither the documentation nor the declaration states is outside the rule, because compatibility policies divide on it: one counts a change in parsing that throws new errors as breaking even when the parsing behavior is not specified in the documentation, while another expects an interface to give explicit contracts for its behavior via documentation and permits behavior that is not part of this contract to change in minor revisions. Where the documentation declares a property unspecified or undefined, the rule does not reach it, since programs that depend on unspecified behaviour may break in future releases. A compatibility policy the project context states that permits the change, such as a declared major-version-zero or provisional status, rejects the finding.

A release below 1.0.0 is outside the rule, except where the project or its package manager treats the leftmost non-zero version component as the breaking-change indicator, as a caret range does; there a change that keeps that component is in the rule.

## Validator
Grep the added lines for a raise or throw, an error constructor or error return, a default value in a parameter list or a defaults implementation, an enumeration or constant value, and a return of a literal or a named constant. For each match, open the base version of the file with `git show <base_sha>:<path>` and find the element that encloses it; keep only elements public in both versions — exported by the code's visibility declarations, not underscore-prefixed, not documented as private or provisional, in a release past major version zero or in one below 1.0.0 where the project or its package manager treats the leftmost non-zero version component as the breaking-change indicator and the change keeps that component. Trace one call the base version accepted — arguments and state an existing caller can already pass — through both versions and compare what it returns, which error it raises or returns, which side effects and events it produces and in what order, which default it takes, which constant value it sees, and when it calls an overridable member. Where they differ, check whether the diff keeps the base behaviour for that call and offers the new one through a new element, a configuration method or a new option whose default is the base behaviour; whether the diff declares a breaking change (a major version or module-path change, a breaking-change entry, a behaviour change made at the end of a stated deprecation period); whether the base behaviour violated the element's specification; whether the base version's documentation or declaration states the changed behaviour at all, and whether the documentation declares the changed property unspecified or undefined; and whether the change is one of the compatible kinds: a more derived error, an error only new arguments or state reach, a wider accepted range on an element that cannot be overridden, a return value of a more derived type under the same static type, a message-text change, or a performance change with no other effect. Validator question: **does the diff change, for arguments and state the base version already accepted, the return value, raised or returned error, side effect, default value, enumeration constant value or overridable-call condition that the base version's documentation or declaration states, of an element public in both versions, with no addition keeping the base behaviour for the calls existing callers already make, no declared breaking release, and none of the specification-fix, declared-unspecified or compatible-change cases applying?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: API-20`, severity major, `file`, `symbol`, `code` = the added line that changes the behaviour, quoted verbatim from the diff, `fix` = the released behaviour kept for existing calls and the new behaviour offered through a new element, a configuration method or an option whose default keeps the released behaviour, in the file's language, `rationale` = naming the call existing callers already make and how its result, error, effect or default now differs).
