# Research note — Error and exception handling

Topic `error-and-exception-handling` of group D. Errors and resilience, domain `errors`, id prefix `ERR`. Formulation locators: SW4.5 (SWEBOK Guide V4.0 ch. 4 §4.5 'Error Handling, Exception Handling, and Fault Tolerance'); CC8 (Code Complete 2nd ed. ch. 8 'Defensive Programming', §8.4 Exceptions, §8.5 Barricade); PP 'Dead Programs Tell No Lies' (The Pragmatic Programmer, 20th anniversary ed., topic 24) and 'Crash Early'; the 97 Things essays on exceptions and on 'Prevent Errors'; SEG (Software Engineering at Google) where it treats error handling.

The canon agrees on a small core. SWEBOK §4.5 (in its V3.0 wording), Code Complete ch. 8, The Pragmatic Programmer topic 24, the 97 Things essays and SEG ch. 8 all say: never drop a caught or returned error silently, make an error carry the context of its failure, catch specifically and only where the code can act, and do not limp on past an impossible state. The evidence is strongest where the canon agrees. Yuan et al. (OSDI 2014, relayed through reading notes) trace 92% of the 48 catastrophic failures they studied to mishandled non-fatal errors, and 35% to trivial handler mistakes: ignored errors, handlers that only log, TODO handlers, and a catch-all followed by an abort. Liu et al. (HotOS 2019, relayed) find handlers that ignore or over-react behind Azure incidents. MSR and ICPC mining studies of Java and C# show empty handlers and generic catches are widespread. Of these anti-patterns, Dummy Handler and Generic Catch correlate with post-release defects. The mining data measure prevalence and correlation, not the effect of following a rule. CERT (ERR00-J, ERR04-J, ERR08-J, ERR33-C), CWE (252, 390, 396, 397, 460, 584) and ASVS 5.0 V16.5 back the rest. So do the Java, Python, Go, Rust, .NET, Swift and TypeScript documentation and lint rules that tools run by default. The industry disagrees on several points, and each card rests on a sourced separating condition. Exceptions versus error values is settled by the language's and the codebase's convention. Crash early versus keep running is settled by whether the state is a broken invariant or an expected failure. A catch-all is settled by whether it sits at an outermost isolation point. Exceptions as control flow ships only in its narrow form, throwing and catching inside one routine, and the no-null rule ships only for collections. Four disputes have no openable separating condition and stay pending: log-and-rethrow versus handling once; in-band null or sentinel returns; expected outcomes as exceptions (Python's EAFP); and a last-resort handler versus not recovering panics. No primary paper could be opened. Research statements are relayed through IEEE abstract mirrors, neverworkintheory.org and The Morning Paper.

## Formulation layer

The canon agrees on a small core: never swallow an error silently (97 Things 'Don't Ignore that Error!', Code Complete §8.4, Effective Java Item 77, Google Java §6.2 and SEG ch. 8, PEP 20, Go style's 'Handle errors'). It also agrees that an exception should carry the context of the failure and sit at the caller's level of abstraction, keeping the cause (CC §8.4, Clean Code ch. 7, Effective Java Items 73/75, PEP 8 chaining, Go %w wrapping, Java Throwable). It agrees that a catch should be specific and small, or sit at one outermost isolation point (PEP 8, Google pyguide, C++ Core Guidelines E.17, APOSD exception aggregation, 97 Things thing_21/28). Opened directly: the 97 Things essays, Software Engineering at Google ch. 8 (through abseil/abseil.github.io raw), the Google Java/Python/C++/TS/Go guides, Uber Go, Effective Go, the Go FAQ, the Rust book ch. 9, PEP 8/20, the Python glossary and tutorial, and the C++ Core Guidelines section E. Code Complete, The Pragmatic Programmer, APOSD, Clean Code, Effective Java and TPoP could not be opened: their items are relayed through search snippets or through third-party reading notes on GitHub, and some are marked unfetched; SWEBOK §4.5 is relayed only in its V3.0 wiki wording. The aposd-vs-clean-code discussion contains no position on error handling. The canon disagrees on five points, and a rule on any of them must keep its precondition or name the language trait: (1) exceptions only for exceptional conditions (Effective Java, CC, PP 1st ed., C++ CG E.3, Fowler) versus Python's EAFP; (2) exceptions over return codes (Clean Code, Google TS) versus Go's error values, Rust's Result and Google's C++ ban; (3) crash early (PP, APOSD 'just crash', C++ CG E.26, Google Go best practices) versus Effective Go's 'let things continue to run', with APOSD's masking in the middle; (4) log and re-raise (Python tutorial, PEP 8 bare-except exception) versus 'handle each error once' (Uber, Google Go, PP 'catch and release is for fish'); (5) don't return null (Clean Code, Effective Java Item 54) versus TPoP returning NULL to fail gracefully, and Go's preference for an extra ok/error value over in-band sentinels.

## Reception layer

Tools agree on the core checks: an empty or swallowing catch, an over-broad catch, a rethrow that drops the cause, and an ignored error result are flagged by Error Prone, PMD, Checkstyle, ESLint, Pylint, Ruff, clippy, errcheck and go vet, and Sonar. Their defaults show where practice draws the line. Most of them let a commented empty catch through. BLE001 and the Google Python guide allow a catch-all that re-raises, logs the traceback, or sits at an isolation point, and OWASP recommends a global handler. Error Prone ships its cause-preservation check (UnusedException) disabled, and Ruff 0.16 (July 2026) turns on BLE001, E722, S110 and TRY203 by default but leaves B904 and TRY003 off. The contested ground is exceptions versus result values (.NET says 'DO NOT return error codes'; the Go FAQ, Google C++ and Joe Duffy say the opposite), checked exceptions (Hejlsberg against; Duffy, matklad and the 2024 Java JEP draft partly for), unwrap and panic in production after the November 2025 Cloudflare outage (Gallant, Hirsch and the Rust book defend panicking on a bug; critics and Uber's 'Don't Panic' push back), returning null (.NET allows it for common error cases; Hoare, the Google Go in-band-errors rule and PMD are against), and exceptions as control flow (Python's EAFP and Google Go's panic-inside-a-parser pattern against the .NET and PMD rules). Freshness check for 2024–2026: the Go team stopped all error-syntax proposals in June 2025 although error handling is still the top survey complaint; ESLint added preserve-caught-error to eslint:recommended on main; Swift 6 shipped typed throws but keeps untyped throws as the default. Papers, Hacker News, Lobsters and vendor blogs were reachable only through WebSearch snippets, and the session's search budget ran out before I could search for 2024–2025 studies of LLM-generated error handling or for the dry-python 'exceptions considered an anti-pattern' essay.

## Evidence layer

Evidence for ERR is strongest on two rules. Do not swallow errors, and do not catch an over-broad type and then over-react. Yuan et al. (OSDI 2014) found that 92% of catastrophic failures come from mishandled non-fatal errors, and 35% from trivial handler mistakes. Liu et al. (HotOS 2019, Azure) and Java mining studies (Kery, Nakshatri, Sena, de Pádua & Shang MSR 2018 and ICPC 2017) show the same patterns are widespread and in part tied to defects. The studies are mostly Java/C#, and their numbers show prevalence or correlation, not a measured effect of following a rule. Standards and official documentation back every candidate rule: CWE-390/252/396, SEI CERT ERR00-J, ERR04-J, ERR08-J and ERR33-C, OWASP ASVS V16.5, the SWEBOK section on error handling (a V3 transcription only), language documentation for Python, Go, Rust, Java, .NET, Swift and TypeScript, and lint rules that tools run (PMD, Error Prone, Ruff, ESLint, typescript-eslint, clippy, go vet, errcheck, Sonar). No paper could be opened directly: WebSearch was exhausted and publisher sites are blocked. Paper statements are therefore relayed through the IEEE abstracts mirrored in the CIRDC-Pro GitHub dataset, neverworkintheory.org abstract reproductions and The Morning Paper notes. For three papers nothing stating the claim was found: Kimura et al. 'Does return null matter?', Cabral & Marques ECOOP 2007 and Ebert et al. JSS 2015. Sources disagree on several rules. Python's EAFP idiom opposes 'no exceptions for control flow'. The Python tutorial's log-and-re-raise pattern opposes Uber's 'handle errors once' and Sonar S2139. The .NET guidelines ('DO NOT return error codes'; return null for common failures) oppose the Rust and Go result style and the no-null rules. Effective Go (libraries should avoid panic) and the Swift rationale's caveat for high-reliability systems qualify 'fail fast'. ASVS 16.5.4 and Google's Python guide allow a catch-all at an isolation or last-resort boundary. The Go blog advises against wrapping when that exposes implementation details.

2. **An error raised, returned or wrapped at a failure site names the operation that failed and the values that caused it, without repeating what a wrapped error already says or exposing secrets** — Put into the error the information that led to it: the operation, the offending operand (a file name, an index, an id) and the underlying cause, so that it is useful even when printed far from the call. Outside tests, examples and prototypes, a forced unwrap of a result or optional says in its message why it is expected to succeed. When wrapping, return the error as-is if there is nothing to add; otherwise add succinct context that the underlying error lacks, since an annotation that only says something failed adds nothing. Secrets such as keys and tokens stay out of the message, and an end user sees a generic message on an unexpected error; the information leak itself belongs to security hygiene, and the content of log lines to logging.
