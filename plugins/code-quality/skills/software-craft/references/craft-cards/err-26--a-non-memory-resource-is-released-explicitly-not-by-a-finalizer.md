# A non-memory resource is released by an explicit call or the scoped-release construct, never only by a finalizer, a cleaner or garbage collection, which may serve at most as a backstop

## Thesis
In a garbage-collected language, a non-memory resource — a file, a socket, a connection, a stream, a temporary file, a buffered writer — is released by an explicit call to its release operation, preferably through the language's scoped-release construct. A finalizer, a destructor hook the collector runs, a cleaner, a finalization-registry callback or a runtime cleanup attached to the owning object is never the only path by which that resource is closed, flushed, deleted or returned, and no code depends on one to do it. Such a cleanup serves at most as a backstop that acts only on an instance whose explicit release was never called, closing the forgotten resource or reporting the leak.

## Rationale
The collector frees memory that is no longer referenced; it cannot free a non-memory resource such as an open file descriptor or a database connection, and de-allocating or collecting the object that holds one is not sufficient to dispose of it, so failing to release the resource can lead to resource exhaustion. A cleanup tied to reachability runs at some arbitrary time after the program can no longer reach the object: it may be delayed for an arbitrarily long time after the object becomes unreachable, a runtime may run the cleanups of different objects in any order, none is guaranteed to run before the process exits, and one specification lets a conforming implementation skip a finalization callback for any reason or no reason. An unexpected reference, from a global or an exception traceback, may keep the object around longer than intended; an object that a coding error keeps reachable never has its finalizer invoked; and in one runtime a cycle that includes an object with a finalizer is not guaranteed to be collected, nor its finalizer to run. Even a runtime that collects most objects as soon as they become unreachable is not guaranteed to collect garbage containing circular references, and other implementations act differently, so its documentation says not to depend on immediate finalization and to close files explicitly. The delay costs the resource itself: code that deals with many open files or sockets may exhaust the system's descriptors when they are not returned promptly after use; an open file collected without being closed can leak its operating-system resource, and in a long-running process such leaks can eventually exhaust the file handles available; a file held open may prevent moving or deleting it; and not closing a resource explicitly can leave it open far longer than expected and cause severe issues at exit. An effect that has to happen is lost when the cleanup does not run: a buffer left for a finalizer to flush is not flushed at program exit, and a temporary file left to be deleted when its object is finalized is not guaranteed to be deleted. Closing files automatically through a finalizer is itself unreliable and may lead to resource exhaustion, and a runtime that tries to close a forgotten file handle this way tells its users not to rely on it, because the file may not be closed. A tool rule calls finalizers unpredictable, often dangerous and generally unnecessary, and a leak checker counts a resource as leaked whenever the program does not explicitly dispose of it. Because collection is not guaranteed to happen, an object that holds an external resource also provides an explicit way to release it, usually a close method, and programs are strongly recommended to call it; the scoped-release construct provides a convenient way to make that call and is the preferred one, and invoking a registered cleanup explicitly when the object is closed is that cleanup's most efficient use. Closing resources explicitly makes the program more deterministic and more reliable.

## Example
```go
bad:  func NewLog(f *os.File) *Log {
          l := &Log{f: f}
          runtime.SetFinalizer(l, func(l *Log) { l.f.Close() })
          return l
      }
good: func NewLog(f *os.File) *Log { return &Log{f: f} }
      func (l *Log) Close() error { return l.f.Close() }
```

## Limits
A cleanup kept as a backstop behind an explicit release operation passes: the release operation is what the code calls, and the collector-run cleanup acts only on an instance whose release was never called. Sources differ on what that backstop does. Runtime and library documentation show it closing the forgotten resource — a file object closing its descriptor when a program discards it without calling its close method, a cleaner running the cleaning action when close was not called, a file handle trying to close itself and emitting a process warning — while the example in the weak-reference proposal logs the leak rather than transparently closing the file, calling automatic closing unreliable. Either form passes, and neither replaces the explicit release. Some sources reject the backstop itself: one secure-coding rule forbids finalizers in new classes and one tool rule flags every finalizer method; this rule does not flag a backstop, and code held to those sources removes it. A finalizer that frees only memory the collector cannot reclaim, such as memory allocated by code written in another language, is outside the rule, provided it performs no work that requires immediate release. An empty finalizer that cannot be overridden, used to prevent a finalizer attack, releases nothing and is outside the rule. In the rare case where the scoped-release construct is infeasible, the code's documentation explains clearly how the resource's lifetime is managed, and the release is still an explicit call.

## Validator
Grep the added lines for a finalizer method, a destructor hook the collector runs, a cleaner or finalization-registry registration, and a runtime finalizer or cleanup registration. Open the file and read the registered callback or the hook's body. Skip it when it frees only memory the collector cannot reclaim, when it only logs or warns that a resource leaked, and when it is empty. When it closes, flushes, deletes or returns a non-memory resource — a file, socket, connection, stream, temporary file or buffered writer — find the owning type's explicit release operation: a close, dispose or release method, or its implementation of the language's scoped-release protocol, that performs the same release without the collector. Check that the operation exists, then trace the file's own uses of the type to the call that releases each instance; a use that drops an instance unreleased, or a comment or document stating that the collector or a finalizer will release it, leaves the release to the collector. Validator question: **Does an added finalizer, collector-run hook, cleaner or finalization callback close, flush, delete or return a non-memory resource whose owning type has no explicit release operation, or whose release the file's own code leaves to that callback?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: ERR-26`, severity major, `file`, `symbol`, `code` = the finalizer, hook or cleanup registration quoted verbatim from the diff, `fix` = an explicit release operation — a close or dispose method implementing the language's scoped-release protocol — that the resource's users call through the scoped-release construct, with the collector-run cleanup kept, if at all, only as a backstop that closes or reports an instance never released, in the file's language, `rationale` = the resource whose release waits on the collector and what is lost when the cleanup runs late or never: descriptors or connections held, a buffer not flushed, a temporary file not deleted).
