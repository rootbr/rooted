# Maintaining software-craft

What changes together when a card, a script, a prompt, a signal or a tier changes, and what to re-run. Paths are relative to the skill directory; `plugins/` paths from the repository root.

- A rule is one card in `references/craft-cards/`; adding or removing one means its card, its `references/craft-cards-provenance.md` line, its topic's research note under `research/software-craft/` (the "Cards derived" table), and a `references/craft-cards-taxonomy.md` value when a facet is new. Run `scripts/validate-craft-cards.py --provenance references/craft-cards-provenance.md --pending references/pending-evidence.md references/craft-cards` before committing; run the audit on every card, agent or SKILL.md change (repository Quality Gate).
- A rule with no openable evidence, or a contested rule with no sourced separating condition, lives in `references/pending-evidence.md` until one is found; it has no card and no id.
- A topic is re-researched, or a new one added, through `scripts/research-topic-workflow.js` with the topic's row from the design note's taxonomy as its arguments; `scripts/write-topic-result.py` writes the run's note, cards, provenance lines and pending entries, renumbering ids contiguously from the cards already in the tree, and merges several runs of one topic. A cut-short run continues from its journal through `scripts/research-continue.py`, whose bundles carry the finished stages as `resume_state`; the second fix round is the same script with `--round 2` over the journals of the first, carrying only the rules the skeptic sent back with `revise`, and `--closing-edit` ships a rule the last verdict sent back after the drafter applies that verdict's edits verbatim. A new topic is a new row in the design note's taxonomy table and a new entry in its deviations section.
- When the aggregation definitions, the schemas, the severity scale or the prompts change, change `scripts/craft-review-workflow.js` and `plugins/code-quality/agents/craft-finder.md` / `craft-verifier.md` in the same commit as SKILL.md §Aggregation and §Workflow; when the developer's procedure changes, `plugins/code-quality/agents/software-developer.md` and SKILL.md §Build change together.
- When a card's triggers, a structural signal, a threshold or the candidate list change, change `scripts/static-craft.py` (`SIGNALS`, `THRESHOLDS`, `CANDIDATE_RULE_IDS`), `scripts/cardlib.py` (`SIGNALS`), the design note's "Structural signals" table and `scripts/tests/test_static_craft.py` together, then re-run `scripts/tests/` and the fixture grading (`evals/grade.py`) in both modes of `evals/fixture/make-fixture.sh`.
- A new facet value (a `step`, an `applies_to` scope) is a `scripts/cardlib.py` constant, a `references/craft-cards-taxonomy.md` row and a `scripts/research-topic-workflow.js` enum in the same commit.
- Pin the tier models in `evals/evals.json`; re-run the fixture on every model change.
- A card the fixture seeds is a row in `evals/expected.json` and a seed plus a control in `evals/fixture/head/`; renaming the card's id renames the row.

## Deferring pairs (`DEFER_TO`)

A finding of the deferring rule drops when any owner listed for it flagged the same span. Keep this table and `scripts/craft-review-workflow.js` in step. The table is filled from the pairs the corpus reviewers find still overlapping after the series.

| Deferring rule | Owner(s) |
|--|--|
| DSN-44 (a unit or identifier is a distinct type, not a primitive) | API-10 (parameter types stop swaps and values outside a closed set): on a public operation's parameters the interface card owns the finding |
| DSN-47 (a fixed set of values is an enumeration, not a string or int) | API-10: on a public parameter that accepts a closed set the interface card owns the finding |
| DSN-66 (a private collection is returned as a copy or read-only view) | API-01 (a type invariant holds after every constructor and operation): where the type keeps an invariant, the accessor that leaks the mutable component is API-01's finding |
| CODE-73 (a multiway branch acts on or explains an unmatched value) | CODE-19 (a switch over an enum names every member or has a default): over an enumerated type the missing member is CODE-19's finding |
| CODE-74 (an if chain on one value and constants is preferably a switch) | CODE-13 (a key-to-value if chain is a lookup table): a chain whose every branch returns a value is CODE-13's finding |
| CODE-64 (an ambiguous construct carries a comment marking it intended) | CODE-75 (a switch case leaves the switch or marks its fall-through): an unmarked fall-through is CODE-75's finding |
| CHG-01 (a change presented as a refactoring alters no observable behaviour) | API-20 (changing the return value, raised errors, side effects or defaults of a published element is a breaking change): where the restructured routine is a published element, the altered behaviour is API-20's finding; CHG-01 keeps the non-published routines, the unedited callers and the order of side effects |
| TST-17 (a test body runs the same statements on every execution) | TST-25 (no assertion sits where the test can skip or catch it): a conditional branch that encloses an assertion is TST-25's finding; TST-46 (a property discards an unwanted input through the framework, never an early return counted as a pass): an early return in a property body is TST-46's finding; TST-17 keeps the branches and loops that choose setup or action statements |
| TST-25 (no assertion sits where the test can skip or catch it) | TST-46: an early return that skips a property's assertions on an unwanted generated input is TST-46's finding; TST-25 keeps the conditional branches, catch blocks and unawaited callbacks of example-based tests |
| CHG-12 (a change that alters behaviour restructures no code beyond small cleanups) | CHG-14 (code moved between files moves unchanged in its own change): where the restructuring is a move between files whose moved code the same change also edits, CHG-14 owns the finding; CHG-12 keeps renames, extractions and other restructurings inside a behaviour change |
| TST-24 (every test makes a complete assertion that can fail) | CHG-20 (snapshot and golden files are rewritten only by an explicit update mode): a stored value the gating run writes and then compares with itself is CHG-20's finding; TST-24 keeps the self-comparisons and incomplete assertions of ordinary tests |
| CHG-21 (a change rewrites only the stored entries its intended behaviour change explains) | CHG-05 (a pure refactoring leaves every existing test's expected results in place): where the change is presented as a refactoring, a re-recorded snapshot or golden entry is CHG-05's finding; CHG-21 keeps changes that intend a behaviour change and re-record more than it explains |
| TST-18 (a failing test's report names the test and its case) | CHG-24 (a test that records several external snapshots names each for its content): a snapshot named by a number is CHG-24's finding; TST-18 keeps test, subtest and row names |
| CHG-25 (an element renamed, moved, re-signed or removed without every use updated keeps the old form working) | API-22 (removing, renaming or changing a published element in place breaks its callers, so the new form is added beside the old one): on a published element the interface card owns the finding; CHG-25 keeps elements whose every caller is in the repository |
| CHG-17 (every change builds and passes on its own) | CHG-25: a rename, move or removal that leaves uses to later changes is CHG-25's finding, whose fix keeps the old form beside the new; CHG-17 keeps every other break a later commit is left to fix |
| API-31 (a deprecated element is implemented by calling its replacement) | CHG-26 (the old name kept for a migrated type is an alias of the new type): an old type name kept as a copy, wrapper or subclass is CHG-26's finding; API-31 keeps deprecated routines that copy their replacement's logic |
| DSN-15 (a forwarding wrapper type is added only to hide, restrict or adapt) | CHG-26: a wrapper that stands in for a migrated type's old name is CHG-26's finding; DSN-15 keeps wrappers added for their own sake |
| CHG-15 (a change holds one logical change) | CHG-29 (a tool-generated change holds only the edits its rewrite requires): hand edits, dependency updates or reformatting inside a tool-generated change are CHG-29's finding; CHG-15 keeps independent fixes and features that share a hand-written change |
| CHG-08 (an unreferenced private declaration is removed) | CHG-30 (a migration's old path is deleted once no use remains): an unused alias, forwarder or replaced implementation left by a migration is CHG-30's finding; CHG-08 keeps other dead private declarations |
| CHG-33 (code added beside debt meets the same bar as code added to clean code) | CODE-59 (added code meets the style guide, then its file's layout): where the repeated smell is a form the style guide requires, CODE-59 owns the finding; DSN-21 (a repeated block or routine body is written once): re-implemented functionality that repeats a routine body is DSN-21's finding; CHG-33 keeps non-descriptive names and other repeated smells |
| CHG-34 (a shortcut that ships unresolved carries the project's debt marker referencing a tracked issue) | CODE-62 (a TODO or FIXME marker points to where its context is kept): a marker present but lacking its context pointer is CODE-62's finding; CHG-34 keeps admissions of temporariness that carry no marker at all |
| TST-13 (a test added for new behaviour fails without the change) | TST-24 (every test makes a complete assertion that can fail): where the new test cannot fail because an assertion compares a value with itself or stops at its subject, the assertion is TST-24's finding; TST-13 keeps the test whose assertions are complete but pass against the base |
