# Research note — Test doubles

Topic `test-doubles` of group E. Tests, domain `tests`, id prefix `TST`. Formulation locators: SEG13 (Software Engineering at Google ch. 13 'Test Doubles': seams, mocking frameworks, the impact on software development, fakes over stubs and interaction testing, 'prefer state testing over interaction testing'); the 97 Things essays on testing; PP 'Test to Code' where it treats mocks; CC22 where it treats stubs and scaffolding.

Software Engineering at Google ch. 13 sets out an order of preference. Use the real implementation first. If that is not possible, use a fake that the owning team writes and contract-tests. Use stubs only to put the system under test into the state the assertions need. Verify interactions only for state-changing calls, without overspecifying them. The chapter also keeps value objects real and wraps an API that has no fake. The mechanically checkable parts are backed independently by framework documentation and static-analysis rules: the Mockito javadoc and wiki, unittest.mock, pytest, RSpec, Jest, testdouble.js, Spock, Error Prone, SonarSource S5969 and S9137, eslint-plugin-jest, flake8-mock-spec, and the Go and Google Go style guides. Together they say to: build a double from the real type; keep value objects, data holders and collections real; use the fake the owner provides or respect a do-not-mock marker; remove stubs and doubles that the code under test never reaches; not verify a call the test also stubs; not overspecify interaction checks; not partially mock the unit under test or chain doubles that return doubles; keep stubs within the real contract. The industry disagrees in five places. (1) Classical versus mockist style: SEG, the Go guides, Beck, Fowler, Shore and Ousterhout against Freeman, Pryce and Martin. (2) Whether mocks should drive the creation of interfaces: Martin against Ousterhout, 'Our experiences differ'; Go Code Review Comments against the .NET seams guidance. (3) Whether to mock the application's own database: Martin against Khorikov. (4) For a third-party client, wrap it and mock the wrapper (Mockito wiki, GOOS) or connect the real client to a test server (Google Go style, Dodds). (5) Osherove's one-mock-per-test count, which Calçado disputes. The research only describes practice. Spadini et al. (MSR 2017, EMSE 2019) find that developers mock infrastructure and prefer not to mock domain classes or library data holders; that they call keeping a mock compatible with the real class hard; that 51% of mock changes are forced by production changes; and that domain objects show no clear trend (36% mocked). Xiao et al. 2024 find that 61.1% of mocked objects are library classes, which runs against 'don't mock types you don't own' as practice but measures no harm. Zhu et al. 2025 find that mock assertions add checks state assertions cannot make. Fazzini et al. 2022 find that doubles introduce smells and mistakes. Hora and Robbes 2026 find that coding agents add mocks more often than other contributors. No controlled study compares state testing with interaction testing, and none measures the effect of any mocking rule on defects. The twelve cards therefore rest on documentation and tool rules, with the research as rationale and the disputes carried as separating conditions or held as pending.

## Formulation layer

The layer rests on Software Engineering at Google ch. 13 'Test Doubles', fetched in full from the abseil/abseil.github.io repository. It adds the ch. 12 passage on interaction tests, the ch. 14 passage on unfaithful doubles, and framework and style-guide documentation opened from GitHub: Mockito javadoc and wiki, unittest.mock, pytest, Jest, Go CodeReviewComments, the Google Go style guide, Error Prone, SonarSource S5969 and eslint-plugin-jest. These sources agree on a clear order of preference. Use the real implementation first. If that is not possible, use a fake that the owning team writes and contract-tests. Use stubs only to reach a state the assertions depend on. Verify interactions only for state-changing calls, without overspecifying them. Never mock value objects, and wrap third-party types instead of mocking them. Several sources could only be reached through WebSearch summaries, so those items are relayed: GOOS (ch. 8, 20, 24), Mock Roles not Objects, Endo-testing, Meszaros's taxonomy, Fowler, Osherove, Khorikov, Seemann, Martin's 'When to Mock' and the Google TotT posts. Code Complete ch. 22 could not be opened, and neither could the part of PP Topic 41 that deals with mocks; both are paraphrased from memory and marked unfetched. The main disagreement in the canon is classical versus mockist style. SEG, the Go guides and Ousterhout prefer real objects and state testing and reject interfaces invented for mocking; Freeman/Pryce, and Martin in the aposd-vs-clean-code discussion, hold that mocks drive the discovery of interfaces. There are two smaller disputes. Martin mocks at the database boundary, while Khorikov says not to mock managed dependencies such as the application database. Osherove's one-mock-per-test rule is disputed by Calçado.

## Reception layer

Tool rules and framework documentation largely agree on a small set of mechanically checkable positions. Error Prone blocks mocks of types marked @DoNotMock and warns on mocked AutoValue data classes, on stubbed checked exceptions that the real method cannot throw, and on mocks that are never passed to the code under test. flake8-mock-spec, the cpython unittest.mock docs (autospec, the unsafe= assert-typo guard) and oslotest (autospec on by default) push for doubles specced to the real interface. eslint-plugin-jest no-untyped-mock-factory does the same through the type checker, and Ruff PGH005 catches mock assertions that silently pass. The framework docs (Mockito javadoc and wiki, testdouble.js) and Google's SWE book ch. 13 also agree on four points: verifying a stubbed query is redundant, overusing verifyNoMoreInteractions over-specifies a test, value objects should be real instances, and fakes need contract tests. Several positions are contested by name. Mocking at all is disputed: Beck, Fowler, Shore, DHH and Google's 2024 TotT argue against it, while Freeman defends mocks as one tool among many. Mocking the database is disputed: Uncle Bob says mock it, Khorikov says it is a managed dependency and should not be mocked. The wrap-and-mock-the-adapter prescription (Mockito wiki, testdouble, Hynek) is disputed by Kent C. Dodds, who says don't mock your API client either. Osherove's one-mock-per-test rule is disputed by Calçado, and Seemann later reversed his own 'mocks for commands, stubs for queries' in favour of fakes. Blogs, HN threads and papers could only be relayed through search snippets; the web-search budget ran out before I could locate a GitHub source for the Test Smell Catalog. Two sources the design note treats as closed are openable: the Mockito wiki (raw.githubusercontent.com/wiki/mockito/mockito/...) and SEG13 itself (raw.githubusercontent.com/abseil/abseil.github.io/master/resources/swe-book/html/ch13.html). SEG13 contains no 'don't mock types you don't own' passage.

The research is descriptive: Spadini et al. None measures whether following a rule improves defect detection. The canon disagrees in three places. First, 'don't mock types you don't own' conflicts with practice: 61.1% (Apache) and 39.4% (GitHub) of mocked objects replace library classes, and Google Go style says not to wrap RPC clients and to use real transports instead. Second, whether domain objects get mocked shows no clear trend: 36% are mocked. Third, 'prefer state over interaction testing' has no controlled comparison, and Zhu et al. 2025 find that mock assertions add checks that plain assertions cannot make. Four sources could not be opened: the Pereira & Hora ICSME 2020 abstract, the Mostafa & Wang QSIC 2014 text (only its numbers, relayed through Xiao), the Arcuri et al.
