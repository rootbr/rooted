# A block of four or more lines or a routine body that repeats another to do the same thing is written once as a routine each place calls

## Thesis
When added code repeats a block found elsewhere in the change or in the repository, and the copies are meant to do the same thing, so that a fix or a change of behaviour in one would have to be made in the other, the block is written once as a routine that each place calls. A block counts from four lines, not counting blank lines, comments, documentation strings, imports and signatures. Copies that differ only in the values, names or types they operate on are one block: the routine takes the values as parameters, and the types as type parameters where the language has them. An added routine whose body of two or more lines is identical to another routine's body is the same defect at routine level: one routine calls the other, or both call one shared routine.

## Rationale
Copies of one piece of logic tax every later change: each fix or refactoring of the block has to be repeated at every copy, and the developer has to find every place in which to make it. A fix made in one copy can be forgotten in another, which leaves the weakness in that copy. Once the copies have been changed differently, duplicate-code detectors may no longer recognise them as duplicates, so keeping them in sync can no longer be left to a tool, and segments first meant to do the same thing can grow apart undetected. In a large-scale case study of commercial and open-source systems, inconsistent changes to clones were very frequent, and a significant number of faults were induced by such changes. In a controlled experiment with 61 novice programmers in a block-based language, duplication decreased the ease with which they modified the program. Two routines with identical bodies can instead be a slip in which one was meant to do something else; that is a fault to correct, not a copy to merge, and falls outside the rule. Merged into one routine that each place calls, a future change no longer has to be made in all locations, and construction guidance favours encapsulating reusable code fragments in well-structured libraries or components to avoid the problem of code clones. Detector defaults set the floor: one reports from four similar lines, another from five lines and 50 tokens, others from 100 or 150 tokens or from a token count the user must set, and an identical-routine check skips empty and one-line routines; the rule takes the four-line floor.

## Example
```rust
bad:  fn total(&self) -> u64 {
          let gross: u64 = self.lines.iter().map(|line| line.price * line.qty).sum();
          gross - self.discount }
      fn amount_due(&self) -> u64 { // copied from total(); keep in sync
          let gross: u64 = self.lines.iter().map(|line| line.price * line.qty).sum();
          gross - self.discount } // copy of total(): same steps as total()
good: fn total(&self) -> u64 { ... }
      fn amount_due(&self) -> u64 { self.total() }
```

## Limits
The rule turns on whether the copies are meant to do the same thing and so must change together; for code that may never change in the future, the duplication is not a problem. Cloning is often a principled engineering choice: in a case study of two medium-sized open-source systems, a web server and a spreadsheet application, as many as 71% of clones could be considered to have a positive impact on maintainability. Verbatim snippets and parameterized copies were the patterns most often judged harmful, and they are what the rule targets. Boilerplate, a copy replicated in order to be specialized, and a cross-cutting concern were judged mostly good when used with care, and for copies caused by platform variation or a language idiom, copying is often the right approach; such a copy is outside the rule. An experimental copy of a subsystem, used as a sandbox for a new feature and migrated back into the stable code as the feature matures, is outside the rule while the change says so. Between test cases, duplication is accepted where folding the cases into one table would make the row values dictate conditional behaviour inside the shared test body, since the extra clarity of the duplication is then necessary for readability. Copies below the floor are outside the rule: a block of fewer than four counted lines, unless it is a whole routine body of two or more lines identical to another routine's body, and a routine body of one line. Cloned code is not shown to be more defect-prone in general: in four medium to large open-source projects the great majority of bugs were not significantly associated with clones, and clones may be less defect-prone than non-cloned code, so the rule rests on the cost and the faults of changing copies inconsistently, not on a defect rate of copying. A project context that documents a copy as one of these accepted cases rejects the finding. A literal repeated in place, a comment that restates code, one decision encoded in both code and data, and the steps of extracting the routine are judged by their own rules. A small copy kept so that its module stays free of a dependency, which a stated dependency policy or a comment beside the copy naming the avoided package records, is outside the rule. A reference implementation or model that a test compares the unit with is meant to reach the same result by a simpler route, so it is not a copy to merge into the unit; an oracle that repeats the unit's code is the test's defect, and a call to the unit in its place would compare the code with itself.

## Validator
Read the hunk's duplicate-block signal and the added comments the triggers matched. For the signal, take the repeated run among the diff's added lines and locate both copies; for a comment that says code was copied, is a copy, does the same as other code or must be kept in sync, open the code it names; for an added routine, search the repository for a routine with the same body. Compare the copies: count their lines without blank lines, comments, documentation strings, imports and signatures, and note whether they differ only in values, names or types. Decide whether they are meant to do the same thing by asking whether a fix or a change of behaviour in one would have to be made in the other; read the comment, the names and documentation of the enclosing routines, and the callers of each copy. Skip boilerplate or a language idiom, a copy made to be specialized and diverge such as a per-platform variant, a cross-cutting concern, an experimental copy the change states will be migrated back, code the project context states will not change, duplication between test cases that one shared table would turn into conditional behaviour, and a copy the project context documents as accepted. Validator question: **Does the change add a block of four or more counted lines that repeats another block, identical or differing only in values, names or types, or a routine whose body of two or more lines is identical to another routine's, where the copies are meant to do the same thing so that a change to one would be needed in the other?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-21`, severity major, `file`, `symbol`, `code` = the first line of the added repeated block, or the added routine's signature, quoted verbatim from the diff, `fix` = one routine holding the block that takes as parameters the values, names or types the copies differ in, with each copy replaced by a call to it, or the duplicate routine's body replaced by a call to the other routine, in the file's language, `rationale` = the file and symbol of the other copy and the change that would have to be made in both).
