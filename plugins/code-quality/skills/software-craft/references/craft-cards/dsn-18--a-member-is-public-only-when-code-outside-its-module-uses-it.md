# A routine, method or type is public only when code outside its module uses it or a library documents it, and an interface declared for a consumer lists only the methods it calls

## Thesis
Each routine, method, type and interface takes the narrowest visibility that still reaches every caller. It is public or exported only when code outside its module — the class, file, module or package whose boundary the visibility marks — uses it, or when it belongs to the documented public interface of a library. Where the entity is meant to be reachable elsewhere in its package but not outside it, public would make it reachable from outside the package, and the language offers a package-wide visibility, it takes that visibility instead of public. A helper, type or interface used only inside its own module stays non-public. An interface type that code declares to describe what it depends on lists only the methods that code calls.

## Rationale
Restricting the visibility of properties, methods and entire types helps keep code decoupled, and every exported type adds to the cognitive load of the reader. A public member is one that unrelated clients are expected to use, with a commitment to avoid backwards-incompatible changes, and compatibility guarantees apply only to public interfaces; a non-public member carries no guarantee that it will not change or even be removed. Exporting an interface likewise commits the module to maintaining it for external callers. Making a member public later is easier than making a public member non-public, so a member in doubt starts non-public. Where an entity is meant for the rest of its package and no further and public would reach beyond the package, a package-wide visibility keeps it inside and states that intent more clearly than public. An interface should capture the minimum essentials of an abstraction, and a component all the important characteristics of an abstraction and nothing more; the larger an interface, the harder it is to implement and to write code that takes advantage of it, so the consumer that declares an interface puts in it only the methods it actually uses.

## Example
```rust
bad:  pub fn total(items: &[Item]) -> u64 { items.iter().map(price_of).sum() }
      pub fn price_of(item: &Item) -> u64 { ... }
good: pub fn total(items: &[Item]) -> u64 { items.iter().map(price_of).sum() }
      fn price_of(item: &Item) -> u64 { ... }
```

## Limits
A library's documented public interface counts as used though no caller in the repository calls it: public members are those unrelated clients are expected to use, documented interfaces are public unless the documentation declares them provisional or internal, and an undocumented interface is assumed internal. An entity that a test runner finds by its name, such as a test routine collected by its name prefix, counts as used from outside as well. A class designed for inheritance has a third category besides public and internal, the members meant for its subclasses, and decides explicitly which members belong to each; that subclass interface is outside the rule. The visibility clauses also leave alone members whose visibility the language sets or requires rather than the author, such as the items of a public trait, the variants of a public enumeration, and a method that implements an interface method or overrides an inherited one, which cannot take weaker access than the method it implements; which methods an interface declared for a consumer lists stays under the interface clause. Exporting an interface from the module that implements it often makes sense when the interface is itself the product (a common protocol that many different implementations must follow, or a generated service contract), when many consumers would otherwise each define an identical copy, or to resolve a circular dependency. An entity marked public inside an enclosing module that is itself non-public already reaches no further than its package, and which spelling it takes there is contested: one compiler lint recommends the package-wide visibility there to state that intent, another lint calls the package-wide visibility misleading there because the enclosing module already confines the entity, and asks for public; the package-wide clause leaves that case alone, and the non-public clause still applies when every caller sits inside the entity's own module. Fields and other representation details, and whether a member may be widened only so that its tests can reach it, are outside the rule. A member that was public before the change and stays public is outside the finding, since narrowing a public member is harder than widening a non-public one and the public member carries a commitment to avoid backwards-incompatible changes. A project context that declares which members form a module's public interface rejects the finding for those members.

## Validator
Grep the hunk's added lines for a declaration that makes a routine, method, type or interface public or exported — a public or export modifier, a class member declared with no access modifier where class members are public by default, a capitalized name where capitalization exports, a name without the leading underscore where that prefix marks privacy, an entry added to an export list — and for an added interface, trait or protocol declaration or a method added to one. Read the hunk's removed lines and skip a declaration that was public before the change and stays public. For each declaration the change makes public, search the repository for its uses. Count a use from outside its module: another class, file, module or package that calls or names it, a public re-export, a routine, field or type used outside the module whose signature names it as a parameter, return or field type, outside code that calls it through an interface it implements, a framework, runtime or test runner the code registers it with, annotates it for or hands it to as an entry point, or that finds it by its name, such as a test, benchmark or example routine a test runner collects by its name prefix. Uses from inside the module do not count; skip an entity whose only outside uses are in test code. Skip the entity when its module is a library whose documentation or export list declares it part of the public interface, when it belongs to the interface a class designed for inheritance offers its subclasses, or when the language sets or requires its visibility, as for a method that implements an interface method or overrides an inherited one; this skip ends only the visibility check, and a method the hunk adds to an interface still goes to the interface check. Where the language offers a package-wide visibility and every module enclosing the entity is public, check whether every caller sits inside the unit that visibility covers; a caller that the visibility does not reach sits outside it even when the build tool counts both in one package. For an added interface type, or an interface the hunk adds a method to, decide whether it is the product — a protocol for many implementations, a generated contract, one shared definition many consumers use, or a cycle breaker — or declared to describe what its consumer depends on; for the latter, list the methods the consumer calls through it. Validator question: **Does the change make a routine, method, type or interface public although only code inside its module, or only inside the unit a package-wide visibility covers where the language offers one and public reaches beyond that unit, uses it and no library documents it, or declare for a consumer an interface method that the consumer never calls?** Yes → flag.

## Finding output
When the validator answers yes, the finder emits one finding (`rule_id: DSN-18`, severity minor, `file`, `symbol`, `code` = the added declaration line that makes the entity public, or the added interface method no consumer calls, verbatim from the diff, `fix` = the same declaration with the narrowest visibility that reaches its callers, or the interface without the uncalled methods, in the file's language, `rationale` = where the search found the entity's callers, all inside its module or package, or which methods the consumer calls through the interface).
